# DOS2: касание в консольном (`_c`) UI — план (15.11.2026, ветка `dos2-tc`)

Решение хозяина 15.11 (заменяет «переносим UI с iPad», `TOUCH_UI_PLAN.md`): iPad-фильмы на телефоне выглядят криво, `characterCreation_t`
сломан (не на весь экран, имена-заглушки «grindcore002», ничего не меняется). **`_t` по умолчанию не ставим.** Изучаем, *как* iPad делает
касание (что и чем тапается), и делаем то же в нашем консольном UI — как в D3 / TL2 / PoE: прямые нажатия на элементы UI и тапы по миру.
Геймпад работает всегда. main = `main.raw` update v786432 (build 4979b200); на телефоне из этого документа ничего не запускалось.

## 0. Главное

1. **В консольных фильмах уже есть свой код мыши.** Это остаток PC-игры в режиме контроллера, а не тач Switch (движок Switch тачскрин не читает:
   в символах и строках `main` нет `TouchScreen`, сырья `nx_touch_*` не существует). `tools/dos2_abc.py` + разбор слушателей (таблица в §2):
   `bottomBar_c` — слоты хотбара (`Slot::onClick` → EI `SlotPressed`, долгое удержание → `startDragging`, тап по панели/мимо — раскрыть/свернуть),
   `msgBox_c` — подсказки-кнопки (`MOUSE_DOWN` → EI `ButtonPressed`), `contextMenu_c` — пункты, `partyInventory_c` / `equipmentPanel_c` /
   `statsPanel_c` / `craftPanel_c` / `waypoints_c` / `dialog_c` / `containerInventory` / `statusConsole` / `playerInfo` — ячейки, вкладки, кнопки.
   Имена EI `SlotPressed`, `startDragging`, `cellInteraction`, `itemClick` есть строками в `main` Switch — классы движка их понимают.
   **Значит основная работа — не писать касание заново, а довести мышь до этих фильмов и убрать две помехи** (п. 2 и 3).
2. **Помеха 1: клик мыши = «принять».** На телефоне левый клик доходит до консольного фильма ещё и как событие `IE UIAccept` (A геймпада; это
   показало главное меню, оттуда 700-мс защита в `mainMenu_d`). С открытым фильтром мыши тап *в любом месте* консольного меню = A на
   выбранном пункте. Лекарство общее и уже написано: `tools/dos2_hint_touch.py` оборачивает `onEventUp` / `onEventDown` документ-класса —
   `IE UIAccept` в течение 400 мс после события мыши сцены глотается. Фильм с этой обёрткой = `<имя>_d.swf`.
3. **Помеха 2: фильтр мыши один на всех** (байт `[mgr+0x170]`, `hle_dos2_touch.c` KBM): открыт — мышь получают все слушатели (весь HUD и
   мир), закрыт — никто. Поэтому фильмы включаем партиями и следим, что под модальным окном нижний фильм не реагирует (эксперимент E1).
4. **Жесты iPad** (из `events` 56 `_t`-фильмов и `touchscreen_1.json`): тап = действие; двойной тап = использовать/надеть (инвентарь, торговля,
   контейнер, путевые точки); короткое долгое нажатие = подсказка (tooltip); долгое = контекстное меню / начать перетаскивание; два пальца =
   прокрутка списков; щипок = зум камеры / карты. У нас мышь уже даёт: тап = клик, долгое = правый клик (контекст), два пальца по
   вертикали = колесо, щипок = зум (правый стик). Двойной тап и «короткое долгое = подсказка» — добавить в `dt_step` (§3, шаг 6).
5. **Кнопки геймпада от фильма:** EI `dmPadBtn(код BTN_*)` → хост держит кнопку npad несколько опросов (`dm_dos2_touch_pad_pulse`, тот же путь,
   что у экранного пада). Этим сделаны тапы по подсказкам «(A) Выбрать (B) Назад»; этим же дёшево закрываются любые места, где у фильма нет
   своего кода мыши (вкладки LB/RB, «Взять всё» и т. п.).

## 1. Что сделано в этой ветке (быстрые победы, всё под `DM_DOS2_TOUCHUI=1`)

| что | как | выключатель |
|---|---|---|
| по умолчанию только главное меню D | `k_def` = 0x48 / 0x57 → `mainMenu_d`; все `_t` в `k_ipad` (`DM_DOS2_TOUCHUI_SET=ipad` или `DM_DOS2_TOUCHUI_MAP`) | `DM_DOS2_TOUCHUI_DENY=48,57` |
| фильтр мыши следует за окнами | `dm_dos2_touchui_gate()`: вне игры открыт, **кроме** случая, когда на экране консольное меню без тач-кода (`k_block`: msgBox, saveLoad, options, mods, gameMenu, characterCreation, serverlist) — там тап ничего не делает (иначе был бы A); в игре — только при модальном тач-окне | `DM_DOS2_TOUCH_KBM=1` (всегда открыт) |
| «нажмите A» / заставка / загрузка | фильтр открыт, клик = `IE UIAccept` = A: тап в любом месте | — |
| Назад (жест / клавиша) = B | `DmActivity.backPressed` / `dispatchKeyEvent` → `nativePadKey(PAD_DEVICE, K_B)` на 110 мс; активность не закрывается; при открытом меню паузы / редакторе раскладки Назад закрывает их; меню паузы открывается кнопкой ⚙ пада | `DM_DOS2_TOUCHUI_BACK=0` |
| тап по подсказке кнопки = эта кнопка | `tools/dos2_hint_touch.py`: общий класс `LS_Classes.controllerBtnHint::setHintIcon(код, …)` обёрнут, нажатие+отпускание на подсказке (иконка + подпись) → EI `dmPadBtn(код)`; в паке по умолчанию — в `mainMenu_d`; A нажимается через 750 мс (мимо защит «тап ≠ принять»), остальные сразу | `DM_DOS2_TOUCHUI_PADBTN=0`, пак `--no-hints` |
| EI-перехват по умолчанию | при `DM_DOS2_TOUCHUI` и незаданном `DM_DOS2_TOUCHUI_EI` ставится только слив EI (`main+0xd25d90`) для обработчиков хоста, без журнала | `DM_DOS2_TOUCHUI_EI=0` |
| набор «hints» (не по умолчанию) | `msgBox_d` (только защита: его подсказки уже кнопки), `saveLoad_d`, `optionsSettings_d`, `mods_d`, `characterCreation_d`, `tutorialBox_d` (защита + подсказки) | `DM_DOS2_TOUCHUI_SET=hints` + пак `hints` |

Пак по умолчанию: `python -I tools/dos2_touchui_pak.py console` → `TouchUI.pak` 2 243 683 Б (один `mainMenu_d.swf`, iPad-файлов нет).

Проверка на телефоне (env `DM_DOS2_TOUCHUI=1`, пак `console` в `<romfs>/Data`):
1. Лог: `[touchui] set: main menu D only`, `[ei] console touch: ExternalInterface drain ... (on)`, `[touch] console touch: ExternalInterface "dmPadBtn"`.
2. Заставка «нажмите A»: тап в любом месте → меню. Пункты меню — тапом (как в 2u).
3. Подсказки внизу главного меню: тап по «(B) …» → то же, что B; по «(A) …» → A примерно через секунду. Лог `[touch] pad button 0x2 pressed for the player (hint tap, BTN code 1)`.
4. Жест «Назад» в настройках / сохранениях / сообщении → как B; приложение не закрывается; лог `[java] back: pad B`. ⚙ открывает меню паузы, в нём «Назад» его закрывает.
5. Открыть «Настройки» / окно сообщения: строка `[touch] DM_DOS2_TOUCH_KBM=2: [mgr+0x170] -> 0 (CLOSED: a console menu without touch code ...)`, тап по экрану ничего не выбирает; после закрытия — `-> 1 (OPEN: a touch window ...)`.
6. Если подсказки в главном меню пропали или меню сломалось — пак `console --no-hints` (байт в байт фильм 2u) и сообщить.

**Почему TU-07 не переключил HUD (лог tu07):** `[hud] ... create-all main+0x10c4580 / destroy-all hooked`, затем
`【红】[touch] main+0x10c4580 differs (the player UI manager's create / destroy): DM_DOS2_TOUCH_LIVE not applied`. `dm_dos2_touchui_hud_install`
ставит прыжок на пролог `0x10c4580` раньше, чем `dm_dos2_touch_install` сверяет те же слова → LIVE выключился, `dt_live_switch` не вызывался
ни разу (и KBM=2 в игре закрыт). Порядок установки, не движок. Не чиним: `_t`-HUD больше не цель.

## 3. Порядок (по пользе)

1. **E1 + хотбар и портреты в игре** (1 прогон, сборка не нужна): env `DM_DOS2_TOUCHUI=1 DM_DOS2_TOUCH_KBM=1` (фильтр открыт всегда; страж
   подсказки стоит с tu03). Проверить: тап по слоту хотбара (ждём EI `SlotPressed` — навык выбран), по портрету (выбор персонажа), по кнопке
   «конец хода»; что даёт тап по миру (`Action1` ← `mouse:left` привязан — идёт ли персонаж?); и E1: окно сообщения поверх главного меню —
   реагирует ли пункт меню *под* окном. С `DM_DOS2_TOUCHUI_EI=1` в логе видно каждое EI. От ответа зависит всё остальное:
   тап = `IE UIAccept` в игре тоже → нужен `bottomBar_d` (Ф) и правило фильтра «в игре открыт, когда нет `k_block`».
2. **Набор `hints` по умолчанию** (msgBox, сохранения, настройки, моды, создание персонажа, обучение): после E1 — перенести `k_hint` в `k_def`,
   пак `hints` (8.3 МиБ). Даёт: подсказки-кнопки везде в меню, тап не «принимает» случайно.
3. **`bottomBar_d` + `playerInfo` + `statusConsole` + `contextMenu_c` + `containerInventory`** (Ф, свой код мыши): хотбар, портреты, конец
   хода, контекстное меню, лут — основной игровой цикл без пада.
4. **Пауза и msgBox геометрией** (Г, общий класс с главным меню), затем диалог (ответы тапом).
5. **Мир: палец = движение** (§4, шаг W1), затем тап по объекту.
6. **Жесты хоста**: двойной тап (второй клик ≤ 300 мс → `FlashLeftMouse` дважды: фильмы с `DOUBLE_CLICK` поймут сами), «короткое долгое» =
   подсказка, перетаскивание списков одним пальцем = колесо.
7. Инвентарь / экипировка / навыки / характеристики / ремесло (Ф + П), торговля и журнал (Г), создание персонажа (Г).

## 4. Мир: как выбрать цель тапом

Что известно (статика, `DOS2_PORT.md` «Касание как мышь»): пикинг экран→мир `0x1388d10` (вызов из `0x109b004`) и `0x1389ad0` (из `0x1258608`)
получает курсор **аргументом** — это PC-путь мыши, он в сборке есть; `Action1` ← `mouse:left`, `ContextMenu` ← `mouse:right` привязаны в
`Default/inputconfig.json`, но слушатели мира в режиме контроллера (байт `main+0x2bb8918` = 1, 670 читателей) клик мыши, судя по прогонам,
не исполняют. В режиме контроллера игра целится иначе: вне боя — движение стиком, A берёт ближайший подсвеченный объект; в бою и для
навыков — свободный курсор контроллера в мире, который двигает левый стик.

Шаги:
- **W1 (первый, без разбора движка, ≈1.5 ч + прогон):** касание вне пада и вне окон, удержанное дольше 150 мс или сдвинутое = виртуальный
  левый стик: вектор от центра экрана (персонаж под камерой) к пальцу → `dm_dos2_touch_pad_pump` дополняется осями (`hle_hid.c fill`).
  Движение стиком в DOS2 идёт относительно камеры, поэтому «палец правее-выше персонажа = идти туда» точно без пикинга. Короткий тап у
  объекта: идём к точке, по отпусканию — A (взять подсвеченное). Это уровень TL2 «tap world». Выключатель `DM_DOS2_TOUCH_WALK`.
- **W2 (разбор, ≈3 ч):** найти, где ветка мира отбрасывает `Action1` в режиме контроллера: читатели байта режима среди вызывающих `0x109b004`
  / `0x1258608`. Вариант «PC-пикинг только на клик»: байт режима = 0 на время обработки одной записи `mouse:left` (точка — `dt_drain`,
  тот же поток), курсор `[main+0x2bb88e8]` уже пишется. Риск: UI на этот кадр считает режим клавиатурным (как `DM_DOS2_TOUCHUI_PCWIN=2`).
- **W3:** в бою — курсор контроллера: найти его позицию в мире (слушатель левого стика в бою; не разобрано) и ставить её результатом
  `0x1388d10(экранная точка)`, затем A. Тогда тап = «навык сюда» / «идти сюда» с предпросмотром пути, как у iPad.
- Камера: щипок = зум (есть), два пальца по горизонтали = поворот (правый стик X, тем же способом, что зум) — 0.5 ч.

## 6. Ветка `dos2-tc2` (15.11): адресная мышь, «тап ≠ A» в движке, мир — шаги 2–4 без ожидания телефона

### Что нашлось в движке
- Раздача ввода UI: `UIManager::OnInputEvent 0xae83e0` идёт по списку объектов `[uimgr+0xf8]` **сверху вниз, два прохода**, на каждый объект —
  `0xaea7b0(uimgr, объект, событие, проход, x4, x5 = &взято)`. Проход 1 обрабатывает только объекты «забираю весь ввод»
  (`флаг 0x200 & видим` или захват клавиатуры `+0xe5`) и возвращает 1 → обход кончается: **под видимым окном с флагом 0x200 никто не
  получает ни одного события, мышь тоже**. Это штатная модальность движка и статический ответ на E1 для окон с 0x200 (настройки из главного
  меню: флаги 0x1e21). Проход 2: каждый объект получает событие (vt+0xa8 → FlashPlayer → Iggy), ответ пишется в `[x5]` (`0xaea8d4`);
  видимый объект ниже взявшего получает «не твоё» (vt+0xb0), движение мыши ему не передаётся вовсе.
- Где `mouse:left` становится `UIAccept` — **по-прежнему не найдено** (привязка `UIAccept` только `c:a`; `FlashPlayer::OnInputEvent 0xd23420`
  зовёт `onEventDown/Up` только для id из `events` фильма). Поэтому защита стоит в общей точке раздачи и не зависит от источника, а
  `DM_DBG=1` печатает каждое событие ввода, пришедшее в UI в течение 600 мс после тапа (`[route] within 600 ms of a tap the UI gets input
  event …`) — один прогон назовёт источник.

## 7. Ветка `dos2-world` (15.11): клик по миру как на PC, `DM_DOS2_TOUCH_WORLD=3`

Повод — прогон tw1 (pack 2w, `DM_DOS2_TOUCH_WORLD=1`): палец-стик работает, тап по сундуку работает (иногда мимо), **тап по полу «иди сюда» не

### Что нашлось (и почему пол не работал)
- Прежняя запись «пикинг `0x1388d10` / `0x1389ad0`» неверна: это контекстное меню у курсора (`0x109af30` → `0x13889e0`), не выбор цели в мире.
- Клик по миру на PC — это `ecl::InputController` (vtable `main+0x29c9738`; `CharacterInputController` `main+0x29c9860` — те же методы):
  - `OnInputEvent 0xe13830(ic, событие)`: id события `+0` (`Action1` = 4 ← `mouse:left`), нажато `+0x20`. Сначала событие получает каждая
    задача персонажа (`task vt+0x88`), при нажатии `Action1` запоминается курсор `[main+0x2bb88e8]` (`ic+0x24`). **Проверки байта режима
    здесь нет** — клик мыши в режиме контроллера исполняется.
  - `Update 0xe11f40(ic, время)`: каждый кадр выбирает задачу-предпросмотр (`0xe14dd0`: приоритет / `CanEnter` каждой задачи по данным
    пикинга), ведёт её предпросмотр (путь, цена ОД, курсор). `ic+0x58` — идущая задача, `ic+0x60` — предпросмотр.
  - Задачи (0x19 штук) создаёт `0xe15b80`; базовый ctor `0xe19860(task, тип, приоритет)`: тип `task+0x10`, флаги `+0x14`.
- **Разница PC / контроллер — в пикинге.** `PlayerPickingHelper`: покадровое обновление `0xfab260(helper)` читает байт режима
  (`0xfab2c4`): контроллер → выбор ближайшего объекта падом (`0x10a0d30`, экранной точки нет вовсе), PC → луч из экранной точки.
  Постановка луча `0xfa9f50(helper)` читает режим ещё раз (`0xfa9fdc`): PC → `[helper+0xe4]` (float2) = курсор UI (`0xfaa494`),
  контроллер → проекция мировой точки выбора. Итог: `[helper+0x80]` объект под точкой (хэндл; тип в старших битах: персонаж
  `[main+0x32bb8d8]`, предмет `[main+0x32bba10]`), `+0x70` персонаж, `+0x78` предмет, `+0x08` мировая точка.
- Значит, в tw1 клик мыши доходил, но действовал на то, что **выбрал пад** (сундук рядом — да, точка на полу — никогда).

### Что сделано (`dm/host/hle_dos2_touch_world.c` + правки в `hle_dos2_touch.c`, 13 участков `TW_*` сверяются пословно)
| часть | как |
|---|---|
| пикинг от пальца | перехват `0xfab260` (заглушка без C: аргументы могут быть в векторных регистрах) и `0xfa9f50`: пока «окно» открыто, функция идёт с байтом режима 0 и на выходе получает прежнее значение → луч из курсора UI = из точки пальца |
| предпросмотр | перехват `Update 0xe11f40`: в окне — с байтом режима 0 → задача-предпросмотр PC (обводка цели, путь, цена ОД — то, что PC показывает под мышью) |
| клик | перехват `OnInputEvent 0xe13830`: `Action1` от **пробного** нажатия (вопрос к UI «кто взял») и от любого жеста по UI до контроллера ввода не доходит (ответ «не обработано»); `Action1` от **клика по миру** идёт с байтом режима 0 = клик PC: пол → идти, NPC → говорить, враг → атака, предмет → взять / использовать, контейнер → открыть |
| жест | палец на мире: окно открыто сразу (курсор = палец, цель подсвечивается до отпускания). Отпустил, не сдвинув и раньше 300 мс → клик: левое нажатие через 2 опроса, отпускание ещё через 2, окно держится ещё 300 мс. Удержание > 300 мс или сдвиг → левый стик, как при `=1` (окно закрывается) |
| два тапа | `DM_DOS2_TOUCH_WORLD_CONFIRM=1`: первый тап только показывает предпросмотр (окно 4 с), второй тап в ту же точку (≤ 7 % высоты) исполняет — как на iPad. По умолчанию один тап = действие (PC второго клика не требует) |

Выключатели: `DM_DOS2_TOUCH_WORLD=3` — новый путь; `=1` — прежний (стик + «дойти и A»), он же запасной: при несовпадении любого участка `=3`
сам работает как `=1` (красная строка `[world] main+… differs`). `DM_DOS2_TOUCH_WORLD_HOLD_MS` (порог стика, 300 при `=3`, 150 при `=1`),
`_WORLD_SETTLE` (опросов до нажатия, 2), `_WORLD_AFTER_MS` (окно после клика, 300), `_WORLD_CONFIRM=1`. Пад и `_c`-HUD не трогаются:
вне окна байт режима не меняется.

### Ветка `dos2-world2` (15.11): пол в обычном режиме контроллера — разбор tw2 и починка

**Что показал tw2** (pack 2y, `DM_DOS2_TOUCHUI=1 DM_DOS2_TOUCH_WORLD=3`): пикинг от пальца верный, `Action1` доходит. По объектам работает и в
обычном режиме (`CHARACTER` → задача 4, диалог; `ITEM` → задача 6, взять / открыть). По полу — только в режиме «огонька» (свободный курсор):

| режим | под пальцем | предпросмотр (`ic+0x60`) | что вышло |
|---|---|---|---|
| обычный (камера на персонаже) | пол, `walkable` | **тип 25** (флаги `0x614`), 28 кликов из 28 | клик уходит задаче 25, персонаж стоит |
| «огонёк» | пол | тип 0 (флаги `0x8`), 9 кликов | `running task type 0` — бежит в точку |

**Так задумано? Да — в режиме контроллера; на iPad тап по полу ходит в обычной камере.** Доказательства:
- Switch / контроллер: `[ic+0x50]` бит 0 — копия байта режима: его ставит `0xe11c20(ic, режим)`, все 6 вызовов передают `[main+0x2bb8918]`
  (конструкторы контроллеров ввода `0xe11b50 / 0xe158f4 / 0xe42114`, смена режима `0x109b280 / 0x143b1a8`). В режиме контроллера персонажа
  двигает **только стик** (задача 25); задача «идти в точку» включается лишь там, где у пада есть курсор: «огонёк» (свободный курсор,
  `0x109b500`), подготовленное умение, бой. То есть огонёк — это и есть курсорный режим пада, а не обход.
- iPad (`work/ipa`, `PlayerProfiles/iOS/Eoc/touchscreen_1.json`): **`Action1 ← touchscr:tap`** — тап рождает то же событие `Action1` (id 4),
  что `mouse:left` на PC; отдельного «идти» у тача нет (`CameraMove ← pan`, `CameraRotate ← rotate`, `CameraZoom ← pinch`,
  `ContextMenu / AreaPickup ← longpress`, `ShowWorldTooltips ← tap2f`). В бинарнике iPad тот же код задач: приоритет «идти в точку»
  `0x101503a1c…` с той же проверкой (`ldr x0,[x8,#0x128]; ldrb w9,[x0,#0x50]; tbz …; bl 0x101996d90`), задача стика `0x1017eb638`.
  iPad работает не в режиме контроллера (тач-UI `_t`, `setTouchScreenMode`), флаг `[ic+0x50]` = 0 → задача 0 берёт точку **без огонька, в
  обычной камере**. Значит наша цель = поведение iPad: тап по полу → идти, при этом пад и `_c`-HUD остаются (режим контроллера не снимаем).

**Причина** (статически, capstone по `main.raw`, 4979b200):
- Тип 25 — задача **движения стиком** пада: создаётся отдельно от 25 PC-задач в `0xe16b04` (vtable `main+0x29cb7c8`), приоритет `0xe40cb0`.
- Задача «идти в точку» (тип 0, vtable `main+0x29c9a30`) в функции приоритета `0xe18790` (`0xe187c8`): если контроллер ввода — «падовый»
  (`[ic+0x50]` бит 0) и `0xe151f0(ic)` вернула 0 → приоритет 0, задача отказывается. У задачи 25 проверка зеркальная (`0xe40cd8`): тот же
  флаг и `0xe151f0 == 0` → приоритет 10, предпросмотр её.
- `0xe151f0(ic)` = «этот контроллер сейчас целится курсором»: 1 в режиме огонька (`0x109b500`), при подготовленном умении, в бою,
  при `[ic+0x20]`; иначе 0. Байт режима (`main+0x2bb8918`) она **не читает** — поэтому окно с байтом 0 на неё не действовало.
- Больше ни у одной задачи такой проверки нет (поиск `[char+0x128] → [ic+0x50]` по всему коду задач: только эти две + две функции задачи 25),
  поэтому разговор / предмет / атака от режима не зависят.
- Запуск задачи (`0xe14760`, следующий `Update` после отпускания) снова спрашивает ту же функцию приоритета (`vt+0x50` → `vt+0x48`), значит
  ответ нужен и в `Update` после клика. Идущая задача (обновление `0xe1ab50`, «продолжать» `0xe18ea0`) такой проверки не имеет; задача 25
  прерывает её, только когда стик отклонён (`[task+0x79]`), — то есть стик по-прежнему отменяет ходьбу.
- Проверенные и отброшенные гипотезы задания: `0xe186d0` (`CanEnter` задачи 0) в окне идёт с байтом режима 0 и не мешает; «нулевой стик
  отменяет задачу каждый кадр» — нет (флаг `0x100` у задачи 25 не стоит, см. `0xe12498`); «задача создаётся и гибнет при закрытии окна» —
  нет, она не становилась даже предпросмотром.

**Починка** (`hle_dos2_touch_world.c`, 4 новых участка `TW_CURSOR / TW_MOVE_GATE / TW_PAD_GATE / TW_PAD_CTOR`, сверяются пословно):
перехват `0xe151f0`: пока он вызван **изнутри наших PC-вызовов** (перехваченный `Update` в окне, `OnInputEvent` клика; только тот же поток),
ответ 1 — ровно состояние режима огонька, в котором клик в tw2 работал. В объекты игры ничего не пишется, вне окна функция идёт как есть.
- `DM_DOS2_TOUCH_WORLD_FLOOR=0` — без этого перехвата (как pack 2y).
- `DM_DOS2_TOUCH_WORLD_KEEP=1` — запасной: ответ 1 держится и в каждом `Update` кликнутого контроллера, пока идёт начатая кликом задача 0
  (включать, только если персонаж делает шаг и встаёт при закрытии окна; по статике не нужно).
- `DM_DOS2_TOUCH_WORLD=3` теперь **по умолчанию при `DM_DOS2_TOUCHUI=1`** (ставит `hle_dos2_touchui.c`, строка `[touchui] DM_DOS2_TOUCH_WORLD=3 (set
  here…)`); `=0` — мир без тача, `=1` — прежний путь. При несовпадении любого участка `=3` сам работает как `=1`.

**Не доказано:** на телефоне не запускалось. Тип 2 (флаги `0x3010`, 5 кликов по полу в 12:21:29–42 — предпросмотр вместо 0) по имени не
разобран. Атака по врагу в обычном режиме в tw2 не пробовалась (по статике проверки режима у неё нет). Байт режима — прежний риск.

## 15. Ветка `dos2-touch5` (16.11): тап ставит перемещаемый предмет, камера — свайпом одного пальца

Хозяин: (1) «Действия… → Переместить»: предмет едет за курсором, поставить можно только A пада, тап по полу уводит персонажа и отменяет
перемещение; (2) крутить камеру свайпом одного пальца, двухпальцевое вращение оставить.

### Что нашлось (статика, capstone по `main.raw` 4979b200)
- **Режим перемещения = задача контроллера ввода типа 10** («переместить предмет», создаётся `0xe323d0`, vtable `main+0x29ca7a8`):
  её функция курсора `0xe32b20` ставит курсор **`CursorItemMove`** (id 19, `0xe32cd8`; таблица курсоров `0xc06244`, имена `main+0x32c2cf0`),
  её `OnInputEvent` `0xe32d00` ставит предмет на **отпускании Action1** и отменяет на `ActionCancel` (0xdf). Пад A = `Action1 <- c:a`
  (`Engine.pak PlayerProfiles/Default/inputconfig_controller.json`), вращение предмета — `RotateItemLeft/Right` (плечи, `WorldDragController`).
- Почему тап ломал: наш PC-клик шёл в `OnInputEvent` с байтом режима 0; после задачи 10 общий путь Action1 (`0xe13a20` → `0xe14760`) на
  отпускании запускал задачу предпросмотра — «идти в точку» (окно ховера + FLOOR), ходьба отменяла перемещение.
- Как хост узнаёт режим дёшево: в уже стоящем перехвате `Update` контроллера (`0xe11f40`, `tw_update`) два чтения — тип задачи `[[ic+0x58]+0x10]`.
  Тип 10 → отметка времени; «режим включён» = отметка моложе 300 мс. Своего опроса нет, читается только то, что игра и так вызывает.
- Другие режимы «выбрать точку» (умение, бросок): не тип 10, их тап остаётся прежним PC-кликом (IN-12: у задач умения нет проверки флага пада,
  по `0xe151f0` они «целятся курсором»). Статически не менялись; в DM_DBG у каждой строки `PC click` теперь есть `running task type N`, чтобы
  на телефоне увидеть тип задачи в режиме умения / броска.

### Что сделано
- `dm/host/hle_dos2_touch_world.c` (пункт 4 шапки): `tw_update` отмечает контроллер с задачей 10; его `Update` в окне ховера идёт как есть
  (байт режима не трогается, FLOOR не отвечает) — пикинг (`0xfab260` / `0xfa9f50`, его читает задача перемещения) по-прежнему от пальца.
  Экспорт: `dm_dos2_touch_world_placing()`, `dm_dos2_touch_world_kinds_clear()`, `dm_dos2_touch_world_run_type()` (лог).
- `dm/host/hle_dos2_touch.c` (pass 9): мировой тап в режиме перемещения = `dt_place_tap`: курсор в точку пальца, окно ховера держится 700 мс,
  через `g_w3_settle` (2) опроса — импульс пада **A** (`dm_dos2_touch_pad_pulse`), затем окно ещё 500 мс (A читается npad ≈ 120 мс). Своего Action1 нет;
  метки «наше нажатие» (`g_kind_*`) перед A сбрасываются, чтобы A пада прошёл `tw_input` нетронутым. `DM_DOS2_TOUCH_PLACE=0` — как раньше (PC-клик).
- Свайп: палец мира, сдвинувшийся дальше 2,5 % высоты **раньше** времени удержания (`g_world_hold_ms`, 300 мс при `DM_DOS2_TOUCH_WORLD=3`) — свайп:
  горизонталь → правый стик x шагами по 2 % высоты (140 мс полного стика на шаг, знак как у двухпальцевого, `DM_DOS2_TOUCH_ROT_SWAP=1` меняет),
  без ходьбы и без тапа, окно ховера закрывается. Удержание без движения — как раньше (ходьба за пальцем на полу, «Действия…» на объекте);
  движение после начала ходьбы — ходьба. Сдвиг во время пробы UI (палец поднят до ответа) — тоже не тап. `DM_DOS2_TOUCH_SWIPE_ROT=0` — старое правило.
  Двухпальцевое вращение / щипок не трогали. Java (`D3PadView`) без изменений: в хост уходят только касания вне кнопок и зон стиков, поэтому правила
  стиков (короткий тап по зоне = L3 / R3) прежние; стик хоста пишется в npad, только когда стик настоящего пада в покое — пад не отключается.
- Правила — чистые функции `dm/host/hle_dos2_touch_gesture.h`; тест `dm/host/tests/dos2_touch_gesture_test.c` (тап / удержание / свайп, шаги,
  знак, тип 10): `PASS`.

### Строки лога (`DM_DBG=1` для подробных; без него — первые 20 строк режима и тапов)
- старт: `[world] item placement (Actions... -> Move): while a controller runs the item-move task (type 10) ...`,
  `[touch] pass 9: one-finger swipe on the world ... = camera rotation ON ...; item placement taps ON ...`;
- вход в режим: `[world] item placement mode: input controller 0x… runs the item-move task (type 10, cursor ItemMove) ...`;
- тап в режиме: `[touch] world tap at X,Y: PLACE (item placement mode ...)`, затем `[touch] placement tap: pad A pressed N ms after the tap ...`
  и `[touch] pad button 0x1 pressed for the player (placement tap: pad A at the finger) ...`;
- свайп: `[touch] world: one-finger SWIPE from X,Y (moved N px within M ms): camera rotation, no walk / tap`;
- сводка раз в 600 опросов: `[touch] world (...): taps N, stick holds N, swipes N, placement taps N, ...`.

### Шаги на телефоне (APK ветки, env `DM_DBG=1`; `grep "\[world\] item placement\|PLACE\|placement tap\|SWIPE\|running task type"`)
1. Долгое нажатие на бочку / ящик → «Действия…» → «Переместить». В логе — `item placement mode ... type 10`. Если строки нет, а предмет едет за
   курсором — прислать строки `PC click ... running task type N` тапа в этом режиме (значит, режим — другая задача: поменять `DT_TASK_ITEMMOVE`).
2. Тапнуть по полу в стороне: предмет встаёт в точку тапа, персонаж не идёт (`PLACE` → `pad A pressed`). Если встал не туда, а в точку прежнего
   курсора пада — задача берёт не пикинг, а свой селектор: прислать лог (следующий шаг — двигать селектор стиком к пальцу).
3. B (отмена) и плечи (поворот) пада в режиме — как раньше; тап, когда режим кончился, — обычная ходьба / действие.
4. Подготовить умение (хотбар) и тапнуть цель; бросок — то же: должно работать как до ветки; записать `running task type` из строки `PC click`.
5. Свайп одним пальцем по миру влево / вправо — камера вращается, персонаж стоит, тапа нет (`SWIPE`). Медленно: палец положить, подержать > 0,3 с,
   повести — ходьба за пальцем, как раньше. Короткий тап — ходьба / действие; долгое нажатие на объекте — «Действия…».
6. Два пальца: вращение и щипок — как раньше. Зоны стиков: короткий тап = L3 / R3, стик появляется как раньше. Подключённый пад работает.

### Риски
- Тип 10 как «режим перемещения» доказан по коду PC-задачи (курсор ItemMove, установка на отпускании Action1), что консольное «Переместить»
  запускает именно её — не проверено на экране (п. 1 проверяет).
- Точка установки: по статике задача читает пикинг игрока (`[main+0x2bbb298]` по игроку, `0xe34ab0`), который в окне ховера идёт от пальца; если в
  режиме пада она берёт селектор — предмет встанет у старого курсора (п. 2).

### 15.2 Ветка `dos2-place` (16.11, после `touch6.log`): тап двигает селектор пада, а не PC-пикинг

**Что показал `touch6.log`** (13:23:19.84–20.33): режим найден (`preview 10`), но при касании открылось окно PC-пикинга → предпросмотр 10 → 0
(«идти в точку»), A пада нажат при предпросмотре 0, затем PC-луч от пальца попал в сам перемещаемый бочонок (`ITEM 0x5c000010000028d`,
`flags 0x101`) → предпросмотр / задача 6 («использовать предмет»). То есть точка была верная, а PC-пикинг ломал сам режим.

**Откуда режим пада берёт точку** (capstone по `main.raw`):
- обновление пикинга `0xfab260` в режиме контроллера: близостный выбор `0x10a0d30` по **селектору** игрока `[helper+0x108]` (объект 0x50 байт,
  vtable `main+0x29e1fa0`, создаётся в конструкторе помощника `0xfa8e7c`; позиция в мире `+0x30` float3; селектор сам пишет её в `0x10a0cbc`,
  `0x10a115c`, `0x10a1818`), затем хвостовой вызов `0xfa9f50`: в режиме контроллера он проецирует `[[helper+0x108]+0x30]` на экран
  (`0x911120` → `helper+0xe4`) и бросает луч оттуда (`0x9113a0`); точка ходьбы `helper+0x50` — то, куда тянется предмет
  (`WorldDragController` `0x1407dc0` → `0x1409da0`, чтение `+0x50` в `0x140aa20`). Левый стик двигает селектор (`SelectorMove*`).
- Приоритет задачи 10 (`0xe32690`) от пикинга не зависит: 150, пока у игрока есть перетаскиваемый предмет (карта `[main+0x2bbb298]`, ручка `+0x10`);
  отказ — при «устройство мышь» и байте режима 0. Отпускание Action1 (A пада) ставит предмет в `0xe32d00` → `0xe34ab0`.
- На PC тот же путь с лучом от курсора; бочонок под лучом PC-пикинг не исключает (наш лог), поэтому окно ховера для этого режима не годится.

**Что сделано** (`hle_dos2_touch_world.c` пункт 5, `hle_dos2_touch.c dt_place_tap / dt_w3_poll / dt_w3_sync`):
- в режиме перемещения окно PC-пикинга не открывается вообще (палец на мире, проба UI, тап), `Update` и пикинг идут как у пада;
- тап: курсор UI в точку пальца, **два** вызова `0xfa9f50` с байтом режима 0 (первый может вернуть прошлый кадр) — земля под пальцем
  (`+0x50`, если ходима, иначе `+0x08`); дальше перед каждым `0xfa9f50` этого помощника позиция селектора = эта точка — для игры это
  «игрок довёл курсор стиком сюда»: выбор, предпросмотр 10, призрак предмета;
- A пада — когда точка известна, селектор продержан ≥ 3 вызова и предпросмотр снова 10 (или через 0,5 с); после A селектор держится 400 мс;
  не нашлось точки / за 1,2 с не дождались — ничего не нажимаем (строка в логе).
- `DM_DOS2_TOUCH_PLACE=1` (умолч.) — так; `=2` — прежний путь 15 (PC-пикинг + A) для A/B; `=0` — выкл.

**Строки лога (`DM_DBG=1`)** — `grep "\[world\] placement\|placement mode\|PLACE\|placement tap"`:
- до тапа: `[world] placement mode, pad target: selector X Y Z, walk point …` (куда сейчас целится пад, при смене) и
  `[world] placement mode: input controller …: preview task type 10 …`;
- тап: `[touch] world tap at x,y: PLACE (item placement mode, preview task type 10): the pad's selector to the ground under the finger …`,
  `[world] placement: ray from the finger x,y px -> ground X Y Z (walk point; first call gave …; under it …)`;
- после: `[world] placement: selector … A B C -> X Y Z (the finger's point), projected to x,y px, walk point now … (hold #N)` — проекция должна
  совпасть с пальцем, точка ходьбы — с землёй под ним; затем `[touch] placement tap: pad A pressed N ms after the tap (preview task type 10)`,
  `placement mode: … preview / running` — предмет встал, задачи 6 / 0 после A быть не должно.

**Шаги на телефоне** (APK ветки, env как обычно + `DM_DBG=1`):
1. Бочонок: долгое нажатие → «Действия…» → «Переместить». Не трогая стик, тапнуть по полу в 2–3 м от бочонка — он встаёт туда, персонаж не идёт.
2. Ещё раз: «Переместить», тапнуть по полу далеко (на краю экрана) — встаёт в точку или так далеко, как пускает игра.
3. «Переместить», сдвинуть курсор стиком пада, поставить A пада — как раньше (пад не сломан).
4. После установки: обычный тап по полу — ходьба, по сундуку — открыть (режим кончился, PC-клики как прежде).
Прислать `grep` выше по каждому тапу.

**Риски.** Селектор может пересчитывать позицию из своего объекта выбора каждый кадр — тогда держим её только на время вызова луча, близостный
выбор того кадра видит старую точку (в логе `selector A B C -> …` с прыгающим `A B C`). Если игра ограничивает дальность селектора — далёкий тап
встанет ближе. Если `projected to` не равно пальцу — проекция селектора не по `+0x30` (тогда прислать лог: следующий шаг — подменять `helper+0xe4`).

### 15.3 После `place1.log` (16.11, пак 4o): мышиная проба отменяла перемещение

**Что в логе.** Режим найден (`preview 10`), но сразу после касания (проба UI: `Action1 down / up … kept away`) предпросмотр 10 → 25 / 8,
затем задача 10 → −1 — перемещение отменено ещё до тапа. Лучевая проба от пальца не пришла ни разу (`given up … point not known`): с отменой
режима выбор точки пада (`0xfab260 → 0xfa9f50`) больше не вызывается — строки `placement mode, pad target` идут, только пока режим жив и
стик двигает селектор (`selector 49.39 … → 52.98 …`, т.е. селектор — верная цель). `walk point 0.00 … (before this frame's ray)` — норма:
`0xfab260` обнуляет результаты до хвостового вызова луча. Значит, виновата сама мышиная запись левой кнопки: в этом режиме клик мыши = отмена
(тот же эффект был в `touch6.log`, где мы списали его на окно PC-пикинга).

**Исправление** (`hle_dos2_touch.c dt_step`): в режиме перемещения (`DM_DOS2_TOUCH_PLACE=1`) палец вне живых прямоугольников HUD
(`dt_hud_hit`, те же `dmHudRects`) — сразу мировой, **без единой мышиной записи**: ни пробы, ни движения, только курсор UI (`dt_cursor`) для
лучевой пробы. Тап → `dt_place_tap` (тоже только курсор) → проба луча → селектор в точку → A пада; свайп правее 0.40 W — камера; удержание —
ничего (ни ходьбы, ни «Действий…»); ведение левее 0.40 W — левый стик (как стик пада: двигает селектор). Палец на HUD — прежний путь (проба UI).

**Строки:** `[touch] placement mode: finger at x,y is the world's without a mouse press`, затем `world tap … PLACE (… preview task type 10)` —
**тип должен остаться 10**, `[world] placement: ray from the finger … -> ground X Y Z`, `[world] placement: selector … -> X Y Z …, projected to x,y px`,
`[touch] placement tap: pad A pressed … (preview task type 10)`, и после — `placement mode: … running task type …` без отмены.
