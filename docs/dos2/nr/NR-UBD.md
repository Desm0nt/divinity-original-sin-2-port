# NR-UBD `DM_NR_UBD` — повторная привязка UBO direct draw не шлётся (ночь 18.11.2026, ветка `dos2-nrubd`)

Worktree `wt-nrubd`, ветка `dos2-nrubd` от `dos2-nr-all` c9eeb0d (с NR-09U `DM_NR_UBO` и NR-09S S3 `DM_NR_STATE=4`). Телефона не было
(adb не запускался): всё доказано на ПК — тестом против модели бэкенда, мутациями, структурным тестом, сборкой APK. **На устройстве не
исполнялось ни строчки.** Всё за `DM_NR_UBD`, умолчание 0.

## 0. Коротко
- **Что.** Аналог `NRDP_TEXF` NR-09R для блоков констант. Фаза 2 функции движка `0x925740` привязывает **каждый** блок шейдера на каждом
  draw, пересобран он или нет (NR-09U §1.1): блок, который не пересобирался, привязывается снова с тем же `{адрес, размер}`. Зеркало
  `nrub_mirror` (`dm/gfx/nr/nr_ubd.h`) знает, что таблица `state.ub[6][16]` бэкенда держит для **этой записи команд**; привязка взятого
  direct draw, чей (стадия, слот) уже держит ровно этот диапазон, при `=1` не шлётся (ни тело `BindUniformBuffer`, ни запись в тень NB-09,
  ни применение в `nbdraw::apply`, ни `++buf_gen`).
- **Где.** Одна строка в теле `nvnCommandBufferBindUniformBuffer` (после строки `NUB` NR-09U, до всего остального) — поэтому работает и с
  `DM_NR_UBO=0` (вызовы идут из функций движка через thunk в тело), и с `DM_NR_UBO=1` (вызовы модели NR-09U через тело в `nrd_job`).
- **Доказательство.** `nr_ubd_test.c`: 3 000 случайных программ (3 буфера команд, 2 потока, Begin / End, одиночные и пакетные привязки
  внутри и вне скобок draw / взятых draw, скобки проверки NB-10, вложенные handle) → модель бэкенда исполняет готовые handle **в любом
  порядке, с повторами, с вложенными вызовами, с чужими привязками между handle, со случайным начальным состоянием** дважды — все записи и
  без выкинутых привязок: **602 992 draw — таблицы равны, 6 827 выкинутых привязок проверены «как ложатся» — 0 плохих**; 6 мутаций зеркала —
  6 пойманы.
- **Выигрыш честно — маленький.** Форт Радость (play-1118): ≈ 4 000 вызовов `BindUniformBuffer` на кадр (≈ 1.96 на запись draw при 2.9
  привязок записи). Какая доля — повторы, без телефона не узнать (строка `=2` даст `would not send N %`). Оценка [м] при 25–60 % повторов
  (1 000–2 400 привязок / кадр): **поток игры −0.02…0.08 мс, транслятор −0.03…0.12 мс на Mi 14**; слабые ядра ×2–3. GPU — 0.
- **Копии в кольцо не убраны** (§5): доказать «никто не читает / не пишет старый диапазон по-другому» без полного разбора всех читателей полей
  блока нельзя. Добавлен только **счёт** этого случая (`DM_NR_UBD=2` + `DM_NR_UBO=1`), чтобы телефон сказал, стоит ли игра свеч.

## 1. Почему невыкинутая привязка равна выкинутой (аргумент TEXF для `state.ub`)
Писатели `state.ub` в бэкенде (`rg 'state\.ub'` по `dm/gfx/vulkan/engine`): `exec_bind_buf` (`OP_BIND_UBO`), `nbd_apply` (привязки
`OP_X_NB_DRAW`, всегда до его draw — у `nbdraw::apply` нет выхода до `nbd_apply`), слияние поста NB-18 (меняет два запасных слота и
возвращает их внутри одного draw), NR-SHCACHE (второе исполнение диапазона — с состояния, сохранённого в его начале, затем конечное
состояние назад), `DM_NB_ORDER / RELOC / MX` (исполнение кусков не по порядку / от ключевых кадров — с ними переключатель не включается, как
TEXF), сброс при старте устройства. Значит, для **одной записи одного буфера команд, которую пишет один поток**: после записанной привязки
(a, n) к (стадия, слот) и без более поздней привязки этого слота таблица держит (a, n), когда бэкенд исполняет любую более позднюю запись
этой записи — что бы ни шло до неё, сколько бы раз handle ни исполнялся, какие бы handle ни шли между в подаче.

Что ещё делает привязка в бэкенде и почему без неё то же:
- `++buf_gen[stage]` — счётчик «таблицы, может быть, менялись». Его читатели кэшируют **функции таблиц**: `driver_block` (банк 0 копирует
  `state.sb` и — для compute — `state.ub`), страж NB-11 `nb_desc_guard`, ключ ленивой оценки пула (`key` с номером draw), ключевые кадры
  NB-14 (выкл.). Мемо дескрипторов ключует UBO по `{адрес, размер}`, а не по `buf_gen`; **содержимое** UBO по `buf_gen` нигде не ключуется
  (изменения на месте — `memo_mod_gen` / `snapshot_invalidate`, NR-06 читает кольцо по адресу, NR-08 «по поколению» — только `tex_gen`). При
  равных таблицах все читатели видят одно и то же; несдвинутый счётчик лишь оставляет кэши годными (NB-11 чаще «reuse»).
- NB-12 `nb_ring_note` — пометка «диапазон кольца этой подачи»: ранняя привязка той же записи её уже сделала; без пометки — путь копии
  (медленнее, не неверно), а с NR-06 (умолчание) NB-12 до этого не доходит.
- Тап NB (`nbt_note(NBN_UBO)`) — только счётчик строки `[nb]`.

Чего зеркало не предполагает: через границу записи (сброс в `BeginRecording`), про другой буфер команд, после вложенного handle
(`CopyCommands / CallCommands` — забыть), после привязки другим потоком в отслеживаемый буфер (порядок неизвестен — забыть). Каждая привязка
UBO потока-владельца в отслеживаемую запись — в скобке draw или нет, `BindUniformBuffer` или `BindUniformBuffers` — обновляет таблицу.
Не шлётся только одиночная привязка внутри **обслуживаемого direct draw** (scope, ставит фронт NR-09R) и внутри скобки NB-09 (adopt: она
идёт в запись draw) без проверки NB-10 / `DM_NATIVE_DRAW` — ровно тот класс, который `=2` проверяет на бэкенде.

## 3. Переключатели (умолчание 0; игрокам не выдаются; `jni_android.c` и `xbg_vendor_policy.h` не тронуты — от GPU не зависит)
| | |
|---|---|
| `DM_NR_UBD` | **0** — ничего: поток команд байт в байт прежний; цена — загрузка + непринятый переход в 5 местах (`BindUniformBuffer`, `BindUniformBuffers`, `BeginRecording`, `CopyCommands`, `CallCommands`) и одна проверка `g_nrd_ubd` дважды на взятый draw. **1** — повторная привязка UBO взятого direct draw не шлётся. **2** — шлётся всё; те, что `=1` не послал бы, помечены в хвосте записи и сверяются бэкендом с `state.ub` в момент, когда ложатся (красные строки, первые 16, итоги раз в 10 с); с `DM_NR_UBO=1` ещё счёт «пересборка с теми же байтами» (§5). **3** — нет: `=1` шлёт те же записи минус привязки, которые ничего не меняют; отравлять нечего |

Нужно: `DM_NR_DIRECT=1` (с частью DRAW; она требует `DM_NR_DRAW=1` — хвост записи), т. е. умолчания DOS2. Иначе красная строка и выкл.
При `DM_NR_DIRECT=1` (TEXF=1) и `DM_NR_UBD=2` у записи с флагами UBO счёт «texture binds not sent» бэкенд-строки NR-09R для этой записи
не пишется (слово одно; фронтовая строка NR-09R считает его по-прежнему).

Строки (поток отчёта NR, раз в 10 с; вместе с `[nr] direct`):
- старт: `[nr] DM_NR_UBD=1 (NR-UBD): a BindUniformBuffer of a served direct draw whose stage / slot already holds that address and size … is not sent; the mirror resets at BeginRecording, forgets …`;
  бэкенд (`=2`): `[nr] DM_NR_UBD=2 (NR-UBD, backend): …`;
- `=1`: `[nr] ubd (DM_NR_UBD=1, NR-UBD, N frames): BindUniformBuffer calls of served direct draws X a frame, not sent Y (Z%: …); uniform binds of this thread into the tracked recording …; tables adopted …, forgotten …`;
- `=2`: `[nr] ubd check (DM_NR_UBD=2 …): … =1 would not send Y (Z%), flagged for the backend F, past bind 24 of their record P …`;
  бэкенд: **`[nr] ubd check (backend, DM_NR_UBD=2, last 10 s): N uniform binds =1 would not send compared with state.ub as they land, bad 0; totals: compared …, bad 0`**;
  красные `【红】[nr] ubd check: uniform bind i of n of an OP_X_NR_DRAW … but the backend's table holds …`;
  с `DM_NR_UBO=1`: `[nr] ubo + ubd (DM_NR_UBO=1, DM_NR_UBD=2): rebuilds of a block dirty again in the frame it was last rebuilt in D a frame, S of them (P%) with the shadow equal …`.

## 5. Копия тени в новый слот кольца — почему оставлена
Пересборка (`REBUILD`) идёт, если блок грязный (`+0x34`) **или** штамп ≠ кадру. Вторая причина — обязательная: раз в кадр каждый блок
получает свежий диапазон (кольцо 19.5 МБ переиспользуется по кадрам; старый диапазон прошлого кадра — не наш). Кандидат только первый
случай: грязный блок, уже пересобранный **в этом кадре**, тень которого равна байтам его прошлого диапазона. Привязать прошлый диапазон вместо
копии было бы равно, только если (1) байты прошлого диапазона не изменятся до исполнения GPU (кольцо пишут 20+ мест кода игры — каждое
в свой свежий диапазон, но писатель через `b+0x18` после копии, «правка константы на месте», не исключён без разбора **всех** читателей
полей блока, а их — каждое место, которое трогает структуру 0x40 Б), (2) никто не читает `b+0x10 / 0x18` иначе, чем для привязки (поля
остаются старыми — это то же, что «движок не пометил блок грязным», но и это надо доказать на всех местах), (3) пропущенный сдвиг головы ничего
не меняет у других писателей (их диапазоны сдвигаются; аллокатору это безразлично). Доказательства (1)–(2) на машинном коде нет и за ночь не
будет; выигрыш — атомики замка кольца (≈ 15 нс ПК) + копия 64–256 Б против `memcmp` тех же байт (≈ столько же) на пересборку **только
этого класса**, плюс меньше прироста кольца для зеркала NR-06 на Mali. Поэтому: **копия остаётся**, а `DM_NR_UBD=2` с `DM_NR_UBO=1`
считает класс (`nru_same_count`, только чтение, до записей пересборки). Если доля большая — следующий шаг: оракул NR-09U + xref-разбор
писателей `b+0x18`.

## 6. Ожидание (модель [м]; замер даст строка `=1` / `=2` и `[cpuprof] threads`)
Данные play-1118 (Форт, 150 окон): ≈ 1 900–2 160 direct draw / кадр, `[nb] draw apply` 2.9 привязки на запись, из них текстур ≈ 0.94 →
**UBO ≈ 1.96 на draw ≈ 4 000 / кадр**; `[nr] desc` — 4.0 блока кольца на draw (глобальные привязываются только при пересборке, раз в кадр);
`ns a direct draw`: блоки движка 541 / 625 / 733 нс (p25 / медиана / p75). Повторная доля неизвестна: фаза 2 перепривязывает блоки текущего
шейдера на каждом draw; повтор = тот же шейдер подряд и блок не грязный (материальные / статичные константы); блок объекта (матрицы)
грязный на каждом draw. Оценка 25–60 % → 1 000–2 400 невысланных привязок / кадр.

| [м] | Поток игры (`main`) | Транслятор | GPU |
|---|---|---|---|
| Mi 14 (X4 / A720), Форт | выкинутая: −(тап + тень NB-09 ≈ 25–35 нс; при `DM_NR_UBO=0` thunk / обёртка остаются) × 1 000–2 400; хук на каждой из 4 000: +5–10 нс → **−0.02…0.08 мс** | `nbdraw::apply` без привязки (≈ 30–50 нс, 165 нс на запись из 2.9) + меньше `buf_gen` → **−0.03…0.12 мс** | 0 (поток команд — те же draw с тем же состоянием) |
| Слабые ядра (A520 / A55 / A510; Helio, S7-класс) | ×2–3: −0.05…0.25 мс | ×2–3: −0.1…0.35 мс | 0 |
| Mali / PowerVR / Xclipse (zero-copy off, предел 8 UBO) | как строка CPU по ядрам SoC | то же + NR-06 зеркало кольца / NR-08 кортеж не меняются (диапазоны те же) | 0 |

Без телефона это потолок: шаг стоит на том, что строка `=2` покажет долю повторов. Если < 20 % — оставить выключенным (выигрыш ≈ цене хука).

## 7. Прогоны телефона (главный агент, по разрешению хозяина; бэкап `files/save`, keyguard снят, ≥ 60 с от загрузки)
Файлы на телефон: **только APK** (паков не нужно). Общее: умолчания сборки (DOS2-блок `jni_android.c`: NB / NR-09 / NR-09R `DM_NR_DIRECT=1` …) + `DM_NR_CPU=1`.
1. **R-UBD-a, сверка + доля:** `DM_NR_UBD=2`. Ждём `[nr] DM_NR_UBD=2 (NR-UBD): every BindUniformBuffer is sent …`, `[nr] DM_NR_UBD=2 (NR-UBD, backend) …`;
   каждые 10 с **`[nr] ubd check (backend, DM_NR_UBD=2 …): … bad 0; totals: compared N, bad 0`**, ни одной `【红】[nr] ubd check`;
   фронт: `=1 would not send Y (Z%)` — **Z = доля повторов**. Палуба 60 с + Форт у ворот 60 с.
2. **R-UBD-b, то же с моделью NR-09U:** `DM_NR_UBO=1 DM_NR_UBD=2` (после сверки NR-09U `=2`): те же `bad 0` + строка `[nr] ubo + ubd` — доля
   «пересборок с теми же байтами» (вопрос §5).
3. **R-UBD-c, включено, ABBA × 60 с в Форте:** A = умолчания, B = `DM_NR_UBD=1`. В B: `[nr] ubd (DM_NR_UBD=1 …): … not sent Y (Z%)`;
   `[nb] draw apply`: binds a record падает на Y / draws, `buf_gen … bumps a record` падает; `[cpuprof] threads` — `main` и `nvn-translate`
   мс / кадр; `[nr] direct, ns a direct draw` — `the engine's uniform blocks` чуть ниже; картинка та же.
4. (Mali, если будет) то же с `DM_GFX_ZEROCOPY=0 DM_GFX_SIM_GPU=ubdyn8` на Mi 14 — `[nr] buf` / `[nr] desc` без новых `bad`.
