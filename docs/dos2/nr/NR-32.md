# NR-32 `DM_NR_XLQ` — качество вывода транслятора Maxwell → SPIR-V: что на самом деле стоит циклов и что из этого можно снять

Ветка `dos2-nr32` (worktree `wt-nr32`, база `dos2-nr-all` debf665). Всё ниже — ПК, офлайн; телефон не трогал, ничего не ставил и не качал.

## 0. Итог
- **Сначала замер, потом код.** Пак игрока (12 329 бандлов, 6 192 FS, 6 132 VS), каждый модуль в том виде, в каком его компилирует Mali-телефон
  сегодня (после цепочки загрузки `NAN_MINMAX`+`NAN_SAT`, `LDC_FOLD`, `FORWARD_TEMPS`, `LDC_CANON`, `F2I_NOTRUNC`, NR-27 `UBOVEC`), счёт классов
  «мусора» по всему паку и цена каждого класса реальным компилятором Mali (`malioc` 2026.5, G52 / G57 / G715 / G720) на рабочем наборе Форт-Джоя
  из журнала хозяина 18.11 (веса — `est_ms` / вершины за кадр из `shader-heat.tsv`).
- **Фрагментные шейдеры: снимать нечего.** Всё, что перечислено в постановке (эмуляция флагов, лишние bitcast / конверсии, адресная арифметика,
  ветвления → select, мёртвые временные, CSE), вместе — это `spirv-opt -O` поверх телефонной цепочки: **−0.9 % (G57), +2.1 % (G52, дороже),
  −3.3 % (G715)** взвешенных циклов FS; у тяжёлых материалов (FlowingWater, Blood, Poison, Oil, Fire_Ground, Ocean) ±0–1 %. NaN-точные
  `NMin/NMax` против `FMin/FMax` — **ровно 0** (Mali делает maxNum сам). Защита координат текстур от NaN — −1 % (G57) / −4 % (G52), но она не
  точна (неточное снятие уже есть: `DM_GFX_TEXCOORD_NAN=0`, DOOM выигрыша не увидел). Фп16-эмуляции (`HADD2`…) в паке почти нет: 192
  `UnpackHalf2x16` в 48 FS. Причина та же, что в NR-25 / SH-21: компилятор Mali сам делает mem2reg / DCE / CSE / if-conversion; трёхкратное
  «раздутие» SPIR-V — это переменные-регистры Maxwell, которые драйвер снимает и без нас. Транслятор / стадию setup по этим классам **не
  меняю** — выигрыша нет (правило брифа).
- **Нашёлся класс, который компилятор снять не может: мёртвые varying.** Транслятор пишет все выходы атрибутов вершинной программы Maxwell
  (vec4 на Location), а DOS2 сочетает один VS с несколькими FS (G-buffer, depth pre-pass, тени, forward), которые читают малую часть:
  **36.9 % компонент, записываемых VS пака, не читает FS своей пары** (6 141 пара: `programs.tsv` + пары журнала Форт-Джоя; Форт-Джой отдельно — 39.6 %).
  `malioc` компилирует VS отдельно и держит все выходы вместе с их вычислением, а VS Форт-Джоя упираются как раз в load/store (запись
  varying). Сделан точный проход `xbg_spirv_vsout.cpp`: **на каждый пайплайн** VS без записей в компоненты, которых этот FS не читает.
- **Цена по `malioc` (весь пак: 5 687 различных пар «VS + маска FS»; Форт-Джой — взвешено вершинами за кадр):**

  | Mali-G715 | **−13.2 %** | **−11.8 %** (18.02 M → 15.90 M) | 598 → 447 | 142 |

  Рабочие регистры VS −4.6 % (G57), −2.0 % (G52), −5.4 % (G715) (прогон на 5 667 модулях до последней правки; та же картина). Всё снятое —
  load/store (запись varying) и арифметика, что их считала (bound = LS у всех VS).
- **Точность:** проверка структуры (`xbg_spirv_vsout_check`) — 0 отказов на всех парах пака; `spirv-val` vulkan1.1 — 0 отказов; интерпретатор

- На телефоне не запускалось. APK собран из этого дерева (§9).

## 3. Проход (`dm/gfx/vulkan/engine/xbg_spirv_vsout.{h,cpp}`, без Vulkan и окружения)
- `xbg_spirv_fs_input_mask(fs, &declared)` — какие компоненты (бит `4·location + component`, Location 0–15) FS **может** прочитать, с запасом:
  каждая ссылка на Input-переменную с Location засчитывает её целиком, кроме `OpAccessChain` с константными индексами (засчитывается выбранное:
  компонента vec, элемент массива, компонента элемента). Динамический индекс, `OpLoad` целиком, `Interpolate*`, любая неизвестная ссылка —
  целиком. Блок / структура / матрица / 64-бит / Location вне 0–15 → `XBG_VSOUT_ALL` (трим для этого пайплайна выключен). `declared` —
  все объявленные компоненты.
- `xbg_spirv_vs_output_mask(vs)` — что VS пишет.
- `xbg_spirv_vsout_trim(vs, keep, out, stats, declared)` — **удаляются только `OpStore`** в Location-выход (переменная целиком или одна компонента
  через `OpAccessChain` с константным индексом), все компоненты которого вне `keep`. Выход, который читается обратно, индексируется
  динамически или используется чем-то ещё, — «приколот», не трогается. Цепочки, оставшиеся без использования, удаляются; выход без единой
  ссылки уходит из интерфейса `OpEntryPoint` вместе с `OpDecorate` / `OpName` / `OpVariable`, **если FS его не объявляет** (иначе остаётся
  объявленным, просто не пишется — каждый объявленный вход FS сохраняет парный выход). Вычисления, питавшие удалённые записи, остаются —
  их снимает DCE драйвера (malioc: arith −16 % G57).
- **Почему точно:** любой компонент, который FS может прочитать, пишет та же инструкция, что и раньше; удалённые записи попадали в
  компоненты, которых FS не видит. Встроенные выходы (`gl_Position`, `PointSize`, `ClipDistance`) не трогаются. Порядок / значения остальных
  инструкций не меняются.
- `xbg_spirv_vsout_check(in, out, keep)` — независимая сверка: `out` = `in` минус инструкции, каждая из которых — `OpStore` в Location-выход вне
  `keep`, цепочка в такой выход без использования в `out`, или `OpVariable` / `OpDecorate` / `OpName` выхода без ссылок в `out`; интерфейс
  отличается только удалёнными выходами. Движок берёт модуль только после неё.
- Литералы, похожие на id (например ширина 32 у `OpTypeFloat`), в типах / константах не считаются ссылками; в остальных инструкциях любое
  совпадение слова с id считается ссылкой — это только «прикалывает» больше (консервативно).

## 4. Переключатель и встраивание (`xbg_game.cpp`)
| `DM_NR_XLQ` | что делает |
|---|---|
| 0 | выключено: маски не считаются, слова VS не хранятся ради него, блок в `draw` и сборка `#vo` в прогреве не выполняются — прежние модули |
| 1 | на каждый пайплайн VS + FS (в списке стадий нет тесселяции / GS): модуль VS без записей, которых этот FS не читает; проверка, потом модуль |
| 2 | трим считается, проверяется и считается в счётчиках; **используется старый модуль** |
| 3 | яд: снимается ещё и самая младшая читаемая Location (этот varying у FS превращается в мусор — видно, куда достаёт проход) |

- Маски считаются при загрузке шейдера (`load_shader`, из финальных слов после всех переписываний): FS — `vo_read` / `vo_decl` (у FS NR-04
  `DM_NR_SH` — `ALL`, не анализируется: его нативный модуль может читать иное), VS — `vo_written`; слова VS хранятся (`p->words`) при
  `vtx_retype_mode() || nr_xlq`.
- `vsout_module(vs, retype_code, base, read, decl)`: кеш по (код retype, read, decl) в `Shader::vo`; при retype-коде слова сначала проходят тот же
  `xbg_vertex_retype` (составление с `DM_GFX_VTX_RETYPE` / `vtxscaled`), потом трим. Ключ модуля / прогрева / pipeguard:
  `<vs>[#vi…]#vo<read16>_<decl16>`; `pgv2::bare` режет по `#`, так что баны и spv-хеши идут от базового шейдера, как у `#at` / `#vi`.
- Прогрев (`warm::load_module`) строит `#vo`-ключи (без `#vi`) только в режимах 1 / 3, после той же проверки. **Старые записи** (до обновления,
  простой ключ VS): `warm::build` для пары VS + FS собирает пайплайн с триммированным VS (`xlq_warm_module`) **только для кеша драйвера**
  (пайплайн уничтожается, в `ready` не попадает — байты записи называют старый модуль), чтобы первый же сеанс Mali-игрока после обновления не
  компилировал эти пайплайны в кадре.
- Лог: `NVN DM_NR_XLQ=N (env | family default; policy family … default …)`; `NVN xlq vs=<key>[#vi…] read=<hex> stores_dropped= outputs_dropped=
  words a -> b` (первые 16 и степени двойки); отказ — `NVN xlq vs=… refused: …` (первые 8), отказ проверки — `【红】NVN DM_NR_XLQ=… check: …`
  (первые 16); в блоке `NVN PERF` — `NVN PERF xlq mode= vs_variants= counted= stores_dropped= outputs_dropped= refused= check_bad= pipelines=
  cpu_us=` (`【红】`, пока `check_bad` ≠ 0); прогрев — `NVN xlq warm-up: N older records built with the trimmed vertex module`.
- Умолчание: `xbg_nr_xlq_default(gpu_policy)`; `DM_GFX_SIM_GPU=family-mali` включает его на Adreno-телефоне.

## 6. Ожидаемый выигрыш
- **Mali (слабый класс — G57 MC2 / G52 MC2, Helio G99 / G8x):** Форт-Джой ~1.5 M вершин за кадр; VS −2.2 M (G57) / −3.0 M (G52) циклов
  шейдерного ядра за кадр → при 2 ядрах ~1 ГГц **≈ −1.1 мс (G57) / −1.5 мс (G52) шейдерного времени кадра** [м], плюс полоса: на IDVS
  varying каждой видимой вершины пишутся в память и читаются FS — 37 % компонент меньше ≈ −15 Б на вершину, порядка −20 МБ за кадр
  (≈ −0.6 ГБ/с при 30 к/с) [м]. Тени (1536², 1.2 M вершин Base_PBR_ST_DEP / Tile / ATM_Wind) и prepass — самая большая доля: там FS читает
  0–2 компоненты.
- **Mali G715 / G720 (Dimensity 9200 / 9300, 11–12 ядер):** те же −10…−12 % VS, в мс ≈ −0.2 мс [м].
- **PowerVR / Maleoon:** не замерено (нет компилятора); тайловые — varying идут в parameter buffer; включено по умолчанию, т. к. проход не может
  добавить работы GPU (цена — модуль VS и пайплайн на новую пару, как у любой новой комбинации).
- **Adreno (Mi 14 Ultra), Xclipse:** 0 — выключено (Turnip: `nir_remove_unused_varyings` при линковке; AMD-компилятор Xclipse линкует пайплайн
  целиком).
- **Честная оговорка:** если драйвер Mali сам выбрасывает невостребованные выходы при создании пайплайна (malioc этого не умеет показать —
  он компилирует стадию отдельно), выигрыш на устройстве будет меньше вплоть до 0; цена тогда — только время создания модулей. Подтвердит
  только Mali-устройство (§11).

  ни повторного setup, ни правок общего vendored-транслятора других портов.

## 11. NRVS (ветка `dos2-nrvs`, база `dos2-nr-all` 75e2179): один трим varying на дерево вместе с NR-33B

После слияния NR-32 и NR-33B в дереве было два прохода, снимающих записи VS в невостребованные выходы: этот (`xbg_spirv_vsout`, на
компоненты, `#vo`-ключи, `Shader::vo`) и `nr_mat_prune` NR-33B (на Location, `#dp<keep>`-ключи, `Shader::nm_dp`). При обоих включённых
пайплайн с близнецом NR-33B получал `#dp`, остальные — `#vo`, а `vs_choose` NR-33B считал вершинный модуль NR-32 «retyped kept».

**Что теперь (один механизм):**
- Единственный трим — `vsout_module` этого шага. NR-33B больше не трогает VS сам: у близнеца `#dz` `vo_read = vo_decl = 0`, так что тот же
  блок в `draw` даёт VS без единой записи в Location-выходы (ключ `<vs>[#vi…]#vo0000000000000000_0000000000000000`). `dp_module`,
  `vs_choose`, `Shader::nm_dp / nm_in / nm_out`, ветка `#dp` прогрева удалены; `nr_mat_prune` в ядре остался только для `nr_mat_test` /
  `tools/dos2_nr_mat_proof.py` (движок его не вызывает).
- **Приоритет:** `xlq_twin` = `DM_NR_MAT` 1 / 3 и `DM_NR_MAT_VS=1` (ставит `nrmat::on()`, вызывается при старте сразу после чтения
  `DM_NR_XLQ`). Пайплайн с близнецом триммируется в режиме 1, что бы ни стояло в `DM_NR_XLQ` (в т. ч. 0 и 2); при `xlq_twin=0` близнец идёт
  по `DM_NR_XLQ`, как любой пайплайн. Все прочие пайплайны — только `DM_NR_XLQ`; `DM_NR_MAT` их не триммирует никогда.
  `DM_NR_MAT_VS=0` значит «NR-33B не добавляет трим», а не «близнец без трима»: для A/B вклада VS на Mali нужно `DM_NR_XLQ=0 DM_NR_MAT_VS=0`.
- **Ключи прогрева — одна схема `#vo`.** `warm::load_module` строит `#vo`-ключ при `DM_NR_XLQ` 1 / 3, а ключ с read = decl = 0 — ещё и при
  `xlq_twin`. Апгрейд старых записей (`xlq_warm_module`): запись «простой VS + `<fs>#dz`» получает VS `#vo0…_0…` (при `xlq_twin` или
  `DM_NR_XLQ` 1 / 3), прочие — как раньше, только при `DM_NR_XLQ` 1 / 3. Записи с `#dp` (сборки этой ночи, игрокам не уходили) не строятся.
- **Кеш модулей** `Shader::vo` по (retype-код, read, decl, **режим**): режим 2 (считать) и 1 (собирать) одной маски не путаются; один
  `bundle_module` на ключ — двойной сборки нет. Деструктор: близнец удаляется, `vo`-модули — если это не базовый / retype-модуль
  (`nm_dp` больше нет; совпадений между записями `vo`, кроме базового / retype, быть не может — каждый удачный трим создаёт свой модуль).
- Счётчики: `NVN PERF xlq mode=… twin=… twin_pipelines=…` (строка печатается при `DM_NR_XLQ` ≠ 0 или `xlq_twin`); сводка `[nr] mat`
  показывает `twin pipelines with the NR-32 vertex trim N`.

**Найден и исправлен пропуск самого трима (выигрыш NR-32 был занижен).** `mentions()` считала ссылкой любое слово инструкции, равное
id выхода; номер инструкции `OpExtInst` — литерал (GLSL.std.450 `InverseSqrt` = 32, `FMax` = 40 …), а выходы транслятора — как раз
`%32`, `%40` … Такой выход «приколачивался», его записи не снимались ни при какой маске. Новый тест `tests/nrvs_equiv_test.cpp` (весь пак,
маска 0, против `nr_mat_prune`): до правки **в 3 017 из 6 130 VS оставалось 21 751 из 147 985 записей** (у `nr_mat_prune` — 0), после — **0**
во всех. Правка: `literal_word(op, k)` — позиции, которые грамматика SPIR-V делает литералами (`OpExtInst` номер, индексы
`OpCompositeExtract/Insert`, компоненты `OpVectorShuffle`, маски `OpSelectionMerge/LoopMerge`, веса `OpBranchConditional`, литералы
`OpSwitch`, `OpLine` / `OpSource` / `OpExecutionMode` …); остальное по-прежнему консервативно. Действует и на маску чтения FS.
- Парам `programs.tsv` (6 129, без пар heat): снятых `OpStore` **32 670** (было 28 243 на 6 141 паре, §5) — **+16 %**, выходов снято 5 525;
  доля мёртвых компонент 36.2 %. `malioc` не перезапускался (бюджет) — таблица §0 теперь нижняя граница выигрыша.
