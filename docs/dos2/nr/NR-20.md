# NR-20 `DM_NR_ROTATE` — pre-rotation swapchain (сегмент S8)

Ветка `dos2-nr20` (worktree `wt-nr20`, база `dos2-nr11` adc021b). На телефоне **не запускалось** (ни один режим). Умолчание 0.
Источник шага: аудит `docs/dos2/nr/AUDIT-REMAINING.md` (ветка `dos2-nraudit`), строка NR-20; KB `nx2android-harvest.md` NXH-A02,
`mobile-gpu-field-notes.md` (Google: pre-rotation).

## 1. Сначала без кода: что известно и как проверить

**Факты из логов телефона** (Mi 14 Ultra, `src/work/logs`, напр. `rd1.log`): `Swapchain: window=2400x1080 extent=2400x1080 currentTransform=2
supported=511 selected=1`, через 3 с — снова, уже `currentTransform=8` (активити `sensorLandscape`: телефон перевернули на 180°, или
датчик выбрал другую сторону при старте). Значит: окно альбомное, панель физически портретная, swapchain создаётся с `preTransform =
IDENTITY`, и **каждый кадр поворачивает композитор**. `currentExtent` Android отдаёт в ориентации окна (2400×1080 при transform 2) — для
pre-rotation размер образов надо менять местами (1080×2400), как велит руководство Google.

**Чего приложение узнать не может:** кто поворачивает. Либо дисплейный контроллер (HWC кладёт слой с поворотом сам — композиция
**DEVICE**, поворот бесплатный или почти: на старых Snapdragon — офлайн-ротатор памяти), либо SurfaceFlinger рисует слой на **GPU**
(композиция **CLIENT**): полноэкранное чтение нашего буфера + запись целевого буфера дисплея каждый вблок, на том же GPU, что и игра; на части
устройств кадр ещё и показывается через вблок (NXH-A02: Retroid Pocket 5 — 30 → 60 fps на экране). Публичного API для этого нет.

**Проверка (главный агент, на телефоне, игра в кадре, без лимита кадров):**
```
adb shell dumpsys SurfaceFlinger > sf.txt
findstr /n /c:"HWC layers" sf.txt             (или grep -n -A14 "HWC layers" sf.txt)
```
В таблице `... HWC layers:` найти строку слоя игры (`SurfaceView[org.dos2.port/com.xiaoboluo.d2r.DmActivity]...(BLAST Consumer)...`) и
посмотреть колонки:
- `Comp Type`: `DEVICE` — поворачивает дисплей; `CLIENT` — GPU-композиция (то, что NR-20 убирает);
- `Transform`: сейчас ожидается `ROT_90` / `ROT_270`; с `DM_NR_ROTATE=1` должно стать `0` (поворачивать нечего);
- дополнительно: строка `Display ... (active)` / `Composition` и раздел вендорного HWC (у Qualcomm — таблица SDM с типом композиции слоя
  `SDE` / `GPU` и признаком ротатора). Снимать два раза: `DM_NR_ROTATE` не задан и `DM_NR_ROTATE=1`.
- Альтернатива без dumpsys: Perfetto / `atrace gfx view` — в процессе `surfaceflinger` каждый кадр срезы `RenderEngine` / `REThreaded::drawLayers`
  / `composeSurfaces` = CLIENT.

**Что из ответа следует (выбор пути для устройства):**

| `dumpsys`: слой игры | Что включать | Почему |
|---|---|---|
| `DEVICE`, `ROT_90/270` | `DM_NR_PRESENT=1` (NR-11), `DM_NR_ROTATE=0` | дисплей поворачивает бесплатно; NR-11 снимает blit, NR-20 вернул бы его (поворачивающий draw) |
| `CLIENT` | `DM_NR_ROTATE=1` (NR-11 тогда простаивает) | снимается GPU-проход композитора (и, где есть, показ через вблок); поворачивающий draw ≈ цена старого blit |
| `DEVICE`, но на Qualcomm SDM виден офлайн-ротатор | A/B `DM_NR_ROTATE=0/1` по `gpu_ms`, `present_gpu_us`, температуре | ротатор = лишний проход памяти вне GPU; по fps не видно, по теплу / шине может быть |

## 2. Что сделано

**Правила** (`dm/gfx/nr/nr_rotate.h`, чистый C, тест):
- *решение* при каждом новом swapchain: `currentTransform` ∈ {ROTATE_90, 180, 270} и есть в `supportedTransforms`, поверхность разрешает
  `COLOR_ATTACHMENT`, нет RCAS (`DM_GFX_SHARPEN`, только DOOM), объекты конвейера созданы, ротация не падала в этом запуске → `preTransform =
  currentTransform`, размер образов для 90 / 270 — переставленный (ориентация панели), usage + `COLOR_ATTACHMENT`. Зеркальные / INHERIT —
  нет (поворачивает композитор, как было). Причина каждого «нет» — в строке лога.
- *картинка:* вместо барьера + чёрной очистки + `vkCmdBlitImage` — **один draw** (`shaders/nr_rotate.vert/.frag`, треугольник на вьюпорт,
  `uv = M·p + t`): текстура окна читается повёрнутой. Прямоугольники — те же, что у blit: вьюпорт = прямоугольник blit-а в окне, отображённый
  в образ (`nrr_map_rect`), `uv` охватывает исходный прямоугольник blit-а (crop / DRS-подпрямоугольник, полосы TL2) — `nrr_uv_affine`.
  Фильтр тот же (nearest; linear — только TL2 pillarbox). Полосы letterbox — `loadOp CLEAR` чёрным, при полном покрытии `DONT_CARE`
  (тайлеры: ни загрузки, ни очистки). Render pass сам делает `UNDEFINED → PRESENT_SRC`; семафор acquire ждёт на
  `COLOR_ATTACHMENT_OUTPUT`; текстура окна `TRANSFER_SRC → SHADER_READ_ONLY → TRANSFER_SRC` (движок отслеживает её в `TRANSFER_SRC`).
- *смысл поворота* — по спецификации Vulkan («ROTATE_90: содержимое повёрнуто на 90° по часовой»); точка образа (a, b) показывает точку
  окна (b, 1−a) для 90 и (1−b, a) для 270 — совпадает с `rot.vert` nx2android, проверенным на экране RP5.
- *поворот телефона на 180°* (2 ↔ 8, окно того же размера): WSI Android отдаёт `SUBOPTIMAL` → `surface_properties_changed()` (transform
  ≠ созданного) → следующий present создаёт swapchain под новый transform (старый уходит как `oldSwapchain`). На случай WSI, который не
  сообщает (старые Android), — опрос поверхности каждые 60 presents, пока swapchain повёрнут. Счётчик `phone turned` в строке. Без нового
  swapchain картинка была бы вверх ногами (тест `turnover`) — поэтому опрос, а не надежда на `SUBOPTIMAL`.
- *отказ:* не создался повёрнутый swapchain / виды / framebuffer-ы → сразу identity-swapchain (старый путь) и ротация выключена до перезапуска
  (красная строка). Не создался вид текстуры окна в кадре → этот кадр чёрный, следующий present — identity.

**NR-11 (`DM_NR_PRESENT`) и NR-20.** Прямой present NR-11 рендерит последний проход игры (комбайн, транслированный шейдер) прямо в образ
swapchain. В повёрнутый образ так нельзя: вьюпорт Vulkan не вращает, а правка VS транслированного шейдера (поворот `gl_Position`) ломает
`gl_FragCoord`, производные и выборки по экранным координатам в FS комбайна. Поэтому:
- **без NR-11:** blit → поворачивающий draw (цена ≈ blit), композитор больше не поворачивает;
- **с NR-11 и повёрнутым swapchain:** презентер отвечает `pre-rotated` (`NRP_P_ROTATED`, было в NR-11), прямой путь не стартует, кадр идёт
  через тот же поворачивающий draw; поток present не паркует образы (их некому брать). То есть **NR-11 и NR-20 — альтернативы**, выбор — по
  таблице §1. Включить оба можно: побеждает NR-20, NR-11 считает отказы.
- (вне шага, §7) на стоковом драйвере Qualcomm есть `VK_QCOM_render_pass_transform` (в логах телефона — только у стокового 750, у Turnip нет):
  с ним проход комбайна можно отрисовать прямо в повёрнутый образ без правки шейдеров — тогда NR-11 + pre-rotation совместимы.

| `DM_NR_ROTATE` | что делает |
|---|---|
| 0 / не задан | ничего: `preTransform = IDENTITY`, usage, размер, blit — как было; по одному сравнению на swapchain и на present; объекты не создаются |
| 1 | pre-rotation, если поверхность повёрнута и всё разрешено; иначе старый путь (причина в строке) |
| 2 | решение и объекты (конвейер, render pass) как у 1, **исполняется старое** (identity-swapchain, blit); каждые 120 presents тот же draw идёт в свой образ повёрнутого размера, 12 пикселей (углы, середины сторон, центр, 3 случайных) сравниваются с текселями текстуры окна, которые они должны показывать (копии в host-буфер, сравнение после fence; с учётом RGBA / BGRA) — `【红】` при несовпадении. Проверяет на устройстве шейдер, отображение, дескриптор, layout-ы и форматы, не трогая экран |
| 3 | как 1, но образ сначала заливается пурпуром (`loadOp CLEAR`): всё, что draw не покрыл, видно |

Умолчание — `nrr_default_mode()` (0). Игрокам флаги не нужны: после `dumpsys` на классе устройств main-сессия ставит умолчание по
детекту. Ключ детекта — SoC / дисплейный контроллер (а не GPU: композицию решает HWC): при `DM_NR_ROTATE≠0` презентер пишет
`ro.soc.manufacturer`, `ro.soc.model`, `ro.board.platform`. Предположительно [м]: MTK / Exynos / старые Snapdragon с RGB-слоем 90° — CLIENT
чаще, новые Snapdragon (DPU с inline-ротатором) — DEVICE; **проверять, не верить** — для того и строка.

**Строки лога** (`dm-vulkan`):
- `[nr] DM_NR_ROTATE=N: … SoC <man> <model> (board <b>) …` — один раз при запуске;
- `Swapchain: window=… extent=… currentTransform=2 supported=511 selected=2` — старая строка; `selected` = выбранный `preTransform`;
- `[nr] rotate (DM_NR_ROTATE=N): surface rotate 90 (supported 0x1ff) -> pre-rotated: swapchain rotate 90, image 1080x2400, window extent
  2400x1080` — на каждый swapchain (=2: `… (=2: would pre-rotate; …)`);
- раз в 10 с: `[nr] rotate (…, last 10 s): P presents, turned draw D, blit B; swapchain … (surface …, <причина>), image WxH; swapchains S
  (pre-rotated R, phone turned T); probes ok K bad 0 skipped 0; red 0`;
- `NVN PERF present_gpu_us=… extent=…` (маркер `gfx-present-timing`) — теперь GPU-время поворачивающего draw вместо blit-а.

## 5. Ожидаемый выигрыш (не замер; [м] — модель)
Цены: blit / поворачивающий draw 2400×1080 RGBA8 — 10,4 МБ чтения + 10,4 МБ записи; GPU-композиция SurfaceFlinger — чтение нашего буфера +
запись целевого буфера дисплея (2400×1080…3200×1440, 10–18 МБ) + остальные слои, **каждый вблок** на том же GPU.
- **Mi 14 / Adreno 750:** если `DEVICE` — 0 (NR-20 выкл., выигрыш остаётся за NR-11: −0,2…0,5 мс GPU); если `CLIENT` — −0,3…0,8 мс GPU на
  кадр от снятой композиции при 105–120 Гц [м] (минус NR-11, который тогда не работает); кадр палубы упирается в GPU → это fps.
- **S7 / Adreno 7xx:** `CLIENT` → −0,6…1,5 мс из ~33 [м], `DEVICE` → 0.
- **MTK / Mali, Exynos / Xclipse (самые вероятные `CLIENT`):** −1…3 мс GPU (KB: Google, Pixel 4 XL −40 % частоты GPU) и −20…30 МБ/кадр шины
  (тепло); где композитор показывал кадр через вблок — до ×2 fps на экране (NXH-A02). Тайлеры: draw с `DONT_CARE` пишет плитку прямо в буфер
  дисплея; на Mali образы с `COLOR_ATTACHMENT` gralloc может выделить с AFBC, которые DPU сканирует без поворота [м].
- **PowerVR:** как Mali по композиции [м]; draw — обычный полноэкранный проход.
- **Слабый CPU:** ≈ 0 (на потоке present: render pass + обновление дескриптора + вид текстуры ≈ 5–15 мкс вместо blit-а).
- Отрицательный случай: `DEVICE`-устройство с `DM_NR_ROTATE=1` и `DM_NR_PRESENT=1` теряет выигрыш NR-11 (≈ blit) — поэтому умолчание по
  таблице §1, не «всем».

## 6. Риски
1. Не исполнялось на телефоне. Направление поворота взято из спецификации и совпадает с nx2android (RP5, на экране); **первый прогон `=1` — со
   снимком экрана** (`adb exec-out screencap -p`): перевёрнутая / зеркальная картинка сразу видна. `=2` направление композитора не проверяет —
   только сам draw.
2. Синхронизация (семафор acquire на `COLOR_ATTACHMENT_OUTPUT` + внешняя зависимость render pass, переходы текстуры окна) — по правилам Vulkan,
   не прогонялась валидацией: прогон `=1 DM_VK_VALIDATION=1`.
3. `currentExtent` в ориентации окна — по логам телефона (2400×1080 при transform 2); на устройстве, где он уже в ориентации панели,
   перестановка дала бы неверный размер → строка `[nr] rotate … image` покажет, а `SUBOPTIMAL` / пересоздание — не зациклится ли (опрос сравнивает
   transform и `currentExtent`, а не размер образа).
4. Поворот 180° «на ходу»: один кадр уходит со старым transform (композитор доворачивает, картинка верная), дальше новый swapchain; если WSI
   не даёт `SUBOPTIMAL` — до 60 кадров на старом (тоже верная картинка, но CLIENT).
5. Общий файл `vulkan_present.cpp` (копии в других портах — свои): при 0 изменений поведения нет (тест структуры держит).
6. Скриншоты / дампы движка — текстуры окна, не swapchain: не затронуты. Сенсорный ввод — в координатах окна, ориентация окна не меняется.

## 7. Не сделано
- Умолчание по детекту (`xbg_vendor_policy.h` / `nrr_default_mode`) — после `dumpsys` на устройствах; таблица по SoC.
- `VK_QCOM_render_pass_transform` (только стоковый драйвер Adreno): NR-11 + pre-rotation без поворачивающего draw — нужен NR-11 `=1`,
  подтверждённый на телефоне, и `CLIENT` у стокового драйвера; правка в движке (begin info прохода комбайна, framebuffer образа).
- `VK_QCOM_rotated_copy_commands` (есть и у Turnip): поворот blit-ом вместо draw — только Adreno, выигрыш против draw ≈ 0, не стоит своего
  пути.
- `DM_GFX_TAA_FIX` lower-left (`taafix::flip`, отдельная копия перевёрнутой текстуры): переворот можно было бы влить в `uv` draw-а и снять копию —
  только для режима, где он включается; не DOS2-умолчание.
- RCAS (`DM_GFX_SHARPEN`) с pre-rotation — отказ (`RCAS sharpening on`); DOOM-функция.

## 8. Прогон телефона (главный агент, по разрешению хозяина; бэкап `files/save`, проверить keyguard, погасить игру после логов)
APK ветки (`wt-nr20`), окружение — умолчания DOS2 + `DM_DBG=1 DM_DOS2_TOUCHUI=1 DM_DOS2_FPS=0`, маркер `gfx-present-timing`; палуба + бой / город.
1. **S0** (база, `DM_NR_ROTATE` не задан), в кадре игры: `adb shell dumpsys SurfaceFlinger > sf0.txt` — `Comp Type` и `Transform` слоя
   `SurfaceView[org.dos2.port/…]`. **Это решает, нужен ли NR-20 на Mi 14** (таблица §1). То же — у тестеров на MTK / Exynos (одна команда).
2. **R2** `DM_NR_ROTATE=2`, 60 с: `[nr] rotate (DM_NR_ROTATE=2): surface rotate 90 … -> pre-rotated … (=2: would pre-rotate …)`, раз в 10 с
   `probes ok ≈ 12 × presents/120, bad 0, skipped 0`, `red 0`.
3. **R3** `DM_NR_ROTATE=3`, 20 с + `adb exec-out screencap -p > r3.png`: картинка не перевёрнута и не зеркальна, пурпура нет (ни полос по краю).
4. **R1v** `DM_NR_ROTATE=1 DM_VK_VALIDATION=1`, 30 с: нет `dm-vvl` про swapchain / render pass / layout / семафоры.
5. **R1** `DM_NR_ROTATE=1` против S0, ABBA по 90 с без лимита: `dumpsys` → слой `DEVICE`, `Transform 0`; `Swapchain … selected=2`, `turned draw ≈
   presents`, `blit 0`; `fps`, `gpu_ms`, `poolreset wait_ms`, `present_gpu_us` (draw против blit-а S0); скриншот тот же, что у S0. Ждём: при `CLIENT`
   в S0 — плюс fps / минус `gpu_ms`; при `DEVICE` — ноль (тогда NR-20 на Mi 14 выключен, NR-11 — да).
6. В R1 один раз: перевернуть телефон на 180° (строка `phone turned 1`, новый `[nr] rotate … surface rotate 270 … image 1080x2400`, картинка
   не вверх ногами — скриншот), «домой → назад», загрузка сохранения — без зависаний.
7. Если в S0 `DEVICE`: **R1+P1** `DM_NR_ROTATE=1 DM_NR_PRESENT=1` 30 с — только для проверки «альтернативы»: NR-11 строки `not started: presenter
   (pre-rotated)`, кадры через draw, без `【红】`.
