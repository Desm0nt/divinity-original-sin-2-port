# VK-SEED — переносимый сид пайплайнов нового пути (`DM_VK_NATIVE=1`) и прогрев на экране загрузки

Ветка `dos2-vk5-seed2` (worktree `wt-vk5-seed2`, база 4b2fc5e). Телефон не трогался: всё ниже — тесты на ПК, сборка APK и таблица прогонов
для телефона (§6).

## 0. Зачем
Прогон T12 (`DM_VK_NATIVE_SEED=2`, тёплые файлы убраны, лог `src/work/logs/T12.dm.log`, строка `[vkn] seed:`): из 249 пайплайнов, собранных
в кадре, старый сид `dos2-pipe-seed.bin` знал 11 (~4 %), «запись тех же шейдеров с другим содержимым» 65, «шейдеры, которых в сиде нет» 138.
Старый сид снят со СТАРОГО пути (переводчик, NR-31): другие пайплайны (свой пост, свои варианты, другие ключи), поэтому на новом устройстве
первый вход в сцену по-прежнему собирал всё в кадре (T12/T13: 2–6 с без кадра на загрузке уровня, 250 сборок в потоке отрисовки, 1,3 с).

## 1. Что хранит список нового пути и что в нём от устройства
Запись `vkn-pipeline-list.bin` (`vkn_warm.h` `vkn_warm_rec`, версия 2, 296 байт) — уже содержимое, не номера прогона: ключи программ
(16 hex = хеш управляющего блока + кода шейдера игры), кортежи аргументов движка для blend / depth-stencil / raster, элементы вершинного
формата движка, примитив, ссылка трафарета, маски записи, форматы прохода (VkFormat), samples, вершинные входы, биты техник (fx, именованная
стадия), рецепт куска (имя + слова). От устройства зависят только:

| Поле | Кто решает | Что делает сид |
|---|---|---|
| заголовок (vendor, device, driver, pipelineCacheUUID) | файл привязан к устройству | в сиде нет привязки; источники перечислены только для справки |
| `retype` (код `#vi`, `vkn_draw.c retype_code`; вкл. везде, кроме Adreno) | правило устройства по шейдеру + вершинному формату | 0; читающее устройство считает своё (`vkn_warm_retype_code`) |
| первое слово рецепта `mat` (его `code` = тот же код retype) | то же | 0; при переводе = код retype этого устройства |
| формат глубины на устройстве без D24 (сток Xclipse, `DM_GFX_SIM_GPU=xclipse`) | `vkn_tex.c`: D24 → D32F / D32S8 | D24-формат + флаг EITHER (pad3 бит 0): «D24 движка или его подмена, или настоящий D32» |
| цветовые форматы | движок (таблица NVN → VkFormat) | как записано; формат, в который это устройство не рисует, — отказ |

Остальное (ключи, состояния, форматы, техники) любое устройство пишет для того же draw одинаково. Пайплайны техник, которые раньше были
«без рецепта», в списке почти не встречаются: в T12 «a piece's shader without a recipe 2 (post)» — сплавленный пост F1 / F1A / F2
(`vkn_post.c`, его ведёт gpu2; рецепт там требует строить `fused` вне потока записи — не «дёшево», оставлено), PRESKIN — 0.

## 2. Инструмент `tools/dos2_vkn_seed.py`
- `build --list F[:nod24|:d24] [F ...] --out dos2-vkn-seed.bin` — один или несколько списков (телефоны, сцены, прогоны; версии 1 и 2) →
  один сид: каждая запись проверяется (сумма, форма, нули в pad, ключи hex), приводится к каноническому виду (таблица выше), дубликаты по
  каноническому содержимому убираются (запись двух устройств об одном draw = одна запись; точная D24-запись важнее EITHER), порядок —
  первого появления (так игра их впервые рисовала, так их и строит прогрев). Способность к D24 списка — по vendor заголовка
  (0x144D Samsung, 0x1002 AMD = без D24), `:nod24` / `:d24` — вручную (прогоны `DM_GFX_SIM_GPU=xclipse` на Adreno пишут заголовок Adreno).
- `audit SEED` — повторная проверка каждой записи (в сиде только ключи, перечисления / форматы Vulkan, байты аргументов движка и вершинных
  элементов, маски, имена кусков и слова рецептов; ни кода, ни SPIR-V, ни байт файлов игры).
- `dump SEED|LIST`, `cover --seed S --list L[:nod24]` — сколько записей списка сид знает по правилу читателя (оценка покрытия «после свежей
  установки» для сцен, которые видел этот список), `selftest`.

Формат файла: заголовок 64 байта (`VKNSEED\0`, версия 1, размер записи 296, число записей, число списков-источников, id = fnv64 тела,
версия списка 2, флаги, до трёх пар vendor/device источников), затем записи `vkn_warm_rec` с суммой (fnv64, как в списке).
Раскладку `vkn_warm_rec` инструмент знает по смещениям; `vkn_seed.c` держит те же числа в `_Static_assert`.

Сид в APK: `dm/android/dos2/dos2-vkn-seed.bin` = `build` из `work/seed-src/vkn-pipeline-list-mi14-1122.bin` (Mi 14 Ultra, Turnip, сборка
4b2fc5e, Форт Радость + меню после многих прогонов): **733 записи, 136 пар шейдеров, 217 032 байта, id 0d88349289fdcceb**, из них техник:
54 с fx-битами, 215 с вершинным модулем `mat`, 3 объекта `lightfuse`; EITHER 0 (Adreno с D24). `audit` чистый.

## 3. Чтение (`vkn_seed.c`, `vkn_warm.c`)
- Порядок файлов: `dos2-vkn-seed.bin` (каталог шейдеров — тестовая заливка — или `files/`), и только если его нет или он испорчен —
  старый `dos2-pipe-seed.bin` (весь прежний перевод сохранён как запасной путь).
- Запись ждёт шейдер движка со своими ключами (то же правило, что у записи списка: без фрагментной стадии = шейдер без неё; поиск по
  индексу пары ключей), затем получает форму этого устройства: цвет / глубина по правилу текстур `vkn_tex_rt_format` (новая функция
  `vkn_tex.c`: та же подмена D24, что при создании текстуры, с `DM_VK_NATIVE_D24` и моделью `DM_GFX_SIM_GPU=xclipse/nod24`; EITHER на
  устройстве с D24 — обе формы, без D24 — одна), код retype по правилу draw для этого шейдера и формата (и в рецепт `mat`), сумма заново —
  и входит в список как ожидающая запись (`vkn_warm_seed_add`, в файл устройства не пишется, дубликат с собственным списком — «known»).
- Точность: draw берёт тёплый пайплайн только по своему ключу и своим модулям; неверный перевод = лишняя сборка, не другая картинка.
- `DM_VK_NATIVE_SEED`: 0 выкл, 1 (по умолчанию) перевести + строить, 2 проверка. С новым сидом сборка в кадре ищется по переносимой
  идентичности (retype и слово рецепта обнулены; на устройстве с подменой D24 — и как D24-форма), поэтому счёт не зависит от того, успел ли
  рабочий поток дойти до записи. Строки переписи:
  `seed: DM_VK_NATIVE_SEED=2, new-path seed …: N records: translated …, waiting for their shader …, refused: …` и
  `seed: in-frame builds since start N (technique T): the seed had H (technique …), … differs D, … no record U; coverage X %`.
  В режиме 1 «the seed had» = сид знал, но рабочий поток не успел (опоздание, а не дыра).

## 4. Прогрев на экране загрузки (`vkn_warm.c`)
Шейдеры уровня движок создаёт во время загрузки (T12: живых 195 → 565 за 30 с), а рабочий поток прогрева был один и с nice 10 — загрузчики
игры его вытесняли, и пайплайны доставались кадрам. Теперь: пока игра грузится (за окно 250 мс нет ни одного кадра или меньше 64 draw на
кадр — как `nr_drift` / качество определяют экран загрузки по своему бэкенду; меню тоже сюда попадает, это безвредно), рабочий поток идёт с
обычным приоритетом и с ним `DM_VK_NATIVE_WARM_JOBS` (по умолчанию 3, максимум 7) помощников строят ожидающие записи списка одной пачкой
(своя очередь; помощник берёт только открытую пачку, рабочий закрывает её после последнего). Вне загрузки — как было: один поток, nice 10.
`DM_VK_NATIVE_WARM_LOAD`: 0 выкл, 1 (по умолчанию) на загрузке, 2 всегда. Строка переписи `warm: loads (VK-SEED …): K load phases with work,
N entries built in them (M by the helpers) in X ms`. Сопутствующее: перебор «запись ↔ шейдер» в раунде теперь через индекс пары ключей
(было списки × шейдеры на каждый раунд), ленивое чтение `DM_GFX_SIM_GPU` в `vkn_pipe_build` стало атомарным (помощники строят параллельно;
TSAN это показал).

Чего нет: «экран загрузки ждёт прогрев» (как `mtl_warm_wait` у D3): у DOS2 в бэкенде нет надёжного признака «загрузка закончилась», а
держать поток отрисовки на экране загрузки рискованно; если прогон S2 покажет опоздания («the seed had» в режиме 1 заметно > 0) — это
следующий шаг.

## 5. Проверки на ПК
- `tools/dos2_vkn_seed.py selftest` — канонизация retype / слова `mat`, EITHER, дедуп между устройствами, заголовок.
- `vkn_warm_test` (`work/seed2_warm_test.sh`; под TSAN `work/seed2_warm_tsan.sh` — чисто): прежние прогоны 1–6 (в прогоне 2 ещё проверено, что
  4 записи построены одной пачкой с помощниками) + круговой путь «список устройства → инструмент → другое устройство»:
  - 7: источник с D24 и включённым retype (uint-вход на unorm-атрибуте: ненулевой код) строит обычный пайплайн, вариант без фрагментной
    стадии и пайплайн с модулем `mat`; список; родитель гонит `python3 tools/dos2_vkn_seed.py build`;
  - 8: `DM_VK_NATIVE_SEED=2` на модели `DM_GFX_SIM_GPU=xclipse` (без D24, без 3-компонентных форматов) с выключенным retype: 3 записи
    переведены (D32S8, retype 0, слово `mat` 0), три сборки тех же draw в форме этого устройства — «сид знал» (2 из них техники), другой
    raster — «те же шейдеры, другое содержимое»;
  - 9: `SEED=1`, `DM_VK_NATIVE_WARM_LOAD=2`, 3 помощника: 3 записи построены пачкой, мейкер `mat` спрошен с кодом 0, все три `take` находят
    свой пайплайн, файл списка устройства пуст;
  - 7b / 11: источник — модель xclipse (`:nod24`): записи EITHER; на устройстве с D24 каждая в двух формах, находится и D24S8-draw, и
    настоящий D32S8;
  - 10: сид из APK — 733 записи, отказов 0.
- `work/vkn_tests.sh` (stage 3: 285 478 проверок, stage 2: 15 523) и `source_structure_test.py` — проходят.
- APK: `tools/build_apk.ps1` (кладёт `dos2-vkn-seed.bin` в ассеты; `DmActivity.dos2PipeSeed(name)` копирует оба сида в `files/` при запуске,
  как раньше старый).

Ожидаемое покрытие: `cover` списка Mi 14 своим сидом — 100 % (733 / 733). На том же классе устройств (Adreno 7xx, Turnip) после свежей
установки в тех же сценах (меню, Форт Радость) режим 2 должен дать «the seed had» ≈ 90–100 % сборок в кадре (было 4 %); остаток — сцены, которых
список не видел, другие настройки графики (другие варианты техник), изменения бэкенда после 4b2fc5e. Mali: ретайп пересчитывается, форматы те
же (D24 есть) — покрыто всё, что не зависит от политик семейства (варианты MAT / LOAD-политики пайплайны почти не меняют); на сток-Xclipse —
то же плюс подмена D24. Сид надо пересобирать, когда меняется содержимое пайплайнов бэкенда (новые fx-биты, рецепты) и когда есть списки
новых сцен / устройств (`build --list a.bin b.bin c.bin:nod24`).

## 6. Прогоны на телефоне (не выполнялись; Mi 14 Ultra, Turnip)
Перед каждым: копия `files/save` внутри телефона; тёплые файлы убрать в сторону (`Download/DivinityOriginalSin2Mobile/dm/vkn-pipeline-list.bin`
и `vkn-pipeline-cache.bin` → `*.aside`, после серии вернуть); проверить, что экран не заблокирован; 50 с от загрузки сохранения, 100 с
остывания после каждых трёх; логи забирать после force-stop.

| # | env (кроме `DM_VK_NATIVE=1`) | Цель | Длительность | Ожидание |
|---|---|---|---|---|
| S1 | `DM_VK_NATIVE_SEED=2` | покрытие нового сида: had / differs / no record, строка `coverage` | меню + загрузка + 50 с | ≥ 90 % (T12: 4 %) |
| S2 | `DM_VK_NATIVE_SEED=1` | время загрузки, сборки в кадре (`render thread: … built itself`), `warm: loads`, кадры без отрисовки | то же | сборок в кадре ≪ 250, нет 2–6 с без кадра |
| S3 | `DM_VK_NATIVE_SEED=1 DM_VK_NATIVE_WARM_LOAD=0` | что даёт прогрев на загрузке (сравнение с S2) | то же | больше сборок в кадре / «the seed had» (опоздания), чем в S2 |
| — | остывание 100 с | | | |
| S4 | `DM_VK_NATIVE_SEED=2 DM_GFX_SIM_GPU=mali` | покрытие на модели Mali (ретайп, политики семейства) | то же | близко к S1 |

Итого 4 прогона ≈ 4 × (≈40 с загрузки + 50 с) + 100 с ≈ 8 мин. База (без сида) не нужна: T12 / T13 уже есть.
