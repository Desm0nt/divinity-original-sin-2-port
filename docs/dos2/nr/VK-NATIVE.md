# VK-NATIVE — свой бэкенд Vulkan на уровне рендерера движка, без NVN (20.11.2026, ветка `dos2-vk`)

Задача хозяина: «нам надо не строиться поверх NVN или ещё чего-то. Первоочередная задача — вообще убрать NVN. Игра должна забыть, что
такое Switch, как страшный сон, и стать обычной игрой на Vulkan под Android».
База: `dos2` f6494bd. Телефон в этой работе не трогался (его ведёт главная сессия). Состояние и план этапов — `VK-NATIVE-STATUS.md`.
Карта интерфейса по методам — `VK-NATIVE-MAP-1.md` (ресурсы), `VK-NATIVE-MAP-2.md` (состояние, константы, текстуры, цели, draw),
`VK-NATIVE-MAP-3.md` (пулы памяти, устройство, окно, кадр, списки команд и 64 кода пакетов).
Пометки: **[бин]** — прочитано в `main.raw` (сборка 4979b200) в этой работе; **[док]** — из прежних разборов; **[выв]** — вывод.

## 0. Коротко
- **Почему прежний путь брошен.** Все ступени над NVN и транслятором (NR-ZERO, NR-NATIVE: карточки, строки, шаги B / D / E) были точны, но
  процессор не экономили: серия CO (Mi 14 Ultra, Форт Джой стоя) — база 89 fps (транслятор 7.5 мс, поток игры 7.0–7.3 мс на кадр), со всеми
  частями NR-NATIVE 85.6 fps (9.3–9.4 и 8.6 мс). Кэшировать ответы транслятора под объектами движка — не цель. Эти слои не расширяются.
- **Где у движка граница.** Рендерер движка — объект `r = [main+0x2bbdc68]` с невиртуальными методами `0x914bb0…0x941ed0` [бин]. Выше него
  стадии кадра пишут **списки команд движка** (пакеты, 64 кода), которые не зависят от NVN; ниже него — только NVN. Движок зовёт извне
  110 функций этого диапазона; NVN трогают 137 функций всего образа, из них вне рендерера — только блок UI (Iggy, `0x1bea840…0x1bf4338`)
  и «немедленные» ветки двухрежимных функций стадий. То есть интерфейс бэкенда — это **(а)** исполнитель пакетов `0x93e5f0`,
  **(б)** функции создания и уничтожения ресурсов, **(в)** сбросы и draw, **(г)** кадр и окно, **(д)** 11 входов UI.
- **Что удобно совпало** [бин]: движок настраивает NVN на глубину 0…1 и начало координат сверху слева (`nvnDeviceSetDepthMode(1)`,
  `nvnDeviceSetWindowOriginMode(1)`), `SetDepthRange` не зовётся нигде — это соглашения Vulkan, переворот не нужен. Объекты состояния —
  малые таблицы (10 смешиваний, 18 глубины-трафарета, 10 растеризации, 26 сэмплеров), форматы вершин дедуплицированы. Константы — одно
  кольцо `0x1380000` байт, только дописывается. В обычном кадре процессор не ждёт GPU нигде.
- **Проект** (§2–§5): свой исполнитель пакетов пишет `vkCmd*` прямо в буфер команд Vulkan **на потоке движка, который исполняет списки**;
  ресурсы создаются один раз по событиям создания движка; конвейер — по ключу из нескольких малых целых; набор дескрипторов — по номерам
  слотов движка; константы — из кольца со смещениями; показ — существующим презентером (`dm_present_async`). Записей NVN, потока
  `nvn-translate` и HLE NVN в этом пути нет.
- **Переключатель** `DM_VK_NATIVE`: 0 — как сегодня (умолчание, пока телефон не докажет); 1 — бэкенд рисует всё, что покрыл; 2 — «рядом»:
  старый путь рисует, бэкенд только создаёт свои ресурсы по тем же событиям (проверка этапа 2, без слоя в кадре). Ступень 2 безопасного
  режима ставит 0.

### 1.3 Сверка с iPad
Сборка iPad (Metal) имеет те же стадии кадра и тот же слой списков команд (`IPA_RECON.md` §3) — отличается именно нижний слой: начало
прохода с явными load / store, ленивая очистка, заборы между кодировщиками. Наш бэкенд встаёт на то же место, что бэкенд Metal, и берёт у
него правило проходов: грузить вложение только если в него писали в этом кадре, очистку сливать в начало прохода, глубину сохранять только
если её кто-то читает дальше (§4.3). Символов в образе iPad нет, поэтому имена методов — наши; структура сверена по описанию.

Модули `vkn_*` не знают адресов игры и не зовут NVN, HLE и транслятор. С остальным кодом порта их связывают три узких места:

(`dm_present_async`).

### 2.2 Объекты
Свои таблицы по **индексу хэндла движка** (как `nr_reg`): запись помнит хэндл целиком, другое поколение на живой записи = замена.
| Объект | Поля |
|---|---|
| текстура | `VkImage`, память, формат Vulkan, размер, уровни, слои, вид целиком + послойные виды, текущая раскладка образа (`layout`), кадр последней записи как цели, отложенная очистка (цвет / глубина), класс (обычная, цель цвета, цель глубины, окно) |
| номер пула → вид | таблица «номер в пуле текстур движка → (текстура, вид)»: слоты текстур в кэше движка хранят именно эти номера |
| сэмплер | `VkSampler`; таблица «номер в пуле сэмплеров → сэмплер» |
| буфер | арена, смещение, размер, указатель процессора (он же лежит в записи движка `+0x10`) |
| шейдер | модули стадий, список привязок (вид, слот движка, стадия), раскладка набора, раскладка конвейера, малый номер шейдера |
| состояние | готовые `VkPipelineColorBlendAttachmentState`, `VkPipelineDepthStencilStateCreateInfo`, `VkPipelineRasterizationStateCreateInfo`, малый номер |
| формат вершин | описания атрибутов и привязок, малый номер |
| проход | `VkRenderPass` по (форматы вложений, операции load / store), `VkFramebuffer` по (проход, виды) |
| конвейер | ключ: шейдер, смешивание, глубина-трафарет, растеризация, формат вершин, примитив, проход, опорное значение трафарета, вариант порога альфы — малые целые в трёх словах по 64 бита (маски записи цвета по целям тоже в ключе); хэш-таблица с открытой адресацией |

### 2.3 Потоки
- **Поток, исполняющий списки движка** (он один: исполнитель и всё под ним пишут кэш `r` без замков [бин]) — пишет буфер команд Vulkan
  кадра, сам подаёт его в конце кадра и сам отдаёт образ презентеру. Второго потока-переводчика нет.
- **Потоки загрузки движка** зовут функции создания: объекты Vulkan создаются на месте под замком своих таблиц; заливки данных ставятся
  в очередь и пишутся в начало буфера команд ближайшего кадра (так же, как движок сам откладывает свои копии буферов до `0x93d9f0`).
- **Очередь Vulkan одна** на весь порт: каждая подача берёт общий замок (`dm_vk_queue_lock`); при `DM_VK_NATIVE != 0` он настоящий в любом
  режиме презентера.

## 3. Ресурсы (этап 2)

### 3.1 Режим «рядом» (`DM_VK_NATIVE=2`)
Старый путь рисует как сегодня; крюки функций создания после оригинала создают объекты бэкенда из тех же аргументов. Это проверка этапа 2
целиком на телефоне: число объектов против реестра движка, ошибки Vulkan, объём памяти, время создания, собранные конвейеры. В кадре
бэкенд не участвует. Буферы вершин и индексов в этом режиме только считаются (память у них одна, владелец — старый путь).

### 3.2 Буферы
- При `=1` тела `0x917630 / 0x9179d0` заменены: запись в таблице движка заводится его же помощниками (`0x917440 / 0x9177d0`), память —
  блок арены Vulkan (куски по 16 МБ, отображены постоянно), `+0x10` записи = указатель в арену. Движок пишет вершины прямо в память
  Vulkan, копий нет ни на одном GPU. Уничтожение (`0x91db40 / 0x91d890`) — своё: запись движка сбрасывается сразу, блок памяти возвращается
  через три кадра (правило движка — два, ещё один на кольцо буферов команд); отложенные таблицы движка для буферов остаются пустыми,
  поэтому `0x91ad20` не тронут.
- Кольцо констант — свой буфер Vulkan `0x1380000` байт; сбросы блоков пишут в него по правилу движка (выравнивание 256, переход в
  начало при нехватке) и отдают смещения как динамические смещения набора.
- Кольца «немедленных» вершин и индексов (`r+0x8d0`, `r+0x8e0`) — обычные буферы движка, становятся блоками арены сами собой.

### 3.3 Текстуры
- Формат: таблица «формат движка 0…62 → `VkFormat`» (прежняя `nr_formats` даёт формат NVN; для BC — нативно либо декод по политике
  семейства GPU, как сегодня).
- Данные: `CreateTexture` — линейные, порядок «слой → уровень → грань»; `CreateTextureFromImage` — либо линейные, либо упакованные в
  раскладку Switch (тогда один раз перекладываются `nvn_deswizzle_gob`).
- Цели и глубина: образы с нужным usage; общий запас памяти целей (`0x914bb0`, флаг `0x2000`) не воспроизводится — каждая цель получает
  свою память.
- Текстуры окна (`0x93c3a0`): два образа-цели; показ отдаёт текущий презентеру.

### 3.4 Шейдеры
- Ключ стадии — `xbg_shader_program_key` (SHA-256 управляющей секции и кода, 16 знаков) — тот же, что у паков.
- Модуль и список привязок берутся через узкий выход из движка трансляции `xbg_vkn_shader(key, …)`: он отдаёт уже готовый модуль со
  всеми переписываниями SPIR-V, которые пак требует при загрузке, и варианты (порог альфы, тип входа вершин). Это кирпич, не слой:
  зовётся один раз на шейдер при создании.
- Привязки Vulkan в паках: один набор, номер = привязка × 6 + стадия. Блоки констант — `UNIFORM_BUFFER_DYNAMIC`, пока хватает
  предела устройства `maxDescriptorSetUniformBuffersDynamic` (шейдеру нужно до 15 буферов; дальше по правилу транслятора: динамические
  только блоки движка, затем ни одного), текстуры — `COMBINED_IMAGE_SAMPLER`. Кроме блоков движка, каждый бандл читает служебный буфер
  (`vkn_shader_support`: размер окна вывода) и, у части шейдеров, готовый блок `c1` — оба даёт бэкенд.

### 3.5 Состояние и конвейеры
- Объекты состояния и форматы вершин переводятся в структуры Vulkan один раз при создании.
- Порог альфы (`r+0x1868 >= 0`) — вариант пиксельного модуля; маска записи цвета — по формату цели (`0x9282c0`); смешивание включено на
  каждой привязанной цели, «без смешивания» выражено коэффициентами.
- Динамическое состояние — только окно вывода и ножницы; опорное значение трафарета входит в ключ.

## 4. Кадр (этап 3)

### 4.1 Исполнитель пакетов
Свой `ExecuteRenderCommand` на все 64 кода (длины и поля — карта 3). Коды состояния пишут те же поля кэша `r`, что и оригинал (их читает
и остальной код движка), и ставят биты «конвейер грязный / набор грязный». Коды без NVN (камера, параметры, вызовы функций) исполняются
родным кодом движка.

### 4.2 Draw
1. Сброс глобальных блоков и блоков шейдера: копия в кольцо, если блок грязный или не заливался в этом кадре (правило движка).
2. Конвейер: из кэша по ключу; промах — сборка (прогрев — прежним списком конвейеров, этап 4).
3. Набор дескрипторов: ключ = раскладка шейдера + номера (текстура, сэмплер) занятых слотов; кэш по хэшу; смещения блоков — динамические.
4. Буферы вершин и индексов: (буфер арены, смещение).
5. `vkCmdDrawIndexed` / `vkCmdDraw`.

### 4.3 Проходы
Проход Vulkan открывается **лениво** — при первом draw после смены целей. К этому моменту известны отложенные очистки (пакеты 0x03–0x05
до первого draw сворачиваются в `loadOp = CLEAR`), кадр последней записи цели (`LOAD` только если писали в этом кадре, иначе `DONT_CARE`)
и чтение цели как текстуры (перед draw, который читает образ в раскладке вложения, проход закрывается и образ переводится). Очистка без
последующего draw исполняется отдельной командой. Пакет 0x37 (состояние ресурса с именем) — подсказка для переводов раскладки.

### 4.4 Кадр, синхронизация, показ
- `0x9215f0(r, 1)`: взять буфер команд кадра (кольцо из трёх, забор на каждый; перед повторным использованием — ждать свой забор:
  это и есть модель движка «контекст на текстуру окна»).
- `0x93d9f0`: залить очередь данных текстур и подготовленных копий, сбросить кэш привязок.
- `0x93ccd0(окно, 1)`: закрыть проход, перевести образ окна, подать, `dm_present_async(образ, формат, размер, обрезка, интервал)`,
  счётчик кадров `dev+0x51f0` += 1, отложенные уничтожения.
- `0x9215f0(r, 0)` + `0x93ccd0(окно, 0)` (чтение текстур вне кадра): отдельный буфер команд, подача с ожиданием забора.
- Темп кадров — прежний (`present_period`), ожидание — на взятии образа у презентера.

### 4.5 UI
UI рисует Iggy через свою таблицу входов; NVN зовут 11. Их заменяют свои функции над тем же буфером команд кадра: три формата вершин,
78 программ (в паках есть), цели и фильтры. До этого куска при `=1` входы UI — пустые.

### 4.6 Что ловит остатки
При `DM_VK_NATIVE=1` любой вызов записи команд NVN — ошибка покрытия. Запись HLE в этом режиме уходит в «песок» (локальная страница) и
считается по адресу возврата; раз в 10 с строка `[vkn] stray NVN calls: N (main+0x… × k, …)`. Пустой список = в кадре NVN не зовётся.

## 5. Переключение и уборка (этап 4)
- Тела функций создания текстур, сэмплеров, состояний, шейдеров, устройства и окна — без вызовов NVN (до этого этапа они зовут
  строители NVN только ради своих записей; в кадре их нет).
- Чтение текстур, запросы видимости, вычислительные проходы — если строка §4.6 их покажет.
- Прогрев конвейеров, политика семейств GPU (тайловые: правило проходов §4.3 уже в основе), безопасный режим.
- Поток `nvn-translate` и очередь HLE не запускаются.

## 6. Что остаётся на старом пути и почему
| Что | До какого этапа | Почему |
|---|---|---|
| Весь кадр при `DM_VK_NATIVE=0` | умолчание до решения телефона | — |
| Вызовы строителей NVN внутри функций создания | 4 | время загрузки, не кадр; тела большие (текстуры 471 и 612 строк декомпиляции) |
| Создание устройства, очереди, пулов | 4 | один раз при запуске |
| Ввод, звук, файлы, потоки (HLE ОС) | навсегда | не графика |

## 7. Проверка
Один раз на этап (`VK-NATIVE-STATUS.md`). Эталон — старый путь: два прогона одной сцены (`DM_VK_NATIVE=0` и `=1`), снимки экрана и
дампы именованных целей; сверка вне телефона. Слоя сверки в кадре нет.

## 8. Риски
- **Раскладки образов** при чтении цели как текстуры в том же кадре — главный источник ошибок Vulkan; закрыт правилом §4.3 и слоем
  проверки Vulkan (`DM_VK_VALIDATION=1`) на первых прогонах.
- **Память**: арены буферов отображены постоянно (до ≈ 200 МБ); на Mali чтение такой памяти процессором медленнее (движок читает её
  только в копии буфера в буфер, пакет 0x2f).
- **Варианты модулей** (тип входа вершин, порог альфы) должны совпасть с тем, что делает сегодня транслятор, иначе картинка разойдётся на
  отдельных материалах — ловится сравнением кадров.
- **Потоки создания**: функции создания зовутся с потоков загрузки; очередь заливок и таблицы — под замком.
- **UI** при `=1` пуст до своего куска.
