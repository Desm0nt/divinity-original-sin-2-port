# VK-NATIVE этап 5.5: свой поток записи (проект ведущего, 21.11.2026)

Зачем: при `DM_VK_NATIVE=1` кадр упирается в поток движка (17.8 мс против 14.9 мс GPU). Этап 5.1 удешевил draw; этот этап
делит работу бэкенда на два потока, как делил старый путь (движок + транслятор). Хозяин хочет оба приёма сразу.

## 1. Где режем

Не на уровне команд Vulkan (там резать нечего — вся цена в поиске и сборке) и не на уровне списков команд движка (перенос
всего исполнителя пакетов просто переносит упор). Режем **на входе бэкенда**: крюки движка на потоке движка пишут короткие записи
в поток записей кадра, второй поток («поток записи») исполняет их по порядку прежними функциями `vkn_draw_*`, `vkn_pass_*`,
`vkn_frame_*`. Для остального бэкенда «поток записи» остаётся единственным — его правило одного потока не меняется.

## 2. Главное правило точности: «снимок при записи»

Всё изменяемое, что draw читает из общего состояния, снимается в момент записи на потоке движка:

| Что читает draw | Как снимается |
|---|---|
| кэш рендерера движка (хэндлы, вьюпорт, ножницы, опорные значения) | уже лежит в `vkn_draw_in` — копируется в запись |
| массивы слотов текстур и сэмплеров (3 × 32 × 2 числа) | копия в запись только при смене (счётчик смен из крюка сброса текстур); иначе ссылка на прошлую копию кадра |
| блоки констант (объявления `vkn_draw_ubo`) | запись «объявление» в общем потоке записей: порядок с draw сохраняется; байты уже в кольце |
| буферы вершин и индексов (хэндл → блок арены, версия содержимого, указатель процессора для перезаписи индексов) | **разрешаются при записи** (`vkn_buf_get_n`): в запись идут блок и версия. Заодно пометка «использован в кадре» ставится вовремя — на ней держится правило переименования при обновлении буфера. Генерируемые индексы (веер, квады, петля) считаются при записи, пока байты движка те же |
| таблицы текстур, сэмплеров, шейдеров, состояний (хэндл / номер пула → объект) | читаются потоком записи позже, поэтому **любое уничтожение или замена записи в этих таблицах с потока движка — точка синхронизации** (см. 3). Создание нового хэндла безопасно: повторное использование индекса возможно только после уничтожения, а оно уже синхронизировано |
| содержимое текстур (обновления, зеркало памяти NVN, заливки в запись) | либо запись в потоке (данные уже скопированы в промежуточный буфер на потоке движка), либо точка синхронизации |

Объекты бэкенда живут ещё 3 кадра после уничтожения (`vkn_retire`), поэтому указатели в записях безопасны.

## 3. Точка синхронизации и передача владения

`vkn_rt_sync()`: поток движка ждёт, пока поток записи исполнит всё записанное, после чего **сам становится потоком записи** на
время своего вызова (поток записи спит). Любой крюк, который не переведён на записи, начинается с `vkn_rt_sync()` — это ставит
общий вход крюков (таблица мест `dm_vkn_site` / переходник стека): у места есть признак «пишет запись»; у всех остальных
синхронизация по умолчанию. Так редкие пути (чтение текстур для сохранений, создание с данными, копии, запросы видимости, UI,
если он не переведён) остаются точными без единой правки, а счётчик по местам показывает, какие из них частые и просят перевода.
Крюки потоков загрузки (не поток движка) синхронизацию не зовут: они и раньше шли параллельно записи.

Переводим на записи в первую очередь: три draw, сбросы констант (объявления), смену целей, очистки, вьюпорт / ножницы (они и так
в `vkn_draw_in`), конец кадра. Во вторую (по счётчику синхронизаций): копии текстур, обновления текстур, UI.

## 4. Кадр и число кадров в полёте

Конец кадра — запись в потоке. Поток движка после неё сразу пишет следующий кадр. Переключатель `DM_VK_NATIVE_RT`:

| Значение | Смысл |
|---|---|
| 0 | потока нет, всё как после этапа 5.1 |
| 1 | поток есть, движок впереди не больше чем на 1 кадр (в конце кадра ждёт, пока поток записи закончит предыдущий) |
| 2 | движок впереди до 2 кадров (больше сглаживание, больше задержка ввода на кадр) |
| 9 | сверка: записи пишутся и тут же исполняются на потоке движка (поток не запускается) — проверяет кодирование без гонок |

Кольцо констант (`0x1380000`, ≈ 1.9 МБ на кадр) и промежуточные буферы должны переживать кадры в полёте GPU (3) плюс кадры
впереди (1–2): проверить правило оборота кольца и добавить в него счёт кадров впереди.

## 5. Приёмы цепочки `vkn_fx`

Цепочка исполняется на потоке записи внутри `prepare()` — как сейчас. Её чтения общего состояния:
- версии буферов (кэш теней) — берутся из записи (снятые при записи), а не из таблицы;
- номер заливки текстуры — меняется только обновлениями, а они в потоке записей или за синхронизацией: порядок верный;
- объявленные блоки констант, цели, раскладки — состояние потока записи, порядок верный;
- таблицы запросов видимости — при `DM_VK_NATIVE_COND` 1 / 3 поток записи выключается (вердикты читает движок); 2 и 4 допустимы.

## 6. Проверка

- хост-тест: тот же набор этапа 3 в режиме 9 (кодирование) и в режиме 1 (настоящий поток, под ThreadSanitizer) — последовательность
  команд Vulkan каждого кадра обязана совпасть с режимом 0 байт в байт (подставной Vulkan пишет журнал команд);
- телефон: `RT=0` против `1` против `2` при равных потолках частот; дамп целей `RT=1` равен дампу `RT=0`; строка
  `[vkn] rt:` — записей на кадр, синхронизаций на кадр по местам, ожидание потока движка в конце кадра, простой потока записи.

Ожидание: поток движка −4…6 мс на кадр; кадр упрётся в GPU (≈ 13.5 мс после 5.1) → 70+ fps стоя, если GPU успевает.
