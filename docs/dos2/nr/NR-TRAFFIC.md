# NR-TRAFFIC — память и трафик памяти в установившемся режиме (ночь 19.11, задача N5, ветка `dos2-nmem`)

Вопрос: сколько байт CPU двигает за кадр (игра → гостевая память → зеркала / стейджинг / кольцо → GPU), что из этого лишнее, и что
убрать. Рост памяти во времени и утечки — задача N4, DRAM-трафик GPU по проходам — N3; здесь только «байты на кадр» и «сколько копий
одного ресурса живёт». Телефона нет: всё из логов Mi 14 Ultra (Adreno 750, Turnip, sysmem), кода и хост-тестов.

## 4. Что сделано: `DM_NR_LINTEX` (pitch-linear текстуры, только написанные строки)
### 4.1 Находка
`play-1118/boot.log`: `NVN big texture hash (untracked) serial=30151 fmt=0x25 1424x1602x1 ... flags=0x10 size=9176256 stable=0 partial_why=0x20`
десятки раз подряд (`stable=0` — менялась при каждой проверке), рядом `partial texture upload serial=30853 fmt=0x11 1424x1602 blocks=5 bytes=40960`
(block-linear двойник того же размера обновляется кусками по 40 КБ → игра пишет мало строк). Это карта тумана / мини-карта уровня
(NR-BN: «открытие карты, большая текстура 1424x1602»; NB-18b-10: `EoCFog` читает «карту тумана»). В сегодняшних прогонах (O_ab_a1,
C_base) она та же (48 строк `big texture hash`). Pitch-linear (флаг 0x10) исключён из частичной заливки (`partial_why` бит 0x20), поэтому
каждое изменение = полный цикл ~45 МБ работы CPU.

### 4.2 Переключатель (умолчание 0 везде; `xbg_nr_lintex.inc`, ядро `dm/gfx/nr/nr_lintex.h`)
| | |
|---|---|
| `DM_NR_LINTEX=0` | старый путь, ничего не исполняется (все врезки за `nrlin::mode`; до init mode = −1) |
| `=1` | pitch-linear 2D цветная, 1 уровень / слой / срез, блок 1x1 с bpp 1/2/4/8/16, не BC / не декод / не ASTC / не NR-05, ≥ `DM_NR_LINTEX_MIN_KB` (256): **защита + штамп до чтения**, строки прямо в стейджинг (без обнулённого vector и второй копии), хэш не берётся (`cpu_hash=1`); проверка с записанными страницами → копируются только строки, задевающие эти страницы (`nrlt_runs`: группы по 16 строк, склейка через ≤ 4 чистых строки, ≤ 64 участков), в пролог подачи, если подача ещё не трогала текстуру (правило `gfx-upload-prologue`), иначе на месте; > 50 % строк 3 обновления подряд (`DM_NR_LINTEX_DENSE` / `_STREAK`) → текстура навсегда на старый путь (полная перезапись стоила бы ошибку страницы на каждую из 2 240 страниц на игровом потоке). Плюс: block-linear текстуры частичного пути защищаются **до** чтения заливки |
| `=2` | сверка: рисует как 0; на каждой заливке такой текстуры — сравнение строк, реально изменившихся с прошлой заливки (тень байт), со строками, которые назвал трекер: `MISSED` = красная строка, должно быть 0; считает, сколько скопировал бы режим 1 |
| `DM_NR_LINTEX_MIN_KB` 256, `_DENSE` 50, `_STREAK` 3, `_GAP` 4, `_SHADOW_MB` 64 | настройки |

Строки: старт `[nr] DM_NR_LINTEX=N (NR-TRAFFIC: …); … dirty tracker present, texture checks through it 1`; раз в 10 окон PERF
`[nr] lintex (DM_NR_LINTEX=N, NR-TRAFFIC, last S s): pitch-linear textures on this path T (given back G); full uploads …; partial P: rows R
copied of H checked (W written, X MB vs Y MB whole), Z ms, … ahead of the submission A / in place B (ended a pass C); hashes skipped …;
block-linear partial textures protected before their upload's read …; verify: uploads compared …, rows changed … / reported … of …, MISSED …,
would copy … of … MB, shadows … MB; tracker write faults …`. Частичные заливки идут и в «длинные кадры» (`重传 … MB`) — маленькими.

### 4.3 Попутная находка: защита после чтения теряет запись
Старый путь для block-linear частичных текстур (`xbg_game.cpp`, конец заливки): чтение → хэш → `nvn_dirty_protect` → штамп. Запись игры
между чтением и защитой падает на незащищённую страницу — ошибки страницы нет, поколение не растёт, трекер считает страницу чистой: строка
изображения устаревает до следующей записи в ту же страницу. `nr_lintex_test` (отрицательный контроль): 4 из 40 прогонов с порядком
«защита после чтения» оставляют устаревшую строку, при порядке «защита + штамп до чтения» 0 из 62 моделей × 150–300 раундов. Под
`DM_NR_LINTEX=1` порядок исправлен и для block-linear (`lin_pre`); при 0 — как было.

Вторая, узкая (окно — наносекунды между `nvn_dirty_protect` и `nvn_dirty_now`): ветка проверки делает «защита, потом штамп». Запись,
упавшая в защищённую страницу между ними, получает поколение ≤ штампа, а её store исполняется повторно после обработчика — возможно,
уже после нашего чтения; страница осталась записываемой, следующая проверка её не видит. И страница, которую другой поток держал BUSY во
время защиты, остаётся записываемой со старым поколением. Под `DM_NR_LINTEX=1` (`nrlin::protect_stamp`, для всех отслеживаемых текстур
ветки проверки): **штамп, потом защита**, повтор защиты, пока `nvn_dirty_version` не скажет «все страницы только для чтения» (≤ 8 раз;
иначе следующая проверка принудительная, `dirty_seen = 0`). Модель «store в полёте» (`nr_lintex_test` §5b, 40 × 300 раундов): штамп →
защита → чтение — 0 потерь, защита → штамп → чтение — 3 121 (в модели окна равновероятны; на устройстве окно в тысячи раз уже).

## 7. Прогоны телефона, которые решают (минимум 3, Форт Радости в ходьбе + с открытием карты / мини-картой; лучше бой из сейва)

| 2 | `DM_NR_LINTEX=1` | то же | `partial P` > 0, `rows … copied of … checked` ≪ 1, `given back 0` (или ≥ 1 — значит игра переписывает целиком, выигрыша нет), `hashes skipped`; `hash_sites texcheck/upload` → ≈ 0; длинные кадры без `重传 … 8.7 MB`; скриншот карты / мини-карты = как в прогоне 1 |
| 3 | база (без env) | то же, для ABBA с прогоном 2 | `submit_cpu_ms`, число и длина `[长帧]`, `parts hash` |
Умолчание менять только при `MISSED 0` в прогоне 1 и `given back 0` в прогоне 2; для слабых устройств — тот же прогон у тестера с Mali.

## 8. Не сделано / риски / идеи
- Ошибки страниц на игровом потоке: если игра пишет туман большими областями, но < 50 % строк, каждая запись в защищённую страницу
  стоит ~2–5 мкс; прогон 1 покажет `tracker write faults` (сейчас сессия play: 320 910 ошибок за ~25 мин по всем текстурам).
- `DM_NR_TRX_STICKY=1` / `DM_NR_TRX_ZC=1` (таблица, #3): уже умолчание приложения с `6a9a780` (поправка 19.11, раунд 2: в первой версии
  отчёта ошибочно «умолчание 0»); 1.9 МБ/кадр в тяжёлых окнах play-1118 — код до этого умолчания.
- Хэш после заливки block-linear частичных текстур тоже можно было бы пропускать (трекер отвечает), но там `partial_upload` может
  вернуть false и тогда нужен хэш; объём мал (почти весь `upload`-хэш — туман) — не делал.
- Двойная копия (гость → гостевая текстура → VkImage) для статичных текстур неизбежна, пока игра владеет хранилищем; освобождать
  гостевые страницы после заливки (`MADV_DONTNEED`) нельзя — игра может читать их снова.

## 9. Раунд 2, часть 1: порядок «штамп → защита до полной RO → чтение» — по умолчанию (исправление ошибки)
Гонки §4.3 — ошибки **пути по умолчанию** (не только `DM_NR_LINTEX=1`): все места, где транслятор копирует отслеживаемую память и потом
верит `nvn_dirty_since(stamp)`. Теперь по умолчанию везде один порядок, переключатель A/B `DM_DIRTY_PROTECT_ORDER` (1 умолч. / 0 = старые).
- Трекер (`dm/gfx/nvn/nvn_dirty.c`): `nvn_dirty_stamp_protect(addr, len, &whole)` — штамп, потом `nvn_dirty_protect`, повтор (≤ 8, с
  `sched_yield`), пока все страницы диапазона не в состоянии PROT; `whole = 0`, если так и не вышло (страницы GEN_STICKY после отказа
  mprotect, страница BUSY 8 раундов). `nvn_dirty_safe_order()` (строка `[vma] dirty tracker: DM_DIRTY_PROTECT_ORDER=…` один раз),
  `nvn_dirty_order_stats`.
- Места (`xbg_game.cpp`, `xbg_nr_buf.inc`; при `=0` — старый текст без изменений):
  | Место | Было | Стало | `whole = 0` |
  |---|---|---|---|
  | vcache (копии вершин между кадрами) | штамп, защита (без повтора) | помощник | копия только на этот раз (VOLATILE), не в кэш |
  | ветка проверки отслеживаемой текстуры | защита, потом штамп (B) | помощник | старый штамп сохраняется (записи той страницы новее него), `dirty_seen = 0` |
  | untracked → tracked (4-я стабильная проверка) | защита, штамп, хэш (B) | помощник, хэш | остаётся на хэш-проверках |
  | конец заливки текстуры частичного пути | чтение, хэш, защита (A) | защита до чтения (`lin_pre`) | `dirty_stamp = 0`, хэш-проверки каждую подачу |
  | NR-06 статические VB / IB | штамп, защита (C) | помощник | буфер понижен на старый путь |
  NR-SHCACHE уже безопасен (версия требует, чтобы все страницы были PROT). `DM_GAME_ETERNAL`-ветки (`nvn_sparse_*`) в DOS2 не собираются.
- Доказательство на настоящем трекере: `dm/gfx/tests/t_dirty_order.c` (включает `nvn_dirty.c`, настоящий `mprotect`, настоящий SIGSEGV через
  тот же хук; ступени через перехват `mprotect`): A / B / C — старый порядок теряет поставленную запись **20 / 20**, новый **0 / 20**;
  нагрузка (2 пишущих потока, 64 страницы, 6 × 150 мс): старый 0–4 / 6 прогонов с устаревшей страницей, новый **0 / 6** (3 запуска).
  Модельный `nr_lintex_test` §5b — то же для «store в полёте».
- Цена: одна загрузка `g_now` и один проход по состояниям страниц на защиту; повтор только при BUSY. Ошибок страниц не больше (те же
  страницы; на заливке — раньше, так что записи во время чтения теперь ловятся). Mi 14 / слабые: ≈ 0 мс; это исправление корректности.
- Строка раз в 10 окон PERF: `[vma] dirty order (DM_DIRTY_PROTECT_ORDER=1, …): N stamp+protect calls, R protect rounds repeated (a page was
  busy), W copies never wholly read-only`. Прогон, который это подтверждает: любой обычный прогон (строка есть, `W` ≈ 0); A/B
  `DM_DIRTY_PROTECT_ORDER=0` против базы — fps / ошибки страниц равны в пределах шума.
- Для других портов: `port-common/modules/dirty-order` (manual) + `port-common/migration/dirty-order.md` (места каждого дерева с номерами
  строк: D16 / ETR / D3 / TL2 / XC2).

## 10. Раунд 2, часть 2: память — stream-арена держит чанки загрузки до конца игры (`DM_NR_ARENA`)
**Находка.** Самый большой не ограниченный никем потребитель из §3 — стейджинг: у каждого из двух слотов кадра своя stream-арена из
чанков по 32 МБ (host-visible device memory, на Adreno — kgsl, ядро считает её памятью приложения). `Arena::trim` после каждой подачи
оставляет до **6** стандартных чанков на слот (правило DOOM: «кадр берёт ~100 МБ, не дёргать kgsl»). DOS2 берёт 0.2–1.6 МБ на подачу
(медиана `arena_peak_mb`), но на загрузках уровня 58–92 МБ (максимумы O_ab / C_base / D_sim / play-1118 / live-1118) — после первой же
загрузки слот держит 2–3 чанка (64–96 МБ) навсегда, оба слота — 128–192 МБ.
**Что сделано** (ядро `dm/gfx/nr/nr_arena.h`, движок `namespace narena` в `xbg_game.cpp`, одна точка — `trim` слота при его отставке):
| | |
|---|---|
| `DM_NR_ARENA=0` (умолч.) | старое правило (до 6 чанков на слот) |
| `=1` | держать максимум чанков, которые трогала подача этого слота за последние `DM_NR_ARENA_HOLD` (600) подач, не меньше 1; рост — сразу, сжатие — только в конце окна (~20 с при 60 fps); запрос NR-29 (уровень ≥ 1) — сразу до нужды последней подачи |
| `=2` | старое правило, считает, сколько держало бы `=1` и сколько раз пришлось бы выделять заново |
Строки: старт `[nr] DM_NR_ARENA=N (NR-TRAFFIC): …`; раз в 10 окон `[nr] arena (DM_NR_ARENA=N, last 10 windows): stream chunks a slot a / b =
X MB held, rule 1 would hold Y MB; readback Z MB; freed F MB in T trims, regrown R times`. Вывод кадра бит в бит (только стейджинг).
**Цифры.** Повтор по логам (`arena_replay.py`, scratchpad: окна по 60 подач, пик окна — одной подаче слота, остальные — 1 чанк):
| Лог | старое правило, в среднем | `=1` | перевыделений `=1` |
|---|---|---|---|
| O_ab_a1 (стоя, 2.5 мин) | 123 МБ | 83 МБ | 3 (на загрузке) |
| C_base (ходьба) | 124 МБ | 78 МБ | 3 |
| D_sim (путь Mali) | 122 МБ | 88 МБ | 3 |
| play-1118 (25 мин игры хозяина) | 155 МБ | 72 МБ | 11 (0.008 на окно) |
| live-1118 (живой стрим, бой) | 188 МБ | 80 МБ | 53 (0.012 на окно) |
Установившаяся игра после загрузки: 64 МБ (по чанку на слот) против 128–192 МБ — **−64…128 МБ**, в среднем по сессиям −40…108 МБ.
| Класс телефона (MemTotal) | бюджет NR-29 на все кэши NR | что даёт `=1` |
|---|---|---|
| 6 ГБ (~5.5 ГиБ) | 192 МБ (`nrm_tier_budget`) | −64…128 МБ: треть–две трети всего бюджета кэшей NR; меньше риск LMK в фоне / на загрузке следующего уровня |
| 8 ГБ (~7.4 ГиБ) | 384 МБ | −64…128 МБ |
| 12+ ГБ (Mi 14) | без капа | −64…128 МБ, fps не меняется |
| 4 ГБ (если запустится) | 96 МБ | −64…128 МБ — больше всего бюджета NR |
Цена: перевыделение 32 МБ чанка (vkAllocateMemory + vkMapMemory, ~1–5 мс, оценка) раз в 1–2 мин, на загрузках. **Умолчание 0** (правило
«умолчание — только бит в бит и бесплатно»: бит в бит — да, бесплатно — почти; кандидат на умолчание для 4/6/8 ГБ после одного прогона).
**Тест:** `nr_arena_test` (3 040 575 проверок: случайные трассы против эталона окна — предел ≥ нужды последней подачи, сжатие только в
конце окна / по запросу; трасса DOS2: загрузка 3 чанка → игра 1 — `=1` держит 1 чанк после одного тихого окна, старое — 3, один рост на
следующей загрузке). **Прогон:** `DM_NR_ARENA=2` (счёт) и `=1` — ходьба 60 с после загрузки сейва + переход в другую зону; решают строка
`[nr] arena` (held / would hold, regrown) и `dumpsys meminfo org.dos2.port` (Graphics / EGL mtrack) против базы; fps и длинные кадры равны.

## 11. Раунд 2, часть 3: точки синхронизации CPU ↔ GPU за кадр — убирать нечего (с доказательствами)
