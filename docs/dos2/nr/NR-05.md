# NR-05 `DM_NR_TEX` — текстуры по событиям движка (сегмент S2a), 17.11.2026, ветка `dos2-nr05`

Шаг NR-05 из `NATIVE_RENDERER_PLAN.md` (§2 S2a, §3, риск §6.3). Основа — NR-01 (хуки `CreateTextureFromImage 0x91f2e0`,
отложенного удаления `0x91d630`, тап NVN). Собрано и проверено на ПК; **на телефоне не запускалось**. Умолчание `0`.

## Что сделано
1. **Событие создания.** Хук NR-01 `CreateTextureFromImage` после возврата (данные картинки уже в памяти пула: упакованные — файл,
   линейные — `WriteTexels` внутри того же вызова) передаёт в таблицу NR-05 NVN-серийник текстуры, её описание / раскладку / адрес
   хранилища и NVN-объект. Тап `nvnTextureInitialize` теперь отдаёт ещё серийник, хранилище, `nvn_texdesc` и `nvn_texlayout`.
2. **Рабочий поток** (один, nice 10, `hle_dos2_nr.c`): по событию — GOB-deswizzle всего хранилища в blob ровно в раскладке staging
   `get_image_slow` (`DM_GFX_DESWZ_DIRECT`: слой снаружи, уровень внутри, начала по 16 Б, pitch = блоки × байт на блок) и, если включён
   ASTC-кэш текстур, его ключ (CRC-32 + Adler-32 хранилища — функция самого движка `xbg_astc_storage_key`). Вокруг чтения берётся
   **проба** — 33 выборки по 32 Б, равномерно по хранилищу (`nr_tex_probe`); если хранилище менялось во время чтения — blob выброшен.
3. **Первая заливка** (`xbg_game.cpp`, namespace `nrtex`): образ материальной текстуры (живая запись, источник image-packaged /
   image-linear) становится «статичным». Если blob готов и проба хранилища совпадает с пробой blob — staging = одна копия blob в
   stream-буфер вместо deswizzle на трансляторе. **Полный хэш после заливки не считается** (на телефоне он стоит столько же, сколько
   сам deswizzle, см. числа ниже).
4. **Без tex-dirty и стабильных хэш-проверок** для статичных образов: не ставится mprotect, вместо хэша на прежнем расписании
   (каждую подачу первые 4 раза, потом каждую 16-ю) — проба. Перезаливка только по событиям:
   - `nvnTextureWriteTexels(Strided)` в эту текстуру — точное событие (новый тап, счётчик записей у записи; движок переспрашивает
     только когда сдвинулась общая эпоха записей);
   - проба изменилась — перезаливка (поздняя запись стримера не теряется), **кроме** текстур, которые движок уже отдал на отложенное
     удаление (хэндл уничтожен, NVN-объект ещё не финализирован): там новые байты — другого владельца, ни один новый кадр её не
     рисует, перезаливка не нужна (это и есть «смена владельца памяти» из §6.3);
   - явные инвалидации старого пути (копии / CPU-диапазоны / замена ASTC-кэшем) работают как раньше.
5. **ASTC (Mali / PowerVR / Xclipse без BC).** Пак setup и ленивый кэш не тронуты: поиск / заливка / «changed later» / «filled later»
   идут прежним кодом, только ключ `astccache::key` берётся у рабочего потока (если проба совпала) — транслятор не хэширует хранилище
   ни при поиске, ни в `offer`, ни в `would_hit`. Перекодирований становится меньше ровно настолько, насколько исчезают перезаливки
   (см. «Ожидаемый выигрыш»). Форматы, которые транслятор на этом устройстве берёт не как есть (BC в декодер / из кэша), рабочий поток
   по «вердикту» больше не готовит в blob (только ключ).
6. **Отказы всегда — прежний путь:** нет blob (ещё в работе — работа отменяется; мал / велик / формат / бюджет / устарел), образ —
   псевдоним чужого хранилища (статичность снимается), запись давно вытеснена — всё идёт старым кодом.

## Переключатель `DM_NR_TEX` (по умолчанию 0; включает реестр NR-01 как `DM_NR=1`, если `DM_NR` не задан)
| Значение | Что делает |
|---|---|
| 0 / нет | ничего: нет таблицы, нет потока, движок читает `g_dm_nr_tex == 0` один раз; все хуки `nrtex::` за `nrtex::mode>0`; тапы — `NRT(...)` (загрузка + непринятый переход, только при `DM_NR`≠0) |
| 1 | как описано выше: blob на первой заливке, без полного хэша, без tex-dirty, проба + WriteTexels + отложенное удаление |
| 2 | **сверка**: исполняется старый путь целиком; плюс полный хэш хранилища в событии (поток движка), рабочий поток готовит blob и ключ; на первой заливке: хэш события ↔ хранилище (`storage changed since the create event`), blob ↔ staging старого пути побайтно (`blob compares / mismatches`), ключ ↔ ключ старого пути; на каждой хэш-перезаливке живой материальной текстуры — красная строка «memory written after creation», увидела ли её проба (`probe saw / MISSED`), отдельно — перезаливки уже уничтоженных движком (`engine-destroyed … owner change`) |
| 3 | как 1, но изменившаяся проба **не** перезаливает («залить один раз» в чистом виде): красные строки показывают, что осталось бы устаревшим (A/B для глаз) |

Тонкая настройка (env, игрокам не нужна): `DM_NR_TEX_PREP_MB` — бюджет blob (по умолчанию RAM/64, 32…128 МБ; работа ждёт, пока
бюджет занят), `DM_NR_TEX_MIN_KB` (16) — меньшие текстуры без blob, `DM_NR_TEX_AGE_S` (30) — невостребованный blob освобождается.
Максимум одного blob — ¼ бюджета.

## Ожидаемый выигрыш (оценка, не замер)
| Класс | Что даёт `=1` |
|---|---|
| Mi 14 / Adreno 750 (BC нативно) | первая заливка материальной текстуры с готовым blob: 0.4–0.73 → ≈ 0.1 мс/МБ на трансляторе (копия в stream-буфер; без deswizzle и хэша). Кадр входа 82 МБ / 60 мс → ≈ 10–20 мс (зависит от доли материальных байт с blob и от п. «повторные»). Повторные: если это смена владельца (`engine-destroyed` в `=2`) — уходят целиком (пары 51.8 МБ кадров исчезают); если поздние записи живых — остаются, но без полного хэша (≈ −50 %). Устойчивый кадр: −0.05…0.1 мс. fps на Mi 14 не изменится (упор в GPU) — смотреть `[长帧]` и `提交+出图` |
| S7 / Adreno 7xx (слабый CPU) | то же ×2–3 по абсолюту: хитч входа ~150 мс → ~40–60 мс; стрим при беге по карте 10–30 мс → 2–10 мс |
| Mali / PowerVR / Xclipse (без BC) | 91 % байт DOS2 — BC1–BC3 → декодер / ASTC-кэш, blob к ним не применяется (только к ~9 % не-BC). Выигрыш: (1) нет полного хэша после заливки у всех материальных; (2) ключ ASTC с рабочего потока: транслятор не считает CRC + Adler (ab7rp3, SIM mali: 16.7 мс на 256 поисков ≈ 65 мкс, на MTK ×2–3) при поиске / `offer` / `would_hit`; (3) **перекодирования вдвое реже — ровно если повторные заливки — смена владельца** (тогда каждая исчезнувшая перезаливка = исчезнувший BC-декод / повторный поиск / копия в очередь кодера); если это поздние записи — их перекодирование остаётся (как и должно). Хитчи при беге по карте: −(хэш + ключ) на каждую новую текстуру |
| Слабый CPU вообще | рабочий поток на nice 10 берёт deswizzle и ключ на себя (одно ядро, ~0.27 мс/МБ на X4, ×2–3 на A7x); поток игры / транслятор не ждут его никогда |

Память: blob живут от события до первой заливки (бюджет RAM/64, 32–128 МБ, пик на загрузке уровня); невостребованные — 30 с.

## Риски (честно)
1. **Посылка «данные готовы в событии»** — из разбора §0, не замерена. Если нарушена: blob отвергается пробой (`no blob: stale`),
   статичный образ всё равно ловит изменения пробой; `=2` считает `storage changed since the create event`.
2. **Поздняя частичная запись живой текстуры мимо `WriteTexels` и мимо 33 выборок пробы** — в `=1` осталась бы устаревшей. `=2`
   считает `probe MISSED`. Если там не 0 — `=1` не включать (или включать только blob + пропуск хэша после заливки, оставив старые
   хэш-проверки — отдельный режим, не сделан).
3. Рабочий поток читает память гостя, пока текстура жива на старте работы; если движок финализирует и **освободит с размапом** пул
   за ~1 мс чтения — теоретически сбой (отложенное удаление движка ждёт кадры, окна практически нет).
4. «Движок удалил» берётся по первому вызову `0x91d630` для объекта. Если удалённая текстура всё же сэмплируется позднее (старый id в
   пуле текстур) — показываем прежние байты, а не байты нового владельца (старый путь показал бы чужие — оба неверны, наш ближе к Switch).
5. Прямая адресация 32 768 серийников: очень старая живая текстура теряет запись (только для новых образов; счётчик `slot reuse`).
6. `=2` медленнее на загрузках (полный хэш в событии, ещё один на первой заливке, чтение staging для сверки) — только диагностика.
7. Общие файлы (`hle_nvn.c`, `xbg_game.cpp`) правят другие ветки: правки — 3 строки `NRT` и точечные вставки в `get_image_slow`.

## Не сделано / дальше
- Рабочий поток не создаёт `VkImage` и не пишет сразу в `VkBuffer` (как ETR TEXSTREAM PERF-E11): убрало бы и копию в stream-буфер,
  и `vkCreateImage` + `vkAllocateMemory` (HITCH_AUDIT п. 4, 40–50 мс остатка) — следующий шаг, если `=1` подтвердится.
- Предвыборка блоков пака setup (`pread`) рабочим потоком для GPU без BC; CPU-декод BC на рабочем потоке (не нужен: GPU-декодер быстрее).
- `CreateTexture` с `initData` (`create-data`) и RT как «нативные» (точные usage, R8 `LEAN_USAGE`) — не здесь.
- Умолчание по детекту в `xbg_vendor_policy.h` — после телефона.

## Прогон на телефоне (главный агент; бэкап `files/save`, после — force-stop)
APK этой ветки: `wt-nr05/work/DOS2-port-debug.apk`. Сцена: меню → загрузка сейва → **2–3 мин бега по карте со сменой локации**
(стример!), инвентарь / карта; ≥ 40 с после загрузки.
1. **R-NR05a, сверка:** `dm/env`: `DM_NR_TEX=2` (можно вместе с R1 NR-01: `DM_NR=2 DM_NR_DUMP=1`). Ждём в логе:
   `[nr] DM_NR_TEX=2 (verify …)`, `NVN nr-tex DM_NR_TEX=2: …`; раз в 10 с `[nr] textures by events (DM_NR_TEX=2): events N (packaged …,
   linear …), jobs …, prepared …, engine destroys …`; `NVN nr-tex verify: first uploads N, storage changed since the create event A;
   re-uploads of live material textures B: probe saw C, missed D; of engine-destroyed ones E; blob compares F, mismatches G; …`.
   Решение: **G = 0** (blob верен), **A ≈ 0** (посылка §0 верна), **D = 0** (проба достаточна) → `=1` безопасен; **E / (B + E)** — доля
   «смены владельца» в повторных заливках (столько повторных исчезнет в `=1`; это ответ на §6.3).
2. **R-NR05b, включено:** `DM_NR_TEX=1`, тот же маршрут, A/B с прогоном без него (ABBA при желании). Ждём: `first uploads from the
   worker's blob N (… MB, … ms on this thread)`, `no blob: …` (сколько `pending` — рабочий не успел), `probes … changed …
   (engine-destroyed kept …)`, `full hashes skipped …`; в `[长帧]` — `上传贴图 … MB / N ms` в событиях входа и стрима заметно меньше,
   чем в базе (82 МБ / 60 мс, 43.6 МБ / 10 мс, пары 51.8 МБ); глазами — нет старых / мусорных текстур при беге.
3. (по желанию) **SIM mali:** `DM_GFX_SIM_GPU=mali DM_NR_TEX=1`: `ASTC keys from the worker N`, в `NVN astc cache: … hashing X ms`
   меньше, чем без NR-05; `uploads first … decoded … astc …, again …` (повторные декоды / ASTC = перекодирования).
