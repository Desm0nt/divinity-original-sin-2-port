# NR-HEAT `DM_NR_HEAT` — постоянный журнал «тепла» шейдеров и проходов (основа для NR-33 и NR-32)

Ветка `dos2-nrheat` (worktree `wt-nrheat`, база `dos2-nr-all` 4006c30). На телефоне **не запускалось** (телефона не было); всё ниже — ПК:
тесты, сборка APK, прогон инструмента на логах телефона 17.11. Задача хозяина: логгер, который **всегда включён** в обычной игре, чтобы по
его логам (форт, города, лес, вода, бой, частицы) выбрать 20–30 самых тяжёлых шейдеров для нативной переписи (NR-33) и направлять работу
переводчика (NR-32). Условие: «только если нет накладных расходов» — цель < 0.05 мс на кадр в среднем на CPU и GPU, без рывка в момент замера.

## 1. Решение: выборка, а не трасса

| Часть | Как | Почему так |
|---|---|---|
| Какие кадры | один кадр раз в `DM_NR_HEAT_S` = 20 с (первый через 30 с) | при 60–100 к/с это 1 кадр из 1200–2000; кадр с замером дороже на ≈1 мс GPU (ниже), в среднем ≈0.0005–0.001 мс |
| Время GPU | существующий профайлер проходов (`DM_GFX_PASS_PROF`): по одной паре `vkCmdWriteTimestamp(BOTTOM_OF_PIPE)` **вне** render pass вокруг каждого прохода / dispatch | внутри прохода на тайлерах (Adreno binning, Mali, PowerVR) времени по draw нет — бинниг идёт по всему проходу; поэтому только границы проходов |
| Что рисовалось | в том же кадре на проход: список программ (VS, FS) с числом draw и вершин, размер цели, формат, число вложений | счёт идёт в уже существующем хуке `pass_prof_draw` (вызывался и раньше на каждый draw и сразу возвращался вне замера); в кадре только-heat **без** строк GPASS (их ключи-строки строились бы на каждый draw) |
| Кто считает | после забора кадра (fence) поток трансляции переводит метки в мкс и ключи в id (десятки мкс на замер) и отдаёт **потоку `dm-nrheat`** (nice 10): тот агрегирует по уровню и пишет файл | никакой записи в файл, хэширования, сортировки на потоках игры |
| Цена шейдера | на каждый загруженный ключ поток `dm-nrheat` считает SPIR-V, **которую получил драйвер этого устройства** (после всех переписываний): инструкции, ALU, трансцендентные, текстуры, ветвления, циклы, загрузки UBO (с динамическим индексом), bitcast; `cost = alu + 4·trans + 4·tex + 2·ubo_dyn + 2·branch` | копия SPIR-V при загрузке (мкс), счёт — на потоке-писателе; NR-04 / NB-18 видно (`src` = `nr` / `f`) |
| Деление времени прохода | три оценки: по доле draw, по доле вершин, **по draw × (цена FS + цена VS)** внутри каждого прохода (формула хозяина «время прохода × доля draw × цена») + полное время проходов, где программа была | покрытия пикселей по draw нет (см. §7) |
| Где игрок | `hle_dos2_heat.c`: таблицы файлов LSPK пяти пакетов с уровнями (Origins / Arena / Shared / Minimaps / CommunityMods) → смещение чтения → `.../Levels/<имя>/` или `.../Globals/<имя>/`; голосование по прочитанным байтам | загрузка уровня читает мегабайты одного уровня (TUT_Tutorial_A 1.4 МБ, FJ_FortJoy_Main 30 МБ, RC_Main 40 МБ упаковано); имя движка из памяти не нужно |
| Файл | `Download/DivinityOriginalSin2Mobile/logs/shader-heat.tsv` (рядом с `boot.log`, `DM_LOG_DIR` из `jni_android.c`), только дописывание, сброс блоков раз в 5 мин и при смене уровня, 4 МБ + один предыдущий `shader-heat.1.tsv` | игроки уже присылают папку `logs` |
| Строка лога | раз в минуту `[nr] heat (60 s, <уровень>): …` | видно в `boot.log` без файла |

### Совместимость (проверено по коду)
- `DM_GFX_PASS_PROF` включён → heat **не берёт свои кадры**, а читает кадры профайлера (их строки GPASS / GVAL как были). `DM_GFX_PASS_VALUES`
  (GVAL) в кадрах только-heat не работает (`passval::on()` требует `pass_prof_enabled`).
- NR-14 (`DM_GFX_SAMPLES_TS` авто 0): отчёты samples — свой путь и пул; метки heat — пул профайлера.
- NB-20b (`DM_NB_MT=3`): `vkCmdWriteTimestamp` / `vkCmdResetQueryPool` — обычные пакеты, порядок тот же. `DM_NB_MX`: контекст draw не тронут
  (`pass_prof_log` — класс D в таблице NB-20a).
- Поток present / NR-20 поворот / NR-11: после проходов кадра, не задеты. NR-21 (сортировка): отметка программы — в момент постановки draw, как
  и счёт `pass_prof_draws`.
- `draw()` и полоса NR-09 (`xbg_nr_draw.inc`, тождество draw в `hle_dos2_nr.c`) **не тронуты** — проверяет `source_structure_test.py`.

## 3. Переключатели
| Ключ | Значения |
|---|---|
| `DM_NR_HEAT` | **0** — ничего: нет выбора кадров, потока, файла, хуки fs только чистят свой байт (профайлер как раньше, байт в байт по поведению); **1** — умолчание DOS2 (`jni_android.c`, все семейства GPU; `dm/env` `DM_NR_HEAT=0` побеждает); **2** — тест на телефоне: каждый кадр пачки `DM_NR_HEAT_BURST` (120) раз в `DM_NR_HEAT_S`, строки `P` по каждому проходу, блок после каждой пачки; другое — красная строка и 0. Без меток времени у очереди (`timestampValidBits` = 0) — строка и 0 |
| `DM_NR_HEAT_S` | 20 (1…3600) с между замерами |
| `DM_NR_HEAT_FIRST_S` | 30 — первый замер (меню / загрузка тоже пишутся — со своим «уровнем») |

## 4. Формат `shader-heat.tsv` (полностью — в `nr_heat.h`)
```
H  v=1 unix= mode= period_s= first_s= burst= flush_s= gpu= vendor= device= driver= ts_ns= app=      начало записи этого запуска / после ротации
L  unix t_s level score_kb previous                                                      смена уровня
F  unix t_s level frame slots passes cpasses draws span_us pass_us compute_us fps skipped   один кадр-замер (fps между замерами)
P  frame i kind us WxH fmt att draws verts vs/fs/draws/verts,...                        проход кадра (только DM_NR_HEAT=2)
S  key stage words src inst alu trans tex branch loops ubo ubo_dyn bitcast cost         ключ, раз на файл (src x / nr / f)
B  unix t_s level frames passes draws span_us pass_us compute_us                        блок: итоги уровня с прошлого блока
A  kind WxH fmt att vs fs frames passes draws verts us_draw us_vert us_pass us_cost     строка блока (суммы с прошлого блока)
```
Размер: строка `F` ≈ 80 Б × 180 в час; блок ≈ 100–400 строк × ≈ 110 Б раз в 5 мин → ≈ 0.5–1 МБ в час; 4 МБ + предыдущий = много часов.

## 5. Инструмент `tools/dos2_shader_heat.py`
```
python tools/dos2_shader_heat.py <logs>/shader-heat*.tsv [boot.log / *.dm.log с NVN GPASS] \
    [--programs <work>/shaders-jobs/programs.tsv] [--pack <work>/shaders-vk/shaders.xgspack] [--top 30] [--level FJ_FortJoy_Main] \
    [--min-passes 20] [--json out.json] [--keys-out top_fs.txt]
```
- Входы смешиваются: файлы heat и логи с GPASS (кадр GPASS = замер; уровень — из строк `[nr] heat: location`, иначе имя файла).
- Имена: `programs.tsv` (по умолчанию ищется в `../work/shaders-jobs/`; ключи одинаковы у всех игроков), NR-04 — по `dm/gfx/nr/nr_sh.c`, NB-18 —
  по префиксу `F1.` / `F1A.` …
- Цена: по паку (плюс оценка живых значений SSA — прокси регистров), иначе из строк `S` устройства. `est` = деление по цене внутри прохода
  (устройство: столбец `us_cost`; GPASS + `--pack`: то же в инструменте), без цены — доля draw.
- Вывод: по всем уровням (вес = число кадров-замеров уровня) и по каждому уровню — проходы по сигнатуре (WxH, формат, вложения) с FS, у
  которого больше всего времени; топ программ (`est_ms`, доля, `draw_ms`, `vert_ms`, `pass_ms`, draw и вершины на кадр, FS / VS, имя, `src`,
  статическая цена); в конце **кандидаты NR-33** — FS / CS по сумме `est`, только транслированные (без `nr` / `f`). `--keys-out` — список
  ключей для `dos2_spvopt_cost.py` / malioc (NR-25).

Прогон на существующем логе телефона (`src/work/logs/nr10_gpass.dm.log`, Mi 14 Ultra, палуба, `DM_GFX_PASS_PROF=300,180,0`, 51 кадр по 43
прохода, `--pack`, `--min-passes 20`): кадр-замер — span 10.29 мс, проходы 9.40 мс; сигнатуры: освещение 2160x972 R11G11B10 2.60 мс (27.6 %),
прозрачные 1.93 мс, G-buffer 1.77 мс, хвост поста F1A 1.05 мс; кандидаты NR-33: `RS3_Surface_Blood_ST_DEF_NX` 1.23 мс (13 %),
`RS3_Cloud_Steam_STI_FOR_NX` 0.70, `RS3_Surface_CloudShadow_ST_FOR_NX` 0.62, `TR_Layer_PBR_ST_DEP_NX` 0.60, `Base_AlphaTest_PBR_ST_DEF_NX`
0.34, `PPBloomUpsampleAndBlur` 0.32, `DeferredFog` 0.24, `CombineUI_NoFetch` 0.22, … Это одна сцена (палуба) — не выбор, а проверка, что цепочка
работает; выбор — по логам форта / городов / боя.

## 6. Цена (оценка + уже снятое с телефона)
- **Между замерами** — ничего нового: хуки профайлера в `pass_prof_draw` / `pass_prof_reserve` уже стояли и возвращаются на `!s.prof`;
  добавлено одно сравнение `nrheat::mode` на подачу и вызов `timing_clock()` на начало кадра; хук `ReadFile` — проверка байта; открытие файла —
  сравнение имени с пятью строками. Поток `dm-nrheat` просыпается раз в секунду (nice 10).
- **Кадр с замером:** GPU — 2 метки на проход: палуба 43–45 проходов → +≈1 мс на этот кадр (span замера 10.3 мс против медианы 9.1);
  CPU потока трансляции — учёт программ ≈ 10–30 нс на draw (1265 draw) + перевод записей после fence (строка `convert … us a sample` в
  минутной строке), ≈0.05–0.15 мс на этот кадр. Рывка нет: +1 мс к одному кадру из ≈2000.
- **В среднем (20 с, 100 к/с):** GPU ≈ 1 мс / 2000 = **0.0005 мс**, CPU ≈ 0.15 мс / 2000 = **0.0001 мс** — в 100 раз ниже цели 0.05 мс.
  Mali / PowerVR: метки между проходами останавливают перекрытие проходов только в этом кадре; цена кадра-замера может быть 2–3 мс — в
  среднем всё равно ≈0.001–0.002 мс. Слабые CPU: ×2–3 к CPU-числам, тот же порядок.
- **Уже снятое A/B (тот же механизм, в 10 раз чаще и дороже):** `nr10_base` ↔ `nr10_gpass` (Mi 14 Ultra, палуба, 60 с, `DM_DOS2_FPS=0`):
  профайлер на каждом 180-м кадре + строки GPASS + GVAL — fps 102.5 → 102.1, GPU медиана 9.09 → 9.11 мс, submit CPU 9.04 → 9.01 мс: в шуме.
  heat берёт кадр в ≈11 раз реже и без строк / GVAL.

## 7. Чего нет / риски
- **Покрытие пикселей по draw не меряется.** Время внутри прохода делится по draw × статическая цена (и по draw / вершинам). Счётчики
  occlusion на каждый draw дали бы покрытие, но конфликтуют с запросами игры / NR-03 (в Vulkan нельзя вложить запросы одного типа) и
  стоят внутри прохода — отложено. Проходы из одного draw (свет, туман, пост, тени) измеряются точно.
- **Место — с точностью до уровня**: форт и окрестности — один `FJ_FortJoy_Main`; города Arx / Driftwood — свои уровни или части
  `ARX_Main` / `RC_Main`. Внутри уровня — время (`t_s`, unix) в строках `F` / `B`; хозяин может отметить время сцены. Голосование:
  ≥ 256 КБ и ≥ 3× текущего, полураспад 1 с; строка `[nr] heat: location A -> B (… KB …; runner-up …)` показывает основание.
- Пакеты с `.holes` (их у уровней нет) не читаются — строка 【红】 и «без места».
- Кадры меню и загрузки пишутся под своим уровнем (`ORI_Menuscreen_A` — фон меню, ожидаемо); фильтр инструмента `--min-passes`.
- Ключи, загруженные до `init()`, не получат строку `S` — инструмент возьмёт цену из пака.
- Имена программ в игре не пишутся (`programs.tsv` на ПК даёт их по ключу).
