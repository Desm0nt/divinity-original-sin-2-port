строке; все тесты после слияния проходят). Аудит: `AUDIT-REMAINING.md` строка NR-21. **На телефоне не исполнялось ни строчки** (adb не трогал).

## 1. Что сделано
Draw, которые обслужил короткий путь NR-09 (`nrdraw::lane`, `DM_NR_DRAW=1`), уже несут всё для своих команд: пайплайн из прямой таблицы,
набор + динамические смещения, свёрнутые привязки вершин / индексов, viewport, scissor, аргументы draw. Если такой draw **не зависит от
порядка** (§2), `lane()` делает весь свой учёт как раньше, но команды не пишет, а отдаёт их `nrsort::take()`: draw встаёт в **сегмент**.
Сегмент записывается (в порядке режима) перед **первой любой другой командой** на этом командном буфере:

| Кто закрывает сегмент | Как |
|---|---|
| любой `vkCmd*` транслятора | все 35 обёрток `xbg_nb_mt.inc` (они уже были единой воронкой всех `vkCmd*` единицы трансляции для `DM_NB_MT`) первым оператором зовут `NBMT_PRE(c, op)`: если у `c` есть ждущие draw — `nrsort::cut` пишет их до команды. Конец прохода, clear, запросы, штампы, барьеры, push constants, условный рендер, draw другого пути — всё сюда |
| конец подачи / `nbmt::sync` | `NBMT_PRE` в `nbmt::end` (прямо перед `vkEndCommandBuffer`) и в `nbmt::sync` |
| draw, который пишется сразу | `lane()` для draw, не прошедшего условие, и старый хвост `draw()` — **перед чтением кэша привязок** (`nrsort::flush_draw()`): кэш должен описывать то, что реально привязано |
| `BeginRenderPass` при открытом сегменте | невозможно (конец прохода всегда идёт через `EndRenderPass` и закрывает сегмент); если бы случилось — draw легли бы вне прохода, поэтому сегмент **выбрасывается** с красной строкой |
| новый командный буфер | `nrsort::cb_begun()` перед `nbmt::begin` — очередь, пережившая свой буфер, считается ошибкой (красная строка) и выбрасывается (не ожидается: подача закрывает её раньше) |

Записываются ждущие draw теми же правилами кэша привязок, что и `lane()` (одна команда на сменившуюся привязку; `emit()` = 8 команд `lane()`).
После сегмента кэш привязок **точен**, если сегмент закрыл путь draw или команда, которая ничего не привязывает (конец прохода, clear,
запрос, штамп, барьер, копия); **сбрасывается**, если сегмент закрыла привязка / push constants / draw / dispatch чужого пути (маскированный
clear сбрасывает кэш и привязывает свой пайплайн — кэш не должен остаться «нашим»).

Порядок внутри сегмента (`nr_sort.h nrs_order`, устойчивая сортировка подсчётом, O(n)): по **первому появлению** ключа 1, затем ключа 2,
затем ключа 3, затем исходному индексу. `DM_NR_SORT_KEY=0` (умолчание): viewport + scissor → пайплайн → первый вершинный поток (каскады
атласа теней остаются целыми, внутри каскада — по пайплайну); `=1`: пайплайн первым.

## 2. Условие и доказательство (бит в бит)
**Сегмент** — серия draw, записанных подряд в один экземпляр render pass одного командного буфера, **без единой другой команды между ними**
(любая другая команда закрывает сегмент раньше — это гарантирует воронка `NBMT_PRE`, тест `nr_sort_hook_test.cpp`). Переставляются только
draw одного сегмента, целиком; порядок примитивов внутри draw — API, не трогается. Каждый draw сегмента удовлетворяет `nrs_why() == NRS_OK`:

| # | Условие (`take()` по `state` — тем же выражениям, из которых `draw()` строит пайплайн, `xbg_game.cpp` блок `VkPipelineDepthStencilStateCreateInfo ds…`) | Почему нужно (контрпример в `nr_sort_test.c`) |
|---|---|---|
| C1 | нет открытого occlusion-запроса на буфере (`open_occlusion`) и draw не считает сэмплы (`count_samples`) | число сэмплов, прошедших тест, зависит от того, что нарисовано раньше: порядок меняет отчёт (`mk_query`). Пары отчётов NR-03 «со своим draw» не спасают — меняется само значение |
| C2 | не действует условие условного рендера (`condr`, `DM_GFX_COND_RENDER`) | предикат читается в момент draw; переносить его вместе с draw не стали — режим выключен по умолчанию |
| C3 | шейдеры draw не читают глубину открытого прохода (счётчик `depth_feedback_reads` `prepare_read` не сдвинулся) | чтение своей глубины в проходе зависит от уже записанного. Чтение вложения открытого прохода всегда идёт через `prepare_read` (NB-12 `NBH_OPEN`, NR-08 `NRD_I_RT` его не пропускают): либо рвёт проход (= конец сегмента), либо считается |
| C4 | нет записи в хранилище: ни `storage_writes` у VS / FS (анализ SPIR-V, при неизвестности — все SSBO), ни storage image / texel buffer в привязках, ни привязанных storage images, ни writeback | порядок записей / атомиков виден |
| C5 | у прохода есть вложение глубины, и оно **фиксированной точки**: D16, X8_D24, D24S8, D16S8 | в float-глубине (D32F, D32F_S8) `+0 == -0` с разными битами: и LESS, и LEQUAL оставляют знак того, кто пришёл первым / последним (`mk_float0_*`). На стоп-заменах `d24s8_as_d32s8` (устройства без D24) пре-пасс не сортируется — счётчик `float depth` |
| C6 | ни один **привязанный** цветовой таргет не пишется: маска каналов 0 (или маска NOOUT `DM_GFX_NOOUT_MASK`, которой `draw()` гасит запись у FS без выходов) | цвет «последний пишет» и float-блендинг (округление) зависят от порядка (`mk_color`, `mk_blend`) |
| C7 | stencil test выключен | Vulkan пишет stencil только через операции включённого теста; INCR при LESS считает прошедших — порядок виден (тест на 2 draw) |
| C8 | depth bounds выключен | тест читает хранимое значение (`mk_bounds`) |
| C9 | alpha to coverage выключен | покрытие от отсутствующего цветового выхода не определено — не берём |
| C10 | запись глубины только с LESS / LEQUAL / NEVER (или запись / тест выключены) | ALWAYS / NOT_EQUAL — «последний пишет»; GREATER / GEQUAL в смеси с LESS / LEQUAL — тоже. EQUAL + запись — пишет то же значение (без эффекта), но не нужен — отказ |

**Теорема.** Для сэмпла с хранимым `d` и фрагментом `z` запись даёт `LESS: z < d ? z : d`, `LEQUAL: z <= d ? z : d` — обе равны `min(d, z)`
как числа; draw без записи (тест выкл. — Vulkan тогда не пишет глубину; запись выкл.; NEVER) значение не меняют. `min` коммутативен и
ассоциативен ⇒ после сегмента в каждом сэмпле `min(d0, все z его фрагментов)` при любом порядке. В фиксированной точке равные числа —
равные биты (C5) ⇒ **те же биты**. Смесь LESS и LEQUAL в сегменте ничего не меняет (оба — min); NaN не проходит ни один из тестов.
`z`, покрытие и `discard` фрагмента зависят только от самого draw (вершины, константы, текстуры, пайплайн, viewport, scissor — всё едет с
ним), не от вложения (C3, C8, C9); alpha test / discard, depth bias, depth clamp, sample mask, `gl_FragDepth`, rasterizer discard — по фрагменту,
допустимы. Цвет, stencil, хранилище, запросы не меняются вовсе (C1, C4, C6, C7) ⇒ **результат сегмента одинаков бит в бит при любом порядке**.

Проверено моделью теста глубины (`nr_sort_test.c`): 20 000 сегментов (до 40 draw, фрагменты с массовыми точными совпадениями `z`, `discard`,
LESS / LEQUAL / NEVER / без записи / без теста вперемешку) × 7 порядков (исходный, отсортированный, обратный, 4 случайных) — глубина одинакова
бит в бит и равна замкнутой форме `min(d0, z)`. Для каждого отказа есть сегмент и порядок с другим результатом (кроме EQUAL+запись и
отдельно GREATER / GEQUAL — там `max`, тоже без порядка; отказ — потому что DOS2 их в проходах глубины не ставит, а смесь с LESS ломает).

**Сверка с тем, что получает GPU (`DM_NR_SORT=2`).** Пайплайн каждого ждущего draw сверяется с его `VkGraphicsPipelineCreateInfo`
(записывается при создании в обоих местах сборки — `pipeline_lookup` и сборка прогрева; только при `=2`): stencil / bounds / A2C выкл., маски
цвета **привязанных** таргетов 0, запись глубины только LESS / LEQUAL / NEVER. Это ловит любое расхождение между `state` и тем, что
транслятор реально положил в пайплайн (оверрайды, о которых условие не знает).

**Почему счётчик NR-16 (`[cpuprof] passes … order-free`) больше, чем возьмёт NR-21:** он считает «order-free» и draw со счётом сэмплов
(«пары NR-03 едут со своим draw»), а это неверно для самого отчёта (C1), и требует одну функцию на весь проход (здесь не нужно). Строка
NR-21 (`[nr] sort`) — точная: сколько draw реально встали в сегменты и сколько привязок сэкономлено.

## 3. Переключатели (умолчание 0; игрокам не выдаются)
| | значение |
|---|---|
| `DM_NR_SORT` | **0** — ничего: `nrsort::pend` всегда null; каждая обёртка `vkCmd*` платит одну relaxed-загрузку и сравнение (как `go(c)` рядом), `lane()` — одну загрузку `nrsort::mode`, старый хвост `draw()` — одну загрузку `pend`. Очереди нет (статические массивы сортировки ≈ 1.1 МБ в `.bss` не трогаются), поток команд байт в байт прежний. **1** — сортировка по `DM_NR_SORT_KEY`. **2** — сверка: сегмент ставится в очередь и пишется **в исходном порядке** (то, что пишет 0, только отложенно); сортированный порядок считается и моделируется для обоих ключей; проверяется, что порядок — перестановка сегмента и устойчив; модель привязок исходного порядка — против реально записанного; пайплайны ждущих draw — против их create info (§2). Красные строки `【红】[nr] sort: …` (первые 16) + строка сверки раз в 10 с. **3** — яд / доказательство: сегмент пишется **в обратном порядке** (самый далёкий порядок; картинка и GVAL проходов глубины не должны измениться, GPASS покажет цену порядка для early-Z) |
| `DM_NR_SORT_KEY` | 0 — viewport+scissor → пайплайн → первый поток (умолчание); 1 — пайплайн первым |
| `DM_NR_SORT_CAP` | draw в сегменте максимум (2048; 16…4096): полный сегмент пишется, начинается новый |
| `gfx-ab-target = nrsort` | A/B в процессе: в «выключенных» окнах ничего не ставится в очередь |

Нужно `DM_NR_DRAW=1` (иначе красная строка и выкл.) — т. е. вся цепочка NR-09: `DM_NR=1 DM_NR_BUF=1 DM_NR_DESC=1 DM_NR_DRAW=1 DM_NR_SORT=1`.
Умолчание — `xbg_nr_sort_default()` в `xbg_vendor_policy.h` (0 у всех семейств до прогонов).

Строки: старт `[nr] DM_NR_SORT=… (NR-21: …)`; раз в 10 с
`[nr] sort: DM_NR_SORT=M key K; a frame: A draws asked, Q queued (W writing depth) in S segments (… draws a segment, longest L); not queued: <причина n, …>; segments ended by: <команда n, …>; the queued draws, recorded order -> sorted: pipeline binds P -> P', sets …, viewport …, scissor …, vertex …, index …, vkCmd* C -> C' (saved D a frame); T us a frame to sort and record them`
(всё на кадр; «recorded order» — модель того, что записал бы режим 0, «->» — реально записанное, при `=2` — модель сортировки);
при `=2` ещё `[nr] sort check: N segments; orders: not a permutation 0, unstable 0; the bind model … bad 0; queued draws against their pipeline's create info: order-free X, NOT 0, not registered U; key 0 -> …, key 1 -> …`.
Сводка NR-09 `[nr] draw: … vkCmd* a served draw …` включает команды ждущих draw (их считает `emit`).

**Риск GPU (честно):** порядок меняет то, что видит early-Z / LRZ. Если движок рисовал пре-пасс спереди назад, сортировка по пайплайну
увеличит число фрагментов FS kill-материалов (late-Z) — выигрыш смен может съесться и стать минусом. Решает A/B GPASS (`=0` / `=1` / `=3`:
обратный порядок — худший случай для early-Z, сразу покажет чувствительность). Поэтому умолчание 0 и решение по семейству.

## 7. Риски
1. **Не исполнено на устройстве**; сам NR-09 (`DM_NR_DRAW=1`) тоже — NR-21 добавляется к нему и без него выключен.
2. **Воронка команд**: доказательство требует, чтобы ни одна команда не попала в буфер мимо обёрток. Это уже инвариант NB-20b (тест
   `nb20b_check`: каждый `vkCmd*` единицы трансляции — в списке обёрток, указатели только через `nbmt::P*`, начало / конец буфера только в
   скобке). Команды из **других файлов** на тот же буфер исключены тем же тестом («the command buffer handed to another file»).
3. **Кэш привязок** — единственное состояние буфера, которое читают пути draw; оба читателя пишут очередь прямо перед чтением (структурный
   тест). Если появится третий читатель кэша, он обязан делать то же (тест упадёт: «no other reader of the bind cache»).
4. **Учёт `lane()` идёт в момент постановки** (uiarea, флаги прохода, `pass_prof`, `nbchk`, `nbui`, счётчики, `drecy`), команды — позже:
   всё, что смотрит на «что уже записано в буфер», а не на учёт, увидело бы разницу — таких мест не нашёл (запись `uiarea` для OTHER-прохода
   без сжатой области проход не рвёт; `drecy` возвращает только CPU-запись дескрипторов, набор и смещения скопированы).
5. **Наборы дескрипторов привязываются позже**, чем при `=0`. Корректно, пока транслятор не переписывает набор, который draw уже взял, до
   конца подачи — то же требование уже есть у немедленного пути (переписать привязанный набор = невалидный буфер), так что нового риска нет.
6. **Счётчик обратной связи** глубины обнуляется раз в 10 с (строка PERF) — один лишний отказ «depth feedback» в 10 с, не ошибка.
7. Проходы с открытым batched-запросом (NB: run счёта держит запрос до конца прохода) — все draw после первого считающего отказываются (C1).
   В пре-пассе DOS2 есть 90–99 условных draw / кадр (`PREPASS.md`): если они стоят в начале прохода, пре-пасс почти не возьмётся — увидим в
   `not queued: occlusion query / counting`. NR-14 (`DM_GFX_SAMPLES_TS=0`) убирает штампы в проходах — сегменты длиннее.
8. Режим 2 дороже (модель обоих ключей, проверки, map create info под mutex — ≈ +0.2 мкс на draw).

## 8. Не сделано
- Сортировка draw **старого пути** (первый draw прохода, промахи таблицы, UI): у них нет самодостаточной записи — только через NR-09.
- Сегменты через границу прохода / подачи — нельзя по определению.
- GREATER / GEQUAL-сегменты (reverse-Z, `max`) — доказуемо тоже без порядка, но DOS2 их не использует; при надобности — одно направление на сегмент.
- Сортировка ради early-Z (спереди назад) — нужна глубина объекта, которой у транслятора нет; если `=3` покажет сильную чувствительность к порядку,
  это отдельная идея (ключ «первое появление» уже сохраняет порядок первых draw каждой группы).

## 10. Прогоны телефона, которые это подтвердят (главный агент, по разрешению хозяина)
Бэкап `files/save`; keyguard снят (`dumpsys window`); без лимита кадров; `DM_NB_MT=0` в одном прогоне для `draw_sections`. Сцены: палуба 60 с
+ Форт Радость / бой / город, инвентарь и карта. APK: `wt-nr21/work/DOS2-port-debug.apk` (или сборка слитой ветки).
1. **R-NR21a, сверка:** `DM_NR=1 DM_NR_BUF=1 DM_NR_DESC=1 DM_NR_DRAW=1 DM_NR_SORT=2`. Ждём: `[nr] DM_NR_SORT=2 (NR-21: compare …)`;
   `[nr] sort: … queued …` — доля спрошенных, `not queued:` по причинам (особенно `occlusion query / counting`, `colour written`, `float depth`),
   `segments ended by:` (ожидаемо `EndRenderPass`, `a draw recorded at once`, `WriteTimestamp`/`BeginQuery`); модель
   `pipeline binds P -> P'` — сколько сэкономит; **`[nr] sort check: … not a permutation 0, unstable 0; … bad 0; … NOT 0`**; картинка как без
   флагов (=2 пишет исходный порядок). `not registered` ≈ 0 после прогрева.
2. **R-NR21b, яд:** то же с `DM_NR_SORT=3` + `DM_GFX_PASS_PROF=300,180,0` (GPASS + GVAL). Картинка (палуба, листва, исчезающие стены, тени
   каскадов) **та же**; `NVN GVAL` пре-пасса / атласа — те же порядки величин, что в `=0` (кадры не детерминированы — сравнивать сцену стоя);
   GPASS пре-пасса / атласа `=3` против `=0` — цена «плохого» порядка для early-Z.
3. **R-NR21c, включено + цена (ABBA × 2, 60 с):** `… DM_NR_DRAW=1` против `… DM_NR_DRAW=1 DM_NR_SORT=1` (и `DM_NR_SORT_KEY=1` по желанию);
   GPASS пре-пасса (i=4) и атласа (i=8), `NVN PERF v= gpu_ms`, `submit_cpu_ms`, `[nb] mt … packets`, `[nr] sort … us a frame`; скриншоты равны.
   Решение по умолчанию (по семейству в `xbg_nr_sort_default`): только при `bad 0 / NOT 0` и выигрыше GPASS; для Mali / PowerVR — лог тестера
   (`[nr] sort`, `draw_sections`) с тестовой сборкой, где режим включён по детекту.
