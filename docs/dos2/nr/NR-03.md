# NR-03 `DM_NR_OCC` — нативный условный рендер (сегмент S7)

Ветка `dos2-nr03` (worktree `wt-nr03`, база `dos2` 94d287d). На телефоне **не запускалось** (ни один режим). Умолчание 0 везде.

## 1. Что делает игра (статический разбор `main` 4979b200, 17.11, capstone по `work/exefs-update/main.raw`)

| Место | Что там |
|---|---|
| `BeginFrame 0x9215f0` (`0x9216a0…0x9216d8`) | обнуляет атомарный счётчик `dev+0x25ac0` и CPU-шно заполняет **половину кадра** буфера счётчиков `dev+0x25ae8` (128 КБ, адрес GPU в `dev+0x25b18`) парами `{0, -1}`: незаписанная пара читается «не равно» = рисовать |
| инициализация `0x938edc…0x939030` | 4096 записей по 16 Б (`dev+0x25ab0`, вторая половина `+0x8000` = `dev+0x25ab8`): запись k = {адрес пары `buf + 32·k`, кадр} |
| выделение `0xb0c5c0` | объект с флагом `0x40000` берёт **следующую** запись половины `[dev+0x31e0]` (`ldaxr/stlxr` fetch_add, максимум 2048), `obj+0x268` = запись, `obj+0x270` = номер кадра `[…+0x51f0]` |
| пара `0xb89330` (и `0x90cbf0`, `0xb87470`; `0xb7e020` только код 61) | код 61 = `ReportCounter(SAMPLES, pair)`, затем **собственный draw объекта** (код 21 состояние материала + код 36 `DrawElements` с его IB / count из `obj+0x2a8 / +0x290`), код 62 = `ReportCounter(SAMPLES, pair + 16)` |
| условие `0xb23970`, `0x142c870` | код 63 `{u8 on, query*}` → `SetRenderEnableConditional(RENDER_IF_NOT_EQUAL, [query])` (`0x93edf0`, кэш `r+0x185c / 0x1860`), затем `0xaab150` (`DrawElements`); `on = 0` → `SetRenderEnable(true)` |
| проверка кадра | и пара, и условие берут `obj+0x268` только если `obj+0x270 == кадр`: **условие всегда про пару этого же кадра** |

Выводы, на которых стоит дизайн:
- Предикат Switch = «прошёл ли хоть один сэмпл собственного draw объекта в пред-проходе», вычисляется GPU в порядке потока, в том же кадре.
  `SetRenderEnable(false)` DOS2 не зовёт (0 красных строк во всех логах), режим условия всегда 1 (`RENDER_IF_NOT_EQUAL`).
- Отчёты samples читает только `SetRenderEnableConditional` (§0 плана) → пара = **один occlusion-запрос Vulkan**; ни счётчик «с начала»,
  ни запись отчётов в память игры не нужны.
- **Адрес пары каждый кадр — другой объект** (порядок выделения, половины чередуются). Поэтому решение «по памяти игры по тому же адресу»
  (`DM_GFX_COND_RENDER=3`, его счётчик `would_skip3`) верно, только пока каждый объект сохраняет свой индекс; при любом сдвиге набора
  видимых объектов оно судит чужой объект. Вариант «по прошлому кадру» обязан ключеваться объектом (его draw), а не адресом.

## 2. Что показывает существующий `DM_GFX_COND_RENDER=4` (и почему его мало)

- Ни одного прогона с ним нет (в каждом логе — красная строка `SetRenderEnableConditional mode 1: the host draws unconditionally`).
- `would_skip2` (отчёт ещё на GPU → рисовать): в DOS2 пара и условие в одной подаче → почти всё «stale» → ≈ 0, ничего не говорит.
- `would_skip3` (память игры по адресу = пара позапрошлого кадра с тем же индексом): приближение, ошибается при каждом сдвиге индексов
  (модель в тесте: при перемешанных индексах — 50 % неверных). Плюс режим 4 включает счёт сэмплов на **каждом** draw (прогоны
  occlusion вокруг всех draw; в D2R это стоило Adreno 730 ≈ 10 мс GPU), т.е. меряет не ту сцену.
- Сделано: строка-предупреждение в логе при `DM_GFX_COND_RENDER=3/4`; точный счёт даёт `DM_NR_OCC=2` (ниже). Логика condr не менялась.

### Переключатели
| Значение | Поведение |
|---|---|
| `DM_NR_OCC=0` / не задан | ничего: нет записи условий в поток, нет запросов, нет выделений, расширение не включается; поток байт в байт прежний |
| `1` | путь GPU: пара = occlusion-запрос (без PRECISE: важно только «хоть один сэмпл»), открывается на первом draw пары внутри прохода, закрывается вторым отчётом; в конце прохода, закрывшего пару, `vkCmdCopyQueryPoolResults(WAIT)` в слово предиката + барьер `TRANSFER → CONDITIONAL_RENDERING`; потребитель рисуется под `vkCmdBeginConditionalRenderingEXT` на это слово (точное решение Switch, тот же кадр). Потребитель в том же проходе, что и пара, рисуется (нельзя: копия только вне прохода). Путь PREV: хост пропускает draw, если объект был скрыт в последних отработавших подачах (см. ниже). Оба пути: пара без draw внутри = 0 сэмплов → пропуск на CPU (точно). Старые отчёты samples (метки времени, pending, запись в память игры) выбрасываются (`DM_NR_OCC_DROP=0` — оставить) |
| `2` | сверка: запросы + решения всех путей, рисуется всё (картинка как 0); на retire решения сравниваются с правдой того же кадра. **Один прогон отвечает: сколько draw / вершин отсекает Switch**, сколько отсечёт путь GPU (и сколько потеряет на потребителях в том же проходе), сколько prev (строгий / нестрогий) отсечёт верно и **неверно**, и насколько ошибся бы судья «по адресу» (`DM_GFX_COND_RENDER=3`) |
| `3` | poison: все решения инвертированы (GPU — `INVERTED`, CPU — пропуск того, что надо рисовать): то, что Switch рисует, исчезает — визуальная проверка, что условия доходят до draw |
| `DM_NR_OCC_PATH` | `gpu` / `prev` / `auto` (умолчание: по семейству; `gpu` без расширения → `prev`) |
| `DM_NR_OCC_N` | prev: сколько подач подряд объект должен быть скрыт (1..60, умолч. 2) |
| `DM_NR_OCC_STILL` | prev: 1 (умолч.) — резать только если константы вершинной стадии совпали с прошлой подачей (объект и камера неподвижны); 0 — любые |
| `DM_NR_OCC_DROP` | при 1 / 3: 1 (умолч.) выбросить старую работу отчётов samples, 0 — оставить (A/B) |
| `DM_GFX_COND_RENDER≠0` | выигрывает (оба владели бы occlusion-запросами): `DM_NR_OCC` выключается с красной строкой |

### Безопасность (кадр задержки, мигание)
- Путь GPU точен: решение — правда того же кадра; мигания и задержки нет (если только драйвер не врёт в запросах).
- Пара непригодна (= рисовать) если: внутри неё хост пропустил draw, который Switch нарисовал бы (вход в `draw()` считается до всех
  пропусков бэкенда — prepass, async, nbpost, неверный viewport…, сделанный — только с активным запросом; `seen ≠ done`), проход
  закончился внутри пары и она рисует дальше (`split`), вложенный отчёт (`nested`), пул полон, пара не закрыта к концу подачи,
  открыт прогон старого счётчика. Условие без пары / с непригодной парой / из другой подачи — рисуется. Всё считается в строке.
- Путь PREV (тайлеры): ключ объекта = хэш его draw внутри пары (prim, count, first, instances, IB-адрес, тип, base vertex, VB-адреса
  0..3, программа VS) + отдельно хэш констант VS (первые 256 Б первых 4 привязанных диапазонов). Резать только если: ключ был в
  **последней** отработавшей подаче ровно один раз, скрыт ≥ N подач подряд, и (по умолчанию) константы те же (неподвижны объект и
  камера — у камеро-зависимых констант любое движение камеры само выключает отсечение). Повторяющийся меш (одинаковые бочки) судится
  строгим ключом меш + константы. Защиты: «сцена сменилась» — после 16 закрытых пар меньше ¾ ключей нашлось в последней подаче
  (смена локации, резкий поворот, загрузка) → до конца подачи без отсечения; «открылся вид» — на retire больше 4 и больше 2 % скрытых
  ключей стали видимыми → 2 подачи без отсечения.
- Остаточный риск PREV: объект, который только что открылся (дверь, ушёл персонаж-заслонка) при неподвижной камере, рисуется на
  **2 подачи позже** (кольцо из 2 слотов: правда кадра t известна на retire, когда пишется t+2). Модель теста: «дверь открылась» —
  26 ложных отсечений на 13 открывшихся объектов (каждый на 2 кадра), «медленная панорама при неподвижных константах» — 432 ложных
  из 5 065 решений; N = 4 почти не помогает (задержка — от кольца, не от гистерезиса). В режиме 1 каждое такое событие считается на
  retire («FALSE CULL on screen», красные строки), в режиме 2 — «would be». Поэтому PREV — только для тайлеров и только после
  прогона `=2`, где видно его WRONG.

## 5. Ожидаемый выигрыш (честно: доля отсекаемых draw неизвестна до прогона `=2`)
- Данные: на палубе 526 отчётов samples на кадр (`samplets reports=526`, `pass_ends … ops=0/1/526`) = **263 пары**, т.е. до 263
  объектов с тестом. Сколько из них Switch реально отсекает и сколько у каждого потребителей — даст `=2`.
- **Mi 14 / Adreno 750 (упор в GPU)**, путь GPU: экономится вершинная работа и растеризация скрытых объектов в поздних проходах
  (G-buffer 1.52 мс; VS транслированы и в 4.6× длиннее нативных — вершины здесь не бесплатны; пиксели G-buffer с EQUAL после
  пред-прохода и так отбрасывались). Оценка 0…0.4 мс GPU при 10–30 % скрытых потребителей. Против: 263 occlusion-запроса на кадр
  (в D2R 2 200 пар стоили A730 ≈ 10 мс → здесь порядка 0.3–1 мс, **может съесть выигрыш**), копии + барьеры между проходами (sysmem
  Turnip — дёшево). За: выброс старых отчётов (526 меток времени в проходах + pending на кадр). Итог — только A/B `=1` против `=0`.
  CPU на Mi 14 путь GPU не экономит (draw всё равно записывается) — кроме пустых пар.
- **S7 (Adreno 710–730)**: то же ×3–4 по абсолюту, если доля значимая; цена запросов там тоже выше — решает A/B.
- **Mali / PowerVR** (путь PREV): пропущенный draw не стоит ни CPU транслятора (18–22 мкс/draw на MTK), ни бининга, ни вершин;
  межпроходной зависимости нет; результаты читаются на retire (без остановки). При 10 % отсечённых потребителей кампании ≈ 90 draw →
  ≈ 1.6–2 мс CPU на MTK [м] + GPU пропорционально. Цена — риск задержки появления (§3) и 263 запроса (на Mali дёшевы, читаются поздно).
- **Слабый CPU**: только PREV экономит CPU; путь GPU — нет.

## 6. Чего нет
- Нет ни одного прогона на телефоне: ни `=2`, ни `=1`; путь записи условий (`OP_X_RENDER_COND`, флаги NB) тоже никогда не исполнялся на
  телефоне (`DM_GFX_COND_RENDER` не запускался).
- Не сделано: чтение результатов соседнего слота досрочно (уменьшило бы задержку PREV до 1 подачи, но GPU-bound телефон почти никогда
  не успевает); «потребитель в том же проходе» на GPU-пути (нужен разрыв прохода — не делал: на тайлерах убыточно, на Adreno — только
  если `=2` покажет, что таких много); обучение «у этой пары нет потребителей → не ставить запрос» (снизило бы цену запросов, если
  `=2` покажет много пар без условий); SIM-проверка тайлерного пути на ПК (нет GPU-теста; на телефоне — `DM_GFX_SIM_GPU=mali` + PREV).
- APK (gradle + подпись) не собирался — только `libdm.so` (§7).

## 8. Прогон для подтверждения (главный агент, по разрешению хозяина)
APK из этой ветки; бэкап `files/save`; без лимита кадров (`DM_DOS2_FPS=0`); остальные env — умолчания сборки.
1. **Счёт (обязателен):** `DM_NR_OCC=2`. Сцены: палуба (стоя 30 с, потом поворот камеры и ходьба 60 с) **и** кампания (Форт Радость,
   ходьба + бой, ≥ 2 мин) — одна стартовая зона не показательна. Строки: `[nr] occ DM_NR_OCC=2 (check…) path=gpu …` при старте,
   затем каждые 10 с две строки `[nr] occ …`: ответ — «the Switch culls X draws/f = Y % of draws, Z % of vertices»; «GPU path culls
   … (same-pass consumers …)»; «prev strict … right, … WRONG»; «by address … WRONG»; «pairs … unusable …» (должно быть ≈ 0);
   «conditions … no pair …» (≈ 0). Красные `false cull (strict, would be)` — сколько раз prev ошибся бы.
   Порог: Y ≥ 5 % draw или Z ≥ 10 % вершин → шаг 2; иначе шаг закрывается как «мало выигрыша» (оставить `=2` для логов игроков).
2. **A/B на Adreno:** `DM_NR_OCC=1` против `DM_NR_OCC=0`, ABBA по 60 с, та же точка кампании; сравнить `NVN PERF gpu_ms`, fps,
   `submit_cpu`; в логе `VK_EXT_conditional_rendering: listed=1 feature=1 -> enabled`, `[nr] occ … executed: gpu predicate N/f` с N > 0,
   `false culls on screen 0`; скриншоты одинаковы. Если нетто ≤ 0 — `DM_NR_OCC_DROP=0` отдельно (цена старых отчётов vs запросов).
3. **Poison (по желанию):** `DM_NR_OCC=3` — видимые объекты с тестом исчезают (скриншот), значит условия доходят до draw.
4. **Тайлерный путь на Adreno:** `DM_NR_OCC=1 DM_NR_OCC_PATH=prev` (+ `DM_GFX_SIM_GPU=mali` для политики): ходьба / поворот камеры,
   смотреть на «запаздывающие» объекты; в логе `executed: … host skip N/f`, `FALSE CULL on screen` (красные) — их число за минуту.
   Затем — хотя бы один лог Mali-игрока (тестовая сборка) с `DM_NR_OCC=2`.
