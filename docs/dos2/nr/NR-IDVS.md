# NR-IDVS (тайловый план T2, PERF-X19) `DM_NR_IDVS` — позиционная часть вершинных шейдеров DOS2 на Mali: что её раздувает и что снято

Ветка `dos2-idvs` (worktree `wt-idvs`, база `dos2-nr-all` 85d2cfa). Всё ниже — ПК, офлайн; телефон не трогал.

## 0. Итог
- **Вопрос постановки:** Mali (IDVS) при раскладке по тайлам гоняет только ту часть вершинного шейдера, которая считает положение; если она
  длинная или читает текстуры, платим за каждый draw дважды. Есть ли у переведённых VS DOS2 такая беда?
- **Сама позиционная часть — нет.** Компилятор Mali выделяет её сам и выделяет полностью: у всех 79 VS рабочего набора Форт-Джоя позиционный
  вариант по `malioc` **ровно равен** модулю, который пишет только встроенные выходы (§3). Порядок инструкций, общие временные, «все выходы
  до gl_Position» роли не играют: драйвер режет по зависимостям, а не по порядку. У самых тяжёлых по вершинам VS (глубина / тени
  `Base_PBR_ST_DEP`, `Base_Tile_*`) позиционная часть — это ровно `мир × вид-проекция` (28 FMA, 28 констант) и по циклам совпадает с
  написанным руками GLSL-эталоном.
- **Выборки текстур в позиционной части** — у 477 VS из 6 132 (эффектные материалы `RS3_FX_*`: смещение вершин шумом, `SampleExplicitLod 0`);
  это замысел материала, не перевод. В Форт-Джое — 2 VS, ~950 вершин за кадр из 1.51 M (0.06 %). **Индексация UBO с вычисляемым индексом в
  позиционной части** — 2 001 VS (палитра костей скиннинга); тоже по существу, загрузки уже сведены в vec4 (NR-27).
- **Нашёлся один артефакт перевода, и он дорогой:** транслятор пишет `gl_PointSize = 1.0` в **каждом** VS (6 132 из 6 132; так же у DOOM,
  Eternal, D3, TL2, XC2 — выборка §6). Vulkan это значение игнорирует, если не рисуются точки, но компилятор Mali запись оставляет:
  - **Valhall / 5-е поколение (G57, G68, G78, G610–G720):** +1 цикл load/store в позиционном шейдере — у тяжёлых VS это 4 → 3 цикла (−25 %);
  - **Bifrost (G52, G72, G76):** запись PointSize **выключает IDVS целиком** — `malioc` выдаёт один вариант «Main» вместо Position + Varying:
    весь VS (с varying) идёт для каждой вершины при раскладке, в том числе отброшенной отсечением.
- **Сделано:** `DM_NR_IDVS` — проход `xbg_spirv_idvs.cpp` снимает эту запись при загрузке шейдера (и в `load_shader`, и в
  `warm::bundle_words`, так что все производные модули — retype, `#vo` NR-32, прогрев — строятся из тех же слов). Пайплайнам, которые рисуют
  точки (`POINT_LIST` или polygon mode POINT, где он есть) или имеют стадию тесселяции / геометрии, отдаётся модуль с записью (ключ `#ps`).
  **Умолчание 0 на всех семействах** (правило: тайловым — только после проверки на устройстве).
- **Цена по `malioc` (Форт-Джой, 79 пар VS + маска FS после NR-32 — что Mali компилирует сегодня, взвешено вершинами за кадр):**

  | ядро | раскладка (позиционный шейдер; без IDVS — весь VS), M циклов / кадр | varying, M циклов / кадр | режим |
  |---|---|---|---|
  | Mali-G52 (Bifrost) | **17.93 → 4.45 (−75 %)** | 0 → 11.25 (только для вершин, переживших отсечение) | Main → IDVS у 79 / 79 |
  | Mali-G57 | **7.10 → 5.59 (−21.3 %)** | 8.94 → 8.94 | IDVS |
  | Mali-G78 | **7.10 → 5.59 (−21.3 %)** | 8.94 → 8.94 | IDVS |
  | Mali-G715 | **7.10 → 5.59 (−21.3 %)** | 9.01 → 9.01 | IDVS |

  Весь пак (6 132 VS как есть, без маски FS): §4.
- **Точность:** проход удаляет только `OpStore` в PointSize (и цепочку доступа к нему); независимая проверка `xbg_spirv_idvs_check` — 0 отказов
  на 6 132 + 79 модулях; `spirv-val` — 0 новых отказов; интерпретатор NR-27 (`spv_interp`) — 0 расхождений по `gl_Position` (бит в бит),
  остальным членам `gl_PerVertex` и всем Location-выходам; отрицательный контроль видит PointSize (§5).

## 1. Метод
- Пак игрока `work/shaders-vk/shaders.xgspack` (6 132 VS). Каждый модуль — после телефонной цепочки загрузки (`NAN_MINMAX`+`NAN_SAT`,
  `LDC_FOLD`, `FORWARD_TEMPS`, `LDC_CANON`, `F2I_NOTRUNC`, NR-27 `UBOVEC`; боевой C++ через `tests/idvs_scan.cpp`).
- Рабочий набор: пары (VS, FS) Форт-Джоя из журнала хозяина 18.11 (`python tools/dos2_shader_heat.py src/work/logs/play-1118/shader-heat.tsv
  --level FJ_FortJoy_Main --json heat.json`): 84 пары, 79 различных (VS, маска чтения FS), 1.51 M вершин за кадр. Для них сначала NR-32
  (`DM_NR_XLQ=1`, умолчание Mali), потом проход — это то, что Mali компилирует сегодня / с `DM_NR_IDVS=1`.
- Позиционный срез (своя разметка SPIR-V, офлайн): обратные зависимости от записей во встроенные выходы `gl_PerVertex` (кроме PointSize),
  с учётом записей в Function / Private / Output-переменные. Считались инструкции среза / всего, выборки текстур и UBO-загрузки с
  вычисляемым индексом в срезе.
- `malioc` 2026.5 (Arm Performance Studio 2026.5, `<Arm Performance Studio>/mali_offline_compiler/malioc.exe`, метод PERF-X13): варианты VS по отдельности — Position / Varying на
  IDVS-ядрах, Main без IDVS; bound = максимум конвейеров по самому длинному пути. Ядра G52 / G57 / G78 / G715.
- Эталон «пола»: GLSL `gl_Position = VP * (W * pos)` с константами в большом UBO, `glslc -O` → `malioc`.

## 3. Позиционный вариант уже минимален (кроме PointSize)
Для всех 79 VS Форт-Джоя собран модуль, который пишет **только** встроенные выходы (все Location-записи сняты, PointSize снят), и сравнён
позиционный вариант полного модуля (после прохода) с ним: **G57 — 79 из 79 равны, G52 — 79 из 79 равны** (взвешено 5.59 M = 5.59 M и
4.45 M = 4.45 M). То есть никакой другой «примеси» в позиционном шейдере нет: ни общие временные, ни порядок вычислений, ни лишние
выходы не попадают в позиционный вариант — компилятор Mali режет их сам. Переставлять / укорачивать срез проходом по SPIR-V нечего.

## 5. Проход и доказательство
- `dm/gfx/vulkan/engine/xbg_spirv_idvs.{h,cpp}` (без Vulkan / окружения):
  - `xbg_spirv_idvs_strip` — только Vertex-модуль с одной точкой входа; указатели на PointSize = переменная с `BuiltIn PointSize` или
    `OpAccessChain` с одним константным индексом члена PointSize Output-блока. Удаляются `OpStore` в них и сами цепочки. Отказ (модуль как
    был), если PointSize читается, передаётся, копируется, блок используется целиком, индекс члена не константа. Переменная, декорации и
    интерфейс точки входа не трогаются (следующая стадия видит тот же интерфейс).
  - `xbg_spirv_idvs_check` — независимая сверка: выход = вход минус инструкции, каждая из которых — запись в PointSize или цепочка к нему, не
    упомянутая в выходе; заголовок и все прочие инструкции слово в слово, в том же порядке. Движок берёт модуль только после неё.
  - `xbg_spirv_idvs_stripped` — PointSize объявлен, но не пишется (флаг для запасного модуля точек).
- **Почему точно:** `gl_Position`, Clip / CullDistance и все Location-выходы пишут те же инструкции, что и раньше. PointSize в Vulkan читается
  только при растеризации точек (и стадиями тесселяции / геометрии через `gl_in[]`) — таким пайплайнам движок отдаёт модуль с записью.
- **Проверки** (`python tools/dos2_idvs_check.py --pack … --out … --cxx clang++ --pairs <пары FJ> --spirv-tools <ndk>/shader-tools/windows-x86_64
  --malioc <malioc> --heat heat.json --runs 2 --negative 24`):
**RESULT PASS** (≈ 45 мин на 12 потоках, из них почти всё — `malioc`):
  - структура: 6 132 VS пака — снято у 6 132 (по одной записи), `check_failed 0`; 79 модулей Форт-Джоя после NR-32 — снято у 79, 0 отказов;
  - `spirv-val --target-env vulkan1.1`: 6 211 модулей, отказов до 0, после 0;
  - интерпретатор: 6 211 модулей × 2 = 12 422 пары прогонов, **0 расхождений**, 0 ошибок интерпретатора, 101 574 сравнённых значений выходов
    (`gl_Position` целиком, Clip / CullDistance, все Location-выходы); отрицательный контроль: PointSize отличается в 24 из 24 (сравнение не слепое).
- `tests/idvs_test.cpp` (синтетика A–G: форма транслятора, чтение PointSize, переменная PointSize, блок целиком, не-VS, две записи, порча
  выхода): clang++ 21 Windows и g++ 11 WSL `-fsanitize=address,undefined` — all passed.

## 6. Переключатель и встраивание (`xbg_game.cpp`)
| `DM_NR_IDVS` | что делает |
|---|---|
| 0 | выключено: `idvs_rewrite` выходит сразу, модули байт в байт прежние (умолчание на всех семействах, `xbg_nr_idvs_default`) |
| 1 | запись PointSize снимается при загрузке VS (после `tidy_rewrite`, в `load_shader` и `warm::bundle_words`); точки / тесселяция / геометрия — модуль `<vs>[#vi…]#ps` с записью (`idvs_point_module`) |
| 2 | проход считается и проверяется, считается в счётчиках; **используются старые слова** |

- Запасной модуль: в `draw` после блока NR-32: если у VS снята запись (`Shader::ps_dropped`) и пайплайн `POINT_LIST`, или polygon mode POINT при
  `fillModeNonSolid` (на Mali / PowerVR его нет — там всё рисуется заливкой), или в списке стадий есть что-то кроме VS + FS — VS-модуль
  заменяется на `idvs_point_module` (слова пака без прохода, `bundle_words(…, idvs=false)`, + retype по коду пайплайна; без трима NR-32).
  Прогрев строит простой ключ `<vs>#ps` (только в режиме 1); `#vi…#ps` собирается своим draw.
- Лог: `NVN DM_NR_IDVS=N (env | family default; policy family … default 0): …`; `NVN idvs vs=<key>: PointSize store dropped (1), words a -> b`
  (первые 4 и степени двойки); режим 2 — `… (counted, old module used; N so far)`; отказ — `NVN idvs <key> refused: …` (первые 8);
  отказ проверки — `【红】NVN DM_NR_IDVS=… check: …`; точки — `NVN idvs vs=…: point / tessellation / geometry pipeline, PointSize kept (<key>#ps)`.
  Блок `NVN PERF`: `NVN PERF idvs mode= shaders= stores_dropped= counted= refused= check_bad= point_pipelines= point_bad=` (`【红】`, пока
  `check_bad` или `point_bad` ≠ 0).
- Совместно с NR-32: `#vo`-модули строятся из `s.words` / `bundle_words` — уже без PointSize; ключи `#vo` прежние (байты модуля другие —
  кеш драйвера на Mali пересоберёт пайплайны один раз, как после любого изменения слов).

## 7. Ожидаемый выигрыш [оценка]
- Шкала (PERF-X13): 2 ядра ~0.95–1 ГГц ≈ 1.9–2 млрд циклов / с.
- **G57 MC2 (Helio G99 и т. п.):** −1.51 M циклов позиционного шейдера за кадр Форт-Джоя ≈ **−0.8 мс** шейдерного времени кадра [м]; плюс
  −3.7 рабочих регистра позиционного варианта в среднем по вершинам (выше занятость).
- **G52 MC2 (Helio G85 / G88 и т. п.):** вместо 17.93 M циклов «весь VS для каждой вершины» — 4.45 M позиции + 11.25 M × доля вершин, переживших
  отсечение. Худший случай (не отсекается ничего) −2.2 M (≈ −1.1 мс); при половине отсечённых (тени / prepass с отсечением граней) ≈ −7.9 M
  (≈ −4 мс) [м]. Плюс полоса: без IDVS varying всех вершин пишутся в память, с IDVS — только видимых.
- **G715 / G720 (11–12 ядер):** те же −21 %, в мс ≈ −0.1…−0.2 мс.
- **Честная оговорка:** `malioc` компилирует стадию отдельно и не знает топологию. Если драйвер Mali при сборке пайплайна сам выбрасывает
  PointSize для не-точечной топологии, выигрыш на устройстве будет 0 (на Bifrost — тогда и IDVS у нас уже работает). Подтвердит только
  реальный Mali: A/B `DM_NR_IDVS=1` против 0.
- **Adreno, Xclipse, PowerVR:** не мерено (нет компилятора); умолчание 0.
