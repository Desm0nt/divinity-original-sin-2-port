# VK-FRAME-WORK — кадр целиком: проходы, draw, масштаб 3D (22.11.2026)

Ветка `dos2-vk5-frame` от `4db88cb` (дерево `wt-vk5-frame`). Свой бэкенд Vulkan (`DM_VK_NATIVE=1`, `dm/gfx/vkn/*`,
`dm/host/hle_dos2_vkn*.c`). Телефон не запускался: всё ниже проверено на хосте (макет Vulkan с журналом команд и моделью
содержимого глубины), числа с телефона взяты из готовых логов. Пометки: **[лог]** — число из лога телефона, **[м]** — модель трафика
бэкенда (байты загрузки + сохранения вложений по области прохода), **[код]** — исходник, **[оценка]** — прикидка, проверит только
устройство.

Не трогал (чужие ветки): тени и атлас (`vkn_shc.c`, `dos2-vk5-shadow`), свет в памяти тайла (`dos2-vk5-p10`), переключение DRS на
лету и качество FSR (`dos2-vk5-drsfsr`).

## 0. Коротко

Задача хозяина: «всё, что можно улучшить, — улучшить: реже переключать цели, меньше draw, правильно пересчитывать при низком
разрешении». Что нашлось и что сделано (всё за переключателями, значения 0 выкл / 1 вкл / 2 сверка или счёт / 3 яд):

1. **Масштаб 3D ниже 100 % почти не снижал работу GPU на тайлерах** — и вот почему. Движок при `DM_HACK_SCALE` / DRS рисует в
   левый верхний угол своих полноразмерных целей (viewport = текущий размер) — это он делает сам и правильно, включая всю цепочку
   поста. Но бэкенд открывал каждый проход **на всю цель**: тайловый GPU загружал, очищал и сохранял все 2160x972 пикселя каждого
   вложения, хотя рисовалась четверть. Сделано: **область кадра** `DM_VK_NATIVE_FRAMEAREA` — проход 3D начинается с области, которую
   реально трогают его draw. По модели [м] на кадре W07: трафик 3D-проходов 231 МБ → 130 МБ при 75 % и → 58 МБ при 50 %.
2. **На стоковом драйвере Qualcomm ни одно доказательство «первый draw перекрывает цель» не срабатывало** (ошибка): правило
   загрузки включалось по «тайлерам прохода» (куда входит стоковый Qualcomm), а программы позиций для доказательств строились только
   для Mali / PowerVR. В записи хозяина: `no position program 31.4` на кадр, доказано 0 [лог]. Исправлено: программы строятся по тому
   же правилу. Ожидание: 22 вложения на кадр начинаются без загрузки, как на модели Mali [лог W07].
3. **Пустые проходы UI**: очистка области цели фильтра открывала проход, а первый же draw закрывал его из-за смены раскладки текстуры
   — 12 проходов с нулём draw из 77 в кадре W07 [лог]; в записи хозяина `tex#0000 x36, 19 draws` (0.53 мс GPU). Сделано: **очистка
   области ждёт прохода следующего draw** `DM_VK_NATIVE_LAZYCLR`.
4. **Один разрыв полноэкранного прохода на кадр из-за барьера** (`ended by: barrier 1.00 (32.0 MB)` [лог]): текстуру сначала делали
   видимой только фрагментной стадии, потом её читал другой потребитель — приходилось закрывать открытый проход. Сделано:
   `DM_VK_NATIVE_TILEBAR_LEARN` — такая текстура 600 кадров получает полный барьер сразу.
5. **Draw**: движок уже сам рисует повторяющиеся меши инстансами (10.8 % вызовов [лог]); слить остальное в инстансы без переписывания
   шейдеров нельзя (у каждого draw свои константы). Точно сливается одно: подряд идущие части одного меша с одинаковым состоянием и
   **соседними диапазонами индексов** в проходах только с глубиной. Сделано: `DM_VK_NATIVE_DRAWMERGE` (внутри окна сортировки
   `DM_VK_NATIVE_SORT`). Сколько таких draw в игре — покажет первый прогон (счётчик есть; верхняя граница 14 % draw кадра [лог]).
6. Журнал проходов (`DM_VK_NATIVE_PASSLOG`) теперь печатает, какую часть цели трогали draw прохода (`drawn x,y WxH`) — прямой ответ
   на вопрос «идёт ли пост по всей цели».

Память (МБ ОЗУ / VRAM) эта ветка не меняет: цели создаёт движок в полном размере. Где её взять — раздел 8, пункт 1.

## 2. Draw: 2100–3600 на кадр

Числа из окон записи хозяина [лог]: 3047–3593 draw движка на кадр; привязок на кадр — конвейер 1850–2173, набор 2616–3078, буфер
вершин 2699–3163, буфер индексов 1448–1745. Draw только с глубиной (атлас теней + пре-пасс) — около 2180 на кадр (71 %), у 1200 из
них фрагментная стадия уже снята (`MAT`). Вызовов движка с инстансами — 3.49 млн из 32.4 млн (10.8 %): **повторяющиеся меши движок
объединяет сам**.

Что можно и что нельзя:

- **Инстансы / multi-draw-indirect для разных объектов** — нельзя точно и дёшево. У каждого объекта свой блок констант (матрица),
  он привязан смещением в общем буфере; чтобы один draw нарисовал несколько объектов, шейдер должен выбирать блок по номеру
  экземпляра / draw — это переписывание всех вершинных шейдеров игры (их 6132 в пакете) с проверкой каждого. Выигрыш был бы только на
  процессоре (драйверу меньше вызовов); GPU рисует те же треугольники. Не делал.
- **Один и тот же draw дважды** — в логах не видно ни одного признака; не искал дальше.
- **Пропуск невидимых** (за экраном, нулевая площадь): `empty scissor 0` [лог] — пустых по ножницам нет; отсечение по рамке объекта —
  тема веток видимости (`dos2-vk5-occ*`), там оно и сделано.
- **Части одного меша подряд** — можно точно. Признак в логах: у 14 % draw (≈ 430 из 3047 на кадр) набор и все смещения констант
  те же, что у предыдущего draw (`binds set 2616` на 3047 draw) — это один объект, нарисованный несколькими вызовами (части меша с
  разными материалами; в проходе только с глубиной разница материалов исчезает). Если у двух таких draw подряд одно состояние
  целиком и диапазоны индексов соседние (второй начинается там, где кончился первый), это один `vkCmdDrawIndexed` с суммой
  индексов: те же треугольники из тех же индексов в том же порядке.

Сделано: `DM_VK_NATIVE_DRAWMERGE` [код `vkn_sort.c`]. Работает внутри окна сортировки (`DM_VK_NATIVE_SORT=1`): там уже лежат draw
проходов только с глубиной (LESS / LEQUAL, без трафарета, без запросов видимости) с полным состоянием каждого, и порядок внутри окна
на результат не влияет. При выдаче окна соседние пакеты сравниваются: конвейер, набор и все динамические смещения, буферы вершин и
индексов со смещениями, viewport, ножницы, смещение вершин, число экземпляров; топология — список треугольников; набранный диапазон
кратен трём; первый индекс следующего = конец набранного. Совпало — пакет приклеивается. Цена — одно сравнение на пакет (десятки
наносекунд).

Чего ждать: неизвестно до прогона. Верхняя граница — 14 % draw кадра; реальная доля меньше (нужны ещё соседние индексы и попадание в
окно). Режим 2 считает «склеил бы» без изменений потока команд. Если счётчик покажет единицы на кадр — кусок просто бесполезен и
безвреден.

Допущение, которое стоит назвать: фрагментные шейдеры игры не читают номер примитива (`gl_PrimitiveID`); после склейки он считался бы
от начала общего диапазона. В проходах только с глубиной фрагментная стадия либо снята, либо делает только альфа-тест по текстуре.

## 3. Масштаб 3D ниже 100 %: область кадра

### 3.1 Что было

Движок при DRS / `DM_HACK_SCALE` оставляет цели полного размера и рисует в их часть — это сделано в нём самом и распространяется на
все проходы 3D: пре-пасс, G-buffer, свет, туман, прозрачные, bloom, половинные и четвертные буферы (у каждого свой viewport, в логе
это видно по набору размеров SUPPORT-блоков, `VK-DRS-SUPPORT.md`). То есть вопрос задачи «идут ли полноэкранные проходы поста по всей
цели» по **закраске** решается так: нет, движок ставит им уменьшенный viewport. (Прямого подтверждения в старых логах нет — там не
печатались области draw; теперь журнал печатает `drawn x,y WxH` для каждого прохода, прогон F10 в таблице ниже это покажет.)

А вот бэкенд открывал проход с `renderArea` = вся цель. Для тайлового GPU (Mali, PowerVR, Adreno в режиме GMEM на стоковом
драйвере) область прохода — это и есть объём работы помимо закраски: какие тайлы загрузить из памяти, очистить, сохранить обратно.
Поэтому при 25 % пикселей кадр хозяина стоил почти столько же, сколько при 100 %: `HalfWidthBackBuffer 2160x972, 1 draw` — 1.02 мс,
`HDRFullBuffer2 x2` — 0.69 мс [лог] — это в основном перекачка полных целей, а не закраска четверти.

Уже существовавший приём «доказанная часть цели = область прохода» (`DM_VK_NATIVE_LOAD`, `area passes`) этого не закрывал: он
требует доказательства по первому draw (только полноэкранные треугольники поста), отказывает, если проход начинается с очистки
(`part with a clear`), и на стоковом Qualcomm не работал вовсе (пункт 4.1).

### 3.2 Что сделано: `DM_VK_NATIVE_FRAMEAREA` [код `vkn_pass.c`, блок «frame F1»]

Проход целей движка начинается с областью = **то, что его draw трогали в прошлых кадрах + прямоугольник draw, который его
открывает**.

- Прямоугольник draw = viewport ∩ ножницы ∩ цель. Путь отрисовки называет проходу draw, который готовит (`vkn_pass_draw_in`), так что
  проверяется **каждый** draw, включая собственные draw приёмов (слитый свет, пост), и в цепочку приёмов ничего не добавлено.
- История: ключ = (набор целей, его порядковый номер среди проходов этого набора в записи). Два кадра проход идёт полным и только
  наблюдается; потом область = объединение за последние кадры. Раз в 32 кадра история обновляется (масштаб упал — область сожмётся),
  выросла — растёт сразу, по первому же draw.
- Область выравнивается наружу до 16 текселей; если первый draw доказуемо перекрывает её всю — берётся как есть, и вложения не
  загружаются вовсе (сочетание с `LOAD`).
- Не сужаются: цели UI и окно, цели с несколькими уровнями / слоями, атлас теней под кэшем теней, проходы с подсказкой области от UI,
  выигрыш меньше 10 % площади.

### 3.3 Почему это точно

1. Vulkan сохраняет все тексели вне области прохода при любых операциях загрузки / сохранения.
2. Draw вне области быть не может: каждый проверяется до записи. Draw наружу — проход закрывается и открывается заново **полным**
   (счётчик `restarts: draw outside`); draw, который модуль не видит (сырые команды UI или приёма), — то же (`draw not seen`). Три таких
   перезапуска за 600 кадров — проход на 600 кадров остаётся полным (`bans`).
3. Очистка. Если проход начинается с очистки движка (пре-пасс, G-buffer), очистить только область — не то же самое, что очистить всё.
   Поэтому сужение разрешено лишь когда про текстуру **известно**, что все её тексели вне области уже содержат ровно это значение
   очистки. Это знание хранится на текстуре (`vkn_tex.fa_*`): появляется после полной очистки (проходом на всю цель, командой или
   заливкой нулями), область «что могло измениться» растёт на то, что рисовали проходы, и сбрасывается любой другой записью (копия,
   загрузка данных, запись из вычислительного шейдера, отброшенное сохранение). Нет знания, другое значение или старое содержимое
   торчит за областью — проход начинается полным (причины в счётчике: `clear: the outside is not known / another value outside / old
   content outside the area`). После полной очистки знание есть, и следующий кадр уже узкий.

При 100 % ничего не меняется: объединение draw = вся цель, проход остаётся полным.

### 3.4 Сверка и яд

- `=2` — решения принимаются и считаются (`would be`, `would restart`), все проходы начинаются полными.
- `=3` — яд: у вложения, которое начинается с суженной очистки, **всё вне области закрашивается пурпуром** (глубина — 0.5) перед
  проходом; следующий проход этой текстуры идёт полным и чинит. Если что-то в кадре читает тексели за пределами 3D-прямоугольника,
  на экране будет пурпур (мигает через кадр). Это и есть проверка «никто не читает снаружи». Возможная находка: розовая каёмка в
  1 пиксель по правому / нижнему краю картинки — билинейная выборка поста на границе. При обычной работе (`=1`) там лежит значение
  очистки, как и раньше, картинка не меняется.
- Хост-тест сверяет **всё изображение глубины** 256x256 покадрово между `=0`, `=1` и `=2` на сценарии с масштабом, который падает,
  растёт и возвращается, с очисткой посреди прохода и одним draw далеко за областью: равно во всех 30 кадрах (раздел 7).

## 4. Прочее

### 4.1 Программы позиций на стоковом Qualcomm и Maleoon (ошибка) [код `vkn_shlib.cpp`]

`vkn_pass.c` включал правило `LOAD=1` по `vkn_policy_tile_pass` (Mali, PowerVR, Maleoon, Adreno на драйвере Qualcomm), а библиотека
шейдеров строила программы позиций по `vkn_policy_load` от семейства — то есть только для Mali / PowerVR. Итог на телефоне хозяина:
`proofs 60.9: whole 0.00, part 0.00; refused: ... no position program 31.37` [лог], тогда как на модели Mali `whole 22.00` [лог W07].
Теперь библиотека берёт то же правило (с `driverID`). Никаких новых переключателей: это то поведение, которое и задумывалось.

### 4.2 Очистка области ждёт прохода: `DM_VK_NATIVE_LAZYCLR` [код `vkn_pass.c`]

Было: очистка области текущей цели при закрытом проходе сразу открывала проход (`vkCmdClearAttachments` внутри). Следующий draw
перед своим проходом переводил свои текстуры в раскладку чтения; если хоть одной нужен барьер — открытый проход закрывался (с нулём
draw) и открывался снова. Стало: очистка запоминается (до 8 штук) и исполняется сразу после начала прохода следующего draw.
Исполняется раньше, если её результат кому-то нужен: смена целей, копия / смена раскладки / запись в эту текстуру, конец записи —
тогда это отдельный проход, как раньше. Полная очистка той же текстуры её отменяет (всё равно перезапишет). Крючки UI видят те же
события, что и раньше. Точно по построению: до первого чтения или записи текстуры очистка выполнена.

### 4.3 Выученный полный барьер: `DM_VK_NATIVE_TILEBAR_LEARN` [код `vkn_pass.c`]

`TILEBAR` делает текстуру видимой только фрагментной стадии (чтобы разбивка на тайлы не ждала). Если потом её читает кто-то ещё
(вершинная стадия, UI, приём), нужен полный барьер, а он невозможен внутри прохода — открытый проход закрывается. Теперь текстура,
из-за которой так закрыли проход, помечается на 600 кадров и получает полный барьер сразу. Полный барьер всегда достаточен, так что
это точно; теряется только «не ждать разбивки» для одной текстуры.

## 6. Счётчики (раз в 10 с)

- `[vkn] pass policy (frame F1): ...` — один раз при старте: что включено и откуда.
- `[vkn] pass frame (frame F1; a presented frame over N): DM_VK_NATIVE_FRAMEAREA=...: passes of the engine's sets A: narrowed B, would be
  C (area P % of their targets, X MB of load + store left out), narrowed clears D (poisoned E); not narrowed: <причины>; restarts: draw
  outside, draw not seen, would, bans; passes with a draw not seen | DM_VK_NATIVE_LAZYCLR=...: region clears held, run in the draw's
  pass, in a pass of their own, superseded, empty passes not begun, would hold | DM_VK_NATIVE_TILEBAR_LEARN=...: full barriers at once,
  textures marked, would`.
- `[vkn] draw merge (DM_VK_NATIVE_DRAWMERGE=...)`: draw окон, приклеено (серий, индексов), «склеил бы».
- `[vkn] passlog k #nnn: ... area x,y WxH drawn x,y WxH | ...` — область прохода и то, что трогали его draw (`drawn ?` — был draw,
  которого модуль не видел).
- Старые строки для сравнения до / после: `pass ends` (число проходов и причины), `pass policy` (`proofs: whole / part`,
  `no position program`, `traffic model`), `gpu by pass`, `rt:` (занятость потока записи), `backend measured`.

## 8. Что не сделано и что дальше

1. **Память.** Ни один кусок ветки не уменьшает МБ: при масштабе цели остаются полного размера (54 цветовые цели 142.7 МБ + 6 глубины
   25.9 МБ [лог]). Настоящая экономия — при **постоянном** масштабе создавать цели уже уменьшенными (не через объект DRS, а через
   размер 3D-целей): при 50 % это ≈ −126 МБ, при 75 % ≈ −74 МБ [оценка от лога], и заодно исчезает сама задача «часть цели». Это
   решение в `hle_dos2_quality.c` (ветка `dos2-vk5-drsfsr`), сюда не входило.
2. **[сделано 22.11, раздел 13]** **Слитый пост при масштабе ниже 100 %** не работает (отказ `a part of the target is drawn`, раздел 1). Нужно научить `vkn_post.c`
   сливать хвост при частичном покрытии (и сочетать с модулем FSR). Выигрыш: 2–3 прохода и полноэкранных draw на кадр именно в режиме
   «слабое устройство, 50–75 %».
3. **`HDRFullBuffer2` → тот же цвет + глубина** одним проходом (туман, затем прозрачные): −1 проход, −16 МБ на кадр [м]. Делается как
   `PASSJOIN`: проход открывается сразу с глубиной, первый draw получает состояние «без теста глубины». Не сделано: нужны свои
   варианты конвейеров для этого draw.
4. **Склейка draw вне проходов только с глубиной** (G-buffer: 598 draw) — там порядок важен, клеить можно только подряд идущие; окна
   сортировки там нет. Делать после того, как счётчик `draw merge` покажет, есть ли вообще такие серии.
5. **Очистка области + загрузка**: если ждущая очистка покрывает всю область прохода, его можно начать с `CLEAR` вместо `LOAD` (цели
   фильтров UI). Области в журнале близки, но не равны (81x55 против 83x57) — нужен прогон.
6. **Turnip**: включать ли `FRAMEAREA` — по прогонам F04 / F05.
7. **Видимость Б** (`DM_VK_NATIVE_COND=7 / 9`) отказывает в проходе с суженной областью (`vkn_occb.c`, причина `VKN_OB_R_AREA` — правило
   было и раньше, для подсказок UI): при масштабе ниже 100 % с областью кадра она не сработает. Умолчание `COND=0`, так что сейчас это
   ничего не меняет; если Б станут включать — научить её проверять свой прямоугольник против области.
8. Запись в общую базу знаний (`docs/port-kb`) — раздел 11, вносит координатор после телефона (база лежит вне моего дерева).

## 11. Заготовка записи в базу знаний (`docs/port-kb/performance.md`, вносит координатор после телефона)

### PERF-X.. Область прохода = то, что рисуют, при масштабе 3D ниже 100 %
- **Симптом:** при 50 % разрешения 3D GPU-время почти не падает на тайлерах (DOS2: 11–14 мс при 25 % пикселей, стоковый Qualcomm).
- **Устройства/GPU:** Mali, PowerVR, Maleoon, Adreno на стоковом драйвере (GMEM). На Turnip (sysmem) эффекта почти нет.
- **Причина:** игра с динамическим разрешением рисует в часть полноразмерных целей; проход, открытый на всю цель, заставляет
  тайлер загружать / чистить / сохранять все тайлы.
- **Фикс:** `DM_VK_NATIVE_FRAMEAREA` (тайлеры 1; 2 сверка; 3 яд): область = объединение draw прошлых кадров + первый draw; суженная
  очистка — только когда известно, что вне области уже лежит то же значение; draw наружу = перезапуск полным проходом.
- **Эталон:** DOS2 → `dm/gfx/vkn/vkn_pass.c`, блок «frame F1» → ветка `dos2-vk5-frame`.
- **Проверка:** хост (изображение глубины равно покадрово), на телефоне не проверено.
- Рядом: программы позиций обязаны строиться по тому же правилу, по которому включается `LOAD` (на стоковом Qualcomm было
  рассогласование: 0 доказательств); очистка области не должна открывать проход раньше первого draw (`DM_VK_NATIVE_LAZYCLR`).

### 13.1 Что было: почему слитый пост не работал ниже 100 %

Хвост поста в кадре (дамп U07r, `trace:` [лог]): `PPApplyLUT` HDR → `f`; `EoCSight` `f` → `e`; `EoCFog` `e` → `f` (пишет обратно в цель
LUT); `PPFXAA` `f` → `4`; `CombineUI` `4` → окно. Ниже 100 % все draw до `PPFXAA` рисуют левую верхнюю часть целей 2160x972, а `PPFXAA`
растягивает часть на всю цель — это и есть увеличение (с FSR это EASU, с `DM_VK_NATIVE_FSR_AA=1` перед ним предпроход FXAA 1:1 части).

Три причины, все от одного правила «доказательство покрытия = вся цель»:

1. **F1 (LUT ∘ Sight) не взводился ни разу при постоянных 50 %.** Пробное окно после Sight следит, не трогает ли кто цель LUT. Туман
   пишет в неё только часть, а правило считало «полной перезаписью» только запись всей цели — каждая запись тумана ломала пробу. В логе
   хозяина это строка `a draw of another class writes a watched image 588` за 10 с [лог `dm-10577-all.txt`] (имя отказа вводит в
   заблуждение: так же назывался и этот случай — запись поста частью).
2. **Если F1 успел взвестись при 100 %, а DRS потом опустил размер, F1 становился вредным**: LUT пропускался, а потом каждый кадр
   рисовался заново из тайника перед записью тумана (`materialised 595` за 10 с при DRS 86–98 % [лог `logcat-before.txt` 02:05]):
   тот же LUT плюс разрыв прохода.
3. **Маршрут A (F1A = FXAA ∘ LUT ∘ Sight, шаг AA пропущен)** при части невозможен в прежнем виде: шаг AA и есть увеличение, его нельзя
   выбросить (`a part of the target is drawn 588`, `AA step coverage differs 588` [лог]).

### 13.2 Что сделано (`DM_VK_NATIVE_POST_PART`, умолчание 1) [код `vkn_post.c`, `vkn_fsr.c`]

1. **Доказательства — по нарисованной части.** Наблюдение за пропущенной целью (и пробное окно) теперь хранит прямоугольник
   пропущенного draw. Draw поста, который заменяет каждый канал этой части (без смешивания, маска записи 0xF, цель не читает),
   закрывает наблюдение так же, как раньше запись всей цели. Почему точно: пропущенный draw писал только свою часть; всё вне её в обеих
   цепочках (с пропуском и без) одно и то же — старое содержимое. Попутно и для записи всей цели теперь проверяется маска записи (раньше
   только «нет смешивания»: запись без альфы считалась бы полной).
   Итог: F1 взводится и при постоянных 50 / 75 %, туман закрывает наблюдение, повторов LUT нет.
2. **Маршрут A на части — только вместе с FSR.** При `DM_HACK_FSR` + `DM_VK_NATIVE_FSR_AA=1` сглаживание растяжения — предпроход FXAA 1:1
   по части (VK-DRS-FSR). F1A рисует то же сглаживание внутри draw Sight (то же приближение, что маршрут A при 100 %), туман несёт его
   дальше, как при 100 %, а предпроход FSR для этого draw **не рисуется**: EASU читает выход тумана напрямую. Проверяется: шаг —
   подменённый модуль FSR с растяжением s < 1, часть в начале координат (`c3.zw = 0`), источник размера цели, viewport на всю цель;
   EASU читает тексели `[0, floor(s × размер + 0,5))` (свой прижим модуля) — они внутри прямоугольника, который нарисовали F1A и туман.
   Копия для EASU (своя цель размера источника, 8 МБ при 2160x972 RGBA8) отпускается через 600 кадров без предпроходов (снова
   делается, если предпроход понадобится).
   Без FSR (растягивает консольный FXAA сам, сглаживание и увеличение в одном draw) маршрут A на части точно не сделать — там остаётся
   F1 (минус проход LUT), отказ маршрута A считается под новым именем `a part of the target is drawn and the AA step is not the FSR
   stretch with DM_VK_NATIVE_FSR_AA=1`.
3. **Яд `DM_VK_NATIVE_POST_VERIFY=2` на части** заливает пурпуром только часть пропущенной цели: вне её изображение никогда не было
   результатом пропущенного draw (раньше яд закрашивал всю цель — показал бы старые тексели, которые читает растяжение у края части, и
   это не наша ошибка).
4. **Шум в счётчиках убран**: наблюдение маршрута A начинается только там, где маршрут возможен (раньше при 50 % без FSR каждый кадр
   считался ещё и `AA step coverage differs`).
5. F2 (Vignette ∘ Combine) части не касается: виньетка идёт после растяжения, по всей цели. В сцене хозяина её всё равно нет.

Переключатель `DM_VK_NATIVE_POST_PART`: 0 — как до этой ветки; 1 — умолчание (выше); 2 — решения по части считаются (`would`), а
делается как при 0. Читается один раз вместе с `DM_VK_NATIVE_POST`.

### 13.5 Пункт 2 задачи: 3D-цели меньшего размера при постоянном масштабе — разобрано, не сделано

Что нашлось в коде игры (`main.raw`, capstone):
- 3D-цели делает пул целей окна `0x912f70(пул, w, h, масштаб)`: у каждой записи пула размер = `max(1, доля × окно)` и, если у записи
  флаг `+0x1c`, ещё × масштаб пула (`+0x2c`); пересоздание — `0x92d9f0`, только если размер окна или масштаб изменились.
- Масштаб пула — `[окно + 0x44]` = 0,9 (это и есть «3D = 0,9 окна», 2160x972 при 2400x1080). Источник 0,9 — настройки рендера
  `[main+0x2bb8a60] + 0x34` (`0x938b90`), а это значение читают ещё и места UI (`0x110e374` — масштаб UI, `0x113f828`, `0xa6c294`,
  `0xae3ca0`, `0xae40f8`, `0x12664fc`).
- Максимум DRS = масштаб пула × окно (`0xa6a770` → `SetSize 0xb21880`).

То есть «цели нужного размера» в этом движке = масштаб пула 0,9 × p при DRS 100 %. Почему не сделано в этой ветке:
1. **Картинка не та же.** Уменьшается и цель шага AA (`4`), растяжение шага исчезает (он становится 1:1), увеличение переезжает в
   билинейную выборку `CombineUI` (окно 2400x1080 из 1080x486). Без FSR это близко к сегодняшнему, но не бит в бит; **с FSR EASU
   пропадает вовсе** — нужен свой модуль `CombineUI` с EASU (новый шейдер, доказательства, как в VK-DRS-FSR).
2. **Общее значение с UI.** Менять `+0x34` нельзя (сдвинется масштаб UI); нужно найти, кто пишет `[окно + 0x44]`, и подменять только его
   (в этой сессии не найдено).
3. **Смена на лету** (шестерёнка применяет строку разрешения сразу, `dm_dos2_res3d_live`) — это путь движка `Window::Resize`
   (`0x912f70` + `SetSize` на границе кадра); у нас он уже заменён в `hle_dos2_vkn_frame.c`, так что можно, но проверяется только на
   телефоне (пересоздание всех 3D-целей посреди сцены, кэши бэкенда по текстурам).
4. **Выигрыш теперь только в памяти.** Трафик и работа тайлера уже идут по части (область кадра, раздел 3), слитый пост на части —
   этот раздел. Память: ≈ −126 МБ при 50 %, ≈ −74 МБ при 75 % [оценка раздела 8 по логу: 54 цветовые цели 142,7 МБ + 6 глубины 25,9 МБ].

План, если хозяин скажет «нужно» (≈ 5–7 агент-часов + прогоны): найти запись `[окно + 0x44]`; переключатель `DM_DOS2_RES3D_POOL`
(0 / 1 / 2 счёт) — при постоянном масштабе p и только на старте: масштаб пула 0,9 × p, DRS 100 %; модуль `CombineUI_fsr` (EASU по
`tScene`, растяжение по производной, как у модуля PPFXAA); затем смена на лету через путь `Resize`. Сравнение картинок
«часть + растяжение» против «маленькие цели + Combine» на телефоне (скриншоты), решение — за хозяином.

### 13.6 Другие проходы, которые должны следовать разрешению 3D

Проверено по коду и логам, что можно проверить без телефона:
- **Туман (`EoCFog`) и контур (`EoCOutlineCombine`)**: рисуют ту же часть, что Sight (их покрытие сравнивается с частью F1A при переносе
  — `memcmp` прямоугольников, тест выше); ничего не пересчитывать.
- **Bloom (Half / Quarter / Eighth), половинные буферы, пирамида яркости**: viewport ставит движок (раздел 3.1, `VK-DRS-SUPPORT.md`);
  пирамида яркости — цели постоянного размера 256…1, читает HDR через отображение своего вершинного шейдера. Подтверждение — прогон
  F10 раздела 10 (`drawn` каждого прохода) и яд области кадра (F06 / F11): если что-то читает за частью, будет пурпур.
- **Предпроход FSR**: копия теперь отпускается, когда маршрут A держится (раздел 13.2).
- Нового «неправильного пересчёта» в бэкенде не нашлось: всё, что было, — правила «вся цель» в слитом посте (исправлены) и область
  прохода (раздел 3).
