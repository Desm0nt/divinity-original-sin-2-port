# NR-10b `DM_NR_COVER` — доказательство покрытия первым draw для вычисляемых позиций (сегменты S1 + S6)

Ветка `dos2-nr10b` (worktree `wt-nr10b`, база `dos2-nr10` 36f66a7). На телефоне **не запускалось** (ни один режим). Умолчание 0 везде.
Источник задачи — NR-10 §5.1: на тайлерах главный рычаг — начинать проход с load `DONT_CARE` вместо `LOAD`, когда первый draw
доказуемо закрывает всю область; в DOS2 старое доказательство не срабатывает ни разу (`ab7rp3`: `noload_passes_per_frame=0.00`,
`why=25.0/0/…`, `[nb] rp … applied: load DONT_CARE 0`).

## 2. Что сделано

**Программа позиции** (`dm/gfx/vulkan/engine/xbg_spirv_pos.cpp`, `nr_cv_prog` в `dm/gfx/nr/nr_cover.h`). Символьный проход по VS из одного
блока (без вызовов и ветвлений, без записи Clip / CullDistance): каждое float-значение — инструкция над листьями «константа / компонента
входа (Location) / float uniform-блока (binding + смещение по `Offset` / `ArrayStride`)» и операциями `+ − × ÷ neg fma abs min max`;
`Function` / `Private`-переменные и выход позиции хранят последнее записанное значение по компонентам (store через цепочку доступа,
целым вектором, через копию указателя). Запись по указателю, который не переменная, — отказ. В программу попадает только то, от чего
зависят четыре компоненты позиции (≤ 48 инструкций, ≤ 4 блока). Строится при загрузке VS и **только при `DM_NR_COVER≠0`**
(`Shader::pos`), по финальному SPIR-V (после всех переписываний — там же, где старые факты).

**Доказательство** (`nr_cv_cover`, чистый C). В момент первого draw прохода программа исполняется на CPU для его 3…18 вершин: байты
вершин — из снимков, которые draw отдаёт GPU (как в старом доказательстве), uniform — из гостевого диапазона, привязанного сейчас к
вершинной стадии (его же копирует `descriptors()`). Дальше геометрия в пикселях framebuffer после viewport-преобразования хоста:
- доказываемая область = **центры пикселей** внутри viewport ∩ scissor ∩ framebuffer (примитивы режутся по viewport, фрагменты — по scissor);
- её закрывает один неотброшенный треугольник **или пара** с общим ребром (общие вершины бит-в-бит), образующая выпуклый четырёхугольник;
- запас 0,25 px за крайние центры — плата за то, что CPU не повторяет GPU бит-в-бит (fma, viewport, привязка вершин к сетке: Vulkan
  гарантирует 4 бита = 1/16 px). Для «точных» программ позиция совпадает побитно, запас всё равно действует;
- как раньше: `w == 1` точно, `z ∈ [0,1]`, конечные `x, y`; culling и front face — в том же виде, что берёт `nvn_cover`.
Результат — прямоугольник пикселей: весь framebuffer или его часть.

**Условия отказа** — все старые (`first_draw_covers`) плюс: logic op ≠ COPY, условный draw (`DM_GFX_COND_RENDER`: может не
нарисоваться), draw без экземпляров, uniform-диапазон, который хост отдаёт GPU не как есть (сдвиг UI `g_ui_moff`, диапазон под ещё
не считанным результатом GPU — `overlaps_pending`). Входы программы — только float-форматы R32…RGBA32, пер-вершинные потоки.

**Решение:**
- **весь target** → `covered = true`: в пути плана NB (`nbrp_begin`) вложения `cover_dc` начинаются с load `DONT_CARE` (как и было
  задумано в NB-05 / NB-06, просто теперь доказательство есть); без плана (`begin_open`) — цветовой twin `DONT_CARE` (бит 27), причём
  он берётся через `lazy_twin`, если у прохода нет готового `pass_noload` (`DM_GFX_NOLOAD` выключен);
- **часть target** (DRS < 100 %: пост рисует viewport 1620×729 из 2160×972) → проход начинается с этим прямоугольником как
  **render area** и load `DONT_CARE` на `cover_dc`-вложениях. Vulkan оставляет всё вне render area нетронутым — ровно то, что дают
  LOAD + draw внутри прямоугольника. Правила: (а) только проходы плана NB; (б) бухгалтерия хоста (история store, transient NB-19,
  точки видимости NR-10, `nbrp::compare`) считает такой проход **LOADed** — биты `DONT_CARE` идут только в маску twin, не в `t.dc`;
  (в) **все store остаются STORE** (биты 18+k сняты); (г) следующий draw / clear этого прохода, который может выйти за область
  (viewport ∩ scissor; линии и точки — с запасом 4 px), завершает проход и хост начинает его заново с полной областью и LOAD
  (`nrcov::pre` / `before_clear`, счётчики restarts); (д) не применяется под режимами poison, чистящими весь target
  (`STORE_HIST=3`, `DM_NB_RP=3`, `DM_NR_RP=3`), и если экономия < 10 % target.

**NB-18b / маршрут A.** Слитый draw (F1 / F1A) идёт через тот же `draw()` со своим FS и теми же проверками: `draw_reads` берётся из его
собственных дескрипторов (stash и перенаправленный слот S попадают туда через `prepare_read`), `discards` / выходы — у слитого модуля.
Пропущенный проход E не начинается вовсе. Правило NB-18b-9 (F1A только при полном покрытии LUT) не затронуто.
**NR-10 fresh.** Свежие вложения добавляют биты `dn.dc` до расчёта twin — на проходе с областью они действуют внутри области (вне её
содержимое остаётся — строже, чем нужно). Poison NR-10 (`DM_NR_RP=3`) чистит весь target, поэтому проходы с областью при нём выключены.

### Переключатели
| | |
|---|---|
| `DM_NR_COVER=0` (умолчание, все семейства: `xbg_nr_cover_default`) | прежний поток команд: оба места начала прохода — `nrcov::mode ? nrcov::at_begin(…) : <прежнее выражение>`; программа позиции не строится; добавлены только `nrcov::red.on=false` в `end_open_pass` и две проверки `if(nrcov::red.on)` (всегда false) |
| `=1` | решает доказательство: старое ИЛИ новое; весь target → load `DONT_CARE`, часть → render area + `DONT_CARE` |
| `=2` | исполняется старое решение; новое считается для каждого прохода, начатого draw: «было бы» целиком / областью, МБ load, первая несработавшая проверка каждого отказа; первые 24 отказа — отдельными строками (`[nr] cover refusal: pass WxH vs … fs … viewport …: причина`). Красная строка `【红】[nr] cover check: …` — старое «да», новое «нет» (не ожидается: новое — надмножество) |
| `=3` | 1 + каждое вложение, начатое `DONT_CARE` по доказательству, сразу после begin заливается пурпуром **внутри доказанного прямоугольника**; первый draw обязан закрасить всё — пурпур на экране = доказательство неверно |
| `DM_NR_COVER_UBO=0` | позиции с uniform (Iggy, ImGui) не доказываются — A/B более рискованной части (умолчание 1) |
| `DM_NR_COVER_AREA=0` | без проходов с областью (умолчание 1) |

Строка раз в 10 с: `[nr] cover DM_NR_COVER=N: F frames; a frame: passes begun by a draw X (by the NB plan Y); old proof yes …; new proof:
whole target A (K attachments = M MB of load at 4 B/px), a part B (…); positions copied / computed; refused: <причина n, …>;
applied / would apply: whole …, area … (area not usable here …, twin failed …), restarts by a draw / by a clear …, poisoned …; never
expected … ; proof N ns`. При старте: `[nr] cover DM_NR_COVER=N: …` и `[nr] cover: positions computed from uniforms … area passes …`.

## 4. Ожидаемый выигрыш (оценки, замеров нет)
Палуба, 2160×972, по дампу: до 22 проходов поста. Полноразмерных среди них ≈ 8 (ClusteredLighting, FadeBlending, LUT, Sight, EoCFog,
FXAA, часть PPDefault / bloom верхнего уровня) × 8,4 МБ (при 4 Б/px; HDR-цели RGBA16F — вдвое больше) + цепочки яркости и bloom
(половины / четверти) — это те самые 70–90 МБ load на кадр из NR-10. Если заливки Iggy (14 проходов 2160×972) закрывают target целиком —
ещё до 118 МБ; этого по дампам не видно (нет вершин), скажет `=2`.

## 5. Что не сделано и почему
1. **`CLEAR` вместо `DONT_CARE`.** На тайлере `DONT_CARE` не дороже `CLEAR`, а `nbrp_begin` не носит значений clear (пришлось бы
   тянуть `pClearValues` в twin-путь). Смысл `CLEAR` — только обход бага драйвера с `DONT_CARE`; если `=3` на живом Mali покажет мусор
   при чистой SIM-картинке, это следующий шаг (маска clear у twin уже есть: биты 2k).
2. **Покрытие суммой нескольких draw** (заливка двумя прямоугольниками, сетка) и **поворот / перспектива** (`w ≠ 1`) — отказ.
   Матричные шейдеры Iggy дают `w` из uniform; если он не ровно 1 — причина `w != 1`. По счётчику `=2` будет видно, стоит ли.
3. **Проходы с областью вне плана NB** (`begin_open`: 14 проходов UI мимо плана) — там уже работает `DM_NB_UIAREA` со своей областью
   (grow-only); два механизма на одном проходе не совмещал. Полное покрытие в `begin_open` работает.
4. **Проходы, начатые clear-путём / с отложенными clear** (`lazy_clear_open`) — они и так начинаются с `CLEAR`.
5. **Сверка позиции с GPU на устройстве** (transform feedback) — нет; вместо неё оракул, интерпретатор и poison.
6. **Первый draw с `quad`-индексами, GPU-indirect, сдвигом UI** — отказ (как у старого доказательства), считается причиной `host draw rewrite`.

## 6. Риски
1. **Uniform на момент исполнения.** Позиция с uniform читается из гостевой памяти в момент draw; GPU получает снимок (один на
   диапазон на submission) или zero-copy вид той же памяти. Расхождение возможно, только если движок переписал диапазон после
   привязки в том же submission (по NB-12 кольцо констант движка пишется один раз до привязки; сверка — `DM_NB_UBO=2`, строка `[nb] ubo … race`). Касается только
   7 шейдеров UI; вся пост-цепочка — «точная», без uniform. Отсечка: `DM_NR_COVER_UBO=0`.
2. **Render area не кратна тайлу** (1620×729): по спецификации содержимое вне области сохраняется, но у старых мобильных драйверов
   с некратной областью и `DONT_CARE` бывают ошибки на крайних тайлах. Проверка — `=3` при DRS 75 % (пурпур / мусор по правому и
   нижнему краю области). Отсечка: `DM_NR_COVER_AREA=0`.
3. **Обрезка по viewport.** Доказательство области и правило «следующий draw внутри» опираются на то, что закрашенный треугольник не
   выходит за viewport (обрезка по объёму отсечения). Если драйвер с guard-band красит за viewport внутри scissor — это запись вне
   render area (UB); на тайлере она просто теряется, что совпадает с «обрезано». Для линий / точек взят запас 4 px.
4. **Ложное «покрыто»** = пропавший кусок старого кадра (мусор / чёрное на тайлере, на sysmem не видно — поэтому poison). Защита:
   оракул, интерпретатор на всех 117 шейдерах, условия старого доказательства + новые отказы, `=3`.
5. Проход с областью, который часто перезапускается (второй draw шире области), стоит лишний проход: счётчик `restarts by a draw`
   должен быть ≈ 0; иначе — `DM_NR_COVER_AREA=0` и разбор, какой это проход.
6. Допущение: финальный модуль VS = тот, что разобран. Варианты retype вершинных входов меняют только не-float входы, а программа
   требует float-форматы у всех читаемых входов; новое переписывание позиции после точки разбора сломает допущение (как и у старых фактов).
7. При `≠0` включается `draw_reads_on` (список чтений draw для отказа «читает свой target») — как при `DM_GFX_NOLOAD=1`; путь
   hit-fast (NB-12) тогда идёт полным путём (в DOS2 он и так полный: `hist_on`).

## 8. Прогоны телефона (Mi 14 Ultra; бэкап `files/save`, проверить keyguard, force-stop после логов)
Сцены: палуба корабля **и** тяжёлая (бой / Форт Радости), меню, инвентарь, карта; по 60 с; `DM_DOS2_FPS=0`.
1. **Счёт:** `DM_NR_COVER=2`. При старте `[nr] cover DM_NR_COVER=2: count only…`. Раз в 10 с `[nr] cover DM_NR_COVER=2: …`: жду
   `old proof yes 0.00`, `new proof: whole target ≈ 15–22 (… MB of load)`, `never expected (old yes, new no) 0`, красных `【红】[nr] cover`
   нет. Записать список `refused: …` и первые строки `[nr] cover refusal: …` — это перечень того, что ещё мешает (blend у bloom,
   геометрия Iggy и т. д.).
2. **Счёт при DRS:** `DM_NR_COVER=2 DM_DOS2_DRS=75:75`: `a part ≈ 15–20 (… MB)`, `whole target` — только проходы после FXAA и цепочки
   малого размера.
3. **Poison:** `DM_NR_COVER=3 DM_GFX_SIM_GPU=mali` — все сцены выше: **нет пурпура**; `applied: whole X, area 0`, `poisoned ≈ X`.
   Затем то же с `DM_DOS2_DRS=75:75`: `area ≈ 15–20`, `restarts by a draw ≈ 0`, нет пурпура и мусора у правого / нижнего края 3D.
4. **A/B:** `DM_NR_COVER=1` против `0` (с `DM_GFX_SIM_GPU=mali` и без), ABBA × 2: `[nb] rp … applied: load DONT_CARE` 0 → ≈ X на кадр и там же
   `load plan\host L/C/D/F` (столбец D растёт на X), картинка та же (`DM_GFX_PASS_VALUES`), `gpu_ms` / fps. На Turnip sysmem разницы не жду.
5. Настоящий Mali / PowerVR — только тестовая сборка игрокам с умолчанием по детекту (`xbg_nr_cover_default`), строка `[nr] cover` в логе.

## 9. N5: покрытие после NR-27 (`DM_NR_UBOVEC`) — ветка `dos2-nrp0` (аудит AUDIT-FINAL §2 п. 3)

На телефоне программа позиции строится из **финальных** слов модуля: после очисток загрузки (`tidy_rewrite`: NaN min / max, LDC fold,
forwarded temps, LDC canon, F2I) и последним — `ubovec_rewrite` NR-27 (`xbg_game.cpp` `tidy_rewrite` → `xbg_spirv_pos_prog`). Перепись §3
шла по сырым бандлам. Новый тест `tests/nr_cover_chain_test.cpp` строит программу из тех же слов, что телефон, и сравнивает с цепочкой без
NR-27 (вход / отказ, причина, инструкции, входы, байты UBO, «точность»); с файлами — пишет программы и финальные модули для
`nr_cover_census.py` (новый 4-й аргумент: каталог `<key>.spv` вместо SPIR-V бандла).

Пак `work/shaders-vk` (12 333 бандла, 6 132 VS), цепочки `nftci` (как на Adreno с `DM_GFX_D3PERF`), `ftc` (как `ubovec_scan`), `-`:
- программ позиции: сырые 117, после очисток 117 (**0** отличий от сырых), после `DM_NR_UBOVEC` 117 (110 точных); список программ
  одинаков во всех трёх цепочках (побайтно);
- NR-27 переписал 2 062 VS (проверка `xbg_spirv_ubovec_check`: 0 отказов), **61 из них — шейдеры с программой позиции**; программ, которые
  он изменил: **0**. То есть пересечение не пусто (у этих 61 чтения с вычисляемым индексом есть, но в выражение позиции не входят — только в другие выходы; что именно это за выходы, не разбирал),
  а не «такие и так отвергаются», как предполагал аудит: доказательство — равенство программ, а не непересечение множеств;
- интерпретатор (`nr_cover_census.py … - <spv>`) на финальных модулях всех 117: 24 случайных набора × 117, **0 расхождений**, худшая
  относительная ошибка вычисляемых 4.34e-6 (как в §3).
Итого NR-27 × NR-10b конфликта нет; включённый на Mali `DM_NR_UBOVEC=1` доказательства покрытия не меняет. Запуск: шапка теста.
