# NR-09S `DM_NR_STATE` — пакет «всё состояние draw» (код 21) нативным кодом (ночь 18.11.2026, ветка `dos2-nr09s`)

Worktree `wt-nr09s`, ветка `dos2-nr09s` от `dos2-nr-all` 528e3a8. Телефона не было (adb не запускался): всё доказано на ПК —
эмулятором на машинном коде игры, тестами, сборкой. **На устройстве не исполнялось ни строчки.** Всё за `DM_NR_STATE`, умолчание 0.

## 0. Коротко
- **Что заменено.** Обработчик пакета кода 21 (`ExecuteRenderCommand 0x93e5f0` → `0x93e6ac`, 0x70 Б: шейдер, depth-stencil + stencil ref,
  raster, blend, формат вершин, VB 0–2, IB, примитив, условный рендер, alpha ref) вместе с `SetShader 0x9283a0` и `SetBlend 0x9284e0`
  при `DM_NR_STATE=1` **не исполняется как машинный код игры**. Нативная модель (`dm/gfx/nr/nr_state.h`) читает пакет и кэш рендерера,
  пишет то, что пишет машинный код (поля `r`, отметки кадра в записях таблиц), а вызовы NVN пакета — **компактная нативная запись
  состояния** (`nrst_op`, 40 Б на вызов) — уходят в тела точек входа HLE **одним вызовом на большом стеке**: ни одного thunk-а, ни одной
  обёртки большого стека на вызов, ни одной инструкции движка.
- **Доказательство.** Unicorn на `main.raw`: 5 000 случайных состояний через `ExecuteRenderCommand(…, 21, …)` целиком (диспетчер, обработчик,
  `SetShader`, `SetBlend`) и через модель: **те же вызовы NVN по порядку со всеми аргументами, тот же возврат 0x70, та же гостевая память
  байт в байт**; 8 мутаций модели — 8 пойманы (§4). `DM_NR_STATE=2` на телефоне сверяет то же на живых пакетах.
- **Что НЕ заменено (и почему).** Записи, которые пишут тела (NVN-записи → тень NB-13a → `OP_X_NB_STATE` → `execute()` бэкенда), остаются:
  бэкенд и полоса NR-09 читают `State`, собранный из них (NR-13 §1.2). Это следующий шаг — S3 (§6): нативная запись состояния
  прямо в бэкенд без NVN-записей и тени. Модель кода 21, доказанная здесь, — его обязательная основа (без неё нечего класть в запись).
- **Выигрыш честно.** S1 срезает только трамплин + обёртку на вызов (≈ 12–37 нс на X4) и одну смену стека на вызов: в Форте Радость
  ≈ 4 000–4 900 вызовов состояния на кадр → **−0.05…0.17 мс на потоке игры (Mi 14)**, ×2.5–3 на in-order ядрах (A55 / A510 / A520, куда
  HyperOS сбрасывает main по NR-CPU) → −0.15…0.5 мс. GPU — 0 (поток команд тот же байт в байт). Точное число даёт один прогон
  `DM_NR_STATE_AB=1` (§7). Большой рычаг — S3 (−0.6…1.2 мс на двух потоках, §6).

## 1. Разбор: что делает код 21 (по машинному коду, `dos2_nr_check`-адреса из NR-02)
| Часть | Условие (фильтр движка) | Вызовы NVN | Запись в память |
|---|---|---|---|
| `SetShader(r, pkt+8)` | `r+0x17d8 ≠ pkt` | VS (1) + FS (2) `BindProgram`; если в записи нет VS или FS — compute (0x20) и `r+0xb78 = 1`; запись не найдена — три `BindProgram(NULL)` | `r+0x17d8`, `r+0x17e0`, отметка кадра в записи (таблица `r+0xc0`, 0x60 Б) |
| depth-stencil / ref | `r.ds == 0` или ≠ или ref ≠ | `BindDepthStencilState`, `SetStencilMask(3, b)`, `SetStencilValueMask(3, b)`, `SetStencilRef(3, ref)` | `r+0x1708`, `r+0x1710` |
| raster | `r == 0` или ≠ | `BindPolygonState` | `r+0x16f0` |
| `SetBlend(r, pkt+0x28, −1)` | `r == 0` или ≠ или маска ≠ | на каждую из 8 привязанных RT: `BlendStateSetBlendTarget` + `BindBlendState`; на все 8: `ColorStateSetBlendEnable` двух colour-state записи; `BindColorState` (с alpha-test, если `r+0x1868 ≥ 0`). Особый хэндл `[main+0x2bbdb70]`: состояния по умолчанию на стеке | `r+0x16f8`, `r+0x1700` |
| формат вершин | ≠ | `BindVertexAttribState(16)` + `BindVertexStreamState(1…3)` | `r+0x1740` |
| VB 0 / 1 / 2 | ≠ или «грязный» `r+0x1788+8i`; 1 и 2 — только если в пакете не 0 | `BindVertexBuffer(i, адрес, размер)` | `r+0x1748+8i` (0 для чужого хэндла), `+0x1788+8i`, отметка кадра записи (`r+0x180`, 0x68 Б) |
| IB | ≠ или `r+0x17d0` | — | `r+0x17c8`, `+0x17d0`, отметка кадра записи (`r+0x240`, без проверки поколения) |
| примитив | байт ≠ | — | `r+0x1714`, `r+0x1718` (таблица `main+0x1f58640`) |
| условный рендер | флаг или указатель ≠ | `SetRenderEnable(1)` / `SetRenderEnableConditional(1, [pkt+0x60])` | `r+0x185c`, `+0x1860`; всегда `r+0x185d = 0` |
| alpha ref | ≠ (NaN ≠ всему) | `SetAlphaRef`, если ≥ 0; затем `SetBlend` ещё раз с принудительной сменой (colour state идёт за тестом) | `r+0x1868`, `r+0x16f8` |

Смена blend = до 33 вызовов NVN (обычно 19 при одной RT) — самый «вызывной» кусок. Хэндлы, которые машинный код превратил бы в плохой
указатель для NVN (DS / raster / blend / формат вершин не найден при ненулевом хэндле) или нулевой указатель таблицы / контекста — модель
**не берёт** (пакет исполняет движок, ничего не тронуто).

## 2. Что сделано
- `dm/gfx/nr/nr_state.h` (чистый C): `nrst_code21` — **только читает** гостевую память и возвращает весь эффект пакета: поля `r` как они
  станут (`nrst_rs` + маска `stored` — что машинный код пишет), отметки кадра (адрес → значение), вызовы NVN по порядку (`nrst_op`);
  `nrst_commit` — записи; `nrst_check_mem` / `nrst_same_op` — сверка `=2`; `NRST_CODE_TABLE` (FNV-1a диспетчера, обработчика, `SetShader`,
  `SetBlend`), `NRST_SLOTS` (19 слотов указателей NVN движка в порядке `NRST_F_*`). Записи до вызовов: ни одно тело NVN не читает поля `r`
  и отметки (тела читают объекты состояния, на которые указывают вызовы, а пакет их не пишет).
- `dm/gfx/nvn/nvn_nr_state.{h,inc}`: исполнитель `nvn_nrs_exec` — `switch` по `fn` → тело точки входа (`h_nvn…`) с теми же аргументами;
  два стековых объекта пути «blend по умолчанию» — свои, обнулённые (`SetDefaults` пишет их целиком). `nvn_nrs_ready` — 19 точек входа
  кончаются именно этими телами (как `nvn_nrd_ready`). Захват `=2`: 19 строк `NST(...)` — первая инструкция каждого из 19 тел (в
  `BindProgram` / `SetRenderEnable` — сразу после строк NR-02 / NR-23); без `=2` — загрузка + непринятый переход.
- `dm/host/hle_dos2_native.c`: у общего хука `ExecuteRenderCommand` — необязательный нативный обработчик опкодов (`dn_install_rc_take`,
  маска); pre / post всех обработчиков (скобка NB-13a, NB-15, отметки прохода) работают как прежде **вокруг** него; `dn_rc_call_orig` —
  оригинал изнутри обработчика (для `=2` и A/B). Без обработчика — одна загрузка и непринятый переход на пакет.
- `dm/host/hle_dos2_nr_state.inc` (+ 6 строк в `hle_dos2_nr.c`): переключатель, проверка хэшей кода и таблицы переходов (опкод 21 →
  `0x93e6ac`), проверка 19 указателей движка (один раз, первый пакет), обработчик `nrs_take`, строки отчёта.

## 3. Переключатели (умолчание 0; игрокам не выдаются; `jni_android.c` и `xbg_vendor_policy.h` не тронуты — от GPU не зависит)
| | |
|---|---|
| `DM_NR_STATE` | **0** — ничего: хука-обработчика нет, 19 строк `NST` — загрузка + непринятый переход. **1** — код 21 нативно (модель → записи → вызовы тел на большом стеке одной сменой). **2** — исполняется обработчик движка; модель считается до него на том же состоянии и сверяется: вызовы NVN, которые увидели тела (все аргументы, порядок; стековые объекты движка = `NRST_LOCAL_*`), каждый байт `r+0x16f0…0x1870` и `r+0xb78`, отметки кадра, длина пакета. **3** — не существует: `=1` делает ровно те вызовы, что делал движок, устаревшего нечего показать |
| `DM_NR_STATE_AB` | `1` (только с `=1`): блоки по 64 пакета чередуются «натив / движок», оба замеряются (1 из 64) — A/B в одном прогоне без дрейфа DVFS |

Нужно: `DM_NR=1|2` (умолчание сборки). `DM_NB` / NB-13a не обязательны (тела одни и те же в любом режиме). Совместимо с NR-09R
(`DM_NR_DIRECT`), NR-23, NR-13 (`DM_NR_LEAN` — тела пишут обычные записи вместо тени, так же как при вызове движком), NR-28.

Строки (поток отчёта NR, раз в 10 с):
- старт: `[nr] DM_NR_STATE=1 (NR-09S): opcode 21 … runs as native code …`; первый пакет: `[nr] state: the engine's 19 NVN pointers of
  opcode 21 are the thunks of the bodies the native packet calls` (иначе красная строка и код 21 остаётся движку);
- `=1`: `[nr] state (DM_NR_STATE=1, NR-09S, N frames): opcode-21 packets P a frame, native Q with C NVN calls a frame made through the bodies
  (c a packet, S stack switches a frame; none through a thunk), … left to the engine a frame: …; calls a frame: BindProgram …, ColorStateSetBlendEnable …;
  ns a packet …` — **карта вызовов состояния по видам** (вход для S3);
- `=1` + `DM_NR_STATE_AB=1`, `=2`: `[nr] state, ns a packet (1 in 64 timed): native X (n), the engine's handler with its NVN calls through the
  thunks Y (m): Z us a frame saved at P packets a frame` — **прямой замер выигрыша**;
- `=2`: `[nr] state check (DM_NR_STATE=2 …): … compared C a frame (totals: N compared, renderer memory bad 0, NVN calls bad 0, packet length bad 0)`;
  красные: `【红】[nr] state check: …` (первые 16: вызов модели против вызова движка / смещение `r`).

## 6. План остального (S2 / S3) — чем код 21 станет настоящей заменой
| Шаг | Что | Выигрыш [м] | Цена |
|---|---|---|---|
| **S3. Нативная запись состояния в бэкенд** | Для взятого пакета 21 вместо вызовов тел — **одна запись `OP_X_NR_STATE`** {маска видов; снимки blob-ов DS / poly / blend по RT / colour / vattr / vstream (копируются один раз на хэндл движка + поколение, дальше ссылка по id в эпохе, как DEF/REF NB-13a, но **без хэша содержимого**: ключ = хэндл); программы VS/FS; VB-диапазоны; stencil; alpha; рендер}. Бэкенд (`xbg_nr_state.inc`) пишет её прямо в `State` теми же полями, что `execute()` NVN-записей, и бампает то же (dirty, группы NB-13b). Тень NB-13a для вида, который пишет запись, — «неизвестно» (её механизм уже есть, `nbs_unknown`); запись + поток в порядке — бэкенд исполняет по порядку, поэтому сырой вызов того же вида до / после остаётся верным без «сброса на запасном пути». Побочные эффекты тел, которые нужны: `nbt_program` (маски слотов тапа IR), `dm_nr_tap_bind` (только `DM_NR_KEY=2`), записи объектов движка `SetBlendTarget` / `SetBlendEnable` (гостевая память — делать нативно, как тело). | фронт: −(тела + `rec` + тень + упаковка/словарь ≈ 60–90 нс на вызов + 0.2–0.4 мкс на draw) ≈ **−0.4…0.8 мс**; транслятор: разбор и `execute()` 1 600 `OP_X_NB_STATE` (150 КБ / кадр) → одна запись на draw: **−0.2…0.5 мс**; слабые ядра ×2–3 | 8–12 агент-часов: формат + бэкенд-применитель + `=2` (применить старым и новым путём в две копии `State`, сравнить байты на каждом draw) + тест на `nb_state_test`-модели; 2 прогона (`=2` в Форте, потом A/B) |
| S2 (промежуточный, не нужен при S3) | исполнитель пишет готовые NVN-записи прямо в тень NB-13a (без `rec` / `nbs_rec` / `settle`) | −0.1…0.2 мс | 3 ч; дублирует тела — не делать, если идём в S3 |
| UBO (`0x926f90` / `0x925740`, 0.57–0.77 мкс на draw) | модель аллокатора кольца (5.9 КБ, спин-блокировка) — тот же метод: Unicorn-оракул на машинном коде | −0.3…0.6 мс | 10+ ч, высокий риск; после S3 |
| Другие опкоды состояния (6–11, 18, 19: ≈ 450 пакетов / кадр в Форте) | тот же метод, по карте вызовов строки `=1` | малый | по 1–2 ч на опкод |

## 7. Прогоны телефона (главный агент, по разрешению хозяина; бэкап `files/save`, keyguard снят, Форт Радость у ворот, ≥ 60 с от загрузки)
Файлы на телефон: только APK (паков не нужно). Общее: умолчания сборки (`DM_NR=1 …`) + `DM_NR_CPU=1`.
1. **R-09S-a, сверка:** `DM_NR_STATE=2`. Ждём: `[nr] DM_NR_STATE=2 (NR-09S): opcode 21 runs as the engine's machine code; the model runs first …`,
   `[nr] state: the engine's 19 NVN pointers of opcode 21 are the thunks …`; каждые 10 с **`[nr] state check (DM_NR_STATE=2 …): … renderer memory bad 0,
   NVN calls bad 0, packet length bad 0`**, ни одной `【红】[nr] state check`; `left to the engine` ≈ 0; строка `ns a packet` даёт цену пакета
   движка с его вызовами (Y). Палуба 60 с + Форт 60 с (бой, если есть сохранение).
2. **R-09S-b, A/B в одном прогоне:** `DM_NR_STATE=1 DM_NR_STATE_AB=1`. Ждём `[nr] state, ns a packet …: native X …, the engine's handler … Y …:
   Z us a frame saved` — **Z = выигрыш на потоке игры** (ожидание 50–170 мкс на Mi 14); картинка без изменений (половина пакетов идёт каждым путём).
3. **R-09S-c, включено:** `DM_NR_STATE=1`, ABBA × 2 по 60 с против `DM_NR_STATE=0`: `[cpuprof] threads` — `main` мс / кадр, `[nr] state … calls a frame: …`
   (карта для S3), `[nb] state` (те же числа записей, что в A: поток тот же), скриншоты те же.
Умолчание (`jni_android.c` DOS2-блок) — только при `bad 0` в (1) и Z > 0 в (2).

### 10.1 Что делает
- **`DM_NR_STATE=4` (S3).** Модель кода 21 (§2, доказана Unicorn-оракулом) даёт вызовы пакета (`nrst_op`). Они больше **не идут через тела NVN**:
  `nr3_build` (`dm/gfx/nr/nr_state3.h`) проходит их по порядку и собирает **одну запись `OP_X_NR_STATE`** — те байты, которые скопировали бы
  тела `bind_state` / `BindProgram` / `BindVertex*` / `SetStencil*` / `SetAlphaRef` в момент своего вызова. Сеттеры объектов (`BlendStateSetDefaults` /
  `SetBlendTarget`, `ColorStateSetDefaults` / `SetAlphaTest` / `SetBlendEnable`) исполняются **телами HLE на локальных копиях** объектов
  (`NR3_BLEND_DEF` … = `h_nvn…`), бинд читает копию, если пакет её трогал, иначе память объекта: байты ровно те. Копии потом пишутся обратно
  в объекты движка (`nr3_writeback` = что оставили бы сеттеры). Хэша содержимого нет нигде; словаря «хэндл → blob» тоже нет: три объекта
  записи blend **пишутся самим пакетом** (цель и `blend_en` следуют привязанным RT), т. е. хэндл не называет содержимое, а DS / raster / vfmt —
  4–80 Б, поиск id на двух потоках стоит столько же, сколько копия. Фильтр движка и так оставляет 2–3 изменения на пакет.
- **Что ещё делали тела, кроме записей, — делается нативно** (`dm/gfx/nvn/nvn_nr_state3.inc`): тап IR NB-07 `nbt_program` и тап NR-02
  `dm_nr_tap_bind` на каждый `BindProgram` в его порядке; счётчики заметок тапа (`NBN_STATE` / `NBN_VBUF`) теми же числами; `SetRenderEnable(Conditional)`
  — через свои тела после записи (их эффект — не запись состояния: флаги draw / `OP_X_RENDER_COND` / hazard NB-16).
- **Ленивая сторона NVN (запасной путь).** Тень NB-13a перед записью отдаёт то, что держит (`nbs_ext_before` = `nbs_flush` без атомика, когда
  нечего), после — виды, которые запись написала, становятся «неизвестны» (`nbs_ext_after` → `nbs_unknown`, как после сырой записи). Поэтому всё,
  что идёт мимо S3 — пакеты, которые модель не берёт (движок), другие опкоды (6–11, 18, 19, `SetRenderTargets` → `SetBlend`), сырые вызовы, —
  продолжает писать обычные записи / блоки NB-13a, а бэкенд исполняет поток **по порядку**: корректность не зависит от пропуска. Мутация «без
  `unknown`» ловится тестом (§10.3). Пакет, который запись не может представить (повтор той же части stencil / второй набор потоков, > 3 программ,
  слот VB ≥ 16, счётчик атрибутов вне 0–16 …), — через тела, как `=1` (в Форте 0 таких в тесте; счётчик в строке).
- **Бэкенд** (`dm/gfx/vulkan/engine/xbg_nr_state3.inc`, `case OP_X_NR_STATE` в `execute()`): запись — прямо в `State` (`NR3_DEFINE_APPLY_RAW`,
  без копии в промежуточную структуру), каждое поле как ставит его кейс `execute()` той записи, которую написало бы тело; программы —
  копией кейса `OP_BIND_PROGRAM` (шейдеры, `missing_program`, таблица программ NB-18b-4; структурный тест держит их текст равным); группы NB-13b,
  которые запись написала, помечаются к перечитыванию (как `nbpipe::mark` для записей биндов). Полоса NR-09 / `nbdraw` читает тот же `State`.
- **`DM_NR_STATE=5` (две копии).** На пакет: запись с флагом `CHECK` (бэкенд применяет её к **копии** сравниваемых полей) → вызовы через тела
  (как `=1`, они пишут настоящий `State` через NB-13a) → `CHECK_END` (бэкенд сравнивает: шейдеры, ds, stencil ×3, poly, blend[8], colour, attrib[16],
  stream[16], vb[16], alpha ref, `missing_program`). Красные строки `【红】[nr] state3 check: opcode-21 packet N: … the state's <поле> differs …`
  (первые 16), итоги каждые 10 с. Пары по `seq`; непарные считаются отдельно.
- **`DM_NR_STATE_AB=1` с `=4`:** блоки по 64 пакета чередуются S3 / S1 (вызовы через тела), обе цены в одной строке.
- `=4 / =5` при `DM_NB_RELOC=1|2` (NB-14 ключует только обычные записи состояния) → работает `=1`, красная строка. `DM_NB_ORDER` совместим
  (`OP_X_NR_STATE` для него «не чистая» запись — консервативно). `DM_NR_LEAN` совместим (без NB-13a хуки `NBS_EXT_*` пустые).

- Счётчики NB-тапа «другой командный буфер» (`NBN_OTHER_CB`) при `=4` считаются раз на пакет, а не на вызов (только статистика).
- `[nb] state` фронта при `=4` показывает намного меньше захваченных вызовов и больше `sub-states made unknown` — это признак работы, не ошибка.
- `DM_NB_RELOC=1|2` выключает S3 (`=1`); вернуть RELOC вместе с S3 — научить ключ NB-14 записи `OP_X_NR_STATE` (не делалось: RELOC снят с умолчаний в NR-15).
