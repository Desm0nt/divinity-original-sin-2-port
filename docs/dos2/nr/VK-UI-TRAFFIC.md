# VK-UI-TRAFFIC — трафик памяти UI (Iggy) на своём бэкенде Vulkan: слой UI одним проходом, кэш всего UI, счётчики (22.11.2026)

Ветка `dos2-vk5-ui` от `4b2fc5e` (дерево `wt-vk5-ui`). Пункт П7 плана `VK-MOBILE-GPU-PLAN.md` + доводка П2 + счётчики UI. Код проверен на хосте,
телефон не запускался. Пометки: **[лог]** — число из лога телефона, **[м]** — модель трафика бэкенда (загрузка + сохранение каждого
вложения по области прохода, без AFBC / UBWC), **[код]** — исходник.

## 0. Коротко

1. На модели Mali (прогон W07, Mi 14 Ultra, `DM_GFX_SIM_GPU=mali`, кадр 600) UI — это **464 МБ из 715 МБ** трафика кадра: слой UI
   `tex#002d` — 15 проходов, 414 МБ, 209 draw; цели фильтров `tex#0000` — 30 проходов, 50 МБ, 16 draw [лог W07 `passlog 600`]. Слой рвётся
   на каждом фильтре: «уйти в цель фильтра — вернуться» = сохранить и снова загрузить 10–20 МБ слоя.
2. Сделано (все за переключателями, значения 0 / 1 / 2 сверка / 3 яд):
   - **`DM_VK_NATIVE_UILAYER` — слой одним проходом.** Все вызовы GDraw придерживаются (копируются) до момента, когда движку нужен их
     результат; потом исполняются так: сначала все блоки фильтров (цели, вытолкнутые на стек GDraw), затем все draw слоя подряд — один
     проход слоя вместо прохода на каждый фильтр. Точно по построению (правила ниже, нарушение = исполнение в исходном порядке со счётчиком).
   - **`DM_VK_NATIVE_UICACHE` — кэш всего UI.** Если первый придержанный «прогон» UI в кадре побайтно равен прогону прошлого кадра (ключ:
     все вызовы, константы, вершины, версии текстур, значение очистки слоя движком) и ничто из написанного им (слой, глубина UI, цели
     фильтров) не трогали с тех пор — прогон **не исполняется вовсе**: слой остаётся прошлым, очистка слоя движком снимается. Ни прохода,
     ни draw, ни работы потока записи. Точно по построению.
   - **Счётчики:** одна строка `ui traffic (mgpu P7)` раз в 10 с: проходы UI, МБ загрузки / сохранения / копий UI на кадр (доля UI в
     журнале проходов), мс процессора UI в потоке записи, всё о придержке и кэше с причинами отказов.
   - **П2 (кэш фильтров) шире:** атлас 2560x1024, принимаются полосы до 2560x256 (в W07 5 эпох на кадр отказывали как «other»: области
     1343x55 и 2400x157).
3. Важная оговорка про кэш всего UI: он срабатывает только когда UI кадра — **один** прогон, то есть внутри UI нет draw движка в цели GDraw
   («custom draw» Iggy: 4 на кадр в Форт Джой [лог W07 `custom draws`], ≈ 11 draw движка внутри проходов UI [лог W07 `passlog`: draw в
   проходах UI 225 против 214 draw UI]). Каждый такой draw = граница прогона, и следующий кадр получает отказ «written since». Что это за
   draw (портреты, миникарта) и пишут ли они прямо в слой — покажет первый прогон телефона (строка `ui traffic`: `flushed by: an engine draw
   on GDraw's binding`, `refused ... written since`). Следующий шаг для таких кадров — раздел 5.
4. Ожидание [м], кадр как W07 (Mali): слой 15 проходов → 1 + число границ прогона (≈ 5 при 4 custom draw): 414 → ≈ 150–200 МБ; цели
   фильтров ≈ 50 МБ (без изменений, копии П2); UI 464 → ≈ 200–250 МБ, кадр 715 → ≈ 450–500 МБ. В кадрах с одним прогоном (меню без
   custom draw, если такие есть) — UI ≈ 0 МБ, 0 проходов, процессор потока записи минус всё время UI (строка `ui traffic`, поле «UI CPU»).

## 1. Как устроено (код: `dm/gfx/vkn/vkn_ui.c`, блок «mgpu P7»)

### 1.1 Придержка

Точки входа `vkn_ui_*` (их зовут записи потока записи, `vkn_rt.c`) при включённом UILAYER или UICACHE не исполняют вызов, а кладут его
копию в буфер (константы, вершины, индексы копируются; блок буфера вершин — по значению, его байты живут до кадра +3). Буфер — «прогон».
Прогон начинается с первого вызова UI и кончается («сброс»), когда движку нужно то, что прогон нарисовал бы. Это решает новый крючок
`vkn_pass_before_ev` (`vkn_pass.c`): он вызывается на входе **каждой** функции `vkn_pass_*`, до того как она что-то прочитала или
изменила, с видом события и текстурой:

| Событие движка, пока прогон придержан | Решение |
|---|---|
| `TARGETS` (движок поставил свои цели) | никогда не сброс; отмечается «набор теперь движка» |
| `READY` / `DEPTH` (draw движка / чтение привязанной глубины) | сброс, если привязан набор GDraw (последнее связывание было в прогоне: это custom draw), или текущий набор содержит текстуру, которую прогон пишет или читает |
| `SAMPLE` | сброс, если прогон эту текстуру пишет (слой — причина «layer used»: Combine) |
| `CLEAR`, `STORAGE`, `LAYOUT` | сброс, если прогон текстуру пишет или читает (загрузка глифов в атлас, который читает прогон, — сюда) |
| `COPY` | сброс, если приёмник пишется или читается прогоном, или источник пишется |
| `END` (конец прохода куском, закрытие записи) | всегда сброс |

Плюс функция цепочки приёмов `ui-layer` (порядок 0, перед всеми): draw движка, пока привязан набор GDraw, сбрасывает прогон до того, как
другие куски посмотрят на набор целей. После сброса набор целей движка возвращается, если движок ставил свой после последнего
связывания прогона; иначе остаётся набор GDraw (как у NVN).

Почему это точно: всё, что движок делает между вызовами UI и не конфликтует, не читает и не пишет ничего из того, что пишет или читает
прогон, — значит, их порядок между собой не наблюдаем. Всё конфликтующее идёт после исполненного прогона, как в исходном порядке.

Прогон в типичном кадре Форт Джой начинается с первого `RenderingBegin` и кончается на чтении слоя в CombineUI (все 3D-проходы кадра идут,
пока UI придержан: они не трогают цели UI) — если внутри UI нет custom draw.

### 1.2 Слой одним проходом (UILAYER = 1)

Запись прогона относится к группе 0, если текущая цель — слой (основание стека GDraw; хост называет его на каждом `RenderingBegin`:
`vkn_ui_layer`, `hle_dos2_vkn_ui.c`), иначе к группе 1 (вытолкнутая цель фильтра). Исполнение: сначала все записи группы 1 по порядку
(блоки фильтров: очистка области, draw, шаги размытия; П1 и П2 работают как раньше), затем все текстуры, которые читает слой, переводятся
в чтение (иначе смена раскладки внутри прохода слоя закрыла бы его), затем все записи группы 0 подряд — **один проход слоя**. Состояние
(цели, вьюпорт, ножницы) ставится лениво: каждая исполняемая запись видит то состояние, которое видела в прогоне. Ограждения
(`RenderingEnd`, начало custom draw) упорядочивают только работу движка после них, а она идёт после сброса: выбрасываются, одно
исполняется в конце прогона. Эпоха слоя не берёт решения об области прохода (`g_up_noarea`): проход один.

Перестановка точна, когда (проверяется при придержке; иначе прогон исполняется в своём порядке, счётчик причины):
- в группе 1 нет работы с глубиной-трафаретом (`pushed DS`): глубина UI общая для слоя и фильтров;
- draw группы 1 не читает слой или глубину (`pushed read of the layer`);
- вытолкнутая цель не пишется после того, как draw слоя её уже прочитал (`target reuse`: GDraw берёт свободные ручки, внутри кадра
  повтор не ожидается, но проверяется);
- прочитанных слоем текстур не больше 48 (`many reads`).

Вытолкнутую цель читают только последующие draw слоя (сведение фильтра) и последующие шаги группы 1 (пинг-понг размытия) — оба порядка
сохранены.

### 1.3 Кэш всего UI (UICACHE = 1)

Ключ первого прогона кадра с содержимым: по каждой записи вид и значения; по draw — программы, состояния, байты констант, вершин,
индексов; по каждому блоку текстуры — версия содержимого: цель этого же прогона — накопленный хэш того, что прогон в неё нарисовал;
иначе `vkn_tex.shc_up` (номер загрузки) или ключ П2; цель, написанная GPU вне прогона, версии не имеет (отказ `a texture without a
version`). Цели в ключе — по порядку появления (указатели ручек GDraw не важны). Начальное состояние входит в ключ, только если запись
его читает. Цель фильтра или глубина, в которую draw рисует до очистки этим же прогоном, — отказ `drawn before cleared`. Последним в
ключ идёт значение запомненной очистки слоя движком (`vkn_pass_clear_take`; её нет — отказ `no layer clear`).

Попадание: ключ и значение очистки равны прошлому кадру, и с момента сброса прошлого прогона никто (в том числе наши же последующие
прогоны того кадра) не писал ни одну текстуру, которую тот прогон писал (`vkn_pass_on_write`: слой, глубина UI, цели фильтров). Тогда их
содержимое — ровно то, что нарисует этот прогон. Действие: запомненная очистка слоя снимается, применяются конечные цели / вьюпорт /
ножницы прогона, больше ничего.

### 1.4 Сверка и яд

- `UILAYER=2`: перестановка на чётных записях, исходный порядок на нечётных; если ключ прогона равен прошлому, полоса слоя 64 строки
  читается до исполнения (там результат прошлого кадра другим порядком) и после, сравнение через 4 кадра. `differ` должен быть 0.
- `UICACHE=2`: каждое «сработало бы» исполняется, та же полоса до / после. `UICACHE=1` делает то же на каждом 256-м попадании; отличие —
  красная строка и кэш выключен до конца сеанса. Полоса движется по экрану (за ~17 сверок весь слой).
- `UILAYER=3`: после переставленного прогона вытолкнутые цели заливаются пурпуром (их содержимое отработало: чтение не по порядку видно).
- `UICACHE=3`: как 1, но одно попадание из 64 заливает слой пурпуром вместо прошлого UI (мигание UI = путь кэша читается).

## 3. Счётчики (одна строка для сравнения до / после)

Строка `[vkn] ui traffic (mgpu P7): a presented frame: UI passes N (draws D), model X MB load + Y MB store, copies C (Z MB); UI CPU on
the recording thread T ms (K calls) | DM_VK_NATIVE_UILAYER=... | DM_VK_NATIVE_UICACHE=...` — раз в 10 с, рядом с `ui pass` и
`ui region / filter cache`. Печатается и при выключенных П7 (база для сравнения).

- «UI passes / MB»: проходы журнала (`vkn_pass.c` П0), у которых есть цветовое вложение-цель UI (`vkn_tex.ui_tgt`: цели GDraw и атлас П2),
  их байты модели по области прохода; «copies» — копии областей П2 из / в цели UI (чтение + запись).
- «UI CPU»: время точек входа `vkn_ui_*` и сбросов прогонов в потоке записи (вложенность учтена), мс на кадр.
- Придержка: прогоны, вызовы и draw, исполнено переставленно / по порядку, причины «не переставлено», сбросы по причинам.
- Кэш: кандидаты, «сработало бы», попадания (draw и вызовов не исполнено), отказы по причинам, сверки и отличия, яд.

Что смотреть: `UI passes` и `MB` до / после; `UI CPU` до / после; при отказах кэша — главная причина (`written since` = внутри UI
были draw движка или наши следующие прогоны; `a texture without a version` = UI читает цель, нарисованную движком; `another key` = UI
правда меняется каждый кадр).

## 5. Что не сделано и следующий шаг

1. **Грязные прямоугольники** (перерисовать только изменившуюся часть слоя) **не сделаны.** Причина: для области изменившегося draw нужны
   границы его вершин на экране, а ножницы GDraw почти всегда — весь экран; программа позиции вершинного шейдера (`vkn_shlib_vs_pos`,
   NR-10b) строится только при `DM_VK_NATIVE_LOAD`, и неизвестно, есть ли она у трёх вершинных программ GDraw. План: (а) прогон M1
   покажет, сколько прогонов в кадре и почему кэш отказывает; (б) если главная причина — custom draw движка, их прямоугольник известен
   (вьюпорт / ножницы draw движка): слой сохраняется, прямоугольник очищается значением очистки слоя, все прогоны исполняются с ножницами
   и областью прохода, обрезанными до него, custom draw — как есть; ошибка предсказания прямоугольника = полная перерисовка до draw движка
   (буфер прогона ещё цел); (в) для изменившегося текста — границы по программе позиции, если она строится для GDraw (включить её
   постройку при UICACHE в `vkn_shlib.cpp`, `g.pos_on`).
2. «Слой одним проходом» на кадре с custom draw остаётся «1 + число границ»: draw движка нельзя придержать (у него нет копии входов, как
   у кэша теней). Если границ много — второй шаг: держать копии draw движка в цели GDraw так, как `vkn_shc.c` держит draw теней.
