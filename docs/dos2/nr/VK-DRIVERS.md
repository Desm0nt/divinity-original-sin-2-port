# VK-NATIVE: бэкенд и драйверы — что он требует, что где есть, какие поправки стоят (21.11.2026)

Ветка `dos2-vk5-drv2` (от `fbada69`, дерево `dos2-port/wt-vk5-drv`). Режим `DM_VK_NATIVE=1` — свой бэкенд Vulkan (`dm/gfx/vkn`) вместо
NVN. Задача хозяина: «работать плотно с кастомными драйверами (PanVK, RADV-Xclipse, Turnip на старых Adreno, стоковые Qualcomm / Mali /
PowerVR) и быть уверенным, что всё будет работать». Ни одной строки на настоящем не-Adreno устройстве не проверено — всё ниже
«не подтверждено устройством», проверено хост-тестами и моделью `DM_GFX_SIM_GPU`.

Источники фактов: KB `docs/port-kb` (gpu-xclipse XCL-01…08, gpu-mali MALI-09/10, gpu-powervr PVR-02…11, gpu-adreno-stock-vs-turnip
ADR-03…08, drivers-adrenotools DRV-06/08, mobile-gpu-field-notes раздел 4 — ANGLE, Skia, Dolphin, PPSSPP, yuzu / Eden, Strato,
GameNative, Mesa driconf), профили `DM_GFX_SIM_GPU` в `xbg_vendor_policy.h` (собраны по отчётам gpuinfo и логам игроков).
Знак `?` — нет данных (нет устройства, нет отчёта); такие места бэкенд проверяет по свойствам устройства, а не по имени.

## 2. Что бэкенд требует от драйвера (инвентарь по коду)

### 3.1 Кастомные драйверы — что важно знать бэкенду

- **Turnip на старых Adreno (A6xx):** бэкенд не опирается ни на что, чего нет у Turnip A6xx; приёмы для Adreno 7xx (LRZ `GBUF_LE`,
  quad / warp32) в A6xx решаются политикой библиотеки шейдеров (`DM_GFX_QUAD_DERIVATIVES` / `DM_GFX_WARP32` только 740–799 / 8xx, ADR-04).
  Известное по KB: A650 + Turnip 25.0+ падает через секунды (24.3 работает) — это выбор пакета в ⚙, не правка бэкенда; при падении
  инициализации — откат на системный (DRV-07), при падении в игре — теперь лестница (поток `tu_*` и библиотека `vulkan.*` считаются).
- **PanVK (JimVulkan поверх kbase):** нет GS, clip-distance, `fillModeNonSolid`, `depthBounds`, fp64 — DOS2 без GS, fill уходит в
  заливку, остальное — в проверках библиотеки шейдеров (`sl_gap`). Половинное смещение глубины — ×2 стоит. AFBC окна — `MESA_GRALLOC_LINEAR`
  (DRV-08, общий `vk_driver.c`).
- **RADV-Xclipse:** ×2 смещения стоит (driverID 3); `minUniformBufferOffsetAlignment` 4 берётся из пределов; BC4–7 драйвер эмулирует сам.
  Мазки на геометрии D16 (XCL-05/08) причины не имеют — для DOS2 это риск, на стоковом Xclipse картинка у D16 чистая.
- **Стоковый Qualcomm:** `CLEAR_REBIND` стоит. Обратный диапазон глубины сломан — DOS2 рисует прямую глубину (`LESS` / `LEQUAL`), не
  относится. Очистка D32F не действует (Dolphin) — бэкенд ставит D32F только там, где нет D24, то есть не на Qualcomm; не включать
  `DM_VK_NATIVE_D24=2` на стоковом Adreno.

### 3.2 Смещение глубины на подмене D32F (открытый пункт XCL-02)

Для float-глубины единица смещения r = 2^(e − 23), где e — порядок наибольшего z примитива; для z ∈ [0.5, 1) это 2^−24, ровно как у D24.
DOS2 рисует прямую глубину [0, 1] с перспективой: z ≥ 0.5 у всего, что дальше двух ближних плоскостей. Значит, множитель 1 даёт то же
смещение, что D24, почти на всей сцене; ослабление (в 2, 4 … раза) только у поверхностей вплотную к камере. Тени (атлас D16, NVN
DEPTH16) подменой не затронуты — подменяются только D24. Поэтому `DM_VK_NATIVE_D24_BIAS=1` по умолчанию; переключатель — для проверки
на устройстве (умножает постоянную часть смещения у проходов с глубиной D32F, когда подмена была). Точный путь —
`VK_EXT_depth_bias_control` (`depthBiasRepresentation = FLOAT`, постоянная × 2^−24) — не сделан: на Android его почти нет.

## 5. Что не сделано (по важности)

1. **Сэмплер NEAREST для форматов без линейной фильтрации** (Mali r32–r54: R16G16 / RGBA16 UNORM; PowerVR: D24 / D32 / R32F). Старый путь
   делал это при создании сэмплера под текстуру; у бэкенда сэмплер выбирается по id в пути привязки (`vkn_sampler_by_id`, `vkn_tex.c`
   ~1102) — там сейчас меняет замки ветка `dos2-vk5-rt`. Нужен «двойник NEAREST» по образцу двойника сравнения (`vkn_sampler_cmp_by_id`)
   и решение по формату последней текстуры (`t_hk_last`). Делать после слияния `dos2-vk5-rt`. Без этого на таком Mali / PowerVR выборка
   линейным фильтром — неопределённое поведение (обычно чёрное или мусор).
2. **Pipeguard между запусками** (стоковый Adreno ADR-03, PowerVR PVR-05/07): падение компилятора на одном конвейере теперь хотя бы
   ведёт лестницу (шаг 1 → 2 → старый путь), но шаги не обходят сам конвейер. Метка «сборка идёт» перед `vkCreateGraphicsPipelines` +
   список пропуска при следующем старте — 1–2 агент-часа.
3. **Замок компилятора на команды** (PowerVR PVR-05/07: драйвер компилирует внутри `vkCmdEndRenderPass` / копий / очисток) — у D16 это
   `COMPILE_LOCK`; у бэкенда поток записи пишет команды вне замка библиотеки. Только PowerVR.
4. **Живой откат сборки** (`live_pipe`): при сбое сборки включать `PIPE_SERIAL` в процессе.
5. `robustBufferAccess` включён презентером (все фичи) — на Mali / PowerVR это цена в каждом доступе; на Xclipse / AMD границы считаются
   до кратного шага вершины (ANGLE `padBuffersToMaxVertexAttribStride`) — у бэкенда буферы вершин внутри больших арен, край арены —
   единственное место риска. Общее со старым путём; решать вместе.
6. Пределы дескрипторов только пишутся в лог (разбить раскладку нельзя); на PowerVR / старом Mali смотреть красную строку `needs ... against`.
7. Maleoon: данных нет; бэкенд решает всё по свойствам устройства, семейство — «другое» (умолчания Adreno-подобные, кроме маски цвета).
   Тайловую политику для Maleoon и стокового Adreno (GMEM) делает ветка `dos2-vk5-gpu`.

8. **Падение в коде самого бэкенда на потоке движка не считается** (поток игры — не «графический», адрес — в `libdm.so`, не в драйвере):
   считаются потоки `vkn-*` (поток записи), потоки и библиотеки драйвера, потерянное устройство и зависший забор. С `DM_VK_NATIVE_RT=0`
   (шаг 1 и выше) запись идёт на потоке движка, и ошибка бэкенда там лестницу не двигает. Тест `DM_GFX_FAKE_GPU_CRASH=<с>:rec` считается
   на любом потоке (метка теста). Решение — пометка «внутри бэкенда» на входах `hle_dos2_vkn_*` (поток-локальный флаг), ≈ 1 агент-час.

## 6. Лестница безопасного режима при `=1` (теперь на всех семействах)

- Решение — `xbg_safe_mode_pre` в `nativeStart` сразу после умолчания `DM_VK_NATIVE=1`: читается `<files>/gfx-safe-mode`, `DM_SAFE_MODE`,
  ставятся строки бэкенда (одинаковые для всех семейств). Шаг 3 ставит `DM_VK_NATIVE=0` до того, как его прочтут таблица умолчаний
  приложения, `dm_dos2_vkn_pre` на потоке хоста и инициализация транслятора — старый путь получает свои обычные умолчания NB / NR.
  Старт Vulkan (`xbg_safe_mode_boot`, семейство известно) добавляет строки семейства: PowerVR (динамические блоки, маска цвета) и
  строки старого пути (только Mali / PowerVR — как раньше, по правилу хозяина).
- На Adreno / Xclipse / Maleoon / прочих: шаг 1 — приёмы этапа 5, поток записи, политика проходов выкл. (бэкенд как после этапа 4);
  шаг 2 — + без прогрева, BC на CPU, зеркала целиком, сборки по одной; шаг 3 — старый путь со своими умолчаниями (рендерер v0.2.1).
- Шаг 3 по счёту — только когда упал сам бэкенд на шаге 2 (в файле счётчика `native=1` и `step=2`), или старый путь уже работал
  (`step=3`). Иначе счёт 3 держится на шаге 2. Файл сборки до этой ветки (без `native=`) на Mali / PowerVR — прежнее правило.
  `DM_SAFE_MODE=3` и «Вкл» в ⚙ решают сами.
- Строка ⚙ «Безопасный режим» видна на Adreno при `=1`: `SafeMode.eligible()` берёт ответ натива (`nativeSafeModeStatus`, поле 0 = 1).
  Заголовок строки в общих текстах (`frontend-common`, `GearText.java` `gear_safe_mode`) всё ещё говорит «(Mali / PowerVR)» — поправить в
  `frontend-common/i18n` (сессия UI), здесь не трогалось.
- Строки лога: `boot: safe mode (early, mode 1, every family): step N ...` (boot.log), `NVN safe mode: step N of 3 on <семейство> (...; mode 1,
  the native backend draws ...)`, при удержании: `The counted step 3 is held at 2 ...`; при счёте падения бэкенда:
  `frame: VK_ERROR_DEVICE_LOST in vkQueueSubmit in the native backend ...: counted for the safe-mode ladder`.
