# NR-31 `DM_NR_SEED` — переносимый сид прогрева пайплайнов (N3 финального аудита)

Ветка `dos2-nr31` (worktree `wt-nr31`, база `dos2-nr-all` 393fcd7). Аудит `dos2-nraudit2:docs/dos2/nr/AUDIT-FINAL.md` §3 N3, основа — NR-07
(`DM_NR_PIPE`, `tools/dos2_nr_pso.py`) и NR-02 (ключи пака). На телефоне не исполнялось (телефона не было, списка DOS2 с Mi 14 на ПК нет);
всё ниже — тесты на ПК, **реальные списки TL2 с того же Mi 14** (тот же движок и формат записи), сборка `libdm.so` и APK.

## 0. Что хранит `vk-pipeline-list.bin` (ответ на первый вопрос N3)
Запись `warm::record` = ключи пака стадий (16 hex `xbg_shader_program_key`, варианты `#at<func>_<bits>` альфа-теста и `#vi<code>[c<conv>]`
retype / конверсии вершин) + **слова `XbgPipelineKey`** — полностью сериализованный CreateInfo **хоста этого устройства**: определение
раскладки (`descriptors()`: binding, тип, число, стадия), определение прохода (`create_pass()`: форматы, samples, ссылки, две зависимости),
сам CreateInfo (модули = `warm::fnv(ключ)`, вершинный ввод с VkFormat, IA, raster, MS, DS, blend, dynamic). Не состояние NVN — уже «скомпилированное»
политикой устройства. Draw берёт тёплый пайплайн только при **точном** совпадении этих байт (`warm::take`).

От устройства зависят (проверено по коду `draw()` / `create_pass()` / `dyn_mode_for` / `format()` / `get_image`, у каждого места — сторож в
`source_structure_test.py`):

| Поле | Политика | На Mi 14 | На Mali / PowerVR / Xclipse |
|---|---|---|---|
| `pass.dep[0/1].dstStageMask` | `DM_GFX_TILE_BARRIER` (`pass_deps`) | ALL_GRAPHICS / ALL_COMMANDS | фрагментные стадии (тайлеры) |
| формат глубины | `d24s8_as_d32s8`, `x8d24_as_d32`, `depth16_as_d24` | родные | D32 / D32S8 (Xclipse), X8_D24 вместо D16 (без линейного D16) |
| тип UBO в раскладке | `dyn_mode_for`: `DM_GFX_UBO_DYNAMIC`, `maxDescriptorSetUniformBuffersDynamic` 16 / 8 | все dynamic при ≤ 16 | ≤ 8 (иначе только пер-draw), PowerVR — ни одного |
| формат атрибута + тег VS | `vertex_format_fallback` (+`#vi…c…`), `DM_GFX_VTX_RETYPE` (`#vi…`) | всё читается, retype 0 | RGB / scaled → RGBA / int, retype 1 вне Adreno |
| `colorWriteMask` | `DM_GFX_NOOUT_MASK` | 0 | 1 вне Adreno: FS без выходов → 0 |
| polygon / depthClamp / biasClamp / depthBounds / logicOp | фичи устройства | все есть | Mali / PowerVR — нет части |
| `depthBiasConstantFactor` | ×256 при D16→X8_D24, ×2 `DM_GFX_DEPTH_BIAS_X2` | ×1 | ×256 / ×2 (PanVK, RADV) |
| тег FS `#at` | `DM_GFX_ALPHA_TEST` | 1 (DOS2) | 1 |

Отсюда: список Mi 14 байт в байт годится только для Adreno с той же политикой; NR-07 §4 это и предсказывал («на Mali / PowerVR часть
записей не совпадёт»). Реально (TL2, тот же Mi 14 с `DM_GFX_SIM_GPU=mali`): из 895 записей с теми же шейдерами **0** совпадают байт в байт.

## 2. Переключатель `DM_NR_SEED` (читается один раз в `launch`; умолчание `xbg_nr_seed_default()` = **1**, приложение ничего не ставит)
- **0** — ничего: файл не читается, крючки — загрузка + непринятый переход.
- **1** — один раз на id сида (маркер `<список>.seed`): каждая запись переносится на это устройство, дедуп со списком, строится на фоновых
  потоках (первый запуск = пустой список: столько же, сколько у прогрева, `min(3, ядра/3)`; иначе 1; ждут, пока draw сам в драйвере — NR-07),
  построенные дописываются в список устройства (`warm::flush`), маркер — после записи. Draw берёт их как записи списка. Отказы — счётчики +
  первые 2 строки на причину. Без файла сида — строка `no seed … nothing to do` и всё.
- **2** — сверка: каждый запуск перенос всех записей, **ничего не строит и не пишет**; каждая сборка в кадре ищется в переносе («сид её имел бы»),
  а при записи сида с теми же шейдерами, но другими байтами — красная строка с первым отличающимся полем (ошибка модели или другое состояние draw).
- Строки: `[nr] DM_NR_SEED=n (NR-31: …): seed <id>, N records, from a device with <политика>; this device: <политика>; list M records; T thread(s)`;
  `[nr] seed (done | in-frame builds | shutdown, …): N records: expanded E, refused <причины>; D already in the list, built B, failed F, taken by draws K;
  in-frame builds since launch C: the seed had P of them, a different record for the same shaders X, shaders the seed has no record of Y`;
  `【红】[nr] seed check: an in-frame build (<ключи>) has a seed record for the same shaders that differs at word W (<поле>: draw …, seed …)`;
  `[nr] seed <id> is in this device's list now`.
- Почему умолчание 1, а не 0 (бриф: «0 до доказательства»; задача: «по умолчанию — только если доказано безопасно»): (1) картинка не может
  измениться — draw берёт пайплайн только при точном совпадении ключа; (2) неизвестное / необратимое — отказ, не сборка; (3) каждый CreateInfo
  проверен против форматов и лимитов устройства; сборки прикрыты теми же pipeguard / gpguard, что прогрев; (4) без файла сида — ничего не
  происходит, а файла в этой ветке нет. Сид в APK появится только когда главная сессия соберёт его из списка телефона и прогон `=2` / `=1` (§9) даст 0 красных.
  Если хозяин хочет строго «0 до телефона» — одна строка `xbg_nr_seed_default(){return 0;}`.

## 3. Mali / PowerVR / Xclipse / слабые CPU
- Главный выигрыш — первый запуск на новом устройстве: без сида список пуст, каждый пайплайн строится **в кадре** при первом входе в
  область (Mali-G76: 50 мс без кэша, 24 мс с кэшем — FN-05; G72 3900 PSO за 160 с; PowerVR компилирует по одному, `DM_GFX_PIPE_SERIAL`).
  С сидом Mi 14 (≈ 1200 записей после палубы; больше после длинного прогона) эти сборки идут в меню на 1–3 фоновых потоках: 1200 × 25–50 мс /
  3 ≈ 10–20 с стены на Mali [м], последовательный PowerVR ≈ 30–60 с [м] — в меню вместо геймплея. Mi 14 / Adreno — ≈ 0 (свой список уже есть).
- Второй и следующие запуски: записи сида уже в списке устройства (маркер) — работает обычный прогрев / NR-07.
- Новый APK с другим сидом: новый id → перенос ещё раз, дубли отсеиваются, строится только новое (1 поток).
- Память: готовые пайплайны держатся в `ready` до взятия (как у списка; у Mali / PowerVR десятки КБ на пайплайн → 1200 ≈ десятки МБ). С NR-07
  `=3` (ленивый) записи сида всё равно строятся все — сид про первый запуск; на 6 ГБ телефонах это вход для N1 (`DM_NR_MEM`).
- Слабый CPU: перенос дешёвый (разбор + заголовки бандлов, для Mali — ещё финальные слова VS / FS для классов входов и выходов FS — те же,
  что прогрев всё равно строит); сборки — на потоках с `setpriority 5`, как прогрев.

## 4. Юридически: что лежит в сиде (`dos2_pipe_seed.py audit`)
Только (a) ключи пака — 16 hex 64-битного хэша control+code шейдера игры (идентичность, из неё ничего не восстановить; тот же ключ — имя
бандла, который игрок сам строит из своей копии игры), + теги `#at<func>_<8 hex>` (функция и порог альфа-теста); (b) id модулей = FNV ключей;
(c) числа фиксированного конвейера Vulkan (форматы, enum'ы blend / depth / stencil / topology, страйды, смещения, маски, константы blend);
(d) заголовок: магия, версия, число записей, id, 21 число политики источника. **Ни кода шейдеров, ни SPIR-V, ни байтов файлов игры** — каждое
слово разобрано как поле известного слота CreateInfo, иначе запись отвергается (`nsd_parse` / `nsd_shape` в рантайме, тот же разбор в `audit`).
Пример (`audit` на реальном списке TL2, 950 записей, 775 552 Б): состояние 611 164 Б, длины / счётчики 79 244, ключи 30 400, форматы 20 428,
рамка записей 19 000, id модулей 15 200, заголовок 116 — «every byte accounted for: True». Сид — данные порта (как список прогрева), не игры.

## 5. `.pso` iPad: можно ли сид без списка телефона? — **Нет**
- Каталог NR-07 (`dos2_nr_pso.py`, только **имена** `.pso` из индекса `ShaderCache.pak`): 743 пары (VS, FS), 2615 пайплайнов iPad;
  `dos2_pipe_seed.py pso` добавил: **743 различных VS на 743 пары** (у каждого материала своя пара), виды FOR 328 / DEP 325 / DEF 90.
- Запись прогрева = ключи **плюс весь CreateInfo** (blend, depth / stencil, raster, форматы RT и проход, вершинный формат / страйды / смещения
  потоков). Имя `.pso` = материал + хэш состояния iPad: ни одного из этих полей. Шаблон «та же VS» невозможен (VS не делятся); шаблон «тот же
  вид + те же локации входов VS» — догадка о blend / RT / форматах вершин (а ошибка = лишняя сборка); без списка телефона шаблонов нет вовсе.
  Содержимое `.pso` (Metal) не читалось и не годится: состояние Metal ≠ состояние NVN хоста, и это были бы данные игры.
- Что каталог даёт: потолок покрытия (`dos2_nr_pso.py --list`) и, со списком, число непокрытых пар, для которых был бы шаблон
  (`dos2_pipe_seed.py pso --list`). Синтез по шаблонам **не делал**: точность неизвестна до телефона, выигрыш только на областях, которых нет
  в списке. Правильный путь — длинный прогон Mi 14 по нескольким областям (бой, город), несколько списков: `build --list A B C` дедупит.

## 8. Риски и чего нет
- **Нет сида**: список DOS2 с телефона не забран; без него `DM_NR_SEED=1` — пустая операция. Синтез по `.pso` невозможен (§5).
- Модель повторяет код хоста (≈ 16 мест `draw()` + `create_pass` + `dyn_mode_for` + fallback вершин): изменение любого места без правки
  `nr_seed.c` ломает `source_structure_test.py` (сторожа), а на телефоне — только лишние сборки (точный ключ), что видно в `=2`.
- Не моделируется → отказ записи / всего сида: NR-08 `DM_NR_DESC=1` split и NR-08b `DM_NR_UBODYN` (оба по умолчанию 0). NR-04 `DM_NR_SH`
  (замена FS для 7 движковых шейдеров) — не моделируется: эти записи просто не совпадут (лишние сборки, видно в `=2`). `uiarea` (NB-18b-6) с
  D16-как-X8_D24: масштаб bias берётся по вложению прохода, у отвязанной глубины — промах (только устройства без линейного D16).
- Источник без фичи (Mali-список → Adreno): поля depthBounds / polygon / clamp / logicOp источник не знает — best effort (лишние сборки),
  поэтому сид — со списка Mi 14 (все фичи; проверено `policy --log g1all.dm.log`).
- `DM_NR_PIPE` (NR-07) не видит записи сида (индекс строится до них): у `=1` draw, которому нужна запись сида в работе, соберёт свою копию;
  `=3` (ленивый) записи сида строит все.
- Поля, которые лог источника не называет (форматы, не выведенные в `NVN caps formats`), считаются читаемыми; для Turnip-источника не важно.
- Записи сида, которые устройство не строит никогда (неверный перенос), лежат в его списке и строятся каждой загрузкой (как у старого
  `vk-pipeline-list.seed`); `=2` их считает — чистки нет.

## 9. Прогоны на телефоне (бэкап `files/save`, keyguard, force-stop после)
1. **Сид** (после следующего прогона Mi 14, лучше длинного: палуба → город → бой): забрать `Download/DivinityOriginalSin2Mobile/dm/vk-pipeline-list.bin`
   и `dm.log`; `python tools/dos2_pipe_seed.py build --list vk-pipeline-list.bin --log <dm.log> --bundles ../work/shaders-vk --out dm/android/dos2/dos2-pipe-seed.bin`
   → ждём `left out: nothing` (или только `duplicate`), `layouts: … limit is ..16`; `audit` → `every byte accounted for: True`.
2. **Модель на Mi 14, тождество** (сид в `dm/shaders/` push'ем, APK этой ветки): `DM_NR_SEED=2`. Ждём `[nr] DM_NR_SEED=2 … this device: tile 0 … features 0x1f`,
   `[nr] seed (done …): expanded N, refused none`, к концу сцены `the seed had P` ≈ все сборки в кадре областей из списка, **`a different record for the same shaders 0`**, 0 строк `【红】[nr] seed check`.
3. **Mali на Mi 14 (политика другая — настоящий перенос)**: `DM_GFX_SIM_GPU=mali,ubdyn8 DM_NR_SEED=2` (список не трогать): та же сцена; ждём
   `this device: tile 1 … dynamic UBO 1 (limit 8), NOOUT 1 … features 0x16`, `refused none` (или только `noout`/`vertex-ambiguous` = 0 для Turnip-сида),
   `a different record for the same shaders 0` → перенос верен для политики Mali.
4. **Первый запуск** (E4 из TESTPLAN, медленный компилятор): `DM_GFX_SIM_GPU=mali,ubdyn8 DM_GFX_PIPE_CACHE_LOAD=0 DM_NR_PIPE_THREADS=1`, список и
   маркер отодвинуть (`mv vk-pipeline-list.bin{,.bak}`; вернуть после!), A: `DM_NR_SEED=0`, B: `DM_NR_SEED=1`, ABBA. Решают: у входа в игру
   `NVN PERF … created / create_ms / create_max_ms` (B ≪ A), `[nr] seed (done …): built B, taken by draws K` (K растёт по мере областей),
   `[nr] seed <id> is in this device's list now`; во втором запуске B — `already expanded … nothing to do`. Картинка та же.
