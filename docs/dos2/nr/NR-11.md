# NR-11 `DM_NR_PRESENT` — финальный проход прямо в образ swapchain (сегмент S8)

Ветка `dos2-nr11` (worktree `wt-nr11`, база `dos2` 94d287d). На телефоне **не запускалось** (ни один режим). Умолчание 0.

## 1. Сначала: «регресс» present thread (`f1pt1`) — его нет

Логи `src/work/logs` (Mi 14 Ultra, палуба корабля, без лимита кадров). В каждом прогоне две фазы: без лимита (~105 fps) и полоса
**ровно 89,7–89,9 fps** — дисплей уходит на 90 Гц (в фазе 90 Гц поток present спит в acquire `busy_ms=10.99` мс на кадр = период 90 Гц).
Сводка `sum.txt` усредняет обе фазы, а доля фазы 90 Гц в прогонах разная. По фазам (медианы окон `NVN PERF v=1`, draws > 500):

| прогон | без лимита: fps / submit / present / GPU, мс | 90 Гц: окон | `poolreset wait_ms` (без лимита) |
|---|---|---|---|
| f0base (PT выкл) | 105,7 / 5,70 / 3,59 / 8,56 (105 окон) | 54 из 159 | 0,008 |
| f1pt1 (PT вкл) | **107,0** / 9,05 / 0,11 / 8,42 (71) | **91 из 162** | **2,85** |
| g0base (без NB, PT выкл) | 100,9 / 6,43 / 3,40 / 9,01 | 0 | 0,001 |
| g1all (всё вкл, PT вкл) | 105,7 / 8,94 / 0,38 / 8,54 | 0 | 0,90 (сред.) |
| h1def (умолчания) | 105,7 / 8,92 / 0,36 / 8,51 | 1 | 0,88 |

- **fps:** в одной и той же фазе PT не хуже (105,7 → 107,0 без лимита; 89,7 → 89,8 в 90 Гц). «100 → 97» — смесь фаз: f1pt1 провёл в 90 Гц 56 % окон,
  f0base — 34 %.
- **`submit_cpu` 5,7 → 9,05 — перенос ожидания, а не работа.** Без PT поток трансляции ждёт GPU в present (fence blit-а двух present назад,
  `present` 3,59 мс). С PT он туда не попадает и ждёт **тот же GPU** в начале следующего слота: `recording_slot` → `poolreset::finish`
  (сброс пула слота идёт после его fence): `NVN PERF poolreset waits 0,02 → 0,98, wait_ms 0,008 → 2,85`; в `parts_ms` это «other» 1,07 → 3,77.
  Сумма submit + present: 9,29 → 9,16 мс. Остальное в `parts` (draw +0,9, submit-часть +0,5…1,0 в фазе 90 Гц) — выборка 1 кадр из 32 и
  блокировка очереди: поток present держит `queue_mutex` на `vkQueueSubmit` blit-а и на `vkQueuePresentKHR`.
- **Вывод для NR-11:** с PT (умолчание) поток трансляции на Mi 14 **ждёт GPU** 0,9–2,9 мс на кадр — кадр упирается в GPU (с пузырями).
  `gpu_ms` (8,5) — это только метки слота, blit в отдельной подаче потока present туда не входит. Значит, снятый blit — это прямо fps на
  Mi 14 в этой сцене, а не только тепло.

## 2. Что сделано

Кадр по дампам IR телефона (ra1 / rb1 / rc1, 41 кадр, меню и палуба): окно — две чередующиеся текстуры 2400×1080 `fmt 0x25` (RGBA8 UNORM,
как swapchain); в кадре у текстуры окна X ровно 5 ссылок: целый ClearTexture (отложен, свёрнут в load op прохода комбайна), проход
комбайна (1 draw, читает цель тумана и цель UI — маршрут A NB-18b-10 подменяет **вход**, не выход), пустой проход (счётчик), present.
X не читает никто, кроме present.

**Правила** (`dm/gfx/nr/nr_present.h`, чистый C, тест):
- *предсказание:* этот кадр покажет текстуру, показанную два present назад (одна текстура — та же);
- *старт* — на `OP_SET_RT`, который ставит предсказанную X: только если первая запись X в кадре — **отложенная целая очистка** (ни один
  проход не грузит старое содержимое X), вид — весь образ (1 уровень, 1 слой, 1 сэмпл, свой формат), прошлый present без crop и без
  переворота (`DM_GFX_TAA_FIX`), нет открытого запроса / GPU-предиката (`DM_GFX_COND_RENDER=1`), и презентер выдал захваченный образ
  swapchain того же формата и размера, swapchain не повёрнут (`preTransform = IDENTITY`);
- *разрез:* командный буфер слота заканчивается в точке старта, хвост кадра пишется во второй буфер слота; в том же `vkQueueSubmit` это
  вторая партия, **только она** ждёт семафор acquire (стадии COLOR_ATTACHMENT_OUTPUT | TRANSFER) — 3D кадра его не ждёт;
- *пока активно:* каждый проход на X цепляет вид образа swapchain (`create_pass`, свой кэш framebuffer-ов на поколение swapchain),
  отложенная очистка X падает на образ swapchain (`pclear_land`), образ UNDEFINED → GENERAL за ожиданием; любое другое чтение / запись X
  (sampled, источник / приёмник копии, частичная очистка) — **откат**: образ swapchain копируется в X, кадр дальше идёт по X и кончается
  старым blit-ом в уже захваченный образ;
- *present:* X, без отката, без crop / переворота → GENERAL → PRESENT_SRC, последняя партия слота сигналит семафор present, презентер
  делает только `vkQueuePresentKHR`; иначе — blit в захваченный образ (если показана не X — сначала копия образа в X: промах предсказания).

**Презентер** (`android/vulkan_present.cpp`, `namespace nrp`): при 1 / 3 образы swapchain получают `COLOR_ATTACHMENT | TRANSFER_SRC` (если
поверхность позволяет) и виды. С present thread: после каждого задания поток present сразу захватывает следующий образ («парковка»,
вне потока трансляции, тот же `vkAcquireNextImageKHR` с 50 мс); движок берёт его, только если у потока нет задания (оно могло бы его
ждать); blit-задание тоже берёт запаркованный образ. Без present thread: acquire с timeout 0 на потоке трансляции (свободного нет — кадр
идёт по-старому). Задание present потока: `nrp=1` — только present (номер подачи отмечается сразу: движку ждать нечего), `nrp=2` —
`present_body` с `pre_index` (без acquire и без ожидания семафора, старый layout GENERAL). Пересоздание swapchain между взятием и present
невозможно по построению (взятие только без заданий в очереди; пересоздание — только в задании); на случай — счётчик `lost`.

| `DM_NR_PRESENT` | что делает |
|---|---|
| 0 / не задан | ничего: каждый хук — одно сравнение; у презентера ни usage, ни видов, ни парковки, ни снимка |
| 1 | как выше |
| 2 | всё решается и считается, исполняется старое (без acquire, без разреза, usage swapchain прежний); нарушенные допущения — `【红】` (первые 16) |
| 3 | как 1 + образ swapchain перед первым проходом красится в пурпур (непокрытое видно) |

Совместимость: **с present thread и без** (оба пути презентера), **с NB-21 `DM_NB_OWN=1`** (подача и present того же кадра идут одним заданием
`x_run_own` в старом порядке — движок видит те же `xbg_submit_now` → `xbg_present_texture_now`), с `DM_NB_MT=3` (разрез: `nbmt::end` основного
буфера, `nbmt::begin` хвоста), `DM_NB_MX` (решение в контексте записи), маршрутом A / NB-POST (их подмены — на входах комбайна, проход
комбайна создаётся тем же `create_pass`), `DM_GFX_STORE_HIST` (present без перехода X всё равно отмечается как чтение X).

**Поворот (currentTransform = 2 / 8 на телефоне).** Swapchain создаётся с `preTransform = IDENTITY` в обоих путях — поворачивает
композитор, как и для blit. Прямой рендер ничего в этом не меняет: та же ориентация, тот же размер (окно 2400×1080 = выход игры после
wide-патча = extent). Чего NR-11 **не может**: если когда-нибудь включить pre-rotation (KB NXH-A02), проход комбайна (транслированный шейдер)
пришлось бы вращать в VS и править `gl_FragCoord` — тогда blit заменяется поворачивающим draw и NR-11 даёт **0** проходов выигрыша; для этого
презентер отвечает `pre-rotated` и прямой путь не стартует. Нужна ли pre-rotation вообще, решает `dumpsys SurfaceFlinger` (слой DEVICE или CLIENT).

## 5. Ожидаемый выигрыш (не замер)
blit 2400×1080 RGBA8 = 10,4 МБ чтения + 10,4 МБ записи на кадр (2,2 ГБ/с при 105 fps), плюс одна подача и `vkQueueSubmit` под замком очереди
на потоке present.
- **Mi 14 / Adreno 750:** −0,2…0,5 мс GPU (UBWC источника; замер даст маркер `gfx-present-timing` → `NVN PERF present_gpu_us`). Кадр палубы
  упирается в GPU (поток трансляции ждёт его 0,9 мс/кадр по `poolreset`) → **+2…5 % fps** в этой сцене; поток present — без записи и подачи
  blit (`busy_ms` 0,5–0,9 → ≈ 0,2–0,4), меньше столкновений на `queue_mutex`. Цена на потоке трансляции: разрез (End + Begin буфера, барьер)
  ≈ 10–30 мкс, взятие образа — два мьютекса.
- **S7 (Adreno 7xx, LPDDR5, упор в GPU ~30 fps):** −0,5…0,8 мс из ~33 → +1,5…2,5 %.
- **Mali / PowerVR (тайлеры):** blit — отдельный фрагментный проход на весь экран: −0,6…1,2 мс (+2…4 % при 30 fps) и −20 МБ/кадр трафика
  (тепло); комбайн пишет плитку прямо в буфер композитора. Отдельной политики по вендорам не нужно (выигрыш везде одного знака); на PowerVR /
  Mali проверить, что поверхность даёт `COLOR_ATTACHMENT` и RGBA8 (иначе — `usage` / `format` в строке, старый путь).
- **Слабый CPU:** без изменений (с PT); без PT acquire переезжает из present в середину кадра на тот же поток — ноль в сумме.

## 6. Риски
1. Не исполнялось на телефоне. Синхронизация (семафор acquire только у хвоста, переход UNDEFINED → GENERAL за ним, PRESENT_SRC в последней
   партии, fallback-blit из GENERAL за ALL_COMMANDS) — по правилам Vulkan, не проверена валидацией: **первый прогон `=1` — с `DM_VK_VALIDATION=1`**.
2. Fence слота теперь включает ожидание acquire (хвост). Запаркованный образ берётся через ~8 мс после захвата — его семафор почти всегда уже
   сигнален; в фазе 90 Гц образ не успевает запарковаться → старый путь (строка: `not started: presenter (no image / job pending)`).
3. Чтения X мимо `prepare_read` / `transition` (storage-запись в окно, копия в layout GENERAL без перехода) не ловятся — в дампах их нет;
   `=2` считает пойманные.
4. Android с timeout-acquire не по стандарту (старые версии блокируют при timeout 0) — только без PT; там это та же блокировка, что была в present.
5. Ровно один захваченный образ: при `minImageCount` = числу образов второй acquire невозможен — поэтому парковка ждёт, пока движок не
   вернёт взятый; образ из выгруженного окна держится до следующего present.
6. Общие файлы (`vulkan_present.cpp` других портов): при `DM_NR_PRESENT` 0 / не задан изменений поведения нет (тест структуры это держит).

## 7. Не сделано
- Старт без отложенной очистки (`DM_GFX_CLEAR_FOLD` / `LAZY_CLEAR` выкл — например, Mali, где самотест LAZY_CLEAR не прошёл): тогда очистка X
  ложится сразу в X и кадр идёт по-старому (причина `no pending whole clear`). Если `=2` на Mali покажет это массово — следующий шаг: стартовать
  на самой очистке и класть её в образ swapchain.
- Pre-rotation (A02) и ASurfaceControl / AHB-текстуры окна (present без swapchain-копии вообще) — вне шага.
- Умолчание по детекту в `xbg_vendor_policy.h` — после телефона.

## 8. Прогон телефона (главный агент, по разрешению хозяина; бэкап `files/save`, проверить keyguard, погасить игру после логов)
APK: `wt-nr11/work/DOS2-port-debug.apk` (если собран) или сборка ветки. Окружение — умолчания DOS2 (NB всё вкл, PT вкл) + `DM_DBG=1
DM_DOS2_TOUCHUI=1 DM_DOS2_FPS=0`; сцена — палуба корабля + бой / город, если есть; по 90 с, чередовать P0 / P1 (ABBA, нагрев).
- **P0** база + маркер `gfx-present-timing` в каталоге данных: `NVN PERF present_gpu_us=… extent=2400x1080` — цена blit на GPU.
- **P2** `DM_NR_PRESENT=2`: строки `[nr] DM_NR_PRESENT=2` (движок и презентер), `[nr] present (DM_NR_PRESENT=2): swapchain gen …, N images
  2400x1080 format 37, colour attachment allowed`; раз в 10 с `[nr] present (…, last 10 s): F frames; would start ≈ F (would present ≈ F,
  blit 0: -); not started: … ; red 0`. Решает: доля кадров, причины отказа (особенно `no pending whole clear`), `red 0`.
- **P1** `DM_NR_PRESENT=1 DM_VK_VALIDATION=1` (короткий, 30 с): нет сообщений `dm-vvl` про swapchain / семафоры / layout.
- **P1** `DM_NR_PRESENT=1` против P0: `started ≈ presented (direct) ≈ frames`, `presenter: parked ≈ taken ≈ presented`, `lost 0`, нет `【红】`;
  fps (без лимита), `poolreset wait_ms`, `present_thread busy_ms`, `gpu_ms`; скриншот тот же. Ждём +2…5 % fps.
- **P3** `DM_NR_PRESENT=3` 20 с: пурпура на экране нет.
- **P1i** `DM_NR_PRESENT=1 DM_GFX_PRESENT_THREAD=0`: путь без потока present (`taken` > 0, при 90 Гц `no image` растёт — нормально).
- В P1 один раз: «домой → назад», поворот телефона на 180° (смена currentTransform 2 ↔ 8: пересоздание swapchain), загрузка сохранения —
  без зависаний, `lost` ≤ единиц.
