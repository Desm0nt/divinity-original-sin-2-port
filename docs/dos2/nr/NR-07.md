## 2. Переключатель `DM_NR_PIPE` (бэкенд читает в `warm::start`; фронт — в `dm_dos2_nr_install`, подсказки только при `DM_NR=1/2`)
- **0 / не задан** — ничего: `worker()` — прежний цикл, `need / took / DrawBuild` — загрузка и непринятый переход, памяти нет, фронт ключи не шлёт.
- **1** — порядок по событиям + без двойных сборок:
  - запись, у которой все ключи стадий названы программами игры, строится раньше остальных (очередь FIFO), остальные — в порядке списка;
  - draw, не нашедший пайплайн в готовых, а его запись **строится сейчас**, ждёт эту сборку (`DM_NR_PIPE_WAIT_MS`, 500 мс; 0 = не ждать) вместо второй компиляции; готовую — забирает; **свободную** — столбит (прогрев её не строит, draw строит сам / через async, как раньше);
  - пока draw-путь сам в драйвере, потоки прогрева не начинают новую сборку (PowerVR `DM_GFX_PIPE_SERIAL`, старые Mali с замком компилятора на процесс: draw не стоит за чужой сборкой);
  - без `DM_NR` (нет подсказок) — порядок списка, но ожидание / столбление работают.
- **2** — сверка / счёт: порядок списка **как раньше**, ничего не столбится и не ждётся; подсказки, сборки и нужды draw записываются со временем. Строка `[nr] pipe (…)` говорит, сколько промахов draw по записям списка было **подсказано заранее и за сколько** (выигрыш `=1`) и сколько застали запись в работе (двойные сборки, которые `=1` убирает). Красные строки `【红】[nr] pipe check: a draw needs warm record … but no program the game set up named all its shaders` — «дыры» подсказок (первые 16), то, что `=3` собрал бы в кадре.
- **3** — ленивый: как 1, но строятся **только** подсказанные записи (потоки ждут подсказок). Для медленных компиляторов и малой памяти: сессия строит области, которые грузит, а не всё, что устройство когда-то видело. Без подсказок работает как 1 (строка в логе).
- `DM_NR_PIPE_THREADS=<n>` — число потоков прогрева (иначе прежнее `min(3, ядра / 3)`), для A/B.
- Строки: `[nr] DM_NR_PIPE=<n> (NR-07: …): N warm records, K shader keys, H hints before the start; hints from every program …`;
  `[nr] pipe (list done | 10 s | shutdown, …): … built X from hints + Y in list order, failed, left, (ready not taken …); hints …: … keys with records (… records queued), … keys no record has (new to this list) …; draws: took … ready (hinted before …: <50ms …; list order …), missed … listed records (ready / in flight / not built / failed / claimed; hinted before …: лид; never hinted …), waited … (ready …, timed out …), claimed …, list builds skipped as claimed …`;
  фронт раз в 10 с: `[nr] pipe hints (DM_NR_PIPE=n): … program keys sent to the warm-up, … programs without a key`.

## 3. Пер-draw: прямая таблица против NB-13b — решение с числами
- Замер на ПК (`nr_pipe_test.c`, x86, clang -O2): поток draw по статистике телефона (150 записей, 56 % попаданий «как прошлый draw», 0,69 группы
  перечитано на draw, запись состояния вычтена) — **шаг NB-13b 31,5 нс, прямая таблица 4,3 нс (×7,3)**.
- На телефоне шаг NB-13b ≈ 280–350 нс; при том же отношении таблица ≈ 40–50 нс → **−0,23…0,3 мкс на draw ≈ −0,25…0,35 мс на кадр** потока трансляции
  (≈ 1000–1200 draw в кампании), на слабых CPU ×2–3 в абсолюте.
- **Но** таблице нужен id ключа NR-02 в записи draw. Сейчас его на бэкенде нет: ключ считает хук `0x924730` на потоке игры (оценка NR-02:
  0,2–0,4 мкс на draw в режиме счёта), записи NVN его не несут, а вставка своей записи между состоянием и draw ломает захват NB-09 / тень NB-13a /
  счёт NB-15. Включить таблицу сейчас = перенести ту же цену с потока трансляции на поток игры (≈ 0 выигрыша) + новая запись в потоке команд.
  Выигрыш появляется **в NR-09**: `OP_X_NR_DRAW` несёт id ключа (он нужен NR-09 и NR-08 в любом случае), состояния NVN уходят — вместе с ними `mark`
  NB-13b и перечитывание групп. Поэтому `nrp_tab` готова и проверена, а сверка «тот же `VkPipeline`, что выбрал старый путь» делается там: NR-09 `=2`
  на каждом draw кладёт в таблицу результат `pipeline_lookup` и сравнивает со своей находкой.
- Что NR-09 кладёт в `nrp_var` (6 слов): `pass_def`, `VkRenderPass`, `VkPipelineLayout`, samples | активные цвета | rt_n | формат глубины,
  `restart_eff`, варианты модулей (`#at` альфа-тест, `#vi` retype, подмена глубины пре-пасса). Глобальные переключатели вне ключа (`alpha_test_on`,
  `taafix`, `depth16_as_d24`) — как у старого мемо и NB-13b: постоянны за сессию.

## 4. Сид прогрева: дамп NR и `.pso` iPad
- **Дамп NR как сид не нужен:** подсказки идут живьём из тапа программ (ключ пака = ключ записи), имена движка для этого не требуются. Дамп
  (`nr_shaders.tsv`, NR-01 / 02) остаётся инструментом: какие шейдеры движок создаёт на загрузке какой области.
- **`.pso` iPad** (`tools/dos2_nr_pso.py`, только имена и ключи; файлы iPad не читаются и не кладутся в APK): 3970 файлов → 3691 различных
  (материал, состояние) на 1068 материалах (DEF 349, DEP 1086, FOR 1180, SHA 1076); 743 материала сопоставлены ключам Switch (`programs.tsv`) →
  **743 пары (VS, FS), 2615 пайплайнов iPad**; 325 `_SHA` — только iPad (Switch рисует тени через `_DEP`). Вариантов на материал: 1–5 у 90 %.
  Это потолок «сколько пайплайнов материалов игра построит за прохождение»; список Mi 14 — 1220 записей с одной палубы / стартовой зоны.
  `dos2_nr_pso.py --list <vk-pipeline-list.bin>` даёт покрытие списка устройства каталогом (пары, записи вне каталога = движок / UI / частицы) и
  число пайплайнов iPad у непокрытых пар — сколько сборок в кадре ждёт игрока в новых областях. Список лежит на телефоне в
  `Download/DivinityOriginalSin2Mobile/dm/vk-pipeline-list.bin` (на ПК его нет — главной сессии забрать при следующем прогоне).
- **Сид в APK** — уже есть механизм `warm::seed()` (`shaders/vk-pipeline-list.seed` становится списком на первом запуске, `merge_warm_lists.py`),
  но DOS2 его не ставит (`setup_dos2.py` про сид молчит): на первом запуске прогревать нечего. Рекомендация: список Mi 14 после длинного прогона
  (несколько областей) → сид; на Mali / PowerVR часть записей не совпадёт байт в байт (другие политики проходов → другой ключ create-info) и
  провалится в прогреве (`warm_failed`, безвредно) — сид по семейству (`DM_GFX_SIM_GPU=mali`), как TL2 (MALI-17). С `DM_NR_PIPE=1/3` большой сид не
  стоит лишнего: подсказанное строится первым, ленивый режим остальное не строит.

## 5. Mali / PowerVR / слабые CPU
- Маркеры FUSE снимают ≈ 13 мс с **каждой** сборки на любом GPU (у слабых CPU демон FUSE ещё медленнее).
- Медленные компиляторы (Mali-G76: 50 мс без кэша, 24 мс с кэшем — FN-05; G72 3900 PSO за 160 с): 1200 записей = 30–60 с времени потоков на каждую
  загрузку даже с кэшем. `=1` строит сначала то, что грузится; `=3` — только это (и держит меньше готовых пайплайнов в памяти: у Mali / PowerVR
  пайплайн — десятки КБ, 1200 штук — десятки МБ).
- PowerVR (`DM_GFX_PIPE_SERIAL=1`) и Mali со старым замком компилятора: draw, которому нужен пайплайн, больше не стоит за сборкой прогрева чужой
  записи (потоки ждут, пока draw в драйвере), а если его запись строится — ждёт её, а не компилирует вторую копию за тем же замком.
- Кэш драйвера: поведение не менялось (`DM_GFX_PIPE_CACHE_LOAD` как было). После маркеров счётчик `new=` в `pipeline cache save` станет честным
  (≥ 2 мс без FUSE = настоящая компиляция) — кэш перестанет переписываться на каждой загрузке без причины.
- Умолчание по семейству (`xbg_vendor_policy.h`, после прогонов): кандидат `=1` везде (только порядок и дедупликация), `=3` на Mali / PowerVR / Maleoon,
  если `=2` покажет 0 дыр подсказок. Сейчас в политике ничего нет — умолчание 0.

## 8. Риски и чего нет
- **Маркеры** — изменение по умолчанию (не за переключателем; так устроен общий модуль). Отказ open / mmap → старый путь. На реальном Mali модуль не
  проверялся нигде; на Mi 14 — только в TL2.
- Подсказки требуют `DM_NR=1/2`: 18 хуков NR-01 (никогда не исполнялись на телефоне) + SHA-256 ключа на каждую программу на потоке загрузки игры
  (у программ в скобке движка NR-01 и так его считает; новое — только программы вне скобок, UI).
- Если движок создаёт программы **непосредственно перед** первым draw (а не на загрузке), подсказка почти ничего не опережает — покажет `=2`
  (ведра лида `<50ms`).
- `=3`: запись, чьи шейдеры ни одна программа не назвала (дыра: код не прочитался → нет ключа), строится в кадре; `=2` перечисляет такие красными строками.
- Ожидание записи «в работе» до 500 мс: если поток прогрева на малом ядре, остаток его сборки может быть дольше своей сборки на большом ядре
  (`DM_NR_PIPE_WAIT_MS` для A/B; при таймауте draw строит сам, как раньше).
- Пока draw-путь собирает в кадре серию пайплайнов, прогрев стоит (сознательно: драйвер и ядра — кадру).
- Записи из `async_request` / в кадре, добавленные в список в этой сессии, планировщик не видит до следующей загрузки (как и прежний прогрев).
- Не сделано: пер-draw таблица в `draw()` (§3, NR-09); сид в APK и `setup_dos2.py` (решение главной сессии, нужен список телефона); умолчание по
  семейству в `xbg_vendor_policy.h`; синтез записей для областей, которых нет в списке (create-info зависит от проходов / раскладок хоста — не по `.pso`).

## 9. Прогоны на телефоне, которые это подтвердят (бэкап `files/save`, keyguard, force-stop после)
1. **Маркеры, без NR** (APK этой ветки, env по умолчанию): в boot.log `[pc] pipe-marker-mmap: applied (pipeline crash markers mapped in /data/user/0/org.dos2.port/files/gfx-gpipe-inflight…)`;
   в `Download/…/dm` нет новых `gfx-gpipe-inflight*`. Ждём: `warm_ms` после `warm_built=12xx` ≪ 16,6 с (оценка 1,5–3 с), список достроен за ≪ 12 с стены,
   `pipeline cache save … new=` на второй загрузке ≈ 0–десятки (не 1100), `create_ms / created` у входа в игру меньше. Сцена: меню → сейв → 2 мин.
2. **`DM_NR=1 DM_NR_PIPE=2`** (счёт, порядок прежний): `[nr] DM_NR_PIPE=2 (NR-07: check …): 12xx warm records, … shader keys`, `[nr] DM_NR_PIPE=2 (NR-07): the pack key …`,
   `[nr] pipe hints: N program keys sent` (≈ число программ движка + UI), `[nr] pipe (list done / 10 s …)`: `keys with records` / `records queued` по
   мере загрузок, ведра лида у `took … hinted before` и `missed … hinted before`, **0 красных строк** `pipe check` (иначе — список дыр подсказок).
   Тот же сейв + смена локации (новая область) + бой.
3. **Медленный компилятор на Mi 14** (имитация Mali / слабого CPU): `DM_GFX_PIPE_CACHE_LOAD=0 DM_NR_PIPE_THREADS=1`, ABBA по 2 прогона:
   (A) `DM_NR=1 DM_NR_PIPE=2`, (B) `DM_NR=1 DM_NR_PIPE=1`, затем (C) `DM_NR=1 DM_NR_PIPE=3`; сразу после меню грузить сейв. Решают: у входа в игру
   `created` / `create_ms` / `create_max_ms` и длинные кадры (B, C < A), в `[nr] pipe`: `built … from hints` до первой нужды, `waited (ready …)`,
   `claimed`, `list builds skipped as claimed`; у C — `built` ≈ подсказанные, `left` > 0 на выходе; картинка та же. Внимание: `PIPE_CACHE_LOAD=0`
   пересоберёт кэш драйвера (он сохранится заново — безвредно, но следующий обычный запуск будет как первый).
4. После прогона: забрать `Download/DivinityOriginalSin2Mobile/dm/vk-pipeline-list.bin` → `python tools/dos2_nr_pso.py --list <файл>` (покрытие
   каталогом iPad; вход в решение о сиде).
