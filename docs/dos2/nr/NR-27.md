## 1. Почему при загрузке, а не в setup
Постановка: «проход в setup + вариантный пак + переключатель». При разборе выяснилось то, чего NR-25 не учитывал:
1. **Телефон компилирует не то, что лежит в паке.** `tidy_rewrite` (`xbg_game.cpp`) при каждой загрузке модуля уже гонит три точных
   прохода ровно по этим чтениям: `DM_GFX_LDC_FOLD` (компонента → константа), `DM_GFX_FORWARD_TEMPS`, `DM_GFX_LDC_CANON` (канонический
   индекс vec4; через `DM_GFX_D3PERF` + самотест на не-Adreno). NR-25 мерил сырой пак (FlowingWater LS 26); после этих трёх на G57 уже 19
   (Mali убирает дословно одинаковые загрузки). Не хватало последнего шага — собственно слияния компонент. Проход в setup по сырому паку
   пришлось бы всё равно проверять вместе с этой цепочкой.
2. **Вариантный пак — это 111.5 МБ** (2 211 бандлов: 149 FS = 12.7 МБ, 2 062 VS = 98.8 МБ; только FS — 12.7 МБ, но тогда теряется
   выигрыш VS) на телефоне и в `adb push`, +минуты setup на чистом
   Python, второй источник устаревания (пак ↔ вариант) и своя сверка голов. Проход при загрузке — 0 байт, 0 секунд setup, работает и для
   бандлов из `dm/missing`, и после любого набора ранних переписываний.
3. **Цена при загрузке ничтожна:** в среднем 68–77 мкс на модуль, максимум ~1.1 мс (Ryzen 5 5600; телефон ×3–4), плюс столько же на
   повторную проверку только у изменяемых модулей. Сборка пайплайна драйвером — десятки мс.
4. Доказательство «по каждому шейдеру» от места прохода не зависит: `tests/ubovec_scan.cpp` гонит **тот же боевой C++** по всему паку на ПК.

Если вариант в setup всё же нужен (например, чтобы убрать и эти ~70 мкс): `ubovec_scan pack` уже пишет `<key>.after.spv` каждого
изменённого модуля; собрать из них пак с теми же головами — ~30 строк. Игрокам при этом нужен был бы компилятор C++ или порт прохода на
Python, поэтому не делал.

## 2. Проход (`dm/gfx/vulkan/engine/xbg_spirv_ubovec.cpp`, 512 строк, без Vulkan и окружения)
- **Факты о целых** (`XbgUvFact`): `значение == (S · mul + add) mod 2^bits`, где S — значение SSA-id (или константа). Правила для IAdd /
  ISub / IMul / сдвигов на константу / AND с маской 2^t−1 / Bitcast / CopyObject точны с учётом переполнения 32 бит (в частности:
  прибавление k к значению с известными младшими битами допустимо только без переноса; сдвиг вправо требует, чтобы множитель делился).
  Сумма двух разных неизвестных даёт «кратно 2^g плюс остаток». Чего правило не выражает — новое неизвестное.
- **Function-переменные транслятора** (регистры Maxwell и одноразовые временные) прослеживаются как при построении SSA: дерево доминаторов,
  значение переменной в точке слияния (итерированная граница доминирования её записей) — новое неизвестное; чтение до первой записи —
  неизвестное на каждое чтение. Переменная с любым использованием, кроме целого `OpLoad` / `OpStore`, не прослеживается.
- **Кандидат:** цепочка в `Uniform`-переменную со структурой `Block` (не `BufferBlock`: SSBO может меняться), все индексы кроме последнего
  ведут в вектор 2–4 компонент (не через матрицу), последний — доказанная константа, все использования цепочки — целые `OpLoad`.
- **Слияние:** ключ = (переменная, факты всех индексов). Обход дерева доминаторов с таблицей по областям: первое чтение ключа — лидер,
  остальные, которыми он доминирует, — члены. Лидер переписывается, только если группа читает ≥ 2 разных компонент и индекс вычисляемый
  (vec4 по фиксированному месту драйвер и так держит в uniform-регистрах: malioc — ровно 0 разницы, поэтому `fixed_too` выключен; с ним
  менялись бы 11 599 модулей без выигрыша).
- **Ничего не поднимается и не пересчитывается:** загрузка vec4 встаёт на место первого чтения и берёт его же id индексов; чтения в
  соседних ветках не сливаются. Поэтому нет загрузки на пути, где её не было.
- **Почему точно:** UBO неизменен за вызов шейдера; равные факты ⇒ равные значения в любой точке, где оба определены (SSA: определение
  доминирует, между лидером и членом значение не может обновиться, иначе лидер бы не доминировал); компонента — доказанная константа.
  Единственное отличие от оригинала — читаются и неиспользуемые компоненты того же vec4 (см. риски).
- `xbg_spirv_ubovec_check(in, out)` — независимая сверка результата: `out` = `in` за вычетом удалённых цепочек, плюс новые пары
  «цепочка vec4 + загрузка», плюс `OpLoad` → `OpCompositeExtract` под тем же id из загрузки той же переменной с попарно доказанно равными
  индексами, верной компонентой и доминированием. Движок принимает переписанный модуль только после неё.
- Не зависит от FOLD / TEMPS / CANON: на сыром паке, после `ft` и после `ftc` результат один (149 / 2 062 модулей, 2 872 / 96 267 чтений).

## 3. Переключатель
`DM_NR_UBOVEC` (читается при инициализации рядом с `gfx-ldc-fold`; последний шаг `tidy_rewrite`, оба загрузчика модулей и потоки прогрева):

| значение | что делает |
|---|---|
| 0 | выключено: `ubovec_rewrite` выходит первой строкой, байт в байт прежнее поведение |
| 1 | переписать, проверить `xbg_spirv_ubovec_check`, использовать; при отказе проверки — старый модуль + красная строка |
| 2 | переписать + проверить + посчитать, **исполняется старый модуль**; строка на каждый модуль |
| 3 | яд: переписанные чтения берут следующую компоненту — свет forward-материалов и скиннинг заметно ломаются (видно, куда проход дотягивается) |

Умолчание без env — `xbg_nr_ubovec_default(gpu_policy)` в `xbg_vendor_policy.h`: **Mali → 1** (замерено, точно), **Adreno → 0** (Turnip
сливает сам: `nir_opt_load_store_vectorize`; стоковый Qualcomm на LLVM — тоже; выигрыша нет, только время загрузки), **PowerVR / Xclipse /
Maleoon / прочие → 0**: офлайн-компилятора нет, не «доказано» — включать после устройства (одна строка в политике).
`DM_GFX_SIM_GPU=mali` (или `family-mali`) включает проход на Adreno-телефоне — так его можно прогнать на Mi 14.

Строки лога: `NVN DM_NR_UBOVEC=N (env | family default; policy family … default …)`; `NVN ubovec shader=<key> reads=… vec4_loads=… words a -> b`
(первые 4 и степени двойки; в режиме 2 — каждый); в периодическом блоке `NVN PERF` — `NVN PERF ubovec mode= modules= of reads= vec4_loads= (scalar loads saved …)
unproven_component= check_bad= cpu_us=`; отказ проверки — `【红】NVN DM_NR_UBOVEC=… check: shader <key>: <причина>` (первые 16) и `【红】` на
сводке, пока `check_bad` ≠ 0.

## 4. Головы бандлов, NR-04, NB_POST
Бандлы и пак не меняются: переписываются только слова, уходящие в `vkCreateShaderModule`, как у FOLD / TEMPS / CANON. Поэтому:
- `native::apply` (`DM_GFX_NATIVE_SHADERS`; NR-04 `DM_NR_SH`, судя по NR-25, подменяет бандлы тем же способом — его ветку не читал) сравнивает голову нативного бандла с транслированным **в байтах бандла при
  чтении** (`xbg_game.cpp`, `xpack::read` → `native::apply`, слово длины SPIR-V исключено) — до любых переписываний;
- `DM_NB_POST` сравнивает host-голову слитого бандла с `xpack::read_translated` (`xbg_nb_post.inc`, `nb_fx_host_head_matches`) — тоже байты пака;
- `spirv_uniform_extent` (обрезка копируемых байт UBO, идёт **после** `tidy_rewrite`): цепочка с вычисляемым индексом и раньше, и теперь
  означает «весь блок»; цепочки с константным индексом проход не трогает. Проверено чтением кода.
- Нативные паки (`packs/2a/native.xgspack.light-mobile`, `shadows-mobile`, `work/shaders-native/native.xgspack`, 978 бандлов): 0 изменений —
  glslc и так грузит vec4.

## 7. Транслятор
`Ldc` (`dm/third_party/ryujinx/src/Ryujinx.Graphics.Shader/Instructions/InstEmitMemory.cs`) эмитит каждое слово отдельно:
`wordOffset = addr >> 2`, затем `EmitLoadConstant(slot, wordOffset)` → `vec4 = word >> 2`, `comp = word & 3`. Соседние `LDC` — разные
инструкции Maxwell со своими регистрами адреса, так что «эмитить vec4 сразу» в точке эмиссии нельзя: нужен тот же анализ (младшие биты
адреса + группировка по общей базе) отдельным проходом в `Translation/Optimizations`. Это возможно и по-своему чище (типизированный IR,
одна правка для всех драйверов), но: меняет все 12 329 бандлов (каждому игроку — заново setup и 284 МБ пака), затрагивает общий
vendored-транслятор других портов и не даёт ничего сверх прохода при загрузке. **Вывод: исправление в трансляторе не лучше; оставить проход
в движке.** Его же (вместе с FOLD / CANON) можно вынести в `port-common` для DOOM / D3 / Eternal — там те же `LDC`.

## 9. Риски и что не сделано
- **Не запускалось ни на одном устройстве.** Умолчание 1 на Mali опирается на офлайн-компилятор Arm и точность; форма результата —
  самый обычный SPIR-V (так glslang пишет `c.data[i].xyz`, так устроены все нативные шейдеры NR-04 / пост).
- **Читаются неиспользуемые компоненты vec4.** Если привязанный диапазон UBO кончается внутри vec4 (размер c-буфера не кратен 16),
  загрузка формально выходит за диапазон; данные лежат в том же буфере (кольцо констант), неиспользуемые компоненты ни на что не влияют.
  Практический риск считаю нулевым, но формально это отличие.
- **Рост спиллинга FS на Bifrost / G57** (§5): по циклам malioc не дороже, вживую не проверено.
- Проверка на устройстве в самотесте (`xbg_selftest`, как у `LDC_CANON`) не добавлена: его шейдер читает SSBO, нужен новый UBO-вариант и
  перегенерация `xbg_selftest_spv.h`. Кандидат, если на каком-то Mali появится артефакт.
- `OpSwitch` с 64-битным селектором не разбирается (транслятор таких не даёт) — функция тогда остаётся как была.
- PowerVR / Xclipse не замерены; чтения в соседних ветках не сливаются (поднятие загрузки — отдельный шаг, по malioc после прохода
  остаётся LS ≈ 12 на FS: 5 загрузок vec4 на источник, 4 побайтных чтения, varying).
- `NATIVE_RENDERER_PLAN.md` и `docs/port-kb` не трогал (правит главная сессия).

## 10. Прогон на телефоне (Mi 14 Ultra, Adreno — проверка корректности; выигрыш виден только на Mali)
Сцена: любая с динамическим светом, водой и персонажами (палуба подходит; лучше бой). `dm/env`:
1. `DM_NR_UBOVEC=2` — ожидание: `NVN DM_NR_UBOVEC=2 (env; …)`, строки `NVN ubovec shader=… (counted, old module used)`,
   `NVN PERF ubovec mode=2 modules=N … check_bad=0`, ни одной `【红】`; картинка и fps как без переключателя.
2. `DM_NR_UBOVEC=1` — та же картинка (скриншоты равны), `NVN PERF v= gpu_ms` без изменений (Turnip), `check_bad=0`, `cpu_us` — цена загрузки.
3. `DM_NR_UBOVEC=3` — свет на воде / прозрачных материалах и скиннинг персонажей заметно сломаны: проход дотягивается до живых шейдеров.
4. (по желанию) `DM_GFX_SIM_GPU=mali` без `DM_NR_UBOVEC` — в логе `family default … default 1`, умолчание Mali работает.
На живом Mali (у хозяина нет; первый игрок): умолчание уже 1; A/B `DM_NR_UBOVEC=0` против 1 с `DM_GFX_PASS_PROF=300,180,0` — GPASS
forward-проходов и `ClusteredLightingWithSSAO` (ожидание на Valhall: −30…−40 % времени этих проходов), теневых каскадов с персонажами.
