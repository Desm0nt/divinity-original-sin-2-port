## 0. Коротко — что нужно исполнителю
| Вопрос | Ответ | Пометка |
|---|---|---|
| Кто рисует глубину каскадов солнца | отдельный класс стадии, таблица методов `0x299b0a0` (имени в коде нет; ниже — «стадия каскада»). **По одному объекту стадии на каскад.** Метод 13 (постройка списка команд) = `0xb15090`, метод 6 (исполнение списка) = `0xb15020`, метод 4 (подготовка, запуск задач) = `0xb14f00`, конструктор `0xb14cd0` | [бин] |
| Кто рисует пре-пасс | не стадия, а **задача внутри `DeferredBufferStage`**: под-объект стадии по `+0x90` с таблицей `0x299b680`, метод 4 = `0xb1be00`. У задачи **свой список команд** (`стадия+0xa8`), он строится отдельно от списка стадии и вливается в него пакетом 2 (вызов функции `0xac1f80` с аргументом `стадия+0xa8`) | [бин] |
| Каким методом рисуются объекты | тем же методом 23 (`таблица+0xb8`), что и G-буфер: `(объект, запись очереди, контекст)`. Отличие только в контексте: флаги и маска прохода | [бин] |
| Флаги и маска прохода (контекст `+8` и `+0xc`) | каскад: флаги `2`, маска `0x10`. Пре-пасс: флаги `0x40000`, маска `0x20`. G-буфер: флаги `1`, маска `8`. Отражение (плоское зеркало, `0xb0b9e0`): флаги `0x20002`, маска `4`. Отбор видимого основной камеры: маска запроса `0x80` | [бин] |
| Какой шейдер | при `флаги & 0x40002` (и каскад, и пре-пасс) — **третий** шейдер набора материала: программа `набор+0x30`, формат вершин `набор+0x48` (а не `+0x20 / +0x38`) | [бин] |
| Константы объекта | метод 26 объекта (`таблица+0xd0`), у 11 из 12 классов это `0x90e280`: одна матрица 4×4 = `объект+0x10…0x4c` × `объект+0x90…0xcc`, ставится по имени (`0x940d80`, имя — глобальная строка `[0x2bbb798]`). Тот же метод и те же данные во всех проходах | [бин] |
| Константы вида | пакет `0x17` (0x98 байт): матрица вида, матрица проекции, положение глаза, два числа; обработчик пишет их в общий блок `[r+0x888]` по `+0x80…0x164` и сам считает произведение. Затем пакет `0x1b` (`0x927310`) | [бин] |
| Плитка каскада в атласе | пакет `0x12` (окно вывода): ширина = высота = `размер плитки`, x = `столбец × размер`, y = `строка × размер`; размер плитки — 16-битное слово `O+0x340`; номер каскада = `строка + столбец × 2` | [бин] |
| Очистка атласа | пакет 5 (очистка глубины, значение 1.0) — **только в стадии каскада № 0**; остальные каскады дорисовывают в ту же цель | [бин] |
| Цель | глубина = `*[O+0x2e8]` (тот же хэндл `ShadowRenderStage` позже называет `DirectionalLightShadowDepth`); цветовых целей нет (пакет `0x16` с числом целей 0) | [бин] |

`O` — объект «тени солнца» (каскады): на него смотрят `стадия каскада+0x90` и `ShadowRenderStage+0x128`.
`r` — рендерер `[main+0x2bbdc68]` (как в `NR-NATIVE.md`).

## 1. Каскады солнца: стадия `0x299b0a0`

### 1.1 Объект стадии (конструктор `0xb14cd0(this, O, матрицы, ?, дальности)`) [бин]
| Смещение | Что |
|---|---|
| `+0x00` | таблица методов `0x299b0a0` (база `0x29980b0`) |
| `+0x10` | вид кадра (ставит метод 4) |
| `+0x18` | список команд стадии (куски по 0x4000 байт); `+0x48` = 1 — «записывать пакеты» |
| `+0x80` | задача постройки списка, таблица `0x299b128` (тело `0xb15610` — тот же метод 13 в рабочем потоке) |
| `+0x90` | `O` — объект каскадов |
| `+0x98` | камера каскада (из неё берётся матрица проекции `0xa4be10(камера)` и положение глаза `камера+0x74`) |
| `+0xa8` | **отборщик** каскада `C` — объект того же класса, что отборщик основной камеры (очереди по фиксированным смещениям, §3) |
| `+0xb0`, `+0xb8` | столбец и строка плитки (64-битные); номер каскада `i = строка + столбец × 2` |
| `+0xc0` | указатель на массив матриц вида каскадов `O+0xe0`, шаг 0x40 (берётся `[+0xc0] + i × 0x40`) |
| `+0xc8` | указатель на массив матриц `O+0x1e0` (четвёртый аргумент конструктора) |
| `+0xd0` | указатель на массив чисел `O+0xbc` (дальняя плоскость каскада, шаг 4) — уходит в пакет `0x17` по `+0x10` |
| `+0xd8` | задача отбора, таблица `0x299b168` (тело `0xb14e40`) |

### 1.2 Метод 13 `0xb15090` — что пишется в список, по порядку [бин]
Условия выхода без рисования: нет сцены (`вид+0x118`), выключены тени (`[вид+0xe0]+0xa4 == 0`).
1. если `i == 0`: пакет 5 — очистка глубины `*[O+0x2e8]`, значение 1.0;
2. пакет `0x16` — цели: 0 цветовых, глубина `*[O+0x2e8]`;
3. пакет `0x12` — окно вывода: `(+4 ширина = T, +8 высота = T, +0xc x = столбец × T, +0x10 y = строка × T)`, `T = u16 [O+0x340]`
   (в кэше рендерера это `r+0x171c…0x1728`; при прямом исполнении зовутся и окно вывода, и ножницы NVN);
4. пакет `0x17` (0x98 байт) — константы вида каскада:
   `+4` положение глаза (3 × float, из `камера+0x74`), `+0x10` число из массива `[+0xd0][i]`, `+0x14` матрица вида 4×4
   (`[+0xc0] + i × 0x40`), `+0x54` матрица проекции 4×4 (`0xa4be10(камера)`), `+0x94` число `камера+0x98`;
5. пакет `0x1b` — применить (`0x927310`);
6. отбор: `C->метод 4 (C, вид)` (`таблица C + 0x20`) — отборщик заполняет очередь каскада;
7. сортировка очереди: `0xa88090(0, n − 1, C+0x380, камера)`;
8. цикл по очереди `C+0x380` **с конца к началу** (записи по 0x18 байт в массиве `[C+0x408]`, число = `([C+0x410] >> 24) & 0xffffff`):
   `объект->метод 23 (объект, запись, контекст)`; контекст на стеке: `+0` список стадии, `+8` флаги = `2`, `+0xc` маска = `0x10`,
   `+0x10` вид, `+0x18` стадия, остальное нули.

Значит: **очередь каскада одна (`C+0x380`), метод один, состояние между draw меняют только сами объекты** (пакеты 21 / 15 / 17 / 28 / 36–37).

### 1.3 Порядок и исполнение [бин]
- Метод 14 `0xb15580` (ключ порядка стадии) = `(i × 2 | 1) + (i ≠ 0 ? 10 : 0)` — каскады идут по возрастанию номера, каскад 0 первым
  (он и очищает атлас).
- Метод 4 `0xb14f00(стадия, вид)`: пишет `C+0x191 = i` (байт) и `C+0x370 = [O + 0x300 + i × 8]`, затем ставит в очередь рабочих
  потоков две задачи стадии (`+0xd8` — отбор — в группу `[O+0x2f8]`, `+0x80` — постройка списка — в группу `[O + 0x320 + i × 8]`). То есть **список команд каскада
  строится в рабочем потоке, параллельно с другими стадиями**.
- Метод 6 `0xb15020` (исполнение): сначала `0x807b20([O + 0x320 + i × 8], 1)` — **ожидание группы задач этого каскада**, потом обход
  списка стадии пакет за пакетом через `ExecuteRenderCommand 0x93e5f0`, потом освобождение списка (`0x941890`).
- Метод 9 `0xb15060`: `камера+0x390 = u16 [O+0x340]` (размер плитки в камеру).

### 1.4 Объект каскадов `O` (стадия-владелец, таблица `0x299b1a8`) [бин]
`O` сам является стадией (11 методов): метод 4 `0xb15ae0(O, вид)` каждый кадр считает камеры и матрицы каскадов и зовёт метод 4
каждой стадии каскада; метод 9 `0xb165a0(O, вид)` создаёт / удаляет стадии каскадов и атлас при смене настроек.
| Смещение | Что | Откуда |
|---|---|---|
| `+0x80 + i × 8` | указатели на стадии каскадов (объекты по 0xf0 байт, создаёт `0xb16780`: всегда **3 стадии**, `O+0x342 = 3`) | `0xb16780` |
| `+0xa8…0xb8` | границы каскадов по дальности (float; каскад `i` — от `[+0xa8 + 4i]` до `[+0xac + 4i]`) | `0xb15ae0` |
| `+0xbc + i × 4` | `камера каскада+0x9c` (дальняя плоскость); это же число идёт в пакет `0x17` по `+0x10` | `0xb15ae0` |
| `+0xcc + i × 4` | `2 × float [камера каскада+0x388]` | `0xb15ae0` |
| `+0xe0 + i × 0x40` | **матрица вида каскада** = копия `камера+0xe0…0x11f` после `0xa4b400(камера)` | `0xb15ae0` |
| `+0x1e0 + i × 0x40` | матрица «мир → место в атласе» = (матрица плитки) × `камера+0x1e0…0x21f`; для каскада 0 матрица плитки: масштаб (0.25, −0.25, 1), сдвиг (0.25, 0.25, 0) | `0xb15ae0` |
| `+0x2e0` | число каскадов, которое читает шейдер сведения: таблица `0x1f58d98` = (2, 3, 3) по качеству | `0xb16a50`, `0xb165a0` |
| `+0x2e8` | указатель на запись цели атласа (первое слово записи — хэндл текстуры) | `0xb16b90` |
| `+0x2f0` | качество теней 0…2 (`[[0x2bc0278]+0x50]`, обрезано до 2) | `0xb16a50` |
| `+0x2f8` | группа задач отбора (общая) | `0xb14f00` |
| `+0x300 + i × 8` | группа задач **отбора** каскада `i` (её ждёт отборщик `C`, §1.5) | `0xb14f00`, `0xb181e0` |
| `+0x320 + i × 8` | группа задач **постройки списка** каскада `i` (её ждёт исполнение) | `0xb14f00`, `0xb15020` |
| `+0x340` | `u16` размер плитки `T`: таблица `0x1f58d92` = (**1024, 768, 512**) по качеству 0 / 1 / 2 | `0xb16a50` |
| `+0x342` | число созданных стадий каскадов (3); `+0x343` — «атлас создан» | `0xb16780`, `0xb16a50` |

**Атлас** создаёт `0xb16b90(O)`: `O+0x2e8 = 0x912ca0(менеджер целей [[O+8]+0x20], имя [0x2bbbf48], формат 0x31, 2T, 2T, 0, 1)` —
именованная цель менеджера, размер **2T × 2T** (2048 / 1536 / 1024 — совпадает с NR-SHCACHE [лог]). При смене качества —
`0x912eb0(…, имя, 2T, 2T)` (та же именованная цель с новым размером; меняется ли при этом хэндл — не читалось). Плитки: каскад 0 —
(столбец 0, строка 0), каскад 1 — (0, 1), каскад 2 — (1, 0); окно вывода x = столбец × T, y = строка × T. Четвёртую плитку (1, 1)
движок не рисует (стадий три).

Имя `ShadowRenderStage::DirectionalLightShadowDepth` стадия каскада своей цели **не даёт**: его ставит позже `ShadowRenderStage`
(`0xac8d10`, пакет `0x37` с под-кодом 9) на тот же хэндл. В самом проходе каскада есть только пакет `0x16` с нулём цветовых целей.

### 1.5 Отбор объектов каскада [бин]
- Камера каскада — объект 0x4c0 байт, таблица `0x299b210` (`стадия+0x98`); отборщик `C` — объект 0x440 байт, таблица `0x299b2a0`
  (`стадия+0xa8`, конструктор `0xb18060`): `C+0x38` камера, `C+0x20` = функция-приёмник `0xb17ed0`, `C+0x50…` плоскости отсечения
  (по 0x10 байт, число в байте `C+0x190`), `C+0x191` номер каскада, `C+0x370` группа задач отбора, `C+0x380` очередь.
- Задача отбора — под-объект стадии `+0xd8` (таблица `0x299b168`, тело `0xb14e40`): очищает очередь `C`, копирует плоскости из
  `камера+0x400` (число `камера+0x4b0`), обходит сцену запросом с маской слоя каскада `(2, 4, 8, 0x10)[i]`.
- Приёмник `0xb17ed0(C, объект, набор шейдеров)`: берёт объект, только если `(u32 объект+0x1d8 & 0x80002) == 2` (бит 2 — «отбрасывает
  тень», бит `0x80000` — исключён), и дописывает запись `(объект, набор, 0)` в очередь без замков (счётчик атомарный, куски по
  `C+0x3c8` записей) — **отбор идёт в несколько потоков**.
- Метод 4 отборщика `0xb181e0(C, вид)` (его зовёт постройка списка, §1.2 шаг 6): `0x807b20([C+0x370], 1)` — **ждёт задачи отбора**,
  затем `0xa87980(C+0x380, C+0x400)` — склеивает куски в один массив `[C+0x408]`.

## 2. Пре-пасс: задача внутри `DeferredBufferStage`

### 2.1 Объект `DeferredBufferStage` (конструктор `0xb1bcf0`) [бин]
| Смещение | Что |
|---|---|
| `+0x00` | таблица `0x299b5b8` |
| `+0x18` | список команд стадии |
| `+0x70` | отборщик основной камеры `V` (второй аргумент конструктора) |
| `+0x78` | группа задач стадии (третий аргумент) |
| `+0x80` | задача постройки списка стадии, таблица `0x299b640` (тело `0xb1cf50`) |
| `+0x90` | **задача пре-пасса**, таблица `0x299b680` (`+0x90 + 0x10` = сама стадия) |
| `+0xa8` | **список команд пре-пасса** (второй список, куски по 0x4000) |
| `+0x100…0x120` | хэндлы целей G-буфера (5 штук: `HDRFullBuffer1`, `GBuffer1…3` и пятая) |
| `+0x140`, `+0x148 / +0x150` | шейдеры полноэкранных шагов стадии |

### 2.2 Метод задачи `0xb1be00(задача)` — постройка списка пре-пасса [бин]
`V = [[задача+0x10]+0x70]`, камера = `[[[задача+0x10]+0x10]+0x60]`.
1. сортировка двух очередей: `0xa88090(0, n − 1, V+0x5c0, камера)` и `0xa88090(0, n − 1, V+0x680, камера)`;
2. контекст: `+0` список пре-пасса (`задача+0x18` = `стадия+0xa8`), `+8` флаги = `0x40000`, `+0xc` маска = `0x20`, `+0x10` = `[стадия+0x10]`,
   `+0x18` стадия;
3. три цикла метода 23 по очередям: `[V+0x648]` (число `[V+0x650] >> 24`) **с конца**, `[V+0x708]` (число `[V+0x710] >> 24`) **с конца**,
   `[V+0x7c8]` (число `[V+0x7d0] >> 24`) **с начала**.

В этот список **не пишутся** ни цели, ни константы вида, ни очистка: только draw объектов.

### 2.3 Что вокруг него пишет стадия (метод 13 `0xb1c580`) [бин]
1. глубина кадра `D` = `[вид+0x10]+0x80` (или `+0x88`, если включён масштаб разрешения: `[[вид+0x10]+0x50]+0x2c ≠ 1.0`);
2. пакет 5 — очистка `D` (значение 1.0, трафарет: байт `+0x14` = 2);
3. пакет `0x16` — цели: 0 цветовых, глубина `D`;
4. `0xab50e0` (окно вывода на весь вид), полноэкранный draw 3 вершин шейдером `стадия+0x140` (в цель только глубины) — один draw, не объект сцены;
5. **пакет 2** `(+8 = стадия+0xa8, +0x10 = 0xac1f80, +0x18 = 1)` — при исполнении вызывает `0xac1f80(стадия+0xa8, 1)`:
   обход списка пре-пасса через `0x93e5f0` и его освобождение. **Вот здесь draw пре-пасса попадают в поток NVN**;
6. пакеты `0x637` (имена целей), пять пакетов 3 (очистка цветов G-буфера), пакет `0x16` — 4 цели + глубина `D`;
7. G-буфер: `0xa87cc0(V+0x800, контекст)` — флаги `1`, маска `8`; затем пакет `0x16` — 5 целей и `0xa87cc0(V+0xb40, контекст)`.

Константы вида основной камеры ставит раньше `0xab2250(вид, список)` (в нём пакет `0x17`) — один раз на стадию; пре-пасс и G-буфер
рисуются под одними и теми же константами вида.

### 2.4 Связь с G-буфером [бин] + [выв]
- Очереди разные: пре-пасс — `V+0x5c0`, `V+0x680`, `V+0x740` (три очереди); G-буфер — `V+0x800`, `V+0x8c0`, `V+0x980`, `V+0xa40`
  (первая четвёрка, 4 цели) и `V+0xb40…` (вторая четвёрка, 5 целей). Объект попадает в очередь при отборе (`0xb0fa40` / `0xb10c10`),
  один и тот же объект может стоять и в пре-пассе, и в G-буфере — **состав не обязан совпадать** [выв] (логи: 264 против 395 draw).
- Запись очереди одна и та же по виду: `+0` объект, `+8` набор шейдеров материала для этого прохода.
- Константа объекта (матрица мира) — та же функция и те же поля объекта в обоих проходах [бин]; параметры материала — те же массивы,
  но отфильтрованные маской прохода (`0x20` против `8`) в `0x90d050`.

## 3. Что известно про draw объекта в проходах глубины

### 3.1 Запись очереди и выбор состояния (`0x90cbf0` — обычный объект, `0xb7e020` — меш с экземплярами) [бин]
Запись очереди: `+0` объект, `+8` набор шейдеров `S` (у меша с экземплярами набор берётся из `объект+0x210`).
| Что | Откуда при `флаги & 0x40002` (каскад и пре-пасс) |
|---|---|
| программа | `S+0x30` (хэндл; обычный проход — `S+0x20`, при флаге `0x20000` или байте `S+0x11d` — `S+0x28`) |
| формат вершин | `S+0x48` (обычный — `S+0x38` / `S+0x40`) |
| смешивание | при `флаги & 0x8002` (каскад) — глобальное `[0x2bbdb70]` (номер 7 таблицы `0x2bbdb38`); иначе (пре-пасс) — `[0x2bbdb38 + 8 × байт S+0x50]` |
| растеризация | `[0x2bbdb88 + 8 × байт M+0x182]`, плюс число `M+0x184`; `M = [S+0]` — материал |
| глубина-трафарет | `[0x2bbdc18 + 8 × байт M+0x181]` |
| порог альфы | `float S+0x120` (только в проходах глубины; в остальных −1.0) |
| запрос видимости | **не ставится** при `флаги & 0x48002` (в каскаде и пре-пассе пакетов 61 / 62 нет) |
| буфер вершин | `меш+0x68`; второй поток — у обычного объекта `[объект+0x1c8]+0xa8` (и `+0xb0` или `+0xb8` по байту `+0xa0`), у меша с экземплярами `объект+0x2e0` |
| буфер индексов, тип | `меш+0x70`, байт `меш+0x78` |
Меш = `объект+0x1c0`. Всё это уходит одним пакетом 21 (0x70 байт, раскладка — `NR-NATIVE.md` §1.1).

После пакета 21: `объект->метод 26 (объект, список)` — матрица мира; `0x90d050(объект, запись, контекст)` — параметры материала по
маске прохода; затем draw.

### 3.2 Сам draw [бин] — **поправка к `NR-NATIVE.md` §1.1**
- меш без индексов (`меш+0x70 == 0`): пакет `0x23` `(+4 = 0, +8 = u32 меш+0x4c)` → `DrawArrays(примитив, 0, меш+0x4c)`;
- меш с индексами: пакет `0x24` `(+4 = 0, +8 = u32 меш+0x44, +0xc = 0, +0x10 = u32 меш+0x4c)` → `0x928e80` →
  `DrawElements(примитив r+0x1718, тип, **число = меш+0x44**, адрес = буфер индексов + размер индекса × первый)`;
- меш с экземплярами: пакет `0x25` `(0, число экземпляров объект+0x294, 0, меш+0x44, 0, меш+0x4c)` → `0x928fb0`.

То есть `меш+0x44` — **число индексов**, `меш+0x4c` — **число вершин** (в `NR-NATIVE.md` записано наоборот).

### 3.3 Константы вида: блок `B = [r+0x888]` [бин]
Обработчик пакета `0x17` (и прямой путь в стадиях) пишет: `B+0x80` матрица вида (0x40), `B+0xc0` матрица проекции (0x40),
`B+0x100` их произведение (считает `0x8e2970(выход, проекция, вид)`), `B+0x140` положение глаза (x, y, z, 1.0), `B+0x160` дальняя плоскость
(пакет `+0x10` = `камера+0x9c`), `B+0x164` ближняя (пакет `+0x94` = `камера+0x98`) — «дальняя / ближняя» [выв] по смыслу полей камеры. Пакет `0x1b` → `0x927310(r)` — применение блока.

### 3.4 Параметры материала и матрица объекта [бин]
- `0x90d050(объект, запись, контекст)`: `S = [запись+8]`; номер варианта шейдера в материале — `u32 S+0x1c` для проходов глубины
  (`S+0x14` обычный, `S+0x18` запасной); `u16 [M + вариант × 0x18 + 0x20]` — какие текстуры прохода нужны варианту (из контекста
  `+0x48…0x58`); далее массивы параметров материала, каждый параметр берётся, только если `u16 маска параметра & u16 контекст+0xc ≠ 0`.
- Метод 26 `0x90e280(объект, список)` → `0x940d80(список, имя, матрица)`: матрица **транспонируется**, имя ищется в хэш-таблице записи
  текущего шейдера (`[список+0x50]+0x40`), значение уходит **пакетом `0x1c`** (0x70 байт): `+8 / +0x10 / +0x18` указатели на описания параметра в записи шейдера для трёх стадий, `+0x20 / +0x22 / +0x24` слоты (`i16`, −1 — нет), `+0x28` длина 0x40, `+0x30` 64 байта матрицы; обработчик `0x924bb0(пакет+8, пакет+0x30, длина)`. У класса `0x29b7ca0`
  (скелетный) метод 26 = `0xc3c7a0`: та же матрица (или только `объект+0x90…`, если `объект+0x280` и режим скелета 1) плюс буфер
  костей (`объект+0x290` или `[объект+0x278]+8`).
- Классы со своим методом 23 (`0xb7e020`, `0xb89330`, `0xc6cc50`, `0xc7f590`, `0xc82c80`) проверяют те же биты `0x40002` / `0x8002`
  и берут те же поля набора — отличие проходов глубины у них то же (по условиям в коде; целиком читалось только тело `0xb7e020`).

## 4. Точки синхронизации [бин]
`0x807b20(группа, 1)` — ожидание группы задач: крутится (и сам исполняет задачи), пока в слове группы `+0` счётчик поставленных
(младшие 16 бит) не равен счётчику завершённых (старшие 16 бит).
| Что | Гарантия |
|---|---|
| отбор каскада `i` | задачи в группе `[O + 0x300 + i × 8]`; постройка списка ждёт её (`0xb181e0`) до сортировки и цикла draw |
| список команд каскада `i` | строится задачей `стадия+0x80` (таблица `0x299b128`, тело `0xb15610` = метод 13) в рабочем потоке, группа `[O + 0x320 + i × 8]`; исполнение `0xb15020` сначала ждёт эту группу |
| список `DeferredBufferStage` и список пре-пасса | метод 4 стадии `0xb1c4b0` ставит задачу `стадия+0x80` (таблица `0x299b640`, тело `0xb1cf50` = метод 13) в группу `[стадия+0x78]`; **метод 13 в самом начале ставит в ту же группу задачу пре-пасса `стадия+0x90`** и дальше строит свой список — два списка строятся одновременно в двух потоках; исполнение `0xb1c530` сначала ждёт группу `[стадия+0x78]`, значит оба списка готовы до первого пакета |
| порядок в потоке NVN | списки исполняются по одному, в порядке стадий; пре-пасс — внутри списка `DeferredBufferStage` (пакет 2) |
| кольцо констант, заборы NVN (`BeginFrame 0x9215f0`) | как в `NR-NATIVE.md` §2.4 — в этой сессии **не перечитывалось** [док] |

Следствия для исполнителя:
1. **Постройка списков — многопоточная** (три каскада, пре-пасс, G-буфер, отражения строятся одновременно). Крюк на методе 23 или на
   `AllocCommand` обязан брать проход из своего аргумента — контекста (`+8` флаги, `+0x18` стадия), а не из общего состояния.
2. **Исполнение — однопоточное и уже после всех ожиданий.** Крюк на исполнении видит готовые очереди `[C+0x408]`, `[V+0x648]`,
   `[V+0x708]`, `[V+0x7c8]`; следующая их очистка — в задачах отбора следующего кадра (`0xb14e40` для каскада). Что поток игры не
   меняет сами объекты и меши между постройкой и исполнением — [выв], кодом не проверено.
3. **Проход можно узнавать по месту исполнения, а не по целям**: каскад `i` исполняется внутри `0xb15020(стадия)` (таблица объекта
   `0x299b0a0`, `i = [стадия+0xb8] + 2 × [стадия+0xb0]`); пре-пасс — внутри `0xac1f80(список, 1)`, когда `список − 0xa8` — объект с
   таблицей `0x299b5b8`. Внимание: `0xac1f80` зовут и тени местных источников (`0xac1a80` — куб, 6 граней, `0xac1270`; `0xac35b0` —
   прожектор, `0xac2de0`), поэтому сверять таблицу владельца обязательно.

## 6. Не дочитано
- строка имени матрицы объекта `[0x2bbb798]` и имени цели атласа `[0x2bbbf48]` (глобальные строки, заполняются при запуске; в образе пусто);
- тела `0xb89330`, `0xc6cc50`, `0xc7f590`, `0xc82c80` (особые классы) в проходах глубины — прочитаны только условия;
- формат `0x31` менеджера целей (какой это формат NVN) и функции `0x912ca0` / `0x912eb0`;
- кольцо кадров и заборы NVN — см. `NR-NATIVE.md` §2.4, здесь не проверялось;
- что именно рисует полноэкранный draw перед пре-пассом (шейдер `стадия+0x140`);
- сортировка `0xa88090` (ключ порядка) — нужна, только если исполнитель будет строить порядок сам, а не идти по готовой очереди.

## 7. Как это читалось

`xr.py <адреса>` — кто зовёт / кто ссылается / в какой таблице методов стоит, `vt.py` — таблицы по записям перемещений). В дерево
не входят. Общий Ghidra с окном не трогался.
