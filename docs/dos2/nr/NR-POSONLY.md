# NR-POSONLY — компактный поток «только позиция» для depth-only draw (ночь 19.11.2026, ветка `dos2-ntrans`)

Задача координатора (следующий шаг после NR-MDI §7): у depth-only draw статических мешей (каскады теней, пре-пасс, пустые FS NR-33B)
брать позицию из плотной копии вместо перемеженного буфера вершин — те же байты и формат (бит в бит), конвейер с одной привязкой
(страйд = размер позиции), только когда VS доказуемо читает одну позицию; скиннинг исключён. Все копии — в одном буфере. Ключ
`DM_NR_POSONLY` (0 / 2 счёт / 1 применить), сброс копии по трекеру записи, память по NR-29. Телефона нет: ниже — логи, пак, хост-тесты. [м] = модель.

## 0. Коротко
- **Замер до кода (сессия хозяина play-1118, список конвейеров `vk-pipeline-list.bin` + лог тепла):** 460 depth-only конвейеров,
  57 вершинных шейдеров. Позиция — `R16G16B16_SFLOAT` (6 Б, 272 конвейера), `R32G32B32` (12 Б, 107), `R32G32` (8 Б, 81); страйды
  18 / 36 / 26 / 22 / 16. Второй вход почти везде — UV (`R16G16_SFLOAT` / `R32G32`) для альфа-теста; 67 конвейеров — скиннинг (веса +
  индексы костей, Location 14 / 15), 9 — инстанс-матрицы.
- **Доказательство VS** (`xbg_spirv_posonly`, консервативный проход зависимостей; тот же в Python `tools/dos2_posonly_check.py`):
  31 из 57 depth-VS — gl_Position зависит только от Location 0. Интерпретатор (`tools/spv_interp.py`, разные случайные значения всех
  прочих входов) ни разу не опроверг: **0 из 31**; по всему паку **1 844 из 6 132 VS** приняты, опровергнуто 0. C++ и Python совпали на
  всех 57.
- **Доля работы:** по вершинам depth-проходов из лога тепла — **69.8 % вершин подходят** (FS без kill → пустой двойник NR-33B + VS
  доказан). Скачиваемые байты вершин depth-проходов (верхняя оценка без кэша) **в 1.76 раза меньше**; у подходящих draw — в ≈ 3 раза
  (18 → 6, 36 → 12, 22 → 6 Б).
- **Ожидание GPU [м], Mi 14:** вершинная часть depth-проходов ≈ 1.9 мс в ходьбе с тенями (VERTEX.md m9: 0.26 нс на индекс; тени 1.46 +
  пре-пасс 0.48). Если 30–60 % её — трафик выборки, то **−0.25…−0.5 мс в ходьбе**, стоя −0.07…−0.15 (кэш теней). Слабые (LPDDR4X, Mali /
  Adreno 6xx): доля трафика больше → **−0.5…−1.5 мс**. CPU транслятора: +0.1…0.2 мс на кадр за решение на draw [м], копия — один проход
  по мешу при первой встрече.
- **Сделано:** `DM_NR_POSONLY=2` (счёт: подходящие draw, байты сейчас / с копиями, память копий рабочего набора) и `=1` (применить:
  копия, конвейер с одной привязкой, привязка в обоих путях — полосе NR-09 и старом `draw()`, сверка 1 из 64 использований). Умолчание 0.
  Хост-тесты: точность копии, арена с задержкой возврата, правило годности копии против **настоящих** сбоев записи (тест нашёл гонку,
  §3.3), C++ = Python на пакe. **На телефоне не запускалось.**
- **Попутно найдено:** та же гонка есть у статических копий NR-06 (на Mali / PowerVR, где zero-copy выключен, они включены по умолчанию):
  страница, которую `protect` пропустил как BUSY, остаётся записываемой без нового поколения → копия может устареть навсегда (§3.3).

| FS | VS доказан | доля вершин depth-проходов |
|---|---|---|
| без kill (NR-33B подменяет пустым двойником) | да | **69.1 %** |
| с kill (альфа-тест: нужен UV) | да / нет | 8.6 % / 14.8 % |

Итог: подходит 69.8 % вершин; байты выборки всех depth-вершин 1.76× меньше (без учёта кэша вершин — верхняя граница).

статистике инструкций шейдера.

## 2. Что сделано
### 2.1 Доказательство VS — `xbg_spirv_posonly.{h,cpp}` (C++ без Vulkan) и `tools/dos2_posonly_check.py` (Python, тот же проход)
Каждому id — маска Location-входов, от которых он может зависеть: через SSA-операнды (литералы `OpVectorShuffle` / `OpCompositeExtract`
/ `Insert` / `OpExtInst` пропускаются), через Function / Private переменные без учёта порядка (запись метит весь корень), каждое условие
ветвления / switch метит все выходы. Отказ: больше одной функции, вызов, запись в другой класс памяти, запись образа, атомики,
`OpCopyMemory`, нет встроенного выхода, нет неподвижной точки за 64 круга. Принято, если gl_Position и прочие встроенные выходы зависят
только от Location 0. Location-выходы не считаются: эти draw рисуются с FS, который ничего не читает. Считается при загрузке модуля
(`Shader::po`), только при `DM_NR_POSONLY ≠ 0`. Обрезка NR-32 и retype входов gl_Position не трогают.

### 2.2 Ядро — `dm/gfx/nr/nr_posonly.h` (чистый C)
`nrpo_fmt_size`, `nrpo_nverts`, `nrpo_gather` (байты атрибута каждой вершины подряд, ничего не конвертирует), арена: первая подходящая
дыра с задержкой возврата (освобождённый диапазон выдаётся снова только после `serial > freed + 3` — GPU мог ещё читать).

### 2.3 Бэкенд — `dm/gfx/vulkan/engine/xbg_nr_posonly.inc` (namespace `nrpo`)
- `decide()` в `draw()` прямо перед полосой NR-09 (план `nrpo::P` читают и полоса, и старый путь): depth-only (нет цветовых целей, есть
  глубина, не GPU-indirect / quads / сдвиг UI), только VS + FS, `fs->vo_read == 0` (двойник NR-33B / FS без входов), `vs->po == 1`,
  позиция — Location 0, известный размер формата с `VERTEX_BUFFER`, страйд больше позиции, ни один вход не инстансный, буфер — живой
  **статический** меш таблицы NR-06 (`nr_stab_find`, класс eligible), смещение привязки кратно страйду, нет ожидающей обратной записи.
- Копия на (меш, страйд, смещение позиции, размер): при первом использовании. Для пула, который трекер записи сторожит: штамп
  `nvn_dirty_now` → `protect` → сбор → жетон `nvn_dirty_version_tok` (Z1) — **жетон обязателен** (все страницы под защитой; иначе копия не
  берётся, собирается снова при следующем draw). Пулы `CPU_NO_ACCESS` пишет только бэкенд. Годность при следующих использованиях (раз за
  эпоху снапшотов): жетон держится → годна; иначе страницы не писались после штампа **и** все снова под защитой → новый жетон; иначе
  копия собирается заново (старый диапазон уходит в арену с задержкой). Запись бэкенда в меш (`snapshot_invalidate` → `nrbuf::cpu_write`)
  и смерть меша (`nr_stab_apply` / `drop_pool`) снимают копии сразу (хуки `nrbuf::po_write` / `po_gone`).
- Один буфер-арена, 32 МБ по умолчанию (`DM_NR_POSONLY_MB`), не больше доли статики NR-29 (`dm_nr_mem_cap(NRM_BUFSTATIC)`). Таблица
  статических мешей NR-06 включается и на Adreno (без копий NR-06), только при `DM_NR_POSONLY ≠ 0`.
- Старый путь `draw()`: для плана не берётся память конвейера по состоянию (`pipe_memo` / NB-13b — она отдала бы конвейер с одной
  привязкой следующему обычному draw), вершинный ввод переписан (`rewrite`: все непостоянные атрибуты на привязку позиции со смещением 0,
  одна привязка со страйдом = размер позиции; прочие входы мертвы по доказательству и читают первые байты копии — копия добита 16 Б), к
  привязке — диапазон копии. Конвейер различается по своему CreateInfo, warm-up список запоминает его как обычный.
- Полоса NR-09: бит варианта `NR_DRAW_VAR_PO` (свой конвейер в таблице), привязка позиции — копия; свёртка вершин NR-09 работает со
  страйдом копии.
- Сверка в `=1`: каждое 64-е использование копии собирает байты заново и сравнивает (красная строка и снятие копии при отличии).
- Строка раз в 10 с: `[nr] posonly (DM_NR_POSONLY=…, NR-POSONLY, last 10 s, F frames): draws …, depth-only …, fragment reads no varying …,
  vertex shader position-only …, position format / stride fit … = eligible (… M indices a frame: vertex bytes A MB now -> B MB with the
  copies, R x); not a static mesh …, unaligned …, untracked pool …, pending writeback …, arena full …; applied / would apply … a frame;
  copies N (… MB …), made … (not verified at the making …), dropped: backend write …, dirty pages …, mesh gone …; checks …, bad …`.

### 2.4 Переключатель
| `DM_NR_POSONLY` | |
|---|---|
| **0** | ничего: `draw()` — одна загрузка и непринятый переход (`P.on = false`), полоса — ещё одна; VS при загрузке не анализируется |
| 2 | счёт: классификация каждого draw, байты сейчас / с копиями, память копий, которые понадобились бы мешам окна; рисуется как 0 |
| 1 | применить (§2.3), сверка 1 из 64 |
Нужны `DM_NR=1`, `DM_NR_BUF=1` (умолчания DOS2). Приложение ключ не ставит. От GPU не зависит.

## 3. Проверки (ПК)
### 3.1 `tests/nr_posonly_test.cpp` (Windows clang++, C++17) — **8 006 проверок PASS**
Сбор против побайтовой модели (4 000 раскладок: размеры 4–16, страйды до +40, смещения), число вершин; арена против модели занятости
(≈ 3 500 выделений, живые не пересекаются, диапазон не выдаётся раньше задержки, освобождённые используются снова); на паке:
`xbg_spirv_posonly` на 57 depth-VS = вердикт Python на всех 57, ни одного «да» там, где интерпретатор видел движение gl_Position.
### 3.2 `tests/nr_posonly_inval_test.c` (WSL gcc, `nvn_dirty.c` как есть, настоящие `mprotect` и сбои записи) — **11 проверок PASS × 5 прогонов**
Без записи копия годна; запись в байт позиции / в другой байт вершины / запись хоста / запись в другой меш пула; гонка 2 с: 3 потока игры
пишут случайные байты 4 мешей (≈ 100 тыс. записей), читатель пользуется копиями по правилу: копия, отличная от байт игры, ни разу не
осталась годной к следующему использованию.
### 3.3 Гонка, которую нашёл тест (и которая есть у NR-06)
Первая версия правила (как у статических копий NR-06: штамп → protect → копия; потом «писали ли после штампа») давала 1 устаревшую
копию за прогон. Причина: `nvn_dirty_protect` пропускает страницу, которую в этот момент держит BUSY другой поток (сбой записи / запись
хоста). Если тот поток получил поколение раньше нашего штампа, страница остаётся записываемой с поколением ≤ штампа — запись в неё не
сбоит и `nvn_dirty_since` её никогда не увидит. Исправлено требованием жетона «все страницы под защитой» после сбора и при каждой
перепроверке. **NR-06 (`nrbuf::first_use`) делает «штамп → protect → копия» без такой проверки** — на Mali / PowerVR (там статические
копии включены, потому что zero-copy выключен) копия статического меша может навсегда устареть, если игра пишет в него в момент защиты.
Стоит перенести то же правило (отдельный шаг, не делался).
### 3.4 Прочее
`source_structure_test.py`: блок NR-POSONLY (план прямо перед полосой и сброс при выкл., нет памяти конвейера по состоянию для плана,
перепись ввода перед списком привязок, привязка копии в обоих путях, VS — при загрузке, FS без входов, правило годности как в тесте, хуки
NR-06, умолчание 0); блок NR-09 принимает строку плана перед полосой; всего 60 блоков PASS. `libdm.so` собрана NDK 29 без новых
предупреждений.

## 5. Риски и чего нет
- Решение на draw стоит CPU транслятора (+0.1…0.2 мс на кадр [м]); если P1 покажет мало подходящих draw — не включать.
- Копия, которая каждый раз «не проверена при создании» (меш, в который игра постоянно пишет), собирается на каждом draw — счётчик
  `not verified at the making` в строке; отката по числу неудач пока нет.
- Скиннинг исключён (нужны веса / индексы; предварительный скиннинг оценивает другой агент). Альфа-тест исключён (FS читает UV).
- `DM_NR_MDI` выигрывает от единого буфера: у подходящих draw все копии в одной арене (одна привязка вершин), но склейка их пока не
  использует.
