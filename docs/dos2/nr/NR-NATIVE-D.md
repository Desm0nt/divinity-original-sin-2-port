# NR-NATIVE, шаг D — карточка при постройке списка и запись draw своим рекордером (20.11.2026, ветка `dos2-nrn3d`)

Дополнение к `NR-NATIVE.md` (§2.6, §6 шаг D). База: `dos2-nrn3` (= `dos2` 88ba03e). Телефон не трогался; всё ниже — разбор `main.raw`
(обновление v786432, сборка 4979b200), логи серии N и хост-тесты. Пометки: **[бин]** — прочитано в двоичном файле в этой сессии,
**[лог]** — число из логов телефона, **[выв]** — вывод, не проверенный ни кодом, ни логом, **[м]** — модель, не замер.

## 0. Коротко
- **Половина a, `DM_NRN_LIST` — построена целиком** (умолчание 0; 2 сверка; 1 применение). Функции движка «нарисуй себя» (метод 23,
  семь тел) обёрнуты: обёртка кладёт в список команд **свой пакет-записку** перед группой пакетов объекта и, когда функция движка
  вернулась, заполняет его — проход из контекста, адрес пакета draw, два хэша группы. При исполнении списка записка даёт draw
  (1) **проход по контексту** (каскад i / пре-пасс / G-буфер), а не по именам целей; (2) **карточку без хэша кэша рендерера**: по
  цепочке «карточка прошлого draw + пакеты между ними». Карточка — то же самое слово, что в шаге B (все слоты текстур и сэмплеров
  в нём), таблицы строк и образы общие, гарантия образа не ослаблена.
- **Половина b, `DM_NRN_REC` — построены составитель записи, сверка байт в байт и замер по частям**; тела входов NVN (привязка блока
  констант, привязка текстуры, обход для плана проходов) для draw с карточкой **остаются** — §5 называет каждое действие этих тел и
  почему оно пока нужно. Без замера по частям на телефоне резать их вслепую нельзя: в эту сборку он встроен (`=2`).
- **Половина c (один пакет вместо группы, без обработчиков движка) — не начата**: что для неё прочитано и что осталось — §7.
- **Ветка `dos2-nrn4` (§12–§14): обе оставшиеся половины построены, умолчание 0, на телефоне не запускались.** `DM_NRN_NOBODY` — привязки draw с
  карточкой сворачиваются на стеке потока игры без тел входов NVN и без смены стека (сверка `=2`: свёртка на копиях против тел, слово в слово).
  `DM_NRN_PKT` — группа пакетов draw становится содержимым записки: для обходчика движка это один пакет; пакеты текстур и параметров внутри
  исполняют модели, сверенные с машинным кодом. Ожидание [м]: −0.6…1.0 и −0.3…0.6 мс потока игры на кадр; обе строки замера печатают нс до и после.
- Выигрыш потока игры от построенного [м]: −0.2…0.4 мс на кадр (карточка из цепочки), см. §6. Главный остаток по замеру серии N —
  1.78 мкс на draw в телах NVN и вокруг них (§5.1) — этим шагом не снят.

## 2. Половина a: записка в списке (`DM_NRN_LIST`)
### 2.1 Постройка списка (рабочие потоки движка; `dm/host/hle_dos2_nrn_d.inc`)
- Обёртка каждого из семи тел: если список контекста записывает пакеты (`список+0x30`), **до** вызова функции движка в список
  кладётся пакет кода `0x40` длиной 0x38 байт — самим `AllocCommand` движка. Поэтому записка живёт в памяти списка, освобождается
  вместе с ним, не нуждается ни в таблице, ни в замке; пишет её только поток, который строит этот список (один список — одна задача).
- После возврата функции обёртка проходит пакеты, которые та дописала (от байта после записки до курсора списка, через куски), и
  заполняет записку: флаги и маска контекста, строитель (каскад с номером / пре-пасс / G-буфер), объект, адрес пакета draw, число
  пакетов и два хэша — пакетов **до** draw (`lpre`) и **после** него (`lpost`). В хэш идут только поля, которые пишут сами функции
  движка, и только те, от которых зависит кэш рендерера (§1: поля пакетов 21, 15, 17, байт двухбайтных пакетов); значения параметров
  (пакет 28) не идут — они меняют только теневые блоки.
- Группа, в которой встретился пакет неизвестной длины, вложенная записка, два draw или draw без индексов, получает записку без
  отметки «целая» / «один draw»: такая записка даёт только проход.
- Проход: три крюка-скобки на строителях (`0xb15090`, `0xb1be00`, `0xb1c580`) держат в переменной потока, чей список строится;
  скобка сохраняется и возвращается (поток, ждущий группу задач, сам исполняет чужие задачи). Проход называется, только когда
  совпали флаги контекста и строитель: `2` + каскад → `SHADOW`, `0x40000` + пре-пасс → `PREPASS`, `1` + G-буфер → `GBUF`. Всё
  остальное (отражения `0x20002`, тени местных источников, прямые очереди) — «контекст не говорит», решают имена целей, как раньше.
  Указатель стадии из контекста (`+0x18`) **не разыменовывается**: у 2 308 мест вызова метода 23 он не обязан быть заполнен.

### 2.2 Исполнение списка (поток, исполняющий списки)
- Общий крюк `ExecuteRenderCommand` (`hle_dos2_native.c dn_rc_hook`) отдаёт пакет кода `0x40` обработчику записки **первой строкой**,
  до цепочки обработчиков и до функции движка: движок этот код не видит никогда. Обработчик регистрируется, только если крюк стоит;
  крюки на функциях «нарисуй себя» ставятся после него — записка не может оказаться в списке без того, кто её снимет.
- Каждый другой пакет проходит через одну строку в обработчике кода 55 (`nr_rc_pre`): счётчик «пакетов группы осталось» убывает, а
  пакет, пришедший вне группы с записью, **рвёт цепочку**.
- У прямого draw (`nrn_pre`, шаг B) записка берётся по **адресу пакета draw** — записка другого draw не подойдёт; проход берётся из
  неё; карточка — из цепочки.

### 2.3 Цепочка и почему её карточка верна
Карточка шага B — хэш байтов кэша рендерера (`r+0x16f0…0x1870` без бухгалтерских слов и четыре таблицы слотов). Кэш после группы
пакетов — функция кэша до неё и пакетов группы. Значит, карточка draw `n` — функция тройки
`(карточка draw n−1, lpost группы n−1, lpre группы n)`, **если между двумя draw не исполнялось ничего другого**. Память «ключ → карточка»
(32 768 строк, принадлежит исполняющему потоку) отвечает карточкой без чтения кэша; промах считает хэш кэша как раньше и учит память.
На чём это стоит и что это охраняет:
| Условие | Чем обеспечено |
|---|---|
| между draw исполнялись только пакеты двух групп с целыми записками | счётчик пакетов группы; любой пакет вне группы, смена списка, незаполненная или нецелая записка, draw без индексов, draw, для которого карточка не бралась (не прямой, проход выключен), — цепочка рвётся, следующая карточка считается из кэша |
| обработчики пакетов группы пишут байты карточки как функцию полей, вошедших в хэш, и самих этих байтов | пакет 21 — модель NR-09S (`nr_state.h`) [док]; пакет 15 — `0x9243d0` (§1) [бин]; пакеты 17, `0x3a`, `0x39` кэш не пишут [бин]; пакет 28 — только теневые блоки [бин]; запросы — только вызов NVN и слова условной отрисовки, которых карточка не читает [бин]. Что **описание текстуры** в записи шейдера (`+0`, `+1`, `+4`) не меняется после создания шейдера — [выв] |
| запись текстуры по тому же адресу — та же текстура | пакет 15 несёт адрес записи, а не хэндл: в ключ входит **счётчик созданий и уничтожений текстур** (крюки NR-01: `CreateTexture`, `CreateTextureFromImage`, текстуры окна, отложенное уничтожение). Любое такое событие меняет все ключи — память учится заново |
| всё вместе | `=2`: карточка каждого draw считается из кэша и сравнивается с ответом памяти — `BAD` и красная строка; `=1`: каждый 64-й ответ памяти так же проверяется, при расхождении память выключается до конца запуска (красная строка), карточки снова считаются из кэша |
Гарантия образа шага B («карточка решает каждый слот, который сброс текстур пересылает») не тронута: память возвращает **то же слово**
`nrn_card_of`, а не новую, более грубую карточку. Отдельной «карточки списка», заменяющей карточку кэша, нет: одного `lpre` для этого мало — он не
знает слотов, оставшихся от прежних материалов.

### 2.4 Переключатель, строки
| | |
|---|---|
| `DM_NRN_LIST=0` | умолчание (`xbg_nrn_list_default`): ни одного крюка, списки движка байт в байт прежние; `nrn_pre` платит одну загрузку |
| `=2` | сверка: записки пишутся и исполняются; карточка и проход каждого draw — прежние; ответ памяти и проход записки сравниваются |
| `=1` | применение: проход записки (когда контекст его называет), карточка из памяти при попадании; проверка 1 из 64 |
Нужны: проход `DM_NRN_<ПРОХОД>` на 1 или 2, `DM_NR_DIRECT=1`, общий крюк `ExecuteRenderCommand`. Ступень 2 безопасного режима гасит.
- старт: `[nr] native list (NR-NATIVE step D, DM_NRN_LIST=…): N of 10 hooks in …`;
- раз в 10 с: `[nr] native list (DM_NRN_LIST=…, step D, last 10 s): notes written … a frame (по телам; group not scanned to its end …,
  no single draw packet …), … ns a note on the building thread; executed …; direct draws that asked …, without a note …; pass named by
  the context … (same as the target names …, other …; note->targets: …); card: the chain held for …, the memo answered … (x %), taught …;
  compared … same … BAD …; ns a card: from the memo …, hashed …`;
- красные: `【红】[nr] native list: the chain of groups did not decide the card …`; несовпадение проходов — обычная строка (первые 16):
  проход по именам целей сам под вопросом (`NR-NATIVE.md` §8.1), строка называет оба.

## 3. Чего сверка `=2` ждёт от телефона
1. `BAD 0` — главное. Иначе в красной строке объект, флаги и число пакетов: какое условие §2.3 не выполнено.
2. `the memo answered … %` — доля draw без хэша кэша: от неё прямо зависит выигрыш. Стоя ждём ≥ 80 % [м]; на ходу меньше (порядок
   очереди меняется, загрузка текстур двигает счётчик — все ключи меняются).
3. `without a note` — draw классов, чьё тело метода 23 не обёрнуто, и draw вне очередей (свет, пост-цепочка): для них всё как раньше.
4. `note->targets` — таблица «проход по контексту → проход по именам целей»: проверка правила `nrn_pass_of` шага B (`SHADOW` и `GBUF`
   после исправления §8.1 ещё не видели телефона).
5. `ns a note` — цена на рабочих потоках (ждём 80–150 нс на draw [м]); `ns a card: from the memo` против `hashed` — выигрыш на draw.

## 4. Риски этой половины
- **Чужой пакет в списке движка** — и в сверке тоже. Проверено [бин]: обходчики идут через `0x93e5f0` (наш крюк стоит на его входе),
  освобождение пакеты не разбирает. Не проверено: нет ли кода, который сам читает пакеты списка мимо `0x93e5f0` (505 мест пишут
  пакеты; читающих не искали) — [выв]. Признак на телефоне: зависание или падение сразу при входе в уровень с `DM_NRN_LIST=2`.
  Поэтому прогон сверки шага D идёт **после** прогонов серии C шага B, отдельным запуском.
- Память списка: +0x38…0x40 байт на draw (≈ 90 КБ на кадр при 1 500 draw).
- Тела `0xb89330`, `0xb87470`, `0xc6cc50`, `0xc7f590`, `0xc82c80` целиком не читались: обёртка берёт у них только третий аргумент
  (контекст) — по первым инструкциям все читают `[x2]` и `[x2,#8]` [бин]. Что они пишут в список, разбирает проход по пакетам; чего он
  не знает — записка остаётся нецелой, draw идёт прежним путём.

## 5. Половина b: запись draw без тел NVN (`DM_NRN_REC`)
### 5.1 Где время потока игры на прямом draw [лог] (N_p0, Mi 14 Ultra, 1 500 прямых draw на кадр, 1 из 64 с часами)
2 858 нс на draw = блоки констант (модель NR-09U) 831 + идентичность 152 + **сброс и запись 1 875**, внутри последнего: обход для плана
проходов 441, блок состояния 91, запись draw 454, **привязки сброса и смена стека 889** (сюда же попадают 4.1 вызова тела привязки
блока констант). Короткая запись шага B убирает блок состояния и запись привязок текстур в тень; остальное остаётся.

### 5.2 Каждое действие тел NVN у прямого draw и что с ним

|---|---|---|

Итог честно: `DM_NRN_REC=1` сам по себе снимает десятки наносекунд на draw. Сотни сидят в трёх строках «остаётся» с жирным шрифтом —
таблицы плана проходов и два зеркала. Их можно не вести для draw с карточкой только вместе с доказательством, что следующий читатель
(обход draw без карточки, фильтр привязок) получит таблицы целыми — то есть с отложенным восстановлением таблиц из кэша движка. Это
отдельная работа (§8); какую из трёх строк резать первой, скажет замер по частям.

### 5.3 Что построено
- **Составитель** `nrnd_rec_put` (чистый C): пишет полезную часть записи `OP_X_NB_DRAW` с идентичностью NR-09, словом NR-09R,
  хвостом карточки и списком опущенного короткой записи. Хост-тест держит его против функций половины NVN — байт в байт.
- **`DM_NRN_REC=2`**: запись пишется старыми функциями, затем составляется рядом из тех же значений и сравнивается байт в байт
  (`DIFFER`, красная строка с номером первого отличного байта). Плюс часы на частях вызова на большом стеке (1 draw из 64): смена
  стека туда, тела привязок блоков констант, привязки текстур сброса, draw (план проходов + запись), смена стека обратно.
- **`DM_NRN_REC=1`**: полезную часть записи draw с карточкой пишет составитель. Всё вокруг — код рекордера в его порядке.
- Строка: `[nr] native rec (DM_NRN_REC=…, step D, last 10 s): records of card draws composed directly … a frame; verify: … compared
  byte for byte …, DIFFER …; the big-stack call of a direct draw by part, ns: onto the big stack …, the uniform-buffer bodies …,
  the texture binds of the flush …, the draw (tap + record) …, back …`.
- Сам выключается при `DM_NR_Z5` (он дописывает слова в уже написанную запись). Ступень 2 безопасного режима гасит.

## 12. Половина b, продолжение: привязки draw с карточкой без тел NVN — `DM_NRN_NOBODY` (20.11, ветка `dos2-nrn4`, коммит `09a1fa1`)
### 12.1 Что именно делают тела, когда draw с карточкой идёт прямым путём [код]
§5.2 называл три «жирные» строки (таблицы плана проходов и два зеркала) причиной, по которой тела нельзя не звать. Разбор тел по строкам
показал: при условиях, которые у прямого draw выполняются почти всегда, тело привязки делает **только** перечисленное ниже и ничего
больше — ни записи в поток команд, ни вызова кода игры:
| Тело | Действия при этих условиях |
|---|---|
| `nvnCommandBufferBindUniformBuffer` (≈ 1.9 раза на draw) | зеркало таблицы блоков бэкенда (`nrub_bind`: диапазон, который бэкенд уже держит, не шлётся), счётчик плана проходов, привязка в тень draw |
| `nvnDeviceGetTextureHandle` + `bind_handles` (≈ 1.15 раза) | таблица / маска «менялось» / подпись плана проходов (`nbt_bind`, `NRD_SIG`), зеркало таблиц привязок (`nrdm_bind`: то, что бэкенд держит, не шлётся и считается в слово записи), поколение набора текстур, маска опущенного короткой записи, привязка в тень, отметка использования текстуры |
Условия (`nvn_nrn_b.inc nrnb_can`, только чтение, решение **до** первой записи): прямой draw внутри скобки NB-09 без режимов сверки других
шагов; тень draw пуста; план проходов уже следит за этим буфером команд; оба зеркала принадлежат этому потоку и этой записи; привязки в
пределах таблиц бэкенда; в памяти команд есть 16 КБ. Со стороны потока игры (`hle_dos2_nrn_b.inc nrnb_front`): у draw есть карточка и
идентичность, сброс текстур и блоки констант посчитаны нашими моделями (NR-23, NR-09U), `SetRenderEnable` не нужен.

### 12.2 Что построено
- **Свёртка** `nrnb_fold`: те же шаги для всех привязок draw одним циклом **на стеке вызывающего** — без смены стека и без тел. Сам draw
  (обход плана проходов `nbt_draw`, запись `nbd_draw`, `rec` / `cmd_alloc`) — прежний код рекордера, вызывается сразу за свёрткой на том
  же стеке: всё, что читают следующие draw, пишут те же функции, что и раньше, или свёртка, сверенная с телами слово в слово.
- **Что из §5.2 осталось телом** (и почему): обход плана проходов и запись — это рекордер, а не «тело входа», их результат зависит от
  таблиц, которые ведёт вся остальная запись кадра; `SetRenderEnable` после отброшенного draw (редко) — draw с ним идёт старым путём;
  блок состояния перед записью (`NBS_BEFORE`) и ожидающие записи состояния — внутри `cmd_alloc`, не тронуты.
- `DM_NRN_NOBODY=0` — умолчание (`xbg_nrn_nobody_default`), одна загрузка в `nrd_draw_take`; ступень 2 безопасного режима гасит.
- `=2` сверка: тела исполняются как раньше; перед первым телом берутся копии состояния, после последней привязки свёртка исполняется
  **на копиях** и сравнивается с тем, что оставили тела: оба зеркала, таблица / маски / подпись плана проходов, тень draw и её буфер
  команд, маска короткой записи, счётчик неотправленных привязок, отметки использования по порядку, поколение набора текстур.
  Расхождение — `BAD` и красная строка `【红】[nr] native nobody: the fold is not what the NVN bodies left - …` с названием слова.
- `=1` применение: свёртка вместо тел. Каждый 8-й замеренный draw (1 из 512) нарочно идёт через тела — мерило для строки замера; оба
  пути оставляют одно и то же состояние, поэтому смешивать их можно.
- Строки раз в 10 с: `[nr] native nobody (DM_NRN_NOBODY=…)` — сколько draw взято, сколько осталось на телах и почему (по каждой
  причине), сверка (сравнено / BAD); `[nr] native nobody, game-thread ns a card draw` — **нс потока игры на draw с карточкой без тел и
  через тела, разница в нс и в мс на кадр**.

### 12.3 На чём стоит и чего не доказывает хост
- Свёртка повторяет тела руками, поэтому тест компилирует **сам текст тел** из исходников (`tools/dos2_nrnb_bodies.py` вырезает 44 куска
  из `hle_nvn.c`, `nvn_nb_tap.inc`, `nvn_nb_draw.inc`, `nvn_nr_direct.inc`), а `source_structure_test.py` держит хэши 13 главных кусков:
  правка тела без пересмотра свёртки роняет тест.
- Исполнение рекордера на стеке игры: `cmd_alloc` может позвать код игры за памятью команд — такой draw свёртка не берёт (запас 16 КБ).
  Глубина стека самого рекордера на стеке потока игры на телефоне не мерилась — **[выв]**, признак беды: падение в `nvn_nrd_draw` сразу
  при `=1`. Поэтому `=1` запускать только после `=2`.
- Один вызов `dm_nb_frame()` в условиях на потоке, который не поток рендера, считается счётчиком строки `[nb]` (тела позвали бы его
  столько раз, сколько привязок) — единственное известное отличие, не состояние.

## 13. Половина c: один пакет вместо группы — `DM_NRN_PKT` (20.11, ветка `dos2-nrn4`, коммит `13eb8d0`)
### 13.1 Что прочитано [бин]
| Что | Факт |
|---|---|
| Обходчик списка `0xa49c30` | **единственное место вызова** `ExecuteRenderCommand 0x93e5f0` во всём коде (одна инструкция `bl` по адресу `0xa49cb0`; указателей на функцию в данных нет); `0xac1f80` — переходник на него, 13 хвостовых переходов и 6 вызовов ведут туда же. Берёт у куска **число пакетов** (`+0x10`), на каждый пакет — байт выравнивания, пакет на следующей границе, сдвиг на длину, которую вернул обработчик; в конце куска — следующий кусок. Это закрывает риск §4 наполовину: исполняет пакеты только он (читателей «мимо» по-прежнему не искали) |
| Пакет `0x0f`, обработчик `0x9243d0(r, пакет+8)` | номер текстуры `[[запись]+0xc0]` или вида; номер сэмплера из описания, при отрицательном — `[запись+0x100]`, при отрицательном — общий (таблица `r+0x540` / `r+0x550`, номер = слово `main+0x2bbda90`); на каждую стадию со слотом ≥ 0 — таблица текстур, затем сэмплеров: другое значение записывается, грязный диапазон (мин `+0x84`, макс `+0x85`) расширяется |
| Пакет `0x1c`, обработчик `0x924bb0(пакет+8, пакет+0x30, длина)` | на каждую из трёх стадий (блок `пакет+8 / +0x10 / +0x18`, смещение u16 `+0x20 / +0x22 / +0x24`, `0xffff` — нет): `блок+0x28` = max(было, смещение + длина); если байты по `[блок+0x20] + смещение` отличаются от значений — `блок+0x34` = 1 и копия |
| Пакеты `0x39`, `0x3a`, `0x11` | только длина (2 / 2 / 0x18); у `0x11` вызов `0x801dd0` над нулевой локальной — ничего не пишет (эмулятор: ни одной записи вне стека) |
| «Особые тела» метода 23 | модели не понадобились: группу по-прежнему пишет функция движка, мы меняем только то, как она исполняется (§13.2); какие пакеты пишет тело, разбирает проход по группе, неизвестное — группа остаётся как есть |

### 13.2 Что построено
- **Слияние при постройке** (`hle_dos2_nrn_c.inc nrnk_built`, рабочий поток, сразу после прохода по группе): если все длины группы
  известны, группа целиком лежит в куске записки и число пакетов куска выросло ровно на группу — число пакетов куска уменьшается на
  группу, записка получает флаг `NRND_F_ONE`. Для обходчика движка теперь это **один пакет**: записка, чья длина покрывает группу.
  Память списка байт в байт та же, копий нет; пишется только память своего списка.
- **Исполнение**: обработчик записки сам проходит пакеты группы (`nr_pkt.h nrpk_group_run`: байт выравнивания + длина, которую вернул
  обработчик) и на каждый зовёт `dn_rc_inner` — то же, что крюк делает для пакета от обходчика: все зарегистрированные обработчики до
  и после, родной пакет 21 (NR-09S), функции draw. Не исполняется только поездка «обходчик → ворота → крюк» на каждый пакет.
- **Модели** (`nr_pkt.h`): внутри слитой группы пакеты `0x0f`, `0x1c`, `0x11`, `0x39`, `0x3a` исполняет наш код, а не обработчики
  движка. Вне слитой группы — движок, как раньше (в том числе в группах-мерилах).
- `DM_NRN_PKT=0` — умолчание (`xbg_nrn_pkt_default`); нужен `DM_NRN_LIST` 1 или 2; код обработчиков и обходчика сверяется хэшем при
  установке (другой код — ключ выключен); ступень 2 безопасного режима гасит.
- `=2` сверка, ничего не исполняется иначе: (1) постройка считает, какие группы слились бы; (2) записка сама проходит свою группу, и
  пакеты, которые затем приносит обходчик движка, обязаны быть теми же по тем же адресам, последний — кончаться там, где кончился бы
  слитый пакет (`walk BAD`); (3) на каждом пакете `0x0f / 0x1c / 0x11 / 0x39 / 0x3a` модель составляет **журнал** того, что записала
  бы, затем исполняется обработчик движка, и каждый байт журнала обязан совпасть с памятью, а длина — с возвращённой (`model BAD`).
  Это и есть сравнение «состояние движка после нашего пакета = после исходной группы», пакет за пакетом.
- `=1` применение; каждая 16-я группа остаётся неслитой — мерило.
- Строки: `[nr] native pkt (DM_NRN_PKT=…)` — слито / не слито и почему, исполнено, сверки; `[nr] native pkt, game-thread ns a draw's
  group` — **нс потока игры на группу одним пакетом и пакет за пакетом** (от записки до первого пакета после группы, draw внутри).

### 13.3 Риски
- Кто-то читает или дописывает пакеты списка, опираясь на число пакетов куска, мимо обходчика — не найдено и не искалось по всем 505
  местам записи: **[выв]**. Признак: зависание или мусор сразу при `=1`; `=2` этого не ловит (он ничего не меняет).
- Список исполняется повторно (статические списки) — слияние постоянно, флаг и число пакетов согласованы: годится.
- Модели сверены с машинным кодом в эмуляторе, но на телефоне `=2` не шёл.

### 13.4 Экономия [м]
5–8 пакетов на draw × (ворота 37 нс [лог] + пролог крюка + обработчик движка вместо модели ≈ 20–40 нс) ≈ 0.25–0.5 мкс на draw →
**−0.3…0.6 мс потока игры на кадр**; на рабочих потоках +5–10 нс на draw. Транслятор — 0.
