# NR-10 `DM_NR_RP` — проходы и барьеры (сегмент S6)

Ветка `dos2-nr10` (worktree `wt-nr10`, база `dos2` 94d287d). На телефоне **не запускалось** (ни один режим). Умолчание 0 везде,
кроме тайлеров Mali / PowerVR — там 1 с ветки `dos2-nrp0` (аудит P0, §9).
Источники чисел: логи Mi 14 Ultra 17.11 `rd2` (умолчания, палуба корабля), `ab7rp3` 16.11 (`DM_NB=1 DM_NB_RP=3 DM_GFX_SIM_GPU=mali`),
дампы IR `ra1 / rb1 / rc1-dumps`. Тяжёлых сцен (бой, город) в логах нет — всё ниже про палубу и 3D-меню.

## 2. Что сделано

**Точки видимости прохода** (`dm/gfx/nr/nr_rp.h`, чистый C; `namespace nrrp` в `xbg_game.cpp`):
- Проход, начатый «чисто» (у каждого вложения прошлая запись уже видима и нет незакрытой storage-записи — `nr_rp_clean`), в момент
  `vkCmdEndRenderPass` ставит своим вложениям точку `Image::nrvis_frag` (всегда) и `nrvis_full` (если зависимость ждёт в
  `ALL_COMMANDS`, т. е. без политики тайлеров): «записи до `last_write` видимы». Условие чистоты закрывает дыру «зависимость говорит
  только о привязанном subresource» (другой мип / слой, записанный до прохода и не закрытый барьером).
- `prepare_read`: барьер нужен, только если `last_write` дальше `max(глобальная точка, точка операции NB-08, точка прохода)`.
  Чтение вложения ещё открытого прошлого прохода закрывает проход — и больше ничего. `storage_write` точкой прохода не покрывается.
- Барьер перед проходом IR (`nbrp::prebar`): по картинкам списка чтений заголовка, по одной (`nr_rp_prebar`). Нет записанных —
  барьера нет. Список неполон (`read_over`) или висит storage-запись буфера — прежнее правило.
- **По семействам.** Без политики тайлеров (Adreno): точки для всех стадий → барьеров между проходами не остаётся. С
  `DM_GFX_TILE_BARRIER` (Mali / PowerVR): точки только для фрагментных стадий; барьер перед проходом — **фрагментный**, если первый
  draw прохода читает только во фрагментной стадии; чтение записанной картинки вершинной стадией получает полный барьер как раньше,
  а проход, который такое чтение порвало, запоминается (`need_full`, по framebuffer) и дальше получает полный барьер заранее.
- Флаги depth-feedback (`dirty_begin`) при 1 / 3 считаются по тем же точкам (иначе без барьеров они всегда были бы «грязными»).
- `hitfast` (NB-12) видит тот же `last_write`, что `prepare_read`.

**«Свежие» вложения** (счёт всегда при `DM_NR_RP≠0`, применение отдельно): цветное вложение, в чью гостевую память с его последней
записи рисовали **другую** текстуру (`Image::nr_clob`; список соседей по памяти кэшируется до перестройки индекса картинок). На Switch
там лежат байты той текстуры — старое содержимое пропало, значит load может быть `DONT_CARE` без доказательства покрытия.
Сбрасывается любой записью самой картинки (проход, `Image::transition` = копия / clear / загрузка, storage-запись); посадка
отложенного clear перед проходом отменяет маску. Только цвет: у глубины UI (serial 11) и сцены (12) общий формат, и stencil UI на
Switch может «работать» на нулях сцены — туда не лезем.

### Переключатели
| | |
|---|---|
| `DM_NR_RP=0` (умолчание Adreno / Xclipse / Maleoon / неизвестных; Mali / PowerVR — 1, см. §9) | прежний поток команд: все ветки за `nrrp::mode` / `nrrp::apply()`; добавлены только безусловные присваивания полей (`nr_clob=false` в `transition` / `mark_storage_images`, `frag_first` в `descriptors`, `++alias_gen` в перестройке индекса) |
| `=1` | точки видимости решают барьеры чтения и барьер перед проходом; свежие вложения считаются; с `DM_NR_RP_FRESH=1` — начинаются с load `DONT_CARE` (только проходы плана NB, `nbrp_begin`) |
| `=2` | исполняются старые барьеры; точки ведутся, тень `nr_sh_b / nr_sh_f` идёт за `barrier_seq / frag_seq` режима 1; каждое чтение и каждый PREBAR раскладываются: оставлен / снят / полный → фрагментный / «узкий путь поставил бы барьер позже». Красная строка `【红】[nr] rp check: …` (первые 16) — узкий PREBAR хочет больше исполненного (не ожидается) |
| `=3` | 1 + свежие вложения применяются **и заливаются пурпуром** сразу после begin (`nbrp::poison_load`) |
| `DM_NR_RP_FRESH=0/1` | только с `=1`; умолчание `xbg_nr_rp_fresh_default`: **1 на Mali / PowerVR с 19.11** (§10, после poison `D_rp3`), 0 на остальных (Adreno никогда: на sysmem load бесплатен) |

Строка раз в 10 с (с подачи): `[nr] rp DM_NR_RP=N (…): F frames; a frame: host passes ended clean X, not clean Y; read barriers …;
barrier before an IR pass: none / fragment / full …; fresh colour attachments A = M MB of loads a frame …; tile: passes split by a
pre-fragment read …`. При старте: `[nr] rp DM_NR_RP=N: …`.

## 5. Что не сделано и почему
1. **Покрытие первым draw (главный рычаг тайлеров).** `first_draw_covers` требует VS «позиция = вход»; у транслированных VS DOS2
   позиция вычисляется (Iggy — матрица, пост — судя по всему масштаб + сдвиг и поправка z). Нужно: доказательство для аффинной
   позиции (вычислить выражение на CPU по входам и константам UBO — они известны в момент draw; офлайн-интерпретатор
   `tools/spv_interp.py` уже есть), плюс render area = прямоугольник DRS при масштабе < 100 %. Тогда `cover_dc` плана заработает:
   ≈ 8 полноэкранных проходов поста × 8.4 МБ + цепочка bloom ≈ 70–90 МБ load на кадр на палубе. Отдельный шаг (S1 + S6), 4–6 ч.
2. **Точные раскладки (не `GENERAL`).** Turnip раскладку не использует — выигрыш 0. У Mali от раскладки зависит transaction
   elimination (по документации Arm подписи тайлов живут только в «безопасных» раскладках: `COLOR_ATTACHMENT_OPTIMAL`,
   `SHADER_READ_ONLY_OPTIMAL`, `TRANSFER_SRC`, `PRESENT_SRC`; `GENERAL` — нет) — это пропуск записи неизменившихся тайлов, для
   статичных UI и камеры потенциально заметно. Но цена: раскладка по subresource вместо одной на `Image`, раскладка в каждой
   записи дескриптора (сейчас везде `GENERAL`, мемо наборов), ~40 мест `layout!=GENERAL → transition`, копии / present / дампы /
   NB-POST. Ссылочная раскладка `COLOR_ATTACHMENT_OPTIMAL` только внутри прохода (initial = final = `GENERAL`) TE не включает
   (переход из небезопасной раскладки сбрасывает подписи). Без устройства Mali выигрыш не измерить → не делалось; сначала нужен
   замер на живом Mali (счётчики драйвера / fps) на тестовой сборке, потом решение.
3. **Идентичность вложений по хэндлу в IR.** Планировщик ведёт картинки по адресу памяти и склеивает текстуры общего пула. Правильно —
   ключ (адрес, serial NVN-текстуры = хэндл движка) в `p_nb_pass` / тапе / `nb_plan.c`; это правка фронта и формата записей
   (их держит цепочка NB). Здесь сделана дешёвая часть на стороне бэкенда (свежие вложения). Реестр NR-01 (`DM_NR`) для этого не
   нужен: `tex_t::serial` и есть объект движка; флаг пула `0x2000` пригодился бы как второе подтверждение.
4. **Проходы UI в плане** (14 на кадр, DS снят NB-18b-6): план дал бы те же решения — не делалось.
5. **`dep[0]`** (вход прохода ждёт `ALL_COMMANDS / MEMORY_WRITE`) не сужался: меняет ключ render pass, а значит пересборку всех
   пайплайнов. Если A/B на Mi 14 покажет, что барьеры вообще что-то стоят, это следующий кандидат.
6. Проходы, открытые путём clear (не `draw()`), точек не ставят — их читатели получают барьер как раньше (счётчик `not clean`).
7. Правило свежести строго доказано только для байтов, которые покрыла другая текстура: маленькая текстура затирает угол большой.
   Опора — контракт пула движка (взятый из пула RT содержимого не имеет) и то, что иначе на Switch был бы мусор в углу. Поэтому
   отдельный переключатель и poison.

## 6. Риски
1. Явные барьеры могли прикрывать ошибку драйвера или хоста (синхронизация, которой никто не заказывал). `=1` против `=0` — сверка
   картинки (`DM_GFX_PASS_VALUES` / `debug_dump_frame`), не только fps.
2. Точка верна, пока у каждого варианта прохода есть `dep[1]` (сейчас: `create_pass`, `lazy_twin`, noload-twin). Новый путь создания
   прохода без неё сломает допущение — проверка в `source_structure_test.py` этого не ловит.
3. Тайлеры: проход с фрагментным первым draw и вершинным чтением записанной картинки позже рвётся один раз (потом `need_full`);
   счётчик в строке. Набор `need_full` по хэндлу framebuffer (до 4096), переиспользование хэндла даёт лишний полный барьер, не ошибку.
4. `=2`: тень точна, пока оба мира рвут проходы одинаково (см. тест); цифры «barriers saved» — оценка с этой оговоркой.
5. Свежие вложения — п. 5.7; при `=3` пурпур на экране = правило неверно для этой сцены.
6. Стоимость при `≠0`: `nrrp_fresh` на каждый открываемый проход (список соседей кэширован), `nrrp_read` на каждое чтение — десятки нс.

## 8. Прогоны телефона (Mi 14 Ultra; бэкап `files/save`, проверить keyguard, force-stop после логов)
Сцены: палуба корабля **и** тяжёлая (бой / Форт Радости / город), по 60 с; `DM_DOS2_FPS=0`.
1. **Счёт:** `DM_NR_RP=2`. Строки: `[nr] rp DM_NR_RP=2: old barriers executed…` при старте; раз в 10 с
   `[nr] rp DM_NR_RP=2 (check…; tile barrier 0)`: жду `read barriers executed ≈ 26, the narrow path keeps ≈ 0–3`,
   `barrier before an IR pass: executed ≈ 38 of 38, narrow none ≈ 36+ / fragment 0 / full ≤ 2`, `barriers saved ≈ 60 a frame`,
   `recorded later instead ≈ 0`, `never expected 0`, красных `【红】[nr]` нет; `fresh colour attachments A = M MB` — записать число.
2. **Счёт под тайлерами:** `DM_NR_RP=2 DM_GFX_SIM_GPU=mali`: `tile barrier 1`, `narrow none / fragment / full`,
   `passes split by a pre-fragment read` → ≈ 0 после первых секунд.
3. **A/B:** `DM_NR_RP=1` против `0`, ABBA ×2: `NVN PERF … barriers op25` 65 → < 5; `[nb] rp … prebar: … nothing to wait for` ≈ все;
   `[nb] check: split` 0 и `pass_ends` не больше прежнего; картинка та же; `gpu_ms` / fps.
4. **Poison свежих:** `DM_NR_RP=3 DM_GFX_SIM_GPU=mali` — палуба, меню, инвентарь, карта, тяжёлая сцена: **нет пурпура**;
   `fresh … begun with load DONT_CARE X, poisoned X`. Чисто → `DM_NR_RP_FRESH` кандидат в умолчания тайлеров.
5. Настоящий Mali / PowerVR — только тестовая сборка игрокам (умолчание по детекту, строка `[nr] rp` в логе).

## 9. Умолчания (аудит P0, ветка `dos2-nrp0`)

`xbg_nr_rp_default(f) = xbg_tile_family(f) ? 1 : 0` — **Mali и PowerVR: 1**, Adreno / Xclipse / Maleoon / неизвестные: 0.
`DM_NR_RP_FRESH` — 0 везде (как было), `DM_NR_COVER` (NR-10b) — 0 везде (не тронут). `dm/env` `DM_NR_RP=0` по-прежнему выключает.

Почему так (а не «1 всем», как обещал комментарий шага):
- **Это починка регресса, а не новый выигрыш.** С 852c6ec `jni_android.c` ставит `DM_NB_RP=1` всем семействам, а PREBAR (`NB_NP_PREBAR`)
  ставит полный барьер перед каждым проходом IR — под политикой тайлеров это отменило `DM_GFX_TILE_BARRIER` (`ab7rp3`, SIM mali: 31
  фрагментный барьер чтения + **43 полных** перед проходами на кадр). Т. е. игроки 0.1.1 на Mali / PowerVR получили binning, ждущий
  fragment прошлого прохода (FN-32: на Mali это было −13 % кадра). С `DM_NR_RP=1` барьер перед проходом — нет / фрагментный.
- **Набор семейств = набор `DM_GFX_TILE_BARRIER`** (`xbg_tile_barrier_default` = `xbg_tile_family`). Только там PREBAR что-то отменил.
  Xclipse (RDNA, не тайлер) и Maleoon политики тайлеров не имеют: у них барьеры и до NB-RP были полными — регресса нет, выигрыш только
  в числе барьеров, как у Adreno → решать по A/B, не здесь (аудит §2 п. 9: комментарий `xbg_nr_cover_default` называет Xclipse, а
  `xbg_tile_family` — нет; здесь набор назван явно).
- **Adreno — 0** до A/B D5 (на Turnip sysmem полные барьеры −60/кадр — оценка, не замер; там регресса нет).
- **Предпосылок нет.** Шаг целиком в бэкенде: ни `DM_NR` (NR-01), ни `DM_NB_RP` не нужны. Без `DM_NB_RP` (dm/env `=0`) остаётся только
  сужение барьеров чтения (`prepare_read`) — оно от NB не зависит. `DM_NB_OPBARRIER=1` (JNI) учитывается (`seen_full / seen_frag` через
  `nb_ob_seen`). NR-10b (`DM_NR_COVER`) от NR-10 не зависит и остаётся 0; при её включении позже решения load NR-10b и барьеры NR-10
  независимы (покрытие меняет load op, не видимость).
- Строка старта теперь говорит, откуда значение: `[nr] rp DM_NR_RP=1 (family default, policy family mali): …` / `(env, …)`.

Проверки: `vendor_policy_test` — 1 ровно там, где `xbg_tile_barrier_default`; Mali / PowerVR = 1; Adreno / Xclipse / Maleoon / other = 0;
SIM: `mali`, `family-mali`, `powervr` на Adreno → 1, `xclipse` / без SIM → 0; FRESH 0 под SIM mali. Мутация (умолчание обратно 0) —
7 провалов. `source_structure_test.py` (строка умолчания), NDK 29 `-fsyntax-only` `xbg_game.cpp` rc 0, 13 предупреждений (как база).

Риск: `DM_NR_RP=1` на телефоне не исполнялся ни разу (модель / оракул: unsound 0). Отдельно (нашёл при разборе P0, в §6 п. 3 не
было): фрагментный PREBAR решается по **первому** draw (`frag_first`), а PREBAR стоит как раз у проходов, где чтение до-проходной записи
идёт в draw 2+. Если такой draw читает в VS (текстура / texel-буфер в вершинной стадии) — полный барьер посреди прохода, разрыв, и
первый кусок уже закрыт store `DONT_CARE` плана, если план его выбросил → второй кусок грузит мусор (на тайлере — один кадр: потом
`need_full` даёт этому framebuffer полный PREBAR, а store-hist банит картинку). Счётчик — `passes split by a pre-fragment read` в
`[nr] rp`; при `=2 SIM mali` он должен быть ≈ 0 после первых секунд, иначе `need_full` надо заполнять заранее (по заголовку). На живом Mali первый же игрок — значит сначала
тестовый пререлиз с CAUTION. Прогон до него на Mi 14: §8 п. 2 (`DM_NR_RP=2 DM_GFX_SIM_GPU=mali`: `never expected 0`, нет `【红】`), затем
`DM_GFX_SIM_GPU=mali` без `DM_NR_RP` в env: строка `[nr] rp DM_NR_RP=1 (family default, policy family mali)`, `NVN PERF … barriers op25`
43+ → < 5, картинка как у `DM_NR_RP=0` (нет пурпура / мусора: палуба, меню, инвентарь, карта, бой).

**Выпущенная линия 0.1.1** (ветка `dos2`, кода NR-10 там нет) — ветка `dos2-nrp0-release` (от `dos2` 94d287d), коммит 46fddd0:
JNI больше не ставит `DM_NB_RP`, решает `xbg_nb_rp_default` = **1 только на Adreno**, 0 на остальных. Почему так, а не «PREBAR
фрагментным под `TILE_BARRIER`» (вторая мысль аудита):
- Фрагментный PREBAR без точек NR-10 ставит только `frag_seq`; любое чтение вершинной стадией (а это любой draw с текстурой / texel-буфером
  в VS, например скиннинг) картинки, записанной после последнего полного барьера (в т. ч. загрузки этого кадра), получит полный барьер
  **посреди** прохода → разрыв; а начало прохода уже взяло store `DONT_CARE` плана → у второго куска мусор на тайлере (один кадр до бана
  store-hist). Это новый, нигде не исполненный путь — в выпуск не годится.
- Умолчание по семейству — ноль нового кода: Mali / PowerVR возвращаются к эвристикам 0.1.0 (CLEAR_FOLD / STORE_HIST / NOLOAD /
  TILE_BARRIER: фрагментные барьеры чтения, без полного барьера перед проходом), и заодно у них нет store `DONT_CARE` плана, который на
  настоящем тайлере не проверялся ни разу (на Adreno sysmem он невидим; `ab7rp3` до правки store-hist — 7 нарушений). Adreno — байт в
  байт 0.1.1. Семейство берётся из Vulkan + `DM_GFX_SIM_GPU` (как `TILE_BARRIER`), не из JNI (там только `/dev/kgsl`): `SIM mali` на Mi 14
  воспроизводит путь игроков.
- Цена на тайлерах против 0.1.1: чтения, которые закрывал PREBAR, снова рвут свои проходы (как в 0.1.0, ≈ 12 сегментов `split` на кадр
  по профилю NB-20b-ctx); `DM_NB_TRANSIENT` без плана кандидатов не имеет (их и так 0); модель NB-20b-ctx для параллельных сегментов без плана хуже
  (T=2 −0.8 против −1.4 мс), но этого режима в 0.1.1 нет (`DM_NB_MT=3` — один воркер воспроизведения пакетов, от разрывов не зависит).
- **При слиянии `dos2-nrp0-release` вперёд в линию NR** коммит надо откатить (или оставить осознанно): на линии NR тайлеры должны идти
  планом + NR-10 (`DM_NB_RP=1` из JNI, `DM_NR_RP=1` по семейству). Если его оставить, тайлеры получат `DM_NB_RP=0` + `DM_NR_RP=1`: верно
  (NR-10 тогда сужает только барьеры чтения), но без плана.
- Проверка на Mi 14: `DM_GFX_SIM_GPU=mali` без `DM_NB_RP` в env — нет строки `NVN DM_NB_RP=`, `NVN tile pass policy (policy family
  mali)`, `[nb] rp` строк нет, картинка без пурпура / мусора (палуба, меню, инвентарь, бой); без SIM — `NVN DM_NB_RP=1`, как раньше.

### 10.1 Единственная `store-hist VIOLATION` (serial 11, кадр ~237): что это и видна ли она на тайлере

Строка `NVN store-hist VIOLATION: serial=11 fmt=0x35 2400x1080 LOADed by a pass (heuristic begin) after its store was discarded by the NB plan
(DM_NB_RP, IR part seq=238 node=30..37) in frame 237 (now 237); never discarded again` есть **во всех** прогонах 18.11 — партия D (SIM mali) и
партия C (чистый Adreno): одна на прогон, кадр 236–237, всегда сразу после первой загрузки шейдера `58bdf8f06f274b07` (stage 4, вид текстуры
с перестановкой `3,3,3,3`); дальше до конца прогона `violations=1 (plan 1)`.

- **Поверхность:** serial 11 — `NVN_FORMAT_DEPTH24_STENCIL8` (`0x35`) в полном разрешении экрана: depth-stencil интерфейса (проходы Iggy,
  меню / экран загрузки). Глубина сцены — serial 12 (2160×972 при DRS 90 %). Запись MALI-DOS2-02 (16.11) называла serial 11 «основным
  depth» — это было до DRS; сейчас это глубина UI.
- **Механизм:** в кадре 237 план NB для IR-прохода `node≈32` поставил этому вложению store `DONT_CARE` (`depth && final && !xread` или
  «следующее использование перезаписывает» в `nb_plan.c`), а позже в **том же** кадре проход, который начали эвристики хоста (`begin_open`:
  план не применён — разрыв / повторное пристёгивание DS / несовпадение вложений), начал его с `LOAD`. Кадр IR = кадр хоста
  (`present 1.00`, `0 mid-frame parts`). Учёт `store_hist` считает такой `LOAD` чтением всегда, даже если draw этого прохода DS не трогает;
  после строки картинка забанена — план больше не выбрасывает её store (`kept STORE for store-hist banned images` ≈ 60–150 за 10 с ≈ 0.1 на кадр).
- **Видно ли на настоящем тайлере:** в худшем случае — **один проход одного кадра** на ~6.5-й секунде запуска (переход экран загрузки →
  меню, ~2 прохода и ~10 draw на кадр): если draw этого прохода проверяют depth / stencil, они увидят старое содержимое памяти (последний
  настоящий store), а не конец прохода `node≈32`. Это может на 1 кадр (≈25 мс) неверно обрезать элемент UI по маске. Если draw DS не
  используют — ничего: старое содержимое загружается и пишется обратно, никто его не читает. Мусором в цвете это быть не может (выброшен
  только DS). После этого кадра — всё как на Switch (бан). На Adreno sysmem невидимо всегда.
- **Почему не чинил:** какой из двух случаев — из логов не выводится (строки `[nb] check` есть только на первые 16 проходов), а починка
  вслепую (не выбрасывать DS проходов Iggy заранее) стоила бы store DS таких проходов до первого нарушения ради одного возможного кадра.
  Умолчания шага 1 на это не влияют: в `D_uix1` (`UIX_DS=1 AREA=1`) та же одна строка.
- **Что сделано (дёшево и безопасно, только лог):** у нарушения с `heuristic begin` при работающем плане строка теперь дописывает читателя:
  `; the reader: IR pass seq=… node=…, plan <applied | no / unplanned header | a later host pass of the span (split / re-attach / restart) |
  guest barriers | attachments differ>, its first draw fs <ключ шейдера> <uses | does not use> the depth-stencil` (`nbrp::open_why / open_at`,
  первые 32 строки). Следующий прогон скажет: `does not use` → ложная строка учёта, вреда нет; `uses` → настоящий риск в 1 кадр, и видно,
  какой путь хоста (разрыв / повторное пристёгивание) надо научить держать store.
