# NR-24 — быстрые ворота HLE: часы, арбитр по адресу, ожидание вместо yield (ветка `dos2-nr24`, 17.11.2026)

Шаг аудита `AUDIT-REMAINING.md` §1 (`DM_HLE_FASTGATE`), сегмент S9a. Ветка `dos2-nr24` от `dos2` 94d287d + слияние `dos2-nr16`
(fast-forward: счётчики NR-16 нужны для замера). Всё за тремя своими ключами, умолчание **0** (байт-в-байт старое поведение: другой
вход ворот не ставится, формула часов, загрузчик, путь `G` и `yield_for` не тронуты). Телефон не трогался; NR-16 на телефоне тоже ещё
не запускался, поэтому числа выигрыша ниже — модель + замеры на ПК; решает один прогон (§7).

## 0. Как это делает Switch (правило «сначала Horizon»)
- **Часы.** `nn::os::GetSystemTick` в sdk DOS2 = `mrs x0, cntpct_el0; ret` (sdk+0xcdcb0); в sdk 32 места `mrs xN, cntpct_el0`
  (x0 ×12, x8 ×6, x20 ×9, x21/x22 ×2, x23 ×1 — ни одного x18/x29/x30), `svc 0x1E` в sdk нет; в `main` ворот 0, но **105 вызовов**
  `GetSystemTick` / `nnosGetSystemTick` через импорт (`tools/plt.py`-подобный скан, §6). На Switch это одна инструкция, 19.2 МГц,
  монотонно. У нас — полные ворота: кадр 800 Б (x0–x30, q0–q31, NZCV/FPSR/FPCR), хэш-поиск, C-вызов `guest_ns()` (`clock_gettime`).
- **Арбитр.** Mesosphere `KConditionVariable` / `KAddressArbiter`: ожидающие упорядочены по приоритету, при равном — по времени
  постановки; ожидающий на условии, переведённый сигналом на замок, ставится в очередь владельца заново (`KThread::AddWaiter`);
  0x1C пишет ключ = 1 до записи слова замка; сигнал атомарен под замком планировщика. Глобального списка нет: деревья по ключу /
  адресу / владельцу. Наш путь `G` — правильная семантика, но один замок и один линейный список всех ожиданий (вместе с 0x18).
- **Yield.** `SleepThread(0/-1/-2)` на Horizon возвращается сразу, если на ядре нет другого готового потока того же приоритета;
  опрос + yield на Switch — честный спин своего ядра. У нас потоки игры и так идут параллельно, поэтому yield — это только «отдать
  ядро». DOS2 собран с ядром DOOM: `thr_yield` уже даёт back-off (сон run/8 после 2 мс без прогресса, подпись x19–x28).
  Адрес `main+0x15ee898` из аудита — из D2R, в DOS2 там нет вызова yield (81 место вызова `nn::os::YieldThread` в main, ни одно не там).

## 1. Ключи
| Ключ | 0 (умолч.) | 1 | 2 |
|---|---|---|---|
| `DM_NR_GATE_TICK` | как было | домен тиков гостя = `cntvct_el0` → 19.2 МГц: (1) импорты `main` `GetSystemTick`/`nnosGetSystemTick` → C-функция хоста (`dm_tick_guest_fn`, обычный вызов); (2) 32 `mrs cntpct` sdk → вход `_dm_gate_fast` (entry.S) без кадра; (3) полные ворота / `svc 0x1E` → `dm_tick_read()` | гость получает старые значения; домен идёт рядом, полные ворота сравнивают (красная строка > 1 мс, сводка раз в 10 с) |
| `DM_NR_GATE_ARB` | путь `G` | 0x1A/1B/1C/1D/34/35 на 256 корзинах по адресу, сон на futex потока | как 1 + проверка инвариантов после каждой операции (ожидающий замка без бита ожидания, ожидающий условия при ключе 0, не та корзина) — красные строки |
| `DM_NR_GATE_YIELD` | `yield_for` (sched_yield, back-off после 2 мс) | после `DM_NR_GATE_YIELD_US` (50) мкс опроса без прогресса — сон на общем futex «прогресса» до run/8 (20…`DM_NR_GATE_YIELD_CAP_US`=250 мкс), будит любое событие ядра гостя (старт/выход/сон/блокировка потока, сигнал события/условия/адреса, отпускание замка, нативное ожидание HLE) | только счёт «ждал бы» |

Отказы с строкой лога: `DM_DETCLOCK` (часы гостя идут по кадрам; ожидания `G` нужны `dm_guest_clock_advanced`), не arm64 Linux (TICK),
нет futex (ARB/YIELD), CNTFRQ расходится с реальным ходом счётчика > 1 % против `CLOCK_MONOTONIC_RAW` (5 мс при загрузке; TICK).
Игрокам ключи не выдаются; приложение их не ставит (`source_structure_test.py` NR-24).

## 2. Устройство
**(а) Часы (`hle_os.c`, `entry.S`, `hle.c`, `loader.c`, `thread.c`, `hle_svc.c`).**
- Блок тиков `{valid, c0, base, mul}` публикуется store-release указателя `dm_tick_cur` и больше не меняется. Тик = `base +
  (cntvct − c0)`, при CNTFRQ ≠ 19.2 МГц ещё `× mul >> 32` (128-бит: `mul`/`umulh`/`extr`; MediaTek 13, Exynos 26, Tensor 24.576 МГц;
  Snapdragon 19.2 — без умножения). Отсчёт до `c0` (спекулятивное чтение) зажимается в `base`.
- Заморозка (`guest_clock_freeze_apply`: пауза, фон, клавиатура, загрузочный экран, `DM_TICK_HOLD`) публикует блок `valid = 0`, затем
  после `dmb ish; isb` читает счётчик и пишет замороженное значение (за флагом `ready`) — оно ≥ всего, что вернули читатели старого
  блока: их перепроверка указателя после чтения счётчика идёт с адресной зависимостью от значения счётчика (как
  `arch_counter_enforce_ordering` в Linux). Разморозка продолжает с замороженного значения: один монотонный счётчик, стоящий в
  заморозке, как `guest_ns()`. Пауза-меню (причина 3) ждёт как раньше (`guest_clock_read_wait`). Хостовые `guest_ns()`/`now_ns()`
  остаются на `CLOCK_MONOTONIC` (разница — NTP-подстройка < 0.05 %, таймауты гостя относительные).
- `_dm_gate_fast`: сохраняет x9–x12 (48 Б), ищет ворота по x30 в той же хэш-таблице (`dm_gate_tab`, 24-байтные записи, проверено
  `_Static_assert`), для вида 1/2 с приёмником x0–x28 (кроме x18) считает значение и кладёт его в xN через таблицу 16-байтных заглушек
  (`bti j; ldr xN; b; nop`, `br x29`; x29 гостя берётся из кадра блока ворот `[sp+48]`). Всё остальное (SVC, obs, probe, x18/x29/x30,
  заморожено, нет блока, блок сменился под чтением, неизвестный адрес) — восстановить x9–x12 и `b _dm_gate` с тем же sp и регистрами.
  Ни одна инструкция не пишет NZCV и SIMD (`source_structure_test.py` проверяет). Вход ставится в KGATE только при `=1`.
- Счёт для NR-16: при `DM_NR_CPU=1` быстрые чтения считаются по регистру (`dm_tick_fast_n`), вызовы хост-функции — атомиком;
  строка `[cpuprof] nr24 probe` меряет одно чтение через полные ворота и через короткий вход на телефоне.

**(б) Арбитр (`hle_thread_arb.inc`, включается в `hle_thread.c`).** 256 корзин (хэш адреса), в каждой mutex + цепочка ожидающих.
0x1A/0x1B/0x34/0x35 — одна корзина; 0x1C — корзины ключа и замка в порядке адресов (ключ = 1 и постановка до отпускания слова замка,
порядок `t_condvar`); 0x1D — под корзиной ключа выбирает весь набор (как Horizon, атомарно) и пишет ключ = 0, затем каждого переводит на
его замок под корзиной замка (захват или постановка заново). Сон — futex на `t->woke` (абсолютный дедлайн `CLOCK_MONOTONIC`), будящему
не нужен замок спящего; `fsleep` — нужен ли futex-wake вообще. Таймаут против сигнала решает корзина (либо таймаут, либо отданный
замок). Сохранено: спин главного потока `DM_HLE_SPIN_US`, bootprof, учёт handoff DOOM (`note_runnable` / `hand_leave` под `G`; порядок
замков: корзины → `G`), значения 0x35 type 2 этой сборки (−2 под `DM_GAME_DOOM`, KB HLE-13 — не менялось), отсутствие проверки
владельца в 0x1A. 0x18 / события / потоки остаются на `G`.

**(в) Yield (`hle_thread_arb.inc`, `thr_yield`).** Описано в таблице; ожидание помечает поток `sleeping` (handoff его не ждёт, как
back-off). Будящие точки: `svc_thread_impl` (кроме yield и информационных SVC) и `dm_thread_native_wait(1)`. Цена для остальных при
`=1`: одна загрузка счётчика ждущих на SVC; futex-wake — только когда кто-то ждёт.

## 5. Ожидаемый выигрыш (до прогона — модель)
Цена полных часовых ворот [м]: кадр 800 Б (≈34 пары stp + 34 пары ldp, `msr fpcr`) + поиск + `clock_gettime` ≈ 60–120 нс на X4/A720,
150–300 нс на A76/A55; короткий вход ≈ 5–15 нс, хост-функция ≈ 3–10 нс. Проба `[cpuprof] nr24 probe` даст реальные числа.
| Часть | Mi 14 (Adreno 750) | Слабые CPU (SD 7xx, Helio G99 2+6, Mali/PowerVR-телефоны) | Условие |
|---|---|---|---|
| (а) TICK | 1 тыс. чтений/кадр → −0.05…0.1 мс; 10 тыс. → −0.5…1 мс CPU | ×2–3 от этого (−0.15…3 мс), CPU-упор на потоках игры | число из `[cpuprof] hle` clock + вызовы `GetSystemTick` main (в `hle` их нет — они идут через sdk-ворота x0) |
| (б) ARB | 0, если `G` не под конкуренцией; иначе −(ожидание `G`) и меньше сна/пробуждения на каждом пробуждении (ПК: ×2…3.5 на пинг-понге) | больше: длинные удержания `G` на малых ядрах | `G` ≥ 5 % «занят» и ≥ 50 мкс/кадр ожидания (`hle svc … | G:`) |
| (в) YIELD | ≈0 fps на GPU-упоре; меньше нагрева (ядро не крутит yield первые 2 мс каждого ожидания) | 4+4 / 2+6: большое ядро отдаётся воркерам на время ожидания главного; риск +15…100 мкс задержки на ожидание без «пинка» | главный ≥ 10 % времени в уступках (`[sleepstat] … 0x1001`) |
Тайлеры (Mali / PowerVR) от этого шага не зависят — всё на CPU, одинаково для всех GPU; политика по семейству GPU не нужна.

## 6. Риски
- (а) Домен тиков гостя отделён от `guest_ns()` хоста на NTP-подстройку; если код хоста отдаёт гостю тики, посчитанные из `guest_ns()`,
  они разойдутся на ≤ 0.05 % (такого кода не нашёл: `grep 12 / 625` — только ворота и 0x1E). Прошивки с неверным CNTFRQ отсекаются
  калибровкой. Ядра с трапом `cntvct` (эррата A73 858921 и т. п.) — эмуляция ядра Linux, медленно, но верно. `=2` покажет расхождение.
- (б) Синхронизация — высокий риск по природе: порядок пробуждения и гонки покрыты тестами, но игра может делать то, чего тесты не
  делают; `=2` проверяет инварианты на живой игре. Сон на futex без приоритетов хоста — как и путь `G`.
- (в) Поллинг без события ядра (например, ожидание отчёта GPU, PERF-X01 D3) ждёт до run/8 ≤ 250 мкс за раз — тот же предел, что у
  back-off, но с 50 мкс, а не с 2 мс. На CPU-упоре главного потока может стоить fps — решает ABBA.
- Нагрузка на G при `ARB=1` остаётся: учёт handoff DOOM на каждом пробуждении (короткое взятие `G`).

## 7. Что не сделано
- Число часовых чтений / конкуренция `G` / доля yield на телефоне не мерены (NR-16 не запускался) — шаг сделан «вслепую по аудиту»,
  но за ключами и с счётчиками.
- Yield не превращён в ожидание по **конкретному адресу** опроса: для этого нужно разобрать места опроса в `main` (81 вызов
  `YieldThread`), что имеет смысл только после `DM_SLEEPSTAT=1` (покажет, какие из них горячие). Общий механизм (в) — первая ступень.
- APK не собирался; Mac / iOS не собирались (на них TICK/ARB/YIELD отказываются строкой лога).

## 9. Прогон на телефоне (главный агент, по разрешению хозяина)
Перед каждым: бэкап `files/save`, нет keyguard; после — force-stop. Сцены: палуба 60 с + тяжёлая (бой / город) 60 с. Базовые строки
`dm/env` во всех: `DM_DBG=1`, `DM_DOS2_TOUCHUI=1`, `DM_DOS2_FPS=0`, `DM_NR_CPU=1`, `DM_SLEEPSTAT=1`.
1. **Безопасность (по одному, 2–3 мин игры, без ABBA):** `+DM_NR_GATE_TICK=2` → ждать `[nr24] DM_NR_GATE_TICK=2: …` и раз в 10 с
   `… reads compared, largest gap X us` с X < 1000, ни одной `【红】[nr24]`; затем `+DM_NR_GATE_ARB=2` → `[nr24] DM_NR_GATE_ARB=2 …`,
   `[cpuprof] nr24 … red 0`; `+DM_NR_GATE_YIELD=2` → `would wait N` (сколько уступок дождались бы).
2. **ABBA по каждому (по 60 с):** A = базовые строки; B = `+DM_NR_GATE_TICK=1` (затем отдельно `ARB=1`, `YIELD=1`).
   Разбор: `python tools/dos2_cpuprof.py --ab a1 b1 b2 a2` (строки `[NR-24] main thread CPU ms`, `full clock gates`, `G takes`,
   `G waited us`, `yield waits`, fps / process CPU) и `python tools/dos2_cpuprof.py b1.dm.log` (ответ «NR-24 switches» + пробы
   `full gate X ns, short entry Y ns`).
   - TICK доказан, если `clock reads by the short entry` + `main's GetSystemTick on the host` ≈ прежние `clock` из `hle`, `full clock
     gates` ≈ 0, CPU потоков игры ниже на (чтений × (X − Y)).
   - ARB: `G takes` падают на число арбитражных SVC, `G waited` → ~0, `bucket takes … found held` мал; fps ≥ A.
   - YIELD: CPU главного ниже, `waits … woken by progress` ≫ `timed out`, fps ≥ A (на телефоне хозяина GPU-упор — fps не должен падать).
