# NR-13 + NR-26 (чистка) `DM_NR_LEAN` — не производить то, что никто не читает, 17.11.2026

Ветка `dos2-nr13` (worktree `wt-nr13`), база `dos2-nr-all` 393fcd7. План: `NATIVE_RENDERER_PLAN.md` §3 строка NR-13, `AUDIT-REMAINING.md` §2,
`AUDIT-FINAL.md` N4. **На телефоне не исполнялось ни строчки** (adb не запускался). Числа с пометкой [м] — модель.

## 0. Коротко
- Посылка N4 («для draw, взятых полосой NR-09, записи состояния NVN и запись draw больше никто не читает, ≈ 220 КБ / кадр можно не писать»)
  **неверна**: полоса NR-09 читает `State` бэкенда и привязки своей записи. Эти записи — её вход, а не тень. Пропустить их нельзя ни по
  правилу «следующий потребитель тоже NR-draw», ни ленивым восстановлением (§1).
- Что действительно осталось без потребителя: **захват состояния NB-13a** (тень + словарь + блоки DEF / REF: id блоков были нужны только
  ключам NB-14 и порядку NB-17, которые NR-15 снял с умолчаний) и **заметки кольца NB-12** при работающем NR-06. Это и снимает `DM_NR_LEAN=1`.
- Пункты §2 аудита про `tex-dirty` / хэш-проверки (NR-05), снапшоты кольца (NR-06) и мемо `descriptors()` (NR-08) **уже сняты внутри этих
  шагов** при их `=1`; остаток посчитан режимом `=2`, пропускать там нечего (§1.3).
- Ожидание «поток игры −0.5…1 мс» **не достижимо чисткой записей**: из +1.2 мс фронта NB 0.69–0.86 мс уже снял NR-15; на захват NB-13a
  приходится ≈ 0.1–0.2 мс на Mi 14 [м]. Реальная оценка §6: поток игры −0.1…0.2 мс, транслятор −0.1…0.45 мс (Mi 14), ×2–3 на слабых CPU.
  Точную цифру даёт один прогон с `DM_NR_LEAN_AB` (A/B внутри процесса).

## 1. Разбор: кто что читает
### 1.1 Что пишет поток игры на draw (логи `rd2` / `h1def`, Mi 14, палуба)
| Запись | На кадр | Кто читает |
|---|---|---|
| `OP_X_NB_DRAW` (NB-09; с NR-09 + хвост 16 Б) | 982 × 151 Б = 148 КБ; 3.3 привязки (≈ 2.6 UBO, 0.5 текстур) | `nbdraw::apply` → таблицы `state.tex / samp / ub` → **NR-08** строит набор и динамические смещения из них; аргументы draw, IB → **полоса NR-09**. Движок привязывает только изменившееся, UBO кольца меняются на каждом draw — лишних привязок в записи нет |
| `OP_X_NB_STATE` (NB-13a) | 2 668 вызовов состояния (93.9 КБ как записи NVN) → 981 запись, 72.2 КБ: 488 DEF + 1 374 REF, 45 «не изменилось» | `nbstate::exec` → `execute()` → `State`. **Полоса NR-09 читает `State`**: шейдеры, набор RT, `state.vb[i]` (диапазоны вершин), viewport / scissor, флаги depth-stencil, restart и шесть id групп NB-13b (перечитываются из байтов `State` после записи состояния) — это и есть «вариант» строки прямой таблицы (NR-09 §2.3) |
| Простые записи состояния вне взятых пакетов | 1 397 | `execute()` → `State` |

Итого те самые ≈ 220 КБ (148 + 72). Движок фильтрует повторы сам: из 2 668 вызовов «не изменилось» только 45 блоков.

### 1.2 Почему запись состояния нельзя пропустить для взятого draw
1. **Решение «взят / не взят» принимает бэкенд** (промах таблицы, первый draw прохода, ленивый clear, uiarea, occlusion…) — позже и на
   другом потоке. Фронт в момент вызова NVN его не знает.
2. Даже для взятого draw запись — вход: без `BindVertexBuffer` нет `state.vb`, без групп нет варианта. Устаревший `State` дал бы **чужой
   пайплайн**, а не запасной путь.
3. Ключ движка NR-02 не описывает состояние целиком (stencil ref, bias, blend color идут мимо кэша движка — NR-09: «второй вариант в
   строке»), диапазоны вершин и viewport в него не входят вовсе. «Ключ → состояние» потребовал бы нести в записи всё, что сейчас несут
   записи состояния.
4. id блоков фронта как ключ отвергнуты ещё в NB-13b (живут одну эпоху, после сырой записи называют часть вида).
5. Работа захвата не зависит от того, уйдёт ли блок: чтобы узнать, что вызов «лишний», его надо сравнить с тенью — это и есть захват.

Вывод: правило «пропускать, если следующий потребитель — NR-draw» не имеет случая применения; «восстановить лениво на запасном пути» —
тоже (восстанавливать не из чего). Снять можно только то, что у записей состояния **сверх** самих записей, — NB-13a.

## 2. Что сделано
### `NRL_STATE` (бит 1, фронт, поток игры)
При `DM_NR_LEAN=1` и без потребителей блоков (`DM_NB_RELOC = 0`, `DM_NB_ORDER = 0` — умолчания после NR-15) биты состояния `DM_NB_OPS`
**не берутся**: `nvn_nb_state_enable` не зовётся, пакеты состояния пишут обычные записи NVN — поток NB-09 / NB-10, то же, что
`DM_NB_OPS=0x3000000000`. Хуки `NBS_*` снова «загрузка + непринятый переход».
**Правило запасного пути** тривиально: каждый draw — взятый или нет — видит ровно то состояние, которое поставили записи в порядке
вызовов (это исходный поток NVN). Тест: три потока (захват всегда / никогда / пауза-возврат) дают одинаковое состояние на каждом draw.
Цена: +≈ 22 КБ командной памяти на кадр (93.9 против 72.2 КБ); бэкенд исполняет 2 668 записей вместо 1 862 блоков, каждый из которых
воспроизводит **весь** свой вид (модель: ×1.43 записей, ×1.46 байт с захватом).

### `NRL_UBO` (бит 2, бэкенд, `nvn-translate`)
Пока NR-06 обслуживает кольцо (`nrbuf::ring_mode > 0`): `nbdraw::apply` не пишет заметки NB-12 (`nbubo::note`), `uniform_snapshot` не
зовёт `nbubo::fast` для блоков, на которые NR-06 не ответил. **Правило запасного пути:** без заметки ответ NB-12 — «not a ring range», т. е.
обычный путь снапшота (то же, что `DM_NB_UBO=0` для этого блока) — консервативно по построению. Без NR-06 часть не действует (NB-12 —
единственный путь «на месте»).

### `DM_NR_LEAN_AB=N` — A/B в одном прогоне
С `DM_NR_LEAN=1`: фазы «выкл N / вкл 2N / выкл N» кадров. Захват NB-13a ставится на паузу и возвращается на границе кадра
(`nvn_nb_state_pause`, поток рендера движка в EndFrame / BeginFrame): пауза — тень уходит в поток (как в EndRecording), возврат —
`nbs_resume` (все виды «неизвестны», новая эпоха; мутация без него ловится тестом: 11 148 из 20 125 draw с устаревшим состоянием).
Строка фронта даёт `recording BeginFrame -> EndFrame` по фазам, строка бэкенда — `apply … ns` по фазам. Без дрейфа DVFS между прогонами.
В фазе паузы остаётся вызов `nvn_nb_state_begin / _end` на пакет (≈ 9.3 тыс. × 2 пустых вызова), т. е. A/B слегка **занижает** выигрыш.

## 3. Переключатели (умолчание 0; игрокам не выдаются)
| | |
|---|---|
| `DM_NR_LEAN` | **0** — ничего: потоки и таблицы байт в байт прежние (фронт: 2 загрузки на кадр; бэкенд: загрузка + непринятый переход на запись / блок / снапшот). **1** — пропуск годных частей (негодная остаётся, со строкой причины). **2** — всё производится, считается: что `1` не произвёл бы и каждое чтение этого потребителем. **3** не существует (травить нечего: пропущенное либо заменено исходными записями, либо даёт консервативный путь) |
| `DM_NR_LEAN_PARTS` | маска: 1 `NRL_STATE`, 2 `NRL_UBO`; умолчание 3 |
| `DM_NR_LEAN_AB` | N кадров (только с `=1`); 0 — без чередования |

Зависимости: `NRL_STATE` — только `DM_NB=1` с битами состояния (умолчание сборки); **ни `DM_NR`, ни `DM_NR_DRAW` не нужны** (захват лишний и
без NR). `NRL_UBO` — `DM_NR=1 DM_NR_BUF=1`.

Строки: старт `[nr] DM_NR_LEAN=… (NR-13 / NR-26): state capture NB-13a …` (фронт), `[nb] DM_NB_OPS state bits …: not taken (DM_NR_LEAN=1…)`,
`[nr] DM_NR_LEAN=… (NR-13 / NR-26, backend): …`; раз в 10 с `[nr] lean (front, …)`: вызовы состояния, байты, время записи (по фазам при A/B);
`[nr] lean (backend, …)`: заметки не сделаны / сделаны, `nbubo::fast lookups skipped`, `notes READ by nbubo::fast`, `nb_desc_pre ran`,
блоки `OP_X_NB_STATE` и КБ воспроизведённых записей, `apply … ns` lean / full. Красная строка — только на значение вне диапазона.

## 7. Риски
1. Не исполнено на устройстве. `NRL_STATE` = поток NB-09 / NB-10 без NB-13a: на телефоне он отдельно не запускался (все пять env-файлов логов —
   `DM_NB_OPS=0x30002c0fc0`), на ПК покрыт `nb_draw_test` / `nb_tap_test`.
2. Модель времени — ПК и синтетическая смесь вызовов; на телефоне выигрыш может оказаться в шуме. Тогда `NRL_STATE` не включать: захват
   безвреден, а блоки понадобятся, если вернутся `DM_NB_RELOC / ORDER`.
3. `NRL_STATE` несовместим с `DM_NB_RELOC / DM_NB_ORDER` — проверяется на старте (часть остаётся выключенной, причина в строке). Новый
   читатель блоков NB-13a обязан попасть в `nr_lean_state_why` — структурный тест падает на незнакомом читателе.
4. A/B: пауза только когда поток — владелец тени и пакет не открыт; иначе откладывается (`put off` в строке). Если EndFrame всегда внутри
   пакета, смена случится в BeginFrame; если и там нет — `phase changes 0`, и A/B не состоялся (видно в строке).
5. `NRL_UBO`: блок, на который NR-06 не ответил, идёт копией, даже если NB-12 отдал бы его на месте. `=2` считает такие (`notes READ …
   served in place`); если их много — часть не включать.
6. Счётчики `nrlean::s` — обычные глобальные, как у `nbdraw` / `nrdraw` (с `DM_NB_MT` приблизительны).
