# NR-NATIVE, шаг E — ресурсы по событиям движка вместо слежения за страницами (20.11.2026, ветка `dos2-nrn3e`)

Дополнение к `NR-NATIVE.md` (§2.2, §2.4, §6 строка E). База: `dos2-nrn3` = `dos2` 88ba03e. Телефон не трогался: всё ниже — разбор
`main.raw` (обновление v786432, сборка 4979b200), код и хост-тесты. Пометки: **[бин]** — прочитано в двоичном файле в этой сессии
(Ghidra без окна, своя копия проекта; указатели NVN названы по коду загрузчика: 517 пар «имя — ячейка»); **[выв]** — вывод, не
проверенный ни кодом, ни логом; **[м]** — модель, не замер; **[лог]** — видно в логах серии N.

## 0. Коротко
- **Найдено, как движок пишет в буферы вершин и индексов после создания** (§1). Мест ровно пять, и все они перехватываются:
  создание, обновление копией на GPU (одна функция `0x9218c0`), копия на процессоре буфер → буфер (коды пакетов `0x2f` и `0x33`),
  «черновой» буфер немедленных draw (пишется мимо всего — он просто исключён), уничтожение. Прямой записи в отображённую память буфера
  где-либо ещё в `main` нет.
- **Построено** (§2): переключатель `DM_NRN_EV` (умолчание 0; 2 — сверка; 1 — применение). Каждое из этих мест — **событие** одной
  таблицы: журнал по диапазону памяти (его читает транслятор), эпохи по хэндлу движка (для потока игры), счётчик оборотов кольца
  констант. Свои записи в память гостя (исполнение копии буфера, обратные записи GPU) транслятор заносит в тот же журнал сам, в порядке
  потока команд.
- **`=2`** ничего не меняет: каждый запрос кэша теней о диапазоне внутри буфера движка задаётся и событиям, и трекеру страниц; расхождение
  «трекер увидел запись, события — нет» решается хэшем байтов: байты те же — писали в соседа на общей странице, байты другие — **BAD**,
  красная строка. Это и есть доказательство на телефоне, что события покрывают все записи.
- **`=1`**: версия такого диапазона в хэше кэша теней — эпоха событий (трекер не спрашивается, страницы не защищаются); статическая
  копия NR-06 (устройства без общей памяти) сторожится эпохой вместо защиты страниц. Остальное — на трекере (§4).
- **Поправка к `NR-NATIVE.md` §2.4**: `BeginFrame` ждёт не «забор прошлого кадра», а синхронизацию **получения текстуры окна** (§1.5).
- Тесты (§7): хост-тест 308 628 проверок, 10 мутаций, каждая ловится; ThreadSanitizer — 0 предупреждений. APK не собирался (собирает
  главная ветка после слияния); `libdm.so` собирается.

## 1. Что прочитано в двоичном файле

### 1.1 Таблицы буферов рендерера [бин]
`r` — рендерер. Буфер вершин: запись 0x68 байт в таблице `r+0x180` (кусками; поколения в `r+0x188`, размер куска `r+0x190`):
`+0` объект буфера NVN, `+8` адрес GPU (`nvnBufferGetAddress`), `+0x10` **отображённый указатель** (`nvnBufferMap`), `+0x20` смещение в
пуле, `+0x30` пул, `+0x38` номер кадра последнего обновления, `+0x40` размер, `+0x48` usage. Буфер индексов: запись 0x58 байт в
`r+0x240` (`+0x248`, `+0x250`), те же поля со сдвигом (`+0x10` указатель, `+0x18` номер кадра, `+0x38` смещение, `+0x48` пул).
Третья таблица `r+0x300` (записи 0x58, поиск `0x921250`) — вид 2 в обновлении `0x9218c0`; кто её наполняет, не читалось (§6).

### 1.2 Кто пишет байты буфера [бин]
Найдено полным перебором кода: все функции, которые индексируют таблицу `r+0x180` / `r+0x240` (тройка смещений «записи — поколения —
размер куска» в пределах 48 команд), и все места загрузки указателей NVN `nvnBufferMap`, `nvnCommandBufferCopyBufferToBuffer`,
`nvnBufferFlushMappedRange`, `nvnCommandBufferUpdateUniformBuffer`.
| Что | Где | Как |
|---|---|---|
| создание | `0x917630` (вершины), `0x9179d0` (индексы) | `nvnBufferInitialize` над памятью пула, `nvnBufferMap`, один `memcpy` начальных данных в указатель |
| обновление копией на GPU | **`0x9218c0(r, upd)`** — единственное место `nvnCommandBufferCopyBufferToBuffer` в движке | `upd`: `+0` хэндл, `+8` вид (0 вершины, 1 индексы, 2 третья таблица), `+0xc` смещение, `+0x18` адрес данных, `+0x20` пул данных, `+0x28` размер. Создаёт два временных буфера NVN (приёмник над памятью буфера, источник над промежуточной памятью) и пишет команду копии. Байты в память буфера кладёт **бэкенд**, когда исполняет запись |
| кто зовёт `0x9218c0` | пакет `0x30` и `0x32` (`0x921dc0(r, хэндл)`: ищет ожидающее обновление в таблице `r+0x1898` и сбрасывает его), и девять функций игры напрямую (`0xaab5e0`, `0xc69520`, `0xc7d430`, `0xc9d5c0`, `0xd55120`, `0x10e2900`, `0x12b03b0`, `0x12dbd50`, `0x1406ed0`) | — |
| промежуточная память обновления | пакет `0x2e` (вершины) и `0x31` (индексы; `0x921c60` / список `0x9413f0`): место в кольце `r+0x1870` (15 МБ, курсор `r+0x1890`), данные пакета копируются туда | это не память буфера — событий не нужно |
| копия на процессоре, вершины → вершины | пакет `0x2f` (список `0x9412f0`; при списке без записи — сразу) | `memcpy(запись приёмника +0x10, запись источника +0x10, размер приёмника)`; приёмник — хэндл по `+0x10` пакета |
| копия на процессоре, индексы → индексы | пакет `0x33` (`0x921b10`; список `0x9414f0`) | то же для таблицы индексов; приёмник — `+0x10` пакета |
| «черновой» буфер немедленных draw | пакеты `0x26`–`0x2a` (`0x930910`, `0x930e90`, `0x92f730`, `0x93ff20`, `0x930210`) | вершины пишутся прямо в указатель буфера `[r+0x8d0]` по курсору `r+0x8d8` (кольцо 1 МБ); `0x930210` читает ещё `[r+0x8e0]` |
| уничтожение | `0x91db40`, `0x91d890` | — |

`nvnCommandBufferUpdateUniformBuffer` и `nvnBufferFlushMappedRange` движок **не зовёт вовсе** [бин] (нет ни одной загрузки ячейки).
`nvnBufferMap` зовут ещё `0x938330` / `0x939850` (не таблицы буферов рендерера; не читалось) и промежуточный код UI (`0x1bf…`).

### 1.3 Текстуры [бин]
- `nvnTextureWriteTexels` в движке зовёт только `CreateTextureFromImage 0x91f2e0` (создание); `…Strided`, `nvnTextureFlushTexels`,
  `nvnCommandBufferCopyBufferToTexture` движок не зовёт (последнюю — только код UI `0x1bf0c40` / `0x1bf20c0`).
- Запись после создания — **пакет `0x2c`**: по хэндлу (`+8`) берётся запись текстуры (таблица `r+0`, 0x28 байт), байт `+0x17` = 1
  («заперта»), строки (`+0x14` шаг, `+0x18` число) копируются `memcpy` в указатель `[[запись]+0xe0]`; пакет `0x2d` снимает байт.
- Всё остальное содержимое текстур меняет GPU (цели отрисовки, `nvnCommandBufferCopyTextureToTexture` в `0x920b00`) — это не событие
  процессора.

### 1.4 Кольцо констант [бин]
Голова `dev+0x25a60`: выровнять вверх на 0x100; не помещается до `0x137ffff` — начать с 0; `fetch-add` размера (так же в модели
`nr_ubo.h`). Признак оборота — голова меньше предыдущей.

### 1.5 Кадр и ожидания [бин] — поправка к `NR-NATIVE.md` §2.4
- `BeginFrame 0x9215f0(r, флаги)`, бит 0 флагов = кадр с показом: `nvnWindowAcquireTexture(dev+0x3020, синхр. dev+0x31a0, номер
  dev+0x31e0)`, затем **`nvnQueueWaitSync(очередь dev+0x31e8, dev+0x31a0)`** — ждётся синхронизация *получения текстуры окна*, а не
  забор прошлого кадра. Контекст кадра = `dev + номер × 0x1d8 + 0x5250` (кладётся в `dev+0x5248`): **кольцо кадров — по номеру
  полученной текстуры окна**. Там же обнуляется таблица `dev+0x25ac8` (0x1000 записей этого номера) и `dev+0x25ac0`.
- Конец кадра `0x93ccd0`: с показом — `nvnQueuePresentTexture`, счётчик кадров `dev+0x51f0` += 1, **без ожидания**; без показа —
  `nvnQueueFenceSync` + `nvnQueueFlush` + `nvnSyncWait(…, −1)` (полное ожидание).
- Это единственное место `nvnQueueWaitSync` в движке. Значит защита «не писать то, что ещё читает GPU» у движка — номер текстуры окна
  (её не отдадут, пока кадр с ней не показан), а не забор на каждый кадр. Что наша реализация `AcquireTexture` / `WaitSync` держит то
  же обещание по отношению к транслятору — [выв], в этом шаге не проверялось и не используется (§2.3: события читаются в момент
  исполнения, как и трекер).

## 2. Что построено

### 2.1 Таблица событий (`dm/gfx/nr/nr_nrn_ev.h`, чистый C)
| Часть | Что это | Кто пишет | Кто читает |
|---|---|---|---|
| журнал `nrne_j` | один номер на все события; ячейка на страницу (4 КБ) и на блок (64 КБ) по хэшу адреса хранит номер самого нового события, задевшего страницу / блок. Версия диапазона — максимум по его ячейкам. Ячейка только растёт (сравнение-обмен), номер — `fetch-add` | потоки движка (создание, уничтожение, копии на процессоре, пометка чернового буфера) и транслятор (свои записи в память гостя) | транслятор |
| покрытие `nrne_cov` | какие диапазоны памяти — буферы движка, с классом (статический / динамический / без начальных данных / черновой): отсортированный массив за словом последовательности. Писатель один (мьютекс хоста); читатель не ждёт никогда — встретив писателя, получает «не покрыто» | создание / уничтожение | транслятор |
| хэндлы `nrne_h` | хэндл движка (с поколением) → номер его последнего события; ячейка на (вид, индекс), новый хэндл вытесняет старый | все события хэндла | поток игры |
| кольцо `nrne_ring` | число оборотов кольца констант | проба головы на каждом пакете draw | кто угодно |

Почему версия журнала — версия содержимого: событие с номером `s` поднимает до `s` ячейку каждой страницы и блока, которых касается,
*до* возврата; любой более поздний запрос диапазона читает хотя бы одну из них, значит его ответ ≥ `s` > любого ответа, данного до начала
события. Чужое событие на той же ячейке даёт ложную смену (draw просто рисуется), пропуска не даёт. В слово эпохи входят начало и хэндл
записи покрытия — другой буфер по тому же адресу имеет другую эпоху даже при том же номере.

### 2.2 События (`dm/host/hle_dos2_nrn_ev.inc`)
| Событие | Откуда | Что двигает |
|---|---|---|
| создание | крюки NR-01 `0x917630` / `0x9179d0`, **после** оригинала (начальные данные уже записаны) | журнал диапазона, покрытие, эпоха хэндла |
| уничтожение | крюки NR-01 `0x91db40` / `0x91d890` | покрытие снято, журнал диапазона, хэндл забыт |
| обновление копией на GPU | новый крюк **`0x9218c0`** | эпоха хэндла — сразу (draw, записанный после, прочтёт новые байты); журнал диапазона — когда бэкенд исполнит копию (`snapshot_invalidate`) |
| копия на процессоре | пакеты `0x2f` / `0x33` в общей цепочке `ExecuteRenderCommand`, **до и после** `memcpy`; те же две функции списка `0x9412f0` / `0x9414f0` при списке без записи — два новых крюка | журнал диапазона, эпоха хэндла |
| черновой буфер | пакеты `0x26`–`0x2a` и каждый пакет draw `0x23`–`0x25`: хэндлы `[r+0x8d0]`, `[r+0x8e0]` | класс «черновой» в покрытии: эпохи у него нет никогда |
| текстура | фиксация создания NR-01; пакет `0x2c` (до и после) | эпоха хэндла текстуры (диапазона нет) |
| кольцо | пакеты draw `0x23`–`0x25`: проба `dev+0x25a60` | счётчик оборотов |
| записи самого бэкенда | `snapshot_invalidate` (исполнение копии буфера, обратные записи GPU, отчёты, записи процессора в потоке команд), приход / уход пула | журнал диапазона |

Три новых крюка ставятся только при `DM_NRN_EV=1|2`; `tools/dos2_nr_check.py` проверяет их вместе с остальными (22 места: слова пролога,
нет адресации от счётчика команд, нет входящих переходов, `x8` и векторные регистры не читаются до записи). Если хоть один не встал —
красная строка и переключатель выключен целиком (иначе обновление могло бы пройти без события).

Копия на процессоре объявляется дважды, потому что запрос между началом и концом `memcpy` увидел бы новую эпоху и наполовину старые
байты: с двумя событиями у «середины» своя эпоха, которая больше не повторится. Хэндл, вытесненный из своей ячейки другим хэндлом с тем
же младшим индексом, событий не теряет: диапазон берётся из покрытия проходом под мьютексом (`nrn_ev_updated_slow`); уничтожение такого
хэндла тоже снимает покрытие проходом.

### 2.3 Порядок: когда читается эпоха
Транслятор читает эпоху диапазона **в момент исполнения записи draw** — там же, где сегодня читает поколения страниц у трекера. Записи
процессора (создание, копия буфер → буфер) двигают журнал в момент записи, как трекер двигает поколение при сбое страницы; записи самого
бэкенда двигают журнал в порядке потока команд. Поэтому эпоха отвечает на тот же вопрос, что и трекер: «те ли байты сейчас, что были
при прошлом запросе». Эпоха хэндла для потока игры двигается в момент *записи* обновления в поток — draw, записанный позже, прочтёт уже
новые байты, записанный раньше — старые.

### 2.4 `=2`: сверка (`dm/gfx/vulkan/engine/xbg_nr_nrn_ev.inc`)
Каждый запрос `rv()` кэша теней о диапазоне, который может писать процессор игры и который целиком лежит в одном буфере движка:
берётся эпоха событий, ответ трекера (`nvn_dirty_version`, без замков, ничего не меняет) и — когда есть что решать — хэш байтов
(бюджет `DM_NRN_EV_HASH_MB`, 256 МБ на 10 с). Сравнение с прошлым запросом того же диапазона (`nrne_verify`):
| Исход | Значит |
|---|---|
| `same` | не двигалось ничего |
| `both moved` | двинулись оба |
| `event only` | двинулись только события (копия на GPU, которую трекер не видит как запись процессора; событие соседа на общей странице) — считается |
| `tracker only, bytes the same` | писали в **другие** байты общей страницы — не ошибка |
| `tracker only, not hashed` | не решено (бюджет хэша) |
| **`BAD`** | трекер двинулся, эпоха стоит, байты другие: запись, которую не объявило ни одно событие. Красная строка (первые 16), счёт по виду и классу буфера |
То же для статической копии NR-06, которую снимает трекер: была ли эпоха сдвинута; если нет — сравнение копии с памятью.

### 2.5 `=1`: применение
- **Кэш теней**: `rv()` для покрытого диапазона кладёт в версию метку и эпоху и выходит: `nvn_dirty_version` не зовётся, страницы не
  защищаются, «солёных» draw из-за незащищённых страниц у таких диапазонов нет. Слово одно и то же для draw, который строит слой, и для
  draw, который в него попадает. Запрос, на который события ответить не могут (не покрыто, писатель в таблице), идёт к трекеру; его
  слово с эпохой не совпадёт никогда (метка) — такой draw считается новым и рисуется.
- **Статические копии NR-06** (устройства без общей памяти): эпоха берётся **до** чтения байтов в копию; страницы не защищаются; при
  следующем использовании копия годна, пока эпоха та же, иначе буфер уходит на старый путь (как при записи по трекеру).
- `DM_NRN_EV_CLASSES` — какие классы берёт `=1` (бит 0 статические, 1 динамические, 2 без начальных данных; умолчание 7) — для A / B.

## 3. Что эпохи делают доказуемым для «живых» шагов отвеченного draw (для части 4)
| Шаг | Что он проверяет сегодня | Что дают события | Чего не дают |
|---|---|---|---|
| версии вершин / индексов в хэше кэша теней | поколения страниц трекера + журнал записей бэкенда | **заменено** (`=1`): эпоха диапазона | — |
| статическая копия NR-06 (Mali, PowerVR…) | защита страниц + `nvn_dirty_since` раз в эпоху снимков | **заменено** (`=1`): эпоха диапазона | бюджет, обрезка памяти, обратные записи — остаются свои слова (`nrbuf::st_ep`) |
| виды вершин / индексов на месте (Adreno, zero-copy; слово Z3c) | живость куска `zc::live_ep`, версия записи куска `wr_ver`, номер подачи для стража NR-TRX, ожидающие обратные записи | событие «буфер создан / уничтожен» — то же, что смена записи покрытия; содержимое виду на месте безразлично | состояния кусков zero-copy и стража — свойства бэкенда, не содержимого: событиями движка не выражаются. По NR-ZERO §19 таблица видов на Adreno убыточна — этот шаг её не трогает |
| обход образов (слово Z3b) | образ залит, не писан GPU, проверен в этой подаче, раскладка | эпоха хэндла текстуры покрывает записи процессора (`0x2c`) и создание | связи «образ бэкенда ↔ хэндл движка» в карточке нет (в `State` — номер пула, не хэндл); образы, писанные GPU, событий не имеют. Нужна таблица «номер в пуле → хэндл» из NR-01 (`nk_texture` её часть уже держит) — 2–3 агент-часа |
| блоки констант (слово Z3d) | кольцо целиком в живом куске, нет липких страниц и обратных записей | оборот кольца — `nrn_ev_ring_epoch` | на Adreno слово Z3d уже стоит 100 % [лог]; на зеркале (Mali) первая привязка гранулы — копия данных, её события не отменяют |

## 4. Чего нет и что не доказано
1. **На телефоне не запускалось.** `=1` верно ровно настолько, насколько верен перечень §1.2; его проверка — `BAD 0` в `=2`.
2. **Перечень мест записи найден перебором кода с эвристикой** (тройка смещений таблицы в окне 48 команд; места загрузки ячеек NVN):
   функция, которая получает запись буфера иначе (указатель, сохранённый в объекте игры), перебором не ловится [выв]. Ловится сверкой.
3. **Третья таблица буферов `r+0x300`** (вид 2 в `0x9218c0`): кто её создаёт, не читалось; её диапазоны не в покрытии (остаются на
   трекере), её обновления считаются в строке (`another table`).
4. **Немедленное исполнение пакетов текстуры и буферов мимо списка** покрыто только для `0x2f` / `0x33` (крюки функций списка);
   для `0x2c` — только пакет. На ответы по буферам не влияет.
5. **Текстуры**: есть только эпоха по хэндлу. Обход образов и номер заливки в хэше кэша теней (`texver`) не заменены (§3).
6. **Виды буферов на месте (Adreno) и слово Z3c не заменены** — см. §3: там нечего заменять содержимым.
7. **Черновой буфер** помечается на первом же пакете draw любого списка (и на каждом немедленном draw). Любой запрос транслятора
   следует за пакетом draw, поэтому к первому запросу буфер уже помечен, каким бы путём ни шёл первый немедленный draw (у `0x92f730`
   есть и прямой вызов мимо пакетов, из `0xa7eac0`).
8. Таблица покрытия — 16 384 буфера; сверх того буфер просто не покрыт (счётчик `table full` в строке хоста).
9. Обещание «движок не пишет буфер, пока транслятор не дочитал кадр» (§1.5) не проверялось: шаг его не использует.

## 6. Прогоны телефона (главная сессия; 40 с от загрузки уровня; общее `DM_DOS2_FPS=0 DM_SAFE_MODE=0 DM_DOS2_DRS=off DM_NR_CPU=1`)
| # | env (сверх общего) | Сцена | Цель |
|---|---|---|---|
| E_v1 | `DM_NRN_EV=2` | стоя у ворот Форта Радости | сверка: `BAD 0` по всем классам; доля `inside an engine buffer`; сколько `not hashed` |
| E_v2 | `DM_NRN_EV=2` | ходьба к пляжу и назад | то же на подгрузке (создание / уничтожение, обновления) |
| E_p0 | — | стоя | база (`[nr] shcache memo … hash by part`, потоки) |
| E_a1 | `DM_NRN_EV=1` | стоя + снимок | картинка та же; `the event epoch taken`; `[nr] shcache`: доля пропущенных не ниже базы, `verify differ 0`; `hash by part`: часть «vertex / index versions» против базы |
| E_m1 | `DM_GFX_SIM_GPU=mali DM_NRN_EV=2` | стоя | статические копии: `the tracker demoted … BAD 0` |
5 прогонов × 40 с, остывание 2 мин после третьего. **Решают**: в E_v1 / E_v2 `BAD 0` у каждого класса и нет красных строк →
можно E_a1. `BAD` у одного класса → этот класс убрать из `DM_NRN_EV_CLASSES` (строка называет диапазон: по нему искать место записи).
Большое `not an engine buffer` → вершины draw лежат не в буферах таблиц рендерера (третья таблица, §4 п. 3). Большое `tracker only,
bytes the same` — буферы делят страницы с чужими данными: это и есть лишние смены версий трекера сегодня, которых у событий нет.

## 7. Экономия [м] и остаток
- `nvn-translate`: часть «версии вершин / индексов» хэша кэша теней — 0.42 мкс на draw при 861 draw теней [лог] ≈ 0.36 мс на кадр,
  из них поиск по трекеру уже закрыт токенами на 97.5 % [лог]. Эпоха вместо него — поиск в покрытии (≈ 10 сравнений) и чтение ячеек
  журнала (1–30): ждём ≈ 0.15–0.25 мкс на draw → **−0.15…0.2 мс на кадр**, не больше. Основной выигрыш не во времени хэша, а в том,
  что страницы статических мешей больше не защищаются ради кэша теней: меньше `mprotect` и сбоев страниц (у потока игры — когда движок
  пишет рядом), меньше «солёных» draw, которые не могут стать членами слоя. Числом не оценено — покажет E_a1 (`skipped` в `[nr] shcache`).
- Устройства без общей памяти (статические копии): защита страниц копий уходит целиком; цена сбоя страницы там ≈ десятки мкс.
- Поток игры: 0 (события — редкие вызовы; проба головы кольца — две загрузки на пакет draw при включённом переключателе).
- Остаток (агент-часы): таблица «номер в пуле → хэндл текстуры» и замена обхода образов для отвеченного draw — 2–3; третья таблица
  буферов — 1; запоминание записи покрытия в памяти диапазонов кэша теней (убрать двоичный поиск) — 1; по итогам E_v1 — правки
  классов. Телефон: серия §6.
