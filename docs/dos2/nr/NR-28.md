# NR-28 `DM_NR_LEANCALL` — лёгкий путь каждого вызова NVN (17.11.2026, ветка `dos2-nr28`)

Шаг предложен NR-23 (§6 п. 1 и «Чего нет»: «быстрый вход обёртки большого стека не сделан, вероятно, это рычаг побольше»). База:
`dos2-nr23` (в ней nr09 + nr16 + nr23). **На телефоне не исполнялось ни строчки** (adb не запускался). Всё новое за `DM_NR_LEANCALL`,
умолчание 0.

## 1. Что стоил один вызов (до кода)
Каждый вызов NVN игры (≈ 14.6 тыс. за кадр на палубе, на потоке записи) у DOS2 (сборка с `DM_GAME_D3`) идёт так:
thunk (`nvn_thunks.S`: `stadd` счётчика слота, загрузка функции слота, `br`) → `_nvn_bigstack_entry` (`nvn_entry.S`: кадр 240 байт на
**гостевом** стеке, сохранение x0–x7 и q0–q7, номер слота) → `nvn_bigstack_top` (C: строка NR-23, вызов дескриптора TLS за `t_big`,
проверка диапазона, 3 пары callee-saved) → перезагрузка 16 регистров → смена стека → тело → обратно.

Замер на ПК: машинный код **собранного `libdm.so`** (thunk, обе обёртки, скомпилированная `nvn_bigstack_top`, тело `nvn_nop`) в Unicorn,
инструкции по классам (`nr_leancall_test.py --so`, часть B; тело не считается). Резолвер TLS: `libdm.so` грузится `dlopen`, у bionic это
динамический TLS — его быстрый путь смоделирован (17 инструкций, 7 загрузок); статический (2 инструкции) — нижняя граница.

| путь | инструкций | загрузок | записей | атомиков | косв. переходов | вызовов | mrs |
|---|---|---|---|---|---|---|---|
| старый (`=0`): stadd-thunk + обёртка + `nvn_bigstack_top`, TLS динамический | **94** | 30 | 16 | 1 | 3 | 3 | 2 |
| то же, TLS статический | 77 | 22 | 14 | 1 | 3 | 3 | 1 |
| старый, уже на большом стеке | 91 | 30 | 16 | 1 | 3 | 3 | 2 |
| **лёгкий (`=1`)**: простой thunk + `_nvn_lean_entry`, смена стека | **40** | 6 | 3 | 0 | 2 | 1 | 1 |
| лёгкий, уже на большом стеке (хвостовой вызов) | 32 | 4 | 1 | 0 | 2 | 0 | 1 |
| лёгкий вход со stadd-thunk | 39 | 5 | 2 | 1 | 2 | 1 | 1 |

**Минус на вызов: 54 инструкции, 24 загрузки, 13 записей, 1 атомик, 2 вызова** (вызов C и вызов резолвера TLS).

Что из этого лишнее и что сделано:
| Часть | Зачем было | В `=1` |
|---|---|---|
| `stadd` в thunk | счётчик вызовов слота; читают только строки `[nvn] 帧 N：… 次调用` (первые 3 кадра и раз в 300) и `DM_NVN_TSV` | thunk-и ARMv8.0 (`nvnth80_<i>`, уже есть и испытаны на A53/A73): `ldr/add/str` без атомика. Цена: при гонке двух потоков на одном слоте теряется инкремент; `=2` меряет, сколько |
| кадр 240 байт на гостевом стеке + 16 регистров | только потому, что перед телом вызывается C | ничего не сохраняется: до тела трогаются только x9–x11 / x16 / x17 |
| вызов `nvn_bigstack_top` + TLS-дескриптор `t_big` | найти большой стек потока | таблица `nvn_lc_tab[hash(tpidr_el0)] = {указатель потока, вершина}`: одна `ldp` после 4 АЛУ-инструкций хэша, без C и без TLS |
| строка NR-23 (`g_nc_count`) в `nvn_bigstack_top` | счёт `=2` NR-23 | лёгкий путь её не проходит, поэтому `=1` с `DM_NR_NOCALL=2` не включается (строка в лог) |
| «смена стека на каждом вызове, когда уже на большом» | — | в игре почти все вызовы идут с гостевого стека (на большом — только обратные вызовы и NR-23 `=1`). Лёгкий вход на месте = хвостовой вызов (32 инструкции против 40). Исполнять `ExecuteCommandList` движка целиком на большом стеке сэкономило бы ещё ≈ 8 инструкций на вызов (≈ 2–3 нс, ≈ 0.03–0.04 мс за кадр) ценой хука в коде игры — **не делается**, выигрыш не стоит риска |

Попутные находки (не исправлялись, кроме того, что лёгкий путь их не имеет):
- старая обёртка **портит x8** (регистр адреса возвращаемой структуры) и x9–x15 / q16–q31 вызовом C до тела. Сейчас безвредно (ни одно тело
  не берёт x8), лёгкий вход сохраняет всё, кроме пяти scratch-регистров (тест проверяет все x0–x28 и q0–q31 у тела);
- `DM_NVN_TRACE=1` под обёрткой большого стека: обёртка передаёт в `x16` **номер** слота, а `_nvn_trace_entry` ждёт **адрес** — номер
  получится мусорный (давняя ошибка D3-линии; с трассой здесь не работаем);
- NB-15 `DM_NB_FOREIGN`: обход кадров `nbf_caller` (не дальше 256 КиБ от первого кадра) из тела на большом стеке до записи обёртки на
  гостевом стеке почти никогда не доходит. С лёгким входом запись кадра `{x29, x30 гостя}` лежит на вершине большого стека, рядом с телом —
  вызывающий в main находится. Счётчики NB-15 при `=1` станут точнее (не путать с регрессией при сравнении прогонов).

## 2. Что сделано
### 2.1 `_nvn_lean_entry` (`dm/gfx/nvn/nvn_entry.S`, 31 инструкция)
`mrs tpidr_el0` → хэш `t = tp >> 12; t ^= t >> 10; t ^= t >> 20; t & 4095` → `ldp {tp, top}` → не свой (первый вызов потока, слот
занят другим потоком): `b Lnvn_bigstack` — **локальный** переход в старую обёртку (не через PLT: x16 остаётся адресом слота), всё как
раньше. Свой: номер слота в x16 (соглашение под обёрткой большого стека — его читает `nvn_prof2_entry` NR-16), функция из
`nvn_real_big[i]`; `top − sp ≤ 1 МиБ` (та же проверка, что в C) → хвостовой вызов тела на месте; иначе запись кадра 32 байта на вершине
большого стека `{x29, x30, sp вызывающего}`, `sp = x29 =` этот кадр, `blr`, восстановление, `ret`. На гостевом стеке не пишется ничего.

### 2.2 Таблица и C (`dm/gfx/nvn/nvn_leancall.inc`, включается в `hle_nvn.c` перед `nvn_bigstack_top`)
- `nvn_lc_tab[4096]` (64 КиБ): запись потока пишется один раз — сначала CAS указателя потока (0 → свой), потом вершина (release); только
  этот поток может с ней совпасть. Никогда не очищается.
- Поток с тем же указателем, что у умершего (bionic отдаёт новому потоку отображение старого), **забирает его большой стек**: живой
  поток с этим указателем один, умерший не исполняется — стек свободен (старый код его просто терял, 1 МиБ на поток).
- `nvn_bigstack_top`: одна строка `if (__builtin_expect(g_lc_mode, 0)) return nvn_lc_top(sp);` после строки NR-23. `nvn_lc_top`:
  выделение / забор стека, регистрация, то же решение, что раньше; `=2` — сверка.
- `nvn_thunk_tab()` — единственный выбор таблицы thunk-ов (`nvn_lookup`, калибровка NR-16, `nvn_nc_ready` / калибровка NR-23):
  `=1` — простой набор на любом CPU, иначе как раньше (LSE или ARMv8.0 по CPU). `NVN_BIG_FN(f)` — «обёртка большого стека или лёгкий
  вход» для `p2_impl` / установки `DM_NVN_PROF=2` и `nc_impl` NR-23.
- Установка (`nvn_lc_install` в `nvn_lookup`, после обёртки большого стека, до `DM_NVN_PROF=2`, который встаёт под любую из двух):
  только aarch64 Linux / Android (на macOS указатель потока в `tpidrro_el0`); выключается при `DM_NVN_BIGSTACK=0` и для `=1` при
  `DM_NR_NOCALL=2`; `=1` меняет `fn` только в слотах, где стоит `_nvn_bigstack_entry`.
- Калибровка (`=1` и `=2`, один раз после 600 кадров, **отдельный поток хоста**, не гостевой): на каждом CPU, куда пускает cpuset —
  30 мс занятости, затем по 4096 вызовов слота-пустышки (лучший из 5): stadd-thunk и простой thunk (→ вход слота), старая обёртка и лёгкий
  вход с маленького своего стека (как с гостевого) и на месте (из `nvn_on_bigstack`), тело напрямую; частота из `scaling_cur_freq`.
  Итог на CPU: старый вызов целиком, лёгкий целиком, экономия в нс и тактах. Внутри тела калибровать нельзя: тело уже на большом стеке,
  а старая обёртка с чужого стека прыгнула бы на его вершину поверх живых кадров.

### 2.3 Строки и разбор
- установка: `[nvn] DM_NR_LEANCALL=1 (NR-28): N NVN slots go through the lean entry …` / `=2 … stay on the big-stack wrapper, every call
  compared …`; `[nvn] thunks: plain counter (DM_NR_LEANCALL=1, the CPU has LSE)`;
- калибровка: `[nvn] leancall calibration (…): cpu0 X GHz: old A ns (thunk stadd … + wrapper …), lean B ns (plain thunk … + entry …),
  in place old … / lean …, body …; saved S ns = C cycles; cpu1 …`;
- раз в 10 с из `nvnQueueSubmitCommands`: `=1` — `[nvn] leancall (DM_NR_LEANCALL=1, …): N NVN calls a frame through the lean entry;
  passed on to the old wrapper P a frame (…); threads in the table T, without (hash slot taken) W, stacks taken over K; saved X ms a frame
  on cpuR (S ns a call), Y ms on the slowest calibrated core`. «Passed on» включает и вызовы `nvn_on_bigstack` NR-23 `=1` (он идёт через C);
  `=2` — `… N calls a frame compared (M on this submitting thread), the lean entry would take the big stack in place … and pass on …;
  bad B (total …); counters: wrapper …, thunks (atomic) …, plain counter … (lost L = …% when threads race); saved by =1 …`; расхождения —
  `【红】[nvn] leancall check (DM_NR_LEANCALL=2): …` (первые 16).
- `tools/dos2_cpuprof.py <лог>` печатает `NR-28 (DM_NR_LEANCALL) calibration …` и `NR-28 (DM_NR_LEANCALL=m): … saved X ms a frame … ->
  GO for =1 / marginal / do NOT run =1`; самотест сверяет форматы с C.

| значение | что |

| **0** | как раньше: слоты, thunk-и (stadd на LSE), обёртка. Единственная разница — одна загрузка + непринятый переход в `nvn_bigstack_top` (как строка NR-23) |

## 6. Ожидаемый выигрыш (модель [м], не замер; замер даёт строка калибровки)
Модель: большое ядро ≈ 3.5 инструкции за такт на таком прямом коде, + 12 тактов на атомик, + 2 такта на лишний косвенный переход, + 1 на
вызов, 3 ГГц; маленькое in-order ядро (A520 / A55) — ×3. Старый путь ≈ 15.3 нс, лёгкий ≈ 4.8 нс: **≈ 10.5 нс на вызов на большом ядре,
≈ 31 нс на маленьком**.

| Класс | на кадр (14.6 тыс. вызовов, палуба) | Замечание |
|---|---|---|
| Mi 14 / Adreno 750 (X4 / A720) | поток записи −0.15 мс из 4.9 (≈ 3 %) | упор в GPU: fps не изменится, только CPU / тепло |
| S7 / 7+ Gen (A715 / A720 на 2.4–2.8 ГГц) | −0.17…0.2 мс | |
| MTK Dimensity 8x00 (A715 / A510), G99 (A76 / A55) | −0.2…0.3 мс на большом ядре; −0.46 мс, если поток записи на A55 / A510 | упор в CPU транслятора: поток записи — другой поток, кадр короче, только если он на критическом пути |
| ARMv8.0 (A53 / A73, без LSE) | −0.1 мс большое / −0.3 мс маленькое | у них thunk уже простой: экономится только обёртка |
| GPU (любой, в т. ч. тайлеры Mali / PowerVR) | 0 | поток команд байт в байт тот же |

В тяжёлых сценах вызовов больше (больше draw) — выигрыш пропорционален. Атомик `stadd` — самое неточное место модели (на ядрах, где
линия слота в L1 Unique, он дешевле 12 тактов): калибровка печатает stadd-thunk и простой thunk отдельно.

## 7. Риски
- Путь на телефоне не исполнялся. Сначала `=2` (сверка, исполняется старое), потом `=1`.
- Указатель потока: гостевой код не трогает настоящий `tpidr_el0` (загрузчик переписывает `mrs/msr tpidr_el0` игры в слот ключа,
  `dm/host/thread.c`), на этом уже стоит `DM_NVN_PROF=2` NR-16. Если когда-нибудь поток сменит `tpidr_el0`, лёгкий вход просто не найдёт
  своей записи и уйдёт на старый путь (не на чужой стек: запись совпадает только с тем указателем, что её записал).
- Таблица не чистится: игра запускает короткоживущие потоки; если они зовут NVN, слоты заполняются, новые потоки уходят на старый путь
  (строка `without (hash slot taken)`). Корректность не страдает.
- `[nvn] 帧 N：… 次调用` / `DM_NVN_TSV` при `=1` считаются простым счётчиком (возможны потерянные инкременты; `=2` печатает, сколько).
  Калибровка однажды добавляет ≈ 6 × 4096 × число CPU вызовов слота-пустышки в эти счётчики (в одном отчёте 300 кадров).
- Калибровочный поток держит 1 МиБ большого стека после выхода (как любой поток с NVN; запись таблицы может забрать следующий поток).
- `DM_NB_FOREIGN` (NB-15) при `=1` находит вызывающего чаще (§1) — счётчики прогонов `=0` и `=1` не сравнивать напрямую.

## 8. Чего нет
- `ExecuteCommandList` движка на большом стеке (≈ 0.03 мс за кадр по модели, хук в коде игры) — не делается (§1).
- Быстрого входа для `nvn_on_bigstack` (NR-23 `=1`, одна смена на draw ≈ 1 тыс. за кадр) нет: он идёт через C, как раньше; по модели ≈ 0.01 мс.
- Счётчики вызовов по потокам (вместо общего по слоту) — нет: строку `次调用` читают только логи.
- Умолчание по семейству GPU не нужно; после телефона с `bad 0` и положительной калибровкой умолчание можно ставить 1 для всех.

## 9. Прогоны на телефоне
**R-NR28a — сверка и калибровка (один прогон):** `dm/env`:
```
DM_NR_LEANCALL=2
DM_NR_CPU=1
```
Сцена: палуба 60 с, затем тяжёлая (бой / город) 60 с. Ждём: `[nvn] DM_NR_LEANCALL=2 (NR-28): … stay on the big-stack wrapper …`; после
600 кадров одна строка `[nvn] leancall calibration (DM_NR_LEANCALL=2, …): cpu0 … saved … cycles; … cpu7 …` (по всем ядрам — числа на
класс ядра); каждые 10 с `[nvn] leancall (DM_NR_LEANCALL=2, …): … bad 0 (total 0); counters: … lost … ; saved by =1 X ms a frame on cpuR`.
Читать: `python tools/dos2_cpuprof.py <лог>` → строки `NR-28`. Решение: `bad 0` и нет `【红】[nvn] leancall check` → R-NR28b; потерянные
инкременты «plain counter» ≪ 0.1 % — простые thunk-и годятся.

**R-NR28b — ABBA по 60 с в одной сцене:** A = `DM_NR_CPU=1 DM_NVN_PROF=2`, B = то же + `DM_NR_LEANCALL=1`. Ждём в B:
`[nvn] DM_NR_LEANCALL=1 (NR-28): N NVN slots go through the lean entry …`, `[nvn] thunks: plain counter (DM_NR_LEANCALL=1, …)`, каждые 10 с
`[nvn] leancall (DM_NR_LEANCALL=1, …): … passed on to the old wrapper ≈ 0 a frame …; threads in the table T, without 0 …`; картинка та
же, красных строк нет, падений нет. Сравнивать: `[cpuprof] DM_NVN_PROF=2: … untimed call X ns` (A против B — это и есть цена thunk +
обёртки против thunk + лёгкого входа на том ядре, где шла калибровка NR-16), `[cpuprof] threads` — мс на кадр потока `rec`,
`[cpuprof] nvn … ns a call`; `NVN PERF` — fps / draws те же.
