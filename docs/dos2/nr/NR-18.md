# NR-18 — ASTC-кэш не читать из write-combined памяти (`DM_NR_ASTCREAD`, по умолчанию 1)

Ветка `dos2-nr18` (база `dos2` 94d287d). Шаг из `docs/dos2/nr/AUDIT-REMAINING.md` (ветка `dos2-nraudit`), перенос TL2 PERF-X15
(`docs/port-kb/performance.md`, TL2 `tl2-port-repo` 1f3ef76).

## Что было
`astccache::upload` (`xbg_game.cpp`) делал `pread` блоков записи кэша прямо в отображённый stream-буфер и затем `xbg_ac_sanitize`
читал его обратно по 16 байт. Память stream-арены — `HOST_VISIBLE | HOST_COHERENT` без `HOST_CACHED`: в логах телефона
`NVN arena chunk cached=0 memoryType=0 flags=0x7` (Mi 14 Ultra), на Mali тот же тип 0x7 (KB `gpu-mali.md`: у Mali есть только 0x7 и 0xb,
`find_memory(VISIBLE, COHERENT)` берёт 0x7), на PowerVR нет кэшируемых когерентных типов вовсе. То есть это write-combined память, и
каждое чтение sanitize — некэшируемое. У TL2 это было 60 % кадра открытия инвентаря: 33,9 МБ за 252 мс, после фикса 25 мс.

В DOS2 через этот путь идут почти все текстуры на GPU без BC (Mali / PowerVR / Xclipse: BC1 / BC3 — 91 % байт паков, кэш включён
`DM_TEX_ASTC_CACHE=auto`): и записи пака setup (`pad[0] = 1`, `pack_fd`), и записи ленивого кэша (`fd`).

## Что сделано
- `xbg_astc_cache.h`: `xbg_ac_read_staged(read_at, bytes, dst, bounce, chunk)` — чистая функция (тест гоняет тот же код). С `bounce`:
  куски по `XBG_AC_READ_CHUNK` = 256 КБ (кратно 16, влезает в L2): `pread` в кэшируемый буфер, sanitize там, один последовательный
  `memcpy` куска в staging (только запись в WC). Без `bounce` — старый путь (чтение и sanitize прямо в `dst`). Результат в `dst`
  побайтно одинаков: прочитанное, хвост короткого чтения (ошибка / конец файла) нулями, затем каждый нулевой 16-байтный блок → void
  extent (потерянный хвост — прозрачный чёрный, как было). Возвращает прочитанные байты, число исправленных блоков, errno.
- `xbg_game.cpp` `astccache::upload`: зовёт её; буфер `thread_local` 256 КБ (одна штука на поток, создаётся при первой заливке);
  строка лога `NVN astc cache: read N uploads, X MB in Y ms (Z ms/MB; DM_NR_ASTCREAD=…)` на 8, 16, 32 … заливках (время чтения +
  sanitize + копии). Строка ошибки чтения та же (errno теперь именно от упавшего `pread`).

## Переключатель `DM_NR_ASTCREAD`
| Значение | Что |
|---|---|
| `1` (по умолчанию) | через кэшируемый буфер, один `memcpy` в staging |
| `0` | старое чтение прямо в WC-staging (только для A/B по времени) |

**Почему по умолчанию 1, а не 0 (вопреки общему правилу NR):** это не новая логика рендера, а тот же результат другим порядком
копирования — байты в staging совпадают со старым путём (тест ниже, 3 024 случая, включая ошибки и обрывы чтения), картинка не может
измениться. Риск только в памяти (+256 КБ на поток, который заливает) и в лишней копии там, где staging кэшируемый (на ПК +1,4 мс на
33,9 МБ; на телефонах из логов staging всегда 0x7, кэш на Adreno по умолчанию выключен). Задача шага разрешала включить такой фикс по
умолчанию; `=0` оставлен для замера на телефоне. Режимы 2 / 3 не нужны (нечего сравнивать / отравлять: байты те же по построению).

## Путь пака setup и остальное чтение кэша — проверено
- `tools/dos2_astc_cache.py` (ПК, setup): пишет пак обычными файлами, нулевые блоки заменяет void extent уже при кодировании (`encode`),
  `verify()` отвергает пак с любым нулевым блоком. WC здесь нет.
- `open_setup_pack` / `init` (движок): заголовок, индекс, журнал ленивого кэша читаются `pread` / `fread` в кучу — кэшируемая память.
- Блоки записей пака setup идут через тот же `upload()` (`src = pack_fd`) — фикс покрывает и их.
- Кодер `xbg_astc_lazy.cpp`: берёт копию хранилища в куче (`offer` → `j.storage`), пишет в файл `pwrite`, sanitize (`void_fix`) в своём
  векторе. WC нет.
- `key()` / `offer()` читают гостевое хранилище `t->mem`: на не-Adreno zero-copy в DOS2 выключен (`xbg_zero_copy_default` = только
  Adreno), гостевая память — обычная куча; на Adreno zero-copy — кэшируемые страницы AHB. WC-чтения нет. Замечание вне шага: при промахе
  `lookup()` и затем `offer()` одно хранилище хэшируется дважды (CRC-32 + Adler-32) — только в первом прогоне, пока кэш наполняется;
  NR-05 (`DM_NR_TEX`) и так отдаёт ключ из рабочего потока, отдельный шаг не нужен.

## Слияние с NR-05 (`dos2-nr05`)
NR-05 меняет в `astccache` `key()` (ключ из рабочего потока), строку в `init()` (`dm_nr_tex_want_key`) и вставляет `extern "C"
xbg_astc_storage_key` между `frame()` и `note()`. NR-18 меняет только `upload()`, три переменные перед ней и заголовок. По смыслу шаги
независимы: NR-05 решает, какая запись (ключ), NR-18 — как читаются её блоки. `git merge-tree dos2-nr18 dos2-nr05` — без конфликтов;
слитое дерево проверено NDK `-fsyntax-only`: 13 предупреждений, 0 ошибок. Порядок слияния любой.
Для **NR-22** (`DM_NR_TEXSTREAM`, рабочий поток пишет прямо в свой staging): ASTC-записи там читать тем же `xbg_ac_read_staged`
(буфер уже `thread_local`), а не `pread` в отображение.

## Ожидаемый выигрыш
| Класс | Выигрыш | Почему |
|---|---|---|
| Mi 14 / Adreno, по умолчанию | 0 | BC родной, кэш не используется (`not used (the device samples BC …)`) |
| Mi 14 с `DM_GFX_SIM_GPU=mali` | как у Mali ниже | staging тоже 0x7 |
| Mali / PowerVR / Xclipse | чтение блоков кэша ≈ ×10 быстрее (по TL2 7,4 → 0,75 мс/МБ на Mi 14; на A55 / A76 абсолют больше, отношение того же порядка) | путь почти всех текстур; вход в зону с 30–80 МБ из кэша: ≈ 220–600 мс → 22–60 мс на потоке трансляции, т. е. −100…500 мс хитча [м по TL2] |
| слабый CPU | то же; плюс меньше занятой шины памяти на время загрузки | |

Xclipse (RDNA): типы памяти на устройстве не видели; если первый `VISIBLE | COHERENT` у него кэшируемый, выигрыша нет, но и потери нет
(+1–2 мс на 34 МБ за лишнюю копию).

## Риски
- +256 КБ на каждый поток, который заливает ASTC (сейчас один — поток трансляции).
- Где staging кэшируемый — лишняя копия (≈ 4 % от ПК-замера, единицы мс на десятки МБ). На известных телефонах staging всегда 0x7.
- Поведение при ошибке чтения то же (хвост прозрачный чёрный), errno в логе теперь точный.

## Не сделано
- Замер на телефоне (нет доступа). Двойной хэш `lookup` + `offer` (см. выше) — не трогал.

## Прогон на телефоне, который это подтвердит (R-NR18, Mi 14 Ultra, ~15 мин)
Предусловие: ASTC-кэш с данными — пак setup в `Download/DivinityOriginalSin2Mobile/astc/dos2-astc.pack` или наполненный ленивый
кэш `Android/data/org.dos2.port/files/astc` (если его нет — один прогон с `DM_GFX_SIM_GPU=mali` по той же сцене, кодер его наполнит).
Бэкап `files/save` перед force-stop. Сцена: загрузка одного и того же сохранения (палуба корабля) + переход в соседнюю зону (Форт Джой),
одинаковый путь в обоих прогонах; после — force-stop.
1. `a18r0`: `DM_GFX_SIM_GPU=mali` + `DM_NR_ASTCREAD=0` (старое чтение).
2. `a18r1`: `DM_GFX_SIM_GPU=mali` (по умолчанию `=1`).

Строки, которые решают:
- `NVN arena chunk cached=0 memoryType=… flags=0x7` — staging write-combined (иначе выигрыша и не ждём);
- `NVN astc cache: using setup pack … + lazy …` — кэш включён;
- `NVN astc cache: read N uploads, X MB in Y ms (Z ms/MB; DM_NR_ASTCREAD=…)` — ждём Z ≈ 5–8 в `a18r0` и ≈ 0,5–1 в `a18r1` при
  близких N / X;
- `NVN astc cache: lookups …: … zero blocks fixed K, read errors 0` — K одинаков в обоих (0 ожидаемо), ошибок чтения нет;
- картинка та же (скриншоты одних мест), хитчи входа в зону короче (`[hitch]` / время кадров загрузки, если включён аудит).
