# NR-19: VK-UBO-MEMO (port-common `desc-memo-keys`) + `cpu-place` / `adpf-boost` в DOS2

Ветка `dos2-nr19` (worktree `dos2-port/wt-nr19`, от `dos2` 94d287d). Только ПК, на телефоне не запускалось.

| коммит | что |
|---|---|
| `7dc29e0` | VK-UBO-MEMO: свой счётчик `ubosnap`, исполняемый тест кода мемо, блок NR-19 в `source_structure_test.py` |
| `1a0d412` | port-common `cpu-place` (APP-14) через `tools/sync_common.sh` |
| `cfcb336` | port-common `adpf-boost` (PERF-E14 + PERF-X08) через `tools/sync_common.sh` |

## 1. desc-memo-keys: слияние уже было сделано, «manual merge» у pc_check ложный

Аудит (`AUDIT-REMAINING.md`, NR-19) считал VK-UBO-MEMO отсутствующим, потому что `pc_check` пишет `desc-memo-keys: MISSING (module
needs a manual merge)`. На самом деле в `dos2` есть обе правки модуля:

- **VK-DRIVER-KEY** — `d2ffc82` (14.11). DOS2 и есть эталон этой правки: `DRIVER0 ? buf_gen : tex_gen`. Хунк модуля не совпадает только
  потому, что посреди строки стоит DOS2-комментарий `/* [DOS2] KB VK-DRIVER-KEY ... */`.
- **VK-UBO-MEMO** — `2f4f2b1` + уточнение `e6e9611` (15.11): `else if(!UBO_DYN(dmode,b) && b.source==XBG_SOURCE_UNIFORM && r.address &&
  r.size){ok=false;...}` стоит перед словами ключа `address+size`. Текст отличается от `patches/ubo-snapshot.patch` (у DOS2 свой
  двухстрочный комментарий вместо пятистрочного), но условие то же, что у D3 `3e45827`.

То есть «предусловие для PowerVR» уже выполнено. Шаг проверил, что **ни один DOS2-путь его не обходит**:

| путь | обходит ли правило |
|---|---|
| NB-11 `DM_NB_DESC=1` (`nbskip`: ключ не строится) | нет: повтор допускается только от записи мемо предыдущего вызова (`nbdesc::P.valid` сбрасывается на каждом вызове, `commit()` — только на попадании / вставке). Набор, который правило отвергло, записью мемо не становится → следующий вызов получает `NBDS_PREV`. Привязка UBO, прочитанного ключом, → `NBDS_USTAT` |
| `memo_front` (повтор последнего ключа) | нет: только после построенного ключа и `ok` |
| `xmemo` (постоянные записи) | нет: вставка только при `ok` |
| `set_cache` (`descriptors_build`) | нет: он идёт после сборки записей и берёт набор только с теми же записями (буфер + смещение того снимка, что взят сейчас), то есть не подставляет старый снимок вместо нового |
| NR-08 `DM_NR_DESC` (ветки nr08 / nr09) | свой путь (блоки = смещения кольца NR-06, живая память, а не снимок); при `UBO_DYNAMIC=0` его запасной путь — этот `descriptors()` с правилом |

### Что изменено в коде (`7dc29e0`)

- Отказ по правилу VK-UBO-MEMO считался в `desc_memo_why[3]` вместе с `dynbuf` (отказ проверки попадания). Теперь у него свой
  `desc_memo_why[5]` (элемент был свободен) и поле в конце строки:
  `NVN PERF setcache ... why=texel/simg/dm/dynbuf/store/ubosnap` (как `ubosnap` у Eternal `c6bd4b0`). Поведение рендера не меняется ни в
  одном режиме; в режимах 1 / 2 ветка не выполняется (`ubosnap0.0`). Отдельного `DM_NR_*` нет: это счётчик, а не новый путь.
- `tests/ubo_memo_snapshot_test.py` (новый): вырезает из `xbg_game.cpp` как есть случаи `UNIFORM/STORAGE` и `DRIVER0/2` ключа мемо и
  макрос `UBO_DYN`, собирает в wasm32 (NDK clang) и гоняет в node модель «игра переписывает константы по тому же адресу между draw».
  Проверяет: режим 0 никогда не берёт запечённый снимок (вторая отрисовка видит новые данные, `ubosnap` = 2 на 2 draw, попаданий 0);
  режимы 1 / 2 сохраняют мемо и видят новые данные; несвязанный UBO / размер 0 / storage — мемо сохраняется; ключ блока драйвера
  идёт за `buf_gen` (DRIVER0) / `tex_gen` (DRIVER2), при динамическом — константа `0xD0D0+source`. Негативные контроли: код без строки
  VK-UBO-MEMO падает с 10 (D3 #22), строка драйвера до `d2ffc82` — с 60.
- `source_structure_test.py`: блок `nr19_check` (правило один раз перед `address+size`, VK-DRIVER-KEY, `ubosnap` в строке, NB-11 только
  от записи мемо — `P.valid=false` на входе и ровно 2 `commit()`).

### Цена на PowerVR (важно для следующего шага)

Режим 0 дорог сам по себе, правило лишь добирает остаток: на палубе DOS2 рисует ~1155 draw / кадр, все с UBO игры, и на Adreno
(режим 1, в ключе только размер UBO) все они — попадания мемо (rd2: `memo_hits=1155.0 memo_misses=0.0`, `hit_total` 2–3 мс / кадр
≈ 2–2.8 мкс на попадание). В режиме 0 в ключе стоит адрес UBO, а константы DOS2 идут из кольца движка (NR-06) — адрес новый почти на
каждом draw, так что мемо промахивается и без правила; правило дополнительно отнимает только попадания наборов, чьи UBO лежат по
повторяющемуся адресу (как раз те, что давали «шипы» у D3). На ПК не измерить, какая это доля: телефонных логов с `ubo_dynamic=0` у
DOS2 нет. Полная сборка набора в DOS2 отдельно не мерилась (rd2: 82 промаха = 6.76 мс, но это первые сборки с загрузками);
**[оценка]** 10–20 мкс на draw → при ~1100 промахах +11–22 мс CPU транслятора на кадр на ядре класса Mi 14, на PowerVR-телефонах
(Dimensity 7020 / A78) больше — то есть DOS2 на PowerVR-политике упрётся в транслятор, с правилом или без. Это не решается здесь
(правило — корректность), а следующими шагами:
1. NR-08 `DM_NR_DESC` на PowerVR (его режим «статический блок = слово кортежа» как раз для `UBO_DYNAMIC=0`);
2. политика: `UBO_DYNAMIC=2` для PowerVR (D16 PVR-06 держит его с 09.11, но режим 2 DOS2 — «только блоки на draw», не D16-шный «только
   читаемые стадией», и отключение dynamic у PowerVR в DOS2 стоит из-за переполнения неиспользуемых dynamic UBO — нужен свой разбор
   и телефон с PowerVR).

Прогон R-NR19a ниже даёт реальные числа вместо оценки: `ubosnap` = draw, отвергнутые правилом; цена режима 0 целиком — `desc_ns_per_frame build`
и `submit_cpu_ms` против того же прогона с `DM_GFX_UBO_DYNAMIC=1`.

## 2. cpu-place и adpf-boost: применены (ложатся чисто, с раскладкой потоков DOS2 не конфликтуют)

`pc_check` (`--nso work/exefs-update`): оба `MISSING (module applies cleanly)` → `sync_common.sh ... --yes` → `present, in sync`.
`pc-core` отказан (у DOS2 свой `pc.h`, `pc_note` определён — как у pipe-marker-mmap / nvn-ctlmem). Файлы модуля побайтно равны
`port-common/modules/*/files` (`hle_cpu_place.c` — плюс строка отчёта `[pc]`).

### Почему конфликта нет (раскладка потоков DOS2)

- **Хост-потоки DOS2 модуль не трогает**: `cpu-place` ставит маски только транслятору (tid из `pin_update`) и гостевым потокам
  (`thr_guest_threads`). `dm-nbmt` (NB-20b, `DM_NB_MT=3` по умолчанию) сам ставит себе все ядра (`worker_start`), `dm-nbx0`, `xbg-bcdec`,
  воркеры NR / NB, `dm-present` — как раньше.
- **Present-поток уже готов к модулю**: `vulkan_present.cpp` (present-thread, `PT_HAVE_PLAN`) берёт маску `present` плана
  (`all & ~translate` при ≥ 2 кластерах) — та же, что сейчас «all but the pin» (rd2: транслятор на cpu7 = `80`, present `7c`).
- **Транслятор**: на Mi 14 Ultra правило ёмкости даёт то же ядро, что старое `fastest_cores` (cpu7, X4); на чипах, где
  `cpuinfo_max_freq` врёт или кластеров три, — ядро по `cpu_capacity`.
- **Главный гостевой поток** (kind 1: без guest entry / arg; в DOS2 это поток, который пишет NVN — rd2 `recording thread 12301`): маска
  сильных ядер без ядра транслятора. **Прочие гостевые** (все `org.dos2.port`): все ядра, кроме ядра транслятора (сейчас — все ядра,
  включая его). Малый кластер им не запрещён, так что «не та роль → только малые ядра» здесь не случается.
- **ADPF**: DOS2-шные куски `perf_android.c` сохранены (период по частоте экрана при `DM_DOS2_FPS=0`, GPU-время в
  `reportActualWorkDuration2`, `dm_thermal_headroom` для лесенки R2). Цель = `min(период, 33.33 мс)` = период на 30 / 60 fps DOS2, то
  есть та же цель, что сейчас. Участники сессии — по нагрузке со списком запрета; `dm-nbmt`, `dm-nbx0`, `dm-present`, `nvn-translate` в
  запрет не входят; главный поток добавляется по роли `cpu-place`. Вызывающий сессии — present-поток, как и было.
- Java: `GameStateHint.java` собирается `javac --release 17` с `android-36/android.jar`; `DmActivity` — одна строка после
  `started = true` (поле `resumed` есть).

### Что требует DOS2-специфики и НЕ сделано (NR-16 / NR-17)

- **Роль `jobs`**: `DM_CPU_JOB_NAMES` по умолчанию `JobWorker` (D3). Имена гостевых потоков Larian неизвестны (на хосте все
  `org.dos2.port`; гостевое имя из SDK `ThreadType+0x1a0`), так что роль пуста, воркеры игры — в «прочих гостевых». Имена даст
  первый же прогон (`[cpu] placed` печатает гостевые имена) или NR-16; потом — значение по умолчанию в DOS2-блоке `jni_android.c`.
- **Строка ⚙ «Ядра CPU»** (`DM_CPU_CORES` + `nativeCpuCores`): JNI есть, строки в `frontend-common` gear DOS2 нет.
- **Источник сцены для GameState** (`dm_android_scene_game`): нет; `dm_loadscreen_up` (diag.c, D3-шные UI-сообщения) в DOS2, скорее
  всего, не поднимается → режим GameState «unknown», флаг загрузки 0.
- Хост-тесты модулей (`t_cpu_place.c` 163 проверки, `t_cpu_place_rt.c` 22) требуют POSIX (WSL здесь нет); файлы те же, что прошли их
  15.11.

### Поведение по умолчанию меняется

Оба модуля включены по умолчанию (как у эталона D3; порт-коммон не меняет умолчаний). Переключатели A/B «как раньше»:
`DM_CPU_TOPO=index` (транслятор по старому правилу, остальное свободно), `DM_CPU_CORES=all` (без масок вовсе),
`DM_ADPF_BOOST=0`, `DM_GAME_STATE=0`, `DM_ADPF_TARGET_MS=period`. Если основной сессии нужно строго «0 = старое», ветку можно влить
без `1a0d412` / `cfcb336` (они независимы от `7dc29e0`).

## 4. Ожидаемый эффект

| класс | VK-UBO-MEMO (уже было) + `ubosnap` | cpu-place + adpf-boost |
|---|---|---|
| Mi 14 / Adreno 750 | 0 (`ubo_dynamic=1`, ветка не выполняется) | ≈ 0: частоты держит сам; транслятор на том же ядре |
| Adreno / Mali / Xclipse (dynamic UBO) | 0 | слабые 4+4 / 2+6 (SD 7, G99): без «замедленной съёмки» после стартового буста, fps ×1.3–2 в CPU-упоре **[м, D3 #23, не подтв.]** |
| PowerVR (`UBO_DYNAMIC=0`) | правильная картинка (нет «шипов»); цена — см. §1 (транслятор) | как выше |
| слабый CPU | — | маски переустанавливаются после onResume и раз в 2 с (cpuset / HyperOS их переписывают) |

Риски: `cpu-place` — неверный главный поток (если тяжёлый поток DOS2 не kind 1, он всё равно «прочий гостевой», малые ядра ему не
запрещены); переустановка масок каждые 2 с — системный вызов на поток. `adpf-boost` — на горячем телефоне подсказки «нагрузка растёт»
тянут против лесенки R2 (сначала `DM_ADPF_BOOST=0`); `APerformanceHint_sendHint` — непубличный символ Android 14–15 (`DM_ADPF_BOOST=2`).

## 5. Прогоны на телефоне (с разрешения хозяина; бэкап `files/save`, потом force-stop)

**R-NR19a — VK-UBO-MEMO под PowerVR-политикой** (Mi 14 Ultra, палуба корабля с персонажами + бой, 90 с):
`dm/env`: `DM_DBG=1`, `DM_GFX_SIM_GPU=powervr`. Потом то же с `DM_GFX_UBO_DYNAMIC=1` для сравнения.
Доказывают: `NVN gpu policy: ... ubo_dynamic=0`; персонажи / NPC / пол без «шипов» и разлёта (скриншот); `NVN PERF setcache ...
memo_hits=... memo_misses=... why=.../ubosnap N` — N ≈ числу draw с UBO, `memo_hits` ≈ 0; цена: `NVN PERF desc_ns_per_frame build=…` и
`submit_cpu_ms` против прогона с `UBO_DYNAMIC=1` (там `ubosnap0.0`). Обычный прогон без SIM: `ubosnap0.0` всегда.

**R-NR19b — cpu-place + adpf-boost** (умолчания, без флагов; палуба 60 с, home → назад, ещё 60 с):
`boot.log`: `[pc] cpu-place: applied (mode auto, capacity rule, translate … main … jobs free guests …)`, `[cpu] topology:`, `[cpu] plan:`,
`[cpu] placed (...)` — **записать гостевые имена потоков** (для `DM_CPU_JOB_NAMES`, NR-17), `[cpu] where 30s:`, после возврата
`[cpu] resume:`; `[pc] adpf-boost: applied (session open, target … ms (budget 33.33) …)`, `[perf] ADPF session threads: …` (ожидаются
dm-present, nvn-translate, main, dm-nbmt), `[perf] ADPF 10s: … boost up U … reset S`, `[perf] ADPF workload reset (back in front)`,
`[perf] game state: …`. На Mi 14 fps и `submit_cpu_ms` как в rd2. A/B: `DM_CPU_TOPO=index DM_ADPF_BOOST=0 DM_GAME_STATE=0
DM_ADPF_TARGET_MS=period`. Эффект проверяется только на слабом CPU (тестер с G99 / SD 7: fps через 30–60 с игры, до и после).
