## 1. `DM_CPU_SELF` — маски ядер, которые HyperOS сбрасывает

Факт (play-1118, `[cpu] where`): translate с маской `80` (cpu7, X4) **ни разу** не замечен на cpu7 в тяжёлых минутах, 18–25 / 120 замеров
на A520 (cpu0/1); main с маской `7c` — 12–23 / 120 на A520; «masks set again» +60 в минуту = обе маски сброшены в `ff` к каждой
проверке раз в 2 с. Значит, сброс происходит много чаще 2 с, и 2-секундная проверка почти ничего не держит.

Что сделано (`dm/host/hle_cpu_place.c`, `cpu_topo.h`, одна строка в `hle_nvn.c`):
- поток транслятора (в `dm_cpu_place_translator`, его зовёт `pin_update` на каждом present) и главный гостевой поток (новый
  `dm_cpu_place_self` из `nvnQueuePresentTexture`, только DOS2) раз в кадр делают `sched_getaffinity` **на себе** (≈1 мкс) и, если маску
  сбросили, сразу ставят её снова. Проверяет только сам поток (`tid == gettid()`); чужой вызов с tid транслятора ничего не трогает;
- маска транслятора из одного ядра, сброшенная 3 раза за 10 с, **расширяется** до сильных ядер (`strong` = всё, кроме малого кластера:
  на Mi 14 `fc`, cpu2–7). Причина: система может сбрасывать маску, единственное ядро которой паркует / ставит на паузу (cpu7 не видели
  ни разу), — широкая маска держит поток хотя бы вне A520. Отказ `sched_setaffinity` тоже считается сбросом (паузнутое ядро может его
  не принять). 2-секундная проверка `dm-cpu` дальше держит ту же расширенную маску (`xlate_mask`);
- `DM_CPU_SELF=2` — только считать (и логировать первые 6), маски ставит лишь 2-секундная проверка, как раньше; `0` — выкл.

Строки: старт `[cpu] DM_CPU_SELF=1 (NR-CPU): ...`; первые 6 сбросов `[cpu] self (DM_CPU_SELF=1): translate tid N found its mask ff (want 80):
set again`; расширение `[cpu] self (DM_CPU_SELF=1): the translator's one-core mask 80 was reset 3 times in T ms: widened to fc ...`; в
`[cpu] where 60s: ...` хвост `; self (DM_CPU_SELF=1): translate C checks, reset found F (failed X), main C checks, reset found F (failed X),
translator mask fc (widened)` — **F / C = доля кадров, перед которыми маску сбросили**.

Если `nvnQueuePresentTexture` зовёт не главный гостевой поток (kind 1), проверка main — пустая (tid не совпал): в строке будет
`main 0 checks` — тогда нужен другой покадровый вход (например, `BeginRecording` потока записи).

Умолчание 1: это та же маска, которую модуль и так ставит каждые 2 с, только чаще; расширение лишь ослабляет пин. Цена ≈1–2 мкс на поток
за кадр (+1 вызов при сбросе). `DM_CPU_CORES` не меняется (auto / big / all дают те же маски; в `all` масок нет — проверять нечего).

Тест `dm/host/tests/t_cpu_self_rt.c` (WSL, gcc, `-D__ANDROID__`, поддельное дерево Helio G99: translate = cpu7, main = cpu6–7, 2-с проверка
отодвинута на 60 с, «система» = тест ставит `ff`): режим 1 — main возвращается к `c0` за ≤ 60 мс, вызов с чужого потока не трогает маску,
3 сброса транслятора → `c0` + строка «widened», после ещё одного сброса снова `c0`, счётчики в `where` (10 проверок); режим 2 — сбросы
логируются, маски остаются `ff` (7); режим 0 — ни одной строки self (7). **PASS** все три.

Внимание: `hle_cpu_place.c` / `cpu_topo.h` — файлы модуля port-common `cpu-place`; `pc_check` покажет «modified». Правку стоит перенести
в `port-common/modules/cpu-place/files` (+ тест) главной сессией — она полезна всем портам на HyperOS.

## 2. Разбивка CPU транслятора (`DM_NR_CPU=1`)

`NRCPU_SCOPE` = обычный `CPU_SCOPE`, но только при `DM_NR_CPU=1` (`nrcpu_on` из `cpf::init`) и только в кадрах выборки (1 из 32), так что
без ключа — загрузка и непринятый переход. Новые виды `xbg_cpu_timing.h` стоят после старых и печатаются в `NVN PERF parts_ms_per_frame`
только когда замерялись (без ключа строка байт в байт прежняя):
- `nbstate` — `nbstate::exec` (разбор `OP_X_NB_STATE` и исполнение его блоков; `program` внутри — свой вид);
- `nbdraw` — `nbdraw::exec` минус `draw()` (привязки NB-09 / NB-11 / NR-09R `pre`, хвост записи);
- `mtend` — `nbmt::end`: ожидание / помощь рекордеру NB-MT в конце сабмита (по NR-BN 2.6 мс / кадр — подозреваемый номер 1 в «other»);
- `nrdesc` — `nrdesc::serve` (NR-08; сам `Scope` не тронут: сверка `=2` идёт в его деструкторе после старого пути), вынимается из `draw`;
- `nrlane` — `nrdraw::lane` (NR-09, вместе со снимками вершин / индексов — они внутри свой `snapshot`), вынимается из `draw`.

Строка рекордера NB-MT (`xbg_nb_mt.inc` / `nb_mt.h`, только `DM_NR_CPU=1`): каждый пакет считается по op, 1 из 16 замеряется —
`[nr] cpu mt (DM_NR_CPU=1, NR-CPU; 1 in 16 packets timed): replay X ms in N vkCmd* a submission (by the timed sample); BindDescriptorSets
n x ns = ms; DrawIndexed ...` (по убыванию мс). Отвечает, что из 6 мкс / draw Turnip — draw, наборы или вершины.

Главный поток (`nvn_nb_state.inc`, `nvn_nr_direct.*`, `hle_dos2_nr_direct.inc`): в замеренном direct draw `nbs_before` (блок состояния)
меряет себя; строка `[nr] direct, ns a direct draw ...` получила `(NR-CPU: state block S, draw record R), the flush's binds + stack switch B`.

Что уже известно без прогона (из play-1118): у обслуженного draw вызовов почти нет лишних — lane сам фильтрует (`vkCmd* a served draw
3.79: pipeline 0.56, set 0.79, vertex 0.91, index 0.53, viewport / scissor 0.001`). Дедупликация на уровне пакетов NB-MT ничего бы не
убрала, поэтому не делалась; цена — работа самого Turnip на оставшихся вызовах. Наборы (0.79) меняются из-за динамических смещений
UBO (3.9 блока кольца на draw), вершины (0.91) — из-за разных VkBuffer zero-copy-чанков (статические копии NR-06 в логе: «static: 0
vertex / index binds» — путь не обслуживает ни одного draw). Это следующие рычаги рекордера, после строки `[nr] cpu mt`.

## 3. NR-TAPSET (`DM_NR_TAPSET`, умолч. 0)

Тап IR на каждом обойдённом draw делает `nb_read` на каждый сэмплируемый слот, а `nb_read` искал образ **линейно по всем ссылкам
открытого прохода** — квадратично в проходе (G-буфер / forward / UI-проходы Форта держат десятки-сотни ссылок). Теперь (`nb_plan.c`,
`nb_ir.h`): у кадра IR есть хэш-набор ссылок открытого прохода (2048 слотов, теги вместо очистки, догоняет ссылки, добавленные
кем угодно; проход > 1024 ссылок — снова скан, счётчик). Ссылки добавляются в том же порядке, что и раньше: IR бит в бит.
- `0` — скан (как было; набор не трогается); `1` — набор; `2` — оба, решает скан, расхождения считаются (`【红】` при ≠ 0).
- Строка (вместе с `[nb] ir`): `[nr] tapset (DM_NR_TAPSET=1, last report): R reads a frame through the set, H of them already held;
  passes over 1024 refs (scan) B; set vs scan differ D`.
- Тест `nr_cpu_test.c` §2: три IR (скан / набор / набор + скан) из одного случайного потока (проходы, draw по 1–12 чтений из 3000
  образов, op-ы, clear, барьеры, сбросы, сабмиты, проходы > 1024 ссылок) — равны узел в узел и ссылка в ссылку на каждом шаге (2.4 М шагов,
  9.35 М чтений), `rs_bad` 0; ссылка, добавленная мимо набора, находится; мутация «догонялка пропустила ссылку» ловится `=2`.
- Бенч (ПК): кадр как в play-1118 (1832 draw, 3.5 чтения, 40 материалов в большом проходе): **87 → 27 нс на обойдённый draw (−68 %)**;
  худший случай (400 материалов в каждом проходе): 249 → 48 нс (−81 %). На телефоне обходят ≈ 735 draw движка + ≈ 500 UI за кадр.

## 4. Отвергнуто: NR-TAPIMG (кэш образа слота)

Гипотеза: 600 нс тапа — промахи кэша по `g_wt_id_mem` (1 М id × 8 Б). Модель с настоящим IR, таблицей 8 МБ, id Форта вразброс и
«работой игры» между draw (64 / 256 строк кэша): таблица 246 / 299 / 335 нс, кэш слота 261 / 312 / 340 нс — **выигрыша нет** (−6…+1 %).
Время обхода — в `nb_read` (п. 3), а не в таблице. В код не вошло; модель оставлена в `nr_cpu_test.c` §1 / §3 как доказательство.

## 5. Не сделано и почему

- **Перенос работы с главного потока.** На direct draw main: блоки UBO движка 0.57–0.77 мкс (машинный код игры — не перенести),
  идентичность 0.2–0.45, тап 0.6, блок состояния + запись 0.86–1.1, привязки сброса + смена стека ≈ 0.6. Тап (IR) и блок состояния
  можно перенести только в поток, который идёт по потоку записи в том же порядке: транслятор (он и так узкое место, 15–22 мс против
  14.5 у main — перенос сдвинет, не уберёт) или новый рабочий «dm-nbtap» по журналу событий тапа, который должен закончить план до
  `dm_nb_submit`. Оценка 6–10 агент-часов + 2 прогона; делать после прогона R-CPU1 (с правильными ядрами main может перестать быть
  узким местом) и R-CPU2 (точная доля state / record).
- **NR-08 serve 1.9 мкс, NR-09 lane 1.85 мкс, «other» 5.55 мс** — теперь разбиты (`nrdesc`, `nrlane`, `nbstate`, `nbdraw`, `mtend`);
  правка вслепую не делалась. Кандидаты по коду: `mtend` (ожидание рекордера), `nbdraw` (295 нс / запись в play-1118 = 0.5 мс),
  `nrbuf::ubo` 3.9 раза на draw внутри serve (119 нс на решение по логу), снимки вершин (`snapshot` 2.65 мс / 4251 вызов, 2.2 МБ
  копий вершин за кадр от `sticky_miss` zero-copy).
- **NB-MT 6 мкс / draw** — см. §2: лишних вызовов нет, нужна строка `[nr] cpu mt`.
- ADPF `setPreferPowerEfficiency(false)` не добавлялся: у сессии это и так значение по умолчанию.

## 9. Прогоны на телефоне (главный агент, с разрешения хозяина; бэкап `files/save`, keyguard снят, Форт Радость у ворот, ≥ 60 с)
