## 1. NR-HEAT: почему «7 кадров»

Факт из лога: строки `[nr] heat (60 s, …): 3 samples` идут каждую минуту всю игру — сэмплер работал как задумано (F-строки каждые 20 с:
912, 932, 952 … 1353 с). Но все они до 1373 с помечены `TUT_Tutorial_A`; `location TUT_Tutorial_A -> FJ_FortJoy_Main` случилось только в
строке 119049 (≈1400 с) с 4617 КБ «прочитано недавно» — это открытие карты (большая текстура 1424x1602 рядом в логе). Тяжёлые окна
(2100 draw, 22–40 fps) — строки 80633–100000, т. е. ≈ 900–1370 с, всё под чужой меткой.

Почему голосование не увидело вход в Форт:
- **загрузка сохранения** не читает уровень из `Origins.pak`: `SaveNNNN.lsv` — тоже LSPK v13 (проверено на 18 сохранениях из
  `work/save-backup`): `globals.lsf` (3.6–5 МБ, состояние текущего уровня целиком), `meta.lsf` (1.5 КБ, имя уровня в values),
  `levelcache/<уровень>.lsf` (прошлые уровни). Голос считал только пять паков;
- чтение приписывалось целиком файлу, в котором оно **начинается** — буферизованное чтение, начатое в чужом файле, терялось
  (за всю игру FJ набрал 5 МБ из 46 МБ своих файлов в Origins.pak + CommunityMods.pak).

Исправление (`dm/host/hle_dos2_heat.c`, `dm/gfx/nr/nr_heat.{h,c}`, коммит d23d61d):
- открытие `*.lsv` на чтение: список файлов → `meta.lsf` (zlib, libdeflate из `dm/third_party` — теперь собирается и для DOS2) →
  LSF v3..v5 → секция values (LZ4 frame, свой декодер `nrh_lz4f`, связанные блоки) → известное имя уровня (целое слово, без регистра,
  чаще всех) → чтения `globals.lsf` этого дескриптора идут в голос за этот уровень. Меню загрузки читает только `meta.lsf` — не считается;
- чтение пака раскладывается по всем файлам уровня, которые оно перекрывает (`nrh_span_range`), по байтам;
- раз в минуту `[nr] heat: reads (60 s): N pak reads, X MB in level files (top-3), Y MB outside them, largest K KB; save loads S MB;
  location L` — следующий прогон сам покажет, чем читает игра; первые 12 открытий сохранений — строка `[nr] heat: save …: level …`.
- `tools/dos2_shader_heat.py --relabel FJ_FortJoy_Main@901-1370` (коммит 53e0e0e) — переразметка уже снятого лога.

Тест: `nr_heat_test` 157 проверок с реальным meta (156 без него, полный прогон run_tests: 70 PASS): поиск записи LSPK, LZ4 frame (связанные блоки, сырой блок, обрыв, без end mark), LSF
(частота, целое слово, регистр, v6 / не LSF / обрезанные values), диапазоны; реальная проверка: Origins.pak (109 имён) + `meta.lsf`
настоящего сохранения → `TUT_Tutorial_A`. Сохранения Форта в бэкапах нет (все 18 — палуба), FJ покрыт синтетикой.

## 2. CPU (окно строк 86258–86620: 26–36 fps, 2170–2214 draw)

### 2.1 Три потока по ~13–22 мс
| Поток | мс / кадр | Откуда | Что внутри |
|---|---|---|---|
| main (игра) | CPU 14.5, «recording» BeginFrame→EndFrame 22.0 мс стены | `[nvn] 主线程`, `[nb] frame` | NR direct: **3.77 мкс / draw × 1633 = 6.2 мс** (UBO 0.77 + identity 0.45 + flush/record 2.56) |
| nvn-translate | **15–22** (`submit_cpu_ms`) | `parts_ms_per_frame` | draw 9.4 (2259 draw) + snapshot 2.65 + **other 5.55** + pass 1.3 + program 0.96 + hash 0.52 + pipeline 0.61; по draw: NR-08 serve **1.9 мкс**, NR-09 lane **1.85 мкс**, `desc` секция 6.3 мс |
| dm-nbmt (рекордер) | **13.3** на сабмит | `[nb] mt` | 9535 пакетов в 37.8 чанках = vkCmd* Turnip, ≈ 6 мкс / draw; транслятор ждёт его 2.6 мс / кадр (макс 31 мс) |
| dm-present | 4.4 | `present_thread busy_ms` | NR-20 поворот + RCAS |

«other» 5.55 мс — время транслятора вне всех CPU_SCOPE (разбор потока NB / NR записей: 1652 `OP_X_NB_STATE` = 156 КБ / кадр,
2389 REF + 526 DEF блоков, 1633 `OP_X_NR_DRAW`) — на палубе 0.17. Это первый кандидат на профайлер (`DM_NR_CPU`, NR-16).

### 2.2 Длинные кадры (3022 строки `[长帧]` в 80000–119000)
Медиана длинного кадра 30.4 мс; классы: CPU-сабмит ≥ 60 % кадра — 1038, GPU ≥ 60 % — 914, прочее (main / ожидания) — 1070.
Сборка конвейеров — 20 кадров, загрузки > 2 мс — 93. **Это не рывки, а ровная перегрузка трёх потоков и GPU у 16.7 мс**: `[nvn] 计时`
кадр p50 16.87 / p95 45 мс, 160 из 300 кадров > 16.7. Любое превышение 16.7 у 60-герцового такта = 33.3 мс → отсюда §1 п. 6.

### 2.3 Пейсинг (сделано, `DM_PACE_ADAPT=1`)
`[nvn] 出图节拍 60.00 Hz, display (каждый такт — кадр)` на экране 120 Гц: такт 60 Гц, опоздавший кадр ждёт следующего такта. В DOS2
`present_auto_hz` возвращал цель ⚙ раньше ветки адаптивного темпа, так что `DM_PACE_ADAPT=1` ничего не делал. Теперь (hle_nvn.c,
коммит d125ef7): при цели ≤ 60 и `DM_PACE_ADAPT=1` такт = min(цель, частота / k), k ведёт существующий `pace_adapt_tick` (промахи
слота показа по `dm_present_late_count`, вниз при ≥ 6 из 60, проба вверх с удвоением паузы); 120 Гц: 60 → 40 → 30, 90 Гц: 45 → 30,
60 Гц: 60 → 30 (там выигрыша нет). Цель DRS (`g_nvn_present_period_ns`) остаётся периодом цели ⚙, DRS по-прежнему тянет к 60.
Умолчание 0 = байт в байт старое поведение. Решение о включении (или пункт ⚙ «адаптивно») — за владельцем: это вопрос плавность /
задержка, качество картинки не меняется.

### 2.4 Находка: размещение потоков на HyperOS не держится
`[cpu] where` всю игру: translate (пин на cpu7 = X4) на cpu7 — **0/120** почти в каждой минуте, сидит на cpu2–4 вместе с main и
JobWorker; «masks set again» растёт на 60 в минуту = маски translate и main сбрасываются в `ff` между каждыми проверками (2 с).
В тяжёлых минутах 90055–107641 translate 18–25/120 замеров на **A520** (cpu0/1), main 12–23/120, cpu3/4 почти пропали (паркинг ядер).
Так же во всех прошлых логах `nr16_* / nr17_*`. Кто сбрасывает — из лога не видно (кандидаты: ADPF-сессия, куда translate и main входят
с 4198-й строки, или игровой сервис HyperOS). Не правил: без телефона это гадание. Проверка — §5 R-BN2.

### 3.2 UI Iggy (`[nb] uiarea` того же окна)
175.8 host-проходов / кадр, из них **137 начинаются шейдером Iggy**, 111.6 — заливка/размытие фильтров (по 1–3 draw), 500 draw UI.
`DS attached and unused` 123.4 прохода = 2440 МБ load+store (по модели на тайлере), detach применён лишь 2.9 — фильтр-проходы
начинаются с clear всего набора RT (пасс clear-пути, к которому detach не применяется). `read break why=6` (Iggy читает вложение
открытого прохода) 51 / кадр. На Adreno Turnip ведёт такие короткие проходы в sysmem — GPU-цена ≈ то, что в таблице (1.4 мс);
CPU-цена ≈ 500 draw × (3.8 + ~3.7 + ~6) мкс ≈ 2–3 мс на поток. На Mali / PowerVR (всегда тайлы) каждый лишний DS-store и разрыв
2400x1080 стоят 10–20 МБ — главный UI-рычаг там.

### 3.3 Тайлер
`[nb] ir`: load clear/dc/load 15 / 0 / **368**, store dc/store 2 / **381** на кадр; `noload_passes_per_frame=0`; `[nb] rp` применил
store DONT_CARE 1 / кадр. На Adreno 750 почти всё это sysmem (не стоит ничего); на Mali — сотни полноэкранных load/store.

## 4. Что делать дальше (по выигрышу; ни одно не начато вслепую)
1. **R-BN1 (телефон) → включить `DM_PACE_ADAPT` по умолчанию в DOS2** при 90/120 Гц экранах, если ровные 40 нравятся владельцу.
2. **CPU транслятора: профиль, потом правка.** `DM_NR_CPU=1` (NR-16 сэмплер) в Форте 60 с: «other» 5.55 мс и serve/lane 3.8 мкс / draw.
   Кандидаты без профиля: разбор `OP_X_NB_STATE` (156 КБ / кадр) пропуском REF без изменений; NR-08 by_hash 61 % → по поколению.
3. **Mali / PowerVR UI:** фильтр-проходы Iggy с DS, который никто не читает: clear DS отложить (lazy clear) и пасс без DS; разрывы
   why=6 → `VK_EXT_attachment_feedback_loop_layout` / rasterization order access (родной путь вместо end/begin). Нужен SIM mali-прогон + Mali.
4. **UI-кэш** (рисовать слой Iggy раз, пока не меняется): сначала счётчик «сколько кадров подряд UI-поток совпадает» (хэш draw Iggy +
   вершин + UBO + поколений текстур). Выигрыш до 1.8 мс GPU + 2–3 мс CPU на поток, но только в кадрах без анимации UI — неизвестно.
5. Тень / pre-pass — после шейдеров (1.2 + 1.0 мс, A/B `DM_DOS2_PREPASS` в Форте).

  и `submit_cpu_ms`. Если в C translate держится на cpu7 — сброс масок идёт от ADPF-сессии.
- **R-BN3 heat:** обычная игра с загрузкой сохранения Форта: ждать `[nr] heat: save …: level FJ_FortJoy_Main` и
