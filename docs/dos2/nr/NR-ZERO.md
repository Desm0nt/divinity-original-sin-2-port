# NR-ZERO — что ещё осталось от транслятора и как убрать всё, кроме переведённых шейдеров (ночь 19.11.2026, ветка `dos2-ntrans`)

Задача N2 ночи 19.11. База: `dos2-night1119` 7780b92 (все умолчания партии C, кэш теней на Adreno). Телефона не было: всё ниже — по
логам O_* (19.11, ABBA стоя у ворот Форта Радости, Mi 14 Ultra, Turnip, sysmem, 81–83 fps без капа, GPU ≈ 11.8 мс), C_* (18.11),
nr11_dir2 / nr13_f5 / nr2_a2 (17–18.11, для счёта вызовов NVN), коду и хост-тестам. [м] = модель, не замер.

## 0. Коротко
- **20.11 утро, первая серия телефона Z8 (Q8) и её разбор, ветка `dos2-z10` (§36–§38):** на телефоне Z8 не делал ничего, а все
  сверки «прошли», потому что сравнивать было нечего. Причина одна главная: транслятор не опубликовал ни одного шаблона — он
  отказывал каждому набору, в котором кроме блоков игры есть служебные блоки стадий, привязанные динамическими буферами, а на
  Adreno таков каждый набор игры. Вторая: поток обходчика не запускался при `DM_NB_OWN` (умолчание игры) по неверному основанию.
  Обе исправлены, обе сначала воспроизведены на ПК (хост-тест падал с картиной телефона: 0 отвечено, 0 взято, 0 сравнено).
  Умолчания по-прежнему 0; исправленная серия — §37.
- **Ночь 20.11, после Z8, ветка `dos2-z9` (§28–§35):** сделаны четыре из шести частей §25.8, каждая за своим ключом (умолчание 0,
  `=2` сверка): (1) `DM_NR_Z8_THREAD` — обход на своём потоке `dm-z8walk`, поток игры только сдаёт список хэндлов, обходчик ничего
  не пишет в память команд (слова записи — в кольце меток по месту записи в подаче); (2) `DM_NR_Z8_IMG` — слово чтения записи
  NR-08: образы, писанные GPU, не обходятся, пока слово стоит (на тайлерах не работает); (3) `DM_NR_Z8_VIEW` — виды раз за подачу
  на диапазон по номеру от обходчика; (4) `DM_NR_Z8_VAL` — вердикт хвоста из памяти самого транслятора, без чтения кусков
  обходчика. **Части 5 и 6 (серия без разбора записей, тихий пролог) не построены** — §32, ещё 9–13 агент-часов. По модели:
  транслятор −1.2…1.8 мс из 7.4–7.6, поток игры не растёт, новый поток 0.75–1.2 мс. На телефоне не запускалось; серия — §34.
- **Ночь 20→21.11, ветка `dos2-z8` (§25–§27):** Z8 `DM_NR_Z8` (0 умолчание / 2 сверка / 1). Поток, который сдаёт запись команд, перед сдачей
  проходит её и ведёт **точную копию `State`** (те же записи, порядок и операторы, что у транслятора), по словам копии находит шаблон draw и
  пишет его пакеты; транслятор для такого draw берёт план, запись NR-08 и запись NR-09 без ключа и поиска. Пролог `draw()` и «живые» шаги
  (образы, виды, блоки) остались на трансляторе на каждый draw. По модели `=1` в этом виде **не выигрыш**: транслятор −0.7…1.1 мс, поток игры
  +0.75…1.2 мс, самым длинным потоком становится поток игры. До «почти нуля» ещё 20–28 агент-часов (§25.8), первым — обход на своём потоке.
  На телефоне не запускалось; таблица прогонов — §26.
- **20.11 вечер, ветка `dos2-z7` (§22–§24):** у Z5 построена и включена за `DM_NR_Z5` (2 сверка / 1) половина потока игры: он пишет пакеты
  draw, для которых у него есть значения (шаблон слота от транслятора + слова записи), транслятор берёт их по одному draw после сравнения
  значений и кэша привязок. Точно по построению, но транслятор по-прежнему исполняет каждую запись — с него уходит только секция команд:
  по модели `=1` в этом виде не выигрыш (сумма CPU +0.05…0.4 мс). Серия K (20.11) показала, что и Z3 / Z3K выигрыша не дают; рычаг остаётся
  один — транслятор не трогает отвеченные draw (§22.8: ещё 23–32 агент-часа, и только если `=2` покажет, что поток игры знает draw заранее).
  На телефоне не запускалось; таблица прогонов — §23.
- **20.11, ветка `dos2-z5` (§13–§16):** Z3 отвечает и при `DM_NR_PRESKIN` (умолчание тайлеров); Z3b / Z3c / Z3d — «живые» шаги draw
  проверяются одним словом (`DM_NR_Z3B` / `_Z3C` / `_Z3D`, каждая 0 / 2 сверка / 1); у Z5 построена сторона пакетов (вставка куска на
  позиции записи, сборщик серии, сверка `DM_NR_Z5=2`), половина потока игры не построена (`=1` отказывает). Всё умолчанием 0, на
  телефоне не запускалось; таблица прогонов — §15.
- **Транслятор сегодня — это не «вызовы NVN», а три перегона одного draw.** Движок по-прежнему зовёт NVN только ≈ 1 000 раз за кадр
  (было 14–15 тыс. до NR-09R / S3 / 09U). Остальное время — наш собственный конвейер: поток игры пишет запись draw (≈ 2.45 мкс на draw),
  поток `nvn-translate` разбирает её в состояние и сопоставляет с объектами Vulkan (≈ 3.5–4 мкс на draw), поток `dm-nbmt` отдаёт
  `vkCmd*` драйверу (≈ 1.6–1.9 мкс на draw — это цена Turnip, она останется и у «родного» рендера).
- На кадр (стоя, ≈ 1 660 draw движка, ≈ 1 100–1 500 записей до исполнителя): **поток игры 6.4–7.1 мс** (из них наша прослойка ≈ 4.9 мс),
  **транслятор 6.0–6.4 мс CPU** (стена 9.3–11.3 мс: 3.7–4.8 мс он ждёт GPU), **рекордер 2.5–3.2 мс**, present 0.8–1.1 мс; весь процесс
  31–34 мс CPU на кадр. HLE-ворота и SVC — 0.03–0.04 мс, не рычаг.
- **Самый крупный отдельный кусок транслятора в стоячей сцене — хэш кэша теней NR-SHCACHE: 1.0–1.9 мкс × 840–960 draw каскадов =
  0.9–1.6 мс на кадр** (вровень с дескрипторами NR-08 1.3–1.5 мс в установившихся окнах и больше полосы NR-09 0.7–0.8 мс). Сегодня сделан первый шаг по нему:
  `DM_NR_SHC_MEMO` — точные памяти поисков хэша (узлы регистрации текстур, версии страниц вершин по жетону трекера), значения хэша те
  же; плюс разбивка хэша по частям в логе (§4).
- Путь к «нулю»: семь ступеней Z1–Z7 (§3). Главная — Z5: запись draw сразу в пакет рекордера на потоке игры (поток `nvn-translate`
  для взятых draw исчезает): −4…5 мс транслятора, +1…2 мс потоку игры на Mi 14 [м]; на слабых CPU критический путь из трёх потоков
  становится двухпоточным. До неё — Z2 / Z3 / Z6 (по 4–12 агент-часов, каждая со сверкой `=2`).
- На Mi 14 FPS это **не двигает** (кадр упирается в GPU ≈ 11.8 мс; CPU транслятора 6 мс < GPU). Цель — слабые CPU (Snapdragon 7-класс,
  MTK G99, Mali-телефоны), где транслятор и поток игры по 15–20 мс.

## 2. Карта: нативно / частично / транслируется — и почему оставлено

## 3. Ступени к «нулю, кроме шейдеров» (агент-часы; мс CPU Mi 14 / слабый CPU ≈ ×2.5–3 [м]; GPU 0 везде)

## 4. Сделано сегодня: Z1 `DM_NR_SHC_MEMO` (кэш теней, точные памяти поисков хэша)
### 4.1 Что дорого в хэше (по коду `xbg_nr_shc.inc hash()`; по частям его меряет новая строка)
На каждый draw каскада: ≈ 30–50 перемешиваний + 15 вызовов `nrshc_bytes` по полям состояния; байты UBO (память по адресу, 260 КБ / кадр);
**версия диапазонов вершин и индексов**: журнал + `nvn_dirty_version` — скан всех страниц диапазона (2 атомарных чтения на страницу) на
каждый draw, хотя страницы те же, что в прошлом кадре (`CPU pool protected and unchanged` 1.59 млн / 10 с = 99.8 %); **текстуры**:
`texrev` + `texver` — два поиска в `std::map<int,RegisteredTexture>` (тысячи узлов) + поиск таблицы пула на каждую текстуру (1.1 / draw).

### 4.2 Что сделано
- `dm/gfx/nvn/nvn_dirty.c`: у каждого слота трекера своя эпоха `ep` (никогда не сбрасывается). +1 **до** того, как страница может стать
  записываемой (`unprotect_run` перед `mprotect` — это и сбой записи игры, и запись хоста `prep_write`, и `relieve`), при регистрации и при
  удалении пула. `nvn_dirty_version_tok` = прежний ответ + жетон (слот, эпоха; эпоха читается **до** страниц и сверяется после);
  `nvn_dirty_tok_ok(tok)` — две загрузки. Пока жетон держится, ни одна страница диапазона не выходила из «защищена» и пул тот же — ответ
  тот же (доказательство в комментарии и тест §4.4).
- `dm/gfx/nr/nr_shc.h`: `nrshc_pmemo` — прямой кэш (таблица, id) → узел, 4096 слотов, штамп `gen`; хранит только найденные ответы.
- `dm/gfx/vulkan/engine/xbg_nr_shc.inc`: `tfind()` (узел регистрации: память / map / обе со сверкой), `cur_tmap()` (таблица пула по ключу),
  `rv()` (версия страниц: жетон в `VMemo` диапазона). Узлы `std::map` бэкенда не стираются до выключения (как уже пользуется
  `texture_pool_cache`), выключение поднимает `images_epoch` — штамп памяти.
- Разбивка хэша: каждый второй замеренный draw (1 из 128) меряет части — байты UBO, версии вершин / индексов, текстуры, остальное; его
  время в старое «hash us a draw» не идёт (то число остаётся сравнимым со старыми логами).

## 6. Риски и чего нет
- Память узлов держится на том, что бэкенд не стирает узлы `textures` / `legacy_textures` до выключения (так сегодня в коде; так же

- `get_image()` в `texver` не трогался (у него побочные эффекты — проверка загрузки, как у дескрипторов).
- Z2–Z7 не начаты (план выше). Счётчик вызовов NVN по точкам входа на текущем коде (`DM_NVN_PROF=2`) не снимался с 17.11 — числа §1.5

Вывод для Z3: самое дорогое в draw — то, что зависит от момента (состояние образов, смещения блоков, виды вершин, сами `vkCmd*`), а не поиски.
Поэтому Z3 сделана так, чтобы всё «от момента» считалось тем же кодом, что и сегодня, а из таблицы бралось только то, что от момента не зависит.

### 9.2 Что сделано
Сегодня draw движка, который берёт короткий путь, проходит: `descriptors_stable` → `descriptors()` → `serve()` NR-08 (план набора шейдеров, запись
по поколению или по хэшу хэндлов, блоки, образы, набор) → `create_pass` (открытый проход продолжается) → `nrdraw::lane()` (ворота, группы
состояния, вариант, таблица NR-09, потом хвост). Три поиска в этой цепочке отвечают одно и то же для всех draw одного материала в одном
состоянии прохода: **план**, **номер записи NR-08**, **запись таблицы NR-09** (конвейер + список вершинных привязок).

`nrz3` (`dm/gfx/vulkan/engine/xbg_nr_z3.inc`, чистая часть `dm/gfx/nr/nr_z3.h`) держит одну таблицу «слова, которые читают эти три поиска →
их ответы» и на попадании идёт по прямой:
- **ключ** (`nrz_key`, до 39 слов): 5 объектов шейдеров, 6 фиксированных слов NR-08 (размер viewport, пул текстур: память / смещение / число,
  пул сэмплеров: память / смещение), пары (хэндл текстуры, хэндл сэмплера) по строкам плана (до 12), key id записи, слово варианта NR-09
  (примитив, сэмплы, число целей, маска цветов, глубина, restart, формат глубины, бит перекрытия пре-пасса), шесть id групп состояния,
  определение render pass. Определение раскладки в ключ не входит — оно функция плана;
- **ответ**: адрес плана, номер записи NR-08, адрес записи таблицы NR-09. Конвейер и привязки читаются из самой записи NR-09 на каждом draw
  (старый хвост может научить её заново, уничтоженный конвейер там обнуляется) — отдельного штампа на «переучили» не нужно;
- **штампы** (ответ годен, пока все три те же): поколение номеров NR-08 (`nrdesc::tab_gen`: каждый сброс таблицы и `release`), поколение
  таблицы NR-09 (`nrdraw::tab_gen()`: каждая очистка, в том числе при переполнении), эпоха объектов бэкенда (`nbpipe::epoch`: id групп
  начаты заново, уничтожены конвейеры / раскладки / render pass).

Что **не** кэшируется и считается на каждом draw тем же кодом (точность по построению — то, что в §8 названо «знает только транслятор»):
| Шаг | Чей код |
|---|---|
| ворота `descriptors()` и полосы (capture, граф проходов, статистики, A/B, `read_preflight`, сдвиг UI…) | те же выражения |
| отступление плана, эпоха мемо, запись NR-08 жива / её кольцо / `images_alive` | проверки `serve()` |
| смещения блоков в кольце — годность вида «на месте» (живой кусок zero-copy, липкие страницы, ожидающие обратные записи, сдвиг UI) | `nrdesc::blocks` → `nrbuf::ubo`, как сегодня |
| набор записи и его узел утилизатора | `nr_dfifo_use`, как в `serve()` |
| образы записи: правило `nr_dimg_skip`, для образа «путём чтения» — `get_image` + `prepare_read` | цикл `serve()` слово в слово |
| «открытый проход продолжается» + метки записи вложений | проверка и строка быстрого пути `create_pass` |
| `uiarea::detach` | `detach_peek` — тот же ответ без побочных действий; где `detach` сделал бы больше, чем ответить, draw идёт обычным путём |
| проверка прохода, виды вершин / индексов (`snapshot`), свёртки, viewport / scissor, `uiarea`, кэш привязок, `vkCmd*`, счётчики | **общий хвост** `nrdraw::lane_tail` — `lane()` разрезана на «разрешение» и «хвост», `nrz3` зовёт тот же хвост |

Порядок: сначала все проверки, которые могут отказать, потом действия. Пока draw не «отвечен», ничего не изменено (кроме повторяемых без
последствий вызовов `blocks()` и узла утилизатора) — отказ = обычный путь с первой строки. Исходы после ответа:
- `1` — draw записан;
- `2` — хвост оставил draw старому хвосту (вид, viewport, проход закончился внутри `snapshot`): `draw()` получает запись Descriptors и Pass
  ровно такие, какие оставили бы `serve()` и `create_pass`, и идёт дальше как после `lane()`, вернувшей false;
- `3` — чтение образа закончило открытый проход: дескрипторы отвечены, `create_pass` и полоса идут обычным путём;
- чтение образа закончило подачу — draw собирается заново обычным путём в новой подаче (как делает `descriptors_stable`).

Чего попадание не делает вовсе: запись Descriptors и её возврат, пролог `descriptors()` (в том числе чтение часов и обход привязок шейдеров
для правила «только фрагментные чтения» — оно теперь запомнено у плана), второй ключ и хэш NR-08, копия Pass в куче, вариант и обход строки
таблицы NR-09.

Обучение: таблицу учит обычный путь — в конце общего хвоста (`nrz3::served`), только если NR-08 ответила записью, и только под ключом,
который называет то, что путь действительно разрешил (вариант, id групп, определение прохода, раскладка сверяются со словами полосы, номер
записи — с поиском по хэшу в таблице NR-08; расхождение — красная строка и счётчик `odd`, запись не делается).

### 9.4 Строки лога
- старт: `[nr] DM_NR_Z3=…`;
- раз в 10 с: `[nr] z3: DM_NR_Z3=…; N engine draws asked, answered A (x %), recorded by the shared tail R; not answered: <причины>; table: … hits, no entry,
  stale, stored (replaced), odd; … ring blocks and … images an answered draw (read path …); vkCmd* a served draw …; T ns a served draw from the lookup to the end (1 in 64)`;
- `[nr] z3 by part (NR-ZERO, N served draws split, 1 in 128): T ns = gates, key and lookup A + entry, blocks, images and set B + pass marks C + vertex / index views D +
  viewport and checks E + bookkeeping and vkCmd* F + finish G` — части D…G меряет тот же код, что в `[nr] draw by part`, числа сравнимы напрямую;
- **`[nr] draw span (NR-ZERO, N recorded engine draws timed, 1 in 64): T ns from the command buffer to the end of the draw (descriptors, pass, lane; DM_NR_Z3=…)`** —
  печатается при любом `DM_NR_Z3` (и при 0): время от взятия буфера команд до конца записанного draw движка, каким бы путём он ни шёл.
  **Это число сравнивает `=0` и `=1`** (вместе с `[cpuprof] threads … nvn-translate` и новой частью `nrz3` в `parts_ms_per_frame` при `DM_NR_CPU=1`);
- при `=2`: `[nr] z3 check (DM_NR_Z3=2): the table answered P draws …: same plan / NR-08 entry / NR-09 entry S, the path left at a step the table does not cache L, bad B; stored after a miss M`;
- красные: `【红】[nr] z3: …` (первые 16).

Старые строки: `[nr] desc` и `[nr] draw` при `=1` считают только draw, которые таблица не взяла (формат прежний, но выборка — промахи таблицы);
draw таблицы — в `[nr] z3`. При `=0` и `=2` старые строки считают всё, как раньше.

### 9.7 Риски
- Умолчание 0, на телефоне не запускалось. Сверка `=2` доказывает ключ / штампы / проверки только на тех сценах, что были в прогоне (стоя и
  ходьба — минимум; бой и город — отдельно, когда будут сейвы).
- Узел утилизатора набора помечается до цикла образов (в `serve()` — после). Влияет только на порядок в очереди утилизатора, не на выбор набора.
- При отказе после `blocks()` счётчики `[nr] ring` считают блоки дважды (обычный путь повторяет вызовы) — только статистика.
- Сброс таблицы NR-08 (`table full`) делает устаревшими все записи Z3 разом — после него один кадр промахов.
- Любой новый код, который добавит в `descriptors()` / `create_pass` / пролог `lane()` действие «на каждый draw», обязан попасть и в
  `nrz3::draw` — `source_structure_test.py` держит форму этих мест (быстрый путь `create_pass`, правило образов, первые строки `detach`), но
  новое действие в другом месте он не поймает; его поймает `=2` только если оно меняет исход.
- Разрез `lane()` на две функции и вынос двух выражений в функции (`restart_eff_of`, `desc_frag_only_shaders`) трогают путь при `=0`: логика та же,
  но это новый машинный код — прогон Z1a (§11) сверяет его с `Z_1a`.

## 10. Z5 `DM_NR_Z5` — пакет рекордера с потока игры: НЕ построено, проект и блокирующие факты
(Состояние на вечер 19.11. Что построено ночью 19→20.11 — сторона пакетов и её сверка `=2`, эпохи Z3b–d — и что осталось: §13, §14.)
(20.11 день: замер Z3 на телефоне, дешёвый ключ Z3K — §17; пакетная половина второго писателя Z5 и уточнённый перечень того, что не построено, — §18.)
(20.11 вечер: половина потока игры построена и включена за `DM_NR_Z5` = 2 / 1 с вердиктом на каждый draw — §22; прогоны — §23.)
(Ночь 20→21.11: точная копия `State` на сдающем потоке и ответ на draw без ключа и поиска на трансляторе, `DM_NR_Z8` — §25; прогоны — §26.)
В этой сессии Z5 не сделан и за переключателем ничего нет (ключ зарезервирован, `≠ 0` — красная строка). Точным его сейчас сделать нельзя:
1. **Поток игры опережает транслятор.** Он пишет записи в память команд гостя, транслятор исполняет их позже. В момент записи не существует
   ни одного входа «живых» шагов Z3: открытого прохода (`open_pass` / `last_pass`), кэша привязок, номера подачи, штампа узла набора,
   состояния образов, годности видов zero-copy и кольца на момент исполнения, ожидающих обратных записей, id групп состояния (их строит
   транслятор из `OP_X_NR_STATE`).
2. **У очереди NB-MT один писатель по построению** (`nb_mt.h`: пакеты пишутся без замков, кусок передаётся под одним замком, `=2` хэширует
   кусок, исполнитель один). Второй писатель = замок на пакет (KB PERF-E18: стоит как сам `vkCmd*`) либо вставка готовых кусков.
3. **Порядок с проходами и барьерами** держится только вставкой «в позиции записи»: поток игры собирает кусок пакетов на серию draw,
   транслятор, дойдя до первой записи серии, проверяет штампы и передаёт кусок целиком. То есть поток транслятора для этих draw не исчезает,
   а становится короче (обход записей остаётся).
4. **Что нужно потоку игры из общих таблиц** (публикация без замков, как `nb_sm_table`): таблица Z3, записи и наборы NR-08, таблица NR-09 (без
   перестановки «в начало»), карта кусков zero-copy (адрес → буфер + смещение) с эпохой живости, смещения кольца с эпохой липких страниц.
   Двух из этих эпох сегодня нет — это Z3b / Z3c / Z3d из §9.6: пока «живые» шаги не проверяются одним словом, поток игры их повторить не может.
5. **Кэш привязок.** Внутри серии поток игры может вести свой, но первая draw серии обязана привязать всё (или транслятор правит её при
   вставке). Серии рвутся на каждом draw, который Z3 не взял (18–28 % записей) → средняя серия 4–5 draw → `vkCmd*` рекордера +15–25 % [м]
   (+0.4…0.7 мс к 2.9–3.0), если не делать правку первой draw.
6. **`State` для запасного пути.** Draw, который уходит на старый путь, читает `State` на момент своей записи — транслятор всё равно должен
   применить привязки и состояние каждой записи (или лениво проиграть журнал). Часть `nbdraw` 2.1–2.5 мс (включая хэш кэша теней) остаётся.
7. **Пролог `draw()`** (кэш теней, пре-пасс, двойники MAT / SURF, LIGHTFUSE) решается на трансляторе по `State`; серии возможны только там,

Порядок работ: Z3b + Z3c + Z3d со сверками (9–14 агент-часов, 2–3 прогона) → публикация таблиц и «вставка в позиции записи» со своей

### 13.1 Z3 вместе с PRESKIN и «погашенным» ONCHIP
Было: при любом `DM_NR_PRESKIN ≠ 0` таблица не отвечала ни на один draw. С 19.11 на Mali / PowerVR умолчания `DM_NR_PRESKIN=1`, `DM_NR_MAT=1`,
`DM_NR_IDVS=1`, `DM_NR_ONCHIP=1` — то есть на слабых устройствах Z3 был пуст.

Что на самом деле зависит от этих переключателей:
| Переключатель | Что видит draw | Что сделано |
|---|---|---|
| `DM_NR_ONCHIP=1` при `DM_NR_LIGHTFUSE=1` | бэкенд ONCHIP выключен при старте (`nroc::mode = 0`, строка `[nr] onchip … is superseded`); остаются только метки цепочек от фронта для LIGHTFUSE | ворота Z3 смотрели на `nroc::mode > 0` — «погашенный» ONCHIP воротами не был и не стал. Слитый draw LIGHTFUSE по-прежнему не отвечается (`nrlf::fused_draw`) |
| `DM_NR_MAT=1`, `DM_NR_SH_SURF` | двойник фрагментного шейдера подставлен в `state.shader[4]` до крюка Z3 | ничего: ключ Z3 берёт объекты шейдеров из состояния на момент draw — двойник входит в ключ сам |
| `DM_NR_IDVS=1` | выбор модуля вершинного шейдера при создании конвейера (старый хвост) | ничего: конвейер учит старый хвост, таблица хранит то, что он выучил |
| `DM_NR_PRESKIN=1` | `nrps::decide` на каждом draw: запись скиннинга этой подачи, её привязка и вариант конвейера (биты 40–63 слова 4 варианта NR-09) — «живое» решение | см. ниже |

PRESKIN внутри Z3:
- `nrps::decide` зовётся из `nrz3::draw` **на том же месте, что в `draw()`**: после меток прохода, до полосы — для каждого draw (счётчики
  PRESKIN те же). Если после ответа хвост оставил draw старому хвосту (возврат 2), `draw()` второй раз `decide` не зовёт (`nrz3::ps_called`).
- draw со скиннинговым вершинным шейдером при `DM_NR_PRESKIN=1` (`Shader::psk == 1`): таблица отвечает дескрипторы и проход (план, запись
  NR-08, блоки, образы, набор, метки вложений), а дальше draw идёт **в саму полосу** `nrdraw::lane` целиком — она сама ищет запись NR-09 по
  варианту с битами PRESKIN и зовёт общий хвост. Запись NR-09 из таблицы для таких draw не берётся никогда (вариант зависит от записи
  скиннинга, которая живёт одну подачу). Цена: остаются запись Descriptors и поиск варианта полосы (167–180 нс); экономится поиск NR-08,
  пролог `descriptors()`, копия Pass.
- остальные draw при включённом PRESKIN идут как раньше (`decide` для них — один счётчик и выход).
- сверка `DM_NR_Z3=2`: слово варианта сравнивается без битов PRESKIN; запись NR-09 скиннингового draw не сравнивается (её и при `=1` ищет
  полоса); план, запись NR-08, правило «только фрагментные чтения», быстрый путь прохода — сравниваются как раньше. При обучении запись
  NR-09 draw, который PRESKIN спланировал, в таблицу не кладётся.
- по-прежнему ворота: `DM_NR_POSONLY`, `DM_NR_SORT`, `DM_NR_MDI`, включённый (не погашенный) ONCHIP, слитый draw LIGHTFUSE, диагностика.

Строка `[nr] z3:` получила счётчик `DM_NR_PRESKIN draws answered and handed to the lane: recorded N, old tail M`; они входят в «answered».

### 13.2 Z3b `DM_NR_Z3B` — слово образов
Обход образов записи NR-08 (495–621 нс на draw, 2.5 образа) почти всегда находит одно и то же: все образы «тихие» (никогда не писались GPU,
залиты, проверены в этой подаче, раскладка для чтения) — правило `nr_dimg_skip`. Запись теперь помнит «мой обход нашёл все образы тихими»
под тремя словами: **эпоха образов**, **номер подачи**, **серийный номер слота**. Пока все три те же, обход не делается.

Как обеспечено «каждый писатель двигает эпоху» (в коде ≈ 40 мест пишут эти поля — расставлять руками значило бы пропустить):
- семь полей `Image`, которые читает `nr_dimg_skip`, получили **типы-обёртки** (`dm/gfx/nr/nr_z3e.h`): присваивание, которое может закончить
  «тихо», двигает `nrz_img_ep` само — `gpu_written`, `last_write`, `storage_write`, `opw`: 0 → не 0; `uploaded`: да → нет; `layout`: раскладка
  чтения → любая другая; `checked_submission`: «эта подача» → любое другое значение. Присваивание, которое «тихо» не кончает (метки вложений
  на каждом draw у образа, который уже писался; первая проверка образа в подаче), эпоху не двигает — иначе слово не стояло бы никогда;
- код, который обёртка не понимает (ссылка на поле как на число, `++`, передача поля в `printf` без приведения), **не компилируется** —
  два таких места в логах поправлены приведением;
- уничтожение `Image` двигает эпоху (`~Image`): новый образ по тому же адресу «тихим» не считается;
- запись, собранная заново, начинает без слова; `slot_use` пишется только значением серийного номера слота (проверяет тест структуры).

Слово спрашивается в обоих обходах — `serve()` и `nrz3::draw`. Сверка `=2`: слово спрошено, обход сделан; если слово стояло, а обход
отправил хоть один образ путём чтения — `bad` и красная строка.

### 13.3 Z3c `DM_NR_Z3C` — виды меша
Диапазон вершин / индексов draw (адрес, размер) → (буфер, смещение) запоминается в таблице прямого отображения (4096 записей, 88 байт) под
словами, от которых зависит ответ `snapshot()`:
| Чем отвечено | Слова | Кто их двигает |
|---|---|---|
| вид zero-copy на месте (Adreno) | `zc::live_ep` | кусок стал живым / снят (`map_pool`, `retire`) |
| | версия записи куска `Chunk::wr_ver` | каждая запись CPU при проигрывании на этот кусок (`zc::mark`: липкие страницы и диапазоны NR-TRX), добавление «горячего» диапазона |
| | серийный номер слота | подача: вид отмечается для стража NR-TRX один раз за подачу, класс «давно писано» считается от номера |
| | `hit_pend_gen` | любое изменение списка ожидающих обратных записей |
| статическая копия NR-06 (Mali / PowerVR) | эпоха снимков | новая эпоха: проверка копии по трекеру страниц делается заново |
| | `nrbuf::st_ep` | снятие копии с пути, освобождение копии / куска арены, обрезка памяти, любое изменение таблицы буферов |
| | `hit_pend_gen` | как выше |

Любой другой ответ `snapshot()` (копия, передний кэш, ожидающий результат GPU) не запоминается — у переднего кэша своя эпоха. Виды zero-copy
запоминаются только пока статические копии NR-06 выключены (в `snapshot()` они спрашиваются первыми). Счётчики, которые подвинул бы
настоящий ответ (`zc::hits`, привязки NR-06), двигаются и на попадании. Сверка `=2`: таблица спрошена, `snapshot()` вызван; если запись
стояла, а ответ другой (другой путь, буфер, смещение) — `bad`.

### 13.4 Z3d `DM_NR_Z3D` — слово кольца
Блок констант в кольце на месте = (адрес − база куска), если: кольцо целиком в одном живом куске zero-copy, никакой другой живой кусок его
не задевает, ни одна страница кольца не липкая, нет ожидающих обратных записей, нет сдвига UI, блок целиком внутри кольца и выровнен. Первые
три условия — одно слово (`nrbuf::zd`), годное, пока стоят `zc::live_ep`, версия липких страниц куска `Chunk::st_ver`, база и размер кольца;
пересчёт — один проход по байтам страниц кольца (≈ 5 тыс.). Остальные проверяются на каждом блоке, как их проверяет `nrbuf::ubo` (его
собственные первые строки). На телефоне `sticky 0`, `pending 0` — слово должно стоять всё время.
**На Mali / PowerVR (зеркало кольца) Z3d выключает себя строкой в логе:** там на первой привязке гранулы в эпохе идёт копия — это путь
данных, а не поиск, запоминать нечего. Сверка `=2`: слово ответило → обход страниц обязан дать тот же буфер и то же смещение.

- Z3c: если записи CPU при проигрывании идут в те же куски, что и меши, версия куска двигается 20+ раз за кадр и таблица почти не стоит
  (видно в `stale`); тогда нужна версия не куска, а диапазона — не сделано.
- Z3b: запись, которую рисуют один раз за подачу, слова не использует (обход + запись слова) — цена 3 записи в память.
- Ветки `#ifdef` других игр (DOOM Eternal, XC2) в этой ветке не собираются: если там есть передача поля `Image` в `printf` без приведения —
  сборка той игры остановится на этой строке (громко, не молча).
- Счётчик `decision … ns` строки `[nr] buf` при Z3d меряет только блоки, не взятые словом.

## 14. Z5 `DM_NR_Z5` — что построено и что нет
§10 остаётся в силе как перечень блокирующих фактов. В эту ночь построена **сторона пакетов** и её сверка на устройстве; **половина потока
игры не построена**, `DM_NR_Z5=1` отказывает красной строкой.

### 14.1 Построено (точно, проверено на ПК; на телефоне — только сверкой `=2`)
1. **Вставка «в позиции записи»** — `nbmtq::Queue::splice` (`dm/gfx/nb/nb_mt.h`): готовый кусок пакетов передаётся целиком; текущий кусок
   транслятора уходит перед ним, всё записанное позже — после. Обе передачи идут через тот же `flush()` (номер, хэш режима 2, режим 1,
   полная очередь) — порядок воспроизведения = порядок передачи, как и раньше. Проходы и барьеры остаются на местах: их пакеты пишет тот же
   код в тех же позициях.
2. **Сборщик куска** — `xbg_nb_mt.inc` `Build` / `Z5Sink`: восемь команд записанного draw пишутся в свой кусок теми же раскладками пакетов,
   что и у обёрток (раскладки вынесены в именованные структуры, код обёрток не менялся).
3. **Команды серии без кэша привязок транслятора** — `dm/gfx/nr/nr_z5.h` `nrz5_emit`: секция команд `lane_tail` над кэшем с маской
   «известно». Вывод, который снимает факт 5 из §10 (кэш привязок):
   - draw, который читает только поля, уже выставленные его серией, даёт одни и те же команды при любом настоящем кэше → его пакеты можно
     писать заранее (**хвост серии**);
   - draw, который читает поле, серией ещё не выставленное, может записать только транслятор (**голова серии**: её первые draw). После
     любого draw все прочитанные им поля известны и равны его значениям;
   - «правка первой draw серии» поэтому = «голову заранее не пишем»: голова идёт обычным путём, кусок хвоста вставляется на позиции его
     первого draw, потом известные поля модели переносятся в настоящий кэш. Draw, который после начала хвоста читает новое неизвестное поле
     (например, привязку 5, которой в серии ещё не было), серию заканчивает.
4. **Сверка `DM_NR_Z5=2`** (`xbg_nr_z5.inc`, ничего не записывает иначе): каждый draw движка, который записал хвост полосы, собирается
   ещё раз сборщиком — из значений хвоста и модели кэша, **пустой в начале каждой серии**; пакеты сравниваются с только что записанными
   пакет в пакет. После каждого draw известные поля модели обязаны равняться настоящему кэшу; перед каждым draw серии настоящий кэш обязан
   их всё ещё держать (иначе кэш сдвинули без пакета — серия кончается, считается отдельно: поток игры этого увидеть не мог бы).
   Заодно считаются серии: длина, чем кончаются, доля головы и хвоста — числа, без которых решение о Z5 принимать нельзя.

**Про «байт в байт».** Сырые байты двух кусков равны быть не могут: пакет держит указатели на собственные массивы внутри своего куска,
адрес своей функции-переходника и незаполненные промежутки выравнивания. Поэтому: (а) на телефоне сравнение пакет в пакет — та же операция,
те же аргументы, то же содержимое массивов (`nbmt::same_stream`); (б) на ПК сравнивается то, что действительно должно совпасть, — журнал
вызовов на буфере команд, и он совпадает байт в байт.

### 17.2 Почему вопрос дорогой и что сделано
Арифметики в вопросе мало (ПК-бенч всего пути «собрать слова, хэш, поиск» — 47 нс). Дорого то, что он трогает: слот плана и сам план
набора шейдеров (чтобы узнать, из каких слотов читать текстуры), копия до 39 слов состояния в буфер, хэш слово за словом, запись таблицы
на 448 байт (хэш, штампы, ответ и ключ лежат в 4–5 строках кэша), потом ещё запись NR-08 и запись NR-09. За кадр проходит ≈ 1 000–1 250
разных draw, поэтому к следующему кадру все эти строки снова холодные: 6–8 промахов кэша на draw.

Направление хозяина — «готовый отпечаток с потока игры». Что поток игры реально знает в момент записи: **key id** (NR-02: шейдер, blend,
depth-stencil, raster, формат вершин, набор форматов целей, примитив) — он уже лежит в хвосте записи. Чего он не знает и узнать дёшево не
может: объекты шейдеров бэкенда, id групп состояния (их выдаёт словарь транслятора), определение прохода (создаёт транслятор), а набор
текстур в «лёгком» отпечатке NR-09R не считается вовсе (`texset` = 0: хэш 64 слотов на каждый draw как раз и убрали). Поэтому сделано так:
- **место поиска** даёт поток игры: key id из записи + слова, которые у транслятора уже в руках без обхода (два слова варианта, определение
  прохода, номер набора «фиксированных слов», объекты вершинного и фрагментного шейдера) + хэндлы до трёх текстур из слотов, которые
  читает набор шейдеров этого key id (подсказка `kd`, выученная на (key id, фрагментный шейдер)). Место — только место: неверная или
  устаревшая подсказка даёт промах, а не ответ;
- **точность** даёт сравнение **на месте**: запись передней таблицы (`nrzk_ent`, 320 байт; слова сравнения первыми) хранит **полный ключ**
  `nr_z3.h` и строки (стадия, слот текстуры, слот сэмплера), из которых читались его слова текстур. Попадание = каждое слово записи равно
  живому состоянию: два объекта шейдеров (три средние стадии у спрашивающего draw пусты — ворота `nrz3::draw`), шесть фиксированных слов
  (одним номером: точное нумерование сравнением, `nrzk_fixed`), каждая пара (хэндл текстуры, хэндл сэмплера) против `state.tex` /
  `state.samp` по строкам записи, key id, оба слова варианта, определение прохода. Ничего не собирается в буфер и ничего не хэшируется;
- **штампы** те же три (поколение номеров NR-08, поколение таблицы NR-09, эпоха объектов бэкенда): передняя таблица **чистится целиком**,
  когда любой из них не тот, под которым она заполнялась (`nrzk_sync`: три сравнения на draw, штампов в записях нет);
- **ответ** — тот же `nrz_val` (план, номер записи NR-08, запись NR-09), что кладёт `nrz_put`. Передняя таблица заполняется в тех же двух
  местах, где учится основная: когда основная ответила, а передняя нет, и в `served()` после обычного пути.

После попадания идут **все** прежние живые проверки (отступление плана, эпоха мемо, «открытый проход продолжается», запись NR-08 жива,
конвейер в записи NR-09 цел) и весь прежний путь — те же строки кода, по одному разу в файле. План при попадании берётся из записи (планы
уходят только с поколением NR-08), `plan_of`, `gather`, `nrz_key`, `nrz_hash`, `nrz_find` не зовутся.

Чтобы попадание трогало меньше строк и в остальном пути: поля `nrdesc::Plan` и `nrdesc::Ent` переставлены (то, что читает и пишет каждый
обслуженный draw, — в первой строке; векторы обхода образов — в конце), обе структуры выровнены на 64 байта. Логика не менялась.

### 17.3 Почему это точно
1. Попадание передней таблицы ⇔ полный ключ состояния равен полному ключу, под которым запись положена. Сравниваются те же слова, что
   пишет `nrz_key`; строки текстур — строки плана, а план — функция набора шейдеров, пока стоит поколение NR-08 (под ним таблица и живёт).
2. Ответ под равным ключом и теми же штампами — тот, что хранила бы основная таблица: это и есть довод §9.
3. Запись, которую основная таблица уже вытеснила (два пути её набора заняты), продолжает отвечать из передней — вытеснение не событие
   годности. На телефоне это видно счётчиком «front answers the table … no longer held».
4. Чего сравнение не покрывает, покрывают прежние живые проверки после попадания — они не тронуты.

## 18. Z5: второй писатель — пакетная половина потока игры (построена и проверена на ПК, в движок НЕ включена)
`DM_NR_Z5=1` по-прежнему отказывает красной строкой. За переключателем нет ничего наполовину верного: новая часть не включается ни в один
файл движка (это проверяет `source_structure_test.py`).

### 18.1 Что построено
1. **Запас кусков для второго писателя** — `nbmtq::Queue::take_spare` / `splice_spare` / `give_back_spare` (`dm/gfx/nb/nb_mt.h`): поток,
   который не транслятор, берёт куски из общего свободного списка под замком очереди (один замок на кусок, не на пакет), статистику
   писателя-транслятора не трогает, одновременно на руках не больше `spare_max` кусков (нет куска — эта серия заранее не пишется).
   Каждый такой кусок кончается либо вставкой, либо возвратом.
2. **Протокол серии** — `dm/gfx/nr/nr_z5w.h`:
   - *писатель* (место потока игры, пока он пишет записи draw): модель кэша привязок пустая в начале серии; draw, читающий поле, которого
     серия ещё не выставляла, — «голова»: его запись без метки, его записывает транслятор как сегодня. Первый draw, который читает только
     известные поля, открывает «хвост»: запасной кусок + место в кольце серий; его запись получает метку `MARK_SPLICE` с номером серии,
     следующие draw хвоста — `MARK_COVERED` с тем же номером. Серия кончается на любой записи, которая не draw движка, на новом
     неизвестном поле, на полном куске. Публикуется серия одной атомарной записью (кольцо «один писатель — один читатель»), когда она
     кончилась, — то есть до того, как запись команд уйдёт транслятору. Хвост короче `min_tails` публикуется без куска (две передачи
     куска дороже нескольких draw);
   - *читатель* (транслятор, на каждой записи draw по порядку): без метки — записывает сам. `MARK_SPLICE` — берёт из кольца серию с этим
     номером (серии записей, которые так и не исполнялись, — старшие номера впереди — возвращает по дороге; серии уже нет — записывает
     сам). Серию **берёт** только если (1) настоящий кэш привязок держит каждое поле, которое серия знала перед первым draw хвоста
     (сравнение полей, а не штамп: о том, как записывались головы и что ещё трогало кэш, ничего не предполагается), и (2) собственный
     вердикт транслятора «да» на всё остальное, что draw хвоста сделали бы помимо команд (§18.3). Взял — кусок вставляется на этой
     позиции, известные поля серии переносятся в настоящий кэш, записи `MARK_COVERED` этой серии пропускаются. Не взял — кусок
     возвращается, все записи серии записываются как сегодня, draw за draw;
   - *сверка* (форма `DM_NR_Z5=2` со вторым писателем, `Reader::verify_*`): ничего не берётся, транслятор записывает всё сам и сравнивает
     свои пакеты каждого draw хвоста с куском писателя пакет в пакет, кусок обязан кончиться там же, где хвост.
3. Порядок с проходами и барьерами не меняется по построению: серия не переходит через запись, которая не draw движка, а её кусок
   передаётся той же одной передачей очереди на позиции первого draw хвоста (`splice`, §14.1).

### 18.3 Что НЕ построено и почему (блокирующие факты; оценка — агент-часы, не дни)
Пакетная половина отвечает на вопрос «как передать». Не построено «что писать» и «можно ли это взять»:
| Часть | Блокирующий факт | Агент-часы |
|---|---|---|
| **Значения draw у потока игры** (конвейер, набор и смещения, виды вершин / индексов, viewport) | Их выдаёт цепочка, входы которой знает только транслятор **в момент исполнения**: объекты шейдеров бэкенда и двойники MAT / SURF (подставляются в прологе `draw()` по состоянию), id групп состояния (словарь транслятора), определение прохода, запись NR-08 и её набор, запись NR-09. ## 22. Z5: половина потока игры — построена и включена за `DM_NR_Z5` (20.11 вечер, ветка `dos2-z7`)
На телефоне не запускалось. Умолчание 0. Коротко и честно:
- **Сделано:** поток игры сам пишет пакеты рекордера тех draw движка, для которых у него есть значения, а транслятор забирает их **по одному
  draw** — только после того, как сам разрешил этот draw и сравнил свои значения с записанными. Работает весь путь: предсказание на потоке
  игры → запасной кусок очереди → метка в записи → проверка на трансляторе → передача куска на своём месте. `DM_NR_Z5=2` — сверка на
  устройстве (ничего не берётся), `DM_NR_Z5=1` — применение. Точность не зависит от того, насколько хорошо поток игры угадал.
- **Не сделано:** транслятор по-прежнему исполняет **каждую** запись целиком (состояние, пролог `draw()`, дескрипторы, проход, виды, viewport).
  С него уходит только секция команд хвоста полосы. Это не тот выигрыш, который обещала модель §18.3.
- **Что это значит после серии K** (главный агент, 20.11, dos2 `210d8f3`, Mi 14: все сверки `bad 0`, но `draw span` с Z3 + Z3K ≈ база,
  «front table» 306 нс вместо 50–120, образы 683 нс даже с `DM_NR_Z3B=1`): дешевле сделать вопрос к таблице не получается, выигрыш Z5 возможен
  **только если транслятор вообще не трогает отвеченные draw**. Построенное здесь — транспорт и сверка для этого шага, а не сам шаг (§22.8).

### 22.1 Почему вердикт на каждый draw, а не один на серию
Один вердикт на серию (§18.1) должен до исполнения записей серии поручиться за всё, что сделал бы каждый её draw. Для этого поток игры
обязан вести точную копию состояния транслятора, а транслятор — уметь её подтвердить одним сравнением. Разбор по коду показал, чего для этого
нет и за один заход точно не построить:
- блок состояния `OP_X_NB_STATE` — не функция своего содержимого: он несёт только записи, изменённые с последнего «неизвестно», остальное
  поле `State` остаётся от прежних блоков. Один и тот же блок на разном прошлом даёт разное состояние, поэтому «id содержимого блока» ключом
  ответа быть не может; нужна точная свёртка по каждому полю и её подтверждение транслятором;
- пролог `draw()` (кэш теней, дальний каскад, окклюзия, пост, условная отрисовка, пре-пасс, двойники MAT / SURF, LIGHTFUSE, ONCHIP, барьер
  тайлера) читает состояние транслятора и может draw пропустить или подменить шейдер — на потоке игры этого не видно;
- «живые» шаги (образы записи NR-08, виды вершин, блоки кольца) верны только на момент исполнения.

Поэтому выбран протокол, который ничего из этого не предполагает: транслятор исполняет запись как сегодня и **в том месте, где хвост полосы
начал бы писать команды**, спрашивает, не написаны ли они уже. Это точно по построению и закрывает пункты задачи так:
| Пункт (§18.3) | Состояние |
|---|---|
| 1. Значения draw у потока игры | **сделано как предсказание**: шаблон слота, опубликованный транслятором, + слова самой записи (`nr_z5p.h`). Точной свёртки состояния нет |
| 2. Пролог `draw()` | **исполняется на трансляторе как сегодня**; draw, который пролог пропустил или увёл на старый хвост, обрывает серию перед собой (запись «не дошла») |
| 3. Публикация без замков | **сделано** для таблицы шаблонов (один писатель, версия на слот, каждое слово — атомик). Таблицы Z3 / NR-08 / NR-09 / карта кусков не публикуются: поток игры их не читает |
| 4. Вердикт и учёт | **вердикт на draw** (значения + кэш привязок), серия режется на первом «нет»; учёт каждого draw исполняет сам транслятор — он не менялся |
| 5. `DM_NR_Z5=2` / `=1` | **сделано**: кусок потока игры против пакетов транслятора пакет в пакет; применение с удержанием куска |

### 22.2 Что сделано
1. **Место и шаблон** (`dm/gfx/nr/nr_z5p.h`). Слова записи, которые есть у потока игры: key id, вид и аргументы draw, адрес индексного
   буфера, адрес, привязанный к потоку вершин 0. Хэш этих слов и номер повторения этого же набора слов в кадре дают **слот** таблицы
   (8192 слота). Транслятор, записав draw сам, кладёт в слот **шаблон**: конвейер, раскладку, набор, для каждого динамического смещения —
   слот UBO, из которого оно берётся (по плану NR-08), и разность «адрес − смещение», виды вершин и индексов как их привязал хвост (уже
   свёрнутые), viewport, scissor, `first_index`, число свёрнутых вершин. Draw, который шаблон описать не может (больше 8 смещений или 8
   привязок вершин, слот смещения не найден), публикуется как «не предсказывать».
2. **Публикация без замков.** Один писатель (транслятор), читатель — поток игры. У слота версия: нечётная — идёт запись; чтение берёт версию,
   копирует 46 слов, читает версию ещё раз; не совпало — чтение выбрасывается. Все слова — `std::atomic` (гонки нет и по букве стандарта).
3. **Поток игры** (`nvn_nb_draw.inc` `nbd_draw` → `xbg_nr_z5_game_draw`, `xbg_nr_z5g.inc` `nrz5g`): в момент упаковки `OP_X_NR_DRAW` считает
   слот, читает шаблон, подставляет адреса UBO, которые этот поток привязал последними (`Z5G_UBO`, до фильтра NR-UBD), и аргументы записи —
   получает значения draw или «нет значений». Со значениями — писатель серии (`nr_z5r.h`, как в §18.1): draw, читающий поле кэша привязок,
   которого серия ещё не выставляла, остаётся транслятору (голова); остальные пишутся в запасной кусок очереди (хвост), а значения, из
   которых они написаны, — во второй запасной кусок («бок»). Запись несёт слот (`hdr._pad2`) и метку серии (`hdr._pad1`); без переключателя
   оба слова 0, как раньше. Серия кончается на любой другой записи потока (кроме `OP_X_NB_STATE`), на draw без значений, на смене буфера
   команд, на конце записи команд.
4. **Транслятор** (`xbg_nr_z5g.inc` `nrz5t`). Два места:
   - `nbdraw::apply` — `rec_begin` / `rec_end` вокруг `draw()` записи: метка и слот записи в руках; помеченная запись, чей draw не дошёл
     до секции команд хвоста, обрывает серию;
   - `nrdraw::lane_tail` — `tail()` сразу после взятия кэша привязок. Draw хвоста **берётся** только если (1) настоящий кэш привязок держит
     во всех полях, которые читает этот draw, то же, что держала модель серии («тень»: поля серии перед хвостом, затем значения каждого
     взятого draw), и (2) значения из «бока» поле в поле равны значениям, которые транслятор только что разрешил. Тогда секция команд не
     исполняется, в кэш привязок пишутся значения draw (то, что оставил бы хвост), кусок **удерживается**. Иначе секция исполняется как
     сегодня, а после неё публикуется шаблон слота этой записи.
5. **Передача на своём месте.** Пока кусок удержан, `nrsort::pend` указывает на буфер команд, и крюк `NBMT_PRE`, который стоит в каждой
   обёртке `vkCmd*`, в `nbmt::end` и `nbmt::sync`, первым делом отдаёт кусок (`nrsort::cut` → `nrz5t::cut` → `Reader::flush`): обрезает его
   по последнему взятому draw и передаёт очереди (`splice_spare`). То же делает старый хвост `draw()` перед чтением кэша привязок и запись,
   которая «не дошла». После обрыва остаток серии пишется как сегодня. `DM_NR_SORT` при этом равен 0 (с ним Z5 не берёт ничего).
6. **Никогда не берётся:** draw интерфейса, draw в скобке условной отрисовки (`condr::gpu_would`), подача, записанная прямыми вызовами,
   `DM_NR_SORT` / `DM_NR_MDI`.

### 22.3 Почему это точно
- Пакеты draw хвоста зависят только от значений draw и от модели кэша (`nrz5_emit`). Взят draw только при равных значениях и при настоящем
  кэше, равном модели в читаемых полях, — значит, это те пакеты, которые записал бы хвост. О писателе читатель не предполагает ничего:
  писатель, который напишет заранее «не тот» draw, только потеряет серию.
- Порядок: между первым взятым draw серии и передачей куска в буфер команд не пишется ничего — любая запись идёт через обёртку, а обёртка
  сначала отдаёт кусок.
- Всё остальное (состояние, пролог, образы, метки вложений, счётчики, `State`) делает тот же код, что и сегодня.
- Не меняется при `DM_NR_Z5=0`: по одной загрузке и непринятой ветви в `nbd_draw`, в четырёх точках входа NVN (`BindUniformBuffer(s)`,
  `BindVertexBuffer(s)`), в `rec()`, `EndRecording`, `QueuePresentTexture`, в `nbdraw::apply` и в хвосте полосы. На обёртках `vkCmd*` нового
  нет (тот же один `load` у `NBMT_PRE`).

### 22.7 Риски
- На телефоне не исполнялось. `=2` ничего не рисует иначе, но поток игры при нём уже берёт куски у очереди рекордера и пишет в них: ошибка
  там — это падение, а не красная строка. Путь «второй поток берёт и возвращает куски» проверен на ПК с двумя потоками и ThreadSanitizer.
- Слот по «номеру повторения в кадре»: если один и тот же меш с тем же key id рисуется в двух проходах и первый раз отсечён, второй
  попадает в слот первого — промах (viewport). Потери покажет разбивка «values differ» в строке.
- Адрес потока вершин 0 поток игры берёт из точек входа `BindVertexBuffer(s)`; путь `DM_NR_STATE=4 / 5` их не зовёт — там слова места у
  потока игры и у транслятора разойдутся и предсказаний не будет (не ошибка, 0 % в строке).
- Удержанный кусок: всё, что пишет в буфер команд мимо обёрток `vkCmd*` файла `xbg_game.cpp`, нарушило бы порядок. Таких мест быть не
  должно уже сегодня (это правило очереди NB-MT), но `=1` добавляет зависимость от него; `=2` её не проверяет. Первое включение `=1` —
  со скриншотом.
- Память: 8192 × 372 Б = 3 МБ таблица (не освобождается: поток игры может быть внутри), до 256 запасных кусков по 64 КБ в полёте.
- Поток игры — один: первый поток, записавший draw движка, становится владельцем; записи других потоков не помечаются (счётчик в строке).
- По модели поток игры после `=1` — самый длинный поток кадра (7.0–7.9 мс против 7.1–7.3 у транслятора). Если кадр упрётся в него,
  перенос работы на него — вред, даже когда сумма CPU падает. Это риск всего Z5, не только этого шага.

## 25. Z8 `DM_NR_Z8` — поток, который сдаёт запись команд, знает draw точно (ночь 20→21.11, ветка `dos2-z8`)
На телефоне не запускалось. Умолчание 0. Коротко и честно:
- **Сделано.** Из трёх недостающих частей §22.8 построена первая целиком и половина третьей:
  1. *Точное свёрнутое состояние вне транслятора* — готово. Поток, который зовёт `nvnQueueSubmitCommands`, перед постановкой задания в
     очередь проходит свои записи в том порядке, в каком их исполнит транслятор, и ведёт собственную копию `State`. Это не предсказание:
     те же записи, тот же порядок, те же операторы (а для привязок draw и пакетов состояния — те же функции, что у транслятора).
  2. *Ответ на draw без ключа и поиска на трансляторе* — готово. По словам копии поток находит шаблон draw; транслятор для такой записи
     берёт план, запись NR-08 и запись NR-09, которые сам разрешил для этого шаблона, — не строит ключ и ничего не ищет.
  3. *Пакеты* пишет тот же поток (транспорт Z5 без изменений), транслятор берёт их по одному draw после сравнения значений.
- **Не сделано.** Пролог `draw()` по-прежнему исполняется на трансляторе (он дешёвый — его цену теперь меряет своя строка; дорогая его
  часть, хэш кэша теней, относится к draw каскадов, которые до ответа не доходят). «Живые» шаги — образы записи NR-08, смещения кольца,
  набор, метки прохода, виды вершин, viewport — исполняются на каждый draw, как и раньше. Вердикт на серию и пропуск записей серии без
  разбора не построены. То есть транслятор отвеченный draw всё ещё трогает — примерно на треть меньше, а не «почти ноль».
- **Что это значит по модели (§25.7):** транслятор −0.7…1.1 мс из 7.4–7.6, поток игры +0.75…1.2 мс к 6.9–7.4. Сумма CPU около нуля, а самым
  длинным потоком кадра становится поток игры. **По правилу задачи («если добавка потоку игры больше экономии — всё выключено и записано
  почему») `DM_NR_Z8=1` умолчанием быть не должен и выигрышем в этом виде не является.** Ценность шага — точная основа (копия состояния и
  ответы без ключа, обе со сверкой) и строки, которые на телефоне покажут настоящие числа обеих сторон по частям.

### 25.1 Откуда поток берёт данные (ответ на «он же берёт откуда-то данные»)
Транслятор знает о draw ровно три вещи: (а) записи, которые ему прислали; (б) свои таблицы, построенные по прошлым записям; (в) то, что
верно только в момент исполнения (состояние образов, открытый проход, куда сейчас смотрит кольцо). Первое есть у потока игры — он сам
эти записи написал. Второе транслятор может опубликовать. Третье ни один другой поток знать не может: это остаётся на трансляторе.
Z8 делает (а) и (б) и оставляет (в):
- **(а) копия `State`.** Обход (`dm/gfx/nr/nr_z8.h` `Walker`) идёт по памяти команд как `execute()`: `OP_JUMP`, `OP_CALL`, блоки
  `OP_X_NB_STATE` со своим словарём DEF / REF по эпохам, `OP_X_NATIVE_DRAW`. Каждая запись, которая у транслятора пишет `State`, пишет и
  копию: простые записи — операторами веток `execute()` (`fold()`; `source_structure_test.py` следит, что операторы те же и что у
  `execute()` нет ветки с записью в `State`, которой нет в `fold()`), привязки записи draw — `nbd_apply`, пакет `OP_X_NR_STATE` —
  `NR3_DEFINE_APPLY_RAW` (обе — функции самого транслятора). Вместо объектов шейдеров копия держит слово программы на стадию — `serial`,
  под которым бэкенд кэширует шейдеры программы.
- **id фиксированной части.** Всё, что читает разрешение draw помимо таблиц (цели, viewport, scissor, пулы, программы, формат вершин,
  смешение, глубина / трафарет, растеризация, привязки хранилищ), разбито на пять групп; содержимое группы получает номер в словаре,
  который сравнивает байты (не только хэш), пять номеров — ещё один. Равные id = равные байты. Номера не выдаются повторно.
- **(б) шаблон и ответ.** Слова места (key id, вид и аргументы draw, индексный буфер, адрес потока вершин 0) + id выбирают слот таблицы.
  Транслятор, записав draw сам, публикует в слот шаблон: значения хвоста полосы (как в Z5) **и слова, которые читало разрешение**, с их
  значениями из своего `State`: хэндлы текстур и сэмплеров по строкам плана NR-08, диапазоны вершин привязок конвейера, слот и размер
  каждого блока UBO. Рядом, в своей памяти, — ответ: план, номер записи NR-08, запись NR-09, определение прохода, объекты шейдеров и три
  поколения, при которых они разрешены. Поток игры берёт шаблон только если **каждое** сравниваемое слово равно слову его копии.
- **(в) на трансляторе.** Запись несёт номер слота и версию шаблона. Транслятор на крюке `draw()` (там, где спрашивает таблицу Z3)
  проверяет: версия слота та же, поколения NR-08 / NR-09 / объектов те же, определение прохода то же, объекты шейдеров те же, ворота
  полосы открыты — и идёт в `nrz3::answered` (вторая половина `nrz3::draw`, вынесенная в отдельную функцию: запись NR-08 жива, блоки,
  набор, обход образов, метки прохода, общий хвост). В хвосте — вердикт Z5: значения, разрешённые сейчас, равны записанным, кэш привязок
  держит модель серии → пакеты берутся, иначе команды пишет хвост.

### 25.2 Почему это точно
- Копия равна `State` по построению (те же записи в том же порядке теми же операторами) — и это проверяется: на ПК поле в поле против
  независимого исполнителя, на устройстве `=2` — свёрткой по восьми частям у одной записи draw из восьми.
- Ответ — не предсказание: его дал сам транслятор для draw с теми же сравниваемыми словами при тех же поколениях своих таблиц. Что
  сравниваемых слов достаточно, на устройстве проверяет `=2` (ответ обхода против собственного разрешения пути на каждом draw).
- Значения проверяются на каждый draw в момент исполнения, как в Z5. Ошибка в них стоит серии, а не кадра.
- Draw, которому пролог изменил `State` (переопределение пре-пасса, двойники MAT / SURF, LIGHTFUSE, ONCHIP, слитый пост), не отвечается и не
  публикуется: в этот момент `State` — не копия.
- Запись берётся только если её слова написал обход **этой** подачи (штамп номера подачи в записи) и это первое исполнение записи
  (повторное исполнение диапазона кэшем теней не берётся). Запись, достигнутая через `OP_CALL`, не отвечается.
- Порядок обходов = порядок очереди: обход и постановка задания идут под одним замком фронта, номер подачи берётся под ним же.
- При `DM_NR_Z8=0`: `nvnQueueSubmitCommands` платит одну загрузку, `draw()` — одну загрузку и непринятую ветвь, `xbg_submit` — две записи
  в переменную. Формат записей не меняется (слова `_pad0` / `_pad1` / `_pad2` / `cond_addr` остаются нулями).

### 25.3 Что не отвечается (идёт как сегодня)
UI Iggy; draw без key id; draw с условием отрисовки; QUADS; draw с программой без `serial`; набор шейдеров со статическим блоком UBO, больше
12 строк текстур или 8 смещений (с §36 — 16; служебные блоки стадий, привязанные динамическими буферами, шаблону не мешают); draw без собственной записи NR-09 (варианты PRESKIN / POSONLY), с нулевым потоком или узором QUADS;
draw под переопределением пре-пасса и любой, чей `State` менял пролог; draw каскадов под кэшем теней (их отбрасывает пролог); при
`DM_NR_SORT` / `DM_NR_MDI`. **На тайлерах (Mali / PowerVR) из-за этого доля будет заметно ниже, чем на Adreno:** пре-пасс, двойники и
PRESKIN там включены умолчанием. Сколько именно — покажет прогон под `DM_GFX_SIM_GPU=mali` (разбивка «not describable»).

### 25.5 Строки лога (раз в 10 с)
- старт: `[nr] DM_NR_Z8=… (NR-ZERO Z8, read at init)` и `[nr] DM_NR_Z8=… (NR-ZERO Z8: apply / verify …)`;
- **`[nr] z8 walk`** — поток игры: подач, записей и записей draw на подачу; отвечено (%), причины «нет» (нет ключа, через `OP_CALL`, слот пуст,
  другое место, другой id, текстуры, вершины, UBO); головы, хвосты, серии и их длина; новых id и обновлений групп на draw; **`walk N ns a
  record = X ms a submission`** — вся добавка потоку игры на подачу; `a draw record … N ns` — одна запись draw (1 из 64);
- **`[nr] z8, translation thread`** — сколько записей взяли ответ обхода и почему нет (нет шаблона, слот переиздан, сдвинулось поколение,
  другое определение прохода, ворота, другие объекты шейдеров); вердикты хвоста (взято, серии, обрывы по причинам, какое значение разошлось);
  опубликовано шаблонов и почему draw не описывается;
- **`[nr] z8 by part`** — транслятор на отвеченный draw по частям: проверки записи, блоки UBO, образы, набор и метки, метки прохода, виды
  вершин, viewport, учёт и вердикт, конец; `N ns an answered draw`; **`the prologue of draw() before the hook N ns`** — цена пролога;
- `[nr] draw span` (как раньше) — весь путь записанного draw движка: сравнивать `=1` с базой;
- `[nr] z8 check (DM_NR_Z8=2)` — копия против `State`: compared / same / **bad**; слова программ; id не от байт копии; ответы обхода против
  пути: compared / same / устарело / **bad**; пакеты: compared / same / **bad**;
- красные: `【红】[nr] z8: …` (копия ≠ `State`; ответ ≠ разрешению пути; draw отвечен по шаблону, слова которого не равны `State` — ключ сам

### 25.9 Риски
- На телефоне не исполнялось. `=2` ничего не рисует иначе, но обход уже работает на потоке игры и берёт куски у очереди рекордера:
  ошибка там — падение, а не красная строка. Путь проверен на ПК двумя потоками и ThreadSanitizer на модели, не на движке.
- Обход читает объект пула (`OP_SET_TEX_POOL` / `_SAMP_POOL`) и `serial` программы в момент сдачи, транслятор — в момент исполнения. Игра
  между сдачей и исполнением их не меняет (иначе и сегодняшний путь читал бы не то), но формально это два момента; `=2` поймает (часть
  «targets / viewport / scissor / pools», слова программ).
- Номер подачи обход берёт как «следующий» под своим замком. При `DM_NB_OWN=1` задание кадра ставится иначе; если номер не совпадёт,
  штамп записи не совпадёт с номером у транслятора — ничего не берётся (строка покажет `records of another walk`), ошибки не будет.
- Замок вокруг обхода и постановки в очередь: сдающие потоки ждут друг друга на время обхода (сегодня — только на время постановки).
- Повторная инициализация бэкенда сбрасывает `State` — обход после этого останавливается навсегда (красная строка), ключ в этой сессии
  больше не работает.
- `=2` дороже базы: свёртка 12 КБ таблиц у каждой восьмой записи draw на обоих потоках (≈ +0.3…0.5 мс каждому). Числа `walk … ns` из
  `=2` слегка завышены; чистые — из `=1`.
- Самый длинный поток после `=1` — поток игры (§25.7). Это главный риск шага, а не побочный.

## 28. Z8, часть 1: обход на своём потоке — `DM_NR_Z8_THREAD` (ночь 20.11, после Z8, ветка `dos2-z9`)
На телефоне не запускалось. Умолчание 0. Это первая строка §25.8 и условие для всего остального: пока обход идёт на потоке игры,
включать `DM_NR_Z8=1` незачем.
- **Сделано.** При `DM_NR_Z8_THREAD=1` поток, который зовёт `nvnQueueSubmitCommands`, под тем же замком и на том же месте только
  **сдаёт** список хэндлов (копия до 8 хэндлов на месте, один `notify`, если обходчик спит). Обход — свёртка, id, шаблон, пакеты —
  идёт на потоке `dm-z8walk` тем же кодом. Порядок обходов = порядок очереди, как и раньше: сдача под замком фронта.
- **Обходчик ничего не пишет в память команд.** Транслятор может исполнять ту же запись в тот же момент, поэтому слова записи
  (метка серии, слот, id и версия шаблона) идут в кольцо меток `nr_z8.h` `Marks` — по **месту записи в подаче** (k-я запись
  `OP_X_NB_DRAW` без `NBD_F_CHECK` в порядке обхода = порядке `execute()`). У места жетон «подача << 24 | k», который не повторяется.
  Писатель: жетон 0 → слова → жетон. Читатель (транслятор считает те же записи сам): жетон равен (подача, k), адрес записи равен
  адресу записи, жетон тот же после чтения слов — только тогда слова взяты.
- **Транслятор не ждёт обход на записи.** Если он обогнал обходчика (записи ещё нет в кольце) или кольцо перекрыто, запись идёт
  без слов: draw разрешается и записывается как сегодня. Счётчики в строке покажут, как часто.
- **Транслятор ждёт обходчика в конце подачи** (`Z8G_DONE` в `x_submit`, перед тем как подача считается исполненной): игра
  переиспользует память команд после исполнения подачи, и обходчик к этому моменту обязан из неё уйти. Обычно обходчик далеко
  впереди и ожидания нет; каждое ожидание считается. Подача, которую не сдавали (ключ ещё не взведён или уже снят), не ждёт.
- **Первые серии подачи режутся короче** (`nr_z5r.h` `Writer::max_tails` / `split()`): когда транслятор стоит без дела и начинает
  подачу одновременно с обходчиком, серия из 150 draw была бы опубликована уже после того, как транслятор дошёл до её начала.
  Поэтому первая серия такой подачи публикуется через 8 draw хвоста, следующая через 16, 32 … (`DM_NR_Z8_SPLIT`, 0 — выкл.);
  новая серия продолжает ту же модель кэша привязок (читатель и так проверяет кэш на каждый draw).
- **Не сделано:** присоединение транслятора к серии с середины (если он обогнал начало серии, серия пропадает целиком — пакеты
  пишет хвост; ответы без ключа при этом берутся). С `DM_NB_OWN` поток не включается (номер последней подачи кадра при сдаче
  неизвестен) — обходит сдающий поток. **[Неверно, исправлено 20.11: номер известен, поток с `DM_NB_OWN` запускается — §36.2.]**

### 28.1 Почему это точно
- Слова записи берутся только если их написал обход **этой** подачи для **этой** записи на **этом** месте порядка (жетон + адрес +
  повторное чтение жетона). Запись, исполненная дважды в одной подаче, получает слова своего места, а не последнего обхода.
- Если счёт записей у двух потоков разойдётся (не должен: обход повторяет `execute()`), запись ищется дальше по кольцу (до 2 048
  мест), иначе остаётся без слов; расхождение — красная строка. Диапазон, исполняемый кэшем теней второй раз, не считается.
- Всё, что проверяла `DM_NR_Z8=2` (копия против `State`, ответ против собственного, пакеты против собственных), проверяется и на
  своём потоке: свёртка копии едет в той же записи кольца.
- При `DM_NR_Z8_THREAD=0` ничего не изменилось: одна загрузка в `x_submit` (`Z8G_DONE`), записи пишутся как в §25.

### 28.2 Строка `[nr] z8 thread` (раз в 10 с)
Сдающий поток: сдач, **нс на сдачу**, сколько раз будили обходчика. `dm-z8walk`: подач, **мс CPU потока на подачу**, серий разрезано.
Транслятор: записей спросило слова, **есть (%)**, ещё не написано, обход подачи не начат, найдено дальше, счёт разошёлся; **ожиданий
в конце подачи и мс на ожидание**. В строке потоков `DM_NR_CPU=1` обходчик виден по имени `dm-z8walk`.

## 29. Z8, часть 2: слово чтения записи NR-08 — `DM_NR_Z8_IMG`
На телефоне не запускалось. Умолчание 0 (2 сверка / 1). Работает и без своего потока.
- **Что выяснилось до кода.** Постановка §25.8 («слово ставит первый draw записи в подаче») уже почти выполнена словом Z3b: по
  серии K оно стоит 61 % обходов. Остальные 39 % (≈ 480 обходов на кадр по ≈ 1.75 мкс — это и есть «683 нс на draw») — не вторые
  обходы тихих записей (они дешёвые), а записи, у которых есть **образ, писанный GPU** (цель прохода, которую потом сэмплируют):
  такой образ `nr_dimg_skip` никогда не считает тихим, и каждый draw ведёт его в `get_image` + `prepare_read`, хотя те почти
  всегда ничего не делают. Цена — не команды, а холодные строки кэша объектов `Image`.
- **Сделано.** Слово чтения `nrz_rtq` в записи NR-08 (`nr_z3e.h`): ставится после обхода, который оставил каждый образ записи
  либо тихим, либо «прочитан и делать нечего» — проверен в этой подаче, в раскладке для чтения, не вложение открытого прохода,
  нет ждущей очистки, не писан после барьера, который видит это чтение (выражение — дословно из `prepare_read`). Стоит, пока
  стоят: эпоха образов (те же типы полей, что у Z3b), подача, серийный номер слота, открытый проход (проход + кадровый буфер),
  признак «чтение только фрагментным шейдером» и **счёт меток записи, кроме меток, которые draw ставит вложениям своего прохода**
  (`write_seq − nrz_pm`; `nrz_pm` считается в двух местах — быстрый путь `create_pass` и `nrz3::answered`). Каждая метка записи
  любого образа — новый `write_seq` (проверяет `source_structure_test.py`), поэтому пока счёт стоит, ни один образ вне открытого
  прохода не писался, а точки барьеров только растут. Пока слово стоит, образы записи не трогаются вовсе.
- **Когда слово не спрашивается:** ждёт хоть одна очистка (`pclear_n`), включён учёт чтений (политики тайлеров: `DM_NR_RP`,
  пре-пасс, история store, `DM_GFX_NOLOAD`; `DM_NB_TRANSIENT`, `DM_NR_PRESENT`, значения проходов, `DM_NB_OPBARRIER=2`). То есть
  **на Mali / PowerVR эта часть не даёт ничего** — там каждое чтение кому-то нужно. На Adreno (`DM_NB_OPBARRIER=1`) спрашивается.
- **`=2`:** слово спрашивается, обход идёт и обязан ничего не изменить (открытый проход, точки барьеров, метки записи, слот,
  эпоха образов, образ за текстурой). Строка `[nr] z8 images`: спрошено, **стояло (%)**, поставлено, не поставлено по причинам
  (первое использование / другая раскладка, вложение открытого прохода, писан после барьера), **bad**.

## 30. Z8, часть 3: виды раз за подачу на диапазон — `DM_NR_Z8_VIEW` (нужен `DM_NR_Z8_THREAD=1`)
На телефоне не запускалось. Умолчание 0 (2 сверка / 1).

## 31. Z8, часть 4: вердикт хвоста из памяти самого транслятора — `DM_NR_Z8_VAL` (нужен `DM_NR_Z8_THREAD=1`)
На телефоне не запускалось. Умолчание 0 (2 сверка / 1).

  вердикте другое: он читает память, которую только что писал **другой поток** — боковой кусок со значениями и пакеты куска

  `nr_z8.h` `expect_diff` сравнивает значения, разрешённые сейчас, с ожидаемыми, **не читая бокового куска**; длина и число

  привязок, длина куска — ни боковой кусок, ни пакеты куска не читаются. Серия идёт одним способом от первого draw хвоста до
  последнего; draw, чей `State` менял пролог, так не называется.
- **`=2` (и при `DM_NR_Z8=2`):** идёт прежний вердикт, и то, что он находит в кусках, обязано совпасть с названным (код различия

- Сравнение значений осталось (оно дешёвое и держит точность на момент исполнения); убрано чтение чужой памяти.

## 36. Первая серия телефона (Q8, 20.11 утро): Z8 не делал ничего — причины и исправление (ветка `dos2-z10`)
Серия главного агента: Mi 14 Ultra, Adreno 750, dos2 `e34c3c7`, APK `0ad0c7dd`, Форт Радости, стоя (`Q8_v1`) и ходьба (`Q8_v2`),
окружение §34 «сверки». Обе записи показали одно и то же: красных строк Z8 нет, во всех сверках `bad 0` — и при этом **ни одна
сверка, кроме копии состояния, ничего не сравнила**. Что было в логе и что это значит:
| Строка телефона | Что на самом деле |
|---|---|
| `z8 walk: 547 submissions walked, 302 records and 0 draw records each` | это меню и загрузка — там записей draw движка нет. В уровне та же строка: `6063 records and 2216 draw records each`. Обход записи видит, записи идут тем же путём, что и на ПК (`OP_X_NB_DRAW` в сданной памяти команд; `through OP_CALL 0`, `no key 0`) |
| `State against the walk's copy: compared 275355 same 275355 bad 0` | копия состояния точна — единственная сверка, которая работала |
| `answered (template matched) 0`, `slot empty or being written 2202840` | обход на каждой записи draw находил пустой слот: шаблонов нет |
| `templates published 0, not describable 1428743 (… a static uniform block 1428743 …)` | **причина 1** (ниже): транслятор не описал ни одного draw |
| `0 engine draw records at the hook of draw()` | при `=2` так построено (причина 3) — не ошибка, но строка этого не говорила |
| `DM_NR_Z8_THREAD=1: DM_NB_OWN queues … the submitting thread walks`, затем `DM_NR_Z8_VAL=2 needs … off`, `DM_NR_Z8_VIEW=2 needs … off` | **причина 2**: поток обходчика не запускался, с ним отключались части 3 и 4 |
| `z8 walk (DM_NR_Z8=1643886944)` | причина 4: в строку печатался адрес функции |
| `z8 images: 0 walks of an answered draw asked` | причина 3: при `DM_NR_Z8=2` эта часть не исполняется вовсе |

### 36.1 Причина 1 (главная): ни один draw не был шаблоном
- **Что было.** `nrz8t::publish` отказывал draw, если у набора число динамических смещений не равно числу блоков кольца
  (`pl->p.nubo != pl->p.ndyn`), с причиной «a static uniform block». Условие писалось против блока кольца, запечённого в набор.
  Но на устройстве с включёнными динамическими буферами (Adreno: `dyn_mode_for` даёт режим 1, «every block a dynamic offset»)
  динамическим буфером привязан **каждый** буфер набора: и блоки игры (смещения в кольцо констант), и служебные блоки стадий
  (`XBG_SOURCE_SUPPORT`), и константы c1 (`XBG_SOURCE_C1`) — у этих смещение своё и от draw не зависит. В плане NR-08 это строки
  `NRD_K_FIXED_DYN`: в `ndyn` они входят, в `nubo` нет. Тот же лог телефона: `NVN PERF binds … offsets_per_bind=7.1` при
  `[nr] desc … 4.2 ring blocks a draw`. То есть условие отказывало **каждому** набору игры.
- **Почему не поймано на ПК.** Модель `nr_z8_test` строила наборы только из блоков кольца, а само решение «можно ли описать»
  жило в движковой части (`xbg_nr_z8.inc`), которую хост-тесты не исполняют (§25.6: «только собрана»).
- **Исправление.** Решение и описание вынесены в `dm/gfx/nr/nr_z8.h` — `plan_form` и `describe` над настоящим планом
  `nr_dplan`; движок зовёт их же. Шаблон несёт динамические смещения двух видов:
  - блок кольца — как раньше: (адрес − смещение), слот, размер; обход считает смещение по адресу из своей копии;
  - служебный блок — **само смещение** (слово с признаком `DYN_FIXED`); `match()` отдаёт его как есть, `expect_diff` сравнивает.
  Отказ остался для блока кольца, запечённого в набор (`nstat > 0`, `DM_NR_DESC_SPLIT`: сам набор зависит от смещения), и для
  хвоста, привязавшего не столько смещений, сколько в плане. Смещений в шаблоне теперь до 16 (было 8): это предел устройства, а
  среднее по Форту Радости — 7.1, то есть наборы с девятью и больше не редкость. Слот шаблона 960 → 1 152 байта, таблица
  7.7 → 9.2 МБ при включённом ключе.
- **Почему это точно.** Смещение служебного блока хранит запись NR-08 (`nrdesc::Ent::off`), а запись называет ответ; при
  применении `nrz3::answered` берёт его из записи, как и до этого. Содержимое служебного блока зависит от размера viewport и
  функции альфа-теста — оба входят в id фиксированной части, то есть в выбор слота. И как любое значение шаблона, смещение
  сравнивается на каждом draw с разрешённым в момент исполнения: ошибка стоила бы серии, а не кадра.

### 36.2 Причина 2: поток обходчика не запускался при `DM_NB_OWN`
- **Что было.** `DM_NB_OWN=1` — умолчание игры (блок JNI приложения), игрокам его не выключить. `nrz8t::boot` при нём отказывал
  ключу `DM_NR_Z8_THREAD` с объяснением «номер последней подачи кадра при сдаче неизвестен» (§28, §25.9).
- **Это объяснение неверно.** Номер и обычной подаче, и открытому заданию кадра (`XJ_OWN`) выдаёт одно место — `x_push`
  (`g_x_subs + 1`), и выдаёт под замком Z8, под которым идёт сдача (`Z8G_SUBMIT_BEGIN` … `Z8G_SUBMIT_END`); больше номеров
  подач никто не выдаёт. Объявленный обходу номер и есть номер задания. Телефон это уже показал сам: при `DM_NB_OWN=1` свёртки
  копии сравнивались по точному номеру подачи — 275 355 из 275 355, `records of another walk 0`. `DM_NB_OWN` порядок исполнения
  записей не меняет (`xbg_nb_own.inc`: «nothing is executed differently»).
- **Исправление.** Отказ снят (`nr_z8.h` `walker_thread`). Фронт на каждой подаче отдаёт бэкенду оба номера — объявленный и
  полученный заданием (`Z8G_SUBMIT_END` → `xbg_nr_z8_sub_end`); расхождение (по построению невозможное) — красная строка и
  остановка обхода, счёт — в конце строки `z8 walk`: `submission numbers: N announced … differ 0`. Запасной путь проектировать не
  пришлось: выключать `DM_NB_OWN` не нужно.

### 36.3 Причина 3: «крюк не достигается» при `=2` — так построено; `DM_NR_Z3` не нужен
Крюк `draw()` спрашивается только при `DM_NR_Z8=1`. При сверке каждый draw разрешает и записывает сам транслятор, а ответ
обхода сравнивается в хвосте полосы (`publish`; счётчик `answers of the walk … compared` строки `z8 check`). Ни `DM_NR_Z3`,
ни другой ключ полосы для Z8 не нужен — окружение §34 по ключам было верным. Строка `z8, translation thread` теперь пишет это
сама. Следствие, которого в §34 не было: **`DM_NR_Z8_IMG=2` при `DM_NR_Z8=2` ничего не проверяет** — слово чтения спрашивает
только draw, взявший ответ обхода. Сверка этой части — `DM_NR_Z8=1 DM_NR_Z8_IMG=2`, то есть после чистой сверки самого Z8;
при старте об этом теперь строка. Части 3 и 4 (`_VIEW`, `_VAL`) при `DM_NR_Z8=2` исполняются.

### 36.4 Причина 4 и защита от повторения
- `DM_NR_Z8=1643886944`: в `nrz8t::tick` имя `boot` — это функция `nrz8t::boot()`, а не переменная `nrz8g::boot`; печатался
  её адрес. Исправлено, `source_structure_test.py` следит.
- **Пустая сверка больше не выглядит пройденной.** Если за окно 10 с записано ≥ 20 000 draw движка и не сравнено ни одного
  ответа, в лог идёт красная строка `【红】[nr] z8: verify compared NOTHING in this window …` с числами (отвечено обходом,
  опубликовано шаблонов, не описано).

**Строки, которые доказывают, что Z8 исполняется** (в окне 10 с внутри уровня; в меню и на загрузке записей draw нет — их окна
не считаются):
1. При старте: `[nr] DM_NR_Z8_THREAD=1 (NR-ZERO Z8, the walk on its own thread "dm-z8walk") …`. Строк `the submitting thread
   walks`, `DM_NR_Z8_VAL=2 needs …: off`, `DM_NR_Z8_VIEW=2 needs …: off` быть не должно.
2. `[nr] z8 walk (DM_NR_Z8=2)` — в скобках 2, а не большое число; `… and N draw records each`, N ≈ 2 000;
   **`answered (template matched) X (Y%)` с X > 0**; `slot empty or being written` — малая доля записей draw, а не все;
   в конце `submission numbers: N announced …, differ 0`.
3. `[nr] z8, translation thread (DM_NR_Z8=2): 0 engine draw records at the hook of draw() (verify never asks the hook …)` —
   ноль здесь верен; дальше **`templates published` > 0** (в первом окне уровня — сотни и больше), `a static uniform block 0`
   на Adreno, `at the lane's command section N draws (marked M` с M > 0`)`, `would take K` с K > 0.
4. `[nr] z8 check (DM_NR_Z8=2)`: `State against the walk's copy: compared` > 0, **bad 0**; **`answers of the walk against the
   path's own resolution: compared` > 0**, **bad 0**; **`draws =1 would take: compared` > 0**, `same` = `compared`, **bad 0**.
5. `[nr] z8 thread`: `walker thread dm-z8walk: N submissions walked`, `there x %` с x > 0, `counts differ 0`; в строке потоков
   `DM_NR_CPU=1` есть `dm-z8walk`.
6. `[nr] z8 views`: `asked` > 0, **bad 0**; `[nr] z8 values`: `named from this thread's memory` > 0, **bad 0**.
7. Красной строки `z8: verify compared NOTHING in this window` нет.
Что решает серия:
- Любой `bad` > 0 или красная строка `z8` / `z5 game` / `z3 epochs` — стоп, строка называет часть.
- Красная `verify compared NOTHING` или `answered 0` — Z8 снова не исполняется: причину называет разбивка `not describable (…)`
  в строке `z8, translation thread` и причины «нет» в `z8 walk` (другое место, другой id, текстуры, вершины, размер блока).
- Доля `answered` в R_v1 / R_v2 и разбивка причин — первые настоящие числа Z8; `walk … ms`, `ms thread CPU a submission`,
  `ns a post` — цена обходчика. R_m1: ждём долю ниже и ненулевые `State changed by the prologue`, `a static uniform block`.
- Применение в эту серию не входит. Следующий шаг только при `bad 0` во всех трёх сверках: один прогон
  `DM_NR_Z8=1 DM_NR_Z8_THREAD=1 DM_NR_Z8_IMG=2 DM_NR_Z8_VIEW=2 DM_NR_Z8_VAL=2 DM_NR_Z3B=2 DM_NR_Z3D=2` — там крюк обязан быть
  ненулевым (`N engine draw records at the hook of draw(); took the walk's answer X`), `z8 images: asked` > 0, **bad 0**,
  `spot checks … bad 0`, снимок экрана против R_p0.
