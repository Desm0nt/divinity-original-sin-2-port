# VK-NATIVE: динамическое разрешение ломало 3D (SUPPORT-блоки), 21.11

Ветка `dos2-vk5-drs` от `3387f0f`, дерево `wt-vk5-drs`. Телефон не трогался.

## Симптом (прогон S08, Mi 14 Ultra, APK `3387f0f`)
`DM_VK_NATIVE=1`, `DM_DOS2_DRS=70:100`, `DM_DOS2_DRS_TARGET_MS=16.6`. Как только DRS игры меняет размер 3D во время игры
(`DRS current 1485x668 = 68.7 %`, потом `1755x790 = 81.2 %`), 3D пропадает: поверх HUD ровная серо-зелёная заливка с зелёными
вспышками. В логе — красная строка `[vkn] ui: no SUPPORT block: draw dropped` (только в S08, ни в одном другом прогоне). Постоянные 75 / 85 %
(`DM_HACK_SCALE`, S04 / S06 / S07) рисуют правильно.

## Причина
Каждый шейдер DOS2 читает SUPPORT-блок — 1392 байта переводчика с размером viewport (`xbg_support_defaults`: 1/w, 1/h с байта 144,
w, h с байта 160, 73 единицы с байта 192). Бэкенд держит один блок на размер (`vkn_shader_support`, `dm/gfx/vkn/vkn_shader.c`), и кэш был
**на 32 размера на весь процесс** (`SUPPORT_CAP = 32`), без освобождения. Старый путь (`xbg_game.cpp support_block`) держал неограниченную
карту.

Динамическое разрешение рисует часть полноразмерных целей, viewport = текущий размер, и каждый шаг контроллера (1,25 % вверх, 2,5 %
вниз, скачок по модели) даёт **новые** размеры: сама 3D-часть и цепочка половин / четвертей / восьмых (HalfRes, Quarter, Eighth и т. п.).
Около 20 размеров уже заняты на 100 % (окно, атлас теней, пирамида яркости...). В S08 первый подъём на загрузке
(100 → 73,7 → 86,2 → 98,7 → 100 %) выбрал остаток кэша, и дальше каждый новый размер получал отказ:
- путь отрисовки (`vkn_draw.c build_set`) при отказе привязывал **нулевой блок** — 1/w, 1/h, w, h = 0: каждый полноэкранный проход
  считал UV = 0 и читал один тексель → ровная заливка цветом этого текселя (серо-зелёный туман), вспышки — где размер ещё был в кэше;
- UI (`vkn_ui.c`) выбрасывал рисунок с красной строкой `no SUPPORT block`.

На 100 % размеры уже были в кэше — картинка возвращалась. Постоянный масштаб добавляет 4–6 размеров один раз и в 32 укладывается,
поэтому S04 / S06 / S07 чистые.

Техники с частью цели проверены и тут ни при чём: пост (`vkn_post.c` `R_PART`, `R_HCOVER`, `R_STEP_COVER` — слияние берётся только при
полном покрытии; в S08 и так `fused 0`), LIGHTFUSE Fog (`F_COVER`: «Fog draw does not cover its target» в логе — отказ, Fog рисуется как
записан, обучение сбрасывается), Sky + Light требуют один viewport у обоих рисунков. Политика LOAD / STORE в S08 выключена (`LOAD=0 STORE=0`).

## Исправление (умолчание, без флагов)
- `vkn_shader.c`: кэш на 256 размеров; когда заняты все — переписывается на месте самый давно не использованный размер, который не
  использовался 16 кадров (в полёте не больше 3: GPU его уже не читает). Каждое обращение помечает размер кадром `vkn_frame()`.
  Строка в логе один раз при первом переиспользовании и строка счётчиков в переписи шейдеров (`shaders: SUPPORT blocks: N viewport sizes
  (cap 256), rewritten in place R, none idle F, frame-local copies C`).
- Страховка: если блока нет и переписать нечего (все размеры использованы за 16 кадров), путь отрисовки и UI кладут копию блока в
  кольцо записи (`vkn_ring2`, на этот кадр) — **никогда не нулевой блок**. `vkn_shader_support_fill` даёт байты. Красная строка
  (первые 8) `SUPPORT block for WxH: all N sizes used in the last 16 frames: a frame-local copy is bound`.
- `vkn_draw.c`: быстрый кэш на 4 размера теперь верен только в своём кадре (в другом кадре спрашивает `vkn_shader_support` заново и так
  помечает размер использованным — размер, нужный каждый кадр, никогда не переписывается под GPU).

Затронутые общие файлы: `dm/gfx/vkn/vkn_shader.c/.h`, `dm/gfx/vkn/vkn_draw.c`, `dm/gfx/vkn/vkn_ui.c`; тест
`dm/gfx/vulkan/engine/tests/vkn_stage2_test.c` (`test_support_drs`).

## Проверка (хост)
`test_support_drs`: 200 шагов DRS по 2 кадра, каждый шаг — 3D-часть + 3 половинки (800 размеров) и окно каждый кадр: ни одного отказа,
содержимое каждого блока = его размер, блок окна не сдвинулся и не переписан, кэш 256, переиспользований > 400; возврат к размеру
раннего шага даёт верный блок; 300 новых размеров в одном кадре → часть отказов, `vkn_shader_support_fill` даёт верные байты; после 20
пустых кадров размеры снова выдаются.

## Попутно: уровень хаков 2 и масштаб (S04)
`DM_HACK_TIER=2` в `dm/env` не даёт 85 % — **так задумано**: шестерёнка всегда экспортирует `DM_HACK_SCALE` явно (`Tl2Gear.java`
секция 3D-разрешения: `100` при DRS, значение строки при постоянном масштабе) и `DM_HACK_FSR` (1 / 0), а явное значение сильнее уровня
(`nr_hacks.h nrh_value_from`). Лог S04 это и показывает: `SCALE=0 -> the game's DRS object`. Масштаб уровня работает, только если
шестерёнка его не задала (например, `DM_HACK_SCALE=85` в `dm/env`, как сделал S06 с 75). То же на старом пути: S10 (`=0`,
`TIER=2`) — 100 %, S09 (Mali-модель, `TIER=2`) — 100 %: дело не в бэкенде, а в правиле шестерёнки (коммит `973da1e`, 19.11: строка
«Разрешение 3D» по режиму — единственный источник масштаба, страница хаков больше не показывает и не задаёт SCALE / FSR). Столбец
«Разрешение 3D» в таблице 8.3 NR-HACKS.md при запуске из шестерёнки не действует. Менять правило (чтобы уровень снова опускал 3D) —
решение хозяина: оно идёт против выбранной игроком строки разрешения.
