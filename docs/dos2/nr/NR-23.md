# NR-23 `DM_NR_NOCALL` — собственные вызовы NVN движка на draw: счёт, сверка и то, что режется чисто (17.11.2026, ветка `dos2-nr23`)

Шаг из аудита `docs/dos2/nr/AUDIT-REMAINING.md` (ветка `dos2-nraudit`), строка NR-23, сегменты S9 / S5. База: `dos2-nr09` (NR-02/05/06/07/08/09)
+ слитая `dos2-nr16` (merge `4b4c5c0`: конфликты в `source_structure_test.py` и в одной строке `xbg_game.cpp` — оставлены обе стороны).
**На телефоне не исполнялось ни строчки** (телефона не было). Главный вывод — в §1: посылка аудита для этого движка верна только на
13–24 % вызовов, и на них режется только трамплин, а не тело вызова.

## 1. Что оказалось (до кода): почему «оборвать 14.6 тыс. вызовов в thunk» в этом движке нельзя
Аудит предполагал: после хука `0x924730` движок делает привязки текстур / UBO / VB и сам draw, запись `OP_X_NR_DRAW` уже всё несёт,
значит вызовы можно обрывать по флагу потока. По коду игры (`main.raw` v786432, разбор capstone + `NATIVE_PLAN.md` 1.7) и по коду HLE:

| Факт | Откуда | Следствие |
|---|---|---|
| Запись draw **строится из этих вызовов**: внутри скобки NB-09 `BindUniformBuffer` / `BindTexture` пишут в тень `nbd_shadow`, а `DrawElements` превращает тень в `OP_X_NB_DRAW` (+ хвост NR-09) | `nvn_nb_draw.inc`, `hle_nvn.c bind_handles / nbd_draw` | «запись уже всё несёт» верно только **после** вызовов. Хвост NR-09 (id ключа и набора текстур) привязок не заменяет: таблицы NVN бэкенда (`state.tex / state.ub`, нужны запасному пути) пишутся хэндлами и адресами из записи |
| Состояния (программа, blend / depth / raster, формат вершин, **VB**) движок шлёт в NVN **из обработчиков своих пакетов** (`0x9283a0` и др.), а не на draw | `NATIVE_PLAN.md` 1.7, дизассемблер | в момент вызова неизвестно, возьмёт ли следующий draw NR-09; это не «вызовы draw». Их записи уже сворачивает NB-13a. Убрать сами вызовы = нативные обработчики пакетов состояния (основная линия NR, не NR-23) |
| UBO: `0x926f90` + `0x925740` (5.9 КБ кода: кольцо констант, спин-блокировка, аллокатор) на каждом draw зовут `BindUniformBuffer`; готовых диапазонов в рендерере нет | там же | их вызовы можно только перехватывать (как сейчас). Модель этого кода — отдельная большая работа с высоким риском |
| Текстуры: `0x924730` — 173 инструкции: для слотов грязного диапазона с id ≠ −1 `GetTextureHandle(dev+8, id, сэмплер)` + `BindTexture(cb, стадия, слот, handle)`, затем сброс шести диапазонов | дизассемблер (полностью) | **моделируется точно** |
| Draw: `0x928e80` / `0x928fb0` — по 75 инструкций: запись индексного буфера по хэндлу, [UBO], сброс текстур, `SetRenderEnable(cb, 1)` если рендер был выключен, `DrawElements` / `DrawElementsInstanced`, один байт флага | дизассемблер (полностью) | хвост (после UBO) **моделируется точно** |
| Каждый вызов NVN у DOS2 (сборка с `DM_GAME_D3`) = thunk (`stadd` счётчика) + обёртка большого стека (сохранение x0–x7 / q0–q7, вызов `nvn_bigstack_top`, смена `sp`) + тело | `nvn_thunks.S`, `nvn_entry.S` | режется только **трамплин**; тело (тап NB, тень NB-09, метки WT, запись) должно отработать — его эффекты читают планировщик NB, `wt_use_ids`, бэкенд |

Числа из логов телефона (палуба, не тяжёлые сцены): 982.8 draw движка в скобке на кадр, 3.3 привязки на запись, из них UBO ≥ 1.98
(`buf_gen 1.98 bumps a record`), текстур 0.47…1.32 (`tex_gen 0.47`). На draw чисто режется `2·T + 1` вызов (T — привязки текстур):
**1.9–3.6 вызова × 983 ≈ 1.9–3.6 тыс. из 14.6 тыс. (13–24 %)**. Остальное: UBO ≈ 2.0–2.6 тыс. (перехват), пакеты состояния и прямой
NVN (UI Iggy, пост) ≈ 8–10 тыс.

Оценка выигрыша `=1` (трамплин ≈ 12–25 нс на X4, одна смена стека вместо 2–4 трамплинов на draw): **≈ 0.02–0.06 мс на кадр на Mi 14**
(0.4–1.2 % от 4.9 мс потока записи), ×3 на слабых ядрах — 0.06–0.2 мс. Это на порядок ниже «−0.5…1.5 мс» аудита: та оценка считала
все 14.6 тыс. вызовов вместе с телами. Точные числа даёт `=2` за один прогон (калибровка на потоке записи). Поэтому шаг сделан так:
**счёт и сверка (`=2`) — главное; `=1` реализован для того, что режется чисто, выключен, и по модели цены, скорее всего, не окупится.**

## 2. Что сделано
### 2.1 Модель кода движка — `dm/gfx/nr/nr_nocall.h` (чистый C)
- `nrnc_flush_plan / nrnc_flush_run` — сброс текстур `0x924730`: три стадии (NVN 0 / 1 / 5) в порядке кода; привязки стадии, сброс её
  двух диапазонов, следующая стадия. План только читает; диапазон вне слотов 0..31 → «не берём» (машинный код пошёл бы по соседней памяти —
  пусть идёт сам).
- `nrnc_draw_pre / nrnc_draw_tail / nrnc_draw_expect` — функции draw: поиск записи индексного буфера (страница, поколение 22 бита),
  `SetRenderEnable` на командном буфере «как сейчас» (код перечитывает контекст), draw на командном буфере, прочитанном на входе, адрес
  индексов двумя формами (36: `размер × первый + база`; 37: `[r+0x17d0] × размер + база`), байт `r+0x185d = r+0x185c`.
- Все вызовы NVN модели идут через `nrnc_ops`; фронт подставляет **тела точек входа HLE** (те же функции, что достигает вызов движка
  через thunk), тесты — регистратор. Поэтому тень NB-09, тап NB, `wt_use_ids`, `dm_nr_tap_draw` (идентичность NR-09), запись — те же
  по построению: состояние NVN для запасных draw остаётся согласованным без отдельной логики.
- `NRNC_CODE_TABLE` — FNV-1a 64 слов трёх функций (всё после 4 слов пролога под хуком); слоты указателей NVN движка
  (`main+0x2bbeee8 / fab0 / fb20 / fb38 / fcd0`), таблица размеров индекса `main+0x1f5865c`.

### 2.2 Сторона NVN — `nvn_nr_nocall.inc / .h`, 6 строк в `hle_nvn.c`, 15 инструкций в `nvn_entry.S`
- Прямые входы `nvn_nc_bind / _ren / _draw` = вызовы `h_nvnDeviceGetTextureHandle`, `h_nvnCommandBufferBindTexture`,
  `h_nvnCommandBufferDrawElements(Instanced)`, `h_nvnCommandBufferSetRenderEnable`. `nvn_nc_ready` на каждом запуске проверяет, что слот
  каждой из пяти функций кончается именно этим телом (обёртки большого стека / замера / трассы сняты) и отдаёт адреса thunk.
- `nvn_on_bigstack(fn, arg)` — `fn(arg)` на том же 1 МиБ стеке хоста, на котором тела исполняются под обёрткой (тела не меняют стек:
  обратный вызов игры за памятью команд идёт оттуда же, как сейчас). Одна смена на draw вместо одной на вызов.
- `=2`: четыре строки `NCT(...)` (BindTexture, DrawElements, DrawElementsInstanced, SetRenderEnable) — захват аргументов потока; одна
  строка в `nvn_bigstack_top` — счётчик вызовов NVN потока (каждый реализованный вызов проходит её один раз); калибровка
  `nvn_nc_calibrate` (вызов через thunk + обёртку с пустым телом, прямой вызов, одна смена стека — по 4096 раз на потоке записи).

### 2.3 Фронт — `dm/host/hle_dos2_nr_nocall.inc` (+ 3 строки в `hle_dos2_nr.c`, 2 в `hle_dos2_nr_key.inc`, обработчик в `hle_dos2_native.c`)
- Хук сброса текстур: при взведённом `DM_NR_NOCALL` ставится `nr_h_tf_nc` (= `nk_draw` NR-02/09, затем нативный / сверяемый сброс, иначе
  оригинал с теми же аргументами); без переключателя — прежняя `nr_h_tf`.
- Общий хук draw (`dn_draw_common`) получил необязательный «нативный обработчик» (`dn_install_draw_native`): `take()` = 1 — draw исполнен,
  функция движка не зовётся; 0 — зовётся как раньше, затем `after()`. Без обработчика — одна загрузка и переход, вызов прежний.
- `=1`, draw 36 / 37: вход (`nrnc_draw_pre`; отказ → функция движка, ничего не тронуто) → `0x926f90(r)`, `0x925740(r)` движка, как есть →
  `nk_draw` → **одна смена стека**: сброс текстур, `SetRenderEnable`, draw, байт флага. Сброс с остальных 23 мест вызова (полноэкранные
  draw, прямые пути, код 33, compute) — нативно через хук (смена стека только если есть привязки).

## 3. Переключатели (умолчание 0; игрокам не выдаются; `jni_android.c` не тронут)
| | значение |
|---|---|
| `DM_NR_NOCALL` | **0** — ничего: хук сброса — прежняя функция, у хука draw нет обработчика (одна загрузка с непринятым переходом на draw, если хук draw стоит), `nvn_bigstack_top` — одна загрузка с непринятым переходом на вызов NVN, 4 строки `NCT` — то же в четырёх точках входа. **2** — счёт + сверка, исполняется код движка (см. §2.4 и строки ниже). **1** — моделируемая часть исполняется нативно. **3 не существует**: нативный путь зовёт те же тела с теми же аргументами, пропущен только трамплин и счётчик вызовов thunk — отравить нечего |
| `DM_NR_NOCALL_PARTS` | для `=1`: бит 0 — сброс текстур, бит 1 — хвост draw; умолчание 3 (A/B частей) |

Нужно: `DM_NR=1|2` и хук сброса (`DM_NR_DRAW=1|2` или `DM_NR_KEY=1|2`); `DM_NB` не обязателен (тела одни и те же в любом режиме NB).
С `DM_NVN_BIGSTACK=0` счётчик вызовов `=2` мёртв (строки дадут нули, сверка числа вызовов пропускается).

Строки (поток отчёта NR, раз в 10 с):
- старт: `[nr] DM_NR_NOCALL=… (NR-23): …; the three functions hash to the analysed code; …`; первый сброс: `[nr] nocall: the engine's
  GetTextureHandle / … pointers are the thunks of the bodies the direct entries call`;
- `=2`: `[nr] nocall (DM_NR_NOCALL=2, …): NVN calls of the threads that run engine packets N a frame: engine draws 36 / 37 … (uniform blocks
  before the flush …, the texture flush …, after it …); other packets … (op 9 …, op 21 …); outside the packets …` — **карта вызовов NVN по
  кодам пакетов движка** (данные для нативных обработчиков состояния);
  `[nr] nocall, what =1 would not call through the thunks: … = S NVN calls a frame (P% of the N above) for W stack switches; …; binds whose
  slot already held that handle this frame Z a frame (… %)`;
  `[nr] nocall cost model (calibrated on the recording thread): an NVN call through thunk + big stack A ns, its body called directly B ns, one
  stack switch C ns: =1 would save about X ms a frame (…); all N calls a frame cost Y ms in the thunk + wrapper alone`;
  `[nr] nocall check (DM_NR_NOCALL=2, totals): F texture flushes compared, bad …; D draws 36 / 37 compared, bad …`;
- `=1`: `[nr] nocall (DM_NR_NOCALL=1, parts …): native texture flushes … with … binds, native draws … : S NVN calls a frame not made through
  the thunks, W stack switches; left to the engine a frame: …` + та же строка модели цены.
`tools/dos2_cpuprof.py` читает три строки `=2` и печатает ответ: «`NR-23 (DM_NR_NOCALL=2): the cut … covers S of N NVN calls … -> GO for =1
(>= 0.15 ms) / NO-GO`» и «`model check: … bad`».

## 6. Ожидаемый выигрыш (оценка, не замер)
| Класс | `=1` (сброс текстур + draw нативно) | Замечание |
|---|---|---|
| Mi 14 / Adreno 750 | поток записи −0.02…0.06 мс из 4.9 (упор в GPU: fps 0) | ниже порога шума A/B; решает строка модели цены |
| S7 / A7xx, MTK A55 / A510 | −0.06…0.2 мс на потоке записи | там же трамплин дороже (in-order ядра): строка калибровки покажет |
| GPU, тайлеры (Mali, PowerVR) | 0: поток команд байт в байт тот же | — |

Что даст больше (не сделано, вне определения шага; числа для решения печатает `=2`):
1. **Обёртка большого стека на всех 14.6 тыс. вызовов** — строка «all N calls a frame cost Y ms in the thunk + wrapper alone». Если Y ≥ 0.3 мс:
   быстрый вход (проверка «уже на большом стеке» до сохранения 16 регистров) или исполнение `ExecuteCommandList` целиком на большом стеке —
   без семантического риска, на все вызовы сразу (в духе NR-24).
2. **Повторные привязки** — «binds whose slot already held that handle»: сброс движка перевязывает весь грязный диапазон. Если их много,
   фильтр в `bind_handles` (тот же handle на том же буфере в той же записи; сброс на смене пула / регистрации / записи) убирает тело,
   24 байта записи, 80 нс применения в бэкенде и подъём `tex_gen` (попадание мемо дескрипторов). Нужна своя сверка.
3. **Пакеты состояния** (8–10 тыс. вызовов) — нативные обработчики кодов по карте «other packets (op …)»; это основная линия NR.

## 7. Риски
- `=1` на телефоне не исполнялся. Модель доказана эмулятором, но путь «тело NVN на большом стеке из хука» в живом процессе — впервые.
  Сначала `=2`: при `bad ≠ 0` или красной строке про указатели `=1` не включать.
- Счётчик вызовов thunk (`[nvn] 帧 N：… 次调用`, `DM_NVN_COUNT`) и окно `DM_NVN_PROF=2` при `=1` не видят нативных вызовов — число вызовов на
  кадр падает на S (это и есть признак работы), сравнивать прогоны по нему нельзя. `DM_NVN_TRACE` их тоже не пишет.
- `DM_NB_FOREIGN=1` (NB-15, только счёт): класс «первый вызывающий в main» для нативных записей определяется обходом кадров стека через
  кадры хоста — может уйти в «other».
- План сброса читается до привязок (машинный код читает слот перед каждой своей привязкой). Разница возможна, только если обратный вызов
  игры за памятью команд меняет кэш текстур рендерера; `=2` ловит это как «a bind» / «bind count».
- Другая сборка игры: хэши не совпадут — переключатель выключится сам (красная строка), как остальные хуки NR.

## 8. Чего нет
- Вызовы UBO (`BindUniformBuffer` из `0x925740`) и вызовы пакетов состояния не трогаются (§1).
- Повторные привязки только считаются. Быстрый вход обёртки большого стека не сделан (п. 1 в §6).
- `xbg_vendor_policy.h` не тронут: умолчания по семейству GPU нет — выигрыш не зависит от GPU, а по модели он мал.

## 9. Прогоны на телефоне
**R-NR23a — счёт и сверка (один прогон, он же отвечает на вопросы NR-16):** `dm/env`:
```
DM_NR=1
DM_NR_KEY=1
DM_NR_NOCALL=2
DM_NVN_PROF=2
DM_NR_CPU=1
```
(`DM_NR_KEY=1` даёт хук сброса и ничего не рисует иначе; вместо него годится `DM_NR_DRAW=2`.) Сцена: палуба 60 с, затем тяжёлая (бой /
город) 60 с — отдельно по сценам. Ждём: `[nr] DM_NR_NOCALL=2 (NR-23): count + compare …`, `[nr] nocall: the engine's … pointers are the
thunks …`, затем каждые 10 с четыре строки `[nr] nocall …`. Читать: `python tools/dos2_cpuprof.py <лог>` → строки `NR-23`. Решение:
`nocall check … bad 0` в обеих сценах обязательно; `=1` имеет смысл только при «would save about ≥ 0.15 ms»; «all N calls … cost Y ms» —
делать ли быстрый вход обёртки; «already held that handle» — делать ли фильтр повторных привязок; «other packets (op …)» — с каких кодов
начинать нативные состояния.

**R-NR23b — `=1` (только после R-NR23a с `bad 0`), ABBA по 60 с в одной сцене:** A = `DM_NR=1 DM_NR_KEY=1 DM_NR_CPU=1`, B = то же +
`DM_NR_NOCALL=1`. Ждём в B: `[nr] nocall (DM_NR_NOCALL=1, parts 3, …): native texture flushes … native draws ≈ 983 a frame …`, картинка та
же, красных строк нет. Сравнивать: `[cpuprof] threads` — мс на кадр потока `rec`; `NVN PERF` — `draws`, `ops`, fps те же. Если разницы
нет в пределах шума — оставить выключенным и закрыть шаг по строке модели цены.
