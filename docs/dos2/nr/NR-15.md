# NR-15 — умолчания NB: снять с DOS2 то, что ничего не делает (17.11.2026, ветка `dos2-nr15`)

Шаг из аудита `docs/dos2/nr/AUDIT-REMAINING.md` (ветка `dos2-nraudit`), §1 NR-15 и §2. Сегмент S5 (фронт NB). Телефон не трогался.

## 1. Что сделано
`dm/android/jni_android.c`, блок DOS2 `k_nb_on` (NB-22, 852c6ec, «врубай всё»): **убраны из умолчаний** четыре переключателя —
`DM_NB_RELOC` (было 1), `DM_NB_ORDER` (было 3), `DM_NB_TRANSIENT` (было 1), `DM_GFX_HIT_FAST` (было 1). Их код не тронут; каждый по-прежнему
читается из окружения при установке (`hle_dos2_nb.c`) и в бэкенде (`read_mode` / `init`), так что `dm/env` с `=1` (`ORDER` `=1/2/3`)
включает их как раньше (файл `dm/env` грузится до умолчаний, `setenv(..., 0)` его не перебивает). Остальные шаги NB (DM_NB, OPS, RP,
OPBARRIER, PIPE, DESC, UBO, UIAREA, OWN, POST, POST_AA, MT, MX, PRESENT_THREAD, PARTICLES_FULL) остаются включёнными. Причина с числами —
в комментарии у таблицы.

Значения после шага (DOS2, без `dm/env`): `DM_NB_RELOC` не задан = 0, `DM_NB_ORDER` = 0, `DM_NB_TRANSIENT` = 0, `DM_GFX_HIT_FAST` = 0.
Режимы `=2` (сверка) и прочие — как в NB-плане, без изменений. Других мест, где эти четыре ставятся по умолчанию, в дереве нет
(`rg` по всему `dm/`: только `jni_android.c`; `xbg_vendor_policy.h` их не знает).

## 3. Зависимости (что могло бы на них опираться)
- **`DM_NB_OWN` (NB-21) без RELOC / ORDER работает.** `nvn_nb_own.inc`: `nbw_frame` / `nbw_pass` зовутся в `nbt_sync` под своим `g_nbw_on`
  (не под `g_nbk_on` / `g_nbo_on`); адрес ключа ставит только `nbw_key` из `nbk_pass` — без RELOC он 0; `nvn_nb_own_build`:
  `nord = g_nbo_on ? g_nbo.last : 0` → без ORDER порядок тождественный. `nb_own.h nbw_build`: ключ 0 только снимает `NBW_F_KEYS`, без хвоста —
  `order[k] = k`; `nbw_valid` ключ 0 принимает (`g->key & 7`), порядок проверяет как перестановку. Бэкенд (`xbg_nb_own.inc`) ключи только
  считает (`s.keys`), сверка `nbw_chk_*` их не читает. Передача задания (`nbw_hand`, XJ_OWN — то, что даёт OWN) от ключей и хвоста не
  зависит. Новый тест: `nb_own_test.c test_nr15_no_keys_no_order` — часть DOS2-вида без ключей и без хвоста: задание валидно, флаги
  `FINAL | PLANNED` (без KEYS / ORDER / MERGED), порядок тождественный, исполнение как записано = 0 расхождений, пропуск / чужой адрес PASS
  ловятся. Случайные части с ключами 0 / 1 / 2 и без хвоста были в тесте и раньше (3000 итераций).
  В строках `[nb] own` после шага ожидается `with every key 0` и `order from the order tail 0` при прежних `handed to their submit N`,
  `executed = the job N, differ 0` — это норма, а не поломка.
- **`DM_NB_MT=3` / `DM_NB_MX=1` (NB-20b)** — пакеты vkCmd* и копия контекста; ни ключей, ни хвоста, ни `nbw_stop` не используют
  (`xbg_nb_mt.inc`, `xbg_nb_mx.inc`; профиль `DM_NB_MX_PROF` берёт сегменты из задания OWN, не из ключей).
- **`DM_NB_POST` / `DM_NB_POST_AA` (маршрут A)** работают по месту в потоке и сами выключают планировщик слияний; от ключей / хвоста не зависят.
- **`DM_NB_RP=1`**: в бэкенде `nbord::in_run` (единицы с членами) задействуется только при ORDER; при «0 continue the pass before them»
  единиц нет — план проходов тот же.
- **NR-ветки** (nr02…nr11, nr14, nr19, nrend): ни одна не ссылается на `DM_NB_RELOC` / `DM_NB_ORDER` / `DM_NB_TRANSIENT` /
  `DM_GFX_HIT_FAST`, `nbkey::` / `nbord::` / `nbtr::` / `hitfast::` (кроме перенесённого контекста строки NR-11 и одной строки NR-10 в
  `hitfast::fill`, которая лишь держит `last_write` как у `prepare_read`); таблицу `k_nb_on` никто не правит — слияние без конфликтов.
- Кому они понадобятся потом: NB-18b вариант b (сегмент UI в конец кадра) и `aba`-слияния NB-17b требуют RELOC + ORDER вместе, NB-19 —
  subpass'ы G-buffer → lighting, HIT_FAST — путь попадания мемо без вооружённого хука (NR-08 этот путь заменяет). Тогда их включает тот шаг,
  своим `dm/env` / политикой, с замером.

Ни один из четырёх не нужен и не полезен на DOS2 сейчас — оставленных нет.

## 6. Риски
- Низкий. Возможная разница — только если в тяжёлых сценах (бой, город) какой-то из четырёх **начал бы** работать: ORDER не может (POST
  выключает планировщик), RELOC сам ничего не делает без ORDER-перестановок, HIT_FAST блокирован `DM_NB_RP=1`, TRANSIENT упирается в
  чтения вложений следующим проходом. Логи — только палуба / стартовая зона, это оговорка, но все четыре механизма заблокированы
  структурно, а не цифрами сцены.
- Теряется диагностика `[nb] key` / `[nb] order` / `[nb] transient` / `[gfx] hit fast` в обычных прогонах; для сверок их включает `dm/env`.

## 7. Прогон на телефоне, который подтвердит (вместе с NR-14, аудит §5 п. 2)
Бэкап `files/save`, проверить keyguard (`dumpsys window`), палуба, без лимита кадров (`DM_DOS2_FPS=0`), 60 с на прогон, ABBA:
- **A (новое умолчание):** `DM_DBG=1`, `DM_DOS2_TOUCHUI=1`, `DM_DOS2_FPS=0`.
- **B (старое):** то же + `DM_NB_RELOC=1`, `DM_NB_ORDER=3`, `DM_NB_TRANSIENT=1`, `DM_GFX_HIT_FAST=1`.

Смотреть:
- `[dm] [nvn] 主线程 至帧 …：每帧 CPU X ms` — A ниже B на ≈ 0.7–0.9 мс (главное число шага).
- Бэкенд: `NVN PERF … submit_cpu_ms` минус `NVN PERF poolreset … wait_ms` — A ниже B на ≈ 0.6–0.9 мс (при упоре в GPU часть уйдёт в ожидание).
- `[nb] own (DM_NB_OWN=1): … with every key 0 … order from the order tail 0 …, handed to their submit N` и `[nb] own (backend …): … not valid 0
  … executed = the job N, differ 0` в A; в B — как в h1def.
- В A нет строк `[nb] key`, `[nb] order`, `[nb] transient`, `[gfx] hit fast: …` (одна строка `[gfx] DM_GFX_HIT_FAST=0 … - off` при первом
  попадании мемо — норма).
- Без изменений между A и B: `[nb] post … elided`, `[nb] rp … plan applied`, `NVN PERF … gpu_ms` / `passes=` / `draws=`, скриншоты одной точки.
- Затем force-stop игры.
