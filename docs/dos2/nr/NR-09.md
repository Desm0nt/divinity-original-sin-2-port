## 2. Что сделано
### 2.1 Запись: `OP_X_NR_DRAW` = `OP_X_NB_DRAW` + `NBD_F_NR` + хвост 16 Б
- **Отдельного кода операции нет — намеренно.** Запись draw движка уже есть (NB-09 / 10: привязки + аргументы draw). NR-09 добавляет к ней
  **идентичность движка**: флаг `NBD_F_NR` в заголовке и `nrd_tail` после привязок: `key` (id ключа NR-02: шейдер, blend, depth-stencil,
  raster, формат вершин, слово маски, набор форматов RT, примитив, alpha test), `texset` (id набора текстур NR-02), `why` (маска `NR_NE_*`
  ключа), `site` (место вызова движка), версия. Все читатели `OP_X_NB_DRAW` (`nbd_view / nbd_unpack`, `wt_scan`, зеркало NB-14, счётчики
  NB-15, порядок NB-17, проверка NB-10) берут запись как раньше — хвост для них просто длиннее полезной нагрузки (проверено тестом).
  Свой код операции потребовал бы правки каждого из них без выигрыша. Запись 151 → 167 Б.
- Откуда id: хук NR-02 на сброс текстур `0x924730` (его зовёт каждый путь draw движка прямо перед draw NVN) кладёт идентичность в TLS
  (`idp`); первый оператор входа draw NVN (`dm_nr_tap_draw`) переносит её на **этот** draw (`idn`); `nbd_draw` забирает один раз
  (`dm_nr_draw_ident`). Draw NVN без сброса перед ним идентичности не получит — запись остаётся обычной `OP_X_NB_DRAW`.
- `DM_NR_KEY` для этого не нужен: без него хук ставится в режиме «только идентичность» (`g_nr_key == 3`): без счёта и без мьютекса на
  повторяющемся ключе (64 последних ключа потока, прямое отображение по хэшу; чистый диапазон текстур — без блокировки). С `DM_NR_KEY=1/2`
  id отдаёт сам счёт.

### 2.2 Исполнитель: `nrdraw::lane()` (`xbg_nr_draw.inc`) — одна строка в `draw()` после `create_pass`
`draw()` исполняет вход как раньше (правила пропуска, пре-пасс, диагностика), дескрипторы (NR-08) и `create_pass`; затем **одна строка**
спрашивает `nrdraw::lane()`. Если draw продолжает открытый проход, остаток делается коротким путём, `draw()` возвращается:

| Шаг | Как |
|---|---|
| Пайплайн | **прямая таблица NR-07** `nrp_tab`: строка = id ключа из записи, вариант (6 слов) = VS, FS, определения раскладки дескрипторов и прохода, примитив / samples / цели / restart, **шесть точных id групп состояния NB-13b** (по 10 бит). Попадание даёт `VkPipeline` + список вершинных привязок. Ключ не строится и не хэшируется; группы перечитываются только после записи состояния |
| Вершины / индексы | те же диапазоны через `snapshot()` (NR-06 / zero-copy / старые кэши), затем **свёртка смещений** (`nr_draw.h`): индексный буфер привязывается со смещением `off mod размер индекса`, draw получает `firstIndex = off / размер`; повершинные потоки сдвигаются на k вершин назад, `vertexOffset += k`. Байты выборки те же (тест), а привязки двух мешей одного `VkBuffer` становятся одинаковыми — их отсекает кэш привязок |
| Команды | пайплайн (если сменился), набор + динамические смещения (если сменились), **один** `vkCmdBindVertexBuffers` на серию соседних сменившихся потоков, `vkCmdBindIndexBuffer` (если сменился), draw. Viewport / scissor считаются только при смене состояния |
| Учёт | то же, что делает старый хвост: флаги открытого прохода, `uiarea` (счёт draw; полный вызов только при смене viewport / scissor), `pass_prof`, `condr`, `nbchk`, `nbui`, счётчики PERF, `drecy::done` |

**Запасной путь — по draw и без следов:** `lane()` возвращает `false` до первой команды и первого счётчика (проверяет структурный тест), и
`draw()` продолжает как раньше; его хвост в конце одной строкой (`nrdraw::done`) учит таблицу своим пайплайном. Причины считаются
(`NRW_*`): нет id, диагностика (capture, статистика, crumbs, граф проходов, `gfx-ab-target = nrdraw`), нет id групп (`DM_NB_PIPE=0`,
`DM_GFX_DRAW_FAST≠1`), лишние стадии (tess / GS), GPU-indirect / quads / сдвиг UI / переопределение пре-пасса, промах таблицы, **draw не
продолжает открытый проход** (первый draw прохода, ленивый clear), проход Iggy у `DM_NB_UIAREA`, точный счёт occlusion, writeback хранилища,
непривязанный поток / u8-индексы, viewport, который старый путь пропускает / проверяет.

### 2.3 Почему таблица точна (главное решение шага)
Ключ движка **только выбирает строку**. Вариант содержит всё, от чего зависит пайплайн старого пути: указатели шейдеров, определения
раскладки и прохода, слова draw и id шести групп NB-13b — это ровно байты `PipeMemoKey` (группы интернируются `memcmp`, подтверждены на
телефоне: 100 % попаданий, `stale 0`). Состояние, которое движок ставит мимо своего кэша (stencil ref, bias, blend color — в этом бэкенде
они запечены в пайплайн), даёт **второй вариант в строке, а не чужой пайплайн**. Мутация в тесте (вариант игнорируется) — 151 009 неверных
пайплайнов из 200 000; с вариантом — 0 из 2 000 000. Таблица очищается, когда двигается `nbpipe::epoch` (перезапуск id групп, удаление
пайплайнов / раскладок / проходов — те же места, где чистится мемо NB-13b).

### 2.4 Размещение копий NR-06 под свёртку (`nrbuf::place`, только при `DM_NR_DRAW` со свёрткой)
Модель (`nr_draw_test`) показала: сама по себе свёртка даёт мало — меши лежат в разных `VkBuffer`, а смещения не кратны stride.
Поэтому при включённом NR-09 статические копии NR-06 (устройства **без zero-copy**: Mali, PowerVR, Xclipse, MTK) размещаются иначе:
индексные копии — в своей последовательности чанков (все статические индексы в 1–2 `VkBuffer`), вершинная копия — со смещения, кратного
stride первого draw (`nrbuf::stride_hint`; тогда каждый меш чанка сворачивается к смещению 0 при любом stride). При `DM_NR_DRAW=0`
размещение прежнее (байт в байт NR-06). Размер чанка — `DM_NR_BUF_CHUNK_MB` (16).

| Раскладка мешей (модель, 1 159 draw, 400 мешей) | `vkCmd*` на draw: старый хвост → обе свёртки | VB | IB |
|---|---|---|---|
| zero-copy (Adreno), 21 чанк | 3.93 → 3.73 | 0.85 → 0.84 | 1.00 → 0.81 |
| копии NR-06 как были, 8 чанков | 3.92 → 3.64 | 0.85 → 0.83 | 1.00 → 0.74 |
| копии размещены: 8 вершинных чанков + 1 индексный | 3.92 → **2.81** | 0.85 → 0.74 | 1.00 → 0.00 |
| то же, 3 вершинных чанка | 3.92 → **2.64** | 0.85 → 0.57 | 1.00 → 0.00 |
| то же, 1 вершинный чанк | 3.92 → **2.07** | 0.85 → 0.00 | 1.00 → 0.00 |

Порядок мешей в модели случайный (худший случай: у движка draw идут по материалам / областям, соседние меши чаще в одном чанке).
«≤ 4 `vkCmd*` на draw» выполняется на типичном draw везде (пайплайн + набор + draw + одна из привязок); среднее 2.1–2.8 — там, где
вызов дорог. Сколько статической геометрии у DOS2 в памяти (число чанков), покажет строка NR-06 `copies live in … MB`.

### 2.5 Чего свёртка не трогает
- вершинный шейдер, объявляющий `gl_VertexIndex / gl_VertexID / gl_BaseVertex` (`Shader::vindex`, скан SPIR-V на загрузке) — потоки не
  сворачиваются (значение встроенной переменной изменилось бы);
- draw с primitive restart — вершинная свёртка выключена (KB `mobile-gpu-field-notes`: старые Mali, Midgard < r22 / Bifrost < r10,
  ломают restart при 16-битных индексах и `vertexOffset ≠ 0`);
- поинстансные потоки и константные входы (stride 0) — смещение прежнее; `firstInstance` не меняется.

| MTK / Mali, Xclipse (без zero-copy, копии NR-06 размещены) | CPU ×3: −4.5…5.5 мкс на draw; команд 3.9 → 2.1–2.8 при 1.2–1.8 мкс за вызов: ещё −1.3…3.3 мкс на draw | **−5…8 мс на кадр** [м] (из них драйвер −1.2…3.0); вместе с NR-06 / NR-08 — «16–20 → 6–8 мс» плана; в упоре в CPU fps ×1.3–1.6 от одного NR-09 |
| PowerVR | как Mali (число команд то же); обновление набора на draw остаётся (NR-08, нет динамических UBO) | −5…8 мс [м] |
| GPU, тайлеры | те же проходы, барьеры, пайплайны; команд меньше | 0 |

Цена на потоке игры (хук сброса): режим «только идентичность» ≈ 0.1–0.2 мкс на draw (чтение ~120 Б кэша состояния, сравнение ключа,
хэш набора только при грязном диапазоне) — ≈ 0.1–0.2 мс на кадр на Mi 14, ×3 на слабых; со счётом `DM_NR_KEY=1` — 0.2–0.4 мкс.
Это новая работа потока записи игры (9.2 мс BeginFrame → EndFrame): на слабом CPU, где узким окажется он, а не транслятор, выигрыш
меньше на эту величину. Запись длиннее на 16 Б (≈ 16 КБ на кадр).

## 7. Риски (честно)
1. **Не исполнено на устройстве.** NR-01 / 02 (хуки, идентичность) — тоже: если хук сброса не встаёт или id не доходит, записи остаются
   обычными (`plain OP_X_NB_DRAW` в сводке), выигрыша нет, картинка прежняя.
2. **Короткий хвост повторяет учёт старого вручную** (флаги прохода, `uiarea`, `pass_prof`, `condr`, `nbchk`, `nbui`, счётчики). Что
   добавят в хвост `draw()` позже, нужно добавить и в `lane()` — или завести причину отказа. Сверка `=2` сравнивает значения команд, но не
   этот учёт.
3. **`uiarea` для проходов не-Iggy** вызывается полностью только при смене viewport / scissor; иначе — счёт draw и флаг DS. Прямоугольник
   объединения таких проходов влияет только на строку статистики; если в `uiarea` появится решение по ним — вернуть полный вызов.
4. **Таблица** держится на точности id групп NB-13b и на `nbpipe::epoch` во всех местах, где уходят пайплайны / раскладки / проходы.
   Пропущенное место = пайплайн уничтоженного объекта (падение / `DEVICE_LOST`). Места — те же, что у мемо NB-13b (включено по умолчанию,
   на телефоне подтверждено).
5. **Свёртка вершин** меняет `vertexOffset`. Закрыто: шейдеры с `gl_VertexIndex / gl_BaseVertex`, draw с restart. Не закрыто: драйвер с
   ошибкой при большом `vertexOffset` без restart (в KB таких записей нет). `DM_NR_DRAW_FOLD=1` оставляет только индексы.
6. **Размещение копий NR-06** (`nrbuf::place`) — только на устройствах без zero-copy, ни одного такого нет для проверки; симуляция:
   `DM_GFX_ZEROCOPY=0` на Mi 14. Копия теряет до stride байт на выравнивание; индексные чанки считаются в тот же бюджет `DM_NR_BUF_MB`.
7. **Доля обслуженных** зависит от порядка движка: draw после смены RT / первого draw прохода идут старым путём. Если проходов с 1–2
   draw много (пост, тени по каскадам), доля ниже 78 %.
8. `snapshot()` внутри `lane()` может закончить проход (ожидающий результат GPU) — проверка открытого прохода повторяется после снапшотов;
   тогда draw уходит старым путём (снапшоты идемпотентны).
9. Режим 2 дороже: каждый кандидат считается дважды (≈ +1 мкс на draw); нулевой поток (константный вход) выделяется дважды.
10. Общие файлы: `xbg_game.cpp` (6 точек; `stride_hint` и `Shader::vindex` — общий код ядра `dm/`, без `DM_NR_DRAW` ничего не решают),
    `xbg_nb.inc`, `xbg_nb_pipe.inc`, `xbg_nr_buf.inc`, `nvn_nb_draw.{h,inc}`, `hle_dos2_nr*.{c,inc}`, тесты.

## 8. Не сделано
- **NVN-записи состояния остаются**: запасной путь по draw требует актуального `State`, поэтому «уходят `mark` и перечитывание групп»
  из NR-07 §3 не случилось — группы перечитываются (0.75 на draw), экономится ключ и хэш. Убрать записи состояния для взятых ключей —
  NR-13 (нужна доля строк с > 1 вариантом, т. е. ключей, которых движок не описывает полностью; сейчас видна как `hits` против
  `first of its row` в сводке).
- **id набора текстур как передний ключ NR-08**: едет в записи и сверяется в режиме 2 (`same / another / first sight`), но в режиме 1 не
  используется: id NR-02 не различает перерегистрацию id пула, и неверное попадание = чужие текстуры. Включать после прогона, если
  `another entry` = 0 вне загрузок.
- Компактная запись 40–64 Б из плана: привязки едут как в NB (24 Б на привязку); сжатие (смещения в кольце вместо адресов) дало бы
  ≈ −150 КБ на кадр памяти записи при переделке всех читателей `OP_X_NB_DRAW` — не стоит.
- Первый draw прохода, UI Iggy (NR-12), коды 38–42, GPU-indirect — старый путь. Умолчание по детекту — после прогонов.
- Вход `draw()` (0.2 мкс) и `create_pass` остались общими: отдельный вход дал бы ≤ 0.1 мкс на draw ценой второй копии правил пропуска.

## 9. Прогоны телефона, которые это подтвердят (главный агент, по разрешению хозяина)
Бэкап `files/save`; keyguard снят; без лимита кадров; `DM_NB_MT=0` в `dm/env` (иначе `draw_sections` не меряются). Сцены: палуба 60 с +
Форт Радость / бой / город (палуба одна не представительна), инвентарь и карта. APK: `wt-nr09/work/DOS2-port-debug.apk` (или сборка
слитой ветки).
1. **R-NR09a, сверка (Adreno, zero-copy):** `DM_NR=1 DM_NR_BUF=1 DM_NR_DESC=1 DM_NR_DRAW=2`. Ждём: `[nr] DM_NR_DRAW=2 (NR-09: compare …)`,
   `[nr] DM_NR_DRAW without DM_NR_KEY: … hooked for the draw identity only`, `[nr] draw ident …: OP_X_NR_DRAW records ≈ 980 a frame
   (… without an identity: 0)`; в `[nr] draw:` — `would serve` ≥ 75 % записей, `old path:` в основном `not the open pass` (≈ число
   проходов) и `table miss` (падает к нулю за секунды); **`[nr] draw check: … bad 0`** по всем шести видам; `another entry` у набора
   текстур — сколько. Картинка — как без флагов.
2. **R-NR09b, сверка без zero-copy (класс Mali):** то же + `DM_GFX_ZEROCOPY=0` (`DM_GFX_SIM_GPU=…,ubdyn8` по желанию). Те же ожидания;
   `bad 0`; строка NR-06 `static: … copies live in … MB` — число чанков; `folds: index / vertex` ≈ число обслуженных.
3. **R-NR09c, включено:** `… DM_NR_DRAW=1` (оба варианта zero-copy). `served` ≈ `would serve` из (1); `vkCmd* a served draw` ≤ 3.8
   (zero-copy) и **≤ 2.8** (`DM_GFX_ZEROCOPY=0`); `ns a served draw after create_pass` ≈ 1.1–1.4 тыс. против `pipe + vtx + bind + tail`
   базы (≈ 3 000 нс); `draw_sections_ms_per_frame`: `pipe / vtx / bind / tail` падают; `parts_ms_per_frame draw`, `submit_cpu_ms`;
   `[nb] mt … packets` на подачу меньше; скриншоты равны (палуба, бой, инвентарь, карта), `DM_VK_VALIDATION=1` в первом прогоне — без
   ошибок привязок.
4. **Цена (ABBA × 2, 60 с):** `DM_NR=1 DM_NR_BUF=1 DM_NR_DESC=1` против `+ DM_NR_DRAW=1`; то же с `DM_GFX_ZEROCOPY=0`; по желанию
   `DM_NR_DRAW_FOLD=0 / 1 / 3` (вклад свёртки) и `DM_NR_BUF_CHUNK_MB=64`. Смотреть `submit_cpu_ms`, запись потока игры в `[nb] frame …
   recording … ms` (цена хука), температуру; fps на Mi 14 меняться не должен.
Умолчание (по детекту в `xbg_vendor_policy.h`) — только при `bad 0` во всех сверках и выигрыше; для MTK / Mali / PowerVR нужен лог
игрока / тестера тестовой сборки (`draw_sections`, `[nr] draw`).
