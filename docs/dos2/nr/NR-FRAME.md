# NR-FRAME: кадр DOS2 как он есть, и что в нём можно перестроить без потери картинки (19.11.2026, ночь, без телефона)

Ветка `dos2-nrender` (worktree `wt-nrender`, база `dos2-night1119` 7780b92). Телефона нет: всё ниже — логи, дампы IR, список конвейеров
владельца, код, хост-тесты, сборка APK. Модели помечены как модели.

## 0. Коротко

| Вопрос | Ответ |
|---|---|
| Что даёт перестройка проходов на Mi 14 (Turnip, `TU_DEBUG=sysmem`) | **Почти ничего, и это измеримо.** В sysmem операции загрузки / сохранения ничего не стоят, слияние подпроходами двигает те же байты (NR-ONCHIP §0), очистка цвета на весь экран стоит 6–12 мкс (замер `gp1`/`gp2`: 36 проходов-очисток RGBA8+D24S8 2400x1080 по 11.8 мкс, 374 D24S8 по 17 мкс). | Что даёт на тайлерах (Mali G57, PowerVR, сток-Adreno в GMEM) | После умолчаний шага 1 (план NB, свежие вложения, UIX DS / AREA) остались: **маска записи без учёта формата** — 9 проходов в кадр, 22 МБ загрузок (сделано: `DM_NR_COVER_FMASK`), подпроходы Sky → Light (NR-ONCHIP S2, 25 МБ, сделано ранее, умолчание 0), G-буфер + свет одним проходом (121–133 МБ, план, не сегодня), Light → Fog подпроходами (16.8–25.2 МБ; раунд 2: c0 читается светом входом — конфликт снят без G; Fade читает соседей 2x2 и в цепочку не входит, §8). |
| Форматы G-буфера / глубины | **Сжимать нечего без потерь:** все цели ≤ 4 Б/пкс и каналы читаются (таблица §3). |

## 1. Кадр (что откуда взято)

  (17.11, Mi 14, палуба; 58 исполняемых проходов из 115 узлов). 34 3D-части дампов ra1 / rb1 / rc1 дают то же (средние в §2).
- Время прохода: тепло `src/work/logs/nrB_still2-heat.tsv` (18.11, `DM_NR_HEAT=2`, стоя, 992 кадра по 53 прохода): медиана мкс по ключу FS и размеру.

  декодер `tools/dos2_pipe_seed.py`; только числа фиксированной функции).
- Байты: **тайлер** = загрузка (план LOAD) + сохранение (план STORE) каждого вложения по его настоящим Б/пкс, без AFBC / UBWC (с ними ×0.5–0.7);
  **sysmem** = запись каждого цветового вложения по площади (×2 при смешивании — читается приёмник) + тест / запись глубины + чтение каждой
  выборки целиком. Это модель, не замер. Размеры из таблицы образов дампа местами ложны (пул движка: адрес хранит последний размер,
  NR-ONCHIP §9) — инструмент берёт размер прохода из тепла, если тепло видело этот шейдер.

Команда: `python tools/dos2_frame_table.py src/work/logs/rc1-dumps/nb_ir_10_f7218_p0.txt --pipes src/work/logs/play-1118/vk-pipeline-list.bin --heat src/work/logs/nrB_still2-heat.tsv --md`

### 2.1 Почему маска (#1) — главная находка для тайлеров
Списки конвейеров владельца (play-1118): все пост-шейдеры движка, пишущие в R11G11B10F, имеют маску **0x7** (в формате нет альфы), в R8 / R16 / R16F —
**0x1**. Доказательство NR-10b требовало `маска == 0xF` и отказывало им всем: на телефоне `[nr] cover … refused: … output / blend / logic op /
write mask / 3D target 18.00` в кадр (nr9_d1, nr10_d5, nr13_d3). Новое правило: маска полная, если покрывает все каналы, которые формат
хранит (`nr_fr_mask_full`, `dm/gfx/nr/nr_frame.h`); формат = формат вложения в render pass (вид) и формат образа, больший из двух; неизвестно — 4.
Выигрывают 11 шейдеров (FadeBlending, DeferredFog, LinearizeDepth, CascadedPCF ×2, PPDownSampleLog2, PPDefault на R11G11B10F,
LuminanceAccum, bloom ×3), остаются отказами смешивающие (Sky, Light, CrossBilateralUpsample, Iggy). Из 22 МБ на тайлере уже могут
быть DONT_CARE через «свежие» (`DM_NR_RP_FRESH`): строка `[nr] cover` считает по плану, не вычитая свежие — честная прибавка = её МБ минус
пересечение; прогон `CV2` (§5) даёт обе строки.

### 2.2 Почему M в GMEM (#2) — единственное для Mi 14
Модель Turnip (`nrgm_bytes`, хост-тест): M в sysmem = очистки Sp, Df (8 Б/пкс) + Sky смешивает в 2 цели (16) + Light смешивает Df (8) =
**32 Б/пкс**, плюс текстурное чтение Sp светом (4); в GMEM = 1.1 × сохранения Sp + Df (8) + 0.1 × draw (2.4) = **11.2 Б/пкс**. На 2160x972:
76 → 24 МБ. Отдельные проходы при одном NR-GMEM: Sky в GMEM (выигрывает сам), Light в GMEM ≈ ничья (загрузка + сохранение Df против
смешивания в памяти). Значит прибавка M в GMEM к NR-GMEM — Light: загрузка Df 8.4 МБ + чтение Sp 8.4 МБ ≈ 16.8 МБ ≈ **−0.1…−0.35 мс** (верх —
если эти проходы упираются в полосу; Sky 644 и Light 778 мкс в тепле во многом АЛУ). Сейчас же `DM_NR_ONCHIP=1` + `DM_GFX_PASS_GMEM=1`
**хуже** одного NR-GMEM: M с двумя подпроходами получает запрет «other» и уходит в sysmem вместе со Sky. Слабые Adreno на Turnip (LPDDR4X
≈ 15–25 ГБ/с): те же 16.8 МБ ≈ −0.7…−1.1 мс.

### 2.3 Отвязка DS (#4): почему инструмент даёт 30–39 МБ, а на деле ≈ 0
Инструмент видит в дампе IR 1.8–2.3 прохода в кадр с одним draw UI-материала (`d1eb8c9b…`, `a28da3d5…`, `4d5bd4f8…`), у которых DS
подключён, а конвейер его не трогает. В проходах хоста (тепло) эти draw идут внутри проходов UI, которые начинаются с Iggy — там решает
NR-UIX DS (история по ключам), и по телефону остаётся «kept and unused 0.75» прохода в кадр (D_uix2) при 18.88 отвязанных. Размер
в дампе — 2160x972 (таблица образов), настоящий — 2400x1080. Остаток мал и уже под NR-UIX.

## 6. Риски / не сделано
- FMASK: если драйвер где-то хранит «несуществующий» канал (не по спецификации), DONT_CARE его испортит — магента CV3 это покажет;
  неизвестный формат и отсутствие данных о проходе = старое правило.
- GMEM_M: ничего не гонялось; Turnip может сам уйти в sysmem для прохода с входным вложением (тогда M просто останется sysmem — строка
  `pass-gmem` покажет). Картинка в любом случае та же.
- Не сделано: G (#5) и композит (#6) — большие; CLEAR → DONT_CARE (#3) — не окупается; DS вне UI (#4) — под NR-UIX.
- Идея для других мест: `TU_DEBUG=sysmem,perf` один раз — причины снятия UBWC / LRZ в logcat (на sysmem UBWC — самый крупный
  рычаг полосы, ни разу не проверен на DOS2).

## 8. Раунд 2: G-буфер → свет одним проходом и вопрос «Fog пишет c0» (дизайн, 19.11; кода нет)
**Факты (шейдеры `tools/dos2_post/*_mobile.frag`, быстрый путь при масштабе рендера 1):** Sky читает c1, c2, c3 и линейную глубину своей точкой
(c0 — нет); Light читает c0 (emissive), c1, c2, c3, глубину, Sp, маску теней своей точкой; Fog — Df и линейную глубину своей точкой, пишет c0
(тот же образ пула); **Fade читает c0 в квадрате 2x2** (свой тексель и соседей справа / снизу) и маску c2 — в цепочку входов не берётся.
Отсюда:
1. **«Fog пишет c0» решается без G:** в M появляется третье вложение c0 (загрузка LOAD — содержимое G-буфера), свет читает его **входом**
   (вариант `light` с OC = 0x48: emissive бит 3 + ambient бит 6), Fog — отдельный подпроход 2 с цветом [c0] и входом Df (вариант Fog с
   binding 16 = `subpassInput`). Зависимости: 0→1 как сейчас; 1→2 by-region: COLOR_ATTACHMENT_WRITE (Df) → INPUT_ATTACHMENT_READ и
   INPUT_ATTACHMENT_READ (c0) → COLOR_ATTACHMENT_WRITE (c0) — это WAR своей точки, by-region законен. Линейная глубина остаётся текстурой
   (её пишет отдельный проход раньше, внутри M её никто не пишет). c0 после M сохраняется (Fade читает его текстурой с соседями). Df после
   Fog **мёртв**, если Fade закрывает его целиком (маска 0x7 по формату — NR-FRAME #1): тогда store DONT_CARE по плану (следующее
   использование — «load + cover_dc» с доказательством; первая версия — STORE). Прибавка к S2: −16.8 МБ (store Df светом + чтение Df
   Fog'ом), −25.2 МБ с DONT_CARE Df. Mi 14: 0 (sysmem), с `DM_GFX_PASS_GMEM_M` в GMEM — да (нужно пустить 3 подпрохода в NR-GMEM).
   Работа ≈ 6–8 агент-ч: планер `nb_onchip.h` (цепочка Sky / Light / Fog подряд, между ними только пустые IR-проходы и сложенные очистки —
   так в дампах rc1: узлы 117 / 118 / 120), `xbg_nr_onchip.inc` (M на 3 вложения и 3 подпрохода, `before_end`, привязки входов 2 образов),
   2 варианта шейдеров + доказательство `spv_interp` (как §3 NR-ONCHIP), пак (`dos2_nr_sh_pack.py`), тесты. Не начат: без устройства с
   тайлами проверить нечем, а Mi 14 выигрыша не видит.
2. **G (G-буфер … свет, −121…−133 МБ):** конфликт c0 у G тоже снимается тем, что весь G-буфер читается входами (`light.g` 0xFF, `sky.g`
   0x0F — уже доказаны бит в бит). Fog может стать подпроходом G по п. 1; Fade остаётся отдельным проходом. Остальное — §5 NR-ONCHIP
   (каскады теней до G-буфера через `DM_NB_ORDER=3`, конвейеры G-буфера под подпроход 0 с прогревом обеих версий, LinearizeDepth входом с
   доказательством выборки). 10–15 агент-ч + телефон + тайлер-тестер. Порядок: сначала S2F (малый риск, доказывает механизм трёх
   подпроходов), потом G.

## 9. Раунд 3: пузыри GPU между проходами на Adreno 750 (sysmem) — **меньше 0.2 мс, рычага нет** (19.11; по исходнику и логам)
**Что стоит граница прохода на a7xx (Turnip 1c3a936, `tu_cmd_buffer.cc` `tu_flush_for_stage`, `tu6_sysmem_render_begin/end`, `tu_clear_blit.cc`):**
- Ожидание простоя (WFI + `WAIT_FOR_BR`) ставится, когда стадия-источник зависимости не раньше стадии-приёмника (`src_stage >= dst_stage`).
  У каждого нашего прохода внешние зависимости полные (`create_pass`: EXTERNAL→0 ALL_COMMANDS / MEMORY_WRITE → ALL_GRAPHICS, 0→EXTERNAL
  ALL_GRAPHICS → ALL_COMMANDS / MEMORY_READ|WRITE; тайловая политика сужает приёмник до фрагментных стадий) → **граница прохода уже = WFI +
  очистка / сброс CCU**. Явный полный барьер между проходами (`full_barrier`, op25 / op26 / op61) добавляет к этому то же самое — повтор.
- Даже узкие зависимости не убрали бы WFI там, где следующий проход читает результат предыдущего: цвет (стадия вывода, позже всех)
  → выборка во фрагментном / вершинном шейдере = `src >= dst` → WFI. Без WFI можно только между независимыми проходами; внутри одного
  прохода by-region зависимость на a7xx — лёгкий `SUBPASS_SLICE_FENCE` вместо WFI (довод в пользу M / S2F, но это единицы мкс).
- Очистка loadOp CLEAR в sysmem: 2D-блит + CCU clean / invalidate + WFI (`tu_clear_sysmem_attachment`) — 6–12 мкс по GPASS (§0).
  Метки времени NR-14 / тепла: `vkCmdWriteTimestamp` BOTTOM_OF_PIPE — сам ждёт конца предыдущей работы.

**Сколько это в кадре (замеры):**
- Сумма промежутков между проходами = `span_us − pass_us` кадров с метками на каждой границе (а метки сами сливают конвейер — это **верх**):
  тепло `nrB_still2` (18.11, 1561 кадр, 53 прохода) медиана **262 мкс**, p90 274; `play-1118` (295 кадров, ~82 прохода) медиана 82, p90 853
  (загрузки); `live-1118` 274 / 852; `gp1` / `gp2` (14.11) 193 / 230. Это всё, что не внутри проходов: барьеры, очистки и копии вне
  проходов, сброс запросов, разрыв на метке. ≈ 5 мкс на границу.
- **A/B барьеров на Adreno уже был:** `nr10_base` против `nr10_d5` (`DM_NR_RP=1 DM_NR_COVER=1`, 17.11, Mi 14, стоя, ~190 окон): полных
  барьеров op25 **63 → 16** за кадр, GPU медиана **9.09 → 9.12 мс**, fps 105.05 → 104.67 (шум). Минус 47 полных барьеров = 0 мс: границы
  проходов сливают конвейер сами, явный барьер после них ничего не добавляет. `ab6rp2` (план NB `=2`) — счёт, не A/B.
- Модель «что ещё можно снять»: независимых соседних пар в 3D-части кадра единицы (атлас теней после LinearizeDepth, первый UI-проход),
  ≈ 5 × 5 мкс = **≈ 0.025 мс**.

**Вывод:** пузыри между проходами на Mi 14 ≤ 0.26 мс в сумме (верх, с разрывами от самих меток), а снимаемая часть ≈ 0.03 мс — меньше
порога 0.2 мс. `DM_NR_RP=1` умолчанием на Adreno не делаю (его A/B = 0, а он меняет поток команд); слияние барьеров, узкие маски доступа и
CLEAR вместо `vkCmdClearAttachments` в начале прохода (последнее уже делает CLEAR_FOLD / lazy-twin) на sysmem не окупаются. Если хозяин
захочет подтверждение — одна пара ABBA стоя: `DM_NR_RP=1` против умолчания, решает `NVN PERF gpu_ms` (ожидание 0 ± 0.05 мс).
