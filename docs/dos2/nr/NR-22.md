# NR-22 `DM_NR_TEXSTREAM` — рабочий поток NR-05 сам создаёт `VkImage` + память и заполняет свой staging (S2a), 17.11.2026, ветка `dos2-nr22`

Шаг NR-22 из `docs/dos2/nr/AUDIT-REMAINING.md` (ветка `dos2-nraudit`, §1), приём ETR PERF-E11 TEXSTREAM (`docs/port-kb/performance.md`
раздел A; эталон — `doom-eternal-port/src-cmp16` `xbg_game.cpp namespace ts`) **без** его GPU-deswizzle. База — `dos2-nr05` (NR-05
`DM_NR_TEX`), в неё первым коммитом влита `dos2-nr18` (NR-18, `xbg_ac_read_staged`, кэшируемое чтение ASTC-кэша; слияние без конфликтов).
Собрано и проверено на ПК; **на телефоне не запускалось**. Умолчание `0`.

## Что было (NR-05 `=1`) и что осталось на потоке трансляции
NR-05 перенёс на рабочий поток deswizzle материальной текстуры в heap-blob. На первой заливке транслятор всё ещё:
1. `vkCreateImage` + `vkGetImageMemoryRequirements` + `vkAllocateMemory` (ядро выделяет и обнуляет страницы) + `vkBindImageMemory`;
2. копирует blob в свой stream-буфер (0.1 мс/МБ, память WC);
3. на GPU без BC (Mali / PowerVR / Xclipse) для записей ASTC-кэша — `pread` + sanitize + копия (после NR-18 ≈ 0.75 мс/МБ на Mi 14 по TL2).

Логи телефона (Mi 14 Ultra, 17.11, `src/work/logs`, строки `[长帧]`; остаток = `提交+出图` − `着色器库` − `上传贴图`; обычный кадр
трансляции ≈ 5–6 мс, скрипт разбора — в отчёте агента):

| Событие | rd1 | h1def | g1all | g0base | rc1 / ra1 |
|---|---|---|---|---|---|
| 192 первых заливки, 33.7 МБ (вход в уровень) | остаток **46.9 мс** (0.24 мс/образ) | 47.5 | — | — | 43.1 / 48.3 |
| 196 + 188 заливок, 82.2 МБ (вход в меню) | — | — | **46.5 мс** | 38.3 | — |
| 216–224 первых, 6.8–9.6 МБ (стрим, мелкие) | 30.3 | 28.3 | 28.8 | 15.6 | 28.6 / 28.0 |
| 1 + 206 **повторных** (без создания образов) | 19.1 / 20.2 | 16.6 / 17.0 | 16.9 / 16.1 | 11.0 / 11.2 | 20.5 / 16.2 |

Вывод: остаток растёт с **числом новых образов**, а не с мегабайтами (192 образа / 33.7 МБ ≈ 224 мелких / 9 МБ по цене), т.е. цена — на
образ. Но и кадры **без** создания (1 + 206 повторных) несут 11–20 мс остатка: это не `vkCreateImage`, а что-то ещё на тех же кадрах
(перепроверки мемо дескрипторов после `memo_check_gen`, `vkCreateImageView` при первой привязке, обычная работа кадра). Сколько из
40–48 мс — именно создание + память, логи не говорят: по ETR (`vkCreateImage` + память ≈ 50 мкс на образ на 750) и по разнице
«192 новых» − «206 повторных» это **≈ 10–25 мс на событие**, не все 40–50. NR-22 сам меряет это на телефоне (строка ниже,
`images made here N (X ms: vkCreateImage + memory + bind)`), так что один прогон с `DM_NR_TEX=1` даёт точную цифру.

## Что сделано
1. **Ядро `nr_tex` (чистый C): «приёмник» (`nrt_sink`).** `make(src, bytes, &dst)` — движок создаёт образ + память и отдаёт отображённый
   staging, рабочий поток deswizzle-ит прямо туда (heap-blob не нужен); `make_astc(src, crc, adler, &bytes)` — запись ASTC-кэша по ключу,
   который рабочий поток только что посчитал; `release(obj)` — объект, который транслятор не взял (устаревшая проба, `Finalize`,
   `WriteTexels`, отложенное удаление движка, истечение 30 с, отмена во время работы, запись во время чтения, вытеснение слота, старый
   `nr_tex_take`, `nr_tex_free`) — ровно один раз, под замком ядра (движок только ставит его в очередь). `nr_tex_take_ts` отдаёт объект
   (+ staging) или heap-blob; бюджет держится до `nr_tex_unhold`. Движок спрашивают **только** для формата, который транслятор уже хоть раз
   взял «как есть» (вердикт NR-05, бит `allow`), и **никогда** для текстуры, которую может держать ASTC-кэш, пока он включён (для неё —
   `make_astc`). Отказ движка → heap-blob NR-05 (счётчик `refused by the engine`).
2. **Движок `xbg_game.cpp namespace nrts`.**
   - `xbg_nrts_make` (рабочий поток): `VkImageCreateInfo` по правилам `get_image_slow` (`ci_of`: usage по свойствам формата — через тот же
     `DM_GFX_SIM_GPU`-макрос, `STORAGE` по флагу 0x4, вложения, `MUTABLE` если `!no_mutable_images`, `CUBE`, повторы запроса формата без
     `STORAGE` / вложений — без логов), BC — только `BC_NATIVE` (устройство семплирует BC, нет ASTC-оверлея), `vkCreateImage` + память
     `DEVICE_LOCAL` + bind, срез staging из своих чанков по 16 МБ (`HOST_VISIBLE | HOST_COHERENT`, `TRANSFER_SRC`, свои, не арены слотов;
     свободных держим ≤ 64 МБ).
   - `xbg_nrts_make_astc` (рабочий поток, GPU без BC): поиск записи по ключу в индексе `astccache::idx` под новым `idx_mu` (`merge()`
     пишет индекс под ним же; до `state=1` — `ts_ready=false`, отказ), ASTC-образ (`xbg_ac_format`) и чтение блоков в срез **через свой
     `thread_local` кэшируемый bounce-буфер** (`xbg_ac_read_staged` NR-18; обратного чтения WC нет). Ошибка чтения → отказ (транслятор
     прочтёт сам и залогирует).
   - `xbg_nrts_release` (любой поток, под замком ядра) — только в очередь; `xbg_nrts_idle` (рабочий поток между работами, без замка
     ядра) — `vkDestroyImage` / `vkFreeMemory` отпущенных. На трансляторе Vulkan-объекты не уничтожаются (кроме возврата чанка).
   - Предел: образы + staging невзятых объектов ≤ `DM_NR_TEXSTREAM_MB` (по умолчанию 2 × бюджет blob NR-05: 192 МБ на 6 ГБ, 256 МБ на
     8+ ГБ) и ≤ 1024 объектов (`vkAllocateMemory` count); сверх — heap-blob (NR-05).
   - Открывается с первого present (`nrts::frame`): к этому моменту формат-политика, `native_bc`, ASTC-оверлей известны.
3. **Транслятор (`get_image_slow`).** При создании образа (`upload=true`, `Image::nr==1`): `on_create` NR-05 спрашивается **до**
   `vkCreateImage`, затем `nrts::claim` берёт объект; если его `VkImageCreateInfo` поле в поле равен собственному (и вид / запись кэша
   те же) — образ и память **принимаются** (ни одного вызова Vulkan), иначе свой `vkCreateImage` как раньше (deswizzle-ный staging всё
   равно годен — раскладка та же). На заливке: deswizzle-ный объект — `staging` = срез рабочего потока (`copies_of` NR-05, ни копии, ни
   deswizzle), ASTC — `astccache::upload` берёт срез вместо `pread` (только для той же записи кэша). Копия записывается как раньше: в
   пролог слота (`gfx-upload-prologue`) или в проход; срез живёт в `retire` слота до его fence. Счётчики / проба / пропуск хэша — как у
   NR-05 `=1`.
4. **Синхронизация.** Рабочий поток не пишет командных буферов и не трогает очередь: образ там только создаётся и связывается с памятью;
   staging `HOST_COHERENT` заполняется до передачи объекта через мьютекс ядра, а `vkQueueSubmit` копии на трансляторе — после (запись
   хоста в когерентную память видна устройству при подаче). Образ `EXCLUSIVE`, впервые используется (UNDEFINED → TRANSFER_DST) на
   единственной очереди транслятора — ни передачи владения между семействами очередей, ни таймлайн-семафора не нужно (в отличие от
   варианта «рабочий поток сам подаёт копию», который потребовал бы второго потребителя очереди и семафора — отвергнут как лишний).
   Порядок замков: замок ядра → `nrts::mu` (release), обратного нет.

## Переключатель `DM_NR_TEXSTREAM` (по умолчанию 0; нужен `DM_NR_TEX` 1 или 3, при незаданном `DM_NR_TEX` включает его как `=1`)
| Значение | Что делает |
|---|---|
| 0 / нет | ничего: приёмник не ставится, `g_dm_nr_texstream == 0`, `nrts::mode == 0`; два новых входа фронта сразу выходят; в движке `nrts::Taken` пуст, путь — NR-05 / старый |
| 1 | как описано: рабочий поток делает образ + память + staging (или ASTC-образ + блоки), транслятор принимает |
| 2 | **сверка**: рабочий поток готовит так же, транслятор исполняет **старый** путь (свой образ, свой deswizzle `DESWZ_DIRECT` / своё чтение кэша) и сравнивает: `VkImageCreateInfo` и вид (красная строка), требования памяти и тип памяти своего образа против подготовленного, байты staging побайтно; объект рабочего потока уничтожается |
| `DM_NR_TEX=2` | `DM_NR_TEXSTREAM` игнорируется (лог): сверка NR-05 идёт по старому пути без blob |

Тонкая настройка: `DM_NR_TEXSTREAM_MB` (предел невзятых, см. выше); при `DM_NR_TEXSTREAM` умолчание `DM_NR_TEX_MIN_KB` = 0 (цена — на образ,
мелкие текстуры тоже). Режима 3 (poison) нет: байты доказываются `=2`, «отравленный» образ ничего не добавил бы.

## Строки лога
- старт: `[nr] DM_NR_TEXSTREAM=1 (on): the worker also makes the VkImage + memory ...`, движок: `NVN nr-texstream DM_NR_TEXSTREAM=1: ...`;
- раз в 10 окон PERF (с NR-05): `NVN nr-texstream DM_NR_TEXSTREAM=N: worker made A deswizzled + B ASTC images (… MB staged, … ms on the worker,
  of it ASTC reads … ms), refused: …, destroyed untaken …, staging chunks …; translator: taken …, adopted C (… ms here), staging used D (… MB)
  + ASTC E (… MB), mismatches create info F / kind G; images made here H (X ms: vkCreateImage + memory + bind); held now … of … MB in … objects`;
- `=2`: `NVN nr-texstream verify: claims …, create info / kind mismatches …, memory requirement mismatches …, staged byte compares …, mismatches …`;
- в `[nr] textures by events …` (10 с): `texstream: prepared images … deswizzled + … ASTC, refused by the engine …, taken …, released untaken …`.

## Ожидаемый выигрыш (оценка, не замер)
| Класс | Что даёт `=1` (поверх NR-05 `=1`) |
|---|---|
| Mi 14 / Adreno 750 | с транслятора уходят создание + память + bind каждого нового материального образа и копия blob (0.1 мс/МБ). Событие «192 новых / 33.7 МБ» (остаток 43–48 мс): −(10…25) мс создания + −3.4 мс копии; «216–224 мелких» (28–30 мс): −10…20 мс; «82 МБ меню»: −15…30 мс. Цели аудита «40–50 → 5–10 мс» это **не достигнет**, если остаток в основном не создание (кадры повторных заливок без создания тоже несут 11–20 мс) — решит строка `images made here … ms`. fps не изменится (упор в GPU), меняются длинные кадры загрузки / стрима |
| S7 / Adreno 7xx (слабый CPU) | то же ×2–3 по абсолюту (ядро A7x, kgsl-выделение и обнуление страниц медленнее): −30…60 мс на событие входа |
| Mali / PowerVR / Xclipse (без BC) | главное: ASTC-записи кэша читаются **на рабочем потоке** (pread + sanitize + копия, ≈ 0.75–2 мс/МБ после NR-18) — вход в зону с 30–80 МБ из кэша: −25…160 мс с транслятора [м по TL2 / NR-18]; плюс создание образов. Без наполненного кэша (первый прогон) BC декодируется на трансляторе как раньше — NR-22 там не помогает (только не-BC ≈ 9 % байт) |
| Слабый CPU вообще | одна нить nice 10 берёт создание и память; занятость ядер на загрузке та же, но транслятор не ждёт; прирост памяти — предел `DM_NR_TEXSTREAM_MB` (невзятые образы 30 с) |

Память: подготовленные, но ещё не взятые образы держат `DEVICE_LOCAL` память до первой заливки (обычно кадры; невзятые — до 30 с), плюс
staging того же размера; предел 2 × бюджет blob (192–256 МБ) и 1024 объекта; свободных чанков ≤ 64 МБ. Старый путь держал staging только
в арене слота. На 6 ГБ телефоне пик загрузки уровня может вырасти до ~+200 МБ на время загрузки — поэтому предел, а не «всё сразу».

## Риски (честно)
1. **Остаток 40–50 мс — не только создание образов** (см. таблицу: кадры повторных заливок без создания несут 11–20 мс). Если `images made
   here` покажет, например, 8 мс на 192 образа — выигрыш NR-22 на Mi 14 мал (≈ 10 мс), и дальше копать надо в мемо дескрипторов / виды.
2. Подготовленный `VkImageCreateInfo` дублирует правила `get_image_slow` (`ci_of`). Расхождение не ломает картинку: транслятор сравнивает
   поле в поле и при отличии делает свой образ (счётчик `mismatches create info`), но тогда выигрыша нет. `=2` считает и требования памяти.
3. Драйверы: `vkCreateImage` / `vkAllocateMemory` с двух потоков разрешены спецификацией; если у какого-то стокового драйвера (PowerVR?)
   с этим ошибка — падение в рабочем потоке. Поэтому умолчание 0 и включение по семейству после прогонов.
4. Образы, созданные под текстуры, которые игра так и не семплирует, держат память до истечения (30 с) — предел ограничивает.
5. ASTC: запись, найденная рабочим потоком, может не совпасть с решением транслятора (`refused`, слияние индекса между ними) — тогда вид
   не совпадает и образ не принимается (счётчик `kind`), транслятор читает сам.
6. Пролог: копия из среза идёт так же, как старая (пролог / проход); срез держится `retire` слота — при очень длинных подачах держит чанк.
7. Общие файлы (`xbg_game.cpp`, `hle_dos2_nr.c`) правят другие ветки; правки NR-22 — точечные вставки, `namespace nrts` отдельным блоком.

## Не сделано
- GPU-deswizzle рабочего потока (ETR `GPU_DESWIZZLE`) — здесь CPU-deswizzle уже на рабочем потоке, транслятору он ничего не стоит.
- Рабочий поток для текстур без события движка (RT, `CreateTexture` с `initData`, UI) — их создаёт транслятор, как раньше.
- `vkCreateImageView` заранее и снятие `memo_check_gen` при приёме (часть остатка, см. риск 1) — отдельный шаг после замера.
- Умолчание по детекту в `xbg_vendor_policy.h` — после телефона.

## Прогон на телефоне (главный агент; бэкап `files/save`, проверить keyguard, после — force-stop)
APK этой ветки (`wt-nr22`). Сцена как у NR-05: меню → загрузка сейва → 2–3 мин бега со сменой локации, инвентарь / карта; ≥ 40 с после загрузки.
1. **R-NR22a, база + цена создания:** `DM_NR_TEX=1` (texstream выключен). Ждём раз в 10 окон PERF строку
   `NVN nr-texstream off (DM_NR_TEXSTREAM=0): images made here H (X ms: vkCreateImage + memory + bind on the translation thread)` —
   **X / H = цена создания + памяти одного материального образа на трансляторе, X за прогон — то, что NR-22 уберёт.** Плюс `[长帧]` как
   база (события «192 новых / 33.7 МБ», «196 + 188 / 82 МБ», «216–224 мелких»).
   Затем тот же маршрут с `DM_NR_TEXSTREAM=2` (сверка, картинка = старый путь): `NVN nr-texstream verify: claims N, create info / kind
