# NR-TCOUNT `DM_NR_TCOUNT` — счёт для тайлерного плана T3 / T4 / T5 (PERF-X19, шаг 3), 18–19.11.2026

Ветка `dos2-tcount` (worktree `wt-tcount`) от `dos2-nr-all` 85d2cfa. Хозяин одобрил 18.11: **только счёт, поведение не меняется.**
`DM_NR_TCOUNT=0` (умолчание на всех семействах) — ничего не считается: `present()` читает одно число и выходит.
На телефоне ещё не запускалось (у этого агента телефона нет) — прогон в §6.

## 1. Как устроено

Модель кадра — уже существующий записыватель графа проходов `pgraph` (`DM_GFX_PASS_GRAPH`, `xbg_game.cpp`): он видит каждый
начатый проход Vulkan (вложения, как грузится и сохраняется каждое, draw, чтения текстур, записи storage-картинок и буферов, номер
отправки), каждую копию / очистку / dispatch вне прохода и чем закончился проход (код операции хоста, строка исходника, разрыв по
чтению). Новых крючков в путь draw нет. Добавлено в `pgraph`:

- событие «проход закончился» (`E`) — чтобы запросы / записи буферов внутри прохода не считались «между проходами» (вывод
  `NVN PGRAPH` от этого не меняется: обход A→B→A его пропускает);
- в `pgraph::draw` (только во взведённом кадре): пишет ли вершинная стадия (стадии 0–3) storage-буфер / storage-картинку (то же правило,
  что `pre_write` тайлового WAR-барьера), доходит ли draw до вложений (нет растеризации, или нет фрагментного шейдера и запись
  глубины / трафарета выключена), первый / последний draw прохода такой ли, класс UI (фрагментный шейдер Iggy, `nb_ui.h`);
- в `pgraph::begin`: маска загрузок DONT_CARE, которую решил NB-план (`nbrp::bi_dc`: план + свежие вложения NR-10) — иначе под
  `SIM_GPU=mali` загрузки плана считались бы как LOAD;
- счётчик чтений, не влезших в предел записывателя (64 на проход) — `reads over the recorder cap`.

Ограничения модели (все в сторону завышения МБ или оптимизма «можно переставить»): DONT_CARE-загрузка площадного близнеца NR-10b
(`nr_adc`) считается загрузкой; буферы по адресу не отслеживаются (поэтому `exact`); если хост переводит цель копии раньше источника,
чтение источника достаётся следующему проходу / операции (ограничение `pgraph`, редкость).

`pgraph::present` взводит кадр для дампа (`DM_GFX_PASS_GRAPH`, раз в 10 с), для счёта (1 кадр из `DM_NR_TCOUNT_EVERY`, умолчание 4)
или для обоих; на следующем `present` кадр копируется в `nrtc_frame` и разбирается `nrtc_analyze` (`dm/gfx/nr/nr_tcount.h`, чистый C++).
Раз в 10 с — 4 строки (одна строка не влезает: `xbg_logf` режет на 1023 байтах).

**Цена.** При 0 — ноль. При 1 взведённый кадр идёт медленным путём записывателя (без мемо дескрипторов, без полосы NR-09 — так
`pgraph` видит каждое чтение): CPU этих кадров выше, **fps в прогоне со счётом не сравнивать**, результат — строки. Картинка та же.

## 2. Модель стоимости

Тайлер (Mali / PowerVR / Xclipse / Maleoon): каждое открытие прохода грузит вложение из памяти (если не CLEAR / DONT_CARE) и
сохраняет в конце (если не DONT_CARE). Считается **4 байта на пиксель на вложение**, какой бы ни был формат (как просил план; AFBC и
«transaction elimination» на Mali реальную цифру уменьшают, поэтому это верхняя граница). «Повторное открытие» = сохранение в
предыдущем открытии + загрузка в следующем. На Adreno в sysmem (Turnip, наш режим) эти байты почти ничего не стоят — счёт там
показывает структуру кадра, а цену — прогон под `DM_GFX_SIM_GPU=mali` (те же решения load/store, что у Mali).

## 3. Строки и что значит каждое число

Везде «в кадр» = среднее по взведённым кадрам; пары чисел `X / Y` = 3D-проходы / проходы UI (Iggy).

### `[nr] tcount T3` — вершинные шейдеры, которые только пишут (скиннинг / палитры в SSBO)

```
[nr] tcount T3 DM_NR_TCOUNT=1: N frames sampled (1 in 4), M with 3D; a frame 3D / UI: passes P / Pu, draws D / Du, load+store X / Xu MB (4 B/px);
  VS-only draws a / au in passes b / bu (only VS-only c / cu = m / mu MB), VS storage writers that also draw e / eu;
  same target re-begun next to a VS storage write s / su (next to a VS-only draw v / vu) = k / ku MB; VS-only by shader: vs<8 hex> n in <цель>, ...
```
- `load+store` — сколько вообще стоят открытия проходов кадра по модели (база для долей).
- `VS-only draws` — draw, у которых вершинная стадия пишет storage, а до вложений ничего не доходит. `in passes` — в скольких проходах.
- `only VS-only` — проходы, где других draw нет: весь их load+store (`m` МБ) уходит, если вынести их в compute / проход без вложений.
- `VS storage writers that also draw` — пишут storage и рисуют (вынос = разбить на compute + draw).
- `same target re-begun next to a VS storage write` — пары «проход → следующий проход в ту же цель» (между ними нет других проходов), где
  первый кончается таким draw или второй с него начинается: хост закрыл проход ради барьера storage (WAR-барьер перед писателем или
  ленивый барьер у читателя). `k` МБ — цена этих повторных открытий. Вынос писателя из прохода их убирает.
- `VS-only by shader` — три вершинных шейдера с наибольшим числом таких draw и цель первого прохода, где они встретились
  (`ШxВ:формат NVN:fs<первый FS прохода>`).

### `[nr] tcount T4` — цель открывается в кадре несколько раз

```
[nr] tcount T4: a frame 3D / UI: images opened 1x .. / .., 2x .. / .., 3+x .. / .. (most N / Nu); re-opens r / ru = R / Ru MB;
  the same attachments again after other passes a / au = A / Au MB: reorderable o / ou (exact x / xu; the rest if buffer writes allow) = O / Ou MB,
  blocked: a pass between uses the target .., other image dependency .., submit .., query / report ..;
  re-opens with another attachment set d / du = D / Du MB; reads over the recorder cap L
```
- `images opened 1x / 2x / 3+x` — гистограмма: сколько картинок-вложений кадра открыто 1, 2, 3 и более раз (очищающие проходы хоста `K`
  тоже открытия); `most` — максимум открытий одной картинки. `re-opens` / МБ — все повторные открытия и их цена.
- `the same attachments again after other passes` — для каждого прохода берётся следующий проход **с тем же набором вложений и размером**,
  между ними — другие проходы. `reorderable` — один из двух можно передвинуть к другому: проходы между ними не читают и не пишут цель, второй
  не читает ничего, что пишут проходы между (или первый можно опустить вниз по тем же правилам), нет отправки и запросов / отчётов
  между ними. `exact` — к тому же нигде нет записей в буферы (буферы не отслеживаются по адресу, поэтому без `exact` это «если буферы
  независимы»). `O` МБ — что уберёт перестановка.
- `blocked` — почему нельзя: проход между использует цель; другая зависимость по картинкам; между ними отправка (`submit`); запрос /
  отчёт (`SIGNAL` / `REPORT_COUNTER`).
- `re-opens with another attachment set` — картинка открыта снова, но в другом наборе / размере (например, общая глубина у G-buffer и
  освещения): перестановка не поможет, нужна склейка подпроходами (не этот шаг).
- `reads over the recorder cap` — чтения, которые записыватель не увидел (>64 на проход): при заметном числе вердикт «можно
  переставить» становится оптимистичным.

### `[nr] tcount T5` — проход закрыт ради копии / очистки, соседние проходы в одну цель

```
[nr] tcount T5: a frame 3D / UI: same target re-begun with only copies / clears / dispatches between c / cu = C / Cu MB: removable k / ku = K / Ku MB
  (ops into the target = drawable in the pass .., independent = move out .., read the target .., dependent ..; across a submit ..) [виды операций];
  back-to-back passes into the same target b / bu = B / Bu MB: mergeable m / mu = M / Mu MB, the second reads the target .., across a submit ..;
  ended by: <причина> n, ...
```
- Первая часть — пара «проход → тот же набор вложений», а между ними только копии / очистки / dispatch (или проход-очистка хоста `K`).
  Каждая операция: `into the target` — пишет в цель (рисуется внутри прохода: `vkCmdClearAttachments` / квадрат), `independent` —
  не трогает ни цель, ни то, что читают / пишут проходы (выносится до первого или после второго), `read the target` — читает цель
  (копия / resolve наружу: нужен store, не убирается), `dependent` — прочее. `removable` = все операции первых двух видов, без отправки
  и запросов между; `K` МБ — что уберёт (плюс открытие прохода-очистки, если он был). В квадратных скобках — 4 самых частых
  «операция + вид» (`COPY_T2T into the target`, `CLEAR_TEX independent`, `clear pass into the target`, `dispatch ...`).
- `back-to-back` — между двумя проходами в одну цель ничего нет. `mergeable` — второй не читает цель (иначе это петля обратной связи) и
  между ними нет отправки / запроса. `ended by` — 4 самые частые причины, по которым закрылся первый из пары: `read break why=N`
  (чтение вложения открытого прохода), `<операция хоста>/L<строка end_open_pass>`, `host` (без строки: проходы-очистки, закрытие при
  отправке).

### `[nr] tcount top` — пять целей с наибольшей ценой повторных открытий

```
[nr] tcount top: re-opened targets by MB a frame: 1) #<serial> ШxВ fmt 0x.. [depth] [UI] opened n, re-opens X MB, pairs with passes between p (reorderable o),
  between: <ШxВ:fmt:fs........>,<...>,+N; 2) ...
```
`serial` — номер текстуры гостя (как в `NVN PGRAPH imgs`), `fmt` — формат NVN, `opened` — открытий в кадр, `between` — проходы между
двумя открытиями этой цели в последнем кадре, где они были (цель их первого вложения + первый фрагментный шейдер).

## 4. Когда делать T3 / T4 / T5 (пороги) и ожидаемый выигрыш на Mali-G57

Перевод МБ в мс: Mali-G57 MC2 (Helio G99, Dimensity 700) — LPDDR4X 2×16 бит ≈ 17 ГБ/с пик, GPU реально получает 8–10 ГБ/с, когда CPU тоже
работает. **1 МБ load+store ≈ 0.1 мс** (верхняя граница; с AFBC на цвете ≈ 0.05 мс). Мерить на `DM_GFX_SIM_GPU=mali` (решения load/store
как у Mali); Adreno sysmem — только структура кадра.

| Шаг | Число в строке (3D, ходьба по Форту) | Делать, если | Ожидание на G57 | Не делать, если |
|---|---|---|---|---|
| T3 вынос VS-only | `VS-only draws` и `next to a VS storage write … MB` (T3) | `VS-only draws` ≥ 1 в кадр **и** (`… = k MB` ≥ 10 МБ **или** `only VS-only` ≥ 1 прохода с ≥ 5 МБ) | k × 0.1 мс: 10 МБ ≈ 1 мс; одно повторное открытие полного кадра 2400x1080 с 4 вложениями ≈ 79 МБ ≈ 4–8 мс | `VS-only draws` = 0 и `writers that also draw` = 0 — в DOS2 скиннинг не в вершинных шейдерах: T3 закрыт для DOS2 (проверить у D16 / ETR) |
| T4 перестановка в NB-плане | `reorderable … (exact x) = O MB` (T4) и `top` | `exact`-часть ≥ 10 МБ в кадр (≈ 1 мс) | O × 0.1 мс (exact-доля — сразу; остальное после учёта буферов по адресу, +4–8 агент-ч) | почти всё в `blocked: a pass between uses the target` или в `another attachment set` — это не порядок, а зависимость / склейка подпроходами |
| T5a копия / очистка внутри прохода | `removable … = K MB` (T5) | K ≥ 5 МБ в кадр (≈ 0.5 мс) | K × 0.1 мс | в скобках в основном `reads the target` (копия цели наружу — нужен store) |
| T5b склейка соседних проходов | `mergeable … = M MB` (T5) | M ≥ 5 МБ в кадр; смотреть `ended by` — какая строка рвёт | M × 0.1 мс | в основном `the second reads the target` (петля; это NR-UIX `rb`, там 0) |

UI (правое число) — отдельно: по NR-UIX под SIM `разрывы для слияния 0`; значимый UI-выигрыш даст сначала `DM_NR_UIX_DS / AREA` (там
модель на сотни МБ), а не T4 / T5. Порог «≥ 10 МБ ≈ 1 мс» выбран, чтобы шаг окупал свои часы (T4 в NB-плане ≈ 8–16 агент-ч + прогоны,
T5 ≈ 4–8 ч, T3 ≈ 8–16 ч: compute-копия вершинной стадии в трансляторе).
