# NR-09R `DM_NR_DIRECT` — draw движка пишется напрямую, без своих вызовов NVN (17.11.2026, ветка `dos2-nr09r`)

Задача хозяина: нативный код должен **заменять** транслированный путь, а не работать поверх него. База: `dos2-nr-all` c1c2db7 (NR-20, NR-06,
NR-08 — умолчания DOS2). **На телефоне не исполнялось ни строчки** (adb не запускался). Всё новое за `DM_NR_DIRECT`, умолчание 0.

## 0. Коротко
- Что заменено: **draw-часть** пути движка. Функции `0x928e80 / 0x928fb0` для взятого draw не исполняются: поиск индексного буфера, сброс
  текстур `0x924730`, `SetRenderEnable`, сам draw и байт флага идут нативно (модель NR-23, доказана эмулятором на машинном коде игры) и
  попадают в запись **одним вызовом** на большом стеке. Вызовов `GetTextureHandle / BindTexture / DrawElements(Instanced)` движка, их
  thunk-ов, обёрток, входа в хук сброса и передачи идентичности через тап больше нет.
- Что убрано сверх вызовов: привязки текстур, которые ничего не меняют (слот уже держит этот хэндл) — не шлются; обход слотов тапом IR на
  draw, чей набор чтений проход уже содержит — не делается; идентичность NR-09 — без блокировок и атомиков, без набора текстур (его в
  `DM_NR_DRAW=1` никто не читает).
- Что **не** заменено и почему (§1): вызовы состояния (пакет 21 и др.) и UBO (`0x926f90 / 0x925740`). Это не draw-время, и запись
  состояния — вход полосы NR-09, а не тень.
- Причина «+0.44 мс на потоке игры» у NR-09 найдена в коде: хук идентичности на каждом draw собирал набор текстур (копия 512 Б + хэш,
  492 раза на кадр, под мьютексом), который в `DM_NR_DRAW=1` бэкенд не читает вовсе (`texset_note` — только режим 2), плюс 4 атомика и
  таблица на 64 ключа (97 блокировок на кадр).

## 1. Разбор: что можно заменить, что нельзя
Числа — палуба, Mi 14 Ultra, логи `nr2_a2` (профиль NVN), `nr8_*`.

| Вызовы движка на кадр (поток записи) | Сколько | Цена тела | Судьба в NR-09R |
|---|---|---|---|
| `DrawElements` (+ `Instanced`) | 1 095 (из них 983 — draw движка 36 / 37) | **966–1 017 нс** = 1.06–1.11 мс | 983 вызова не делаются; тело = тап IR + блок состояния NB-13a + запись — остаётся, тап дешевеет (§2.3) |
| `GetTextureHandle` + `BindTexture` | 1 895 пар | 80–84 нс = 0.15 мс | пары сброса draw 36 / 37 не делаются; привязка «тот же хэндл» не пишется вовсе |
| `BindUniformBuffer` | 2 634 | 39–42 нс = 0.10 мс | **остаются** (код движка, см. ниже) |
| `BindProgram` / `BindVertexBuffer` / vattr / vstream / depth-stencil | 1 103 / 1 100 / 298 / 298 / 180 | 113 / 70 / 86 / 92 / 123 нс ≈ 0.3 мс | **остаются** (пакеты состояния) |
| вход хука сброса `0x924730` (28 аргументов через трамплин) + идентичность | 983 | замер NR-09: +0.44 мс на потоке игры | хук для draw 36 / 37 не входит; идентичность — §2.4 |

Почему тело `DrawElements` стоит 1 мкс (по коду, без замера по частям — его даст строка `ns a direct draw`): (а) тап IR `nbt_draw`:
после каждого `BindProgram` маски слотов ищутся заново (до 5 поисков в таблице с атомиками), обходятся все сэмплируемые слоты
(`nbt_prog_draw`: чтение `g_wt_id_mem` — 8 МБ таблица, линейный поиск в `sread`), `nb_read` — линейный поиск по чтениям прохода;
(б) `cmd_alloc` → `NBS_BEFORE`: упаковка грязных видов состояния (копия, хэш, словарь) и запись `OP_X_NB_STATE`; (в) запись
`OP_X_NB_DRAW` 167 Б; (г) 5–6 атомиков счётчиков.

**Что не стало заменой и доказательства.**
1. **Вызовы состояния.** Их делает код обработчиков пакетов движка задолго до draw (`NATIVE_PLAN` 1.7, NR-23 §1); в момент вызова не
   известно, какой draw их возьмёт. Запись состояния — вход полосы: `state.vb`, viewport, шесть id групп читаются из `State` (NR-13
   §1.2). Ключ движка состояние не описывает: в `nr8_draw` из 1 698 829 попаданий таблицы 1 677 347 — первый вариант строки, т. е.
   **1.26 % draw рисуются вторым вариантом строки — пайплайном, который ключ сам не определяет** (состояние мимо кэша движка: stencil
   ref, bias, blend color — NR-09 §2.3 — или другое определение прохода / раскладки). Замена = модели
   обработчиков пакетов 21 / `0x9283a0` / `0x9284e0` с доказательством на машинном коде + ленивая материализация `State` в бэкенде.
   Это отдельный шаг (оценка §8), без телефона его не проверить — не делался.
2. **UBO.** `0x925740` — 5.9 КБ кода с аллокатором кольца и спин-блокировкой (NR-23 §1); его `BindUniformBuffer` попадают в тень draw
   как раньше. Модель этого кода — высокий риск при 0.10 мс тел.
3. **Запись остаётся `OP_X_NB_DRAW` + хвост NR-09.** Бэкенд получает на взятый draw одну запись (привязки + draw + идентичность) и, если
   состояние менялось, блок `OP_X_NB_STATE`; NVN-пакетов draw-времени нет. Свой формат записи дал бы 0 выигрыша: её читатели —
   `nbdraw::apply`, полоса, NR-08 — уже работают с этой.

## 2. Что сделано
### 2.1 `NRDP_DRAW` (бит 1): нативная функция draw → рекордер одним вызовом
`nrd_draw_take` (`hle_dos2_nr_direct.inc`) — нативный обработчик общего хука draw (тот же вход, что у NR-23):
1. `nrnc_draw_pre` (запись индексного буфера по хэндлу), `nvn_nrd_can(cb)` (поток внутри скобки NB-09 этого draw, нет режимов проверки
   NB-10 / `DM_NATIVE_DRAW` / захвата NR-23, буфер пишется), указатели NVN движка = наши thunk-и (`nrd_verify`, один раз). Любой отказ —
   **до первой записи и первого вызова**: исполняется функция движка, нетронутая (структурный тест).
2. `0x926f90(r)`, `0x925740(r)` движка — как есть.
3. Идентичность (§2.4), план сброса текстур (`nrnc_flush_plan`).
4. **Одна смена стека** (`nvn_on_bigstack`): `nrnc_flush_run` + `nrnc_draw_tail` — порядок машинного кода; их операции = рекордер
   (`nvn_nr_direct.inc`): `nvn_nrd_bind` = `bind_handles()` с хэндлом `GetTextureHandle`; `nvn_nrd_draw` = тело `DrawElements`
   (`nbt_draw`, затем `nbd_draw`) без строк, которые здесь выключены; `SetRenderEnable` — тело точки входа (редко).
Рекордер пишет **теми же функциями, что точки входа**: тап NB, тень NB-09, метки `DM_NVN_WT_DRAIN`, блок состояния NB-13a, запись —
те же по построению. Отдельной логики «согласованности NVN-состояния для запасных draw» нет: её даёт сам общий код.

### 2.2 `NRDP_TEXF` (бит 2): привязка, которая ничего не меняет, не шлётся
Сброс движка перевязывает весь грязный диапазон слотов, в т. ч. неизменившиеся. Зеркало `nrd_mirror` (`nr_direct.h`) знает, что
таблицы бэкенда держат **в рамках одной записи команд**: после привязки хэндла h к (вид, стадия, слот) и до следующей привязки этого
слота таблица бэкенда держит h при исполнении любой более поздней записи того же хэндла команд — что бы ни шло до него и сколько бы раз
он ни исполнялся (писатели `state.tex / samp / img` — только `exec_bind_handles` и `nbd_apply`; слияние поста меняет слот и возвращает
его внутри одного draw). Через границу записи команд, для другого буфера, после вложенного хэндла (`CopyCommands / CallCommands`) и
после привязки другим потоком ничего не предполагается (сброс / забывание). Не шлётся только то, что проверяет режим 2: одиночная
привязка текстуры внутри скобки draw движка. Метка использования `wt_use_ids` ставится всегда. Бэкенд: меньше привязок в записи,
`tex_gen` не двигается → NR-08 чаще находит запись «по поколению», а не по хэшу (в `nr8_draw` — 49 % по хэшу).

### 2.3 `NRDP_TAP` (бит 4): тап IR не обходит слоты повторно
`nbt_draw` на каждом draw добавляет в открытый проход чтения (множество) и список сэмплируемых образов / ключ fs (флаги меняются в одну
сторону). Память `nrd_tapmemo`: подпись = таблицы привязок стадий 0–4 (XOR примесей по слотам, ведётся в `nbt_bind`) + программы стадий
+ поколение регистраций пула + счётчик публикаций масок. Если draw этого же прохода с этой подписью уже обходил слоты (и у всех его
программ опубликованы маски и ключ fs), обход ничего не добавит (доказательство — в `nr_direct.h` у `nrd_tapmemo`) и пропускается.
Не пропускается: первый draw прохода, `DrawTexture`, draw после ожидающего барьера (идёт раньше в `nbt_draw`). Работает для всех draw
(и UI). Побочно: после публикации масок кэш масок привязанных программ сбрасывается (иначе жил до следующего `BindProgram`).
Подпись — 64-битный хэш: два разных состояния с одной подписью не различаются (как у наборов текстур `nr_key.h`).

### 2.4 `NRDP_IDENT` (бит 8): идентичность без блокировок
`nrd_ident`: 120 Б кэша состояния рендерера читаются блоком и сравниваются с прошлым draw (`memcmp`) → тот же id; иначе таблица
потока на 4096 ключей в 2 пути (id плотные, не переиспользуются; `why` фиксирован) → иначе общая таблица под мьютексом (первый раз на
ключ). Набор форматов RT ищется только при смене RT-хэндлов. Набор текстур не считается (id = 0). Счётчики — свои у потока. Только в
режиме «одна идентичность» NR-09 (`DM_NR_KEY` не задан) и при `DM_NR_DRAW=1`; с `DM_NR_KEY=1/2` или `DM_NR_DRAW=2` — прежний `nk_ident`
(им нужен набор текстур / счёт). Для draw 36 / 37 вызывается прямо из `nrd_draw_take`, для остальных 23 мест — из хука сброса.

### 2.5 Бэкенд (`xbg_nr_direct.inc`, одна строка в `nbdraw::apply`, одна в `tick`)
Свободное слово хвоста NR-09 (`nrd_tail._pad`, раньше 0; прежние читатели его не смотрят): `NRD_X_DIRECT`, число неотправленных
привязок (режим 1), битовая карта «эту привязку режим 1 не послал бы» (режим 2, первые 24 привязки записи). Режим 2: каждая помеченная
привязка сверяется с `state.tex` **в момент, когда она ложится** (с учётом более ранних привязок той же записи).

## 3. Переключатели (умолчание 0; игрокам не выдаются; `jni_android.c` и `xbg_vendor_policy.h` не тронуты — от GPU не зависит)
| | |
|---|---|
| `DM_NR_DIRECT` | **0** — ничего: поток команд байт в байт прежний; цена — загрузка + непринятый переход в 9 местах (`bind_handles`, `nbt_bind`, `nbt_draw` ×2, `nbd_draw`, `nbd_reset`, `BeginRecording`, `Copy/CallCommands`, `wt_register`), `nk_draw`, `nbdraw::apply`. **1** — вкл. **2** — исполняется старое, новое считается рядом и сверяется (красные строки, первые 16): вызовы NVN движка против модели (сверка NR-23, взводится этим же переключателем: `[nr] nocall check`), помеченные привязки против таблицы бэкенда, обход тапа на draw, который режим 1 пропустил бы (не должен ничего изменить), лёгкая идентичность против `nk_ident`. **3** — не существует: режим 1 шлёт те же записи минус привязки, которые ничего не меняют; отравить нечего |
| `DM_NR_DIRECT_PARTS` | маска: 1 `DRAW`, 2 `TEXF`, 4 `TAP`, 8 `IDENT`; умолчание 15 (A/B частей) |

Нужно: `DM_NR=1|2`, `DM_NR_DRAW=1|2` (идентичность и хвост записи), `DM_NB_OPS` с битами 36 / 37 (умолчание). `DM_NR_DIRECT=1` вместе с
`DM_NR_NOCALL≠0` не включается (оба встают на место функций draw). `=2` сам ставит `DM_NR_NOCALL=2`, если тот не задан. Часть `TEXF`
выключается сама (строка в логе) при `DM_NB_ORDER`, `DM_NB_RELOC` или `DM_NB_MX` ≠ 0: они исполняют куски записи не в порядке потока /
от ключевых кадров, а зеркало стоит именно на порядке потока (все три — 0 по умолчанию после NR-15).

Строки (поток отчёта NR, раз в 10 с):
- старт: `[nr] DM_NR_DIRECT=… (NR-09R, parts …): …`; первый draw: `[nr] direct: the engine's … pointers are the thunks of the bodies the
  direct recorder stands for`; бэкенд: `[nr] DM_NR_DIRECT=… (NR-09R, backend): …`;
- `=1`: `[nr] direct (DM_NR_DIRECT=1, parts …): engine draws recorded directly D a frame … with T texture binds of their flush, F of them

  `[nr] direct, the tap and the identity …: … skipped (x %) …; identity (lean): … state of the previous draw p %, thread table q %, shared
  table (lock) k a frame …`; `[nr] direct, ns a direct draw (1 in 64 timed, n): T = the engine's uniform blocks A + identity B + flush and
  record C (inside it: the tap E, the state block + draw record F)`; бэкенд: `[nr] direct (backend, DM_NR_DIRECT=1, last 10 s): …`;
- `=2`: `[nr] direct check (DM_NR_DIRECT=2, …): … would not send … tap: … bad N; identity (totals): … bad N; …`; бэкенд:
  `[nr] direct check (backend, DM_NR_DIRECT=2, last 10 s): … bad N; totals: …`; строки NR-23 `[nr] nocall …`; красные:
  `【红】[nr] direct check: …`.

## 8. Риски и чего нет
- **Не исполнено на устройстве.** Путь «рекордер на большом стеке из хука draw» в живом процессе — впервые (как у NR-23 `=1`, который
  тоже не прогонялся). Сначала `=2`.
- `TEXF` держится на том, что таблицы привязок бэкенда пишут только записи привязок в порядке потока. Новый писатель в бэкенде (как
  слияние поста, которое слот возвращает) без возврата сломает посылку; `=2` это ловит (`backend … bad`).
- `TAP`: подпись — хэш 64 бита; обход, пропущенный зря, = потерянное чтение прохода = пропущенный барьер перед проходом (артефакт на
  тайлерах). Сверка `=2` считает такие случаи напрямую.
- `IDENT`: id набора текстур в хвосте = 0. Если следующий шаг начнёт читать его в режиме 1 (NR-09 §8 «передний ключ NR-08») — вернуть
  расчёт (лучше лениво, по грязному диапазону).
- Счётчики `[nvn] 帧 N：… 次调用` / `DM_NVN_PROF=2` при `=1` не видят 2.0–2.8 тыс. вызовов (это и есть признак работы).
- Кэш масок тапа сбрасывается после публикации (и в `=2`): чтения прохода могут стать точнее, чем у сборки без переключателя.
- **Нет**: нативных обработчиков пакетов состояния и ленивого `State` в бэкенде (главный остаток «двойного пути»: ≈ 0.3 мс вызовов +
  блок состояния на draw на потоке игры, `program` 0.2 мс + перечитывание групп на трансляторе; оценка 12–18 агент-часов + оракул на
  обработчики + 3–4 прогона); модели UBO; быстрого входа `BindUniformBuffer` на гостевом стеке (≈ −0.1 мс [м]).
- **NR-12 UI — не подошёл.** Draw Iggy идут не из пакетов 36 / 37, а прямыми вызовами NVN из GDraw (`0x1bf0cd0` и ещё 10 входов);
  модели этих функций нет, состояние UI ставится сырыми вызовами вне взятых пакетов. На потоке игры у NR-12 своей работы нет (полоса UI
  целиком в бэкенде), т. е. «двойного пути» хука там нет. Из NR-09R к UI применимы только `TAP` и зеркало (привязки UI учитываются).

## 9. Прогоны телефона (главный агент, по разрешению хозяина)
Бэкап `files/save`; keyguard снят; `DM_DOS2_FPS=0`; палуба 60 с от загрузки, затем сцена потяжелее. APK: `wt-nr09r/work/DOS2-port-debug.apk`.
Общее для всех: `DM_NR_CPU=1` (остальное — умолчания сборки: `DM_NR=1 DM_NR_BUF=1 DM_NR_DESC=1`).
1. **R-09R-a, сверка:** `DM_NR_DRAW=1 DM_NR_DIRECT=2`. Ждём: `[nr] DM_NR_DIRECT=2 (NR-09R, parts 0xf): the old path runs …`,
   `[nr] DM_NR_NOCALL=2 (NR-23): count + compare …`; каждые 10 с: **`[nr] nocall check … bad 0 … bad 0`**, **`[nr] direct check
   (DM_NR_DIRECT=2 …): … tap: … bad 0; identity (totals): … bad 0`**, **`[nr] direct check (backend …): … bad 0; totals: compared N,
   bad 0`**; ни одной `【红】[nr] direct check`. Заодно ответы: `would not send` (доля привязок-пустышек), `=1 would skip … %` (тап).
2. **R-09R-b, то же без zero-copy и с пределом 8 UBO:** `+ DM_GFX_ZEROCOPY=0 DM_GFX_SIM_GPU=ubdyn8` (как `nr7_c5b`). Те же `bad 0`; затем
   то же с `DM_NR_DIRECT=1` — картинка и строки NR-06 / NR-08 (`ring … bad 0`, `desc … served`) как в `nr7_c5b`.
3. **R-09R-c, включено, ABBA × 2 по 60 с:** A = умолчания, B = `DM_NR_DRAW=1 DM_NR_DIRECT=1`. Ждём в B: `[nr] direct: the engine's …
   pointers are the thunks …`, `[nr] direct (DM_NR_DIRECT=1 …): engine draws recorded directly ≈ 983 a frame …, NVN calls … not made ≈ 2
   000–2 800 a frame`, `left to the engine's function` ≈ 0; `[nr] draw: … served ≈ 99.7 %` как в `nr8_draw`; `[nb] check` / `[nb] rp` без новых
   расхождений; картинка та же. Сравнить `[cpuprof] threads`: `main` (цель ≤ 4.9–5.0 против 5.50 у `nr8_draw`), `nvn-translate`;
   строка `ns a direct draw` — куда уходит остаток (тап / состояние + запись / UBO движка).
4. **По частям (по желанию):** `DM_NR_DIRECT_PARTS=8` (только идентичность), `=9`, `=11`, `=15`.
5. **Стопка:** B + `DM_NR_LEAN=1 DM_NR_LEANCALL=1` (после их собственных сверок) — ожидание `main` ≈ 4.45–4.8.
Умолчание — только при `bad 0` во всех сверках (1, 2) и `main` в B не выше A.
