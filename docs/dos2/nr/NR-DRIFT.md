# NR-DRIFT — «после старта локации теряем 10–15 fps навсегда» (19.11, ночь, ветка `dos2-ndrift`)

Ветка `dos2-ndrift` от `dos2-night1119` (7780b92), worktree `wt-ndrift`. Телефона не было: всё ниже — разбор логов Mi 14 Ultra
(Adreno 750, Turnip 27, `TU_DEBUG=sysmem`), хост-тесты и сборка APK. Инструмент: `tools/dos2_drift.py`. KB: `performance.md` PERF-X24.

## 0. Ответ
**Кадры теряет не порт и не телефон, а динамическое разрешение игры (DRS) сразу после загрузки.** В первых кадрах после экрана загрузки
игра видит время GPU 26–55 мс (сборка конвейеров, заливка текстур, первые тени; строка `[quality] GPU frame time … max 29.12`), её
модель сразу прыгает на минимум (75–85 % высоты окна = 56–72 % пикселей) и поднимается обратно на 1,25 % в секунду. Первые ~20 с
после каждой загрузки идут на меньшем разрешении — 105–120 fps; когда DRS возвращается к 100 %, остаются настоящие 77–83 fps сцены.
Вернуться «на то же место с тем же видом» после этого — увидеть именно эти 77–83: прежние 110 были при 75–80 % разрешения.

У хозяина DRS включён в доке из шестерёнки (лог play-1118: `[java] dynamic resolution docked: DRS on, floor 75 %, target 60 fps
(gear), live`), цель 15,83 мс, игра без лимита кадров — ровно этот случай.

Что проверено и **не** растёт с временем игры (§2): ни один кэш / список / пул порта, ни цена кадра на CPU, ни GPU-время при
постоянном разрешении (3 мин 8 с стоя: 76,9 fps / 12,60 мс без наклона), ни память процесса. Тепло телефона (кожа 25 → 45 °C) на
уровень fps в 50–60 с прогонах не влияет. Что за пределами логов (часы GPU / памяти за 15+ минут) — теперь меряется (§3, проба).

## 3. Что сделано
### 3.1. `DM_DOS2_DRS_SETTLE` (`hle_dos2_quality.c`, политика `dm/gfx/nr/nr_drift.h`), умолчание 0
- `0` / не задан — как сегодня (лог: `DM_DOS2_DRS_SETTLE=0: load-time GPU spikes may drop the DRS…`).
- `1` (`1:<с>`, 1…60, по умолчанию 6 с) — пока открыт экран загрузки (у бэкенда < 64 draw за кадр в окне перф-отчёта: экраны
  загрузки DOS2 рисуют 13–15, 3D-меню ~1200, кампания 700–2500; или байт «off» объекта DRS) и ещё 6 с после него контроллер читает
  цель 100 мс — путь самой игры «DRS выкл.»: он не опускает разрешение. Потом снова обычная цель. Нормальная цель (лимит кадров,
  живая смена из шестерёнки) хранится отдельно (`g_tq`) и публикуется после удержания; страница цели вне удержания пишется как раньше.
- `2` — только счёт: окна открываются так же, удержания нет, в строке окна видно, куда DRS упал внутри него.
- Строка на окно: `[quality] DRS settle (DM_DOS2_DRS_SETTLE=1, 6.0 s after a load screen): window N closed, DRS S % at its start,
  lowest L % inside it, P % now; target T ms again; windows with a drop so far D of N`; в 10-с строке `GPU frame time` — `, settle hold`.
- Не бит в бит (картинка сразу в полном разрешении вместо 20 с на 75–80 %), поэтому умолчание 0. Работает при любом `DM_DOS2_DRS`,
  кроме `skip` (нужна наша копия цели); `off` (цель 100) — без изменений.

### 3.2. `[nr] growth` + проба часов GPU (`xbg_nr_growth.inc`, `DM_NR_GROWTH` / `DM_NR_GPUPROBE`, у DOS2 умолчание 1, у других игр 0)
Раз в `DM_NR_GROWTH_S` = 10 с (поток трансляции, из перф-отчёта):
```
[nr] growth (10 s, frame F, load 37 s ago, loads 2, level FJ_FortJoy_Main): sizes pipelines=… pipe_fast=… pod=… shaders=… programs=…
  layouts=… samplers=… sampler_fast=… passes=… lazy=… fbs=… images=… image_mb=… host_segs=… desc=… desc_free=… memo=… pinned=…
  spare_sets=… desc_pools=… img_cache=… texel=… epochs=… epoch_queries=… pend_reports=… pend_wb=… pend_img_wb=… pend_events=…
  retire=… occ_pools=… ts_pools=… arena_chunks=… zc_chunks=… zc_mb=… vcache=… vcache_mb=…; since load pipelines+12 images+3 …;
  walks retire cleanup 9.5 us a frame (600 frames); gpu alu 100.0 (5.000 ns/iter, 80 us, n 16384, runs 3, recal 1) copy 110 us 76.2 GB/s
  index 100.0 (runs 3); drs 100.0 % target 15.83 ms; thermal 0 headroom 0.41; mem rss 1650 MB; cpu MHz p0 … p2 … p5 … p7 …; cost 140 us
```
- **sizes** — все кэши / списки / пулы бэкенда, которые могли бы расти с временем игры; **since load** — разница с моментом, когда
  кончился последний экран загрузки (рост на загрузку = утечка на загрузку); **walks** — нс на кадр в уборке `retire_slot` (обходы
  отчётов / эпох / видов / наборов: если какой-то список растёт, этот кадр растёт вместе с ним).
- **gpu** — проба (`DM_NR_GPUPROBE=1`): раз в 5 с в начале одной отправки, вне прохода, по очереди: (а) цикл ALU (`xbg_nr_probe.comp`:
  4 цепочки FMA в регистрах, 8 × 64 потока, число итераций само подбирается на 40–400 мкс) между двумя метками BOTTOM_OF_PIPE, (б)
  копия 4 МБ → 4 МБ в памяти устройства между двумя метками; после каждой — полный барьер (работа игры не накладывается). Результат
  читается без ожидания в следующей строке. **alu index** 100 = частота GPU первой пробы, 80 = цикл идёт в 1,25 раза дольше (частоту
  сбросил DVFS / тепло); **copy GB/s** и его index — пропускная способность памяти (частота DDR / шины). sysfs у Mi 14 закрыт — эта
  проба единственный способ видеть частоты без root. Есть и sysfs: читаемые `kgsl` / `mali` / `/sys/class/devfreq/*` узлы пишутся в
  строку сами (на Mi 14 ожидаем «none», строка `[nr] growth: … nodes readable: none` один раз).
- **drs / thermal / mem / cpu** — высота DRS и удержание, статус и запас Android Thermal, RSS, `scaling_cur_freq` всех политик.
- Цена (логируется в каждой строке, `cost`): ~40 `.size()` + обход пары эпох и наборов + 8–10 чтений sysfs ≈ 0,1–0,3 мс раз в 10 с
  на потоке трансляции = ≤ 0,03 мкс на кадр в среднем; проба — один элемент 0,05–0,5 мс GPU раз в 5 с (≤ 0,0001 мс на кадр в среднем)
  + 8 МБ памяти устройства + один крошечный compute-конвейер. Таймер уборки — 2 чтения часов на кадр.

### 3.3. `tools/dos2_drift.py`
`python tools/dos2_drift.py <log> [<log> …] [--csv out.csv] [--all-sizes]` (logcat, `*.dm.log`, `boot.log` без меток времени):
по процессам и сегментам между экранами загрузки — fps / GPU первых и последних 10 с, DRS (мин / конец, сколько ниже 100 %), полка

частоты. `--self-test`.

## 7. Риски и что не сделано
- `DM_DOS2_DRS_SETTLE=1`: если сцена после загрузки и правда тяжелее цели, DRS опустит разрешение на 6 с позже. Признак загрузки —
  < 64 draw в окне 60 кадров; затемнённая сцена с < 64 draw тоже держит цель (дёшево, вреда нет).
- Проба: компьют-конвейер на старте (как GVAL / BC-декодер), 8 МБ; на драйверах, падающих в компиляторе на компьюте, — `gpguard`, при
  ошибке «GPU probe off» и всё. Метки BOTTOM_OF_PIPE на Turnip сериализуют — в кадре с пробой +0,05–0,5 мс GPU раз в 5 с.
- `VK_EXT_memory_budget` не читается: `vkGetPhysicalDeviceMemoryProperties2` не экспортирует прослойка драйвера (`vk_driver.c`).
- Утечек / неограниченного роста не найдено — чинить нечего; если D1 покажет `since load` с ростом на каждую загрузку, строка назовёт что.
- Не сделано: фильтр одиночных всплесков GPU-времени посреди игры (вход в новую зону, первые эффекты боя тоже роняют DRS на 6–8 с);
  делается кодовой пещерой на `ldr s16,[x9,#0x18f0]` (0xc05dcc, мин. из 2–3 кадров) — только если D1 / ходьба покажут частые провалы.

## 8. Раунд 2: `DM_DOS2_DRS_SPIKE` — один плохой кадр не роняет разрешение (19.11)
- **Зачем:** контроллер DRS игры опускает разрешение по **одному** кадру, если `цель − GPU < 0,5 мс` (сразу до размера своей модели, часто до
  пола), а подъём идёт 1,25 % в секунду. Вход в новую зону, первый кадр эффекта боя, сборка конвейера — 1–2 таких кадра, и 3D ~20 с мутнее.
  В ходьбе (C_base) DRS уходит на 91–92 % посреди прогона.
- **Как:** кодовая пещера на месте чтения GPU-мс контроллером: `main+0xc05dcc` (`ldr s16,[x9,#0x18f0]`) и три инструкции после неё
  (`mov x9,x20; ldr s0,[x9,#0x28]!; ldp w11,w12,[x9,#-0x20]`; ни одна ветка туда не ведёт — проверено capstone по всему контроллеру
  0xc05c80…0xc06a00) → `ldr x16,#8; br x16; .quad пещера`. Пещера: GPU-мс = минимум этого замера и 1–2 предыдущих замеров контроллера
  (`fminnm`, история в нашей странице данных), счётчики, три перенесённые инструкции, назад на `0xc05ddc`. Регистры: только x16, x17,
  s22…s25 и флаги — в контроллере они не читаются (capstone: он использует s0–s7, s16–s21, x0–x2, x8–x12, x19–x24), флаги через место не
  живут (до `fcmp` на 0xc05e18 их никто не читает). Продолжительная перегрузка всё равно опускает разрешение — на 1–2 оценки позже.
  Исходник пещеры — в комментариях `nrd_spike_cave` (`dm/gfx/nr/nr_drift.h`), собран NDK clang.
- **Переключатель:** `DM_DOS2_DRS_SPIKE` 0 / не задан — как сегодня; `2` — только счёт (контроллер читает сырое значение); `1` — применить;
  `:2` — минимум из 2 замеров вместо 3 (по умолчанию 3). Нужна наша страница данных (любой `DM_DOS2_DRS`, кроме `skip`). Строки:
  на старте `DM_DOS2_DRS_SPIKE=1 (NR-DRIFT): code cave at …`, раз в 10 с `[quality] DRS spike filter (…): evaluations over target so far N,
  of them one-off (the filter kept the size) M`. Слова места сверяются до вставки (другая сборка — красная строка, ничего не меняется).
- **Тесты:**
  - `nr_drift_test.c`: модель `nrd_spike_step` (один всплеск, пачка из 2 кадров при минимуме из 2 / 3, постоянная перегрузка проходит,
    счёт, NaN) + повтор контроллера в ходьбе: всплеск 30 мс каждые ~8 с, пачка 2 × 24 мс каждые ~13 с, тяжёлое место 17,5 мс с 40 по 46 с.
