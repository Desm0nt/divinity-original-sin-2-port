Ветка `dos2-vk`, HEAD `fbada69`. Только чтение кода и логов: ничего не собиралось, телефон не трогали. Все числа — из строк

## 0. Итог в десяти строках

1. Из 13.28 мс занятости потока записи **12.5 мс — исполнение записей draw** (4.15 мкс на вызов, 3015 вызовов за кадр); объявления
   констант, копии слотов, UI, конец кадра вместе — меньше 1–1.5 мс. Поток упёрт в процессор (12.7–12.9 мс CPU из 13.3), а не в ожидания.
2. Внутри draw: текстуры + набор 2.92 мс, команда draw (чистый Turnip) 2.95, конвейер 1.93, цепочка приёмов 1.93, буферы 1.75,
   поиск состояния 0.69. Наше — около 8 мс, драйвер — около 4–4.5 мс **[оценка]**; точнее покажет `DM_VK_NATIVE_PROF=3` (раздел 2.4).
3. Тот же код на потоке записи **дороже, чем на потоке движка**: 4.29 против 3.63 мкс на draw при равном потолке частот (У2 против У4),
   то есть +2 мс за кадр. Причина по коду — общие замки и общие строки кэша двух потоков (буферы, текстуры, счётчики очереди).
4. Самое дешёвое и самое выгодное: убрать замки и повторные поиски из пути draw (куски Р1–Р3, 5–6 агент-часов) — **−2.2…−3.2 мс**.
5. Далее: цепочка приёмов по классу прохода и хэш констант на потоке движка (Р4, −0.6…−0.9 мс; под моделью Mali −2 мс).
6. Наборы дескрипторов менять не нужно: строится 16 наборов за кадр. Push descriptor, descriptor buffer, шаблоны, вторичные
   командные буферы на одном потоке, multi-draw — **не окупаются** и сейчас (раздел 3.6).
7. Сортировка (бывший `DM_NR_SORT`) и динамическое состояние теперь окупаются лучше, но это −0.3…−0.9 мс за 3–4 часа: делать после
   счётчика «чем отличаются соседние конвейеры» из Р0.
8. Два потока записи возможны (несколько первичных командных буферов кадра, без вторичных), но это 8–12 часов и риск гонок;
   на Mi 14 они ничего не дадут сверх Р1–Р4 — кадр упрётся в GPU (12.6 мс). Отложить до настоящего слабого телефона.
9. Ожидание на Mi 14: поток записи 13.3 → 9.5–10.5 мс, кадр упирается в GPU: **74.5 → 78–79 к/с** холодным, 66–72 → 78 горячим;
   в ходьбе (У15, 19.8 мс) — около 50 → 65–68 к/с **[оценка]**.
10. Слабые устройства: там поток записи — потолок процессора (27–40 мс на классе Snapdragon 7, 40–60 мс на Mali со штатным
    драйвером **[оценка]**), и каждый сэкономленный процент работы потока — тот же процент к/с в сценах, упёртых в процессор.

### 2.3 Почему тот же код на потоке записи дороже (У2 против У4, потолок 1.92 ГГц у обоих)

| Часть, мкс на вызов | U04 (на потоке движка) | U02 (на потоке записи) | Разница |
|---|---|---|---|
| flush + fill (остались на потоке движка) | 0.38 | 0.00 | −0.38 |
| state | 0.11 | 0.27 | +0.16 |
| fx | 0.63 | 0.76 | +0.13 |
| buffers | 0.41 | 0.57 | +0.16 |
| tex+set | 0.82 | 0.98 | +0.16 |
| pipeline | 0.57 | 0.63 | +0.06 |
| draw-cmd | 0.60 | 0.97 | **+0.37** |
| всего | 3.63 | 4.29 | +0.66 (≈ 2.0 мс за кадр) |

Причины по коду (первые три — доказуемы чтением, четвёртая — гипотеза):

1. **Замок буферов берут оба потока на каждый draw.** Поток движка: `mark()` → `vkn_buf_mark` + `vkn_buf_lookup` (`vkn_rt.c:455–461`).
   Поток записи: `vkn_buf_lookup` и `vkn_buf_get_n`. Один `g_mu` (`vkn_buf.c`), строка кэша с замком гуляет между ядрами.
   При этом проект потока (VK-STAGE55-THREAD, раздел 2) обещал «в запись идут блок и версия» — в `op_draw` (`vkn_rt.c:445`)
   блоков нет, поток записи ищет заново.
2. **Замок текстур — на каждую текстурную привязку каждого draw** (в среднем 5.7 привязки на шейдер: 3260 привязок на 572 шейдера,
   строка `shaders`), по два захвата на привязку. Быстрый путь `tex_bind_draw` помнит только **один** последний шейдер
   (`g_te`, `vkn_draw.c:343`) и срабатывает редко: `texture bindings reused 2 267 496 / looked up 17 062 633` — 12 %.
3. **Чтение записей с чужого ядра** (2 МБ за кадр) и счётчики очереди в общей строке кэша (2.2).
4. **draw-cmd +0.37 мкс не объяснён.** Это чистый вход в Turnip; гипотезы: гонка за общий кэш третьего уровня с работающим
   одновременно потоком движка, доля главного ядра (в U04 поток движка 34 % времени был на главном ядре, поток записи — 0–10 %).
   Разделит замер из 2.4.

### 2.4 Чего не хватает: `DM_VK_NATIVE_PROF=3`

Сейчас «tex+set», «pipeline», «buffers» смешивают наш поиск и вход в драйвер, а не-draw записи не меряются вовсе. Режим 3
(только выборка 1 из 128, как сейчас; при 1 и 2 поведение прежнее):

- **в `prepare()`** новые метки: поиск текстур / `vkn_pass_sample` / сборка ключа набора / поиск набора / `vkCmdBindDescriptorSets`;
  ключ конвейера / поиск / `vkCmdBindPipeline`; поиск буферов / `vkCmdBindVertexBuffers` + `vkCmdBindIndexBuffer`; в draw-cmd — скобки
  запросов отдельно от `vkCmdDraw*`. Итог одной строкой: `draw by part 3: ... ; driver X.XX ms a frame (calls N), ours Y.YY ms`;
- **в `vkn_fx_run`** время по функциям цепочки (массив на `VKN_FX_CHAIN`): `fx by function: shcache 0.41, mat 0.08, ...`;
- **в `exec()`** (`vkn_rt.c:724`) время по видам записей на выбранных записях: draw / объявления / слоты / вызовы по функции
  (UI draw, цели, очистки, запросы) / конец кадра: строка `rt by record`;
- **счётчик «чем отличается новый конвейер от предыдущего»** в `vkn_draw.c:843` (XOR полей `vkn_pipe_desc`): шейдер / формат вершин /
  глубина-трафарет / растеризация / смешивание / опорное значение трафарета / варианты / проход. Решает судьбу сортировки и
  динамического состояния (3.4);
- **счётчик замков**: сколько раз `pthread_mutex_trylock` не взял замок с первого раза в `vkn_buf.c` и `vkn_tex.c` на потоке записи.

Что покажет: долю драйвера (ожидаю 4–4.5 мс), долю поиска текстур (ожидаю 1–1.5 мс из 2.92), кто в цепочке приёмов дорог
(ожидаю кэш теней), сколько стоит UI. Плюс без кода: `tools/perf_run.sh grab` (simpleperf, dwarf) на поток `vkn-record` 10 с — плоский
профиль с именами функций Turnip; это прямой ответ на пункт 4 из 2.3.

## 3. Что удешевляет поток записи

### 3.1 Убрать замки и повторные поиски (главное)

| Приём | Суть | Точность | Ожидание, мс потока записи |
|---|---|---|---|
| **Блоки буферов из записи** | поток движка уже разрешает буферы при записи (`mark()`); положить в `op_draw` готовые `{VkBuffer, смещение}` потоков вершин и индексного буфера (+ размер индекса, размер) и не искать их на потоке записи | вид таблицы у потока движка в момент записи равен виду потока записи в момент исполнения — на этом стоит порядок записей `commit_fn` (`vkn_buf.c:291`); блоки живут 3 кадра после замены | −0.6…−0.8 (buffers 1.75 → ≈ 1.0) |
| **Шейдер и номера состояний из записи** | `shader_lookup` и четыре `state_id` — на потоке движка, в запись идут указатель и номера | уничтожение шейдера — точка синхронизации (`DestroyShaderIfOld`), объект живёт 3 кадра; у состояний уничтожений нет (`state: ... 0 destroys`) — добавить синхронизацию в `vkn_*_kill` | −0.4…−0.5 (state 0.69 → ≈ 0.2), потоку движка +0.2 |
| **Зеркало «номер пула → вид, текстура, сэмплер» без замка** | своя таблица потока записи, ячейка годна, пока не изменился `vkn_tex_bind_gen()` (то же условие, что у `tex_bind_draw`, `vkn_draw.c:434–440`); при несовпадении — прежний поиск под замком и обновление ячейки | поколение меняется при любой смене того, что называет номер | −0.5…−0.8 |
| **Память привязок по шейдеру, а не одна на всех** | `g_te` → таблица на 64 шейдера по 2 записи: пары (номер текстуры, номер сэмплера) → готовые элементы, ключ, набор | условия прежние (`tex_bind_draw`), `vkn_pass_sample` по-прежнему зовётся для каждой текстуры | −0.4…−0.6 (вместе с предыдущим tex+set 2.92 → 1.6–2.0) |
| **Очередь без общей строки кэша** | `g_pushed`, `g_done`, `g_wait_*`, счётчики — по своим строкам (`alignas(64)`); `g_done` публикуется в конце пачки или когда кто-то ждёт (`g_wait_done != 0`); счётчики `ST_ADD` потока движка — обычные, не атомарные, сводка читает с опозданием | порядок исполнения не меняется; ожидающий по-прежнему выставляет цель до проверки | −0.2…−0.4, столько же потоку движка |
| **Не писать пустые записи** | начало / конец запроса при выключенном учёте (`g_track == 0`) считать на потоке движка; объявление блока с теми же смещением и размером, что уже объявлены (`g_eubo`, `vkn_rt.c:383`), не писать | `vkn_draw_ubo` для такого объявления меняет только счётчик | −0.1…−0.2 |

Сумма: **−2.2…−3.3 мс** при 5–6 агент-часах. Всё это чистая экономия процессора — помогает и слабым устройствам, и горячему Mi 14.

### 3.2 Наборы дескрипторов: кэш уже работает, менять механизм не нужно

- `sets built 16` за кадр стоя (174 в ходьбе) при 1915 привязках: создание и обновление наборов — не цена. Цена — сборка ключа и
  поиск (3.1) и сама привязка в драйвере.
- **Привязка набора в Turnip дорога из-за динамических смещений:** на каждый `vkCmdBindDescriptorSets` он копирует по 64 байта на
  каждый динамический дескриптор, выделяет память и копирует их ещё раз целиком, взводит «константы шейдера грязные»
  (`tu_cmd_buffer.cc:5112–5258`), а на draw пишет `SP_UPDATE_CNTL(gfx_bindless = 0xff)` (`:5011–5090`) — это же стоит и GPU
  (PERF-X26: 0.3–1.0 мкс GPU на перепривязку **[оценка]**). У нас динамические **все** блоки всех шейдеров: строка `shaders: dynamic
  all / engine blocks / none: 572 / 0 / 0` — в среднем 10.6 блока на шейдер, из них 4.4 (SUPPORT и C1) не меняются никогда.
- **Проверить без кода:** правило «динамические только блоки движка» уже есть (`vkn_shader.c:330`, включается `DM_GFX_UBO_DYNAMIC=2`,
  `vkn_policy.h:117`). Один прогон на Adreno: копий в Turnip на привязку станет на ~40 % меньше; число наборов вырасти не должно
  (SUPPORT зависит только от размера вьюпорта). Ожидание −0.2…−0.5 мс потока и, возможно, немного GPU; смотреть `sets built`
  и строку `shaders`.
- **`VK_KHR_push_descriptor`** (в Turnip есть, `tu_device.cc:277`): каждый draw платил бы запись всех дескрипторов вместо поиска
  готового набора; в Eternal подозревался в ~20 мкс на draw (PERF-E18). **Отказ.**
- **`VK_EXT_descriptor_buffer`** (есть, `:332`): по исходникам Turnip на draw стоит столько же, сколько обычная привязка, а блоки
  констант перестают быть «предсказуемыми» для компилятора шейдеров (PERF-E20). **Отказ на Turnip.**
- **Шаблоны обновления:** экономят на 16 (174) построениях за кадр — до 0.2 мс в ходьбе. Не сейчас.
- **Сброс всего кэша наборов при любой смерти текстуры** (`death_check` → `forget_now`, `vkn_draw.c:273–293`): 396 сбросов на
  12.7 тыс. кадров стоя — раз в 32 кадра пересобирается ~500 наборов (рывок ≈ 1 мс **[оценка]**); в ходьбе это и есть 174 набора за
  кадр ≈ 0.4–0.5 мс. Точечное выселение (у записи кэша — список её текстур) — отдельный кусок на 2 часа, после Р3.

### 3.3 Цепочка приёмов: 1.93 мс (модель Mali — 3.76 мс)

- Все функции зовутся на каждый из 3015 draw (`vkn_fx.c:68`). Большинству нужен один класс проходов: кэшу теней — атлас глубины,
  посту — цели поста, слитому свету — проход света. **Фильтр по классу набора целей:** функция при регистрации называет маску
  классов; класс считается один раз на смену целей (`vkn_pass_targets`), а не на draw.
- **Хэш констант кэша теней** (`vkn_shc.c:439–486`, 994 КБ за кадр) считается на потоке записи по памяти, которую только что писал
  поток движка на другом ядре. Считать его там, где блок копируется в кольцо (`hle_dos2_vkn_draw.c:205`, `:245`), и нести в записи
  объявления (в `ubo_e` есть 4 свободных байта, нужно 8 → запись 24 байта). Потоку движка +0.15…0.3 мс, потоку записи −0.3…−0.6 **[оценка]**.
- Точное распределение даст строка `fx by function` из Р0; без неё не начинать.

### 3.4 Меньше смен состояния: сортировка, динамическое состояние, multi-draw

- **Факт:** 1317 смен конвейера на 2125 draw при всего 235 конвейерах — то есть в основном чередование A-B-A. В ключе конвейера сидит
  даже опорное значение трафарета (`vkn_state.h:138`), а динамических состояний два: вьюпорт и ножницы (`vkn_state.c:693`).
- **Цена смены конвейера на потоке записи** ≈ 1.0–1.4 мкс нашей части + 0.3–0.5 мкс в команде draw (Turnip заново выгружает
  группы состояния) **[оценка; KB: 1.4–1.8 мкс в Eternal]**.
- **`DM_NR_SORT` заново.** Отвергали при +0.7 к/с, когда кадр стоял в GPU. Теперь экономия идёт в упёртый поток: по счёту NR-21 в
  проходах «только глубина» конвейеров 673 → 64, вершинных привязок 1025 → 619. При цене 1.3–1.8 мкс за смену это **−0.8…−1.0 мс в
  ходьбе**, стоя −0.3…−0.4 (кэш теней уже убирает 63 % draw теней). Но в новом бэкенде сортировки нет — писать заново: окно из
  подряд идущих записей draw одного набора целей «только глубина», снимок объявленных блоков на draw, условия NR-21 (одна функция
  LESS / LEQUAL, без трафарета и смешивания, без открытого запроса). 3–4 часа + режимы сверки и яда. **Да, но после Р1–Р4.**
- **Динамическое состояние** (`VK_EXT_extended_dynamic_state` 1–3 и `VK_EXT_vertex_input_dynamic_state` в Turnip есть,
  `tu_device.cc:340–342`, `:412`). Убирает смены конвейера только там, где соседи отличаются глубиной-трафаретом, растеризацией,
  опорным значением. Если отличаются шейдером — ноль. **Решает счётчик из Р0**; при доле таких смен ≥ 30 % — −0.3…−0.6 мс за 2–3 часа,
  иначе не делать. На штатных драйверах Mali выигрыш от меньшего числа вызовов втрое больше (вызов 1.2–1.8 мкс, PERF-X10).
- **Multi-draw / `NR-MDI`:** по-прежнему нет. Turnip на каждый draw пачки делает то же, что на отдельный (`tu_cmd_buffer.cc:9632`),
  а наши соседние draw отличаются смещениями блоков — склеить можно только с переписанным вершинным шейдером (`блок[gl_DrawID]`),
  пачки в среднем по 1.8 draw. Экономится один вход в функцию. **Отказ остаётся.**
- **Вторичные командные буферы на одном потоке:** лишняя работа, состояния после `vkCmdExecuteCommands` всё равно привязывать заново.
  Имеют смысл только для параллельной записи (раздел 4).

### 3.5 Интерфейс (UI): набор на каждый draw

246 draw × (выделение + обновление набора) ≈ 0.4–0.7 мс **[оценка]**. Кэш наборов по содержимому, как у игровых draw (текстур у UI
мало), — 1–2 часа, −0.3…−0.5 мс. Делать, если Р0 подтвердит цену.

## 4. Два потока записи

**Как это можно сделать правильно.** Не вторичные буферы внутри прохода (тогда проход обязан состоять только из них, а ведущий поток
всё равно ждёт), а **несколько первичных командных буферов кадра**: кадр режется на куски по границам проходов, каждый кусок пишет
один из двух потоков в свой буфер, `vkQueueSubmit` получает их массивом по порядку. Vulkan и Turnip это умеют без оговорок
(`VK_EXT_nested_command_buffer` тоже есть, `tu_device.cc:372`, но не нужен).

**Что мешает — не Vulkan, а наш бэкенд,** он весь на правиле одного потока:

- состояние между кусками: объявленные блоки констант и массивы слотов «живут дальше» — начало куска 2 зависит от конца куска 1.
  Решаемо предварительным проходом по записям (объявления и слоты дёшевы), ≈ 0.2 мс;
- **раскладки изображений** (`vkn_tex->layout`, `vkn_pass.c`): кусок 2 должен знать, в какой раскладке оставил текстуры кусок 1.
  Нужна либо предсказанная раскладка на границе с проверкой, либо отдельный буфер переходов между кусками;
- статические таблицы `vkn_draw.c` (`g_b`, `g_ubo`, `g_el`, `g_kw`, кэш наборов и пулы), состояние приёмов (кэш теней, слитый свет,
  пост, сверки покрытия) — всё это надо сделать «на поток» или оставить одному потоку целиком;
- пулы дескрипторов и кэш конвейеров — под замок или на поток.

**Цена:** 8–12 агент-часов в 3–4 куска плюс хост-тест под ThreadSanitizer, плюс серия прогонов сверки. Риск — гонки и тихая порча
картинки, которую сверки внутри прогона (`RT=9`) не ловят.

**Что даёт:** время стены ≈ 55–60 % от одного потока (куски неравные). На Mi 14 после Р1–Р4 это ничего не меняет — кадр стоит в GPU.
На слабых устройствах выигрыш съедает нехватка больших ядер: у игры уже три нагруженных потока (7.4–7.8 мс каждый) плюс поток
записи = 3.2 ядра (`process 42.33 ms CPU a frame (3.19 cores)`), а у Snapdragon 7 и Dimensity 8100 больших ядер четыре, у Helio G99 — два.
Пятый занятый поток сядет на малое ядро (втрое медленнее) или вытеснит поток игры.

**Вердикт:** не сейчас. Вернуться, если на настоящем слабом телефоне после Р1–Р5 поток записи останется узким местом при свободном
большом ядре. Тогда первым куском резать самый отдельный проход — карту теней (свой набор целей, ничего не читает).

## 5. Что перенести с потока записи или не делать вовсе

- **На поток движка (у него 4.9 мс простоя в кадре):** разрешение буферов (уже там — только донести), поиск шейдера и состояний,
  хэш констант для кэша теней. Это пункты 3.1 и 3.3. Цепочку приёмов, проходы и наборы переносить нельзя — они читают состояние записи.
- **Не делать вовсе:** пустые записи запросов и повторные объявления (3.1); синхронизации уничтожения текстур и уменьшения мипов в
  ходьбе — заменить записью «уничтожить на потоке записи в этой точке» по образцу `vkn_rt_retire` (`vkn_rt.c:357`). Это снимает
  3.9 мс ожиданий потока движка за кадр в ходьбе (U15r); станет важным, как только поток записи перестанет быть самым медленным.
- **Draw, которые ничего не меняют:** 890 пропускаемых за кадр draw всё равно проходят запись, объявления и state + fx
  (≈ 0.5–0.7 мс на потоке записи и загрузка констант на потоке движка). Решить пропуск при записи нельзя — решение зависит от
  состояния кэша теней на потоке записи; точного дешёвого способа нет. Оставить.
- **Повтор одинакового состояния:** привязки уже отсекаются сравнением с `g_b`; ключ набора «тот же, что у прошлого draw» — 30 %
  случаев (`same key as before 5 750 241` из 19.3 млн). Дальше — только сортировка (3.4).

## 7. Что это значит в к/с

**Mi 14 Ultra.** После этапов А и Б поток записи ниже 12.6 мс при любом потолке частот, кадр упирается в GPU (12.6–12.7 мс):

| Сцена | Сейчас | После А + Б **[оценка]** | Что ограничивает |
|---|---|---|---|
| стоя, холодный (U02h) | 74.5–75.2 | 78–79 | GPU 12.6 мс |
| стоя, горячий, потолок 1.7–1.9 ГГц (У2b, У7) | 66–72 | 76–79 | GPU |
| стоя, модель Mali (U13r, поток 16.0) | 62.4 | 74–78 | GPU / поток ≈ 12–13 мс |
| ходьба, модель Mali (U15r, поток 19.8, 3514 вызовов) | 49.6–53.6 | 62–68 | поток ≈ 14–15 мс и GPU 12.9–14.7; с Р5 — GPU |

То есть на Mi 14 стоя выигрыш мал (+4–5 к/с), потому что GPU сразу за потоком; настоящая польза — в ходьбе, в нагреве и в запасе:
дальше к/с растут только от экономии GPU. Попутный кандидат на GPU — меньше перепривязок динамических наборов (3.2).

**Слабые устройства** (правило хозяина — столбец обязателен; чисел с таких телефонов для нового бэкенда нет, всё **[оценка]**):

|---|---|---|---|

## 9. Что не доказано

- Доля драйвера (4–4.5 мс) и доля замков — оценки по числу вызовов и по коду; замер Р0 может переставить Р3 и Р4 местами.
- Почему команда draw на потоке записи на 0.37 мкс дороже, чем на потоке движка (2.3, пункт 4).
- В U02h большие ядра шли на 2.13 ГГц при потолке 3.15 ГГц и потоке, занятом на 97 % (`policies ... p2 614/2131/3148`,
  `uclamp.min 0/eff 0`, `ADPF ... limited 723`); главное ядро почти свободно (1.31 ГГц в среднем, поток записи на нём 0 %).
  Что держит частоту — неизвестно (похоже на ограничение HyperOS), обещать от этого ничего нельзя. Поток записи в сеансе ADPF уже
  есть (строка `threads ... vkn-record`), запись в VK-NATIVE-STATUS «не входит в сеанс» устарела.
- GPU 12.6 мс принят за потолок; есть ли запас частоты GPU — в логах не видно (нет строки частоты GPU).
- Цифры для слабых устройств — пересчёт с Mi 14, а не замер.
