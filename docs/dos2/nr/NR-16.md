# NR-16 — атрибуция CPU: один прогон телефона отвечает, куда уходит CPU (17.11.2026, ветка `dos2-nr16`)

Шаг из аудита `docs/dos2/nr/AUDIT-REMAINING.md` (ветка `dos2-nraudit`), §1 NR-16. Сегменты S9 / S5. Основа для NR-17 (потоки по ядрам),
NR-21 (сортировка draw), NR-23 (`DM_NR_NOCALL`), NR-24 (`DM_HLE_FASTGATE`) и для решения по `DM_NB_MX` / `DM_GFX_PRESENT_THREAD`.
Только ПК: телефон не трогался, APK не ставился.

## 1. Что сделано
Всё выключено по умолчанию; приложение ни один из ключей не ставит (`jni_android.c` не тронут; проверяет `source_structure_test.py`).
Шаг только измеряет — поведение игры при любом значении то же, поэтому режимов `=2` (сверка) и `=3` (poison) у него нет.

| Ключ | Значения | Что делает |
|---|---|---|
| `DM_NR_CPU` | **0** / 1 | 1: с первого present — поток `dm-cpuprof` (nice 10, без привязки к ядрам) раз в `DM_NR_CPU_MS` (200 мс) читает у каждого потока `/proc/self/task/<tid>/schedstat` (нс на CPU и нс в очереди готовых) и, если поток работал, ядро из `stat` (поле 39); `/proc/stat` (занятость ядер; приложению может быть закрыт SELinux — тогда «busy -») и `scaling_cur_freq` / `scaling_max_freq` каждой политики cpufreq. Каждый вход в ворота HLE считается по потоку и виду (svc / часы / obs), каждый SVC — по номеру со временем (`cntvct`); один круг через ворота измеряется своими «пробными» воротами (`dm_gate_probe`, entry.S). Глобальный замок `G` (`hle_thread.c`) — взятия, взятия «занят» с ожиданием, время удержания. В трансляторе — CPU потока против стены у подачи и present, CPU рабочего `DM_NB_MX`, GPU подач и промежутки между ними, проходы по сигнатуре со сменами пайплайна |
| `DM_NR_CPU_MS` | 50…2000 (200) | период выборки потоков |
| `DM_NVN_PROF` | **0** / 1 / 2 | 2 (новое): выборочный замер NVN на потоке, который подаёт работу (поток записи игры). Каждый реализованный слот, кроме `nvnQueuePresentTexture`, идёт через `nvn_prof2_entry` (nvn_entry.S) — для DOS2 **под** обёрткой большого стека. Вне окна и на других потоках — сравнение `tpidr_el0` и переход (несколько нс). Окно = один интервал «конец `nvnQueueSubmitCommands` → конец следующего» из `DM_NVN_PROF_EVERY` (16): каждый вызов NVN этого потока со временем (`cntvct`) и счётом, CPU потока и стена интервала. Постоянная цена замеренного вызова (калибровка через слот-пустышку при установке) вычитается. 1 — старая обёртка, оставлена как была (см. §3.1) |
| `DM_NVN_PROF_EVERY` | 1…1024 (16) | один замеряемый интервал из N |
| `DM_SLEEPSTAT` | 0 / 1 | есть (hle_thread.c): раз в 5 с по потокам с > 500 SleepThread — уступки / сны по длине, доля времени, вызывающие (`main+0x15ee898` и т. п.) |
| `DM_FS_STATS` | 0 / 1 | есть (hle_fs.c): раз в 5 с чтения игры — число, МБ, среднее / максимум задержки, > 20 мс. Для отдельного прогона загрузки |

| `[cpuprof] hle svc (…): 0x0b SleepThread* 120.0 x 30.1 = 3.612; … \| G: T takes a frame, P% found it held, waited W us a frame (longest L us), held H us a frame` | `dm-cpuprof` | SVC на кадр: число × мкс = мс (`*` — ждут по смыслу); замок `G` | NR-24 (б) |

| `[cpuprof] gfx (…; DM_NB_MX=… DM_GFX_PRESENT_THREAD=… DM_NB_MT=…): translation thread a frame: submit wall A ms CPU B ms (waited …), present wall … CPU …; MX worker CPU …; GPU a frame: engine submissions G ms, between them J ms (present blits + idle; …)` | транслятор | стена ≠ CPU: сколько поток трансляции работает и сколько ждёт; GPU-упор: fps = 1000 / (G + J) | **A/B MX / PT** |
| `[cpuprof] passes (…, a frame): … pipeline binds (S if every pass were sorted by pipeline), … set binds, … draws counting samples; order-free (…): FP passes, FD draws, FB binds -> FS sorted = D binds saved a frame` + `[cpuprof] passes by signature …` | транслятор | смены пайплайна и наборов по проходам; «order-free» = кандидаты NR-21 (глубина без цвета, одна функция LESS / LEQUAL на весь проход, без stencil, пишет глубину или считает сэмплы) | **NR-21** |

## 3. Находки без телефона
### 3.1 `DM_NVN_PROF=1` на Android не работал ни разу
Обёртка ставилась конструктором библиотеки (`nvn_nops_register`), а `dm/env` применяется в `nativeStart` — после загрузки `libdm.so`;
`getenv("DM_NVN_PROF")` в конструкторе на телефоне всегда NULL. Если бы ключ сработал (переменная в окружении процесса), он сломался бы
на DOS2: обёртка большого стека (D3-линия, по умолчанию вкл.) вызывает реализацию с `x16 = номер слота`, а старая обёртка ждёт адрес слота.
Отсюда «`DM_NVN_PROF` есть, не запускался» в аудите. Режим 2 ставится в `nvn_lookup` (после env), под обёрткой большого стека,
и принимает оба вида `x16`. `=1` оставлен для Mac-хоста как был.

### 3.2 «Поток игры 4.9 мс» в аудите — это поток present, а не поток записи
`[nvn] 主线程 至帧 …` меряет CPU того, кто зовёт `nvnQueuePresentTexture` (h1def: tid 28031, rd1: 10934). 14.6 тыс. вызовов NVN и все
записи делает **другой** поток: `[nvn] recording thread 28033 … 6250515 records … 1056 submits` (h1def), `10936` (rd1). Цена HLE NVN
(NR-23) и роль «рендер» (NR-17) — про поток `rec`; новые строки показывают оба потока раздельно (`rec`, `pres,main`).
Попутно: `NVN present thread started … inherited cpus=80` — present thread унаследовал привязку трансляции к cpu7 (X4) и сам
перекладывается (`place()`), это увидит строка threads.

### 3.3 `DM_NB_MX=1` (по умолчанию вкл.): стоит, не даёт
Логи 16–17.11 (Mi 14 Ultra, палуба, без лимита). В каждом прогоне две фазы: без лимита (~105–108 fps) и **ровно 89.7–89.9 fps** —
дисплей на 90 Гц (вывод NR-11). Сводки `sum.txt` смешивают фазы; ниже — медианы окон `NVN PERF v=1` с draws > 800 по фазам
(скрипт `tools/dos2_cpuprof.py --ab` делает то же).

| Прогон | Ключи | Окон без лимита / 90 Гц | fps без лимита | GPU мс | submit + present, мс |
|---|---|---|---|---|---|
| d0base | NB=1 | 214 / 1 | 107.9 | 8.41 | 5.55 + 3.62 = 9.17 |
| d1prof | NB=1 MT=1 MX_PROF | 243 / 1 | 108.2 | 8.39 | 5.33 + 3.81 = 9.14 |
| **d3mx** | NB=1 **MX=1** | 100 / **92** | **106.6** | 8.42 | 7.63 + 1.67 = 9.30 |
| **d4mxmt** | NB=1 **MX=1** MT=2 | 62 / **324** | **106.5** | 8.49 | 6.45 + 2.83 = 9.28 |
| d5base | NB=1 | 30 / 48 | 96.5 (нагрев: GPU 9.34) | 9.34 | — |

- «106.3 → 97.2 fps» — в основном **фаза 90 Гц** (в d3mx 92 окна из 192, в d4mxmt 324 из 386). В одной фазе MX стоит **−1.3…1.7 fps
  (≈ −1.2…1.6 %)** при том же GPU: кадр +0.11–0.15 мс.
- Это ровно цена передачи: `[nb] mx … worker ran 7.20 ms, the translation thread waited 7.57 ms` — **ожидание − работа = 0.31–0.36 мс
  на подачу** без `DM_NB_MT=3` и **0.08–0.10 мс** с `MT=3` (g1all, h1def, rb1, rd1, rd2: 8.83 / 8.91 … 12.21 / 12.31), плюс перенос контекста
  0.013–0.03 мс (27 переменных, 43.7 КБ). Подача ≈ 1 на кадр → **+0.1…0.4 мс на критическом потоке трансляции**, рабочий и поток
  трансляции по очереди будят друг друга, кеш L1 / L2 рабочего холодный (не мерено — это даст `CPU` в новой строке `[nb] mx`).
- Выигрыша нет по устройству: режим 1 — **последовательное** продолжение (комментарий `xbg_nb_mx.inc`: «it proves the context
  mechanism … it is not faster»), а параллельная трансляция отвергнута (NB-20b, PERF-E18: −0.2…0.3 мс при 3–4 заходах правок).
- Слабые CPU [м]: на A76 / A55 пробуждение чужого потока 20–80 мкс, при упоре в CPU транслятора +0.2…0.8 мс / кадр прямо в кадр; на
  4+4 рабочий, наследующий маску трансляции, делит с ней те же большие ядра.
- **Вывод:** держать `DM_NB_MX=1` по умолчанию нет причины; рекомендую снять его из `k_nb_on` (решение главной сессии / хозяина, здесь
  умолчания не трогал). Подтверждает A/B ниже: ожидаем `translation submit wall` −0.1…0.35 мс, `process CPU` −(CPU `dm-nbx0` − прирост
  CPU `nvn-translate`) ≈ 0, `GPU busy + gaps` без изменений, fps +1…1.5 % в фазе без лимита.

### 3.4 `DM_GFX_PRESENT_THREAD=1` (по умолчанию вкл.): нейтрален на Mi 14, решает CPU-упор
| Прогон | Ключи | fps без лимита | submit + present, мс | present thread busy, мс |
|---|---|---|---|---|
| f0base | NB=1 | 105.7 | 5.70 + 3.59 = 9.29 | — |
| f1pt1 | NB=1 **PT=1** | 107.0 | 9.05 + 0.11 = 9.16 | 3.66 |
| f3pt2 | NB=1 PT=2 (протокол без потока) | 106.2 | 5.69 + 3.59 = 9.28 | — |
| e1mt3 / e5mt3 | NB=1 MT=3 | 107.2 / 107.1 | 4.29 + 4.96 = 9.25 | — |
| f2pt1mt3 | NB=1 **PT=1** MT=3 | 107.2 | 8.83 + 0.35 = 9.18 | 5.01 |
- В одной фазе PT не хуже (105.7 → 107.0; с MT=3 107.2 = 107.2), «100 → 97» — смесь фаз (как нашёл NR-11). Сумма стен трансляции
  ≈ кадру во всех вариантах: поток трансляции и есть «метроном» кадра, ожидание GPU просто переезжает из present в submit
  (`submit_cpu_ms` — это **стена**, `timing_clock` вокруг `xbg_submit_now`, а не CPU). На GPU-упоре PT ничего не меняет.
- Что PT переносит: тело present (ожидание забора кадра, acquire, letterbox / RCAS, blit, `vkQueuePresent`) — `busy_ms` 1.1–5 мс
  **стены** на `dm-present`; сколько из этого CPU — не мерено. Если CPU-часть ≈ 0.3–1 мс, на CPU-упоре (S7 / MTK [м]) это −0.3…1 мс с
  критического потока трансляции; цена — пробуждение `dm-present` и замок очереди на каждой подаче.
- **Вывод:** оставить; решающий A/B — ниже (`present CPU` на трансляции, CPU `dm-present`, `GPU gaps`).

### 3.5 Смены пайплайна (для NR-21) по имеющимся логам
`[nb] pipe`: `previous draw 804 801` из 1 350 142 попаданий (rd1, 60 %), 431 317 из 892 928 (аудит, 48 %) — 40–52 % draw меняют ключ
пайплайна (≈ 460–600 смен на кадр при 1155 draw). По проходам не разложено — это даёт новая строка `[cpuprof] passes` (сколько из них в проходах только глубины).

## 6. Риски
- `/proc/stat` приложению закрыт на многих Android 8+ (SELinux) — строка cores покажет `busy -`, частоты останутся; per-thread данные
  из `/proc/self` доступны всегда. `schedstat` может не быть на ядрах без `CONFIG_SCHED_INFO` — тогда тики `stat` (10 мс, «stat ticks»
  в заголовке строки), ожидание очереди 0.
- Ядро потока («где работал») — по полю 39 в момент выборки, взвешено CPU с прошлой выборки: приближение (200 мс).
- Окно NVN: если подают два потока, сопровождается первый (другой игнорируется, пока первый активен < 2 с); строка `the submitting
  thread is now …` при смене. Вызовы, ждущие GPU / дисплей, вынесены отдельно, но ожидание внутри «рабочих» вызовов (замок трансляции
  при полной очереди) попадёт в NVN-время — его покажет топ-12.
- `cntvct` 19.2 МГц = 52 нс на тик: отдельный вызов не разрешается, суммы по тысячам вызовов несмещённые; пол обёртки вычитается.
- Обёртки `G` меняют `lock` на `trylock + lock` только при `DM_NR_CPU=1` (честность замка та же у bionic).
- Пробные ворота регистрируются во время работы игры (вставка в пустой слот хэша; цепочки существующих ворот не меняются).

## 8. Прогон на телефоне (главный агент, по разрешению хозяина; один APK для NR-14…19)
Перед каждым прогоном: бэкап `files/save`; `dumpsys window` — нет keyguard; без лимита кадров; после логов — force-stop.
Сцены: палуба корабля 60 с + одна тяжёлая (бой или город) 60 с. Без нагрева между сериями ABBA ≥ 2 мин.

**M — замер (одна сессия ≥ 2 мин в сцене):** `dm/env`
```
DM_DBG=1
DM_DOS2_TOUCHUI=1
DM_DOS2_FPS=0
DM_NR_CPU=1
DM_NVN_PROF=2
DM_SLEEPSTAT=1
```
Ждём: `[cpuprof] DM_NR_CPU=1: sampler …`, `[cpuprof] cpus …`, `[cpuprof] gate probe …`, `[cpuprof] DM_NVN_PROF=2: … calibration …`, затем
раз в 10 с `threads` / `cores` / `hle` / `hle svc` / `nvn` / `nvn top` / `gfx` / `passes` / `passes by signature`, раз в 30 с `roles`; ни одного
`【红】[cpuprof]`. Разбор: `python tools/dos2_cpuprof.py work/logs/m1.dm.log`. Проверка цены: `dm-cpuprof` в строке threads < 0.1 мс / кадр,
калибровка NVN «untimed» < 10 нс.

**simpleperf (в той же сессии M, в сцене, 20 с; APK отладочный — `--app` работает без root):**
```
adb push <ndk>/simpleperf/bin/android/arm64/simpleperf /data/local/tmp/      (3.7 МБ, один раз)
adb shell chmod 755 /data/local/tmp/simpleperf
adb shell /data/local/tmp/simpleperf record --app org.dos2.port --call-graph fp -f 1000 --duration 20 -o /data/local/tmp/dos2.data
adb pull /data/local/tmp/dos2.data work/logs/m1.perf.data                  (≈ 10–30 МБ; по удалённому adb — спросить хозяина, правило > 50 МБ)
python <ndk>/simpleperf/binary_cache_builder.py -i work/logs/m1.perf.data -lib work/build-android
python <ndk>/simpleperf/report_sample.py -i work/logs/m1.perf.data > work/logs/m1.samples.txt
python tools/dos2_perf_map.py --log work/logs/m1.dm.log --samples work/logs/m1.samples.txt --top 40
python tools/dos2_perf_map.py --log work/logs/m1.dm.log --samples work/logs/m1.samples.txt --thread <tid rec из строки threads>
```
`--call-graph fp`: гостевой код (main / sdk в анонимной памяти) держит цепочку x29, ворота её не рвут (`dm_gate` не трогает x29), DWARF
у гостя нет. Имена: `ExportFunctionsTsv.java` на своей headless-копии проекта Ghidra (не общий GUI) → `--funcs main=main_funcs.tsv`.
Если `perf_event_open` откажет — `-e cpu-clock` вместо аппаратного счётчика. Порог из аудита §3: HLE-замены `memcpy` / LZ4 / zlib /
аллокатора — только если один лист ≥ 10 %.

**L — загрузка:** те же строки + `DM_FS_STATS=1` (без `DM_NVN_PROF`): главное меню → загрузить сейв → перейти в другую зону. Смотреть
`[fs] N reads X MB in 5s: mean …, max …, K over 20 ms` в окнах загрузки и `threads` (кто грузит, на каких кластерах).

**A/B MX / PT (решающий):** ABBA × 2 по 60 с на палубе, во всех — `DM_DBG=1 DM_DOS2_TOUCHUI=1 DM_DOS2_FPS=0 DM_NR_CPU=1`
(без `DM_NVN_PROF`, чтобы цена была минимальной и одинаковой):
- **A** — умолчания; **B** — `+ DM_NB_MX=0`; **C** — `+ DM_GFX_PRESENT_THREAD=0` (A B B A, затем A C C A).
- `python tools/dos2_cpuprof.py --ab work/logs/a1.dm.log work/logs/b1.dm.log work/logs/b2.dm.log work/logs/a2.dm.log` (и то же для C).
- Решение: fps в фазе без лимита и `GPU busy + gaps` (окна 89–91 fps скрипт выкидывает сам); `translation submit/present wall` и `CPU`;
  CPU `nvn-translate` + `dm-nbx0` + `dm-present`; `process CPU`. MX снимаем, если B: fps ≥ A и стена трансляции ≤ A (ждём −0.1…0.35 мс).
  PT оставляем, если A: CPU трансляции ниже C на ≥ 0.3 мс при равных fps / GPU gaps; если CPU-часть present < 0.2 мс и `GPU gaps` A > C —
  PT в умолчаниях не нужен.
