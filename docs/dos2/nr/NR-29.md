# NR-29 — один бюджет памяти NR-кэшей по объёму ОЗУ + `onTrimMemory` (`DM_NR_MEM`, по умолчанию 1)

Ветка `dos2-nr29` (база `dos2-nr-all` 393fcd7). Шаг N1 финального аудита (`dos2-nraudit2:docs/dos2/nr/AUDIT-FINAL.md`, §2 п. 10, §3 N1).
Телефон не трогался; всё ниже, помеченное [м], — модель, не замер.

## Что было
У каждого NR-кэша свой потолок, и они складываются (аудит, п. 10):

| Кэш | Переменная | Старое умолчание |
|---|---|---|
| NR-05 блобы текстур (`hle_dos2_nr.c nrt_start`) | `DM_NR_TEX_PREP_MB` | RAM / 64, 32…128 МБ (6 ГБ: 88, 8 ГБ: 118) |
| NR-22 готовые VkImage + staging, ещё не взятые | `DM_NR_TEXSTREAM_MB` | 2 × блобы (176 / 236 / 256) |
| NR-06 неизменяемые копии статики (`xbg_nr_buf.inc`) | `DM_NR_BUF_MB` | 192 |
| NR-06 зеркало кольца | — | 19,5 МБ (размер кольца + 64 КБ), всегда |
| очередь ленивого ASTC-кодировщика (`xbg_astc_lazy.cpp`) | `DM_TEX_ASTC_QUEUE_MB` | 96 |
| SPIR-V прогрева для `load_shader` (`gfx-shader-reuse`, `warm::rewritten`) | — | без потолка (6–13 МБ) |
| NR-07 готовые, но не взятые пайплайны прогрева (`warm::ready`) | — | без потолка (число не ограничено) |

На телефоне 6–8 ГБ рядом с кучей гостя 3285 МБ это до 550–650 МБ пиковой памяти при включённых NR-05 / 06 / 22 (и 96 МБ очереди ASTC
на Mali уже сейчас). `DmActivity.onTrimMemory` для DOS2 не делал ничего (только крошку для DOOM-семейства).

## Что сделано
- **`dm/gfx/nr/nr_mem.{h,c}`** (чистый C, без движка / хоста): классы ОЗУ по `MemTotal` (< 4,75 ГиБ — 4 ГБ, < 6,75 — 6 ГБ, < 10 — 8 ГБ,
  иначе 12+), бюджет класса (96 / 192 / 384 МБ / **без потолка**), раздел бюджета между **включёнными** кэшами по весам (NR-05 2,
  NR-22 4, NR-06 статика 4, очередь ASTC 2, SPIR-V прогрева 1) за вычетом 20 МБ резерва зеркала кольца (если NR-06 включён), с полом
  на кэш (16 / 32 / 32 / 16 / 4 МБ), с округлением вниз до 1 МБ. Каждый кэш берёт `min(своё старое умолчание, доля)` — **только
  снижает**; явная переменная `DM_*_MB` всегда главнее. Уровни `onTrimMemory` → ступени очистки, порог опроса `MemAvailable`, «ворота»
  (одна очистка ступени не чаще, чем раз в N с; старшая ступень проходит сразу), разбор `/proc/meminfo`.
- **`dm/host/hle_dos2_nr_mem.c`** (новый фронт; ставится из `main.c` перед `dm_dos2_nr_install`, до кода гостя): читает `DM_NR_MEM`,
  ОЗУ (`ActivityManager.MemoryInfo.totalMem` из приложения → `/proc/meminfo MemTotal` → `sysconf`), набор включённых кэшей по тем же
  правилам, что их установки (`DM_NR` / `DM_NR_TEX` / `DM_NR_TEXSTREAM` / `DM_NR_BUF`), строит план, отдаёт `dm_nr_mem_cap(кэш,
  умолчание)` и `dm_nr_mem_pipe_lazy()`. Поток `dm-nrmem` (nice 10): раз в 1 с — запрошенная приложением очистка и опрос
  `MemAvailable`; раз в 10 с — строка `[nr] mem`.
- **Потолки на месте:** NR-05 (`nrt_start`: блобы; NR-22 от старого умолчания 2 × блобы), NR-06 (`nrbuf::init`), очередь ASTC
  (`astccache` перед `astclazy::start`), SPIR-V прогрева (`warm::rewritten_cap`: сверх него шейдер не хранится, `load_shader` перепишет
  сам — `rewritten_bytes` считается под `warm::mu`), NR-07: `DM_NR_PIPE=1` → `3` (ленивый) в классе 6 ГБ и меньше (`read_mode`).
- **Очистка по ступеням (дешевле перестроить — раньше):**
  1. спекулятивное, чем ещё никто не пользовался: блобы NR-05 и не взятые объекты NR-22 (`nr_tex_expire(…, 0)` — как истёкшие: транслятор
     сделает старым путём; объекты NR-22 уходят в «могилу», их уничтожает рабочий поток), свободные staging-чанки NR-22 (до 64 МБ
     `KEEP`), ожидающая очередь кодировщика ASTC (`astclazy::drop_queue`; эти текстуры остаются декодированными в этом запуске и будут
     закодированы в следующем);
  2. + SPIR-V прогрева (`load_shader` перепишет: 1–9 мс на большой шейдер) и копии статики NR-06 (`nrbuf::trim`: только на потоке
     трансляции, в начале следующей отправки; каждая запись → `NRS_NEW`, при следующем bind копируется снова — возвращаются только
     меши, которые ещё рисуются; чанки уходят через `retire_handle` за этой отправкой);
  3. + пайплайны прогрева, построенные и не взятые (`vkDestroyPipeline` под `warm::mu`; NR-21 `forget_pipeline` — хэндл может вернуться;
     draw, которому он нужен, соберёт его сам, с попаданием в `VkPipelineCache`).
  Зеркало кольца NR-06 не чистится никогда: следующая же отправка построила бы его заново, ничего бы не сэкономилось.
  Уровни: 5 RUNNING_MODERATE → 1; 10 RUNNING_LOW → 2; 15 RUNNING_CRITICAL → 3; 20 UI_HIDDEN → 2; 40 / 60 / 80 (фон) → 3.
  Опрос `MemAvailable` (Android 14+ больше не шлёт приложениям уровни RUNNING_*): ≤ max(8 % ОЗУ, min(2 × порог AM, 12 %)) → 1,
  ≤ max(4 %, min(1,25 × порог AM, 6 %)) → 2, ступень 3 опрос не даёт никогда (игра на экране); ворота: приложение 5 с, опрос 30 с.
- **Движок, `xbg_nr_mem.inc`** (подключён в `xbg_game.cpp` на уровне файла после входов NR-07): `xbg_nr_mem_usage` (атомики +
  собственные замки кэшей, **никогда** не замок движка) и `xbg_nr_mem_trim` (под замком движка `mutex`, проверяет `initialized`; порядок
  замков как у потока трансляции: `mutex` → `warm::mu` / `nrts::mu` / замок кодировщика). Для учёта: `nrts::out_img` (память образов
  не взятых объектов NR-22; их staging уже в таблице NR-05), `nrbuf::pub_arena / pub_mirror`, `nrts::trim_free`.
- **Приложение:** `DmActivity.onTrimMemory` → `nativeTrimMemory(level)` (DOS2, `libraryLoaded`, старая библиотека терпится) + крошка
  `trim memory level N` и для DOS2; перед `nativeStart` — `nativeMemInfo(totalMem, threshold)`. JNI (`jni_android.c`) только передаёт
  (слабые ссылки: в чужих сборках ничего); на UI-потоке уровень только запоминается, освобождает поток `dm-nrmem`.

## Переключатели
| Значение | Что |
|---|---|
| `DM_NR_MEM=0` | ничего: старые умолчания всех кэшей, нет потока, `onTrimMemory` игнорируется (строка в логе), нет строки `[nr] mem` |
| `DM_NR_MEM=1` (**по умолчанию**) | потолки по классу ОЗУ + очистки (приложение + опрос) + строка `[nr] mem` раз в 10 с |
| `DM_NR_MEM=2` | проверка: план и очистки считаются и пишутся («would …»), используются старые умолчания, ничего не освобождается |
| `DM_NR_MEM=3` | стресс: как 1 + принудительная очистка каждые 30 с по кругу 1 → 2 → 3 (прогоняет все пути освобождения; хитчи нарочно) |
| `DM_NR_MEM_TRIM=0` | без очисток (потолки и строка остаются) |
| `DM_NR_MEM_POLL=0` | без опроса `MemAvailable` (только уровни приложения) |
| `DM_NR_MEM_RAM_MB=<n>` | считать, что ОЗУ столько (прогон класса 6 / 8 ГБ на большом телефоне) |

**Почему по умолчанию 1 (вопреки общему правилу NR, по задаче шага):** потолки только снижают (меньше бюджет = старый путь, не ошибка);
в классе 12+ ГБ (Mi 14 Ultra) потолков нет вовсе. Очистки освобождают только то, что пересобирается старым путём. `DM_NR_MEM=0` —
побайтно старое поведение.

## Ожидаемый выигрыш [м]
- **6–8 ГБ телефоны (Snapdragon 7, MTK / Mali, PowerVR, Xclipse)** при включённых NR-05 / 06 / 22: пик NR-кэшей на входе в зону −300…400
  МБ (потолки), плюс очистки: при UI_HIDDEN / BACKGROUND (переключение в другое приложение) отдаётся всё спекулятивное, копии статики,
  SPIR-V и не взятые пайплайны (от десятков до сотен МБ) — меньше убийств LMK в фоне (= потеря несохранённого прогресса). Mali уже
  сегодня: очередь ASTC 96 МБ при нехватке памяти отдаётся (опрос / уровень), NR-07 ленивый в классе 6 ГБ.
- **Mi 14 Ultra (16 ГБ, Adreno 750):** потолков нет (класс 12+) — 0. Очистки только при реальной нехватке (опрос 8 % = 1,2 ГБ свободных)
  или при уходе в фон.
- **Цена:** без нехватки — поток `dm-nrmem` (чтение `/proc/meminfo` раз в 1 с, ~20 мкс) и строка раз в 10 с. Меньшие потолки = больше
  работы старым путём на слабых телефонах (меньше блобов NR-05 / объектов NR-22 заранее — часть их выигрыша на загрузке уходит;
  копии статики сверх 52 / 112 МБ — старый путь со снапшотом). Это и есть обмен «память ↔ время загрузки», выбранный в сторону памяти.

## Риски (честно)
- **Опрос `MemAvailable` — эвристика.** lmkd убивает по PSI, а не по `MemAvailable`; на телефонах, где под игрой `MemAvailable` всё время
  < 8 %, ступень 1 будет срабатывать раз в 30 с (дёшево, но очередь ASTC на Mali каждый раз теряется, и NR-05 / 22 теряют часть заранее
  сделанного). Строка `[nr] mem` покажет `poll N`; если часто — поднять ворота или отключить `DM_NR_MEM_POLL=0`. Нужен лог слабого
  телефона.
- **Копии статики NR-06 в фоне:** освобождаются в начале следующей отправки и уходят через `retire_handle` за ней. Если игра в фоне
  перестаёт отправлять кадры (вероятно: Horizon-фокус уходит гостю), память вернётся только после возврата. Остальные ступени
  освобождаются сразу (поток `dm-nrmem` под замком движка).
- **Ступень 3 под замком движка:** уничтожение сотен пайплайнов держит `mutex` — хитч, если игра на экране (только RUNNING_CRITICAL,
  на Android 14+ не приходит; фон — не важно). Опрос ступень 3 не даёт.
- `nr_tex_expire(…, 0)` считает очищенные блобы как «expired» в строке NR-05 (`expired N`, `blob_miss expired`) — читать вместе со
  строкой `[nr] mem: trim …`.
- Очищенные задания ASTC в этом запуске не предлагаются снова (`known`), закодируются в следующем.
- NR-07 `=1 → 3` на 6 ГБ: если подсказок нет (`DM_NR=0`), `start()` и так вернёт 1. Ленивый режим строит в кадре записи без подсказки
  («hint holes» в `DM_NR_PIPE=2`) — проверено в NR-07 как допустимое; NR-07 по умолчанию 0.
- Доли кэшам, которые включены переключателем, но не работают на этом GPU (статика NR-06 и зеркало на Adreno с zero-copy, очередь ASTC
  на GPU с BC), пропадают зря — бюджет консервативен, не превышается.

## Что НЕ сделано
- Динамический общий пул (кэш занимает долю соседа, пока тот пуст) — раздел статический; при нехватке помогают очистки.
- Потолок на число не взятых пайплайнов NR-07 и учёт их драйверной памяти (размер `VkPipeline` неизвестен; в строке только их число).
- Немедленное освобождение копий NR-06, когда очередь пуста (без ожидания следующей отправки).
- Зеркало кольца (19,5 МБ) — не трогается (см. выше).

## Прогон на телефоне, который это подтвердит
1. **A0 (Mi 14 Ultra, умолчания):** в логе `[nr] DM_NR_MEM=1 (NR-29: on): RAM 14.xx GiB (ActivityManager) = 12+ GB class, budget 0 MB`;
   строки `[nr] mem (…)` раз в 10 с; нет строк `[nr] mem: <кэш> … -> … MB`. Вход в зону (палуба → Форт Радость) и одновременно
   `adb shell dumpsys meminfo org.dos2.port` раз в 2–3 с (TOTAL PSS / RSS). Затем Home на 30 с и обратно: строки
   `[nr] mem: onTrimMemory level 20` и `trim tier 2 (onTrimMemory level 20): freed … MB`, после возврата игра рисует (копии статики
   возвращаются, `[nr] buf: memory trim (DM_NR_MEM): N static copies dropped`, если NR-06 включён).
2. **Класс 6 / 8 ГБ на том же телефоне:** `DM_NR_MEM_RAM_MB=5632` (и `7577`) `DM_NR=1 DM_NR_TEX=1 DM_NR_TEXSTREAM=1 DM_NR_BUF=1`:
   строки `[nr] mem: NR-05 texture blobs 128 MB -> 26 MB …` для каждого кэша; `[nr] mem` — `NR caches hold … (peak …)` ≤ 176 / 356 МБ;
   `dumpsys meminfo` пик при входе в зону против того же без `DM_NR_MEM_RAM_MB` (ожидание −300…400 МБ [м]); картинка та же; время входа
   в зону (строка NR-05 `taken` / NR-22 `images made here` — часть работы вернулась транслятору).
3. **Стресс путей освобождения:** `DM_NR_MEM=3` + `DM_NR=1 DM_NR_TEX=1 DM_NR_TEXSTREAM=1 DM_NR_BUF=1` 3–5 мин в бою / городе:
   `trim tier 1/2/3 (DM_NR_MEM=3 stress)` каждые 30 с, без `【红】`, без падений, без пурпура / пропавших мешей (NR-06 `bad 0`).
   С `DM_VK_VALIDATION=1` один раз — без ошибок об уничтоженных объектах в работе.
4. **Слабый телефон (6–8 ГБ, Mali):** лог игрока с умолчаниями: класс, `poll N` в строке `[nr] mem`, `MemAvailable`, были ли очистки.
