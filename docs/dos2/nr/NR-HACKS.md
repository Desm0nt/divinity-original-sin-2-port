# NR-HACKS (N6, 19.11.2026): страница «Хаки скорости» — упрощения графики ради FPS, `DM_HACK_*`

Ветка `dos2-nhacks` (worktree `wt-nhacks`, база `dos2-night1119` 7780b92). Телефона этой ночью нет: всё ниже — код, хост-тесты,
интерпретатор SPIR-V, `malioc` и **замеры из старых логов**; где цифра — модель или оценка, так и написано.

и ветка в `draw()` и `sampler()`).

### 1.2 Разрешение 3D: настоящий A/B
`rc1` (17.11, палуба, всё по умолчанию, 3D 100 %) против `rc3` (то же + `DM_GFX_TS_TOP=0`: старый баг держал DRS на минимуме 75 %):
**GPU 11.98 → 8.24 мс**, fps 76.7 → 93.4 (у `rc3` упор уже в CPU: `submit_cpu` 8.29). Модель `GPU(s) = F + P·s²`: F = 3.43 мс
(draw / вершины / фикс.), P = 8.55 мс (площадь) → 85 % −2.37 мс (−20 %), 75 % −3.74 (−31 %), 67 % −4.71 (−39 %), 50 % −6.4 (−53 %).
Сверка: `m7` → `m9` (меню, окно 900p → 720p, 44 % пикселей) −0.6 мс — там 6 мс из 12 тени + pre-pass, зависящие от draw: та же формула
с F ≈ 7.4. Кампания ближе к палубе (`nr10_gpass`: площадь ≈ 6.5 из 9 мс).

### 1.3 Дальний каскад теней
NR-SHCACHE §1 (дамп палубы ra1): каскады по draw 148 / 187 / **609** → дальний ≈ 65 % draw карты теней; на 750 ≈ 2.4–2.8 мкс GPU на draw
теней (m7: 1116 draw = 3.09 мс) → в ходьбе (кэш не попадает) **−1.2…−1.8 мс GPU** и **−2…−4 мс CPU потока трансляции** (≈ 3–5 мкс на draw);
стоя кэш теней (`DM_NR_SHCACHE=1` на Adreno) и так не рисует статичные — выигрыш ≈ 0.

### 1.4 Что уже отвечено логами (не переделывать)
- `DM_DOS2_SHADOWS=0` / `=2` на палубе: GPU 8.66 / 8.40 мс против баз 8.22–8.50 (`c4sh0` / `c5sh2` / `c0base` / `c6base` / `c16base`, 16.11, 3D тогда 75 %) —
  на Mi 14 ≈ 0 (в карте теней платят draw, не площадь). 512 × 3 оставлен в «Среднем» ради слабых (площадь растра карты 2.25× меньше).
- `DM_DOS2_AA=0` (`c9aa0`) ≈ 0; `DM_DOS2_PARTICLES_FULL=1` (`c2pfull`) −0.1…−0.3 в тихой сцене, в бою может быть хуже — не хак.
- ModelDetail (`GraphicSettings +0x40`) **уже на минимуме**: консоль пишет 2, читатели (0xa85180, 0xa99da4, 0x1423224 ×10) берут
  `min(ModelDetail, LOD−1)` как **нижний индекс LOD** — Switch и так рисует LOD ≥ 2; 3 только обрежет модели с 4+ LOD. Рычага нет.
- LightingDetail (`+0x48 = 2`) выбирает варианты пайплайна освещения (0xab9a44 / 0xabac74 / 0xc91590 `< 2`) — варианты, которых консоль
  не использует, могут отсутствовать в паке Switch (риск чёрного кадра); без телефона не включал, в таблице «кандидат».
- SSAO, DOF, GodRays, LensFlare, MotionBlur уже 0 у консоли.

### 2.2 FSR 1: EASU в проходе растягивания, RCAS на выводе
- Почему туда: при DRS < 100 % пост рисует 3D в левый верхний угол s × s своих 2160x972, а **шаг FXAA растягивает** его на всю цель (его VS:
  `TexCoord0.xy = uv · c3[0].xy + c3[0].zw`, `c3[0].xy = s` — проверено по SPIR-V `28b24f7288e2abe4`; NB-18b-11). Это и есть единственное
  место, где кадр увеличивается (потом `CombineUI` растягивает 2160 → 2400, ×1.11). EASU встаёт ровно на место FXAA + билинейки.
- Модуль: при отношении `dFdx(TexCoord0.x) · ширина текстуры` = 1 (±1/1024; 100 %, портреты HUD 1:1) — тело `PPFXAA_mobile.frag` слово в
  слово (тест структуры сравнивает), иначе EASU (fp32 `FsrEasuF` из ffx_fsr1.h, MIT, переписан на GLSL; приближения `APrxLoRcp/Rsq` как там).
  12 выборок (4 × gather R/G/B) с зажимом 4x4-окна к нарисованной части (за ней — старый кадр).
- RCAS = существующая «Резкость» ⚙ (`DM_GFX_SHARPEN`, `rcas.comp` / NR-20-rcas в повороте): весь кадр, включая UI. Хаки её не включают сами
  (это общая настройка), подпись строки FSR советует.
- EASU хочет сглаженный вход: при масштабе < 1 FXAA консоли заменён — края несут лесенку низкого разрешения, которую EASU восстанавливает
  по направлению; это потеря (лесенка мельче, чем у билинейки на 85–75 %, но не сглажена).

### 2.3 Страница ⚙
`Tl2Gear.dos2Hacks()` через `GearSettings.page(...)` (уже есть в порте; **общие файлы `frontend-common` не менялись**). Префы `hack_tier`
(0–4) и `hack_<имя>` (только «Свой»). Старт: Выкл. → ничего не ставится (`dm/env` `DM_HACK_*` работает); уровень 1–3 → только
`DM_HACK_TIER=<n>` (натив берёт таблицу и правило семейства GPU); «Свой» → все `DM_HACK_*` явно. Выбор уровня перерисовывает строки;
правка строки переключает уровень на «Свой»; «Свой», совпавший с уровнем, сохраняется как уровень. Строки RU + EN (`d3_settings.xml`, ресурсы
порта, как у остальных строк DOS2).

## 3. Доказательства / проверки (без телефона)

### 3.1 Интерпретатор (`python tools/dos2_post_fsr.py --bundles ../work/shaders-vk --n 400 --images ../src/work/logs --out <dir>`)
- Сборка: glslc vulkan1.1 -O → spirv-val → интерфейс = переведённого PPFXAA → `dm/android/shaders/ppfxaa_fsr.frag.spv.inc` (5756 слов).
- **1:1 (FXAA-путь): 400 / 400 бит в бит** с переведённым PPFXAA (spirv-opt -O) на случаях `dos2_post_mobile.py` (шум, прямые края, NaN
  текселей и координат, странные константы); исполнено на пиксель 128.5 против 118.6 (+10: отношение растяжения).
- **EASU-путь: 400 / 400** против независимого numpy `FsrEasuF`, читающего 12 текселей по смещениям (не по углам gather), отношения
  0.5–0.9, шум / ступени / края нарисованной части: макс. разница **2.4·10⁻⁷**. Исполнено на пиксель 593.
- Интерпретатор: OpDPdx / OpDPdy (+ Fine / Coarse) = константы `m.dpdx` / `m.dpdy` (производная линейной переменной) — подкласс `DModule` в `tools/dos2_post_fsr.py` (раунд 2, §8.1: не в `spv_interp.py`).

### 3.2 Цена EASU
`malioc` (Arm Performance Studio 2026.5): **G57: EASU длинный путь 10.25 A-цикла/пиксель (64 регистра, 50 % заполнения) против PPFXAA 3.0
(T)**; G52: 12.7 против 6.0. На G57 MC2 при выходе 1440x810: ≈ +4.5 мс к растягиванию консоли (≈ 40 % того, что даёт 75 %) → уровни на
Mali / PowerVR EASU не включают. Пробный mediump-вариант (fp16 для операций EASU) дал только 10.25 → 8.27 — нужен настоящий
`FsrEasuH` (упаковка half2), в бэклог. Adreno 750: оценка +0.3…0.9 мс к FXAA-растягиванию (12 gather на пиксель против 3–5 выборок FXAA;
не мерено).

### 8.1 EASU в половинной точности (`DM_HACK_FSR=1`, умолчание хака; fp32 — `=3`)
- `tools/dos2_post/PPFXAA_fsr.frag -DEASU_H` = форма `FsrEasuH` из ffx_fsr1.h: два отвода и два квадранта на одну упакованную операцию,

## 9. Предел ламп без мерцания (22.11, ветка `dos2-vk5-gpu2`, `DM_VK_NATIVE_LCAP_SEL`)

**Жалоба хозяина** (прогоны S04 / S05, видео `work/compare/S_tiers.mp4`): на уровнях хаков 2–3 свет в тенях мерцает. **Причина**: предел
раунда 2 (§8.2) брал «первые N ламп, которые освещают пиксель, в порядке списка кластера», а этот порядок движок от кадра к кадру меняет —
каждый кадр гаснет другая лампа; на границе кластера 128 пкс (другой список) — тоже. Интерпретатор: при перемешивании списка выход прежнего
предела меняется больше чем на 1 % в 15 из 120 случаев (N=2) и в 8 из 120 (N=4); лампа, входящая в радиус, при N=2 гасит соседнюю целиком
(скачок яркости 0.999 между соседними шагами).

**Сделано** (переключатель `DM_VK_NATIVE_LCAP_SEL`, один и тот же для нового бэкенда и старого пути `xbg_nr_sh.inc`):

| Значение | Что | Модули |
|---|---|---|
| **1** (умолчание) | каждая лампа судится отдельно: её наибольший возможный вклад = наибольший канал цвета (по модулю) × ослабление (те же числа, что считает шейдер: угол к нормали, спад по дальности, конус прожектора) × пик отражения пикселя (max(dc)·kd + max(F)·D_пик/4, D_пик Блинна-Фонга = pw/2π). Если это меньше τ от света, который у пикселя уже есть без кластерных ламп (окружение + солнце + свечение после экспозиции, наибольший канал), лампа не считается; от τ до 2τ входит плавно; дальше — код шейдера без изменений. τ = **1/64** для `DM_HACK_LIGHTS=4` («Средний»), **1/16** для `=2` («Максимум»). Пиксели с анизотропным GGX (у их лепестка нет дешёвого пика — касательная не обязана быть перпендикулярна нормали) считают все лампы | `light_lcap<N>t.frag.spv.inc`, слитые со Sky `light_lcap<N>t_f / _g` |
| 0 | прежний предел «первые N по списку» (быстрее, мерцает) | `light_lcap<N>`, `light_lcap<N>_f / _g` |
| 2 | 1 + яд: пиксель, где лампа выброшена или ослаблена, пурпурный (с его яркостью); только модуль предела — слитый со Sky свет уступает (`DM_VK_NATIVE_LCAP` 2 → 1) | `light_lcap<N>tp` |

Свойства (доказаны интерпретатором, `tools/dos2_light_cap.py --only thr`, `tools/dos2_light_cap_fused.py`): решение по лампе зависит только от
неё и пикселя — порядок списка в нём не участвует (перемешанный список: разница 1.1·10⁻⁷, порядок суммы); при τ = 0 модуль = модуль без
предела бит в бит; ошибка на лампу ≤ 2τ света пикселя (наибольшее наблюдённое отношение к границе 0.035 и 0.148); лампа, входящая в радиус,
меняет яркость так же плавно, как без предела (наибольший шаг 0.081). Слитые со Sky модули = своя цепочка Sky → свет → смешение бит в бит
(60 / 60, обе формы).

**Цена — главное для хозяина**: в счёте инструкций интерпретатора новый предел почти ничего не экономит (−1.5 % … +2 % к модулю без
предела; прежний N=2 давал до −60 % в плотных кластерах). Выигрыш прежнего предела был ровно в тех лампах, которые он гасил на виду.
Проверен и «N самых сильных ламп пикселя с плавным уходом последней» (`--only strong`, доказан, в сборку не включён): он **дороже**
модуля без предела (выбор сильнейших — второй проход по всему списку). Поэтому: «Ламп на пиксель» в уровнях 2–3 теперь безвреден, но и
почти бесполезен (ждём 0 … −0.2 мс на свете [м]); решение — оставить или убрать строку из уровней (`nrh_tier_table` = `Tl2Gear.HACK_TIERS`),
прежний быстрый вариант для желающих — `DM_VK_NATIVE_LCAP_SEL=0`. Прогоны — `VK-MOBILE-GPU-PLAN.md` §8.4 (L1–L3).
