# NR-25 `spirv-opt` транслированных шейдеров в setup — решение по числам: выигрыша нет, стадию не добавляю

Ветка `dos2-nr25` (worktree `wt-nr25`, база `dos2` 94d287d). Аудит `docs/dos2/nr/AUDIT-REMAINING.md` (ветка `dos2-nraudit`), строка NR-25:
«сначала офлайн `malioc` на топ-30 FS / VS кадра (циклы до / после) — решение по числам». Всё ниже — ПК, офлайн. Телефон не трогал.

## 0. Итог
- `spirv-opt -O` / `-Os` (SPIRV-Tools v2022.4 из NDK r29, та же библиотека, что у `DM_GFX_SPV_OPT` в APK) сокращает SPIR-V до 0.36x
  инструкций, но **компилятор Mali почти всё это делает сам**: циклы FS, взвешенные по GPU-времени кадра, −0.7 % на Mali-G57 / G52
  (слабый класс), −2.1 % на G715 / G720; **VS — ровно 0** на всех четырёх ядрах; регистры, спиллинг — без изменений; на G57 из 300
  случайных FS 27 стали **дороже**, 22 дешевле. Компиляция (прокси: время `malioc`) −5.7 %.
- После NR-04 (`DM_NR_SH=1`, свои ClusteredLighting / DeferredSky / пост) от `-O` остаётся ≈ −0.5 % (G57 / G52) / −0.7 % (G715) взвешенных
  циклов FS — верхняя оценка ≤ 0.2–0.25 мс на кадре 36–48 мс слабого Mali, реалистично ~0.1 мс, в шуме прогона.
- Цена варианта в setup: второй пак ≈ 110–120 МБ на телефон (или подмена `shaders.xgspack` — тогда **все** рантайм-анализы и
  переписывания (bindless, gscull, lone, early-Z, invariant, quad, warp, tidy, `#at`, `#vi`, raster facts, storage writes, классы входов
  VS, uniform extent) и проверки голов NR-04 / NB_POST работают по чужим для них словам и требуют перепроверки), +2–4 мин setup, риск
  багов драйверов на оптимизированном SPIR-V.
- **Решение:** стадию setup и переключатель не добавляю (правило брифа «только реальный выигрыш»). `DM_GFX_SPV_OPT` остаётся 0.
  В коде изменений нет; добавлен только инструмент замера `tools/dos2_spvopt_cost.py`, чтобы числа воспроизводились.
- **Попутные находки (важнее самого NR-25):** см. §4 — подтверждение NR-04 для Mali (−48…−56 % взвешенных циклов FS) и причина, почему
  транслированные шейдеры с кластерным светом упираются в load/store на Mali: **скалярные загрузки UBO с динамическим индексом**
  (1152 FS пака, из них ~150 forward-материалов с 23–24 такими загрузками в цикле света). Это кандидат на настоящий «оптимизирующий
  проход в setup» (векторизация загрузок UBO), а не `-O`.

## 1. Метод
- **Компилятор:** Arm Mali Offline Compiler `malioc` v2026.5.0 (Arm Performance Studio 2026.5). MSI уже был скачан с сайта Arm без
  входа и распакован `msiexec /a` (не установлен) в папку инструментов хозяина (KB PERF-X13, Pillars, 16.11).
  Лицензия: EULA Arm Development Tools, при бесплатном получении — «internal use only» (п. 3.2): замер у нас — внутреннее использование,
  в APK / setup / репозиторий ничего от Arm не попадает. Это реальный компилятор драйвера Mali: циклы по конвейерам (arith / load_store /
  varying / texture), ограничивающий конвейер, рабочие и uniform-регистры, спиллинг.
- **Ядра:** Mali-G52 (Bifrost, самые слабые: Helio G8x), Mali-G57 (Valhall, Helio G99 / Dimensity 700 — класс issue #2 Pillars),
  Mali-G715 (Dimensity 9200), Mali-G720 (5-е поколение, Dimensity 9300).
- **Что меряю:** для модуля — циклы самого длинного пути (`longest_path_cycles`; у модулей с циклами malioc его не даёт — тогда
  `total_cycles`, т. е. тело цикла один раз), «bound» = максимум по четырём конвейерам. Уровни: raw (пак как есть), `-O`, `-Os`. Каждый
  вариант прошёл `spirv-val --target-env vulkan1.1` (0 отказов: 283 модуля рабочего набора + 300 случайных, все три уровня).
- **Веса (какие шейдеры важны в кадре):** строки `NVN GPASS` прогонов `gp1` + `gp2` (Mi 14 Ultra, `DM_GFX_PASS_PROF`, 131 кадр кампании с
  ≥ 60 проходами): время прохода делится между FS (VS) его первого и последнего draw. Это время Adreno 750, а не Mali — прокси «сколько этот
  шейдер работает в кадре»; для Mali он занижает долю ClusteredLighting (там она ещё больше). Рабочий набор — все модули из строк
  `NVN shader … loaded` прогонов `rc1` (палуба), `gp1`, `gp2`: **145 FS, 138 VS**; 54 FS / 50 VS имеют GPU-время. Плюс 300 случайных FS
  пака (seed 25) — проверка, что вывод не зависит от выборки.
- **Пак:** `work/shaders-vk/shaders.xgspack` (12 329 бандлов, 6 192 FS) — тот, что строит setup.

Воспроизвести (1 мин 40 с, 14 потоков):
```
python tools/dos2_spvopt_cost.py --pack <work>/shaders-vk/shaders.xgspack --logs src/work/logs \
  --malioc "<Arm Performance Studio 2026.5>/mali_offline_compiler/malioc.exe" \
  --spirv-tools <sdk>/ndk/29.0.14206865/shader-tools/windows-x86_64 --random 300 \
  --native packs/2a/native.xgspack.light-mobile --json nr25.json --top 30
```

## 3. Adreno, PowerVR, Xclipse
- **Adreno:** бесплатного офлайн-компилятора нет (Qualcomm-овский — за учётной записью; в локальном дереве Mesa нет
  отдельного `ir3_compiler`, сборка Turnip под drm-shim потребовала бы ставить пакеты — не делал). Довод по исходникам: ir3 гонит
  `nir_lower_vars_to_ssa`, `nir_opt_copy_prop_vars`, `nir_opt_dead_write_vars`, `nir_opt_cse`, `nir_opt_dce`, `nir_opt_constant_folding`,
  `nir_opt_algebraic`, `nir_opt_if`, `nir_opt_peephole_select`, `nir_opt_loop_unroll`, `nir_opt_gcm` в цикле `ir3_optimize_loop`
  (`src/freedreno/ir3/ir3_nir.c`) — это надмножество `-O` SPIRV-Tools; **плюс** `nir_opt_load_store_vectorize` для UBO / SSBO
  (`ir3_nir.c:827–834`), которой у `-O` нет вообще. Стоковый компилятор Qualcomm — LLVM-основанный, делает то же. NR-04: 750 не упирается
  в ALU. Ожидание −0 %.
- **PowerVR / Xclipse:** офлайн-компиляторов не пробовал (PowerVR — PVRShaderEditor Imagination, не проверял лицензию / доступ; Xclipse —
  AMD-основа, RGA не репрезентативен для драйвера Samsung). Компиляторы этих драйверов тоже на LLVM / собственном SSA — оснований ждать
  иного, чем у Mali, нет; не замерено.

## 4. Попутные находки (для главной сессии)
1. **NR-04 на Mali — настоящий рычаг (malioc подтверждает).** Свои шейдеры `packs/2a/native.xgspack.light-mobile` (те же SPIR-V, что
   `native-nr.xgspack` NR-04) против транслированных, циклы bound:

   | FS | G57 трансл. → свой | G52 | G715 |
   |---|---|---|---|
   | ClusteredLightingWithSSAO | 47.0 → **17.0** | 47.0 → 16.0 | 47.0 → 16.0 |
   | DeferredSky | 4.53 → 3.60 | 4.0 → 4.0 | 5.00 → 1.71 |
   | CascadedPCF_3x768 (exact) | 11.94 → 6.06 | 23.0 → 10.5 | 5.75 → 2.55 |
   | CascadedPCF_2x1024 | 7.00 → 5.38 | 14.0 → 6.5 | 3.50 → 2.36 |
   | PPDownSampleLog2 | 1.75 → 1.12 | 0.5 → 0.5 | 0.87 → 0.87 |
   | FadeBlending | 3.53 → **3.85** | 7.5 → 7.5 | 1.62 → 1.74 |
   | EoCOutlineCombine | 1.16 → **1.27** | 1.5 → 1.5 | 1.00 → 1.00 |

   Взвешенно по GPU-времени кадра: **−48.6 % (G57), −48.3 % (G52), −56.1 % (G715 / G720)** циклов FS рабочего набора — против −0.7 / −2.1 %
   у `-O`. Значит, для Mali-политики NR-04 (`xbg_nr_sh_default`, класс light) стоит включать первым; PCF exact на Mali вдвое дешевле
   транслированного (но не бит в бит — решение NR-04 остаётся). FadeBlending / EoCOutlineCombine свои на G57 на 9 % дороже (мелочь, в
   ничью на G52 / G715) — можно исключить из замены на Mali, если будут считать каждый цикл.
2. **Почему транслированный кластерный свет упирается в load/store на Mali.** После `-O` в ClusteredLighting 46 `OpAccessChain
   %_ptr_Uniform_float` с **динамическим индексом** (скалярные чтения c-буфера Maxwell `LDC` по одной float) — и load_store = 47 цикла;
   у своего NR-04 те же данные читаются 10 загрузками `vec4` → 16 циклов. Счёт по всему паку: **1152 из 6192 FS** имеют такие загрузки;
   **144 FS по 24 и 3 по 25** (цикл кластерного света forward-материалов: FlowingWater, Base_AlphaBlending_PBR, следы-декали и т. п.;
   у замеренных четырёх load_store 24 цикла против arith 8.7–13.8), 2 по 47 (ClusteredLighting), 999 — по одной; из всех 1152 модулей
   1056 — forward-материалы `*_FOR_*`, 84 — EngineShaders. Turnip это склеивает сам
   (`nir_opt_load_store_vectorize`), компилятор Mali — нет, `spirv-opt -O` — тоже нет (такого прохода в SPIRV-Tools нет).
   **Кандидат нового шага** (не NR-25): проход в setup или в трансляторе, склеивающий соседние скалярные `LDC` с одной базой и
   индексом в `vec4`-загрузку (точно эквивалентно: те же байты, только ширина чтения; проверка — `spv_interp.py` бит в бит + malioc).
   Ожидание на Mali: forward-материалы 24 → ~8–14 циклов (упор уходит в arith), т. е. −40…−60 % на этих модулях; их доля в кадре
   зависит от сцены (палуба: вода 2.4 % времени 750; бой с эффектами / города — больше). Adreno ≈ 0.
3. **`DM_GFX_SPV_OPT` в APK.** Раз `-O` ничего не даёт GPU, библиотека SPIRV-Tools в `libdm.so` DOS2 (+2.35 МБ урезанного, ≈ +1.8 МБ
   APK, `dm/android/spirv_tools.cmake`) — кандидат на снятие в NR-26 (чистка). Сам не трогал (сборка, другие агенты).
4. G52 (Bifrost): 10 из 138 VS рабочего набора спиллят в стек (G57 / G715 — 0); `-O` не меняет. Для слабейших Mali возможен
   отдельный рычаг на VS, вне NR-25.
