# NR-MDI — склейка depth-only draw в один multi-draw: сначала замер (ночь 19.11.2026, ветка `dos2-ntrans`)

Задача координатора: карта теней 2.7–3.1 мс при ≈ 1 116 draw и пре-пасс 0.66–3.06 мс платят за draw, а не за пиксель (m7 → m9 их не
уменьшает). Склеить подряд идущие depth-only draw с одним конвейером в `vkCmdDrawMultiIndexedEXT` / `DrawIndexedIndirect`, данные
draw (матрицы, кости, смещения UBO) — в буфер, читаемый по `gl_DrawID`; вариант VS через перепись SPIR-V; ключ `DM_NR_MDI`.
Телефона нет: ниже — то, что говорят логи, исходник Turnip и хост-тесты. [м] = модель.

## 0. Коротко
- **На Turnip multi-draw сам по себе GPU не экономит.** `tu_CmdDrawMultiIndexedEXT` (mesa-full-dm, turnip27, `tu_cmd_buffer.cc` 9632)
  на каждый draw всё равно пишет VS params (draw id, vertex offset) и `CP_DRAW_INDX_OFFSET` — ровно то же, что отдельный
  `vkCmdDrawIndexed` без смены состояния. Расширение есть (`EXT_multi_draw`, `maxMultiDrawCount 2048`), но экономия GPU — **только
  состояние между draw**.
- **Это состояние у DOS2 — почти всегда перепривязка набора дескрипторов с новыми динамическими смещениями** (блок матрицы draw в
  кольце движка). Turnip на каждую такую привязку копирует динамические дескрипторы в новую память и пишет
  `SP_UPDATE_CNTL(gfx_bindless=0xff)`: дескрипторы всех наборов читаются заново (DOOM Eternal GPUCOST 05.11, причина №2:
  2–7 мс на 4 300 draw). У DOS2 в depth-проходах ходьбы: 1 121 draw, наборы 989 (после сортировки NR-21 — 878), конвейеры 673 → 64,
  вершины 1 025 → 619 (O_sort2, модель NR-21).
- **Склейку ограничивают буферы вершин, а не конвейеры:** после сортировки остаётся 619 смен буфера / смещения вершин на 1 121 draw →
  в среднем ≈ 1.8 draw в пачке. Убрать можно только ≈ 500 перепривязок из 878.
- **Цена draw на GPU (Mi 14):** регрессия по проходам m9 (VERTEX.md §0): **≈ 1.47 мкс на любой draw + 0.26 нс на индекс**. Тени =
  1.64 (draw) + 1.46 (индексы) = 3.10 мс. Какая доля из 1.47 — перепривязка набора, логи не говорят. Вилка 0.3–1.0 мкс: NR-21 (−600 смен
  конвейера, −400 вершин, −111 наборов) дал только +0.7 fps ≈ −0.1 мс → смены конвейера и вершин дешёвые; Eternal: перепривязка
  0.5–1.6 мкс на draw.
- **Ожидание склейки на Mi 14 [м]:** ходьба с тенями −0.15…−0.5 мс GPU (≈ 500 перепривязок × 0.3–1.0 мкс). Если буферы вершин свести в
  один (статические копии NR-06 в одном буфере, кратно страйду) — до ≈ 1 000 → −0.3…−1.0 мс. Стоя −0.05…−0.15 (кэш теней уже не рисует
  76–83 % draw теней). Против этого — цена чтения данных draw в VS вместо константного кэша (§4).
- **Сделано сегодня (без вреда, решает один прогон):**
  - `DM_NR_MDI=2` — счёт по модели склейки на каждом draw полосы NR-09: пачки подряд и после сортировки, размеры, какие слоты смещений
    меняются, пачки, у которых блоки идут в кольце с одним шагом (тогда копировать ничего не нужно), что меняется между соседними
    depth-draw;
  - `DM_NR_MDI=3` — **проба** (картинка нарочно неверная, только стоя): у depth-only draw не делается перепривязка, меняющая только
    смещения. Разница GPU с `=2` = потолок того, что даст склейка, измеренный, а не модельный.
  - Режим `=1` (настоящая склейка с вариантом VS) **не построен**: по числам выше он может дать от −0.15 до −1 мс, и решать это надо
    пробой `=3`, а не моделью (§5).

## 3. Что сделано: `DM_NR_MDI` (0 умолч. / 2 счёт / 3 проба; 1 не построен → работает как 2)
- `dm/gfx/nr/nr_mdi.h` (чистый C): правило пачки (`nrmdi_same`: проход, конвейер, раскладка, набор, вершинные привязки — буфер +
  смещение после свёртки NR-09, индексный буфер + тип, viewport, scissor, число и первый экземпляр; динамические смещения и диапазоны
  индексов могут отличаться), ключ пачки, счётчики. Пачки по записанному порядку, оценка «после сортировки» (разные ключи среди
  order-free draw прохода, тест NR-21), какие слоты смещений меняются внутри пачки, **пачки, где каждый меняющийся слот шагает одним
  шагом** (блоки draw уже лежат в кольце массивом → одна привязка + `gl_DrawID × шаг`, без копий), что меняется между соседними
  depth-draw (конвейер / набор / смещения / вершины / индексы / viewport / экземпляры).
- `dm/gfx/vulkan/engine/xbg_nr_mdi.inc`: заполняет `nrmdi_draw` из рук полосы NR-09 после её команд; order-free — тот же тест, что у
  `nrsort::take`. Строка раз в 10 с: `[nr] mdi (DM_NR_MDI=…, NR-MDI, last 10 s, F frames): lane draws …, depth-only …; recorded order: B
  batches a frame (D draws in batches of 2+, sizes 1/2/3-4/5-8/9-32/33+ = …), set rebinds a batch would not emit R a frame; varying dynamic
  offsets per batch (popcount:batches) …; batches whose blocks step by one stride in the ring A a frame (… draws); sorted by key (order-free
  … in … passes): S batches a frame; between consecutive depth draws of a pass: pipeline x %, set y %, dynamic offsets z %, …`.
- `=3` (проба): в привязке набора полосы — если раскладка и набор те же и меняются только смещения, а draw depth-only, привязка не
  делается. Строка `【红】[nr] mdi PROBE … rebinds … not made a frame`. Красная стартовая строка предупреждает: картинка неверная.
- Хост-тест `tests/nr_mdi_test.c`: модель против перебора на случайных потоках draw (21 разнообразие × 20 + длинные проходы + потоки с
  блоками «как кольцо») — пачки, размеры, пачки 2+, перепривязки внутри пачек, сортированная оценка, счётчики смен, пачки с одним шагом;
  каждое поле ключа разделяет пачки: **8 558 проверок PASS**. `source_structure` блок NR-MDI: вызов после команд полосы, за флагом;
  проба только при `=3`; `=1` не построен; ядро без движка; приложение ключ не ставит.

## 4. Как устроить `=1`, если проба скажет «да»
1. **Пачка** = подряд (или после сортировки NR-21) depth-only draw одного ключа `nrmdi_key`; одна `vkCmdBindDescriptorSets` на пачку,
   `vkCmdDrawMultiIndexedEXT(count, {firstIndex, indexCount, vertexOffset}[])`.
2. **Данные draw:** меняющиеся блоки (по строке `=2` — обычно 1–2 слота: матрица мира, палитра костей).
   - если блоки пачки идут в кольце одним шагом (строка «step by one stride») — одна привязка UBO на первый блок, VS читает
     `блок[gl_DrawID]` через ту же константную память (Adreno: `ldc` с равномерным индексом, без SSBO);
   - иначе блоки копируются в одну полосу ≤ 64 КБ (≈ 300 блоков по 200 Б) кольца потока трансляции.
   SSBO не брать: на Adreno UBO идут через константный кэш, а 7.5 М индексов depth-проходов за кадр × 3–12 чтений SSBO могут съесть весь
   выигрыш.
3. **Вариант VS** (перепись при загрузке, как NR-27 / NR-32): у меняющегося блока индекс массива += `DrawIndex × (шаг / 16)`
   (`OpDecorate BuiltIn DrawIndex`, capability `DrawParameters`, Vulkan 1.1 `shaderDrawParameters`); ключ модуля `#mdi<слоты>`.
   **Доказательство:** интерпретатор `tools/spv_interp.py` на настоящих VS пака — выход варианта при `DrawIndex = i` и памяти «блок i на
   месте i» = выход оригинала с блоком по смещению, для всех depth-only VS пака.
4. **Сверка `=2` в рабочем режиме:** пачка из одного draw = старый путь; NR-SHCACHE хэширует draw как раньше (вход тот же).
5. Часы [м]: 12–20 агент-часов (перепись + интерпретатор 5–8, пачки в полосе + NR-21 3–5, раскладки / конвейеры варианта 3–5, тесты 2).

## 5. Когда строить `=1` (решает проба)
Прогоны (60 с от загрузки; бэкап сейва; кэш теней выключить, чтобы карта рисовалась вся: `DM_NR_SHCACHE=0`):
| # | env | Сцена | Решает |
|---|---|---|---|
| M1 | `DM_NR_MDI=2 DM_NR_SHCACHE=0 DM_GFX_PASS_PROF=300,180,0` | стоя у ворот ФР | строка `[nr] mdi …`: сколько перепривязок уберёт склейка подряд / после сортировки, шагают ли блоки в кольце; GPASS карты и пре-пасса |
| M2 | `DM_NR_MDI=3 DM_NR_SHCACHE=0 DM_GFX_PASS_PROF=300,180,0` | то же место, стоя | **разница GPASS карты теней и пре-пасса с M1** = потолок склейки; картинка неверная нарочно (не смотреть, выключить) |
GO для `=1`: M2 − M1 ≥ 0.4 мс на карте + пре-пассе **и** в M1 доля «step by one stride» или пачек 2+ ≥ 40 % depth-draw. Иначе склейку
не строить, а записать отказ (KB) и идти в вершины (ниже).

## 7. Что дороже склейки в этих проходах (на будущее)
Индексная часть карты теней (≈ 1.46 мс из 3.1 по m9) — выборка вершин: у depth-only VS читается только позиция, но вершины
перемежены (страйд 32–64 Б), и каждая строка кэша тянет всю вершину. Копия «только позиция» для статических мешей (NR-06 уже держит
статические копии, по умолчанию они draw не обслуживают) уменьшила бы трафик вершин в 3–5 раз, без потерь: −0.5…−1 мс [м]. Это отдельный
шаг; заодно все статические меши окажутся в одном буфере — тогда и склейка перестанет упираться в буферы вершин (§0).
