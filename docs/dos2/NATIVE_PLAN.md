# DOS2: план нативизации (14.11.2026, ветка `dos2-perf`)

Принцип хозяина: не слой трансляции, а нативное поведение. Где механизм Switch (запросы fsp-srv, потоки, запись и подача команд NVN)
можно заменить прямым механизмом Android / Vulkan — заменять, хуками в `main` разрешено. Многопоточность игры остаётся многопоточной.
Ранжирование ниже: **сколько пути Switch убираем** (HLE → натив) × **ожидаемый выигрыш**. Адреса — `main` DOS2 апдейт v12
(build-id `4979b200…`, `work/exefs-update/main.raw`; text 0..0x1bf7480, rodata 0x1bf7600, data 0x2334000, bss после 0x2b1c120).
Метод: capstone + разбор слотов NVN (загрузчик `0x934f00`, 516 слотов `0x2bbee98…0x2bbfeb0`) + R_AARCH64_RELATIVE (`rela` в образе) для
таблиц виртуальных функций. Начала функций, найденные эвристикой, помечены «≈» — сверить в Ghidra до хука.

## 1. Как DOS2 пишет и подаёт команды NVN (статический разбор main)

### 1.1 Объекты
| Что | Где | Факт |
|---|---|---|

| Командные буферы NVN | **3 контекста**: `device+0x5250 / +0x5428` (по индексу текстуры окна `device+0x31e0`) и `+0x5600` (вне кадра, §1.5); шаг 0x1d8, текущий — `device+0x5248` | конструктор `0x939850` (вызовы `0x938c64/78/8c`): `nvnCommandBufferInitialize` (+0x38 в контексте), command memory 5 МБ (`0x500000`), control memory из аллокатора, memory callback `0x939af0`, `nvnSync` в +0xd8 |

### 1.2 Кадр
1. **BeginFrame** ≈ `0x9215f0` (вызов из `0xa66e48` и `0xa677b8`): `nvnQueueWaitSync(queue, prevsync)` (`0x92166c`), контекст = `device+0x5250 +
   0x1d8 × device[0x31e0]`, запись в `device+0x5248`, сброс таблицы 4096 записей по `device+0x25ac8`, `AddCommandMemory` (`0x921720`, вся 5 МБ),
   `AddControlMemory` (`0x92173c`), **`BeginRecording` (`0x92174c` — единственный вызов в main)**, таймстемп ReportCounter.
2. **Исполнение собственных командных списков движка**: `ExecuteCommandList` `0xa49c30` (вызовы из кадра `0xa66e08`, `0xa67da0` и из ~20 проходов
   `0xab181c … 0xb1f88c`). Список = цепочка блоков (`+0x18` следующий), пакет = байт кода + данные, выравнивание по первому байту;
   каждый пакет → `ExecuteRenderCommand(ctx, opcode, data)` **`0x93e5f0`** (switch на 64 кода, таблица u16 `0x1f50716`, база `0x93e648`;
   возвращает длину пакета). Карта кодов → NVN — §1.4.
3. Часть проходов зовёт NVN напрямую (DrawElements в `0xaab248`, `0xabcf60…0xabf15c`, `0xaf3160`, `0xb895dc`; Barrier в `0xac672c`,
   `0xac70c0`; UI/Iggy-подобный блок `0x1bea840…0x1bf4290` — свои обёртки draw/state).
4. **Промежуточный flush** в кадре `0xa66bc0` (`0xa67960`: EndRecording + SubmitCommands на текущий контекст; `0xa679dc`: FenceSync + Flush +
   `nvnSyncWait(-1)`) — когда CPU нужен результат GPU (ReadTexels `0x9291c0`/`0x929880` из этой же функции) или кончилась память.
5. **EndFrame** `0x93ccd0` (slot 8): ReportCounter, EndRecording (`0x93cd3c/0x93cd50`), SubmitCommands (`0x93cd6c`), PresentTexture (`0x93ce38`),
   FenceSync + Flush (+SyncWait `0x93cec8` при ожидании).

**Вывод:** на Switch запись NVN **однопоточна**: один поток рендера, один командный буфер на кадр (кольцо из 3), одна подача в кадр
(+ редкие flush). Лог это подтверждает (`submits=1.00` во всех окнах, `ops≈1519` на 962 draw). Наш хост соответствует 1:1 — игровой поток рендера
записывает NVN-записи (cmd_alloc на своём потоке), `nvn-translate` переводит их в Vulkan. **Параллелизм движка — выше NVN:** командные списки
Larian (`0xa49c30`) готовятся проходами/задачами, а на NVN их сводит один поток. Значит «сохранить многопоточность» = (а) не стягивать в один
поток то, что игра делает на своих потоках (загрузка текстур, ФС, шейдеры), и (б) в нативном бэкенде исполнять независимые списки
параллельно (§3 шаг 6).

### 1.3 Первый безопасный шаг (сделан): перепись потоков записи — `DM_NVN_THREADS`
- `dm/gfx/nvn/hle_nvn.c`: на каждом `cmd_alloc` (любая записывающая `nvnCommandBuffer*`) — счётчик по `gettid` (32 слота, TLS-индекс,
  relaxed add); на `BeginRecording` — счётчик и число смен командного буфера; на `QueueSubmitCommands` — подачи и хэндлы; первый адрес
  возврата (`module+off`). Раз в 10 с строка: `[nvn] recording thread <tid> '<comm>' (last 10.0 s): N records, B BeginRecording (C command
  buffer changes), S submits (H handles); first begin from main+…, first submit from main+…`.
- Там же: `nvnTextureWriteTexels(Strided)` ждёт **всю** очередь трансляции (`x_drain`) перед записью CPU — считаем вызовы и время ожидания:
  `[nvn] WriteTexels (last 10.0 s): N calls waited X ms in all … last writer tid T` (данные для шага 4 ниже).
- Умолчание: 1 в сборке dos2, 0 в остальных; `DM_NVN_THREADS=0` выключает. Цена — TLS + atomic на запись.
- **Ожидание на телефоне:** один поток с `BeginRecording` ≈ 60/с (BeginFrame `0x92174c`), `submits` ≈ 60–62/с, адрес возврата begin
  `main+0x921750`, submit `main+0x93cd70` / `+0xa679b0`. Иное (2+ потока) — пересмотреть §3 шаг 6.

### 1.5 Точки хука — сверено 14.11 (Ghidra 12.1.4 headless, свой проект на копии `main.raw`, без общего GUI; + capstone)
Все начала стоят после `udf`-выравнивания или `br` предыдущей функции; первые 4 инструкции — `sub sp` / `str`/`stp` пролога без PC-относительных
операндов, то есть 16-байтовый хук (`ldr x16, #8; br x16; .quad`) с переносом пролога в трамплин безопасен. Исключение — `0x93cef0` (4 инструкции
всего, хук не нужен).

| Функция | Начало (точно) | Аргументы | Что делает (по декомпиляции) |
|---|---|---|---|
| `ExecuteCommandList` | **`0xa49c30`** (512 б) | x0 = список, w1 бит 0 = «освободить и сбросить» | Список: `+0` первый блок, `+0x18` второй список (ресурсы на освобождение), **`+0x38` рендерер**. Блок: `+0` данные, `+8` u32 размер, `+0x10` u32 **число пакетов**, `+0x18` следующий блок. Цикл: `A = *p; p += A − (p mod A)` (1…A байт набивки, байт набивки = выравнивание), затем `len = ExecuteRenderCommand(список, *p, p); p += len`. При бите 0: у записей второго списка с типом 1 зовётся виртуальный метод `+8` (освобождение), потом `0x941890(список, итератор, 1)` — сброс/перевыделение блоков. |
| `ExecuteRenderCommand` | **`0x93e5f0`** (кадр 0x140) | x0 = **список** (не рендерер; рендерер = `[x0+0x38]`), w1 = код (байт), x2 = пакет (первый байт = код) | `br` по таблице u16 `0x1f50716` (база `0x93e648`, шаг ×4), код > 63 → `0x93fc88`; общий эпилог `0x93e660`, **x0 = длина пакета** (по умолчанию 1). Обработчики читают `x19` = пакет, `x8` = список. |
| `BeginFrame` | **`0x9215f0`** | x0 = рендерер, w1 бит 0 | бит 0 = 1 (кадр): `nvnWindowAcquireTexture(dev+0x3020, sync dev+0x31a0, &dev[0x31e0])`, `nvnQueueWaitSync(dev+0x31e8, dev+0x31a0)`, контекст = `dev+0x5250 + 0x1d8 × индекс текстуры окна`, сброс таблицы 4096 записей (`dev+0x25ac8`), затем общая часть. бит 0 = 0 (вне кадра: чтение текстур, загрузка): контекст = **`dev+0x5600`** (третий, не кольцо!). Общая часть: `AddCommandMemory(ctx+0x38, [ctx+0x28]+0x50, [ctx+0x18], [ctx+8])`, `AddControlMemory`, `BeginRecording` (`0x92174c`), для кадра — таймстемпы `nvnDeviceGetTimestampInNanoseconds` и `ReportCounter`. `dev` = `[рендерер+0xb70]`. Вызовы: `0xa66e48` (кадр, бит 1) и `0xa677b8` (бит 0, перед копией для ReadTexels). |
| `EndFrame` | **`0x93ccd0`** (слот 8 окна `0x2984d00`) | x0 = окно (`[x0+0x48]` = рендерер), w1 бит 0 | бит 0 = 1: `ReportCounter`, `EndRecording` (`0x93cd50`), `QueueSubmitCommands(queue, 1, &h)` (`0x93cd6c`), `0x91abd0`/`0x91ad20`, `nvnQueuePresentTexture(queue, window, idx)`, счётчик кадров `dev+0x51f0`. бит 0 = 0: `EndRecording`, `Submit`, **`QueueFenceSync(ctx+0xd8) + QueueFlush + SyncWait(-1)`** — подача с ожиданием. В конце — хвостовой вызов слота 10 окна (`0x93cef0`: при бите 1 меняет местами `+0x68/+0x70`). |
| Кадр NX | **`0xa66bc0`** (5040 б, слот 20 устройства `0x29a6398`, он же в `0x29958a0`) | x0 = устройство | Порядок: чтения текстур (`BeginFrame(…,0)` → `0x920b00` копия → `End+Submit` `0xa67990…` → `EndFrame(окно,0)` либо `FenceSync+Flush+SyncWait` `0xa679dc` → `0x9291c0`/`0x929880` ReadTexels) → `BeginFrame(…,1)` (`0xa66e48`) → `ExecuteCommandList([[x28]+0x60], 1)` (`0xa66e08`, `0xa67da0`) → проходы → `EndFrame(окно, …)` через слот `+0x40`. |

Замок `0x2bbee38` берётся вокруг каждой группы только при байте `0x2bbee88 == 1`.

**Контексты записи:** не кольцо из трёх, а **два по текстурам окна** (`+0x5250`, `+0x5428`) **и один вне кадра** (`+0x5600`). На хосте это три
`NVNcommandBuffer`; запись вне кадра и запись кадра идут друг за другом (чтение — до `BeginFrame(…,1)`). Проверить на телефоне, что
`DM_NVN_WT_DRAIN` не пишет `two recordings open at once` / `submitted twice` (ветка `0xa67990` подаёт хэндл сама, а затем `EndFrame(окно,0)`
зовёт `EndRecording`+`Submit` ещё раз — при каком условии, не разобрано).

**Кто зовёт `ExecuteCommandList`.** 19 мест: 2 в кадре `0xa66bc0`, одно `0xa49b90` (виртуальный метод класса `0x2994758`: `Execute([this+0x10], 1)`),
остальные 16 — короткие виртуальные методы классов-проходов (`0xab17f0`, `0xab2240`, `0xab9e70`, `0xac10e0`, `0xac2cc0`, `0xac5f60`, `0xac8bc0`,
`0xb0b720`, `0xb15020`, `0xb164d0`, `0xb19e20`, `0xb1c530`, `0xb1d650`, `0xb1f860`; таблицы `0x2997ff8…0x299b820`): `Execute(this+0x18, 1)` —
список **встроен в объект прохода** по `+0x18`. Прямых вызывающих у них нет (только через vtable), поэтому поток статикой не доказывается.
Косвенно: `ExecuteRenderCommand` и всё под ним пишут в `[dev+0x5248]` (текущий контекст) и в кэш состояния рендерера без замков → исполнение
однопоточное; **строят** списки, вероятно, задачи проходов (каждый в свой объект), исполняет поток рендера — это предположение. Доказательство
на телефоне: `DM_NVN_THREADS` — если NVN пишет один поток, то и все `ExecuteCommandList` на нём. Аллокатор пакетов (кто пишет байт кода в блок)
не найден — нужен для шага 6 (tid строителей).

**Кэш состояния рендерера — главный факт для шага 5.** Обработчики кодов привязок NVN не зовут, а пишут в рендерер; NVN летит при draw:
`0x928e80` (код 36: `x0 = рендерер, w1 = первый индекс, w2 = число`) берёт индексный буфер по хэндлу `[r+0x17c8]` из таблицы
(`[r+0x240]` страницы по `[r+0x250]` записей × 0x58, проверка поколения в `[r+0x248]`; запись: `+8` адрес, `+0x24` тип индекса, размер из
`0x1f5865c`), при `[r+0x17e0] != 0` зовёт `0x926f90` + **`0x925740` (сброс грязных UBO → BindUniformBuffer)**, затем **`0x924730` (сброс
текстур → BindTexture)**, условный `SetRenderEnable`, и `nvnCommandBufferDrawElements(ctx+0x38, [r+0x1718] примитив, тип, число, адрес + шаг × первый)`.
Значит нативный исполнитель обязан либо повторить эти сбросы, либо встать уровнем ниже (см. рецепт §3.5).

### 1.6 Шаг 4 сделан: `DM_NVN_WT_DRAIN` (`dm/gfx/nvn/hle_nvn.c`, блок `wt_*`)
- Было: `nvnTextureWriteTexels(Strided)` → `x_drain()` (вся очередь трансляции) → запись в память текстуры (`dm_guest_write_prepare` метит
  страницы грязными, движок перезаливает при следующем использовании).
- Стало (0, умолчание dos2): запись та же, ждём только подачи, которые ещё могут читать **эту память**. Каждая запись, называющая текстуру
  (привязка по id пула, RT, копии, clear, resolve), метит адрес её памяти номером записи команд (`BeginRecording…EndRecording`); `Submit`
  сопоставляет запись с номером подачи. `WriteTexels`: память не называлась ни разу (стрим новой текстуры) → **без ожидания**; последнее
  использование уже переведено → без ожидания; иначе `x_wait_sub(подача последнего использования)`. Использования в ещё не поданной записи
  не ждём (их не покрывал и слив; на Switch они увидят новые данные).
- Ключ — адрес памяти, не объект: пересозданная текстура на том же месте пула и псевдонимы с тем же началом учитываются. Перерегистрация
  id наследует последнее использование id (привязки по id разрешаются при трансляции).
- Точное правило требует «записи подаются по одной в порядке начала» (так у DOS2: нет `CallCommands`/`CopyCommands`). Нарушение (две открытые
  записи, хэндл подан дважды / не по порядку, вложенные хэндлы) → строка `[nvn] WT: <причина> - exact rule off` и навсегда грубое правило:
  называвшаяся память ждёт все выданные подачи, не называвшаяся — не ждёт.
- `=2`: поток трансляции перед каждой подачей, которую писатель не ждал, просматривает её записи и пишет красную строку, если она называет
  записанную память (`by pool id as registered now` может быть ложным: id перерегистрировали после записи).
- `ReadTexels` оставлен со сливом: чтение обязано видеть результат GPU, игра сама делает перед ним `FenceSync+Flush+SyncWait(-1)`.
  `CopyBufferToTexture` (UI, `0x1bf1a78`/`0x1bf273c`) — запись в поток команд, слива там нет.
- Вызовы `WriteTexels` в main: `0x91ec84`, `0x920040`, `0x9200d0` (ресурсы рендерера), `0x1bedd34` (UI).
- **Не проверено исполнением** (нет телефона и хостового компилятора для `dm/gfx/tests`): только сборка `dm` arm64 и чтение кода.
  Известные упрощения: таблица меток 65 536 слотов с вытеснением (вытесненная память считается использованной в самой поздней вытесненной
  записи — лишнее ожидание, не пропуск); гонка двух записывающих потоков при вытеснении может потерять метку (у DOS2 записывает один поток).

### 1.7 Кэш состояния рендерера: поля, которые нужны draw (Ghidra, 14.11, второй заход)

Выводы для шага 5:
- Сброс кэша **инкрементный**: на draw уходят только изменившиеся слоты текстур и пересобранные блоки констант, а не «десятки привязок».
  Сколько именно записей хоста приходится на draw, теперь считает `DM_NATIVE_DRAW` (строка `[native] draws … host records and bytes a draw`).
- Программа и состояния (blend / depth / растеризация / вершинный формат / VB) идут в NVN прямо из обработчиков кодов, мимо отложенного сброса.

  упаковщик `0x925740` — второе не нужно.
- Коды 40 / 42 (`0x92f730`, `0x930210`, «draw со всем состоянием») и прямые NVN-draw проходов (§1.2 п.3) через `0x928e80/0x928fb0` не идут —

## 3. Дизайн нативного бэкенда (шаги 5–6) — для передачи Fable-агенту

### 3.1 Точки хука (по убыванию «нативности»)
1. **`ExecuteRenderCommand` `0x93e5f0`** (x0 = контекст рендера, w1 = код, x2 = пакет; возвращает длину пакета в байтах) — заменить своим
   исполнителем кодов §1.4, который пишет **прямо в VkCommandBuffer** текущего кадра. Длину пакета брать из оригинальной логики (сначала —
   звать оригинал в «сухом» режиме? нет: оригинал зовёт NVN; поэтому сначала таблица длин по кодам из разбора обработчиков, сверка
   `=2`: исполняем оригинал (NVN-путь, как сейчас) и сравниваем свою длину с возвращённой).
2. **`ExecuteCommandList` `0xa49c30`** (x0 = список, w1 = флаги) — точка, где виден весь список: для шага 6 (параллель) — отдать список
   воркеру, который пишет secondary CB; на потоке рендера оставить только порядок (`vkCmdExecuteCommands` в порядке списков).
3. **BeginFrame ≈ `0x9215f0`** (контекст по `device+0x31e0`, `BeginRecording` `0x92174c`) и **EndFrame `0x93ccd0`** (submit `0x93cd6c`,
   present `0x93ce38`) — начало/конец VkCommandBuffer кадра, `vkQueueSubmit` + `vkQueuePresentKHR` **на потоке игры** (нативно; сейчас — на
   `nvn-translate`). FenceSync/QueueWaitSync → VkFence/timeline-semaphore на тех же местах.
4. **Mid-frame flush** `0xa67960…0xa67a54` — submit + ожидание (timeline semaphore); ReadTexels `0x9291c0/0x929880` → readback-буфер.
5. Прямые NVN-draw вне списков (§1.2 п.3) и UI-блок `0x1bea840…0x1bf4290` — оставить на текущем пути NVN (HLE) до последнего; гибрид
   допустим, если оба пути пишут в один VkCommandBuffer в порядке вызовов (см. 3.2).

### 3.2 Поток данных и совместимость с текущим хостом
- Ресурсы (VkImage/VkBuffer/пулы/сэмплеры/пайплайны) уже создаёт хост из NVN-объектов (`xbg_game.cpp`); нативный исполнитель берёт их по
  тем же хэндлам (NVN texture handle → `Texture*` хоста, программа → `Shader*`/пайплайн через `pipeline_lookup`). Не дублировать менеджеры.
- Порядок: пока смешанный режим (часть кодов нативно, часть через NVN-записи), натив пишет **в тот же поток записей** особый код
  `OP_X_NATIVE` с указателем на готовый secondary CB (или на свой мини-список), а `nvn-translate` вставляет его по порядку — это даёт
  постепенный перевод кодов по одному с проверкой `=2` (оба пути, сравнение картинки `DM_GFX_PASS_VALUES` / хэшей вложений).
- Финал шага 5: все коды списков нативны → поток рендера игры пишет primary CB сам, `nvn-translate` остаётся для прямых NVN-вызовов
  (§1.2 п.3–5) или исчезает.
- Синхронизация памяти: зеро-копи пулов (Adreno AHB) сохраняется; снапшоты UBO/вершин (кольца констант Larian) — те же правила, что
  у `prepare_read` (zero-copy или копия в stream-буфер **в момент исполнения пакета** — это и есть момент «GPU читает», как на Switch).
- Барьеры: код 55 (`Barrier`) и смены RT (21/22/5) — единственные места барьеров/проходов; не вставлять своих по эвристике (урок ETR
  `GUEST_BARRIER`/RP_DEPS).

### 3.3 Параллельная запись (шаг 6)
- Единица параллели — **командный список движка** (вызов `0xa49c30`), а не draw. Список, не содержащий смены RT/барьера/flush/ReadTexels
  (флаги по первичному проходу байтов, без исполнения), исполняется воркером в **secondary CB** с `VkCommandBufferInheritanceInfo`
  (render pass + subpass текущего прохода; на Vulkan 1.3/ext — `VK_KHR_dynamic_rendering` + inheritance rendering info). Пулы команд —
  по одному на воркер на слот кадра (`vkResetCommandPool` целиком, Khronos sample *command_buffer_usage*); потолок числа secondary CB и
  возврат в запас (урок ETR nrec: 3600 CB/кадр → bad_alloc).
- Списки со сменой RT — на потоке рендера (или делятся по границам RT на части).
- Состояние на входе списка: Larian задаёт состояние внутри списков (коды 6–11, 18, 25…), поэтому secondary CB самодостаточен; «грязный»
  кэш состояний — по списку (сброс на входе).
- Воркеры: потоки игры уже распределены по ядрам; свои 2–3 воркера на A720 (`DM_PIN_AUTO`-подобная логика ETR, A520 — никогда).
- Проверка: `DM_NATIVE_LISTS=2` — воркер пишет, но исполняется прежний путь; сравнение числа draw/байт состояния; затем `=1`.

### 3.5 Рецепт первой реализации шага 5 (после сверки §1.5)
Цель первого захода — не весь бэкенд, а **смешанный режим с проверкой**, который можно включать по одному коду.
1. **Хук `ExecuteRenderCommand` `0x93e5f0`** (механизм патчей игры хоста, 16 байт пролога в трамплин). `DM_NATIVE_RC=0` — нет хука (умолчание),
   `2` — оригинал исполняется, рядом считаем: вызовы по кодам за кадр, свою длину пакета против возвращённой, tid; `1` — коды из маски
   `DM_NATIVE_RC_OPS` исполняет натив, остальные — оригинал.
2. **Шаг 5a (дешёвый, сразу даёт выигрыш): draw-коды 36/37 без записи NVN-записей привязок.** Не повторять кэш рендерера, а заменить его
   сбросы: хук `0x928e80`/`0x928fb0` (draw), `0x925740` (UBO), `0x924730` (текстуры) → одна запись хоста `OP_X_NATIVE_DRAW` (программа,
   вершинный формат, VB/IB, диапазоны UBO, хэндлы текстур — всё читается из рендерера один раз) вместо отдельных записей
   `BindUniformBuffer/BindTexture/…` на draw. Поток трансляции получает готовый «пакет draw» — это половина пути к прямой записи Vulkan,
   без изменения порядка и потоков. Проверка `=2`: оригинал пишет обычные записи, натив — теневой пакет, поток трансляции сравнивает
   итоговое состояние перед draw (программа, буферы, текстуры, RT) и пишет расхождения. Поля рендерера для пакета (смещения программы,
   VB, массива UBO, массива текстур) ещё не сняты — первая работа следующего агента: декомпилировать `0x925740`, `0x924730`, `0x9283a0`,
   `0x9243d0`, `0x925130`.
3. **Шаг 5b: поток рендера сам пишет Vulkan.** Когда 5a чист: `BeginFrame(…,1)` → `vkBeginCommandBuffer` кадра на потоке рендера,
   `OP_X_NATIVE_DRAW` → прямой `vkCmdDraw*` (пайплайн — `pipeline_lookup` хоста, дескрипторы — существующие кэши), `EndFrame` →
   `vkQueueSubmit` + present. Прямые NVN-вызовы (UI `0x1bea840…`, проходы с собственным draw) до конца идут в поток записей; порядок
   держит один VkCommandBuffer: перед нативным участком поток трансляции догоняется (`x_wait`), после — продолжает в тот же буфер.
   `FenceSync/QueueWaitSync/SyncWait` → `VkFence` той же подачи.
4. **Что считать на телефоне до кода:** `DM_NATIVE_RC=2` — гистограмма кодов (ожидание: 36/37/42 ≈ число draw, 25/15/28 — привязки, 21/22/5 —
   ≈ число проходов), доля NVN-записей вне списков (UI и прямые draw) — она решает, окупится ли 5b.

**Проходы для тайловых GPU в нативном бэкенде (обязательная часть 5b, не «потом»):**
- Проход Vulkan начинается только на коде 21/22 (SetRenderTargets) и 5 (RT + clear), кончается на следующем таком коде, коде 52 (копия RT),
  55 (барьер), 43 (compute), чтении RT как текстуры (15/28/33 с хэндлом текущего RT) и `EndFrame`. Никаких разрывов по эвристике.
- **Отложенное начало:** `vkCmdBeginRenderPass` ставится на первом draw, а не на коде 21: коды 3/4/5 (clear), пришедшие между сменой RT и
  первым draw, становятся `loadOp=CLEAR` (сейчас 3 clear на кадр не сворачиваются — `lazy_clear folded=0`); если draw покрывает всё вложение
  и не читает его — `DONT_CARE`; иначе `LOAD`.
- **storeOp** решается в момент закрытия прохода по карте жизни кадра (кто читает вложение дальше: коды 15/28/33/52, следующий 21/22 с тем
  же вложением); карта копится с прошлого кадра (списки проходов стабильны), первое расхождение → `STORE` и пересбор карты. Depth основной
  сцены, не читаемый после — `DONT_CARE`; MSAA — resolve вложением прохода.
- Возврат к тому же набору RT без чтения между ними (A → B → A) — кандидат на слияние: считать на `DM_GFX_PASS_PROF`, сливать только при
  доказанной независимости B от A.
- Барьеры внутри прохода — только из кода 55, со стадиями фрагмента; на Mali не трогать vertex-стадии.
- Все решения — за `DM_NATIVE_RP=0/1/2` (2 = считать, что решил бы новый планировщик, исполнять прежний путь, писать расхождения load/store).

### 3.6 Что сделано из §3.5 (14.11, второй заход) и что это даёт на самом деле
- **Шаг 1 — сделан:** поля кэша состояния сняты, §1.7.
- **Шаг 2 — сделан:** `DM_NATIVE_RC=2` (`dm/host/hle_dos2_native.c`): хук `ExecuteRenderCommand 0x93e5f0` (сверка 4 слов пролога, трамплин, оригинал
  исполняется). Раз в 10 с: `[native] render commands (last 10.0 s): N packets on T thread(s) [tid…]; length differs from the table in K; per opcode: 36:… 22:…(len a..b)`;
  расхождение длины с таблицей §1.5 — красная строка по коду. Умолчание — хука нет.
- **Шаг 3 (5a) — сделан в минимальном виде, умолчание 0:** `DM_NATIVE_DRAW` — хуки `0x928e80` / `0x928fb0` ставят скобки вокруг одного draw движка
  (`nvn_native_draw_begin/_end` в `hle_nvn.c`).
  - `=1`: все записи хоста внутри скобок (привязки, которые выдал сброс кэша, `SetRenderEnable`, сам draw) собираются в буфер потока и кладутся
    в поток команд **одной записью `OP_X_NATIVE_DRAW`** (полезная нагрузка = те же записи + `OP_END`); поток трансляции исполняет её на месте
    (`xbg_game.cpp`: `execute` вложенно). Порядок и семантика те же, что без переключателя.
  - `=2`: путь NVN как есть + перед каждым draw запись `OP_X_NATIVE_CHECK` с хэндлами текстур из кэша рендерера (стадии 0 и 1); поток трансляции
    сравнивает их со своей таблицей привязок: `[native] draw check: stage S slot I: renderer cache has …, the NVN binds left …` (первые 16) и
    сводка каждые 262 144 draw.
  - В обоих режимах: `[native] draws (… last 10.0 s): N engine draws, X host records and Y bytes a draw`.
- **Честная оценка 5a.** Запись-контейнер сама по себе **ускорения не даёт**: привязки на потоке трансляции — это запись в таблицу состояния
  (`state.tex/ub`), время уходит в `draw()` (пайплайн, дескрипторы, проход). Посылка «десятки записей на draw» не подтверждена: сброс
  инкрементный. Ценность сделанного — (а) измерение записей/байт на draw и гистограмма кодов; (б) проверка `=2`: если кэш рендерера всегда
  равен состоянию NVN, нативный бэкенд может читать текстуры прямо из `r`, а не вести свою таблицу; расхождения укажут, где NVN меняют мимо
  кэша (UI-блок, прямые draw проходов); (в) draw как единица в потоке — носитель для 5b.
- **Не проверено исполнением** (телефона нет): только сборка `dm` arm64. Риски `=1`: запись-контейнер до 4 КБ (больше — делится, счётчик
  `split`); хуки draw на горячем пути (2 вызова + TLS на draw).

**Крючки для 5b (планировщик проходов, следующий заход):**
- границы прохода: обработчики кодов 21 `0x93e6ac` / 22 `0x93efa8` → `0x9279a0` (SetRenderTargets), 5 `0x93f630` → `0x928be0`, 3 `0x93f268` → `0x928ab0`,
  4 `0x93f70c` (clear), 52 `0x93f654` → `0x920b00` (копия RT), 55 `0x93edac` (барьер), 43 `0x93f968` → `0x9290f0` (compute); `BeginFrame 0x9215f0`,
  `EndFrame 0x93ccd0`;
- хук `0x93e5f0` уже стоит (`DM_NATIVE_RC`): планировщику достаточно смотреть поток кодов в нём (режим `DM_NATIVE_RP=2`: считать, какие
  load/store он выбрал бы, и писать в поток записей подсказку перед `OP_SET_RT`; исполнять прежний путь);
- на стороне движка точка применения — начало прохода в `xbg_game.cpp` (`LastPass`, `lazy_clear`): подсказка заменяет эвристику
  `first_draw_covers` известным фактом «следующий код — clear / вложение дальше не читается».

## 4. Тайловые GPU (Mali вкл. PanVK, PowerVR, Xclipse вкл. RADV) — что делать в нативном бэкенде и в текущем хосте
Публичные источники: Arm *Mali GPU Best Practices Developer Guide*; Qualcomm *Adreno GPU Developer Guide (Vulkan / OpenGL ES)*; Imagination
*PowerVR Performance Recommendations* и *PowerVR Low-level GLSL Optimisation*; Khronos *Vulkan-Samples* (`render_passes`, `subpasses`, `msaa`,
`pipeline_barriers`, `layout_transitions`, `command_buffer_usage`, `pipeline_cache`, `16bit_arithmetic`); Samsung *Galaxy GameDev Vulkan
Usage Recommendations*; GDC/SIGGRAPH Arm «Moving Mobile Graphics».
- **loadOp/storeOp.** Смена RT (коды 21/22/5) = начало прохода. `CLEAR` вместо `ClearTexture`/`ClearDepthStencil` внутри прохода (код 3/4/5
  сразу после 21/22 → loadOp CLEAR; в текущем хосте это `LAZY_CLEAR`, у DOS2 `lazy_clear folded=0.00 flushed=3.0` в меню — **3 clear на кадр
  не сворачиваются**: разобрать, почему (вероятно clear без последующего draw в том же RT или другой RT) — дешёвая победа для всех GPU).
  `DONT_CARE` для depth, если проход дальше не читает его (типично depth основной сцены после пост-обработки); STORE `DONT_CARE`/`NONE` для
  вложений, которые после прохода не читаются (D16 `STORE_DEAD` — только с доказательством, иначе мусор).
- **Transient.** Depth/MSAA-вложения, живущие один проход: `TRANSIENT_ATTACHMENT` + память `LAZILY_ALLOCATED` (на Mali/PowerVR — ни байта
  в DRAM). Нужна карта жизни RT по кадру (кто читает как текстуру после) — собирается из потока кодов 21/22/15/28/33/52 за 1–2 кадра.
- **Меньше проходов.** 35 проходов в меню. Пары «RT A → RT B → снова A» рвут проход; на тайлерах каждый возврат = load+store всего A.
  Слияние соседних проходов с теми же вложениями (`tbdr_pass_merge.py` в `dm/gfx/tools` — офлайн-оценка по дампу) и subpass'ы для
  G-buffer → lighting (input attachments), если DOS2 рендерит отложенно (проверить по набору RT кода 21).
- **MSAA.** Resolve через `pResolveAttachments` в том же проходе (не `vkCmdResolveImage`) — на тайлерах бесплатно.
- **Барьеры.** Только фрагментные стадии внутри графики (`DM_GFX_TILE_BARRIER` D16), не `ALL_COMMANDS`; на Mali барьер к vertex-стадии
  сериализует тайлинг.
- **Точность.** `RelaxedPrecision` (mediump) только там, где Maxwell считал в fp16 (`HADD2/HMUL2` в шейдерах) — глобальное понижение уже
  отвергнуто (ETR `XLATE_REDUCED`, пропадает геометрия). Источник истины — офлайн-транслятор (`dmsh_xlate`), правка в паке шейдеров.
- **Вершины.** IDVS на Mali: позиция отдельным потоком — у DOS2 формат вершин задаёт игра (код 10); не трогать, но не раздувать (без лишних
  атрибутов при `VTX_RETYPE`).
- **AFBC/UBWC.** Без `STORAGE`/`MUTABLE_FORMAT` на RT, где можно (D16 `LEAN_USAGE`); PanVK — окно без AFBC (`DM_VK_PANVK_LINEAR`, DRV-08).
- **Xclipse.** Blend в статическом состоянии (EDS3 blend сломан, XCL-03), D24 → D32 (XCL-02), BC4–7 нет на стоке (XCL-01).
- **Что нужно от телефона:** на Mi 14 — модели `DM_GFX_SIM_GPU=mali|powervr|xclipse` (fps, вспышки), `DM_GFX_PASS_PROF="300 120 0"` +
  `tools/gpass_report.py` (цена каждого прохода, кандидаты на слияние); реальные Mali/PowerVR — только через тестовые сборки игрокам.

### 4.1 Сделано в текущем хосте (14.11, ветка `dos2-tile`; собрано, на телефоне не проверено)
Подробно — `DOS2_PORT.md`, раздел «Тайловая политика проходов». Кратко, что из списка выше уже в `xbg_game.cpp` (метки `[tile]`):
- **loadOp/storeOp:** `DM_GFX_CLEAR_FOLD` — ClearTexture (код NVN 38) и clear-only проходы становятся `loadOp CLEAR` следующего прохода с этой
  картинкой (те 3–4 несвёрнутых clear меню: это были 4 clear-only прохода `lazy_clear flushed=4` и ~11 ClearTexture с 22 полными барьерами);
  `DM_GFX_STORE_HIST` — `STORE DONT_CARE` для вложений, которые никто никогда не читал (история по картинке, а не доказательство «в этом
  кадре», как D16 `STORE_DEAD`), `=2` проверка, `=3` poison; `DM_GFX_NOLOAD` по умолчанию на Mali/PowerVR с отказами D16.
- **Барьеры:** `DM_GFX_TILE_BARRIER` перенесён из D16 (Mali/PowerVR).
- **Transient / MSAA:** только перепись (`transient_cand`, `msaa_passes`, `resolves` в `NVN PERF tile`).
- **Для 5b:** планировщику проходов в нативном бэкенде (подсказка перед `OP_SET_RT`, режим `DM_NATIVE_RP=2`) теперь есть куда класть знание:
  «следующий код — clear этого RT» = отложенный clear (`pclear_put`), «вложение дальше не читается» = бит DONT_CARE twin'а (`lazy_twin`,
  биты 18+k). Эвристики (`first_draw_covers`, история `STORE_HIST`) тогда заменяются фактом из потока кодов движка.

### 4.2 Граф проходов и дизайн слияний (14.11, ветка `dos2-merge`; собрано, на телефоне не проверено)
Подробно — `DOS2_PORT.md`, раздел «Граф проходов `DM_GFX_PASS_GRAPH`». Кратко:
- **Перепись (`DM_GFX_PASS_GRAPH=1`, умолчание 0):** хук `0x93e5f0` (§3.6) кладёт в поток команд `OP_X_ENGINE_MARK {код, младшие 32 бита
  списка}` перед кодами, способными закрыть проход (1, 3, 4, 5, 21, 22, 35, 40, 42, 43, 44, 46, 47, 52, 55, 56, 59, 61), и перед первым
  пакетом каждого списка (64); трансляция раз в 10 с пишет кадр целиком: проходы (список движка, вложения с load/store, draw, первый FS,
  входы с писателем и классом координат, причина конца: хостовая операция + коды движка с последнего draw), dispatch / копии, анализ
  `aa` / `aba exact|blocked(…)` и кандидаты `sub` (input attachment). Класс координат — статический разбор SPIR-V FS (`pgraph::spirv_coords`);
  на 76 FS «тот же пиксель» у DOS2 = texelFetch от `gl_FragCoord` через helper с uniform-частью (`fcu` 12), чистых `fc` нет.
- **A → B → A (шаг 2):** не look-ahead по записям NVN (неточно: состояние NVN наследуется, привязки по id пула разрешаются при трансляции),
  а **спекулятивная парковка прохода A на уровне Vulkan**: B пишется во вторичный CB, сброс (End A + Execute B) при первом нарушении
  (B трогает A, буферы, CPU-видимое, подача; draw A2 читает выход B); возврат того же `Pass` продолжает A без второго LOAD. Точность — по
  операциям, без предсказаний. Делать после цифр `summary aba= exact=` с телефона (стоит, если exact ≥ 2 на кадр с полноэкранными наборами).
- **Subpass (шаг 3, `DM_GFX_SUBPASS`, не сделан):** кандидаты `sub … fc|fcu adj=1`; нужен разбор uniform-части helper'а координат
  (`fcu`), затем двухсабпассовый проход + `OpImageFetch → OpImageRead(SubpassData)` в варианте FS. Только тайлеры (FN-24…28).
- **Для нативного бэкенда (5b):** маркеры — готовый канал «код движка → поток трансляции»; планировщику проходов достаточно расширить
  `p_engine_mark` (например, набор RT из пакета кодов 21/22), чтобы решать load/store и парковку по факту, а не по истории.

## 6. Термо-лестница на ADPF headroom (R2) — дизайн, точки хука найдены (14.11, ветка `dos2-drs`)
**Вход.** `perf_android.c` уже держит AThermal: `AThermal_getThermalHeadroom` (`T.headroom`, прогноз на 10 с; NaN при частом опросе),
слушатель статуса (`g_tstatus`, `dm_thermal_now()`) и ADPF-сессию CPU-подсказок (`APerformanceHint`, цель = период кадра). Лестнице нужен
только headroom: опрос ≤ 1 Гц из уже существующего потока подсказок (там счётчик кадров `wn`, раз в N кадров) или своего таймера; NaN —
пропуск шага. Сглаживание: EMA по 3 замерам.

**Ступени** (вниз — при headroom ≥ порога 2 замера подряд; вверх — только при headroom < порога − 0,1 в течение 20 с; не чаще одной
ступени в 10 с):
| headroom | ступень | точка в main 4979b200 | как |
|---|---|---|---|
| < 0,7 | 0: как задал игрок (`DM_DOS2_DRS`) | — | — |
| ≥ 0,7 | 1: потолок DRS 85 % | объект DRS `[main+0x2bbb198]` (+0x28/+0x2c текущий, +0x18/+0x1c шаг вверх) | `dm_dos2_drs_set_ceiling(85)` (hle_dos2_quality.c) — уже есть |
| ≥ 0,8 | 2: потолок 70 % + тени | GraphicSettings `[main+0x2bc0278]`: кандидаты +0x6f / +0x70 / +0x71 (ShadowsEnabled / PointLightShadows / ?) | запись байта в GraphicSettings; сначала доказать байт и что рендер перечитывает его каждый кадр (читатели 0xa4cee0, 0xa69438, 0xcb8f4c..) |
| ≥ 0,9 | 3: эффекты | Bloom +0x68 (читатель 0xab4690 / 0xab50b8), +0x64 пост-шейдер (0xab6e34 / 0xab6ec8 / 0xab6f80) | запись байта; проверить, что стадия не держит ресурсы под старое значение |
| ≥ 0,95 или статус SEVERE | 4: лимит fps | VSyncDivider +0x24 (уже 2 = 30 fps) / интервал окна NVN | на 30 fps уже стоит; дальше — только пропуск present на хосте (vulkan_present.cpp), не в игре |

**Гистерезис и защита.** Ступени 2–3 включать только после проверки на телефоне, что запись поля на лету безопасна (иначе — только на
загрузочном экране: объект DRS +0x48 = 1 при загрузке, 0x158cde8). Всё за `DM_DOS2_THERMAL` (0 — выкл.; по умолчанию выкл., пока не
проверено), тумблер в ⚙ (frontend-common) позже. Лог одной строкой на смену ступени: headroom, статус, ступень, текущий DRS, GPU мс
(`[[main+0x2bbdc68]+0x18f0]`).

## Эксперимент: `spirv-opt -O` для транслированных шейдеров (14.11.2026, гипотеза)
Конвейер `dm/gfx/tools/dmsh_vk_xc2.py` вызывает spirv-opt только для `--trim-capabilities` (и `-O` лишь в пробе топологии GS); оптимизирует
транслятор Ryujinx. Сравнение агента dos2-shsrc на 489 парах: транслированные VS в 4.6× длиннее нативных по SPIR-V (187 017 → 40 748 после

Проверка на телефоне: пак шейдеров с `-O` (300 МБ, только с согласия хозяина) против текущего — `create_ms` первых сборок пайплайнов,
`gpu_ms` в кампании (Turnip NIR и стоковый компилятор многое делают сами — выигрыш по GPU не гарантирован). При выигрыше и запрете на заливку
игровых файлов — SPIRV-Tools в APK: оптимизация бандла на устройстве при первой загрузке + кэш в `Android/data/<пакет>/files`.
